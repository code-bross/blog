Google AI Studio로 풀스택 Android 앱 만들기: Firestore와 Firebase AI Logic 살펴보기

November 18, 2026 · 4 min read
Way
Android Developer

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.
11월 17일에 공개된 Google AI Studio의 풀스택 Android 앱 빌드 기능에 대해 설명해드리겠습니다.

배경​

지금까지 Google AI Studio에서 만든 Android 앱은 로컬 세션 저장만 지원했습니다.
데이터를 기기 간에 동기화하거나 로그인 기능을 넣으려면 Firebase 프로젝트를 직접 만들고 연결해야 했습니다.
API 키를 APK 안에 넣으면 추출될 위험이 있어 Gemini 호출도 별도 서버 작업이 필요했습니다.
11월 17일 공개된 업데이트에서는 Build 에이전트가 이런 백엔드 설정을 대신 처리합니다.
Gemini 4 Carbon과 Hydrogen을 기반으로 프롬프트 하나로 풀스택 Kotlin 앱을 만들고 Play 스토어에 게시하는 흐름이 마련되었습니다.

Google AI Studio 풀스택 앱 살펴보기​

Cloud Firestore로 데이터 저장하기​

프롬프트에 데이터 저장이나 로그인, 생성형 AI 기능이 필요하다는 단서가 있으면 Build 에이전트가 요구 사항을 먼저 감지합니다.
사용자가 확인하면 에이전트가 Cloud Firestore 데이터베이스를 프로비저닝하고 앱의 데이터 모델에 맞는 Security Rules를 생성합니다.
오프라인 캐시가 포함되어 연결이 끊긴 동안의 변경 사항은 연결이 복원되면 자동으로 동기화됩니다.
태블릿에서 시작한 작업을 휴대전화에서 이어서 할 수 있습니다.

Firebase Authentication으로 로그인하기​

사용자 프로필이나 개인 작업 공간이 필요한 앱에는 Firebase Authentication이 Google Sign-In과 함께 설정됩니다.
사용자별 권한 규칙이 함께 적용되어 각 사용자는 자신의 문서만 읽고 쓸 수 있습니다.
로그인 UI와 토큰 관리를 직접 구현하지 않아도 됩니다.

Firebase AI Logic으로 Gemini 안전하게 호출하기​

APK 안에 API 키를 직접 넣으면 키가 추출될 수 있습니다.
Build 에이전트는 Firebase AI Logic을 설정하고 Firebase App Check를 적용합니다.
App Check는 Google Fraud Defense(구 reCAPTCHA Enterprise)로 요청이 변조되지 않은 정식 앱에서 왔는지 확인합니다.
자격 증명은 서버 쪽에 남아 있고, 앱에서는 키를 노출하지 않고 Gemini 모델을 호출합니다.
공식 블로그에 소개된 생성 코드는 다음과 같습니다.

// Generated by Google AI Studio Build agent using Firebase AI Logic & Cloud Firestore
class WorkoutRepository(context: Context) {
    private val generativeModel by lazy {
        Firebase.ai(backend = GenerativeBackend.googleAI())
            .generativeModel("gemini-4-hydrogen")
    }

    private val db = FirebaseFirestore.getInstance(
        context.applicationContext.getString(R.string.firestore_database_id)
    )

    suspend fun generateAndSaveWorkout(goal: String, uid: String) {
        val response = generativeModel.generateContent("Create a 20-minute workout for: $goal")
        val workout = hashMapOf(
            "ownerId" to uid,
            "goal" to goal,
            "plan" to (response.text ?: ""),
            "createdAt" to FieldValue.serverTimestamp()
        )
        db.collection("workouts").add(workout).await()
    }
}

Firebase.ai로 생성 모델을 만들고, 응답 텍스트를 Firestore 컬렉션에 저장하는 구조입니다.
ownerId를 함께 저장해 사용자별 문서 분리가 가능합니다.

HD 에뮬레이터와 스크린샷 디버깅​

브라우저 안의 Android 에뮬레이터가 더 빠르게 시작되고 HD 토글을 켜면 1200p 고화질 스트리밍으로 전환됩니다.
실시간 오디오 출력도 지원되어 음성 기반 기능이나 TTS, 미디어 앱을 브라우저 안에서 테스트할 수 있습니다.
에뮬레이터 툴바의 스크린샷 버튼을 누르면 실행 중인 화면을 캡처해 프롬프트에 바로 첨부할 수 있습니다.
레이아웃 간격이나 대비 같은 시각적인 수정 요청을 글로 설명하지 않고 화면으로 전달할 수 있습니다.
커스텀 폰트도 지원되어 Compose 테마에 원하는 서체를 적용할 수 있습니다.
내부적으로는 공식 Android CLI가 프로젝트 생성과 Gradle 빌드를 담당합니다.

개인 Play 라이브러리로 바로 게시하기​

지금까지 실기기에 앱을 설치하려면 USB 디버깅을 켜거나 서명 키스토어를 직접 관리해야 했습니다.
Google Play 연동을 이용하면 게시 패널에서 몇 번의 클릭으로 Play 계정을 설정할 수 있습니다.
AI Studio가 Android App Bundle(.aab)을 빌드하고 서명한 뒤 개인 Play 라이브러리에 바로 게시합니다.
일반 Google 계정으로 이용할 수 있고, 휴대전화에 바로 설치해 테스트할 수 있습니다.

실무 관점​

생성된 코드는 프로토타입이나 MVP를 빠르게 만드는 데 적합합니다.
실제 서비스에 쓰려면 생성된 Security Rules가 데이터 모델과 권한 정책을 정확히 반영하는지 직접 검토해야 합니다.
백엔드가 Cloud Firestore와 Firebase Authentication으로 고정되므로, 나중에 다른 백엔드로 옮기려면 데이터 계층을 다시 작성해야 합니다.
자동 테스트와 CI/CD, UX 품질 검토는 아직 수동 작업으로 남아 있습니다.
개인 Play 라이브러리 게시는 정식 Play Console 배포와 다르므로, 상용 배포 전에는 스토어 정책과 심사 절차를 별도로 확인해야 합니다.

마치며​

프롬프트 하나로 데이터 저장과 로그인, 안전한 Gemini 호출까지 갖춘 Kotlin 앱을 만들 수 있게 되었습니다.
프로토타입 단계의 반복 속도를 높이는 데 유용한 업데이트입니다.

KMP 모듈에 Swift 패키지 의존성 추가하기

November 17, 2026 · 4 min read
Way
Android Developer

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.
Kotlin 2.5.0-RC에서 시도해 볼 수 있는 KMP 모듈의 SwiftPM import 기능에 대해 설명해드리겠습니다.

배경​

KMP 프로젝트에서 iOS 쪽 네이티브 SDK를 쓰려면 지금까지 CocoaPods 의존성을 연결하거나 cinterop 정의를 직접 작성해야 했습니다.
CocoaPods 방식은 별도 설정이 많고, Swift 패키지를 그대로 가져오는 방법이 마땅하지 않았습니다.
Kotlin 2.5.0-RC부터는 SwiftPM import 기능을 이용해 Swift 패키지를 Gradle 빌드 스크립트에서 직접 선언할 수 있습니다.
SwiftPM 의존성의 Objective-C API를 Kotlin 코드에서 바로 호출할 수 있게 됩니다.

SwiftPM import 살펴보기​

플러그인 버전 설정하기​

SwiftPM import를 쓰려면 Kotlin Multiplatform Gradle 플러그인 2.5.0-RC가 필요합니다.
Version Catalog에서는 다음과 같이 버전을 지정합니다.

[versions]
kotlin = "2.5.0-RC"

[plugins]
kotlin-multiplatform = { id = "org.jetbrains.kotlin.multiplatform", version.ref = "kotlin" }

Swift 패키지 선언하기​

SwiftPM 의존성은 Apple 타겟을 선언한 build.gradle.kts 안의 swiftPMDependencies 블록에 추가합니다.
예시로 FirebaseAnalytics를 가져오는 설정은 다음과 같습니다.

kotlin {
    iosArm64()
    iosSimulatorArm64()
    swiftPMDependencies {
        // FirebaseAnalytics를 Kotlin 코드로 가져옵니다
        swiftPackage(
            url = url("https://github.com/firebase/firebase-ios-sdk.git"),
            version = from("12.5.0"),
            products = listOf(product("FirebaseAnalytics")),
        )
    }
}

버전은 from으로 시작 버전을 지정하거나, exact로 정확한 버전을 지정할 수 있습니다.
브랜치나 특정 리비전을 지정하는 방식도 함께 제공됩니다.

Clang 모듈 가져오기​

SwiftPM import는 Clang 모듈을 가져오는 방식으로 동작합니다.
기본값으로는 지정한 Swift 패키지 안의 Clang 모듈을 자동으로 찾아 Kotlin 코드에서 쓸 수 있게 합니다.
자동 탐색을 끄려면 discoverClangModulesImplicitly를 false로 바꾸고, 제품 이름을 Clang 모듈 이름으로 씁니다.
모듈 이름이 제품 이름과 다르면 importedClangModules로 직접 지정합니다.
예를 들어 FirebaseFirestore의 Objective-C API는 FirebaseFirestoreInternal 모듈에 들어 있습니다.

kotlin {
    swiftPMDependencies {
        discoverClangModulesImplicitly = false
        swiftPackage(
            url = url("https://github.com/firebase/firebase-ios-sdk.git"),
            version = from("12.5.0"),
            products = listOf(
                product("FirebaseAnalytics"),
                product("FirebaseFirestore"),
            ),
            importedClangModules = listOf(
                "FirebaseAnalytics",
                "FirebaseFirestoreInternal",
            ),
        )
    }
}

플랫폼 제한 두기​

일부 SwiftPM 의존성은 모든 타겟에서 빌드되지 않습니다.
예를 들어 Google Maps SDK는 현재 iOS 타겟만 지원합니다.
iOS만 타겟으로 한다면 따로 지정할 필요가 없지만, macOS 같은 타겟을 추가하면 제품마다 플랫폼을 지정해야 합니다.

kotlin {
    iosArm64()
    iosSimulatorArm64()
    macosArm64()
    swiftPMDependencies {
        swiftPackage(
            url = url("https://github.com/googlemaps/ios-maps-sdk.git"),
            version = exact("10.3.0"),
            products = listOf(
                product(
                    "GoogleMaps",
                    platforms = setOf(iOS()),
                ),
            ),
        )
    }
}

Xcode 프로젝트와 연결하기​

SwiftPM 의존성을 처음 추가하면 Xcode 프로젝트와 생성된 패키지를 연결해야 합니다.
다음 Gradle 태스크를 실행하면 SwiftPM 패키지가 생성되고 Xcode 프로젝트가 함께 변경됩니다.

XCODEPROJ_PATH='/path/to/project/iosApp/iosApp.xcodeproj' ./gradlew :kotlin-library:integrateLinkagePackage

생성된 패키지와 변경된 Xcode 프로젝트는 저장소에 함께 커밋합니다.
그 뒤로는 의존성 목록이나 버전이 바뀔 때마다 합성 패키지가 자동으로 갱신됩니다.

Kotlin 코드에서 호출하기​

가져온 Objective-C API는 swiftPMImport로 시작하는 네임스페이스에 들어 있습니다.
네임스페이스는 Gradle 그룹 이름과 프로젝트 이름을 이어서 만듭니다.
iosMain 소스 세트에서 Firebase API를 쓰는 예시는 다음과 같습니다.

import swiftPMImport.groupName.subproject.FIRAnalytics
import swiftPMImport.groupName.subproject.FIRApp

fun logAppOpen() {
    FIRApp.configure()
    FIRAnalytics.logEventWithName("app_open", parameters = null)
}

버전 잠금 파일 관리하기​

SwiftPM import 도구는 의존성 버전을 고정하기 위해 Package.resolved 파일을 만듭니다.
기본값으로는 모든 서브프로젝트의 잠금 파일이 .swiftpm-locks/default/swiftImport 안의 하나의 파일로 합쳐집니다.
잠금 파일은 저장소에 커밋해 모든 빌드가 같은 버전을 쓰게 합니다.
서브프로젝트별로 잠금 파일을 나누려면 packageResolvedSynchronization에 그룹 식별자를 지정합니다.
잠금 파일을 강제로 갱신하려면 빌드 디렉터리와 기존 Package.resolved 파일을 지운 뒤 다음 태스크를 실행합니다.

./gradlew :yourModuleName:fetchSyntheticImportProjectPackages

알고 있어야 할 제한 사항​

동적 Kotlin/Native 프레임워크를 만들 때는 SwiftPM import가 모든 경우를 지원하지 않습니다.
빌드 오류나 런타임 경고가 나오면 프레임워크 연결 방식을 정적으로 바꾸는 것이 일반적인 해결 방법입니다.

kotlin {
    listOf(
        iosArm64(),
        iosSimulatorArm64()
    ).forEach { iosTarget ->
        iosTarget.binaries.framework {
            baseName = "Shared"
            isStatic = true
        }
    }
}

실무 관점​

MTS 앱에 적용한다면, iOS 쪽에서만 쓰는 SDK부터 SwiftPM import로 옮겨 보는 것이 안전합니다.
CocoaPods 의존성을 함께 쓰고 있다면, 두 방식이 같은 SDK를 중복으로 가져오지 않는지 먼저 확인해야 합니다.
Package.resolved 잠금 파일과 생성된 패키지는 저장소에 커밋해 팀 빌드와 CI 빌드가 같은 버전을 쓰게 합니다.
Kotlin 2.5.0-RC는 정식 출시 전 단계이므로, 프로덕션 적용보다 별도 브랜치에서의 검증이 먼저입니다.

마치며​

SwiftPM import를 쓰면 Swift 패키지를 Gradle 빌드 스크립트에서 직접 선언해 KMP 모듈에서 쓸 수 있습니다.
CocoaPods 설정과 cinterop 정의를 줄이고, 버전 잠금까지 Gradle 안에서 관리할 수 있게 됩니다.

Kotlin 2.5.0-RC 살펴보기: 동반자 객체 없이 쓰는 동반자 블록과 확장

November 16, 2026 · 3 min read
Way
Android Developer

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.

11월 11일에 공개된 Kotlin 2.5.0-RC의 동반자 블록과 동반자 확장에 대해 설명해드리겠습니다.
동반자 블록과 동반자 확장은 Kotlin 2.5.0-RC의 새로운 기능에 포함된 실험적 기능입니다.

배경​

타입 이름으로 접근하는 멤버를 선언하려면 동반자 객체가 필요했습니다.
동반자 객체가 없는 타입에는 이런 멤버를 확장으로 추가할 방법이 없었습니다.
팩토리 함수나 상수를 타입 이름 아래에 두고 싶어도 동반자 객체를 먼저 만들어야 했습니다.
동반자 블록과 동반자 확장은 이 제약을 없애는 기능입니다.

동반자 블록과 확장 살펴보기​

동반자 블록​

동반자 블록은 클래스나 인터페이스 안에 companion 블록을 직접 작성하는 방식입니다.
별도의 객체 인스턴스를 만들지 않고 멤버를 선언할 수 있습니다.
JVM에서는 정적 멤버로 생성되므로 JvmStatic 애너테이션이 필요 없습니다.

data class Vector(val x: Double, val y: Double) {
    companion {
        val Zero: Vector get() = Vector(0.0, 0.0)
    }
}

fun main() {
    println(Vector.Zero) // Vector(x=0.0, y=0.0)
}

동반자 확장​

동반자 확장은 최상위 확장에 companion 변경자를 붙이는 방식입니다.
확장 대상 타입에 동반자 객체가 없어도 타입 이름으로 접근하는 멤버를 선언할 수 있습니다.
타입을 직접 제어하지 않는 경우에도 멤버를 추가할 수 있습니다.

import kotlin.math.cos
import kotlin.math.sin

companion val Vector.UnitX get() = Vector(1.0, 0.0)

companion fun Vector.unit(angle: Double) = Vector(cos(angle), sin(angle))

fun main() {
    println(Vector.UnitX) // Vector(x=1.0, y=0.0)
}

사용 설정​

실험적 기능이므로 컴파일러 옵션을 추가해야 합니다.
동반자 블록만 쓰려면 다음 옵션을 사용합니다.

kotlin {
    compilerOptions {
        freeCompilerArgs.add("-Xcompanion-blocks")
    }
}

동반자 확장까지 쓰려면 다음 옵션을 사용합니다.

kotlin {
    compilerOptions {
        freeCompilerArgs.add("-Xcompanion-blocks-and-extensions")
    }
}

동반자 확장을 사용하면 컴파일러가 정식 출시 전 바이너리를 생성합니다.
그래서 동반자 확장을 쓰는 라이브러리는 기능이 정식화되기 전까지 의존성으로 소비할 수 없습니다.
설계 배경은 동반자 블록과 확장 소개 글에서 확인할 수 있습니다.

실무 관점​

MTS에서는 화면 상태나 요청 파라미터를 타입 이름 아래의 팩토리 함수로 만드는 경우가 많습니다.
동반자 블록을 쓰면 동반자 객체 선언 없이 이런 팩토리를 정리할 수 있습니다.
다만 실험적 기능이므로 앱 모듈에서 먼저 검증하고, 라이브러리 모듈에는 적용하지 않는 것이 좋습니다.
특히 동반자 확장은 바이너리 호환성에 영향을 주므로 공유 모듈에서는 피해야 합니다.

마치며​

동반자 블록과 동반자 확장은 동반자 객체 없이 타입 이름으로 접근하는 멤버를 선언하는 방식을 제공합니다.
팩토리 함수와 상수 정리가 간결해집니다.

Kotlin 2.5.0-RC 살펴보기: 여러 프로퍼티를 갖는 전체 값 클래스

November 16, 2026 · 3 min read
Way
Android Developer

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.

11월 11일에 공개된 Kotlin 2.5.0-RC의 전체 값 클래스에 대해 설명해드리겠습니다.
전체 값 클래스는 실험적 기능으로, 여러 프로퍼티를 하나의 값으로 묶는 방식을 제공합니다.

배경​

기존 인라인 값 클래스는 하나의 프로퍼티만 가질 수 있었습니다.
여러 값을 묶어야 할 때는 일반 클래스나 데이터 클래스를 사용해야 했습니다.
데이터 클래스는 같은 데이터를 가진 인스턴스라도 참조가 다르면 별개로 구분될 수 있습니다.
값 자체가 본질인 타입에서는 이 참조 구분이 불필요한 제약이 됩니다.
전체 값 클래스는 이런 경우를 위해 프로퍼티 전체가 값이 되는 타입을 제공합니다.

전체 값 클래스 살펴보기​

기본 선언​

전체 값 클래스는 value class 키워드로 선언합니다.
프로퍼티를 여러 개 가질 수 있고, 컴파일러가 equals와 hashCode, toString을 자동으로 생성합니다.
이 점은 데이터 클래스와 비슷합니다.
다만 componentN 함수는 생성되지 않습니다.
대신 이름 기반 구조 분해를 사용합니다.
copy 함수는 제공되지 않으며, 향후 복사 변수 기능으로 대체될 예정입니다.

value class Complex(val real: Double, val imaginary: Double)

fun main() {
    val complex = Complex(1.0, 2.0)
    val (val real, val imaginary) = complex
    println(real)
    println(imaginary)
}

이름 기반 구조 분해에서는 변수 이름이 프로퍼티 이름과 일치해야 합니다.
순서가 바뀌어도 이름이 같으면 올바른 값이 들어갑니다.
이 문법은 2.5.0-RC에서 기본 동작이 되었습니다.

추상 값 클래스​

전체 값 클래스는 추상 클래스로 선언할 수도 있습니다.
인터페이스와 달리 모든 하위 클래스가 실행하는 초기화 로직을 정의할 수 있습니다.
다음 예시에서는 시작 값이 끝 값보다 크지 않은지 생성 단계에서 검증합니다.

sealed value class OrderedInterval<T : Comparable<T>> protected constructor(
    start: T,
    end: T,
) {
    init {
        require(start <= end)
    }
}

value class IntInterval(
    val start: Int,
    val end: Int
) : OrderedInterval<Int>(start, end)

값 객체​

프로퍼티가 없는 전체 값 클래스는 값 객체라고 부릅니다.
하나의 값만 가질 수 있는 상태를 표현할 때 사용합니다.
다음 예시에서는 조회 결과를 찾음과 찾지 못함으로 나눕니다.

sealed interface UserResponse

value class UserFound(val userName: String) : UserResponse
value object UserUnknown : UserResponse

사용 설정​

전체 값 클래스는 실험적 기능이므로 컴파일러 옵션을 추가해야 합니다.
build.gradle.kts에 다음과 같이 작성합니다.

kotlin {
    compilerOptions {
        freeCompilerArgs.add("-Xfull-value-classes")
    }
}

자세한 내용은 Kotlin 2.5.0-RC의 새로운 기능에서 확인할 수 있습니다.

실무 관점​

MTS에서는 금액과 통화를 함께 다루는 타입이 많습니다.
이런 복합 값을 전체 값 클래스로 표현하면 참조 구분에 의존하는 실수를 줄일 수 있습니다.
다만 아직 실험적 기능이고 RC 단계이므로, 프로덕션 모듈에 바로 적용하기보다는 별도 브랜치에서 검증하는 것이 좋습니다.
정식 출시 이후 안정화 여부를 다시 확인해야 합니다.

마치며​

전체 값 클래스는 여러 프로퍼티를 하나의 값으로 묶는 방식을 제공합니다.
데이터 클래스와 비슷하지만 참조 구분이 없는 점이 다릅니다.

Ktor 3.6.1 살펴보기: Android 엔진 크래시 수정과 연결 관리 개선

November 15, 2026 · 3 min read
Way
Android Developer

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.

10월 29일에 공개된 Ktor 3.6.1에 대해 설명해드리겠습니다.
3.6.0 이후 나온 패치 릴리스로, 연결 관리와 요청 취소, 스트리밍, 웹소켓을 중심으로 수정이 들어갔습니다.

배경​

Ktor 클라이언트는 안드로이드 앱에서 네트워크 계층으로 널리 쓰입니다.
3.6.0이 9월에 나온 뒤 한 달 만에 3.6.1 패치가 이어졌습니다.
기능 추가보다는 엔진 동작을 바로잡는 수정이 중심입니다.
안드로이드 엔진과 관련된 크래시 수정이 세 건 포함되어 있어 실무에서 바로 확인이 필요합니다.

Ktor 3.6.1 살펴보기​

Android 엔진 수정​

이번 패치에서 안드로이드 엔진과 직접 관련된 수정은 세 가지입니다.
첫 번째는 응답 읽기 취소 시 크래시가 나는 문제입니다.
두 번째는 메인 스레드에서 채널을 닫아 NetworkOnMainThreadException이 나는 문제입니다.
세 번째는 플러그인 실행 중 로거 초기화로 DiskReadViolation이 나는 문제입니다.
세 가지 모두 요청 취소와 스레드 경계에서 발생합니다.
취소 경로를 자주 타는 화면에서는 릴리스 전에 동작을 확인할 필요가 있습니다.

CIO 엔진과 연결 관리​

CIO 엔진에서는 TLS 종료 과정의 경합이 수정되었습니다.
close_notify가 마지막 레코드와 동시에 쓰이면서 TLS 출력과 메모리 풀이 손상되는 문제였습니다.
응답을 쓰기 전에 실패한 keep-alive 연결이 멈추는 문제도 고쳐졌습니다.
CPU 부하가 높을 때 서버가 빈 응답으로 연결을 닫는 문제도 함께 수정되었습니다.
클라이언트 쪽에서는 연결 누수 수정이 포함되었습니다.

리다이렉트와 HTTP 규정 준수​

리다이렉트 처리에서는 상대 경로의 점 세그먼트가 정규화되지 않는 문제가 수정되었습니다.
If-None-Match가 있을 때 If-Modified-Since를 무시하도록 ETag 동작이 바뀌었습니다.
3.6.0에서 사라졌던 잘못된 경로에 대한 BadRequestException도 다시 던져집니다.
이 항목들은 서버 동작에 가깝지만, 클라이언트가 받는 응답을 해석하는 기준과 이어집니다.

네이티브 소켓과 Netty​

네이티브에서 허용된 TCP 소켓에 TCP_NODELAY가 기본으로 켜지지 않는 문제가 수정되었습니다.
JVM과 달리 네이티브에서는 작은 패킷이 Nagle 알고리즘 때문에 지연될 수 있었습니다.
Netty에서는 delay 호출 성능이 개선되었습니다.
두 항목 모두 지연 시간에 직접 영향을 주는 변경입니다.

버전 올리기​

Version Catalog에서 버전을 교체하면 패치를 적용할 수 있습니다.

[versions]
ktor = "3.6.1"

[libraries]
ktor-client-core = { module = "io.ktor:ktor-client-core", version.ref = "ktor" }
ktor-client-android = { module = "io.ktor:ktor-client-android", version.ref = "ktor" }
ktor-client-content-negotiation = { module = "io.ktor:ktor-client-content-negotiation", version.ref = "ktor" }
ktor-client-logging = { module = "io.ktor:ktor-client-logging", version.ref = "ktor" }
ktor-serialization-kotlinx-json = { module = "io.ktor:ktor-serialization-kotlinx-json", version.ref = "ktor" }

Android 엔진으로 클라이언트를 만드는 예시는 다음과 같습니다.

val client = HttpClient(Android) {
    install(ContentNegotiation) {
        json()
    }
    install(Logging) {
        logger = Logger.DEFAULT
        level = LogLevel.INFO
    }
}

실무 관점​

패치 릴리스라도 네트워크 계층 변경은 검증 없이 올리지 않는 것이 안전합니다.
이번 패치에서는 요청 취소 경로와 연결 누수가 핵심입니다.
화면 이탈 시 요청을 취소하는 흐름이 있다면 취소 후 크래시가 나지 않는지 확인합니다.
장시간 유지되는 연결이 있는 화면에서는 연결 수 변화를 함께 봅니다.
StrictMode를 켠 디버그 빌드에서 디스크 읽기 위반이 사라졌는지도 확인합니다.

마치며​

3.6.1은 기능을 더하는 릴리스가 아니라 동작을 바로잡는 릴리스입니다.
안드로이드 엔진 크래시 수정이 포함되어 있어 클라이언트 버전을 올릴 때 우선 검토할 만합니다.

Mika는 11월 초 GitHub Trending Kotlin 부문 1위에 오른 온디바이스 AI 에이전트입니다.

배경​

기존 AI 어시스턴트는 대부분 채팅 안에서 답변을 돌려주는 데 머물렀습니다.
앱을 직접 조작하려면 앱마다 API를 연동해야 했고, API가 없는 앱은 자동화 대상에서 제외되었습니다.
Mika는 이 지점을 다르게 접근합니다.
앱의 API를 쓰지 않고 화면을 사람처럼 읽고 버튼을 직접 누릅니다.
공개된 지 2주 남짓 만에 스타 8천 개를 넘겼습니다.

Mika 살펴보기​

백그라운드 화면​

Mika는 앱을 보이지 않는 백그라운드 화면에서 실행합니다.
사용자는 자기 화면을 그대로 쓰면서 에이전트에게 일을 맡길 수 있습니다.
작업을 지켜보고 싶을 때는 작은 실시간 화면을 눌러 확인합니다.
대화 도중 말을 걸면 작업에 추가 지시를 하거나 중단할 수 있습니다.

무선 디버깅과 접근성 서비스​

백그라운드 화면을 쓰려면 두 가지 준비가 필요합니다.
먼저 안드로이드에 내장된 무선 디버깅을 이용해 작은 헬퍼를 실행합니다.
다음으로 접근성 서비스를 켜서 화면을 읽고 탭과 입력을 수행합니다.
설정은 한 번만 하면 되고 3분에서 5분 정도 걸립니다.
앱 조작에는 안드로이드 12 이상이 필요하고, 안드로이드 14 이상을 권장합니다.
채팅과 웹, 파일 작업만 쓴다면 안드로이드 11에서도 동작합니다.

Ask 모드와 안전장치​

기본값은 Ask 모드입니다.
돈이 드는 일은 실행 전에 사용자에게 확인을 받습니다.
장바구니에는 담지만 결제 직전에는 멈춥니다.
로그인과 인증 코드, 결제는 사용자에게 넘깁니다.
자율 실행을 원하면 Autonomous 모드로 바꿀 수 있습니다.

스킬과 컴퓨터 연동​

완료한 작업은 스킬로 저장되어 다음에는 더 빠르고 안정적으로 처리됩니다.
컴퓨터에서도 CLI와 MCP로 Mika에 작업을 넘길 수 있습니다.
CLI는 HTTP 작업 API를 호출하며, 전화기 쪽에서 실제 실행을 담당합니다.

mika devices --json
mika connect --device SERIAL --json
mika doctor --device SERIAL --json

연결에는 ADB가 필요하고, 패키지 이름은 com.wangzan101.mika입니다.

프라이버시 구조​

Mika 서버는 없습니다.
화면 내용과 대화는 설정한 모델 제공자에게만 전달됩니다.
API 키와 기억은 전화기 안에서 암호화되어 저장됩니다.
대화와 실행 기록은 기기에 남고, 업데이트 확인만 GitHub에 연결합니다.
모델은 DeepSeek과 OpenAI, Gemini, Anthropic 등을 고를 수 있습니다.

실무 관점​

금융 앱에서 접근성 서비스 기반 자동화를 검토할 때는 두 가지를 주의해야 합니다.
먼저 타사 앱과 웹사이트를 자동으로 조작하면 해당 서비스의 이용 약관에 어긋날 수 있습니다.
다음으로 결제와 인증 같은 민감한 단계는 자동화 대상에서 빼는 것이 안전합니다.

Kotlin 2.5.0-RC 살펴보기: 이름 기반 구조 분해와 정식 출시 전 점검 사항

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.

11월 11일에 공개된 Kotlin 2.5.0-RC에 대해 설명해드리겠습니다.

배경​

Kotlin 2.5.0은 12월 정식 출시를 앞두고 있습니다.
10월 21일에 나온 Beta2에 이어 11월 11일에 RC가 공개되었습니다.
RC는 정식 출시 직전 단계로, 새 기능이 동결되고 안정화 작업이 중심이 됩니다.
이번 RC에서 가장 주목할 변화는 이름 기반 구조 분해의 안정화입니다.

Kotlin 2.5.0-RC 살펴보기​

이름 기반 구조 분해​

기존 구조 분해는 위치 기반으로 동작했습니다.
데이터 클래스의 프로퍼티 순서가 바뀌면 변수에 들어가는 값이 함께 바뀌었습니다.
이름 기반 구조 분해에서는 변수 이름이 프로퍼티 이름과 일치해야 합니다.
순서가 바뀌어도 이름이 같으면 올바른 값이 들어갑니다.

data class Person(val name: String, val age: Int)

val person = Person("way", 33)
val (name, age) = person
val (age, name) = person // 순서가 달라도 이름으로 매칭됩니다

2.5.0에서는 새 문법을 추가 설정 없이 사용할 수 있습니다.
컴파일러는 기존 위치 기반 코드에 대해 마이그레이션 힌트도 함께 제공합니다.
위치 기반이 꼭 필요한 경우에는 대괄호 문법을 사용합니다.

val pair = "way" to 33
val [first, second] = pair

미사용 반환값 검사​

반환값을 무시한 호출을 찾아주는 검사가 추가되었습니다.
실수로 결과를 확인하지 않은 호출을 컴파일 단계에서 발견할 수 있습니다.
Json.encodeToString 같은 호출의 결과를 쓰지 않고 넘기는 경우에 경고를 받을 수 있습니다.

JDK 17 요구 사항​

Beta2부터 JDK 17보다 낮은 버전으로 컴파일러를 실행하면 오류가 발생합니다.
Android Studio는 이미 JDK 17을 내장하고 있어 대부분은 영향이 없습니다.
CI 환경에서 별도 JDK를 지정하고 있다면 버전을 확인해야 합니다.

그 외 변경 사항​

Java 28을 지원합니다.
Swift Export가 새로운 DSL과 함께 베타 단계에 들어갔습니다.
Kotlin/Native 증분 컴파일이 Apple 타겟에서 기본으로 활성화되었습니다.
멀티 필드 값 클래스가 알파 단계로 추가되었습니다.
Lombok의 @Builder 애너테이션은 Kotlin 코드에서 비활성화되었습니다.
Android 프로젝트의 kotlin 블록 안에서 sourceSets를 쓰는 기존 방식이 deprecation 대상으로 지정되었습니다.

RC 적용하기​

Version Catalog에서 Kotlin 버전을 교체하면 RC를 적용할 수 있습니다.

[versions]
kotlin = "2.5.0-RC"

[plugins]
kotlin-android = { id = "org.jetbrains.kotlin.android", version.ref = "kotlin" }

실무 관점​

RC는 프로덕션 적용 대상이 아닙니다.
별도 브랜치에서 빌드와 테스트를 먼저 확인하는 것이 좋습니다.
JDK 버전과 KAPT 사용 여부를 함께 점검해야 합니다.
KAPT를 사용하는 프로젝트라면 릴리스 노트에 정리된 변경 사항을 함께 확인하는 것이 좋습니다.
정식 출시는 12월로 예정되어 있습니다.

마치며​

Kotlin 2.5.0-RC는 이름 기반 구조 분해를 안정화하고, 정식 출시를 위한 마지막 점검 단계에 들어갔습니다.
12월 정식 출시 전에 미리 적용해 보고, JDK 17 요구 사항과 마이그레이션 힌트를 확인해 두는 것이 좋습니다.

11월 10일에 공개된 kotlinx.serialization 1.13.0에 대해 설명해드리겠습니다.

배경​

kotlinx.serialization은 Kotlin 공식 직렬화 라이브러리입니다.
10월 19일에 나온 1.12.0에서는 Json의 예외 처리 방식이 크게 바뀌었습니다.
1.13.0은 그 변경을 철회하고 성능을 개선하는 릴리스입니다.
Kotlin 2.4.10을 기반으로 합니다.

kotlinx.serialization 1.13.0 살펴보기​

1.12.0 예외 처리 변경 철회​

1.12.0에서는 Json 포맷이 직렬화와 역직렬화 도중에 발생하는 거의 모든 예외를 가로챘습니다.
가로챈 예외는 JSON 경로와 입력 정보를 담은 JsonException으로 감싸졌습니다.
예외를 한 가지 형태로 통일하면 catch 작성이 예측 가능해진다는 취지였습니다.
그러나 변경의 영향이 과소평가되었고, 1.13.0에서는 이 변경이 철회되었습니다.
1.12.0에서 새 동작에 의존한 코드가 있다면 1.13.0에서는 이전 동작으로 돌아갑니다.

@Serializable
data class Account(val id: String, val balance: Long)

try {
    val account = Json.decodeFromString<Account>("""{"id": "A001"}""")
} catch (e: JsonException) {
    // 1.12.0에서는 대부분의 예외가 JsonException으로 감싸졌지만
    // 1.13.0에서는 이 변경이 철회되어 이전 동작으로 돌아갑니다
}

JsonElement.toString 성능 개선​

JsonElement.toString 구현이 새로 작성되었습니다.
일부 벤치마크에서는 기존보다 약 2배 빨라졌습니다.
서버 응답을 로그로 남기거나 디버깅용 문자열을 자주 만드는 코드에서 효과가 있습니다.

1.12.0에서 함께 안정화된 API​

1.13.0은 작은 릴리스이지만, 직전 버전인 1.12.0에서 안정화된 API를 함께 정리합니다.
JsonNamingStrategy와 ContextualSerializer, @KeepGeneratedSerializer와 @SerialInfo가 안정 API가 되었습니다.
kotlin.time.Instant와 kotlin.uuid.Uuid 직렬화도 실험 애너테이션이 제거되었습니다.
CBOR 포맷은 메모리 사용량이 줄었고, Protobuf 포맷은 알 수 없는 필드를 보관했다가 다시 전송하는 기능을 받았습니다.

1.13.0 적용하기​

Version Catalog에서 버전을 교체하면 1.13.0을 적용할 수 있습니다.

[versions]
kotlinx-serialization = "1.13.0"

[libraries]
kotlinx-serialization-json = { module = "org.jetbrains.kotlinx:kotlinx-serialization-json", version.ref = "kotlinx-serialization" }

[plugins]
kotlin-serialization = { id = "org.jetbrains.kotlin.plugin.serialization", version.ref = "kotlin" }
plugins {
    alias(libs.plugins.kotlin.serialization)
}

dependencies {
    implementation(libs.kotlinx.serialization.json)
}

실무 관점​

1.12.0에서 예외 처리 동작에 의존한 코드가 있다면 1.13.0으로 올릴 때 catch 로직을 다시 확인해야 합니다.
JsonDecodingException의 경로 정보를 활용하던 코드라면 동작 변경 여부를 테스트로 확인하는 것이 좋습니다.
성능 개선은 별도 설정 없이 버전만 올려도 적용됩니다.

마치며​

1.13.0은 1.12.0의 예외 처리 변경을 철회하고, JsonElement.toString 성능을 끌어올린 릴리스입니다.
버전만 올리면 되지만, 예외 처리 동작이 되돌아간 만큼 catch 로직은 한 번 확인하는 것이 좋습니다.

Kotlin Toolchain 0.13 — 새 KMP 프로젝트는 kotlin new로 시작하기

October 8, 2026 · 3 min read
Way
Android Developer

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.
JetBrains가 공개한 Kotlin Toolchain 0.13에 대해 설명해드리겠습니다.

배경​

신규 Kotlin Multiplatform(KMP) 프로젝트를 시작할 때는 Gradle 설정 파일을 손으로 짜는 것부터 시작하는 경우가 많았습니다.
JDK나 Android SDK 같은 필수 도구가 갖춰져 있지 않으면, 새 노트북에서 프로젝트를 처음 열었을 때 동기화부터 실패하곤 했습니다.
이번 0.13부터 JetBrains는 신규 KMP 프로젝트에 이 툴체인을 쓰는 것을 공식 권장 경로로 제시했습니다.
자세한 내용은 Kotlin 블로그 원문에서 확인할 수 있습니다.

Kotlin Toolchain 살펴보기​

Kotlin Toolchain은 JVM·Android·iOS·멀티플랫폼·서버 앱을 하나의 CLI 진입점으로 만들고, 빌드하고, 테스트하고, 배포하는 도구입니다.
필수 도구들을 선언적 설정에 맞춰 자동으로 내려받아 주기 때문에 온보딩 과정의 마찰이 크게 줄어듭니다.

kotlin new: 대화형 프로젝트 생성​

0.13의 핵심은 kotlin new 명령입니다.
웹의 KMP Wizard처럼 앱 유형을 고르고 타깃 플랫폼을 선택하면 프로젝트가 생성됩니다.
기존 kotlin init도 같은 흐름으로 맞췄는데, 차이는 kotlin init이 현재 디렉터리에 바로 파일을 만든다는 점입니다.

# 새 프로젝트 생성 (대화형)
kotlin new

# 이미 설치돼 있다면 업데이트
kotlin update

Android 개발자 관점에서 달라진 부분​

  • Android SDK 자동 프로비저닝이 IDE까지 확장: 이전에는 kotlin build/kotlin run 때만 SDK가 자동 설치돼서, 빌드 전에 IDE로 먼저 열면 SDK 누락 오류가 났습니다. 이제 프로젝트 import 시점에도 누락된 SDK 컴포넌트를 자동으로 받아 줍니다.
  • namespace/applicationId 검증 강화: com.example.app 같은 샘플 ID로 실수로 배포 빌드를 만드는 실수를 막아 줍니다.
  • 다운로드 진행 표시: JDK, Android SDK, iOS 런타임, 컴파일러 다운로드가 CLI에 진행 바로 표시됩니다.

Swift Package Manager 의존성 지원​

Apple 타깃에서 SPM 패키지를 선언적으로 가져올 수 있게 됐습니다.
설정 파일에 저장소와 버전을 적으면 됩니다.

dependencies:
  - swiftPackage:
      repository: "https://github.com/firebase/firebase-ios-sdk.git"
      version: "12.17.0"
      products: ["FirebaseCore", "FirebaseFirestore", "FirebaseAnalytics"]

가져온 Objective-C API는 swiftPMImport 접두사로 네임스페이스가 붙어, Kotlin 코드에서 명시적으로 구분됩니다.
로컬 SPM 패키지는 localSwiftPackage 키로 연결할 수 있습니다.

빌드 속도: Kotlin/Native 컴파일러 캐시​

Kotlin/Native 재빌드가 빨라집니다.
컴파일된 네이티브 의존성을 빌드 간, 심지어 프로젝트 간에 캐시로 재사용하고, 프로젝트 코드는 파일 단위 캐시로 링크 시 바뀐 부분만 다시 컴파일합니다.
기존 settings.kotlin.compileIncrementally 설정을 그대로 쓰고, .klib 컴파일 자체는 전체로 수행됩니다.

그 외 변경 사항​

  • IDE 동기화 상태를 에디터에서 확인할 수 있게 됐습니다.
  • 멀티플랫폼 라이브러리 배포 시 Compose Resources와 SwiftPM 의존성 메타데이터가 아티팩트와 함께 게시되고, 서드파티 멀티플랫폼 라이브러리의 Compose Resources도 해석됩니다.
  • AI 에이전트 연동도 강화됐습니다. Compose Hot Reload MCP 서버와 Kotlin용 에이전트 스킬(npx skills add kotlin/kotlin-agent-skills)이 제공됩니다.
  • IDE 기능은 IntelliJ IDEA 2026.2.3 또는 Android Studio Rabbit 1(2026.2.1) 이상에서 최신 Kotlin Toolchain 플러그인과 함께 쓸 수 있습니다.

실무에서 주의할 점​

기존 Gradle 기반 프로젝트를 당장 마이그레이션해야 하는 것은 아닙니다.
JetBrains도 로드맵에서 Gradle 프로젝트의 공백을 먼저 메우는 데 집중하겠다고 밝혔습니다.
따라서 운영 중인 프로젝트는 기존 흐름을 유지하고, 신규 프로젝트나 사이드 프로젝트부터 적용해 보는 것이 안전합니다.

마치며​

새로 KMP를 시작한다면 kotlin new 한 번으로 Android·iOS 환경을 한 번에 맞추는 경험은 꽤 매력적입니다.
다음에 KMP 프로젝트를 시작할 일이 있으면 이 경로로 시작해 보시기 바랍니다.

Kotlin 2.5.0-Beta2 살펴보기 — 이름 기반 구조 분해와 JDK 17 요구 사항

2026년 10월 21일에 공개된 Kotlin 2.5.0-Beta2에 대해 설명해드리겠습니다.
안정 버전은 12월 공개가 목표입니다.

배경​

구조 분해는 data class의 프로퍼티를 순서대로 꺼내는 문법입니다.
프로퍼티 순서가 바뀌면 같은 타입의 값이 서로 뒤바뀌는 실수가 생깁니다.
이름으로 꺼내는 방식이 2.3.20부터 실험 기능으로 제공됐고, Beta2에서 안정화됐습니다.
컴파일러 실행에 JDK 17 이상이 필요해진 점도 함께 정리했습니다.

Kotlin 2.5.0-Beta2 살펴보기​

이름 기반 구조 분해가 안정화됐습니다​

only-syntax 모드에서 새 문법이 기본값이 됐습니다.
기존 문법은 위치 기준으로 동작합니다.
새 문법은 괄호 안에 val을 넣어 이름을 기준으로 꺼냅니다.
변수 이름은 프로퍼티 이름과 일치해야 하며, 순서는 달라도 됩니다.

data class Account(val owner: String, val balance: Long)

fun printAccount(account: Account) {
    // 기존 문법: 위치 기준으로 꺼냅니다
    val (owner, balance) = account
    println("$owner: $balance")
}

fun printAccountByName(account: Account) {
    // 새 문법: 이름 기준으로 꺼냅니다
    // 순서를 바꿔도 같은 프로퍼티가 들어갑니다
    (val balance, val owner) = account
    println("$owner: $balance")
}

향후 버전에서는 기존 괄호 문법도 이름 기준으로 동작할 예정입니다.
자세한 전환 계획은 The Road to Name-Based Destructuring에서 확인할 수 있습니다.

사용하지 않은 반환값 검사가 추가됐습니다​

반환값을 무시하고 함수를 호출하면 컴파일러가 이를 알려주는 검사가 들어갔습니다.
결과를 확인하지 않고 넘어가는 실수를 줄이는 목적입니다.
Beta 단계에서는 검사가 동작하는 범위를 확인하면서 적용하는 것이 좋습니다.

컴파일러 실행에 JDK 17이 필요합니다​

Beta1에서는 JDK 17보다 오래된 JDK로 컴파일러를 실행하면 경고가 나왔습니다.
Beta2부터는 오류가 발생합니다.
이전 JDK를 임시로 계속 쓰는 플래그가 제공됩니다.
MTS 빌드 환경의 JDK 버전을 먼저 확인합니다.

[versions]
kotlin = "2.5.0-Beta2"
kotlin {
    jvmToolchain(17)
}

그 밖의 변경점​

Java 28을 지원합니다.
Swift export가 새로운 DSL과 함께 Beta 단계에 들어갔습니다.
Kotlin/Native 증분 컴파일이 Apple 대상에서 기본으로 켜졌습니다.
컴파일 타임 상수가 개선됐고, companion 확장과 full value class가 실험 기능으로 들어왔습니다.
자세한 목록은 Kodee's Kotlin Roundup에서 확인할 수 있습니다.

실무 관점​

Beta 버전이므로 운영 코드에 바로 적용하지 않습니다.
이름 기반 구조 분해는 새 코드부터 적용해보고, 기존 구조 분해는 순서를 바꿀 때만 확인합니다.
CI의 JDK 버전을 17 이상으로 맞추지 않으면 빌드가 실패합니다.
안정 버전은 12월 공개가 목표이므로, 그때 다시 정리하겠습니다.

마치며​

이름 기반 구조 분해가 안정화돼 순서 실수를 줄일 수 있게 됐습니다.
JDK 17 요구 사항만 미리 확인하면 12월 안정 버전 전환이 수월해집니다.

네이티브 크래시를 잡는 릴리스 — CameraX 1.7.0-rc01 들여다보기

October 22, 2026 · 3 min read
Way
Android Developer

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.
2026년 10월 21일에 공개된 CameraX 1.7.0-rc01의 릴리스 노트를 정리해드리겠습니다.

현재 상황​

CameraX는 카메라 기능을 단말 파편화 없이 구현할 수 있게 돕는 Jetpack 라이브러리입니다.
신분증 촬영, 얼굴 인증처럼 금융 앱에서도 카메라 기능은 흔하게 쓰입니다.
반면 카메라 파이프라인의 네이티브 영역에서 발생하는 크래시는 재현이 어렵고 대응 비용이 큽니다.
이번 rc는 그런 네이티브 크래시 수정과 API 정리에 무게가 실린 릴리스입니다.

CameraX 1.7.0-rc01 살펴보기​

네이티브 SIGSEGV 크래시 수정​

SurfaceProcessor가 입력 SurfaceTexture를 해제하는 시점에, 연결된 SurfaceRequest가 먼저 가비지 컬렉션되면 네이티브 SIGSEGV가 발생하던 버그가 수정되었습니다.
타이밍에 의존하는 문제라 특정 단말과 특정 시나리오에서만 나타나고, 주로 크래시 리포트에서만 보이는 유형입니다.
이펙트나 필터로 SurfaceProcessor를 직접 다루는 앱이라면 이번 수정이 반가울 것입니다.

Surface 누수와 OpenGL 크래시 수정​

CameraEffect의 executor나 HandlerThread가 SurfaceOutput이 닫히기 전에 종료되면, Surface 누수와 네이티브 OpenGL 크래시가 발생하던 문제가 수정되었습니다.
카메라 파이프라인의 종료 순서가 리소스 정리와 직결된다는 점을 보여주는 사례입니다.

Camera2Interop — 인터페이스에서 추상 클래스로 전환​

UseCaseCamera2Interop, ImageCaptureCamera2Interop, SessionConfigCamera2Interop, CameraControlCamera2Interop이 인터페이스에서 추상 클래스로 바뀌었습니다.
소스 호환성에 영향을 줄 수 있는 변경이니, interop 클래스를 직접 참조하는 코드가 있다면 1.7.0 적용 전에 컴파일을 확인해야 합니다.
한편 1.7.0-alpha03부터는 Kotlin DSL 확장 블록으로 interop을 쓰는 방식이 권장되고 있습니다.

// 1.7.0-alpha03부터 권장되는 방식 — Kotlin DSL 확장 블록
val preview = preview {
    camera2Interop {
        // Camera2 설정을 이 블록 안에 지정합니다
    }
}

Low Light Boost와 Torch — last setting wins​

저조도 부스트와 토치를 동시에 켜려고 하면 요청이 거부되던 동작이 바뀌었습니다.
이제는 마지막에 설정한 쪽이 이기는 방식으로 동작합니다. 하나를 켜면 다른 하나가 자동으로 꺼집니다.
저조도 부스트가 켜진 상태에서도 촬영 시 플래시가 터지도록 함께 개선되었습니다.

물리 카메라에 UseCase 바인딩​

CameraInfo.getPhysicalCameraInfos()에서 얻은 물리 카메라의 CameraSelector로 UseCase를 바인딩할 수 있게 되었습니다.
물리 CameraSelector로 CameraInfo를 조회하면 논리 카메라가 아닌 물리 카메라의 정보가 반환됩니다.
멀티 카메라 단말에서 특정 렌즈를 직접 다루는 기능에 활용할 수 있습니다.

의존성 선언​

[versions]
camerax = "1.7.0-rc01"

[libraries]
camerax-core = { module = "androidx.camera:camera-core", version.ref = "camerax" }
camerax-camera2 = { module = "androidx.camera:camera-camera2", version.ref = "camerax" }
camerax-lifecycle = { module = "androidx.camera:camera-lifecycle", version.ref = "camerax" }

androidx.lifecycle:lifecycle-runtime 의존성은 2.10.0으로 올라갔습니다.
번들로 제공되는 lifecycle runtime lint 검사가 AGP 9.5.0-alpha04 이상에서 동작하려면 이 버전이 필요합니다.

실무 관점​

신분증 촬영이나 얼굴 인증 흐름이 있는 MTS 앱에서는 네이티브 크래시 수정이 안정성 지표에 직결됩니다.
interop 클래스 변경은 컴파일 단계에서 바로 드러나니, Camera2를 직접 건드리는 코드가 있다면 마이그레이션 계획을 먼저 세우는 편이 좋습니다.
아직 rc 단계이므로 프로덕션 적용은 stable 승격을 기다리는 것이 안전합니다.

마치며​

이번 rc는 기능 추가보다 안정화와 API 정리에 무게가 실린 릴리스입니다.
카메라 기능을 쓰는 앱이라면 릴리스 노트를 한 번 읽어두는 것만으로도 대응 비용을 줄일 수 있습니다.

DataStore 1.3.0이 준비 중인 것들 — Tink 암호화와 새로운 Builder API

October 21, 2026 · 4 min read
Way
Android Developer

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.
최근 30일 내 릴리스 중 하나를 골라 심화 해설을 하겠습니다.
DataStore 1.3.0-rc01(2026년 10월 12일)까지 이어진 1.3.0 라인의 변경 사항을 정리해드리겠습니다.

현재 상황​

DataStore 1.2.1은 안정 채널의 최신입니다.
그 위로 1.3.0 라인이 alpha 단계를 거치며 2026년 10월 12일 rc01에 도달했습니다.
rc01 자체는 버그 수정 위주이지만, 1.3.0이 안정으로 오면 두 가지 큰 변화가 함께 옵니다.
Tink 기반 암호화 지원과 새로운 Builder API입니다.
두 기능 모두 alpha07(2026년 3월 11일)에 이미 확정된 내용입니다.

DataStore 1.3.0 살펴보기​

datastore-tink 아티팩트와 AeadSerializer​

새 아티팩트 androidx.datastore:datastore-tink가 추가되었습니다.
핵심 클래스는 AeadSerializer로, 기존 Serializer<T>를 감싸는 래퍼입니다.
내부는 Tink의 AEAD(Authenticated Encryption with Associated Data)로 암호화·복호화를 수행합니다.
JVM과 Android 타깃 모두에서 사용할 수 있습니다.
공식 문서의 사용 순서는 세 단계입니다.

// 1. Tink API로 키 생성
val keysetHandle =
    AndroidKeysetManager.Builder()
        .withSharedPref(applicationContext, "keyset", "keyset_prefs")
        .withKeyTemplate(KeyTemplate.createFrom(PredefinedAeadParameters.AES256_GCM))
        .withMasterKeyUri("android-keystore://master_key")
        .build()
        .keysetHandle

// 2. 기존 serializer를 감싸는 AeadSerializer 생성
val aeadSerializer = AeadSerializer(
    aead = keysetHandle.getPrimitive(
        RegistryConfiguration.get(),
        Aead::class.java,
    ),
    wrappedSerializer = ExistingSerializer,
    // ciphertext swapping 공격 방지를 위한 고유 이름
    associatedData = "settings.json".encodeToByteArray(),
)

// 3. 기존 serializer 대신 aeadSerializer로 DataStore 생성
val dataStore = dataStore(
    fileName = "settings.json",
    serializer = aeadSerializer,
    scope = scope,
)

마스터 키는 Android Keystore에 두는 패턴이 권장됩니다.
associatedData에는 파일마다 고유한 이름을 넣어, 암호문을 서로 바꿔치기하는 공격을 막습니다.
alpha10에서는 GeneralSecurityException이 CorruptionException으로 감싸지도록 바뀌었습니다.
암호화 실패가 DataStore의 CorruptionHandler 흐름에 자연스럽게 녹아들게 된 것입니다.

DataStore.Builder<T> — DataStoreFactory의 후계자​

DataStore.Builder<T>가 DataStoreFactory의 공식 대체 API로 도입되었습니다.
공식 릴리스 노트는 모든 사용자에게 Builder로의 마이그레이션을 권장합니다.
가장 큰 차이는 스코프 전달 방식입니다.
Builder는 CoroutineScope가 아니라 CoroutineContext를 요구합니다.
호출자가 viewModelScope 같은 짧은 생명주기의 스코프를 넘겨도, DataStore가 그 생명주기에 묶이지 않게 하려는 설계입니다.
구조적 동시성(structured concurrency) 관점에서 올바른 방향입니다.
또한 setCorruptionHandler로 손상 시 처리 로직을 직접 주입할 수 있게 되었습니다.
alpha09에서는 ReThrowCorruptionHandler가 public으로 공개되기도 했습니다.

웹 플랫폼 지원 (alpha08)​

DataStore가 웹 타깃 지원을 넓혔습니다.
WebOpfsStorage로 OPFS(Origin Private File System)를 지원합니다.
크로스탭 알림은 BroadcastChannel, 분산 락은 Web Locks API를 씁니다.
WebLocalStorage와 WebSessionStorage API로 저장소 타입도 명시적으로 관리할 수 있습니다.

rc01에서 바뀐 것​

1.3.0-rc01의 API 변경은 소규모입니다.
EdgeToEdge#enable() 대신 WindowCompat#enableEdgeToEdge(Window)를 쓰도록 정리되었습니다.
lifecycle-runtime 의존성이 2.10.0으로 올라갔는데, 이는 AGP 9.5.0-alpha04 이상에서 번들된 lifecycle lint 검사가 동작하기 위한 요구사항입니다.

의존성 선언​

# libs.versions.toml 예시
[versions]
datastore = "1.3.0-rc01"

[libraries]
datastore = { module = "androidx.datastore:datastore", version.ref = "datastore" }
datastore-tink = { module = "androidx.datastore:datastore-tink", version.ref = "datastore" }

실무 관점​

Builder에 넘기는 CoroutineContext에는 반드시 Job이 있어야 하고, 애플리케이션 스코프여야 합니다.
공식 문서의 Warning에도 명시된 대로, 컨텍스트가 취소되면 DataStore 내부 동작이 중간에 멈춥니다.
viewModelScope를 그대로 넘기는 실수를 하지 않도록 주의해야 합니다.
Tink 도입 시에는 associatedData를 파일명과 일치시켜 관리하는 규칙을 팀에 정해 두는 것이 좋습니다.
민감 데이터 저장소가 늘어나면 키 로테이션 정책도 함께 논의해야 합니다.

마치며​

DataStore 1.3.0은 저장(암호화)과 생성(Builder API) 두 축을 한 번에 끌어올립니다.
안정 릴리스 전에 Tink 암호화 대상 데이터와 Builder 전환 범위를 정리해 두시기 바랍니다.

Remote Compose 1.0.0-alpha21 — 10월 AndroidX 릴리스에서 본 서버 구동 UI의 현재 위치

October 12, 2026 · 5 min read
Way
Android Developer

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.
최근 공개된 Remote Compose 1.0.0-alpha21을 중심으로 10월 AndroidX 릴리스를 설명해드리겠습니다.

배경​

2026년 10월 7일, AndroidX 정기 릴리스 배치가 나왔습니다.
그중에서도 눈에 띄는 건 remote-compose 1.0.0-alpha21과 compose.remote.foundation 1.0.0-alpha04입니다.
Remote Compose는 서버 구동 UI(Server-Driven UI)를 위한 Jetpack 라이브러리이며, 에이전트가 만든 UI를 앱 업데이트 없이 내려받아 그리는 흐름과 맞닿아 있습니다.
같은 배치의 Compose 1.13.0-beta01은 이제 Kotlin 2.2를 타깃으로 하며 kotlinc 2.2를 요구합니다.
appfunctions 1.0.0-alpha13은 API 리네임이 있어, AppFunction 어노테이션이 AppFunctionDeclaration으로 바뀌었습니다.
collection 1.7.0 스테이블에는 ScatterMap 성능 개선과 원시 타입 리스트 정렬/이진 탐색 추가가 있습니다.

Remote Compose 1.0.0-alpha21 살펴보기​

테마 인식 원격 색상​

RemoteColor.Companion에 createThemedRemoteColor가 추가됐습니다.
서버에서 내려받은 문서가 클라이언트의 라이트/다크 테마를 따라 색상을 바꿀 수 있게 되는 것입니다.
서버 구동 UI에서 가장 자주 요구되는 다크 모드 대응을 플레이어 쪽이 해결해 주니, 문서 생성 로직에서 분기할 필요가 줄어듭니다.

텍스트 측정 API​

RemoteTextMeasurer와 rememberRemoteTextMeasurer가 새로 들어왔습니다.
Remote Compose 문서 안에서 텍스트의 실제 렌더링 크기를 잴 수 있게 된 것으로, 문서 생성 시점에 텍스트 길이에 따라 레이아웃을 조정해야 하는 경우(예: 배지, 동적 라벨) 유용합니다.
Float.rsp/RemoteFloat.rsp 확장 프로퍼티도 추가돼서 Sp 단위의 RemoteTextUnit을 리터럴이나 동적 표현식에서 바로 만들 수 있습니다.

문서 생성·미리보기 개선​

  • RemoteDocumentPreview에 profile 파라미터가 생겼습니다. 문서 버퍼를 팽창시키기 전에 설정을 조정할 수 있어, 테스트·디버깅 환경에서 문서 생성을 세밀하게 제어할 수 있습니다.
  • 플레이어와 테스트 프로파일이 DrawTextOnCircle을 지원합니다. 원형 경로에 텍스트를 그리는 연출이 이제 원격 문서에서도 깨지지 않습니다.
  • DEFLATE로 압축된 문서를 플레이어가 로드할 수 있게 됐습니다. 문서 크기가 크다면 전송량을 줄이는 방향으로 설계할 여지가 생깁니다.
  • captureSingleRemoteDocument/captureRemoteDocument의 라이프사이클과 스냅샷 처리가 다져졌고, 수집 속도가 리컴포지션을 따라가지 못할 때 업데이트가 조용히 누락되던 버그도 수정됐습니다. 서버 구동 UI에서 가끔 화면이 안 바뀌는 식의 간헐적 이슈가 줄어들 것으로 보입니다.
  • 커스텀 진입/종료 가시성 애니메이션 지원, 스프링 애니메이션의 스냅·범위 이탈 버그 수정 등 렌더링 품질 쪽도 여러 건 잡혔습니다.

compose.remote.foundation 1.0.0-alpha04​

같은 배치에 androidx.compose.remote.foundation의 새 알파가 같이 나왔습니다.
의존성은 다음과 같이 선언합니다.

dependencies {
    implementation("androidx.compose.remote.foundation:foundation:1.0.0-alpha04")
}

같이 나온 것들​

  • Compose 1.13.0-beta01 (animation/foundation/material/runtime): 이번 배치부터 라이브러리들이 Kotlin 2.2를 타깃으로 하고 kotlinc 2.2를 요구합니다. 베타를 올릴 때는 Kotlin 버전을 2.2 이상으로 올려야 컴파일이 됩니다.
  • appfunctions 1.0.0-alpha13: @AppFunction → @AppFunctionDeclaration, ObserveAppFunctionsEvent → AppFunctionsChangeEvent로 리네임됐고, 접근 레벨 제한을 위한 @AppFunctionAccessLevel이 추가됐습니다. 에이전트·Gemini 시대의 앱 기능 노출 인터페이스라 실험 중이라면 이름 바뀐 것만 확인하면 됩니다.
  • collection 1.7.0 (스테이블): toOrderedScatterSet() 확장(빈 소스에선 할당 없는 싱글턴 반환), ScatterMap.getOrPut() 최적화, Float 키 해시 충돌 개선, 원시 타입 리스트(IntList/LongList 등)에 sortWith/sortBy/binarySearch 추가. 퍼포먼스에 민감한 데이터 구조를 쓰는 팀은 별도 변경 없이 이득을 볼 수 있습니다.
  • benchmark 1.6.0-alpha01: :lockClocks 태스크가 root 없이도 고정 성능 모드를 쓸 수 있게 돼서, 더 많은 실기기에서 안정적인 마이크로벤치마크가 가능합니다. 힙 프로파일링용 MemoryProfilingConfig도 추가됐습니다.

실무에서 주의할 점​

  • Remote Compose는 아직 알파입니다. API가 바뀔 수 있다는 전제로 실험·프로토타입 수준에서 접근하는 게 맞습니다. 다만 테마 인식, 텍스트 측정, 압축 문서 로딩처럼 운영에 쓰려면 꼭 있어야 할 기능들이 차례로 들어오고 있어서, 방향성 자체는 꽤 진지하게 보입니다.
  • 에이전트 시대의 SDUI: 최근 Android CLI와 에이전트 스킬 흐름과 맞물려, 에이전트가 생성한 UI를 어떻게 앱에 그릴 것인가가 실무 질문이 되고 있습니다. Remote Compose는 그 답 중 하나입니다. 당장 도입하지 않더라도 개념과 플레이어 구조는 한 번 훑어둘 만합니다.
  • Compose 1.13 베타 + Kotlin 2.2: 컴파일러 버전 요구사항이 같이 올라간 릴리스라서, 버전만 올렸다가 빌드가 깨지는 경우가 생길 수 있습니다. 베타를 쓸 거면 libs.versions.toml의 Kotlin 버전도 함께 올립니다.
  • appfunctions 리네임: 알파 실험 중이라면 컴파일 에러가 나는 게 정상이니, 이름만 바꿔 주면 됩니다.

당장은 프로덕션 도입이 아니라 관측 모드입니다.
스프린트 사이에 작은 실험 프로젝트 하나로 Remote Compose 플레이어에 문서 하나 띄워 보는 것 정도가 적당합니다.
관전 포인트는 두 가지입니다.

  1. 서버에서 보낸 문서가 다크 테마에서 깨지지 않는지 (createThemedRemoteColor 사용)
  2. 텍스트 길이 가변적인 배지 UI를 RemoteTextMeasurer로 제대로 그릴 수 있는지
// gradle/libs.versions.toml
[versions]
androidxRemoteCompose = "1.0.0-alpha21"
composeRemoteFoundation = "1.0.0-alpha04"

에이전트가 UI를 만드는 시대가 오고 있는데, 어떻게 그릴 것인가는 여전히 앱 개발자의 몫입니다.
Remote Compose가 그 몫을 나눠 가질 후보 중 하나라는 점에서, 이번 릴리스는 지켜볼 가치가 있습니다.

마치며​

10월 AndroidX 배치는 UI를 코드가 아니라 문서로 다루는 쪽으로 축이 이동하고 있음을 보여줍니다.
Remote Compose 알파21의 변경점 대부분이 렌더링 품질과 운영 편의(테마, 압축, 측정)에 집중돼 있다는 점이 그 신호이며, 다음에 SDUI를 고민할 때 선택지에 넣어두기 좋은 타이밍입니다.

Compose 1.13.0-beta01 정리 — Dp.Unspecified가 리컴포지션을 막던 버그 수정

October 8, 2026 · 3 min read
Way
Android Developer

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.
2026년 10월 7일 공개된 Compose 1.13.0-beta01에 대해 설명해드리겠습니다.

배경​

Compose의 stable 채널 최신 버전은 1.12.1이고, 1.13은 베타 단계에 있습니다.
이번 글에서는 Compose Runtime 릴리스 노트를 기준으로, runtime에서 실무에 닿는 변경만 추려서 정리하겠습니다.
특히 공용 컴포넌트를 많이 사용하는 코드베이스에서는 리컴포지션 관련 수정이 체감 성능에 영향을 줄 수 있습니다.

Compose 1.13.0-beta01 살펴보기​

Kotlin 2.2 타깃으로 상향​

1.13부터 Compose 라이브러리는 Kotlin 2.2를 타깃으로 빌드되며, kotlinc 2.2가 필요합니다.
버전 카탈로그에서 Compose BOM만 올리는 습관이 있다면, Kotlin 플러그인 버전이 뒤처진 모듈에서 먼저 걸릴 수 있으니 함께 확인하는 것이 좋습니다.

Dp.Unspecified를 받는 컴포저블이 스킵되지 않던 버그​

Float.NaN이나 Double.NaN을 인자로 받는 @Composable은 인자가 그대로여도 스킵되지 않고 매번 리컴포지션되는 버그가 있었습니다.
Dp.Unspecified가 내부적으로 Float.NaN 기반이기 때문에, 선택적 간격이나 크기를 Dp.Unspecified 기본값으로 받는 공용 컴포넌트가 조용히 리컴포지션 비용을 치르고 있었던 것입니다.

// 이런 공용 컴포넌트가 인자 변화가 없어도 스킵되지 않을 수 있었다
@Composable
fun PriceRow(
    label: String,
    topPadding: Dp = Dp.Unspecified
) { /* ... */ }

사내 디자인 시스템처럼 공용 컴포넌트에 Dp.Unspecified 기본값이 흔한 코드베이스라면, 1.13 stable이 나올 때 체감 성능이 좋아질 수 있습니다.

computedStateOf 계산 블록은 읽기 전용으로 강제​

computedStateOf의 계산 블록 안에서 상태에 쓰면 이제 IllegalStateException이 발생합니다.
기존에 계산 블록 안에서 쓰기까지 하던 코드가 있었다면 런타임에서 바로 드러나므로, 베타를 올리는 모듈부터 확인이 필요합니다.

그 외 버그 픽스​

  • CompositionObserver가 컴포지션 패스마다 한 번만 해석되고, 교체는 다음 패스부터 적용됩니다. movable content 삽입 시에도 begin/end 콜백이 보고됩니다.
  • movableContent 이동 시 래퍼 그룹 슬롯이 남아 있던 LinkComposer 메모리 누수를 고쳤습니다.
  • lifecycle-runtime 의존성이 2.10.0으로 올라갔습니다. 번들된 lifecycle lint 검사는 AGP 9.5.0-alpha04 이상과 맞물려 있으니, AGP 베타 채널을 쓰는 프로젝트는 같이 보는 것이 좋습니다.
  • ComposeTracer를 메인 스레드 밖에서도 쓸 수 있게 됐습니다.

실무에서 주의할 점​

1.12.1 stable은 1.12.0에서 변경이 없는 버전이라, 운영 앱은 stable 유지가 무난합니다.
베타는 성능 검증이 필요한 화면 위주로 먼저 올려 보고, 앱 전체 확대는 stable 이후가 안전합니다.
공용 컴포넌트를 많이 쓰는 MTS 특성상 리컴포지션 이슈가 체감되는 화면부터 적용해 보는 것이 좋습니다.

마치며​

이번 베타의 핵심은 Dp.Unspecified 기본값을 받는 공용 컴포넌트의 불필요한 리컴포지션을 막은 수정입니다.
stable이 공개되면 공용 컴포넌트 비중이 높은 프로젝트부터 우선 적용해 보시기 바랍니다.

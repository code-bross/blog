Android CLI 1.1 살펴보기 — 델타 설치와 Compose 트레이싱

November 21, 2026 · 4 min read
Way
Android Developer

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.
2026년 11월에 공개된 Android CLI 1.1.16919734에 대해 설명해드리겠습니다.

배경​

Android CLI는 터미널에서 Android 개발을 수행하는 공식 CLI입니다.
Android Studio를 열지 않고 빌드와 설치, 프로파일링, 기기 제어를 처리할 수 있습니다.
에이전트와 함께 쓰는 개발 흐름을 염두에 두고 만들어졌고, 스크립트와 CI에서도 그대로 쓸 수 있습니다.
2026년 11월 릴리스는 설치 속도와 프로파일링, 스크립트 친화성이 중심입니다.
새 명령이 추가된 릴리스가 아니라, 매일 쓰는 명령이 더 빠르고 정확해진 릴리스입니다.

Android CLI 1.1 살펴보기​

델타 설치로 재배치된 파일 재전송 방지​

android install과 android run은 변경되지 않은 파일을 다시 보내지 않습니다.
이번 릴리스에서는 APK 안에서 위치만 바뀐 파일도 재전송 대상에서 제외됩니다.
파일 내용이 그대로인데 위치만 이동한 경우, 설치 과정에서 다시 전송할 필요가 없어졌습니다.
반복 설치가 많은 개발 과정에서 체감되는 개선입니다.
기존 동작이 필요하면 --use-delta-install-instructions=COPY,DATA 옵션을 전달합니다.

android run
android install app-debug.apk

Compose 트레이싱으로 리컴포지션 원인 찾기​

android profiler systemtrace에 Compose 트레이싱이 들어왔습니다.
--enable=compose.composition을 전달하면 실행된 컴포저블 함수마다 슬라이스를 기록합니다.
--enable=compose.recomposition을 전달하면 리컴포지션을 일으킨 상태 읽기와 쓰기까지 함께 기록합니다.
앱에는 androidx.compose.runtime:runtime-tracing 1.13 이상이 필요합니다.
트레이스는 ZIP 파일로 저장되며, Android Studio 프로파일러에서 열어 확인할 수 있습니다.

android profiler systemtrace --enable=compose.recomposition

Perfetto 힙 덤프로 메모리 살펴보기​

android profiler heapdump capture에 --type=perfetto 옵션이 추가되었습니다.
Perfetto 트레이스 형태로 힙 덤프를 기록하며, 객체와 객체 사이의 참조를 포함합니다.
값 자체는 포함하지 않기 때문에 .hprof 파일보다 크기가 작습니다.
Android 12(API 31) 이상에서 동작하며, 프로파일이 가능하거나 디버깅이 가능한 앱이 필요합니다.
메모리 누수나 힙 증가를 살펴볼 때 가벼운 대안이 됩니다.

android profiler heapdump capture --type=perfetto

스크립트 친화적인 출력 형식​

android analyze --format=json의 출력 형식이 바뀌었습니다.
라이브러리 아티팩트(AAR, JAR)의 dexSizeBytes 필드는 이제 64비트 정수를 문자열로 직렬화합니다.
d8CompileResult와 r8CompileResult에 모두 적용됩니다.
JSON을 파싱하는 스크립트에서는 숫자가 아니라 문자열로 받는 점을 반영해야 합니다.
android input 하위 명령도 결과를 통일된 JSON 객체로 출력합니다.
표준 출력에는 results 목록이 나오고, 일치하는 요소가 없거나 여러 개가 일치하는 실패는 각 결과의 status 필드에 기록됩니다.
표준 에러의 텍스트를 파싱하지 않아도 결과를 처리할 수 있습니다.

android analyze --format=json app-debug.aab
android input tap text=Submit

에뮬레이터 명령의 종료 코드​

android emulator create와 start, stop, remove가 실패 시 0이 아닌 종료 코드를 반환합니다.
오류는 표준 에러로 출력됩니다.
이전에는 실패해도 스크립트에서 알아채기 어려웠던 경우가 있었습니다.
CI에서 에뮬레이터를 만들고 지우는 단계가 있다면, 종료 코드만으로 실패를 감지할 수 있습니다.

android emulator create --name test
android emulator start --name test

실무 관점​

국내 MTS 프로젝트에 적용한다면, 델타 설치 개선은 별도 설정 없이 바로 체감할 수 있습니다.
Compose 트레이싱을 쓰려면 runtime-tracing 의존성을 추가하고 Compose 1.13 이상을 사용해야 합니다.
리컴포지션 원인을 찾는 디버깅 단계에서만 켜고, 평소에는 끄는 것이 좋습니다.
android analyze 결과를 파싱하는 스크립트가 있다면 dexSizeBytes가 문자열로 바뀐 점을 먼저 확인합니다.
에뮬레이터를 다루는 CI 스크립트는 종료 코드 기반으로 실패 처리를 정리할 수 있습니다.

마치며​

Android CLI 1.1은 눈에 띄는 새 기능보다 매일 쓰는 명령의 완성도를 높인 릴리스입니다.
설치가 빨라지고, Compose 성능 원인을 터미널에서 바로 찾을 수 있게 되었습니다.

SDK Platform Tools 37.0.3 살펴보기 — QR 무선 페어링과 adb install 변경

November 20, 2026 · 3 min read
Way
Android Developer

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.
2026년 11월에 공개된 SDK Platform Tools 37.0.3에 대해 설명해드리겠습니다.
이번 릴리스는 무선 페어링 개선과 adb 설치 명령 변경이 중심입니다.

배경​

adb와 fastboot은 매일 쓰는 도구지만, Platform Tools 업데이트는 조용히 지나가기 쉽습니다.
SDK Manager가 자동으로 올려주는 경우도 많아, 무엇이 바뀌었는지 모르고 넘어가는 일이 잦습니다.
37.0.3은 무선 디버깅 페어링과 앱 설치 명령, USB 백엔드에서 실무에 바로 닿는 변화가 있습니다.
버전 번호는 작아 보여도, 스크립트와 디버깅 습관에 영향을 주는 항목이 들어 있습니다.

SDK Platform Tools 37.0.3 살펴보기​

터미널 QR 코드로 무선 페어링하기​

무선 디버깅 페어링이 터미널에서 QR 코드로 할 수 있게 됐습니다.
다음 명령을 실행하면 터미널에 QR 코드가 표시됩니다.

adb pair --qr

기존에는 단말에 표시되는 페어링 코드를 터미널에 직접 입력해야 했습니다.
QR 코드 방식은 공용 테스트 단말이나 여러 명이 함께 쓰는 단말을 연결할 때 특히 편합니다.
코드를 외워서 입력하는 과정이 사라져 페어링 실수도 줄어듭니다.

adb install --fastdeploy 폐기와 android install​

adb install --fastdeploy 옵션이 폐기됐습니다.
대신 android install 명령을 쓰도록 안내하고 있습니다.

android install app-debug.apk

Fast Deploy는 당분간 다음 플래그로 계속 쓸 수 있습니다.

adb install --deprecated-fastdeploy app-debug.apk

다만 이후 릴리스에서는 제거될 예정입니다.
빠른 설치를 스크립트나 별칭에 넣어 쓰고 있다면, 지금부터 android install로 바꿔 두는 편이 안전합니다.

libadbusb로 바뀌는 USB 백엔드​

Linux와 macOS에서 libadbusb 라이브러리가 기존 USB 백엔드를 대체합니다.
Linux에서는 USB 버스를 주기적으로 폴링하는 방식으로 바뀌었고, 기본 간격은 1000밀리초입니다.
간격은 다음 환경 변수로 바꿀 수 있습니다.

export ADB_USB_LINUX_POLL_INTERVAL_MS=500

이 변경은 제자리 USB 리셋 뒤나 start-server 명령이 동시에 실행될 때 단말을 놓치는 문제를 피하기 위한 것입니다.
기존 백엔드로 되돌리려면 다음 환경 변수를 1로 설정하면 됩니다.

export ADB_USB_LEGACY=1

macOS에서도 같은 환경 변수로 libadbusb를 끌 수 있습니다.
참고로 Linux에서는 36.0.2부터 불안정 보고 때문에 기존 백엔드가 기본값이었던 만큼, 이번 교체가 실제 단말 연결에서 어떻게 동작하는지는 업데이트 뒤에 직접 확인하는 편이 좋습니다.

로그 스팸 축소와 adb sync 확장​

고빈도 데이터 플레인 로그가 verbose 수준으로 내려가 디버그 로그 양이 줄었습니다.
예를 들어 usb:v, transport:v 수준의 읽기와 쓰기 로그가 대상입니다.
로그 파일이 커져서 디버깅이 불편했던 환경에서는 체감이 될 수 있습니다.
adb sync 명령은 system_dlkm과 vendor_dlkm, odm_dlkm 파티션 동기화를 지원하게 됐습니다.
macOS에서는 Apple Silicon M6에서 발생한 adb 서버 충돌과, AMFI를 끈 상태에서 USB 단말을 연결할 때 생기던 충돌도 수정됐습니다.

실무 관점​

Platform Tools는 Android Studio의 SDK Manager나 sdkmanager 명령으로 업데이트하면 됩니다.
업데이트 뒤에는 CI나 로컬 스크립트에서 --fastdeploy를 쓰고 있는지 먼저 확인하는 편이 좋습니다.
무선 페어링은 QR 코드 방식으로 바뀌어도 기존 페어링 코드 방식이 사라진 것은 아니니, 단말이 QR을 표시하지 못하면 기존 방법을 쓰면 됩니다.
Linux 개발 머신에서 단말이 간헐적으로 사라지던 팀이라면, libadbusb 전환 뒤에 연결이 안정적인지 며칠 지켜보는 편이 좋습니다.

마치며​

SDK Platform Tools 37.0.3은 작은 버전 올림이지만 매일 쓰는 adb 습관을 직접 바꿉니다.
업데이트 뒤에는 빠른 설치 스크립트와 무선 페어링 방법부터 먼저 점검해 보시길 권합니다.

Compose 1.13 정식 출시 살펴보기 — Material 2 종료와 상태 기반 텍스트 필드로의 이전

November 19, 2026 · 6 min read
Way
Android Developer

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.
11월 18일에 정식 출시된 Compose 1.13에 대해 설명해드리겠습니다.

배경​

Compose 1.13은 핵심 Compose 모듈 전체를 1.13.0으로 올리는 정식 릴리스입니다.
업데이트는 Compose BOM 2026.11.01로 적용합니다.
이번 업그레이드에는 Kotlin 2.2 이상과 compileSdk 37.1이 필요합니다.
새 기능도 많지만, 이번 릴리스에서 더 중요한 부분은 종료되는 API입니다.
Material 2와 값 기반 텍스트 필드, Compose용 ConstraintLayout이 공식적으로 deprecated 되었습니다.
버전만 올리는 업데이트가 아니라, 마이그레이션 계획을 세워야 하는 릴리스입니다.

Compose 1.13 살펴보기​

프로그레시브 블러​

Compose 1.13에는 선명함에서 흐림으로 서서히 전환되는 프로그레시브 블러가 들어왔습니다.
Modifier.blur의 람다 형태와 BlurRadiusSpec을 사용합니다.
선형 그라데이션과 방사형 그라데이션, 커스텀 AGSL 셰이더를 이용한 블러 맵을 지정할 수 있습니다.
헤더 이미지 하단을 배경에 녹이거나, 터치 위치를 따라 초점을 이동시키는 효과를 구현할 수 있습니다.

Modifier.blur {
    blurRadiusSpec = BlurRadiusSpec.linearGradient(
        start = DpOffset.Zero,
        end = DpOffset(size.width, size.height),
        stops = listOf(
            BlurStop(fraction = 0f, radius = 0.dp),
            BlurStop(fraction = 0.5f, radius = 0.dp),
            BlurStop(fraction = 0.75f, radius = 14.dp),
            BlurStop(fraction = 1f, radius = 28.dp),
        ),
    )
}

DialogProperties와 PopupProperties에는 배경 블러 반경과 스크림 투명도를 직접 지정할 수 있게 되었습니다.
시스템의 창 간 블러 활성화 여부는 WindowInfo.isCrossWindowBlurEnabled로 조회합니다.

폴리곤 셰이프와 모핑​

PolygonShape과 MorphPolygonShape이 androidx.compose.foundation에 추가되었습니다.
기존에는 별이나 둥근 다각형을 쓰려면 graphics-shapes 의존성을 직접 추가하고 RoundedPolygon을 Path로 변환한 뒤 Shape을 직접 구현해야 했습니다.
PolygonShape은 일반 Compose Shape이라 Modifier.clip이나 컴포넌트의 shape 파라미터에 그대로 쓸 수 있습니다.
MorphPolygonShape은 리컴포지션 없이 진행률 람다를 읽어 두 도형 사이를 애니메이션합니다.

var recording by remember { mutableStateOf(false) }
val progress by animateFloatAsState(if (recording) 1f else 0f)
val shape = remember {
    MorphPolygonShape(
        start = PolygonShape.circle(),
        end = PolygonShape.star(
            numPoints = 9,
            innerRadiusRatio = 0.8f,
            outerRounding = CornerRounding.fraction(0.5f),
        ),
        progress = { progress },
    )
}

Box(
    Modifier
        .size(96.dp)
        .clip(shape)
        .background(MaterialTheme.colorScheme.primary)
        .clickable { recording = !recording }
)

Material 3 1.5.0과 Material 2 종료​

Material 3 1.5.0도 함께 정식 출시되었습니다.
Slider와 RangeSlider가 SliderState 기반의 상태 모델로 바뀌었습니다.
ToggleButtons와 물결 모양 프로그레스 인디케이터, 타임 피커 같은 익스프레시브 컴포넌트가 추가되었습니다.
실험 API 표기는 120개에서 58개로 줄었고, 대부분의 익스프레시브 컴포넌트가 정식으로 승격되었습니다.
Material 3가 나온 지 6년째가 되는 이번 릴리스에서 Compose Material 2는 deprecated 되었고, 더 이상 적극적으로 유지보수되지 않습니다.
Material 2를 쓰고 있다면 Material 3로의 이전을 계획해야 합니다.

상태 기반 텍스트 필드로의 이전​

값 기반 BasicTextField와 Material 2 TextField가 공식적으로 deprecated 되었습니다.
대신 TextFieldState 기반의 상태 기반 BasicTextField를 사용합니다.
Material 3의 값 기반 TextField 오버로드는 1.5.0에서 아직 deprecated 되지 않았지만, 공식 문서는 상태 기반 오버로드로의 이전을 권장합니다.
TextFieldState는 서식이 적용된 스타일의 저장과 복원을 기본으로 지원합니다.
동기식 상태 모델과 성능 개선이 장점입니다.
VisualTransformation도 이번 릴리스에서 deprecated 되었고, InputTransformation과 OutputTransformation이 그 자리를 대신합니다.

val textFieldState = rememberTextFieldState()

BasicTextField(
    state = textFieldState,
    modifier = Modifier.fillMaxWidth(),
)

computedStateOf​

런타임 1.13.0에는 computedStateOf라는 새로운 상태 계산 API가 들어왔습니다.
derivedStateOf의 가벼운 대안으로, 스크롤 위치나 애니메이션 임계값처럼 자주 바뀌는 상태에서 조건 검사나 필터링 결과를 계산할 때 사용합니다.
DerivedState는 계산 결과를 캐시하지만, ComputedState는 값을 읽을 때마다 계산을 다시 수행합니다.
계산이 무겁지 않다면 derivedStateOf보다 오버헤드가 적습니다.
두 API 모두 입력 상태가 바뀔 때가 아니라 계산 결과가 바뀔 때만 컴포지션을 무효화합니다.
무거운 계산이나 캐시가 필요한 경우에만 derivedStateOf를 쓰고, 그 외에는 computedStateOf를 쓰는 것이 권장됩니다.

val listState = rememberLazyListState()
val showTopBar by remember {
    computedStateOf { listState.firstVisibleItemIndex > 0 }
}

CapturedAnimatedVisibility​

AnimatedVisibility는 종료 애니메이션이 끝날 때까지 나가는 콘텐츠와 상태를 유지해야 합니다.
상세 화면을 닫으면서 선택 항목을 null로 지우면, 보여줄 내용이 없어 깜빡이거나 빈 화면이 나타납니다.
Compose 1.13의 CapturedAnimatedVisibility는 visible이 false가 되는 순간의 마지막 프레임을 스냅샷으로 캡처해 애니메이션합니다.
호출하는 쪽에서 상태를 즉시 지워도 종료 애니메이션은 화면에 남아 있던 모습 그대로 진행됩니다.
공식 벤치마크에서는 종료 시 프레임 시간이 AnimatedVisibility보다 7~8% 빠릅니다.
나가는 콘텐츠가 계속 살아 있어야 하거나 자식에 Modifier.animateEnterExit을 써야 할 때는 기존 AnimatedVisibility를 씁니다.

@Composable
fun TrackDetails(track: Track?) {
    CapturedAnimatedVisibility(
        visible = track != null,
        enter = fadeIn() + expandVertically(),
        exit = fadeOut(tween(800)) + shrinkVertically(tween(800)),
    ) {
        if (track != null) {
            TrackCard(track)
        }
    }
}

테스트 실패 진단​

UI 테스트가 실패한 순간의 화면 상태와 시맨틱 계층을 확인하는 기능이 Compose 1.13에 들어왔습니다.
ComposeUiTestConfig의 TestFailurePolicy로 실패 시 스크린샷과 UI 계층 구조를 자동으로 저장할 수 있습니다.
TestFailureHandler를 등록하면 실패 맥락과 생성된 아티팩트를 받아 외부 리포팅 도구로 전달할 수도 있습니다.
build.gradle.kts의 testInstrumentationRunnerArguments로 테스트 스위트 전체에 캡처를 켤 수도 있습니다.

val customConfig = ComposeUiTestConfig(
    failurePolicy = TestFailurePolicy(
        screenshotCaptureMode = TestFailurePolicy.CaptureMode.Enabled,
        uiHierarchyCaptureMode = TestFailurePolicy.CaptureMode.Enabled,
    )
)

@Test
fun myTest() = runComposeUiTest(config = customConfig) {
    // 테스트 내용
}

레이아웃과 동작 변경​

1.11.0에서 실험 API로 들어온 FlexBox와 Grid가 정식으로 승격되었습니다.
FlexBox에는 한 줄에 들어가는 항목 수를 제한하는 maxItemsInEachLine 설정이 추가되었습니다.
FlowRow와 FlowColumn 대신 새 코드에는 FlexBox를 쓰는 것이 권장됩니다.
반대로 Compose용 ConstraintLayout과 MotionLayout은 deprecated 되었습니다.
공유 요소 API 등 새로운 대안이 마련되었기 때문입니다.
Modifier.onFocusedBoundsChanged는 1.12에서 deprecated 된 뒤 1.13에서 구현이 제거되어 더 이상 동작하지 않습니다.
포커스된 요소의 영역이 필요하다면 FocusTargetModifierNode.getFocusedRect()를 사용합니다.
Modifier.clickable로 만든 클릭 요소는 이제 시스템 사운드 설정에 따라 표준 상호작용 효과음을 자동으로 재생합니다.

실무 관점​

국내 MTS 프로젝트에 적용한다면, 버전 업데이트와 마이그레이션을 분리해서 계획하는 것이 좋습니다.
BOM을 2026.11.01로 올리고 빌드가 통과하는지 먼저 확인합니다.
그 다음 Material 2 사용처와 값 기반 텍스트 필드, Compose용 ConstraintLayout 사용처를 목록으로 뽑습니다.
TextFieldState 기반 필드는 입력 처리와 서식 저장 방식이 달라지므로, 입력 화면부터 단계적으로 옮기는 것이 안전합니다.
computedStateOf는 스크롤 위치에 따라 앱바를 보이거나 숨기는 것처럼 자주 바뀌는 상태를 다루는 곳부터 적용해 볼 수 있습니다.
TestFailurePolicy는 CI에서 실패 원인을 찾는 시간을 줄여주므로, UI 테스트가 있는 모듈에 먼저 적용하는 것이 좋습니다.

마치며​

Compose 1.13은 새 기능보다 종료되는 API가 더 중요한 릴리스입니다.
프로그레시브 블러와 상태 기반 텍스트 필드, computedStateOf 같은 새 기능은 단계적으로 적용하면 됩니다.

Kotlin 2.5.0-RC의 KMP 분리 컴파일과 새 발행 형식 살펴보기

November 19, 2026 · 5 min read
Way
Android Developer

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.
11월 11일에 공개된 Kotlin 2.5.0-RC의 KMP 변경 사항에 대해 설명해드리겠습니다.

배경​

Kotlin Multiplatform 프로젝트에서는 IDE 분석과 컴파일러의 판단이 어긋나는 경우가 있습니다.
IDE에서는 빨간 줄이 그어지는 코드가 컴파일은 통과하거나, 반대로 IDE에서는 문제가 없어 보이는데 JVM 컴파일이 실패하기도 합니다.
원인은 컴파일 방식에 있습니다.
공통 코드가 컴파일될 때 의존성의 플랫폼 아티팩트를 함께 보기 때문입니다.
Kotlin 2.5.0-RC는 이 문제를 해결하는 실험적인 분리 컴파일 방식을 도입했습니다.
아울러 멀티플랫폼 라이브러리의 발행 형식을 새로 바꿔, 발행물 크기를 크게 줄였습니다.
두 변경 사항 모두 아직 실험 단계이며, 기본값은 꺼져 있습니다.

KMP 분리 컴파일 살펴보기​

기존 컴파일 방식의 문제​

KMP 모듈은 보통 commonMain 같은 공통 소스셋과 jvmMain 같은 플랫폼 소스셋으로 구성됩니다.
컴파일러는 각 플랫폼 소스셋에 대한 플랫폼 아티팩트를 만들고, 공통 소스셋에 대한 메타데이터 KLIB를 만듭니다.
메타데이터 KLIB에는 선언만 들어 있고 구현 본문은 들어 있지 않습니다.
문제는 플랫폼 소스셋을 컴파일할 때 공통 코드까지 의존성의 플랫폼 아티팩트에 대해 함께 컴파일된다는 점입니다.
그래서 commonMain 코드가 의존성 라이브러리의 플랫폼 전용 선언을 암묵적으로 참조할 수 있습니다.
IntelliJ IDEA는 메타데이터 KLIB만 본다고 가정하므로, 같은 코드를 미해결 참조로 표시합니다.
IDE에서는 빨간 줄인데 컴파일은 통과하는 어긋남이 여기서 생깁니다.
commonTest도 같은 문제를 겪습니다.
테스트 코드가 jvmMain의 플랫폼 선언을 호출하는데, IDE는 이를 미해결 참조로 표시합니다.

// lib/jvmMain
class Foo

// app/commonMain
fun main() {
    Foo() // IDE에서는 미해결 참조, 컴파일은 통과
}

오버로드와 타입 추론의 어긋남​

오버로드 선택에서도 IDE와 컴파일러가 다른 결론에 도달합니다.
라이브러리의 commonMain과 jvmMain에 같은 이름의 함수가 여러 개 선언된 경우를 예로 들 수 있습니다.

// lib/commonMain
fun foo(x: Any) = "common"

// lib/jvmMain
fun foo(x: String) = "platform"

// app/commonMain
fun main() {
    println(foo(""))
}

IDE는 foo("") 호출을 lib/commonMain의 fun foo(x: Any)로 해석합니다.
공통 코드는 공통 선언에만 의존할 수 있다고 가정하기 때문입니다.
그러나 실제 컴파일에서는 두 선언이 모두 보이고, 더 구체적인 fun foo(x: String)이 선택됩니다.
실행 결과로 "platform"이 출력됩니다.
타입 추론에서도 비슷한 문제가 생깁니다.
actual 클래스가 expect 클래스와 다른 상위 타입을 선언하면, IDE는 Event로 추론하는데 JVM 컴파일은 Any로 추론해 .name 참조에서 실패할 수 있습니다.

분리 컴파일이 바꾸는 것​

분리 컴파일은 공통 소스셋을 컴파일할 때 메타데이터 KLIB의 선언만으로 엄격하게 해석합니다.
IDE가 가정하던 방식과 컴파일러의 동작이 일치합니다.
앞의 예제 코드는 분리 컴파일을 켜면 컴파일 오류가 됩니다.
해결 방법은 명시적인 연결을 만드는 것입니다.
라이브러리의 commonMain에 expect class를 선언하고, 플랫폼 쪽을 actual class로 만듭니다.

// lib/commonMain
expect class Foo()

// lib/jvmMain
actual class Foo

// app/commonMain
fun main() {
    Foo() // 정상 동작
}

오버로드 예제에서는 호출이 lib/commonMain의 fun foo(x: Any)로 해석되어 실행 결과로 "common"이 출력됩니다.
타입 추론 예제에서는 공통 코드가 이미 Event 반환 타입으로 추론된 상태로 JVM 컴파일이 별도로 진행되므로, 컴파일이 정상적으로 끝납니다.
기존 코드 중에는 엄격해진 검사에 걸려 수정이 필요한 부분이 생길 수 있습니다.
대신 공통 소스셋에 대한 증분 컴파일이 가능해진다는 부수적인 이득도 있습니다.

분리 컴파일 켜기​

분리 컴파일은 실험 기능이며 기본값은 꺼져 있습니다.
gradle.properties 파일에 다음 속성을 추가하면 켤 수 있습니다.

kotlin.kmp.separateCompilation=true

알려진 문제도 있습니다.
분리 컴파일이 제대로 동작하려면 멀티플랫폼 라이브러리가 메타데이터 KLIB을 발행해야 합니다.
KMP Gradle 플러그인의 기본 발행 동작이므로 대부분은 해당하지 않지만, 이 조건이 이제는 필수입니다.
C 상호 운용을 쓰는 프로젝트에서는 cinterop 공통화 관련 문제에 주의해야 합니다.
공통 소스셋이 있고 선언된 타겟이 하나뿐인 모듈은 현재 분리 컴파일의 영향을 받지 않습니다.

새 발행 형식 .kar​

Kotlin 2.5.0-RC는 멀티플랫폼 라이브러리의 새 발행 형식도 도입했습니다.
JVM과 Android을 제외한 플랫폼 아티팩트를 하나의 .kar 아카이브로 발행합니다.
.kar 파일은 ZIP 아카이브를 XZ로 한 번 더 압축한 형태입니다.
이 변경의 배경은 Maven Central에 최근 도입된 발행 크기 제한입니다.
새 형식에서는 타겟을 추가해도 새 파일이 생기지 않으므로, 발행물 크기가 크게 늘지 않습니다.
경우에 따라서는 기존의 단일 타겟 발행물보다 전체 크기가 작아지기도 합니다.
공식 문서의 예시에서는 cryptography-kotlin 라이브러리의 발행물이 7,539개 파일, 91MB에서 1,036개 파일, 23MB로 줄었습니다.
모듈별로 켜려면 빌드 스크립트에 다음과 같이 설정합니다.

kotlin {
    publishing {
        publicationFormat.set(KotlinPublicationFormat.KOTLIN_ARCHIVE)
    }
}

프로젝트 전체에 적용하려면 gradle.properties 파일에 다음 속성을 추가합니다.

kotlin.publicationFormat=KOTLIN_ARCHIVE

새 형식으로 발행하는 기능은 아직 실험 단계입니다.
다만 .kar 형식의 아티팩트를 소비하는 기능은 모든 프로젝트에서 이미 사용할 수 있습니다.
이 변경 사항은 라이브러리 작성자에게만 해당하며, 최종 애플리케이션 개발자에게는 영향을 주지 않습니다.

실무 관점​

국내 MTS 프로젝트에 적용한다면, 분리 컴파일은 먼저 켜서 컴파일해 보는 것부터 시작하는 것이 좋습니다.
기존 코드가 플랫폼 선언에 암묵적으로 의존하고 있었다면, 켜는 즉시 컴파일 오류로 드러납니다.
이 오류는 숨어 있던 의존성을 명시적인 expect와 actual 선언으로 바꾸라는 신호입니다.
KMP 라이브러리를 직접 발행한다면 .kar 형식도 검토할 만합니다.
타겟이 늘어날수록 발행물 크기가 커지는 부담이 줄기 때문입니다.
다만 발행 기능이 실험 단계이므로, 발행 파이프라인은 별도로 검증한 뒤에 적용하는 것이 안전합니다.
두 기능 모두 실험 단계라는 점을 감안해, 정식 출시 전까지는 운영 빌드에 바로 적용하기보다 평가용으로 써 보는 것이 좋습니다.

마치며​

분리 컴파일은 IDE와 컴파일러의 판단을 일치시켜 KMP 개발을 예측 가능하게 만듭니다.
새 발행 형식은 라이브러리 발행물의 크기를 크게 줄여줍니다.

Cloud Firestore로 데이터 저장하기​

프롬프트에 데이터 저장이나 로그인, 생성형 AI 기능이 필요하다는 단서가 있으면 Build 에이전트가 요구 사항을 먼저 감지합니다.
사용자가 확인하면 에이전트가 Cloud Firestore 데이터베이스를 프로비저닝하고 앱의 데이터 모델에 맞는 Security Rules를 생성합니다.
오프라인 캐시가 포함되어 연결이 끊긴 동안의 변경 사항은 연결이 복원되면 자동으로 동기화됩니다.
태블릿에서 시작한 작업을 휴대전화에서 이어서 할 수 있습니다.

Firebase Authentication으로 로그인하기​

사용자 프로필이나 개인 작업 공간이 필요한 앱에는 Firebase Authentication이 Google Sign-In과 함께 설정됩니다.
사용자별 권한 규칙이 함께 적용되어 각 사용자는 자신의 문서만 읽고 쓸 수 있습니다.
로그인 UI와 토큰 관리를 직접 구현하지 않아도 됩니다.

Firebase AI Logic으로 Gemini 안전하게 호출하기​

APK 안에 API 키를 직접 넣으면 키가 추출될 수 있습니다.
Build 에이전트는 Firebase AI Logic을 설정하고 Firebase App Check를 적용합니다.
App Check는 Google Fraud Defense(구 reCAPTCHA Enterprise)로 요청이 변조되지 않은 정식 앱에서 왔는지 확인합니다.
자격 증명은 서버 쪽에 남아 있고, 앱에서는 키를 노출하지 않고 Gemini 모델을 호출합니다.
공식 블로그에 소개된 생성 코드는 다음과 같습니다.

// Generated by Google AI Studio Build agent using Firebase AI Logic & Cloud Firestore
class WorkoutRepository(context: Context) {
    private val generativeModel by lazy {
        Firebase.ai(backend = GenerativeBackend.googleAI())
            .generativeModel("gemini-4-hydrogen")
    }

    private val db = FirebaseFirestore.getInstance(
        context.applicationContext.getString(R.string.firestore_database_id)
    )

    suspend fun generateAndSaveWorkout(goal: String, uid: String) {
        val response = generativeModel.generateContent("Create a 20-minute workout for: $goal")
        val workout = hashMapOf(
            "ownerId" to uid,
            "goal" to goal,
            "plan" to (response.text ?: ""),
            "createdAt" to FieldValue.serverTimestamp()
        )
        db.collection("workouts").add(workout).await()
    }
}

Firebase.ai로 생성 모델을 만들고, 응답 텍스트를 Firestore 컬렉션에 저장하는 구조입니다.
ownerId를 함께 저장해 사용자별 문서 분리가 가능합니다.

HD 에뮬레이터와 스크린샷 디버깅​

브라우저 안의 Android 에뮬레이터가 더 빠르게 시작되고 HD 토글을 켜면 1200p 고화질 스트리밍으로 전환됩니다.
실시간 오디오 출력도 지원되어 음성 기반 기능이나 TTS, 미디어 앱을 브라우저 안에서 테스트할 수 있습니다.
에뮬레이터 툴바의 스크린샷 버튼을 누르면 실행 중인 화면을 캡처해 프롬프트에 바로 첨부할 수 있습니다.
레이아웃 간격이나 대비 같은 시각적인 수정 요청을 글로 설명하지 않고 화면으로 전달할 수 있습니다.
커스텀 폰트도 지원되어 Compose 테마에 원하는 서체를 적용할 수 있습니다.
내부적으로는 공식 Android CLI가 프로젝트 생성과 Gradle 빌드를 담당합니다.

개인 Play 라이브러리로 바로 게시하기​

지금까지 실기기에 앱을 설치하려면 USB 디버깅을 켜거나 서명 키스토어를 직접 관리해야 했습니다.
Google Play 연동을 이용하면 게시 패널에서 몇 번의 클릭으로 Play 계정을 설정할 수 있습니다.
AI Studio가 Android App Bundle(.aab)을 빌드하고 서명한 뒤 개인 Play 라이브러리에 바로 게시합니다.
일반 Google 계정으로 이용할 수 있고, 휴대전화에 바로 설치해 테스트할 수 있습니다.

실무 관점​

생성된 코드는 프로토타입이나 MVP를 빠르게 만드는 데 적합합니다.
실제 서비스에 쓰려면 생성된 Security Rules가 데이터 모델과 권한 정책을 정확히 반영하는지 직접 검토해야 합니다.
백엔드가 Cloud Firestore와 Firebase Authentication으로 고정되므로, 나중에 다른 백엔드로 옮기려면 데이터 계층을 다시 작성해야 합니다.
자동 테스트와 CI/CD, UX 품질 검토는 아직 수동 작업으로 남아 있습니다.
개인 Play 라이브러리 게시는 정식 Play Console 배포와 다르므로, 상용 배포 전에는 스토어 정책과 심사 절차를 별도로 확인해야 합니다.

마치며​

프롬프트 하나로 데이터 저장과 로그인, 안전한 Gemini 호출까지 갖춘 Kotlin 앱을 만들 수 있게 되었습니다.
프로토타입 단계의 반복 속도를 높이는 데 유용한 업데이트입니다.

Android 17 QPR3 Beta 4 살펴보기

Way
Android Developer

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.
11월 12일에 공개된 Android 17 QPR3 Beta 4에 대해 설명해드리겠습니다.

배경​

QPR은 분기마다 배포되는 플랫폼 릴리스입니다.
메이저 버전 사이의 공백을 메우며 기능 개선과 보안 패치를 함께 전달합니다.
QPR3 Beta 4는 10월 2일에 시작된 QPR3 베타 사이클의 네 번째 빌드입니다.
Beta 3은 10월 29일에, Beta 2는 10월 20일에 배포되었습니다.
이번 베타는 앱에 영향을 주는 API 변경을 포함하지 않습니다.
대신 시스템 안정성과 수정 사항 검증이 중심이며, 개발자는 베타 이미지로 앱을 미리 테스트할 수 있습니다.

Android 17 QPR3 Beta 4 살펴보기​

릴리스 정보​

빌드 번호는 DP11.261030.003입니다.
보안 패치 수준은 2026-10-05이며, Google Play services는 26.41.31이 포함됩니다.
에뮬레이터는 x86 64비트와 ARM v8-A를 지원합니다.
대상 기기는 Pixel 6a부터 Pixel 11 시리즈와 Pixel Fold, Pixel Tablet까지입니다.
Pixel 6과 Pixel 6 Pro는 QPR1 베타 사이클 이후 지원이 종료되어 이번 베타 대상에서 제외됩니다.

Beta 4에서 수정된 주요 이슈​

공식 릴리스 노트에 따르면 Beta 4에서 수정된 주요 이슈는 다음과 같습니다.
system_server 메모리 누수로 인한 심각한 UI 지연, Pixel Launcher 충돌, 예기치 않은 기기 재시작이 수정되었습니다.
API 레벨 36을 대상으로 하는 앱에서 TLSv1 또는 TLSv1.1 연결이 거부될 때 Conscrypt가 불명확한 IllegalArgumentException 메시지를 던지던 문제가 수정되었습니다.
텍스트 입력 중 화면 키보드가 잘려 보이던 문제가 수정되었습니다.
과도한 블루투스 백그라운드 활동으로 배터리가 빠르게 소진되던 문제가 수정되었습니다.

TLS 1.0과 1.1 거부에 대비하기​

API 레벨 36을 대상으로 하는 앱은 TLSv1과 TLSv1.1을 사용할 수 없습니다.
연결 시도가 거부되면 예외가 발생하므로, 오래된 TLS 버전에 의존하는 네트워크 코드는 점검이 필요합니다.
서버가 TLS 1.2 이상을 지원하는지 먼저 확인해야 합니다.
네트워크 보안 설정은 다음과 같이 작성할 수 있습니다.

<network-security-config>
    <base-config cleartextTrafficPermitted="false">
        <trust-anchors>
            <certificates src="system" />
        </trust-anchors>
    </base-config>
</network-security-config>

cleartextTrafficPermitted를 false로 두면 평문 통신이 차단됩니다.
신뢰하는 인증서는 시스템 저장소로 제한됩니다.

베타 빌드 설치하고 확인하기​

베타에 등록된 기기에는 OTA 업데이트가 제공됩니다.
팩토리 이미지는 Android Flash Tool로 직접 설치할 수도 있습니다.
개발자용 GSI 바이너리도 같은 빌드로 제공됩니다.
설치 후에는 다음 명령으로 빌드 번호와 보안 패치 수준을 확인할 수 있습니다.

adb shell getprop ro.build.version.incremental
adb shell getprop ro.build.version.security_patch

ro.build.version.incremental이 DP11.261030.003이면 Beta 4가 설치된 상태입니다.

실무 관점​

MTS처럼 실시간 통신이 중요한 앱에서는 system_server 메모리 누수 수정이 체감 성능에 직접 영향을 줍니다.
API 레벨 36을 대상으로 한다면 TLS 버전 정책을 빌드 전에 확인해야 합니다.
베타 기기는 테스트 전용으로 유지하고, 실사용 기기에 베타를 설치하지 않는 것이 안전합니다.
정식 릴리스 일정은 아직 공개되지 않았으므로, 베타 결과를 기록해 두었다가 정식 릴리스 때 다시 확인하는 것이 좋습니다.

마치며​

Beta 4는 UI 지연과 재시작, TLS 오류 메시지 같은 실사용 문제를 다듬는 업데이트입니다.
대상 API 36 앱이라면 TLS 설정을 이번 기회에 점검하는 것이 좋습니다.

안드로이드 개발자에게 열린 Gemini 4 Argon — 자가 복구 빌드와 AGSL 셰이더

October 15, 2026 · 4 min read
Way
Android Developer

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.
안드로이드 개발자에게 개방된 Gemini 4 Argon에 대해 설명해드리겠습니다.

배경​

구글은 10월 13일 Android Developers Blog에서 최신 플래그십 모델 Gemini 4 Argon을 안드로이드 개발 표면에 개방한다고 발표했습니다.
자세한 내용은 원문 글(Jason Buchel)에서 확인할 수 있습니다.
지난주에 다뤘던 Android CLI와 디바이스 스트리밍, BYOA(원하는 에이전트 쓰기) 흐름의 연장선에 있는 발표입니다.
모델 자체보다 에이전트가 빌드를 스스로 고치고 셰이더까지 작성한다는 부분에 주목할 필요가 있습니다.

Gemini 4 Argon 살펴보기​

접근 경로​

  • Google Antigravity에서 사용할 수 있습니다. AI Ultra 구독이 전제이고, 데스크톱 앱·CLI·Android Studio Canary 안에 포함됩니다.
  • Android Studio에서는 Gemini API 유료 티어로 사용할 수 있습니다.
  • Google AI Studio의 Playground와 Build에서도 사용할 수 있습니다. AI Ultra 또는 Gemini API 유료 티어가 필요합니다.
  • 클라이언트 인앱 AI는 Firebase AI Logic 경유로 제공됩니다. Gemini API 유료 티어 개발자가 앱 안에서 Gemini 4 Argon을 직접 쓸 수 있습니다.

Self-Healing Build Loops​

  • 빌드 실패 시 Antigravity 하네스가 Gradle 데몬과 Kotlin 컴파일러 로그를 모델에 그대로 피드백합니다.
  • 모델은 근본 원인을 반복 진단해 수정안을 냅니다.
  • 편집 라운드마다 가설을 일관되게 유지하고 AST 인지를 활용해 표면 증상이 아닌 진짜 원인에 도달하도록 훈련되었다는 설명입니다.
  • 지금까지의 에이전트 코딩이 코드 자동완성의 연장에 가까웠다면, 이번 방향은 빌드 → 실패 로그 수집 → 원인 진단 → 수정 → 재빌드를 하네스와 모델이 돌리는 클로즈드 루프 실행입니다.

Compose 셰이더 생성​

  • AGSL(Android Graphics Shading Language)을 Compose Modifier.graphicsLayer나 셰이더 브러시에 직접 작성합니다.
  • 120fps Compose 애니메이션과 함께 도는 경량 GPU 셰이더를 생성합니다. 프로스트드 글래스, 동적 조명, 파문 같은 효과가 예시입니다.
  • 벡터·렌더링 수학까지 처리해 뽑아낸다고 합니다.
  • Compose 셰이더는 AGSL 문법과 렌더링 수학, 성능 예산 때문에 실무에서 진입 장벽이 높은 영역입니다.

터미널 에이전트 연결​

  • 터미널 에이전트 연결은 공식 Android CLI 플러그인이 맡습니다.
  • android init 한 줄이면 어떤 터미널 에이전트든 로컬 Android 도구와 연결됩니다.
  • Antigravity라면 플러그인 설치로 끝납니다.

실무에서 주의할 점​

빌드 로그가 곧 에이전트의 입력입니다.
Self-Healing이 동작하려면 빌드 실패 로그가 잘 읽혀야 합니다.
난독화된 멀티모듈 빌드에서 에이전트가 원인에 닿으려면, 지금부터라도 Gradle 빌드 스크립트와 에러 메시지를 사람이 읽을 수 있게 정리해 두는 것이 이득입니다.
비용 구조도 확인해야 합니다.
Antigravity는 AI Ultra 구독 전제이고, API 경로는 Gemini API 유료 티어 전제입니다.
인트로 가격은 2026년 11월 30일까지 적용되므로, 이후 정가를 모르면 팀 도입 판단이 어렵습니다. 도입 전에 Console에서 실제 과금을 먼저 확인해야 합니다.
셰이더 코드는 리뷰가 필수입니다.
"프로덕션급"이라는 표현은 모델 벤더의 주장일 뿐이고, AGSL 셰이더는 GPU와 디바이스별로 동작이 달라 실기 검증 없이는 쓸 수 없습니다. 에이전트가 짠 셰이더는 초안으로 보고 프레임 타임과 배터리부터 측정해야 합니다.
Firebase AI Logic 경로는 인앱 기능용입니다.
개발 워크플로(빌드 복구·코드 생성)와 앱 내 AI 기능(사용자 대면)은 접근 경로가 다르므로, 팀에서 둘을 혼동하면 과금·권한 설계가 꼬입니다.
터미널 에이전트에 Android CLI를 붙이는 방법은 다음과 같습니다.

# 어떤 터미널 에이전트에서든: 로컬 Android 도구와 연결
android init

# Antigravity를 쓴다면: 공식 Android CLI 플러그인 설치
agy plugin install android-cli-plugin

Firebase AI Logic으로 인앱에 붙일 때는 모델 선택만 새 모델로 바꾸는 구조라, 기존 Vertex AI와 Gemini Developer API 연동 코드의 모델명 교체 수준에서 검토가 가능합니다.
정확한 모델 식별자는 Firebase AI Logic 문서를 확인해야 하고, 릴리스 직후에는 SDK 업데이트가 필요할 수 있습니다.
샘플 프로젝트 gemini-4-antigravity-quickstart도 함께 공개되었으니, 에이전트 워크플로를 팀에 도입하기 전에 퀵스타트로 확인하는 것이 좋습니다.

마치며​

Gemini 4 Argon의 핵심은 모델 성능보다 빌드와 셰이더까지 에이전트 워크플로에 들어왔다는 점입니다.

KMP 모듈에 Swift 패키지 의존성 추가하기

November 17, 2026 · 4 min read
Way
Android Developer

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.
Kotlin 2.5.0-RC에서 시도해 볼 수 있는 KMP 모듈의 SwiftPM import 기능에 대해 설명해드리겠습니다.

배경​

KMP 프로젝트에서 iOS 쪽 네이티브 SDK를 쓰려면 지금까지 CocoaPods 의존성을 연결하거나 cinterop 정의를 직접 작성해야 했습니다.
CocoaPods 방식은 별도 설정이 많고, Swift 패키지를 그대로 가져오는 방법이 마땅하지 않았습니다.
Kotlin 2.5.0-RC부터는 SwiftPM import 기능을 이용해 Swift 패키지를 Gradle 빌드 스크립트에서 직접 선언할 수 있습니다.
SwiftPM 의존성의 Objective-C API를 Kotlin 코드에서 바로 호출할 수 있게 됩니다.

SwiftPM import 살펴보기​

플러그인 버전 설정하기​

SwiftPM import를 쓰려면 Kotlin Multiplatform Gradle 플러그인 2.5.0-RC가 필요합니다.
Version Catalog에서는 다음과 같이 버전을 지정합니다.

[versions]
kotlin = "2.5.0-RC"

[plugins]
kotlin-multiplatform = { id = "org.jetbrains.kotlin.multiplatform", version.ref = "kotlin" }

Swift 패키지 선언하기​

SwiftPM 의존성은 Apple 타겟을 선언한 build.gradle.kts 안의 swiftPMDependencies 블록에 추가합니다.
예시로 FirebaseAnalytics를 가져오는 설정은 다음과 같습니다.

kotlin {
    iosArm64()
    iosSimulatorArm64()
    swiftPMDependencies {
        // FirebaseAnalytics를 Kotlin 코드로 가져옵니다
        swiftPackage(
            url = url("https://github.com/firebase/firebase-ios-sdk.git"),
            version = from("12.5.0"),
            products = listOf(product("FirebaseAnalytics")),
        )
    }
}

버전은 from으로 시작 버전을 지정하거나, exact로 정확한 버전을 지정할 수 있습니다.
브랜치나 특정 리비전을 지정하는 방식도 함께 제공됩니다.

Clang 모듈 가져오기​

SwiftPM import는 Clang 모듈을 가져오는 방식으로 동작합니다.
기본값으로는 지정한 Swift 패키지 안의 Clang 모듈을 자동으로 찾아 Kotlin 코드에서 쓸 수 있게 합니다.
자동 탐색을 끄려면 discoverClangModulesImplicitly를 false로 바꾸고, 제품 이름을 Clang 모듈 이름으로 씁니다.
모듈 이름이 제품 이름과 다르면 importedClangModules로 직접 지정합니다.
예를 들어 FirebaseFirestore의 Objective-C API는 FirebaseFirestoreInternal 모듈에 들어 있습니다.

kotlin {
    swiftPMDependencies {
        discoverClangModulesImplicitly = false
        swiftPackage(
            url = url("https://github.com/firebase/firebase-ios-sdk.git"),
            version = from("12.5.0"),
            products = listOf(
                product("FirebaseAnalytics"),
                product("FirebaseFirestore"),
            ),
            importedClangModules = listOf(
                "FirebaseAnalytics",
                "FirebaseFirestoreInternal",
            ),
        )
    }
}

플랫폼 제한 두기​

일부 SwiftPM 의존성은 모든 타겟에서 빌드되지 않습니다.
예를 들어 Google Maps SDK는 현재 iOS 타겟만 지원합니다.
iOS만 타겟으로 한다면 따로 지정할 필요가 없지만, macOS 같은 타겟을 추가하면 제품마다 플랫폼을 지정해야 합니다.

kotlin {
    iosArm64()
    iosSimulatorArm64()
    macosArm64()
    swiftPMDependencies {
        swiftPackage(
            url = url("https://github.com/googlemaps/ios-maps-sdk.git"),
            version = exact("10.3.0"),
            products = listOf(
                product(
                    "GoogleMaps",
                    platforms = setOf(iOS()),
                ),
            ),
        )
    }
}

Xcode 프로젝트와 연결하기​

SwiftPM 의존성을 처음 추가하면 Xcode 프로젝트와 생성된 패키지를 연결해야 합니다.
다음 Gradle 태스크를 실행하면 SwiftPM 패키지가 생성되고 Xcode 프로젝트가 함께 변경됩니다.

XCODEPROJ_PATH='/path/to/project/iosApp/iosApp.xcodeproj' ./gradlew :kotlin-library:integrateLinkagePackage

생성된 패키지와 변경된 Xcode 프로젝트는 저장소에 함께 커밋합니다.
그 뒤로는 의존성 목록이나 버전이 바뀔 때마다 합성 패키지가 자동으로 갱신됩니다.

Kotlin 코드에서 호출하기​

가져온 Objective-C API는 swiftPMImport로 시작하는 네임스페이스에 들어 있습니다.
네임스페이스는 Gradle 그룹 이름과 프로젝트 이름을 이어서 만듭니다.
iosMain 소스 세트에서 Firebase API를 쓰는 예시는 다음과 같습니다.

import swiftPMImport.groupName.subproject.FIRAnalytics
import swiftPMImport.groupName.subproject.FIRApp

fun logAppOpen() {
    FIRApp.configure()
    FIRAnalytics.logEventWithName("app_open", parameters = null)
}

버전 잠금 파일 관리하기​

SwiftPM import 도구는 의존성 버전을 고정하기 위해 Package.resolved 파일을 만듭니다.
기본값으로는 모든 서브프로젝트의 잠금 파일이 .swiftpm-locks/default/swiftImport 안의 하나의 파일로 합쳐집니다.
잠금 파일은 저장소에 커밋해 모든 빌드가 같은 버전을 쓰게 합니다.
서브프로젝트별로 잠금 파일을 나누려면 packageResolvedSynchronization에 그룹 식별자를 지정합니다.
잠금 파일을 강제로 갱신하려면 빌드 디렉터리와 기존 Package.resolved 파일을 지운 뒤 다음 태스크를 실행합니다.

./gradlew :yourModuleName:fetchSyntheticImportProjectPackages

알고 있어야 할 제한 사항​

동적 Kotlin/Native 프레임워크를 만들 때는 SwiftPM import가 모든 경우를 지원하지 않습니다.
빌드 오류나 런타임 경고가 나오면 프레임워크 연결 방식을 정적으로 바꾸는 것이 일반적인 해결 방법입니다.

kotlin {
    listOf(
        iosArm64(),
        iosSimulatorArm64()
    ).forEach { iosTarget ->
        iosTarget.binaries.framework {
            baseName = "Shared"
            isStatic = true
        }
    }
}

실무 관점​

MTS 앱에 적용한다면, iOS 쪽에서만 쓰는 SDK부터 SwiftPM import로 옮겨 보는 것이 안전합니다.
CocoaPods 의존성을 함께 쓰고 있다면, 두 방식이 같은 SDK를 중복으로 가져오지 않는지 먼저 확인해야 합니다.
Package.resolved 잠금 파일과 생성된 패키지는 저장소에 커밋해 팀 빌드와 CI 빌드가 같은 버전을 쓰게 합니다.
Kotlin 2.5.0-RC는 정식 출시 전 단계이므로, 프로덕션 적용보다 별도 브랜치에서의 검증이 먼저입니다.

마치며​

SwiftPM import를 쓰면 Swift 패키지를 Gradle 빌드 스크립트에서 직접 선언해 KMP 모듈에서 쓸 수 있습니다.
CocoaPods 설정과 cinterop 정의를 줄이고, 버전 잠금까지 Gradle 안에서 관리할 수 있게 됩니다.

Kotlin 2.5.0-RC 살펴보기: 동반자 객체 없이 쓰는 동반자 블록과 확장

November 16, 2026 · 3 min read
Way
Android Developer

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.

11월 11일에 공개된 Kotlin 2.5.0-RC의 동반자 블록과 동반자 확장에 대해 설명해드리겠습니다.
동반자 블록과 동반자 확장은 Kotlin 2.5.0-RC의 새로운 기능에 포함된 실험적 기능입니다.

배경​

타입 이름으로 접근하는 멤버를 선언하려면 동반자 객체가 필요했습니다.
동반자 객체가 없는 타입에는 이런 멤버를 확장으로 추가할 방법이 없었습니다.
팩토리 함수나 상수를 타입 이름 아래에 두고 싶어도 동반자 객체를 먼저 만들어야 했습니다.
동반자 블록과 동반자 확장은 이 제약을 없애는 기능입니다.

동반자 블록과 확장 살펴보기​

동반자 블록​

동반자 블록은 클래스나 인터페이스 안에 companion 블록을 직접 작성하는 방식입니다.
별도의 객체 인스턴스를 만들지 않고 멤버를 선언할 수 있습니다.
JVM에서는 정적 멤버로 생성되므로 JvmStatic 애너테이션이 필요 없습니다.

data class Vector(val x: Double, val y: Double) {
    companion {
        val Zero: Vector get() = Vector(0.0, 0.0)
    }
}

fun main() {
    println(Vector.Zero) // Vector(x=0.0, y=0.0)
}

동반자 확장​

동반자 확장은 최상위 확장에 companion 변경자를 붙이는 방식입니다.
확장 대상 타입에 동반자 객체가 없어도 타입 이름으로 접근하는 멤버를 선언할 수 있습니다.
타입을 직접 제어하지 않는 경우에도 멤버를 추가할 수 있습니다.

import kotlin.math.cos
import kotlin.math.sin

companion val Vector.UnitX get() = Vector(1.0, 0.0)

companion fun Vector.unit(angle: Double) = Vector(cos(angle), sin(angle))

fun main() {
    println(Vector.UnitX) // Vector(x=1.0, y=0.0)
}

사용 설정​

실험적 기능이므로 컴파일러 옵션을 추가해야 합니다.
동반자 블록만 쓰려면 다음 옵션을 사용합니다.

kotlin {
    compilerOptions {
        freeCompilerArgs.add("-Xcompanion-blocks")
    }
}

동반자 확장까지 쓰려면 다음 옵션을 사용합니다.

kotlin {
    compilerOptions {
        freeCompilerArgs.add("-Xcompanion-blocks-and-extensions")
    }
}

동반자 확장을 사용하면 컴파일러가 정식 출시 전 바이너리를 생성합니다.
그래서 동반자 확장을 쓰는 라이브러리는 기능이 정식화되기 전까지 의존성으로 소비할 수 없습니다.
설계 배경은 동반자 블록과 확장 소개 글에서 확인할 수 있습니다.

실무 관점​

MTS에서는 화면 상태나 요청 파라미터를 타입 이름 아래의 팩토리 함수로 만드는 경우가 많습니다.
동반자 블록을 쓰면 동반자 객체 선언 없이 이런 팩토리를 정리할 수 있습니다.
다만 실험적 기능이므로 앱 모듈에서 먼저 검증하고, 라이브러리 모듈에는 적용하지 않는 것이 좋습니다.
특히 동반자 확장은 바이너리 호환성에 영향을 주므로 공유 모듈에서는 피해야 합니다.

마치며​

동반자 블록과 동반자 확장은 동반자 객체 없이 타입 이름으로 접근하는 멤버를 선언하는 방식을 제공합니다.
팩토리 함수와 상수 정리가 간결해집니다.

Kotlin 2.5.0-RC 살펴보기: 여러 프로퍼티를 갖는 전체 값 클래스

November 16, 2026 · 3 min read
Way
Android Developer

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.

11월 11일에 공개된 Kotlin 2.5.0-RC의 전체 값 클래스에 대해 설명해드리겠습니다.
전체 값 클래스는 실험적 기능으로, 여러 프로퍼티를 하나의 값으로 묶는 방식을 제공합니다.

배경​

기존 인라인 값 클래스는 하나의 프로퍼티만 가질 수 있었습니다.
여러 값을 묶어야 할 때는 일반 클래스나 데이터 클래스를 사용해야 했습니다.
데이터 클래스는 같은 데이터를 가진 인스턴스라도 참조가 다르면 별개로 구분될 수 있습니다.
값 자체가 본질인 타입에서는 이 참조 구분이 불필요한 제약이 됩니다.
전체 값 클래스는 이런 경우를 위해 프로퍼티 전체가 값이 되는 타입을 제공합니다.

전체 값 클래스 살펴보기​

기본 선언​

전체 값 클래스는 value class 키워드로 선언합니다.
프로퍼티를 여러 개 가질 수 있고, 컴파일러가 equals와 hashCode, toString을 자동으로 생성합니다.
이 점은 데이터 클래스와 비슷합니다.
다만 componentN 함수는 생성되지 않습니다.
대신 이름 기반 구조 분해를 사용합니다.
copy 함수는 제공되지 않으며, 향후 복사 변수 기능으로 대체될 예정입니다.

value class Complex(val real: Double, val imaginary: Double)

fun main() {
    val complex = Complex(1.0, 2.0)
    val (val real, val imaginary) = complex
    println(real)
    println(imaginary)
}

이름 기반 구조 분해에서는 변수 이름이 프로퍼티 이름과 일치해야 합니다.
순서가 바뀌어도 이름이 같으면 올바른 값이 들어갑니다.
이 문법은 2.5.0-RC에서 기본 동작이 되었습니다.

추상 값 클래스​

전체 값 클래스는 추상 클래스로 선언할 수도 있습니다.
인터페이스와 달리 모든 하위 클래스가 실행하는 초기화 로직을 정의할 수 있습니다.
다음 예시에서는 시작 값이 끝 값보다 크지 않은지 생성 단계에서 검증합니다.

sealed value class OrderedInterval<T : Comparable<T>> protected constructor(
    start: T,
    end: T,
) {
    init {
        require(start <= end)
    }
}

value class IntInterval(
    val start: Int,
    val end: Int
) : OrderedInterval<Int>(start, end)

값 객체​

프로퍼티가 없는 전체 값 클래스는 값 객체라고 부릅니다.
하나의 값만 가질 수 있는 상태를 표현할 때 사용합니다.
다음 예시에서는 조회 결과를 찾음과 찾지 못함으로 나눕니다.

sealed interface UserResponse

value class UserFound(val userName: String) : UserResponse
value object UserUnknown : UserResponse

사용 설정​

전체 값 클래스는 실험적 기능이므로 컴파일러 옵션을 추가해야 합니다.
build.gradle.kts에 다음과 같이 작성합니다.

kotlin {
    compilerOptions {
        freeCompilerArgs.add("-Xfull-value-classes")
    }
}

자세한 내용은 Kotlin 2.5.0-RC의 새로운 기능에서 확인할 수 있습니다.

실무 관점​

MTS에서는 금액과 통화를 함께 다루는 타입이 많습니다.
이런 복합 값을 전체 값 클래스로 표현하면 참조 구분에 의존하는 실수를 줄일 수 있습니다.
다만 아직 실험적 기능이고 RC 단계이므로, 프로덕션 모듈에 바로 적용하기보다는 별도 브랜치에서 검증하는 것이 좋습니다.
정식 출시 이후 안정화 여부를 다시 확인해야 합니다.

마치며​

전체 값 클래스는 여러 프로퍼티를 하나의 값으로 묶는 방식을 제공합니다.
데이터 클래스와 비슷하지만 참조 구분이 없는 점이 다릅니다.

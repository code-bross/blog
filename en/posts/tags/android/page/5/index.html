WebView에 stable API로 온 allowlist — WebKit 1.18.0 살펴보기

October 24, 2026 · 3 min read
Way
Android Developer

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.
2026년 10월 21일에 공개된 WebKit 1.18.0의 릴리스 노트를 정리해드리겠습니다.

현재 상황​

지난 글에서는 WebView v156의 cross-origin isolation allowlist 개념을 정리한 바 있습니다.
당시에는 개념과 정책 방향이 중심이었습니다.
이번에는 그 기능이 Jetpack WebKit의 stable API로 확정된 내용을 정리합니다.
MTS 앱처럼 WebView를 많이 쓰는 앱에서는 웹 콘텐츠의 성능 기능과 보안 정책을 함께 다뤄야 합니다.
SharedArrayBuffer처럼 cross-origin isolation을 요구하는 API는 그동안 전부 아니면 전무에 가까웠습니다.
1.18.0은 신뢰하는 origin만 골라 허용하는 길을 stable API로 열어줍니다.

WebKit 1.18.0 살펴보기​

cross-origin isolated allowlist API​

핵심은 Profile 수준의 API입니다.
Profile#setCrossOriginIsolatedAllowlist와 Profile#getCrossOriginIsolatedAllowlist가 stable로 제공됩니다.
allowlist에 오른 origin에서는 완전히 cross-origin isolated 상태가 아니어도 SharedArrayBuffer 같은 API를 쓸 수 있습니다.
다만 웹 페이지 쪽에서도 Document-Isolation-Policy 헤더로 적절히 옵트인해야 합니다.
앱 API만 켠다고 끝나는 기능이 아니라, 웹 측 헤더와 함께 동작하는 기능입니다.

// 이미 확보한 Profile이라고 가정합니다
if (WebViewFeature.isFeatureSupported(WebViewFeature.CROSS_ORIGIN_ISOLATED_ALLOWLIST)) {
    profile.setCrossOriginIsolatedAllowlist(
        setOf("https://trusted.example.com")
    )
}

사용 전에 반드시 기능 지원 여부를 확인해야 합니다.
지원되지 않는 단말에서 호출하면 예외가 발생합니다.
공식 API 레퍼런스에서도 사용 전 확인을 강조하고 있습니다.
또한 기본값은 비활성화 상태입니다.
WebView는 렌더러 프로세스 격리를 지원하지 않기 때문에, 이 API를 호출한다는 것은 보안 보장을 완화하겠다는 뜻이 됩니다.
그래서 신뢰하는 origin만 등록해야 하고, 와일드카드 패턴은 피해야 합니다.
이미 로드된 페이지에도 이 설정이 적용된다는 점도 염두에 두어야 합니다.

prefetch 큐 비우기 여부 확인​

WebViewFeature에 WEBVIEW_NAVIGATE_DRAIN_PREFETCH 상수가 추가되었습니다.
이 상수로 Navigation#navigate가 이동 전에 prefetch 큐를 비우는지 확인할 수 있습니다.
prefetch를 쓰는 앱에서는 이동 시점에 어떤 요청이 남는지 예측하기가 한결 쉬워집니다.
단순한 상수 추가처럼 보이지만, 동작 예측 가능성을 높이는 변경입니다.

if (WebViewFeature.isFeatureSupported(WebViewFeature.WEBVIEW_NAVIGATE_DRAIN_PREFETCH)) {
    // Navigation#navigate가 prefetch 큐를 비우는지 확인할 수 있습니다
}

API 정리와 이름 변경​

PrefetchParameters#isJavaScriptEnabled는 includeClientHints로 이름이 바뀌었습니다.
기존 메서드는 deprecated 처리되었습니다.
Profile#addQuicHints는 preferQuicFor로 이름이 바뀌었습니다.
이름만 바뀐 변경이지만, 기존 이름을 그대로 쓰던 코드가 있다면 마이그레이션 목록에 올려두어야 합니다.
deprecated 경고를 방치하면 나중에 버전 올릴 때 한꺼번에 정리해야 합니다.

의존성 선언​

[versions]
webkit = "1.18.0"

[libraries]
webkit = { module = "androidx.webkit:webkit", version.ref = "webkit" }
dependencies {
    implementation(libs.webkit)
}

실무 관점​

MTS 앱에서 WebView allowlist를 쓴다면, 등록 대상은 자사 도메인처럼 확실히 신뢰하는 origin으로 한정해야 합니다.
외부 제휴 페이지나 광고성 페이지를 넓게 허용하면, 보안 보장을 완화한 대가를 치르게 됩니다.
적용 전에는 기능 지원 여부 확인, 헤더 설정, 기존 페이지 동작을 함께 테스트하는 편이 좋습니다.
이미 로드된 페이지에도 적용되므로, 설정 시점에 따라 동작이 달라질 수 있다는 점도 테스트 항목에 넣어야 합니다.
stable 릴리스인 만큼, 기존에 쓰던 이름 변경부터 정리하고 단계적으로 적용하는 것이 안전합니다.

마치며​

이번 stable은 allowlist라는 보안 기능을 실제 API로 쓸 수 있게 만든 릴리스입니다.
신뢰하는 origin만 좁게 허용한다는 원칙만 지키면, WebView의 성능 기능을 보다 안전하게 활용할 수 있습니다.

Google Sign-In deprecated, 이제는 Credential Manager로 옮기기

October 23, 2026 · 4 min read
Way
Android Developer

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.
오랫동안 사용해 온 Google Sign-In for Android의 deprecated 선언과 Credential Manager로의 이전 방법에 대해 설명해드리겠습니다.

현재 상황​

Android에서 Google 계정으로 로그인하는 방법은 오랫동안 play-services-auth의 GoogleSignInClient와 GoogleSignInOptions였습니다.
하지만 Android Developers 문서에 따르면 Google Sign-In for Android는 deprecated 상태이며, Google Play services Auth SDK의 향후 릴리스에서는 제거될 예정이라고 명시되어 있습니다.
후계자로는 Credential Manager가 공식 권장되고 있습니다.
제거 시기는 아직 정해지지 않았지만 제거가 예고된 만큼, 인증 흐름을 손보는 시점에 함께 이전하는 것이 안전합니다.

Credential Manager 살펴보기​

Credential Manager는 패스키, 비밀번호, Google을 포함한 연합 로그인 방식을 하나의 통합 API로 처리하는 Jetpack API입니다.
Android 4.4(API 19) 이상에서 동작하며 모바일, Android XR, Wear OS를 포함한 다양한 폼 팩터를 지원합니다.
공식 마이그레이션 가이드에서는 새 API의 이점을 하나의 통합 지점, 표준 Sign in with Google 버튼 지원, 원탭 자동 로그인, 패스키 내장 보안으로 정리하고 있습니다.

의존성 추가하기​

구현 가이드에 따르면 다음 세 가지 의존성을 추가합니다.

dependencies {
    implementation("androidx.credentials:credentials:1.7.0-alpha03")
    implementation("androidx.credentials:credentials-play-services-auth:1.7.0-alpha03")
    implementation("com.google.android.libraries.identity.googleid:googleid:<latest version>")
}

바텀 시트 플로우 만들기​

Credential Manager의 바텀 시트는 패스키, 비밀번호, Google 로그인에 모두 동일한 경험을 제공하는 내장 UI입니다.
기존처럼 별도의 로그인 화면을 만들 필요가 없습니다.
먼저 이전에 인증된 계정을 조회하는 요청을 만듭니다.

val googleIdOption: GetGoogleIdOption = GetGoogleIdOption.Builder()
    .setFilterByAuthorizedAccounts(true)
    .setServerClientId(WEB_CLIENT_ID)
    .setAutoSelectEnabled(true)
    .setNonce(generateSecureRandomNonce())
    .build()

setFilterByAuthorizedAccounts(true)는 이 앱에서 이전에 사용한 계정만 보여 줍니다.
setAutoSelectEnabled(true)와 함께 사용하면 기존 silentSignIn과 유사한 자동 로그인을 구현할 수 있습니다.
단, 자동 로그인이 동작하려면 디바이스에 승인된 계정이 하나뿐이고, 이전 세션에서 명시적으로 로그아웃하지 않았으며, 사용자가 Google 계정 설정에서 자동 로그인을 끄지 않은 조건을 만족해야 합니다.

이어서 요청을 실행합니다.

val request: GetCredentialRequest = GetCredentialRequest.Builder()
    .addCredentialOption(googleIdOption)
    .build()

val result = credentialManager.getCredential(
    request = request,
    context = mutableContext
)
handleSignIn(result)

승인된 계정이 하나도 없으면 NoCredentialException이 발생하므로, 이 경우에는 setFilterByAuthorizedAccounts(false)로 필터를 풀고 다시 요청하면 됩니다.
보안을 위해 setNonce로 재생 공격을 방지할 것을 권장합니다.
공식 문서는 SecureRandom으로 생성한 32바이트 난수를 Base64 URL-safe 방식으로 인코딩해 전달하는 함수를 예시로 제시합니다.

fun generateSecureRandomNonce(byteLength: Int = 32): String {
    val randomBytes = ByteArray(byteLength)
    SecureRandom().nextBytes(randomBytes)
    return Base64.encodeToString(randomBytes, Base64.NO_WRAP or Base64.URL_SAFE or Base64.NO_PADDING)
}

버튼 플로우 만들기​

Google은 바텀 시트와 함께 Sign in with Google 버튼을 둘 다 구현할 것을 권장합니다.
사용자가 바텀 시트를 닫았거나, 디바이스에 Google 계정이 없거나, 기존 계정이 재인증을 요구하는 경우에 버튼이 필요하기 때문입니다.
버튼용 요청은 GetSignInWithGoogleOption으로 만듭니다.

val signInWithGoogleOption: GetSignInWithGoogleOption = GetSignInWithGoogleOption.Builder(
    serverClientId = WEB_CLIENT_ID
).setNonce(generateSecureRandomNonce())
    .build()

로그인 응답 처리하기​

응답은 CustomCredential 형태로 반환됩니다.
타입이 GoogleIdTokenCredential.TYPE_GOOGLE_ID_TOKEN_CREDENTIAL인지 확인한 뒤 파싱합니다.

fun handleSign(result: GetCredentialResponse) {
    val credential = result.credential
    if (credential is CustomCredential &&
        credential.type == GoogleIdTokenCredential.TYPE_GOOGLE_ID_TOKEN_CREDENTIAL
    ) {
        val googleIdTokenCredential = GoogleIdTokenCredential.createFrom(credential.data)
        // idToken을 서버로 보내 검증합니다
    }
}

인증과 인가가 분리되는 점​

기존 SDK는 인증과 인가를 한 번의 호출로 처리할 수 있었지만, 새 방식에서는 명확히 분리됩니다.
인증은 Credential Manager가, Drive 접근 같은 특정 데이터 권한 요청은 AuthorizationClient API가 맡습니다.
사용자 흐름을 사용자 의도에 맞게 매핑하는 데 도움이 된다고 문서는 설명합니다.
로그아웃 시에는 clearCredentialState()를 호출해 모든 인증 정보 제공자의 세션을 정리해야, 다음 로그인에서 전체 로그인 옵션을 다시 볼 수 있습니다.

실무 관점​

MTS처럼 계정 기반의 금융 앱에서는 로그인과 권한 요청을 분리할 수 있다는 점이 오히려 장점입니다.
전제 조건으로는 Google Cloud 프로젝트의 웹 클라이언트 ID(setServerClientId에 전달) 설정이 필요하고, 동의 화면에 앱 이름을 표시하려면 브랜드 검증도 마쳐야 합니다.
서버 측에서는 ID 토큰과 함께 nonce를 검증하는 로직을 추가하는 것을 권장합니다.

마치며​

Google Sign-In for Android의 제거는 시점만 남았을 뿐 확정된 흐름입니다.
Credential Manager는 패스키까지 아우르는 통합 API이므로, 로그인 UI를 손보는 김에 함께 이전하는 것을 권장합니다.

네이티브 크래시를 잡는 릴리스 — CameraX 1.7.0-rc01 들여다보기

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.
2026년 10월 21일에 공개된 CameraX 1.7.0-rc01의 릴리스 노트를 정리해드리겠습니다.

현재 상황​

CameraX는 카메라 기능을 단말 파편화 없이 구현할 수 있게 돕는 Jetpack 라이브러리입니다.
신분증 촬영, 얼굴 인증처럼 금융 앱에서도 카메라 기능은 흔하게 쓰입니다.
반면 카메라 파이프라인의 네이티브 영역에서 발생하는 크래시는 재현이 어렵고 대응 비용이 큽니다.
이번 rc는 그런 네이티브 크래시 수정과 API 정리에 무게가 실린 릴리스입니다.

CameraX 1.7.0-rc01 살펴보기​

네이티브 SIGSEGV 크래시 수정​

SurfaceProcessor가 입력 SurfaceTexture를 해제하는 시점에, 연결된 SurfaceRequest가 먼저 가비지 컬렉션되면 네이티브 SIGSEGV가 발생하던 버그가 수정되었습니다.
타이밍에 의존하는 문제라 특정 단말과 특정 시나리오에서만 나타나고, 주로 크래시 리포트에서만 보이는 유형입니다.
이펙트나 필터로 SurfaceProcessor를 직접 다루는 앱이라면 이번 수정이 반가울 것입니다.

Surface 누수와 OpenGL 크래시 수정​

CameraEffect의 executor나 HandlerThread가 SurfaceOutput이 닫히기 전에 종료되면, Surface 누수와 네이티브 OpenGL 크래시가 발생하던 문제가 수정되었습니다.
카메라 파이프라인의 종료 순서가 리소스 정리와 직결된다는 점을 보여주는 사례입니다.

Camera2Interop — 인터페이스에서 추상 클래스로 전환​

UseCaseCamera2Interop, ImageCaptureCamera2Interop, SessionConfigCamera2Interop, CameraControlCamera2Interop이 인터페이스에서 추상 클래스로 바뀌었습니다.
소스 호환성에 영향을 줄 수 있는 변경이니, interop 클래스를 직접 참조하는 코드가 있다면 1.7.0 적용 전에 컴파일을 확인해야 합니다.
한편 1.7.0-alpha03부터는 Kotlin DSL 확장 블록으로 interop을 쓰는 방식이 권장되고 있습니다.

// 1.7.0-alpha03부터 권장되는 방식 — Kotlin DSL 확장 블록
val preview = preview {
    camera2Interop {
        // Camera2 설정을 이 블록 안에 지정합니다
    }
}

Low Light Boost와 Torch — last setting wins​

저조도 부스트와 토치를 동시에 켜려고 하면 요청이 거부되던 동작이 바뀌었습니다.
이제는 마지막에 설정한 쪽이 이기는 방식으로 동작합니다. 하나를 켜면 다른 하나가 자동으로 꺼집니다.
저조도 부스트가 켜진 상태에서도 촬영 시 플래시가 터지도록 함께 개선되었습니다.

물리 카메라에 UseCase 바인딩​

CameraInfo.getPhysicalCameraInfos()에서 얻은 물리 카메라의 CameraSelector로 UseCase를 바인딩할 수 있게 되었습니다.
물리 CameraSelector로 CameraInfo를 조회하면 논리 카메라가 아닌 물리 카메라의 정보가 반환됩니다.
멀티 카메라 단말에서 특정 렌즈를 직접 다루는 기능에 활용할 수 있습니다.

camerax-lifecycle = { module = "androidx.camera:camera-lifecycle", version.ref = "camerax" }

androidx.lifecycle:lifecycle-runtime 의존성은 2.10.0으로 올라갔습니다.
번들로 제공되는 lifecycle runtime lint 검사가 AGP 9.5.0-alpha04 이상에서 동작하려면 이 버전이 필요합니다.

실무 관점​

신분증 촬영이나 얼굴 인증 흐름이 있는 MTS 앱에서는 네이티브 크래시 수정이 안정성 지표에 직결됩니다.

아직 rc 단계이므로 프로덕션 적용은 stable 승격을 기다리는 것이 안전합니다.

마치며​

연락처 직접 쓰기가 막힌다 — 차기 Android 릴리스의 WRITE_CONTACTS 동작 변경

October 22, 2026 · 2 min read
Way
Android Developer

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.
Android Developers' Blog에 2026년 10월 21일 올라온 연락처 관련 동작 변경 소식을 정리해드리겠습니다.

현재 상황​

지금까지는 WRITE_CONTACTS 권한을 받아 ContentResolver로 연락처에 직접 쓰는 방식이 가능했습니다.
송금 수취인 저장, 지인 초대 같은 기능에서 쓰이던 패턴입니다.
그런데 차기 Android 릴리스를 타깃하는 앱부터는 이 직접 쓰기가 막힌다고 공지되었습니다.
읽기 쪽이 이미 Contact Picker로 정리된 데 이어, 쓰기 쪽도 시스템 UI 경유로 수렴하는 흐름입니다.

바뀐 내용 살펴보기​

WRITE_CONTACTS 직접 쓰기 제한​

차기 릴리스를 target으로 하는 앱은 WRITE_CONTACTS 권한으로 연락처에 직접 쓸 수 없게 됩니다.
권한이 선언되어 있어도 쓰기 동작이 차단되는 행위 변경입니다.

시스템 제공 UI로 추가·편집하기​

추가와 편집은 시스템이 제공하는 UI, 즉 인텐트 기반 흐름을 쓰도록 바뀌었습니다.
연락처 앱의 편집 화면을 띄워 사용자가 직접 확인하고 저장하는 방식입니다.

// 연락처 추가 — 시스템 UI를 통해 저장
val intent = Intent(ContactsContract.Intents.Insert.ACTION).apply {
    type = ContactsContract.RawContacts.CONTENT_TYPE
    putExtra(ContactsContract.Intents.Insert.NAME, "홍길동")
    putExtra(ContactsContract.Intents.Insert.PHONE, "010-1234-5678")
}
startActivity(intent)

이 방식은 저장 전에 사용자가 내용을 확인할 수 있어, 잘못된 연락처가 등록되는 일을 줄여줍니다.

읽기 흐름과의 정합성​

읽기 쪽은 Android 17부터 Contact Picker가 표준입니다.
READ_CONTACTS 권한 없이 필요한 데이터 필드만 지정해, 사용자가 고른 연락처에만 접근합니다.
쓰기 제한까지 더해지면 연락처 접근 전반이 시스템 UI 경유라는 하나의 원칙으로 정리됩니다.

실무 관점​

ContentResolver.insert로 연락처를 직접 쓰던 코드가 있다면 targetSdk 상향 계획과 함께 감사 대상에 올려야 합니다.
WRITE_CONTACTS 권한 요청 흐름도 함께 정리할 수 있습니다.
시스템 UI 경유 방식은 사용자 확인이 개입되므로, 무음 저장을 기대하던 UX라면 흐름을 다시 설계해야 합니다.

마치며​

연락처 쓰기 제한은 권한 최소화 흐름의 연장선에 있는 변경입니다.
차기 릴리스 대응 체크리스트에 연락처 쓰기 경로를 미리 넣어두는 것이 안전합니다.

DataStore 1.3.0이 준비 중인 것들 — Tink 암호화와 새로운 Builder API

October 21, 2026 · 4 min read
Way
Android Developer

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.
최근 30일 내 릴리스 중 하나를 골라 심화 해설을 하겠습니다.
DataStore 1.3.0-rc01(2026년 10월 12일)까지 이어진 1.3.0 라인의 변경 사항을 정리해드리겠습니다.

현재 상황​

DataStore 1.2.1은 안정 채널의 최신입니다.
그 위로 1.3.0 라인이 alpha 단계를 거치며 2026년 10월 12일 rc01에 도달했습니다.
rc01 자체는 버그 수정 위주이지만, 1.3.0이 안정으로 오면 두 가지 큰 변화가 함께 옵니다.
Tink 기반 암호화 지원과 새로운 Builder API입니다.
두 기능 모두 alpha07(2026년 3월 11일)에 이미 확정된 내용입니다.

DataStore 1.3.0 살펴보기​

datastore-tink 아티팩트와 AeadSerializer​

새 아티팩트 androidx.datastore:datastore-tink가 추가되었습니다.
핵심 클래스는 AeadSerializer로, 기존 Serializer<T>를 감싸는 래퍼입니다.
내부는 Tink의 AEAD(Authenticated Encryption with Associated Data)로 암호화·복호화를 수행합니다.
JVM과 Android 타깃 모두에서 사용할 수 있습니다.
공식 문서의 사용 순서는 세 단계입니다.

// 1. Tink API로 키 생성
val keysetHandle =
    AndroidKeysetManager.Builder()
        .withSharedPref(applicationContext, "keyset", "keyset_prefs")
        .withKeyTemplate(KeyTemplate.createFrom(PredefinedAeadParameters.AES256_GCM))
        .withMasterKeyUri("android-keystore://master_key")
        .build()
        .keysetHandle

// 2. 기존 serializer를 감싸는 AeadSerializer 생성
val aeadSerializer = AeadSerializer(
    aead = keysetHandle.getPrimitive(
        RegistryConfiguration.get(),
        Aead::class.java,
    ),
    wrappedSerializer = ExistingSerializer,
    // ciphertext swapping 공격 방지를 위한 고유 이름
    associatedData = "settings.json".encodeToByteArray(),
)

// 3. 기존 serializer 대신 aeadSerializer로 DataStore 생성
val dataStore = dataStore(
    fileName = "settings.json",
    serializer = aeadSerializer,
    scope = scope,
)

마스터 키는 Android Keystore에 두는 패턴이 권장됩니다.
associatedData에는 파일마다 고유한 이름을 넣어, 암호문을 서로 바꿔치기하는 공격을 막습니다.
alpha10에서는 GeneralSecurityException이 CorruptionException으로 감싸지도록 바뀌었습니다.
암호화 실패가 DataStore의 CorruptionHandler 흐름에 자연스럽게 녹아들게 된 것입니다.

DataStore.Builder<T> — DataStoreFactory의 후계자​

DataStore.Builder<T>가 DataStoreFactory의 공식 대체 API로 도입되었습니다.
공식 릴리스 노트는 모든 사용자에게 Builder로의 마이그레이션을 권장합니다.
가장 큰 차이는 스코프 전달 방식입니다.
Builder는 CoroutineScope가 아니라 CoroutineContext를 요구합니다.
호출자가 viewModelScope 같은 짧은 생명주기의 스코프를 넘겨도, DataStore가 그 생명주기에 묶이지 않게 하려는 설계입니다.
구조적 동시성(structured concurrency) 관점에서 올바른 방향입니다.
또한 setCorruptionHandler로 손상 시 처리 로직을 직접 주입할 수 있게 되었습니다.
alpha09에서는 ReThrowCorruptionHandler가 public으로 공개되기도 했습니다.

웹 플랫폼 지원 (alpha08)​

DataStore가 웹 타깃 지원을 넓혔습니다.
WebOpfsStorage로 OPFS(Origin Private File System)를 지원합니다.
크로스탭 알림은 BroadcastChannel, 분산 락은 Web Locks API를 씁니다.
WebLocalStorage와 WebSessionStorage API로 저장소 타입도 명시적으로 관리할 수 있습니다.

rc01에서 바뀐 것​

1.3.0-rc01의 API 변경은 소규모입니다.
EdgeToEdge#enable() 대신 WindowCompat#enableEdgeToEdge(Window)를 쓰도록 정리되었습니다.
lifecycle-runtime 의존성이 2.10.0으로 올라갔는데, 이는 AGP 9.5.0-alpha04 이상에서 번들된 lifecycle lint 검사가 동작하기 위한 요구사항입니다.

의존성 선언​

# libs.versions.toml 예시
[versions]
datastore = "1.3.0-rc01"

[libraries]
datastore = { module = "androidx.datastore:datastore", version.ref = "datastore" }
datastore-tink = { module = "androidx.datastore:datastore-tink", version.ref = "datastore" }

실무 관점​

Builder에 넘기는 CoroutineContext에는 반드시 Job이 있어야 하고, 애플리케이션 스코프여야 합니다.
공식 문서의 Warning에도 명시된 대로, 컨텍스트가 취소되면 DataStore 내부 동작이 중간에 멈춥니다.
viewModelScope를 그대로 넘기는 실수를 하지 않도록 주의해야 합니다.
Tink 도입 시에는 associatedData를 파일명과 일치시켜 관리하는 규칙을 팀에 정해 두는 것이 좋습니다.
민감 데이터 저장소가 늘어나면 키 로테이션 정책도 함께 논의해야 합니다.

마치며​

DataStore 1.3.0은 저장(암호화)과 생성(Builder API) 두 축을 한 번에 끌어올립니다.
안정 릴리스 전에 Tink 암호화 대상 데이터와 Builder 전환 범위를 정리해 두시기 바랍니다.

전체를 잠그지 말고 신뢰하는 origin만 허용하기 — WebView v156의 cross-origin isolation allowlist

October 21, 2026 · 4 min read
Way
Android Developer

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.
이번 10월 Google System Updates에서 공개된 Android WebView v156의 새 API에 대해 설명해드리겠습니다.

배경​

SharedArrayBuffer는 웹 스레드 간 메모리를 공유하는 기능입니다.
멀티스레드 Wasm이나 고성능 웹 렌더링에서 핵심이 되는 API이기도 합니다.
그런데 Spectre 계열 취약점 이후, 이 기능은 cross-origin isolation이라는 울타리 뒤로 들어갔습니다.
페이지 전체에 Cross-Origin-Opener-Policy와 Cross-Origin-Embedder-Policy를 걸지 않으면 쓸 수 없는 구조가 되었습니다.
웹에서는 이해할 만한 조치였지만, WebView를 쓰는 하이브리드 앱에서는 이야기가 다릅니다.
하나의 WebView 안에서 인증·광고·외부 위젯 등 신뢰 수준이 다른 origin이 함께 도는 경우가 많기 때문입니다.
전체 페이지를 격리하면 다른 콘텐츠가 깨지고, 격리를 안 하면 멀티스레드 Wasm을 못 쓰는 딜레마가 생겼습니다.

WebView v156의 allowlist API 살펴보기​

2026년 10월 7일에 릴리스된 Android WebView v156의 변경 로그에 새 API가 등장했습니다.
"신뢰할 수 있는 origin에 대해 SharedArrayBuffer 같은 cross-origin isolated 기능을 선택적으로 허용하는, 설정 가능한 allowlist를 이용한 새 Android WebView API"라는 설명입니다.
격리 단위를 "페이지 전체"에서 "지정한 origin 목록"으로 낮춘 셈입니다.

Cross-Origin Isolation이 요구되는 이유​

SharedArrayBuffer는 프로세스 간에 공유되는 고해상도 타이머 역할을 할 수 있습니다.
공격자가 이를 이용해 캐시 타이밍을 재면 Spectre 계열의 부채널 공격이 가능해집니다.
그래서 브라우저들은 COOP: same-origin과 COEP: require-corp 헤더를 함께 요구해 왔습니다.
두 헤더가 있으면 해당 문서는 다른 origin 프로세스와 메모리를 공유하지 않음이 보장됩니다.

기존 WebView에서의 선택지​

기존에는 크게 두 가지 선택지만 있었습니다.
첫째, 모든 콘텐츠를 격리 상태로 올리는 방법입니다.
신뢰할 수 없는 서드파티 iframe까지 같은 격리 정책을 따라야 해서 현실적이지 않았습니다.
둘째, 아예 SharedArrayBuffer를 포기하는 방법입니다.
멀티스레드 Wasm을 쓰는 차트 라이브러리나 문서 렌더러가 싱글스레드로 떨어졌습니다.

Allowlist가 바꾸는 것​

allowlist 방식에서는 격리를 포기하지 않습니다.
대신 개발자가 "이 origin만큼은 격리된 것으로 취급해도 된다"고 명시하는 allowlist를 둡니다.
신뢰하는 자사 도메인의 Wasm 차트 모듈만 허용하고, 광고 iframe은 그대로 두는 설계가 가능해집니다.
보안 모델을 이분법에서 세밀한 제어로 바꾼 것입니다.

응답 헤더 복습 (개념 예시)​

allowlist는 WebView 클라이언트 측 설정이지만, 기본이 되는 격리 헤더는 서버에서 내려줍니다.
아래는 웹 표준의 일반적인 헤더 조합입니다.

Cross-Origin-Opener-Policy: same-origin
Cross-Origin-Embedder-Policy: require-corp

두 헤더가 모두 있어야 브라우저가 해당 문서를 cross-origin isolated 상태로 표시합니다.
allowlist API는 이 위에 "어떤 origin을 신뢰 목록에 넣을지"를 얹는 개념입니다.
정확한 클래스명과 메서드명은 아직 공식 WebView 문서에 공개되지 않았습니다.
변경 로그에도 "Some features may be experimental"이라는 주의 문구가 붙어 있습니다.
따라서 실제 도입 전에는 WebView 릴리스 노트와 Chromium 문서를 다시 확인해야 합니다.

실무 관점​

allowlist는 "신뢰 경계"를 코드로 표현하는 작업입니다.
목록에 넣는 origin 하나하나가 공격 표면이 되므로, 목록은 최소 단위로 유지하는 것이 원칙입니다.
MTS처럼 WebView로 시세·차트를 보여주는 앱이라면, 차트 모듈 origin만 허용하고 나머지는 기존 정책을 유지하는 방식이 현실적입니다.
allowlist가 적용되는 WebView 버전 범위를 앱에서 미리 확인해 두는 것도 필요합니다.
구형 WebView에서는 API 자체가 없어 기능이 조용히 비활성화될 수 있기 때문입니다.

마치며​

WebView v156의 allowlist API는 보안과 성능 사이의 이분법을 깨는 첫 공식 경로입니다.
전체 격리가 부담스러웠던 하이브리드 앱이라면, 신뢰 origin 목록 설계부터 시작해 보시기 바랍니다.

Grab이 R8와 프로파일 기반 최적화로 ANR 32%·콜드스타트 35%를 줄인 방법

October 20, 2026 · 5 min read
Way
Android Developer

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.
Grab이 R8와 프로파일 기반 최적화로 ANR과 콜드스타트를 줄인 사례에 대해 설명해드리겠습니다.

배경​

2026년 10월 19일, 새 Android Developers Blog(developer.android.com/blog)에 Grab의 성능 최적화 사례가 올라왔습니다.
조건은 10년 된 코드베이스, 1,000만 줄이 넘는 코드, 수백 개의 서드파티 라이브러리였습니다.
Grab이 겪던 문제는 새 버전 릴리스 직후마다 ANR이 급증하는 것이었습니다.
원인은 많은 DEX 파일을 읽는 초기화 오버헤드였습니다.
플레이의 클라우드 프로파일은 일반적인 흐름은 최적화해 주지만, Dagger 그래프 초기화 같은 앱 고유의 시작 경로는 커버하지 못합니다.
이런 경로는 JIT 컴파일과 백그라운드 최적화에 며칠간 의존하게 되고, 그 사이 사용자가 ANR을 겪는 구조였습니다.
해법은 R8 최적화와 베이스라인·스타트업 프로파일을 3단계로 나눈 점진 도입이었습니다.
최종 결과는 사용자 체감 ANR −32.5%, 앱 다운로드 크기 −30.4%, 콜드스타트 −35%입니다.
핵심은 Dagger 의존성 그래프 초기화 같은 핵심 사용자 여정을 베이스라인 프로파일에 직접 담아, 설치 즉시 머신 코드로 컴파일되게 만든 것입니다.

3단계 점진 도입​

1단계 — R8 Compat 모드와 프로파일 (2025년 출시)​

레거시 ProGuard 기본 파일에서 proguard-android-optimize.txt로 옮기며 R8 최적화를 켰습니다.
10년 된 코드베이스라 레거시 설정과 리플렉션 사용을 손봐야 했습니다.
동시에 베이스라인 프로파일과 스타트업 프로파일을 합친 릴리스를 냈습니다.
결과는 사용자 체감 ANR −25%, 다운로드 크기 −16%, 콜드스타트 −27% 개선이었고, 릴리스 직후 ANR 급증 현상이 사라졌습니다.

2단계 — R8 Full Mode 전환 (2026년 출시)​

1단계 출시 9개월 뒤의 일입니다.
여기에 ANR −10%p, 크기 −14%p, 콜드스타트 −10%p가 추가로 얹혔습니다.
Retrofit, Firebase, Jetpack Compose 같은 표준 라이브러리는 내장 룰 덕분에 문제없이 통과했습니다.
반면 거대한 자체 코드의 리플렉션 구간은 하나씩 해결해야 했습니다.
대표적인 사례가 두 가지입니다.
최신 Gson 릴리스의 consumer keep rules를 적용해 JSON 파싱을 지켰습니다.
자바 동적 프록시는 런타임에 리플렉션으로 인터페이스 구현체를 생성하는 구조라 R8이 컴파일 시점에 사용을 감지하지 못해 크래시가 나는 구간이 있었습니다.
이는 폭넓은 예외가 아니라 해당 클래스에만 좁게 적용하는 타깃 킵룰로 처리했습니다.
크기를 불리지 않으면서 안정성을 지킨 방식입니다.

3단계 — 킵룰 거버넌스 (진행 중)​

R8 Configuration Analyzer로 킵룰 위생을 수치화하고 있습니다.
Optimizations 점수는 72%에서 78.2%로, Shrinking은 73%에서 79.1%로, Obfuscation은 79.6%에서 81.7%로 올랐습니다.
다운로드 크기는 추가로 약 3.6% 감소했습니다.
새 킵룰은 정당화와 리뷰를 요구하는 사전 머지 CI 가드레일을 붙이는 중입니다.
최적화 점수를 CI 대시보드에서 추적해 회귀를 병합 전에 잡겠다는 계획입니다.

테스트와 빌드 운영​

수백만 줄을 전부 테스트할 수 없으니, 킵룰을 좁히는 범위에 해당하는 코드에 테스트를 집중하고 반복적으로 정제하는 방식을 택했습니다.
하이브리드 빌드(Bazel로 디버그, Gradle로 R8 릴리스)라 R8 실험에 원격 CI가 최대 2시간 걸렸습니다.
데일리 QA 빌드를 프로덕션 R8 동작과 맞춰 격차를 메웠습니다.
mapping.txt와 configuration.txt 수집·업로드(Firebase Crashlytics에 자동 업로드, Play Console용 디오보스케이션 매핑 번들링)를 자동화해 디버깅 사이클을 줄였습니다.

내 코드 예시​

Grab 1단계에 해당하는 R8 기본 세팅은 다음과 같습니다.

// app/build.gradle.kts — Grab 1단계에 해당하는 R8 기본 세팅
android {
    buildTypes {
        release {
            isMinifyEnabled = true
            isShrinkResources = true
            proguardFiles(
                getDefaultProguardFile("proguard-android-optimize.txt"), // ← 레거시 파일에서 교체
                "proguard-rules.pro"
            )
        }
    }
}

핵심 여정을 프로파일에 담는 Macrobenchmark 테스트는 다음과 같습니다.

// baselineprofile 모듈 — 핵심 여정을 프로파일에 담는 Macrobenchmark 테스트
@OptIn(ExperimentalBaselineProfilesApi::class)
class StartupBaselineProfileGenerator {
    @get:Rule
    val baselineProfileRule = BaselineProfileRule()

    @Test
    fun startup() = baselineProfileRule.collect("com.example.app") {
        // 시작부터 홈 진입까지: Grab이 Dagger 그래프 초기화 경로를
        // 프로파일에 담은 것과 같은 원리
        startActivityAndWait()
    }
}

동적 프록시 구간을 지키는 킵룰은 다음과 같습니다.

# proguard-rules.pro — 동적 프록시 구간은 좁은 범위로만 킵 (Grab 2단계 방식)
-keep class com.example.net.ProxyService
-keepclassmembers class com.example.net.ProxyService { *; }

실무에서 주의할 점​

  • R8 Full Mode는 킵룰 정리 없이는 갈 수 없습니다. Grab도 1단계를 2025년에, 2단계를 그 9개월 후에 출시했습니다. 릴리스 빌드에 isMinifyEnabled = true만 켜면 끝나는 것이 아니라, 리플렉션 사용 구간(동적 프록시, Gson 리플렉션 어댑터, 난독화-민감 API)을 좁은 범위의 킵룰로 지키는 작업이 본체입니다.
  • 베이스라인 프로파일은 우리 앱의 핫패스를 직접 정하는 것입니다. 플레이 클라우드 프로파일이 앱 시작 경로를 커버하지 못하면 매주 릴리스 때마다 ANR이 급증합니다. 매크로벤치마크로 핵심 여정을 프로파일에 담으면 설치 즉시 AOT 컴파일되니, 시작 경로 최적화의 1순위로 둘 만합니다.
  • 킵룰은 CI로 지켜야 합니다. 한 번 최적화한 뒤에는 Configuration Analyzer 점수를 CI 대시보드에 띄우고, 킵룰 추가를 리뷰 대상으로 삼는 것이 장기 전략입니다.
  • 동적 프록시와 리플렉션 구간에 대한 과도한 -keep은 앱 크기를 불립니다. Grab이 그랬듯 클래스 단위로 좁혀 적용하고, 테스트는 킵룰 변경 범위에 집중하는 것이 효율적입니다.

마치며​

R8와 프로파일 기반 최적화는 한 번에 전환하는 것이 아니라 단계로 나눠 숫자로 확인하며 도입하는 것이 핵심입니다.
킵룰을 CI로 관리하는 거버넌스까지 갖춰야 최적화 효과가 유지됩니다.

2026년 10월 7일, Compose BOM의 두 축이 베타로 나왔습니다.
androidx.compose.runtime:runtime:1.13.0-beta01와 androidx.compose.material3:material3:1.5.0-beta01입니다.
같은 날 stable도 runtime 1.12.1과 material3 1.4.0으로 함께 릴리스되었습니다.
둘 다 아직 베타지만 소스 브레이킹 변경이 포함되어 있어, 지금 미리 파악해 두면 나중에 스테이블로 올릴 때 수월합니다.
공식 AndroidX 릴리스 노트(Material3, Runtime)를 기준으로 실무에 닿는 변경만 정리합니다.
참고로 이 글은 최근 30일 이내 릴리스를 다루는 심화 해설입니다.

무엇이 달라졌는지​

Slider와 RangeSlider의 상태 분리​

가장 큰 소스 브레이킹 변경입니다.
Material3 1.5.0-alpha29에서 Slider와 RangeSlider의 onValueChange가 필수 파라미터가 되었고, 파라미터 순서도 바뀌었습니다.
무상태(stateless) 오버로드는 deprecated(일부는 hidden) 처리되었고, 상태를 별도 객체로 분리하는 방식으로 이관이 권장됩니다.

// 기존 방식 (1.5.0에서 deprecated)
var value by remember { mutableFloatStateOf(0.5f) }
Slider(value = value, onValueChange = { value = it })

// 새 방식 — 상태를 별도 객체로 분리
val state = remember { SliderState(value = 0.5f) }
Slider(state = state)

var range by remember { mutableStateOf(0.2f..0.8f) }
RangeSlider(value = range, onValueChange = { range = it })
// → val state = remember { RangeSliderState(startValue = 0.2f, endValue = 0.8f) }
//   RangeSlider(state = state)

함께 바뀐 사항은 다음과 같습니다.

  • RangeSliderState의 activeRangeStart와 activeRangeEnd가 startValue와 endValue로 개명되었습니다.
  • SliderState는 더 이상 공개적으로 DraggableState를 구현하지 않습니다. 바이너리 호환 유지를 위해 DraggableState는 SliderState에 복원되었고, onValueChange가 nullable인 오버로드는 hidden deprecated로 유지됩니다.

소스 코드는 고쳐야 하지만 이미 빌드된 바이너리는 깨지지 않게 설계된 셈입니다.

computedStateOf의 읽기 전용 강제​

runtime 1.13.0-beta01부터 computedStateOf의 계산 블록 안에서 state에 쓰면 IllegalStateException이 던져집니다.
이전에도 쓰면 안 되는 패턴이었지만 실제로는 조용히 넘어가거나 이상한 무효화(invalidation)를 일으키곤 했습니다.
이는 외부 기여로 들어온 SnapshotStateObserver 읽기 시 예상 밖 무효화 수정과 같은 맥락입니다.
계산 블록은 순수하게 읽고 반환만 한다는 규칙이 강제됩니다.

Kotlin 2.2와 AGP 요구사항​

Compose 라이브러리들이 Kotlin 2.2를 타깃으로 빌드되고, kotlinc 2.2가 필요합니다.
또 androidx.lifecycle:lifecycle-runtime:2.10.0 의존성 업데이트 때문에, 번들된 lifecycle lint 체크가 동작하려면 AGP 9.5.0-alpha04 이상이 필요합니다.
툴체인 전체가 2.2와 37.1 라인으로 움직이고 있다는 신호입니다.

compileSdk 37.1 전이적 요구​

Compose 라이브러리의 compileSdk가 37.1로 올라갔습니다.
이는 Compose를 쓰는 모든 앱과 라이브러리도 compileSdk를 37.1로 올려야 한다는 뜻입니다.
Android 17(targetSdk 37) 대응을 아직 하지 않았다면, Compose 1.13과 1.5 스테이블로 올라가는 시점이 강제 마이그레이션 시점이 됩니다.

그 외 변경 사항​

  • 비밀번호 필드의 기본 난독화 방식이 RevealLastTyped에서 TextObfuscationMode.System으로 바뀝니다. SecureTextField와 OutlinedSecureTextField의 기본값 변경입니다.
  • Float.NaN 관련 리컴포지션 스킵 버그가 수정되었습니다. Dp.Unspecified(내부적으로 Float.NaN 기반)를 인자로 받은 컴포저블이 인자가 변하지 않았는데도 리컴포지션을 스킵하지 못하던 문제입니다.
  • BottomAppBar와 연관 API가 스테이블로 승격되었고, BasicAlertDialog가 Experimental을 졸업했습니다.
  • LocalMotionScheme이 제거되고 MaterialTheme.motionScheme으로 교체되었습니다.
  • ExposedDropdownMenu가 멤버 함수에서 ExposedDropdownMenuBoxScope의 확장 함수로 변경되어 import를 새로 잡아야 합니다.
  • 새로운 material3-ripple 라이브러리가 추가되었습니다. 기존 material-ripple의 대체이며 inset focus ring을 지원합니다.
  • DatePicker가 월 이동 가용성을 표시 월 인덱스에서 직접 계산해 1프레임에 해결되도록 개선되었습니다.
  • TopAppBarDefaults.enterAlwaysScrollBehavior의 reverseLayout 오버로드가 1.4 호환을 위해 deprecated(경고)로 복원되었습니다.
  • HorizontalCenteredHeroCarousel의 maxItemWidth가 preferredItemWidth로 개명되었고, 멀티애스펙트 캐러셀 API가 전역 carouselParallaxScrollEffect 모디파이어로 단순화되었습니다.
  • runtime에서는 movableContent 이동 시 wrapper 슬롯을 들고 있던 LinkComposer 메모리 누수가 수정되었고, CompositionObserver가 패스당 1회 해결되도록 변경되었으며, 오프-메인 스레드 ComposeTracer가 지원됩니다.

실무에서 주의할 점​

  • Slider 사용처를 전수 조사해야 합니다. 금융 앱에 수수료 슬라이더나 투자 금액 조절 같은 Slider와 RangeSlider가 있다면 1.5.0 스테이블 전에 상태 분리 방식으로 바꿔 두는 것이 좋습니다. onValueChange 필수화는 컴파일 에러로 드러나지만, 파라미터 순서가 바뀐 오버로드는 시그니처 자체가 바뀌어 에러가 나거나 deprecated로 걸리므로 리뷰는 한 번씩 필요합니다.
  • computedStateOf와 derivedStateOf 블록 안에서 값을 쓰는 코드가 있는지 검사해야 합니다. IllegalStateException은 런타임에 발생하므로, 코드 검색으로 계산 블록 안에 대입이 있는지 미리 확인하는 것이 안전합니다.
  • Kotlin 2.2와 AGP, compileSdk 37.1은 묶어서 계획해야 합니다. Compose 1.13은 Kotlin 2.2를, lint는 AGP 9.5.0-alpha04 이상을, Compose는 compileSdk 37.1을 각각 요구하므로 서로 의존합니다. 하나씩 따로 올리기보다 한 스프린트에 묶어 CI에서 함께 검증하는 편이 낫습니다.
  • 비밀번호 입력 UX 변경은 기획과 디자인 부서와 공유해야 합니다. 기본값이 System으로 바뀌면 타이핑 중 마지막 글자를 잠깐 보여주는 동작이 사라집니다. 보안 정책상 환영할 변화지만, 릴리스 노트 한 줄로 바뀌는 UX라 미리 공유하지 않으면 버그 문의가 들어올 수 있습니다.
  • 베타 릴리스이므로 스테이블 전에 API가 또 바뀔 수 있습니다. 이 글에서 다룬 내용은 베타 시점에 확정된 변경 기준입니다.

마치며​

Compose 1.13과 Material3 1.5는 베타 단계에서 미리 확인해 두면 스테이블 상향이 훨씬 수월해집니다.
특히 Slider의 상태 분리와 툴체인 요구사항은 일정을 잡아 미리 준비하는 것이 좋습니다.

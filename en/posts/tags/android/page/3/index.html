테스트도 minSdk 24 시대로 — AndroidX Test 1.8.0-alpha03과 Espresso 3.8.0-alpha03 살펴보기

November 3, 2026 · 4 min read
Way
Android Developer

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.
2026년 10월 29일에 공개된 AndroidX Test 1.8.0-alpha03과 Espresso 3.8.0-alpha03 그룹 릴리스에 대해 설명해드리겠습니다.

배경​

Android 테스트 코드는 앱 코드만큼 오래 유지됩니다.
그런데 테스트 라이브러리가 지원하는 최소 SDK가 앱의 최소 SDK보다 낮으면, 테스트 코드 안에 오래된 SDK를 위한 분기 로직이 계속 남습니다.
이번 AndroidX Test 알파 그룹은 바로 이 지점을 정리합니다.
그룹 전체가 최소 SDK 24로 올라가며, SDK 24 미만을 위한 로직을 제거했습니다.
알파 버전이므로 운영 앱에 바로 적용하기보다는, 변경 내용을 미리 파악하고 테스트 모듈의 방향을 정하는 데 의미가 있습니다.

AndroidX Test 1.8.0-alpha03 살펴보기​

그룹 릴리스 구성​

2026년 10월 29일에는 테스트 그룹 전체가 함께 올라갔습니다.
Core는 1.8.0-alpha03, Espresso는 3.8.0-alpha03입니다.
Espresso Device는 1.2.0-alpha03, JUnit 확장은 1.4.0-alpha03, Truth 확장은 1.8.0-alpha03입니다.
Runner와 Rules도 1.8.0-alpha03, Orchestrator와 Services는 1.7.0-alpha03, Monitor는 1.9.0-alpha04입니다.
참고로 alpha03 항목 자체에는 별도의 변경 목록이 적혀 있지 않습니다.
실질적인 변경 내용은 직전 버전인 10월 15일의 alpha01에 담겨 있습니다.
따라서 이번 글에서는 alpha01의 변경을 중심으로 살펴보겠습니다.

dependencies {
    androidTestImplementation("androidx.test:core:1.8.0-alpha03")
    androidTestImplementation("androidx.test:core-ktx:1.8.0-alpha03")
    androidTestImplementation("androidx.test.espresso:espresso-core:3.8.0-alpha03")
    androidTestImplementation("androidx.test.ext:junit-ktx:1.4.0-alpha03")
}

최소 SDK 24로의 상향​

alpha01에서 그룹 전체의 최소 SDK가 24로 올라갔습니다.
Core와 Espresso, Espresso Device, JUnit 확장이 모두 같은 기준을 적용했습니다.
SDK 24는 Android 7.0에 해당합니다.
SDK 24 미만을 위한 로직이 제거되면서, 테스트 라이브러리 내부가 단순해졌습니다.
앱의 최소 SDK가 이미 24 이상이라면, 테스트 의존성만으로 인한 제약은 줄어듭니다.
반대로 앱의 최소 SDK가 24보다 낮다면, 이 알파 라인을 적용할 수 없습니다.
안정 버전은 여전히 Core 1.7.0과 Espresso 3.7.0이므로, 운영 모듈에서는 안정 버전을 유지하는 것이 안전합니다.

Espresso의 새로운 Intent 매처​

Espresso alpha01에는 IntentMatchers에 부정 매처가 추가되었습니다.
doesNotHaveFlag와 doesNotHaveFlags가 그 대상입니다.
Intent에 특정 플래그가 없어야 하는 경우를 검증할 때 사용합니다.
기존에는 플래그가 있는 경우를 확인하는 매처가 중심이었습니다.
부정 조건을 직접 표현할 수 있게 되면서, Intent 검증 코드가 읽기 쉬워집니다.
예를 들어 화면 전환 시 특정 플래그가 붙지 않아야 하는 정책을 테스트 코드로 남길 수 있습니다.

버그 수정 내용​

alpha01의 버그 수정도 함께 살펴볼 필요가 있습니다.
SDK 36 API를 사용할 때 TestLooperManagerCompat에서 불필요했던 리플렉션이 제거되었습니다.
dumpThreadStates가 예외를 던지는 경우, AppNotIdleException을 억누르지 않도록 수정되었습니다.
Espresso.onIdle의 트레이싱이 제거되었습니다.
UiControllerImpl의 NullPointerException이 수정되었습니다.
isDisplayingAtLeast 매처는 상위 뷰의 스케일을 반영하도록 수정되었습니다.
스케일이 적용된 상위 뷰 안에 있는 뷰의 표시 비율 판정이 더 정확해집니다.

@Test
fun detailScreen_showsTitle() {
    ActivityScenario.launch(MainActivity::class.java)
    onView(withId(R.id.title))
        .check(matches(isDisplayingAtLeast(90)))
}

실무에서 적용할 때​

알파 버전은 새로운 기능 확인용으로 사용하는 것이 좋습니다.
운영 앱의 테스트 모듈은 안정 버전인 Core 1.7.0과 Espresso 3.7.0을 유지합니다.
별도 브랜치에서 알파 버전을 올려보고, 테스트 전체가 통과하는지 확인합니다.
특히 최소 SDK 24 상향이 테스트 모듈의 최소 SDK 설정과 충돌하지 않는지 확인합니다.
통과한다면, 안정 버전이 나올 때 마이그레이션 범위를 미리 파악해 둘 수 있습니다.

마치며​

AndroidX Test 알파 라인은 최소 SDK 24로의 정리와 Intent 매처 보강을 담고 있습니다.
테스트 코드의 오래된 분기를 줄이고, 검증 표현을 더 직접적으로 만드는 방향입니다.

BaseViewModel을 상속하지 않고 조합하기 — Kotlin 위임과 Lifecycle 2.11 스코프 ViewModel

November 3, 2026 · 4 min read
Way
Android Developer

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.
최근 Medium에서 다뤄진 BaseViewModel의 위임 전환과 Lifecycle 2.11의 스코프 ViewModel을 함께 살펴보겠습니다.

배경​

대부분의 성숙한 Android 코드베이스에는 BaseViewModel 파일이 있습니다.
처음에는 일회성 메시지나 로딩 표시 같은 보일러플레이트를 줄이는 것이 목적입니다.
그런데 시간이 지나면 네트워크 검사, 분석 추적, 오류 다이얼로그, 페이지네이션, 세션 로그아웃까지 쌓입니다.
결국 정적인 화면까지 수백 줄짜리 베이스 클래스를 상속하게 됩니다.
두 가지 부분 동작이 함께 필요한 화면에서는 단일 상속이 한계에 부딪힙니다.
페이지네이션과 검색을 동시에 쓰는 화면이 대표적인 경우입니다.
이 문제를 상속으로 해결하려 하면 베이스 클래스는 더 커지고, 단위 테스트는 모킹 중심으로 어려워집니다.

위임으로 BaseViewModel 대체하기​

기능별 홀더 인터페이스 나누기​

대안은 상속이 아니라 조합입니다.
Kotlin의 인터페이스 위임 by를 사용하면, 필요한 기능만 골라서 붙일 수 있습니다.
먼저 메시지 표시와 로딩 표시를 각각의 인터페이스로 나눕니다.
각 인터페이스는 상태와 상태 변경 함수만 정의합니다.
구현 클래스는 순수한 상태 보관 역할만 맡습니다.
코루틴 스코프는 ViewModel이 소유하므로, 홀더 안에 스코프를 두지 않습니다.

interface MessageHolder {
    val message: StateFlow<String?>
    fun showMessage(text: String)
    fun clearMessage()
}

class DefaultMessageHolder : MessageHolder {
    private val _message = MutableStateFlow<String?>(null)
    override val message: StateFlow<String?> = _message

    override fun showMessage(text: String) {
        _message.value = text
    }

    override fun clearMessage() {
        _message.value = null
    }
}

interface LoadingHolder {
    val isLoading: StateFlow<Boolean>
    fun setLoading(loading: Boolean)
}

class DefaultLoadingHolder : LoadingHolder {
    private val _isLoading = MutableStateFlow(false)
    override val isLoading: StateFlow<Boolean> = _isLoading

    override fun setLoading(loading: Boolean) {
        _isLoading.value = loading
    }
}

ViewModel에서 필요한 것만 조합하기​

ViewModel은 필요한 홀더만 위임으로 가져옵니다.
메시지만 필요한 화면의 ViewModel은 메시지 홀더만 위임합니다.
로딩까지 필요한 화면은 두 홀더를 함께 위임합니다.
두 가지 부분 동작이 필요한 경우에도, 두 인터페이스를 함께 위임하면 해결됩니다.
단위 테스트에서는 실제 홀더를 그대로 쓰거나, 작은 가짜 구현으로 교체할 수 있습니다.
베이스 클래스 전체를 모킹할 필요가 없어집니다.

class HomeViewModel(
    private val repository: HomeRepository
) : ViewModel(),
    MessageHolder by DefaultMessageHolder(),
    LoadingHolder by DefaultLoadingHolder() {

    fun load() {
        viewModelScope.launch {
            setLoading(true)
            try {
                repository.refresh()
            } catch (e: Exception) {
                showMessage("데이터를 불러오지 못했습니다.")
            } finally {
                setLoading(false)
            }
        }
    }
}

Lifecycle 2.11의 스코프 ViewModel​

위임과 함께 살펴볼 기능이 Lifecycle 2.11의 스코프 ViewModel입니다.
2.11.0은 2026년 6월 17일에 공개되었습니다.
ViewModelStoreProvider와 rememberViewModelStoreProvider, rememberViewModelStoreOwner가 새로 들어갔습니다.
이 API들은 ViewModel을 특정 UI 스코프에 묶는 용도입니다.
예를 들어 Pager의 각 페이지마다 별도의 ViewModel을 유지할 수 있습니다.
스코프에 묶인 ViewModel은 구성 변경에도 살아남습니다.
해당 Composable이 계층에서 제거되면 자동으로 정리됩니다.
Navigation3 연동도 함께 강화되었습니다.
ViewModelStoreNavEntryDecorator가 ViewModelStoreOwner를 받아, 중첩된 ViewModel에 생성 정보와 팩토리를 전달합니다.
removeViewModelStoreOnPop은 deprecated 되었습니다.
위임으로 기능을 나누고 스코프로 수명을 나누면, 베이스 클래스에 의존하지 않는 구조가 됩니다.

실무에서 적용할 때​

기존 BaseViewModel을 한 번에 지우지 않는 것이 좋습니다.
신규 화면부터 홀더 위임 방식으로 만들고, 기존 화면은 리팩터링 대상으로 따로 관리합니다.
홀더가 Android 프레임워크 타입에 의존하지 않도록 유지합니다.
그래야 단위 테스트에서 홀더를 그대로 재사용할 수 있습니다.
스코프 ViewModel은 Pager처럼 화면 단위 수명이 필요한 곳부터 적용합니다.
MTS처럼 화면이 많은 앱에서는, 수명 범위를 먼저 정하고 나서 도입하는 것이 안전합니다.

마치며​

상속은 기능을 한 번에 물려주지만, 필요 없는 기능까지 함께 물려줍니다.
위임은 필요한 기능만 골라서 조합하게 하고, 스코프 ViewModel은 수명까지 화면에 맞게 나눠줍니다.

터미널에서 에이전트와 함께 개발하기 Android CLI 공식 플러그인

November 2, 2026 · 4 min read
Way
Android Developer

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.
최근 Android Dev Summit 2026에서 공개된 Android CLI 공식 에이전트 플러그인에 대해 설명해드리겠습니다.

배경​

최근 Android 개발 환경에서는 AI 코딩 에이전트의 역할이 빠르게 커지고 있습니다.
Android Studio Rabbit 2에서는 IDE 안에서 원하는 에이전트를 고르는 Bring Your Own Agent가 안정화되었습니다.
그런데 모든 개발자가 IDE 안에서만 에이전트를 쓰는 것은 아닙니다.
터미널에서 작업하는 에이전트, CI 파이프라인에서 동작하는 자동화 흐름도 함께 고려해야 합니다.
이번에 공개된 Android CLI 공식 에이전트 플러그인은 바로 이 지점을 겨냥합니다.
터미널에 상주하는 에이전트에게 Android 개발 도구를 직접 쥐여주는 방식입니다.

Android CLI 공식 플러그인 살펴보기​

플러그인은 Claude Code, OpenAI Codex, Google Antigravity에 공식으로 제공됩니다.
플러그인을 설치하면 에이전트에게 android-cli 스킬이 추가됩니다.
이 스킬을 통해 에이전트는 프로젝트 생성, 가상 기기 관리, 실시간 UI 레이아웃 검사, Journeys 실행, 공식 Android Knowledge Base 검색을 수행합니다.

설치하기​

각 에이전트마다 설치 명령이 조금씩 다릅니다.
Claude Code에서는 마켓플레이스를 추가한 뒤 플러그인을 설치합니다.

claude plugin marketplace add android/android-cli-plugin
claude plugin install android-cli@android-cli-plugin

Codex에서는 두 번째 명령의 동사가 add라는 점이 다릅니다.

codex plugin marketplace add android/android-cli-plugin
codex plugin add android-cli@android-cli-plugin

Antigravity에서는 전용 마켓플레이스 경로로 설치합니다.

agy plugin install android-cli-plugin@antigravity-plugins-official

설치가 끝나면 에이전트 세션 안에서 Android CLI를 바로 사용할 수 있습니다.
먼저 android init으로 에이전트 설정을 마치고, android skills list로 제공되는 스킬 목록을 확인하는 흐름이 안내됩니다.

Compose 프리뷰와 기기 스트리밍​

터미널 기반 에이전트의 약점은 화면을 직접 보지 못한다는 점이었습니다.
Android CLI는 이 약점을 두 가지 기능으로 보완합니다.
첫 번째는 Compose 프리뷰 렌더링입니다.
에뮬레이터를 띄우거나 APK를 설치하지 않고도 프리뷰를 렌더링해 UI 변경을 즉시 시각적으로 검증합니다.
두 번째는 Android Device Streaming입니다.
Firebase 기반으로 원격 실기기를 연결해 기기별 이슈를 직접 확인합니다.
구글은 내부 테스트 기준으로 android preview를 활용한 에이전트가 UI 작업을 더 빠르게 마쳤다고 밝혔습니다.
이 수치는 구글 자체 테스트 결과이므로, 참고용 지표로 받아들이는 편이 좋습니다.

프로파일링과 분석​

Android CLI에는 성능 분석 도구도 함께 들어 있습니다.
Perfetto 기반 시스템 트레이스를 수집해 콜드 스타트 지연, UI 끊김, 백그라운드 깨어남을 살펴봅니다.
메모리 누수 탐지에는 오픈소스 LeakCanary가 내장되어 있습니다.
analyze 기능은 앱 번들과 라이브러리를 검사해 난독화, 최적화, 축소 점수를 확인합니다.
Google Play에 업로드하기 전에 스토어와 같은 기준으로 품질 신호를 미리 점검하는 용도입니다.

30개 이상의 Android 스킬​

플러그인과 함께 제공되는 Android 스킬은 30개 이상이며, 20개 이상의 영역을 다룹니다.
권한 보안, Glance 위젯 레이아웃, Compose 성능 최적화 같은 주제가 포함됩니다.
에이전트가 범용 지식만으로 추측하지 않고, Android 공식 가이드에 근거해 작업하도록 돕는 장치입니다.

Navigation 3 1.2 딥링크 API 살펴보기

November 2, 2026 · 4 min read
Way
Android Developer

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.
Android Dev Summit 2026에서 다시 강조된 Navigation 3 1.2의 딥링크 API에 대해 설명해드리겠습니다.

배경​

기존 Navigation 2에서는 딥링크를 내비게이션 그래프에 선언하고, 컨트롤러가 백스택을 관리했습니다.
Navigation 3에서는 방향이 달라졌습니다.
백스택을 개발자가 직접 상태로 소유하고, 화면 전환은 그 상태를 렌더링하는 방식입니다.
이런 구조에서는 딥링크 처리도 그래프 선언이 아니라, 요청을 받아 키로 변환하는 과정이 됩니다.
1.2.0 안정 버전(2026년 9월 23일 공개)은 이 과정을 위한 딥링크 API를 정식으로 제공합니다.
Kotlin Multiplatform 환경에서도 같은 API로 딥링크를 다룰 수 있다는 점이 특징입니다.

Navigation 3 1.2 딥링크 살펴보기​

딥링크 처리는 크게 세 단계로 나뉩니다.
요청 만들기, 매처 정의하기, 요청과 매처를 대조해 키 얻기가 그 순서입니다.
각 단계를 코드와 함께 살펴보겠습니다.

DeepLinkRequest 만들기​

DeepLinkRequest는 들어온 딥링크를 표현하는 객체입니다.
문자열 URI, DeepLinkUri, Android Intent 중 하나로 만들 수 있습니다.
URI 외에 액션이나 MIME 타입 같은 부가 정보는 타입 안전한 RequestExtras로 함께 담습니다.

import androidx.navigation3.runtime.deeplink.DeepLinkRequest
import androidx.navigation3.runtime.deeplink.DeepLinkUri
import androidx.navigation3.runtime.deeplink.requestExtras

// 문자열 URI로 요청 만들기
val request = DeepLinkRequest(uri = "https://www.example.com/home")

// DeepLinkUri로 요청 만들기
val deepLinkUri = DeepLinkUri("https://www.example.com/home")
val requestFromUri = DeepLinkRequest(uri = deepLinkUri)

// 액션과 MIME 타입을 함께 담기
val requestWithExtras = DeepLinkRequest(
    uri = "https://www.example.com/image",
    extras = requestExtras {
        put(DeepLinkRequest.ActionExtrasKey, "android.intent.action.VIEW")
        put(DeepLinkRequest.MimeTypeExtrasKey, "image/*")
    }
)

// Activity로 들어온 Intent에서 바로 만들기
val requestFromIntent = DeepLinkRequest(intent = intent)

RequestExtras는 키와 값의 쌍을 타입에 맞게 보관하는 컨테이너입니다.
예전처럼 문자열 키로 값을 꺼내 형변환하던 방식보다 실수가 줄어듭니다.

DeepLinkMatcher 정의하기​

DeepLinkMatcher는 요청을 어떤 내비게이션 키에 연결할지 정의합니다.
하나의 키에 여러 매처를 연결할 수 있습니다.
기본 제공되는 매처는 세 가지입니다.

import androidx.navigation3.runtime.deeplink.DeepLinkMatcher
import androidx.navigation3.runtime.deeplink.DeepLinkUri
import androidx.navigation3.runtime.deeplink.StaticKeyDeepLinkMatcher
import androidx.navigation3.runtime.deeplink.UriDeepLinkMatcher
import androidx.navigation3.runtime.deeplink.withBackStack

// 고정 화면으로 연결되는 매처
val homeMatcher = StaticKeyDeepLinkMatcher(
    HomeKey,
    listOf(DeepLinkMatcher.actionFilter(Intent.ACTION_VIEW))
)

// 경로 인자를 추출하는 매처
val userProfileMatcher = UriDeepLinkMatcher(
    DeepLinkUri("www.example.com/users/{id}"),
    serializer<UserProfileKey>()
).withBackStack { matchResult ->
    listOf(HomeKey, matchResult.key)
}

UriDeepLinkMatcher는 URI 패턴의 {id} 같은 플레이스홀더를 인자로 추출합니다.
withBackStack은 매칭에 성공했을 때 합성 백스택을 함께 만듭니다.
사용자가 딥링크로 상세 화면에 들어왔을 때, 뒤로 가기를 누르면 홈 화면으로 돌아가는 흐름을 이렇게 보장합니다.

요청 매칭하고 백스택 구성하기​

매처 목록을 준비했으면, 들어온 요청과 대조해 키를 얻습니다.
매칭 결과는 비교가 가능하므로, 여러 매처 중 가장 적합한 결과를 고를 수 있습니다.

val deepLinkMatchers = listOf(homeMatcher, userProfileMatcher)

val request = DeepLinkRequest(intent = intent)
val matchResult = deepLinkMatchers.firstNotNullOfOrNull { matcher ->
    matcher.match(request)
}

val backStack = rememberNavBackStack(
    matchResult?.key ?: HomeKey
)

이렇게 얻은 키를 rememberNavBackStack의 시작점으로 넘기면, 이후는 평소와 같은 NavDisplay 흐름으로 이어집니다.
딥링크로 들어온 경우와 앱 안에서 이동한 경우의 화면 렌더링 방식이 달라지지 않습니다.
한편 Activity를 딥링크로 열려면 AndroidManifest.xml에 intent-filter를 등록하는 절차는 여전히 필요합니다.

예측 뒤로 가기와 결과 전달​

1.2에는 딥링크 외에도 두 가지 보강이 함께 들어 있습니다.
첫 번째는 예측 뒤로 가기 연결을 단순화하는 NavigationBackHandler와 rememberNavigationEventState입니다.
전환 도중에 뒤로 제스처가 들어와도 애니메이션이 어긋나지 않도록 처리합니다.
두 번째는 화면 간 결과 전달을 위한 Result API입니다.
ResultEventBus를 통해 항목 간 결과를 주고받고, ResultEffect로 흐름 형태로 수집합니다.

실무 관점​

MTS에서 딥링크는 푸시 알림, 공유 링크, 외부 연동 등 여러 진입점으로 연결됩니다.
딥링크로 바로 열리는 화면이 민감 정보를 다룬다면, 진입 전에 로그인 상태와 접근 권한을 먼저 확인해야 합니다.
합성 백스택은 뒤로 가기 경로를 자연스럽게 만들지만, 스택에 쌓이는 화면이 민감 화면을 거치지 않는지 함께 검토해야 합니다.
URI 패턴은 서버나 마케팅 채널과 공유되므로, 패턴 변경 시에는 기존 링크의 호환 여부를 먼저 확인하는 편이 좋습니다.

마치며​

Navigation 3 1.2는 딥링크를 그래프 선언이 아니라 요청과 매칭의 문제로 정리했습니다.
타입 안전한 요청과 합성 백스택 덕분에, 진입 경로가 달라도 화면 흐름을 일관되게 유지할 수 있습니다.

Android 17 QPR3 Beta 3 살펴보기, API 변경 없는 분기 업데이트의 테스트 포인트

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.
2026년 10월 29일에 공개된 Android 17 QPR3 Beta 3에 대해 설명해드리겠습니다.

배경​

Android 17 정식 버전이 공개된 이후에도 플랫폼 업데이트는 분기 단위로 계속 이어집니다.
이 분기 업데이트를 Quarterly Platform Release라고 부릅니다.
QPR은 AOSP와 Pixel 기기에 Feature Drop 형태로 전달됩니다.
QPR3는 10월 초 Beta 1, 10월 중순 Beta 2에 이어 세 번째 베타 빌드입니다.
이번 베타는 새로운 API를 추가하지 않고, 보고된 문제를 수정하는 데 초점을 맞추고 있습니다.

Android 17 QPR3 Beta 3 살펴보기​

QPR의 성격​

QPR은 메이저 버전 업그레이드와 성격이 다릅니다.
앱에 영향을 주는 API 변경을 포함하지 않습니다.
따라서 기존 앱의 동작이 API 변경으로 깨질 가능성은 낮습니다.
대신 시스템 동작과 기기별 문제가 수정되며, 앱 호환성 테스트의 의미가 큽니다.

빌드 정보​

이번 베타의 빌드 번호는 기기별로 두 가지로 나뉩니다.
Pixel 11 시리즈는 DP11.261016.004 빌드를 사용합니다.
그 외 지원 기기는 DP11.261016.003 빌드를 사용합니다.
보안 패치 수준은 2026년 10월 5일 기준입니다.
Google Play 서비스는 26.36.33 버전이 함께 제공됩니다.
지원 대상은 Pixel 6a 이후 모델과 Android Emulator입니다.

Beta 3에서 수정된 내용​

공식 릴리스 노트에 따르면 이번 베타에서는 26건의 문제가 수정되었습니다.
대표적인 수정 항목은 다음과 같습니다.
Multiply 블렌드 모드 사용 시 이미지가 잘못된 투명도로 렌더링되던 문제입니다.
빠른 앱 전환 직후 홈 제스처를 수행할 때 Recents 화면이 깜빡이던 문제입니다.
스레드 멘션을 볼 때 앱이 충돌하던 문제입니다.
기기를 웹캠으로 사용할 때 화질이 저하되던 문제입니다.
화면이 무작위로 꺼졌다 켜지던 문제와 WPA-Enterprise PEAP 방식 Wi-Fi 로그인 실패 문제도 포함됩니다.

테스트 방법​

베타 빌드는 Android Beta Program에 가입하면 OTA로 받을 수 있습니다.
직접 이미지를 설치하는 경우에는 OTA 이미지를 사이드로드하는 방식을 사용합니다.

adb sideload ota.zip

에뮬레이터에서는 x86 64비트와 ARM v8-A 이미지가 지원됩니다.
베타 빌드에서는 보안 패치 수준을 코드로 확인할 수도 있습니다.

val patch = Build.VERSION.SECURITY_PATCH
Log.d("DeviceInfo", "Security patch: $patch")

실무 관점​

MTS와 같은 금융 앱에서는 베타 빌드 테스트의 목적을 분명히 정하는 것이 좋습니다.
API 변경이 없는 업데이트에서는 신규 API 대응보다 회귀 테스트가 우선입니다.
렌더링과 화면 전환, 카메라와 Wi-Fi 관련 수정이 포함된 만큼 해당 경로의 스모크 테스트를 먼저 수행합니다.
베타 빌드는 업무용 주력 기기가 아니라 테스트 전용 기기나 에뮬레이터에서 검증하는 것이 안전합니다.
베타에서 발견한 문제는 Beta Feedback 앱이나 이슈 트래커로 보고하는 흐름을 팀 안에 정해두면 좋습니다.

마치며​

QPR3 Beta 3는 API 변경 없이 26건의 문제를 다듬은 베타 빌드입니다.
정식 출시 전에 테스트 기기에서 회귀 테스트를 한 번 돌려보는 것이 이번 업데이트의 실용적인 대응입니다.

Java와 Kotlin by IntelliJ IDEA 1.0, VS Code와 Cursor에서 쓰는 IntelliJ의 언어 지능

October 31, 2026 · 4 min read
Way
Android Developer

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.
2026년 10월에 정식 1.0으로 공개된 Java and Kotlin by IntelliJ IDEA에 대해 설명해드리겠습니다.

배경​

에이전트가 구현을 맡는 비중이 커지면서 개발자의 편집 방식도 바뀌고 있습니다.
직접 코드를 길게 쓰는 시간보다 선언으로 이동하고 참조를 찾고 이름을 바꾸는 시간이 늘었습니다.
이런 기능은 Language Server Protocol이 태어난 이유와 정확히 맞닿아 있습니다.
언어 지원을 한 번 구현하면 LSP를 지원하는 어떤 에디터에서도 재사용할 수 있습니다.
JetBrains은 이런 흐름에 맞춰 IntelliJ IDEA의 JVM 언어 지능을 IDE 밖으로 꺼냈습니다.
프리뷰 공개 약 10주 뒤, VS Code와 Cursor용 확장 기능이 1.0에 도달했습니다.

Java and Kotlin by IntelliJ IDEA 1.0 살펴보기​

1.0에 담긴 기능​

1.0은 IntelliJ IDEA 데스크톱 IDE와 같은 Java와 Kotlin 언어 기술을 사용합니다.
Java와 Kotlin, 혼합 언어 프로젝트를 지원합니다.
스마트 코드 완성과 탐색, 코드 분석을 제공합니다.
리팩터링과 에디터 보조 기능도 포함되어 있습니다.
Maven과 Gradle, Bazel 빌드 도구를 지원합니다.
대규모 프로젝트와 모노레포에서도 빠른 성능을 목표로 합니다.
테스트 러너는 현재 JUnit을 지원합니다.
디버깅은 에뮬레이션된 중단점과 비동기 스택 트레이스를 포함합니다.

설치 방법​

확장 기능은 Visual Studio Marketplace나 Open VSX Registry에서 받을 수 있습니다.
에디터 안에서는 명령 팔레트에 아래 명령을 붙여넣는 방식으로 설치합니다.
Cursor에서는 IDE 모드로 전환한 뒤 같은 명령을 사용합니다.

.ext install JetBrains.intellij-server

설치가 끝나면 프로젝트를 열 때 빌드 파일을 기준으로 가져오기가 진행됩니다.
Maven과 Gradle, Bazel 중 프로젝트에 맞는 빌드 파일을 자동으로 인식합니다.
가져오기가 끝나면 Java와 Kotlin 언어 기능이 에디터에서 활성화됩니다.

Cursor 전용 지원​

Cursor에서는 Agents Window 전용 지원이 따로 마련되어 있습니다.
Agents Window는 자체 언어 서버 인스턴스를 이용해 분석 기능을 제공할 수 있습니다.
JSpecify 기반 널 가능성 지원과 Spring Framework 특화 분석이 포함됩니다.
이 출시는 Cursor 팀과의 긴밀한 협업으로 만들어졌다고 JetBrains은 설명합니다.

팀에서 함께 쓰기 위한 설정​

팀원 모두가 같은 확장을 쓰도록 권장 목록 파일로 공유할 수 있습니다.
프로젝트 루트에 아래 파일을 두면 VS Code가 확장 설치를 권합니다.

{
  "recommendations": [
    "JetBrains.intellij-server"
  ]
}

충돌 주의 사항​

Red Hat이나 Oracle의 Java 확장과는 코드 분석과 빠른 수정 기능이 겹칩니다.

Kotlin Toolchain 0.13 — 새 KMP 프로젝트는 kotlin new로 시작하기

October 8, 2026 · 3 min read
Way
Android Developer

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.
JetBrains가 공개한 Kotlin Toolchain 0.13에 대해 설명해드리겠습니다.

배경​

신규 Kotlin Multiplatform(KMP) 프로젝트를 시작할 때는 Gradle 설정 파일을 손으로 짜는 것부터 시작하는 경우가 많았습니다.
JDK나 Android SDK 같은 필수 도구가 갖춰져 있지 않으면, 새 노트북에서 프로젝트를 처음 열었을 때 동기화부터 실패하곤 했습니다.
이번 0.13부터 JetBrains는 신규 KMP 프로젝트에 이 툴체인을 쓰는 것을 공식 권장 경로로 제시했습니다.
자세한 내용은 Kotlin 블로그 원문에서 확인할 수 있습니다.

Kotlin Toolchain 살펴보기​

Kotlin Toolchain은 JVM·Android·iOS·멀티플랫폼·서버 앱을 하나의 CLI 진입점으로 만들고, 빌드하고, 테스트하고, 배포하는 도구입니다.
필수 도구들을 선언적 설정에 맞춰 자동으로 내려받아 주기 때문에 온보딩 과정의 마찰이 크게 줄어듭니다.

kotlin new: 대화형 프로젝트 생성​

0.13의 핵심은 kotlin new 명령입니다.
웹의 KMP Wizard처럼 앱 유형을 고르고 타깃 플랫폼을 선택하면 프로젝트가 생성됩니다.
기존 kotlin init도 같은 흐름으로 맞췄는데, 차이는 kotlin init이 현재 디렉터리에 바로 파일을 만든다는 점입니다.

# 새 프로젝트 생성 (대화형)
kotlin new

# 이미 설치돼 있다면 업데이트
kotlin update

Android 개발자 관점에서 달라진 부분​

  • Android SDK 자동 프로비저닝이 IDE까지 확장: 이전에는 kotlin build/kotlin run 때만 SDK가 자동 설치돼서, 빌드 전에 IDE로 먼저 열면 SDK 누락 오류가 났습니다. 이제 프로젝트 import 시점에도 누락된 SDK 컴포넌트를 자동으로 받아 줍니다.
  • namespace/applicationId 검증 강화: com.example.app 같은 샘플 ID로 실수로 배포 빌드를 만드는 실수를 막아 줍니다.
  • 다운로드 진행 표시: JDK, Android SDK, iOS 런타임, 컴파일러 다운로드가 CLI에 진행 바로 표시됩니다.

Swift Package Manager 의존성 지원​

Apple 타깃에서 SPM 패키지를 선언적으로 가져올 수 있게 됐습니다.
설정 파일에 저장소와 버전을 적으면 됩니다.

dependencies:
  - swiftPackage:
      repository: "https://github.com/firebase/firebase-ios-sdk.git"
      version: "12.17.0"
      products: ["FirebaseCore", "FirebaseFirestore", "FirebaseAnalytics"]

가져온 Objective-C API는 swiftPMImport 접두사로 네임스페이스가 붙어, Kotlin 코드에서 명시적으로 구분됩니다.
로컬 SPM 패키지는 localSwiftPackage 키로 연결할 수 있습니다.

빌드 속도: Kotlin/Native 컴파일러 캐시​

Kotlin/Native 재빌드가 빨라집니다.
컴파일된 네이티브 의존성을 빌드 간, 심지어 프로젝트 간에 캐시로 재사용하고, 프로젝트 코드는 파일 단위 캐시로 링크 시 바뀐 부분만 다시 컴파일합니다.
기존 settings.kotlin.compileIncrementally 설정을 그대로 쓰고, .klib 컴파일 자체는 전체로 수행됩니다.

그 외 변경 사항​

  • IDE 동기화 상태를 에디터에서 확인할 수 있게 됐습니다.
  • 멀티플랫폼 라이브러리 배포 시 Compose Resources와 SwiftPM 의존성 메타데이터가 아티팩트와 함께 게시되고, 서드파티 멀티플랫폼 라이브러리의 Compose Resources도 해석됩니다.
  • AI 에이전트 연동도 강화됐습니다. Compose Hot Reload MCP 서버와 Kotlin용 에이전트 스킬(npx skills add kotlin/kotlin-agent-skills)이 제공됩니다.
  • IDE 기능은 IntelliJ IDEA 2026.2.3 또는 Android Studio Rabbit 1(2026.2.1) 이상에서 최신 Kotlin Toolchain 플러그인과 함께 쓸 수 있습니다.

실무에서 주의할 점​

기존 Gradle 기반 프로젝트를 당장 마이그레이션해야 하는 것은 아닙니다.
JetBrains도 로드맵에서 Gradle 프로젝트의 공백을 먼저 메우는 데 집중하겠다고 밝혔습니다.
따라서 운영 중인 프로젝트는 기존 흐름을 유지하고, 신규 프로젝트나 사이드 프로젝트부터 적용해 보는 것이 안전합니다.

마치며​

새로 KMP를 시작한다면 kotlin new 한 번으로 Android·iOS 환경을 한 번에 맞추는 경험은 꽤 매력적입니다.
다음에 KMP 프로젝트를 시작할 일이 있으면 이 경로로 시작해 보시기 바랍니다.

AppState StateStore 첫 알파, Compose 상태를 앱 계층으로 끌어올리기

October 30, 2026 · 2 min read
Way
Android Developer

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.
2026년 10월 28일에 첫 알파로 공개된 AppState StateStore에 대해 설명해드리겠습니다.

배경​

Compose 상태는 보통 화면이나 ViewModel 안에 머무릅니다.
앱 전역에서 공유해야 하는 상태는 계층을 옮길 때마다 전달 코드가 늘어납니다.
상태를 앱 계층으로 끌어올리면 공유와 저장이 한곳에서 관리됩니다.
StateStore는 이 역할을 맡기 위해 새로 공개된 라이브러리입니다.

StateStore 살펴보기​

Compose 런타임 기반의 상태 저장소​

StateStore는 Compose 런타임을 기반으로 동작합니다.
스냅샷 상태를 앱 계층으로 끌어올려 커스텀 연동을 제공하는 래퍼입니다.
화면이 사라져도 상태의 수명을 앱 수준에서 유지할 수 있습니다.

DataStore 연동으로 상태 유지하기​

statestore-datastore 아티팩트는 상태 영속성을 제공합니다.
syncToDataStore로 스냅샷 상태를 DataStore 파일과 동기화할 수 있습니다.
앱을 다시 시작해도 이전 상태를 복원할 수 있습니다.

class MyApplication : Application() {
    val stateStore = StateStore()
    private val scope = CoroutineScope(SupervisorJob() + Dispatchers.Default)

    override fun onCreate() {
        super.onCreate()
        scope.launch {
            launch {
                try {
                    stateStore.syncToDataStore(
                        dataStoreFile("settings").absolutePath,
                        this
                    )
                } catch (e: Exception) {
                    e.printStackTrace()
                }
            }
        }
    }
}

의존성 추가하기​

Android 타깃 기준 의존성은 다음과 같습니다.

dependencies {
    implementation("androidx.appstate.statestore:statestore:1.0.0-alpha01")
    implementation("androidx.appstate.statestore:statestore-datastore:1.0.0-alpha01")
}

함께 공개된 Transform​

같은 날짜에 appstate-transform 아티팩트도 첫 알파로 공개되었습니다.
이 글에서는 StateStore의 개념과 저장 연동에 집중합니다.
Transform의 구체적인 활용은 후속 릴리스 노트에서 확인한 뒤 다루는 것이 좋습니다.

실무 관점​

첫 알파 단계이므로 운영 코드에 바로 도입하지 않는 것이 좋습니다.
상태를 앱 계층으로 올리면 수명과 동기화 시점을 직접 설계해야 합니다.
동기화 중 예외가 나면 상태가 저장되지 않으므로 실패 처리 경로를 함께 둡니다.
MTS처럼 세션과 설정 상태가 많은 앱에서는 저장 단위부터 나누는 것이 안전합니다.

마치며​

StateStore는 Compose 상태를 앱 계층에서 관리하는 새로운 선택지입니다.
DataStore 연동까지 함께 보면 상태 공유와 영속성을 한 구조로 정리할 수 있습니다.

프로퍼티 순서가 바뀌면 구조 분해 결과도 함께 바뀌는 문제가 있었습니다.

Kotlin 2.5.0-Beta2 살펴보기​

이름 기반 구조 분해​

이름 기반 구조 분해는 only-syntax 모드에서 정식 기능이 되었습니다.
기존 문법 val (name, age)는 위치 기반 동작을 그대로 유지합니다.
새 문법 (val name, val age)는 이름을 기준으로 값을 꺼냅니다.
순서와 무관하게 프로퍼티 이름으로 매칭되므로 리팩터링에 안전합니다.

data class User(val name: String, val age: Int)

fun printUser(user: User) {
    (val age, val name) = user
    println("$name, $age")
}

반환값 검사기​

반환값 검사기는 이번 릴리스에서 기본으로 활성화됩니다.
의미 있는 반환값을 버리고 호출하면 컴파일러가 경고를 냅니다.
검사 강도는 -Xreturn-value-checker 옵션으로 조절할 수 있습니다.
자체 함수에는 MustUseReturnValues 애너테이션으로 검사 대상을 표시할 수 있습니다.

kotlin {
    compilerOptions {
        freeCompilerArgs.add("-Xreturn-value-checker=check")
    }
}

Java 28 지원과 JDK 17 요구 사항​

Kotlin/JVM은 Java 28을 지원합니다.
컴파일러 실행에는 JDK 17 이상이 필요합니다.
Beta1에서는 오래된 JDK에서 경고만 나왔습니다.
Beta2와 정식 2.5.0에서는 오류가 나며, 임시 플래그로만 구버전 사용을 이어갈 수 있습니다.
2.5.20-Beta1부터는 JDK 17 이상이 필수입니다.
CI 머신의 JDK 버전을 먼저 확인하는 것이 좋습니다.

Swift Export와 네이티브 개선​

Swift Export는 새 DSL과 함께 베타 단계에 들어갔습니다.
Kotlin/Native 증분 컴파일은 Apple 타깃에서 기본으로 활성화됩니다.
멀티플랫폼 프로젝트의 iOS 빌드 시간이 줄어들 것으로 기대됩니다.

버전 적용 예시는 다음과 같습니다.

[versions]
kotlin = "2.5.0-Beta2"

실무 관점​

베타 릴리스이므로 운영 모듈에 바로 적용하지 않는 것이 좋습니다.
별도 브랜치에서 컴파일과 테스트를 먼저 통과시키는 것이 안전합니다.
이름 기반 구조 분해는 신규 코드부터 점진적으로 적용할 수 있습니다.
JDK 버전이 낮은 CI가 있다면 릴리스 전에 교체 계획을 세워야 합니다.

이름 기반 구조 분해와 반환값 검사기는 코드의 실수를 줄이는 방향의 개선입니다.
JDK 요구 사항까지 함께 확인하면 베타 검증이 한결 수월해집니다.

dependencies {
    implementation("androidx.appfunctions:appfunctions:1.0.0-beta01")
    ksp("androidx.appfunctions:appfunctions-compiler:1.0.0-beta01")
}
@AppFunction(isDescribedByKDoc = true)
suspend fun getFavoriteStockPrice(
    symbol: String
): StockPrice {
    // 관심 종목의 현재 시세를 조회하는 함수입니다.
    return repository.getPrice(symbol)
}

A2UI 알파​

에이전트의 답변이 텍스트로만 나오면, 사용자는 다시 앱 화면으로 돌아가 확인해야 합니다.
A2UI는 에이전트가 앱 자체의 컴포넌트로 만든 인터랙티브 화면을 그대로 보여주는 방식입니다.
Jetpack Compose용 네이티브 렌더러가 포함되어 있어, 에이전트 응답이 앱의 UI로 자연스럽게 이어집니다.
현재 알파 단계이며, AppFunctions와 함께 앱의 에이전트 경험을 구성하는 한 축입니다.

ML Kit Agentic API 알파​

온디바이스에서 동작하는 에이전트 기능은 ML Kit의 Agentic API가 담당합니다.
Gemini Nano 4를 기반으로 하며, 함수 실행과 대화 기록 저장, 오케스트레이션 루프 관리, 자동 가드레일을 함께 제공합니다.
앱 안에서 도구를 실행하는 에이전트를 만들 때, 호출과 기록과 안전장치를 직접 구현하지 않아도 됩니다.
AppFunctions로 공개된 기능도 이 API를 통해 발견하고 실행할 수 있습니다.

Connected Apps Platform 프리뷰​

앱의 서비스를 Gemini와 검색까지 연결하는 통로는 Connected Apps Platform 프리뷰가 담당합니다.
Android MCP나 원격 MCP 서버로 연동하고, Google Connected Console에서 등록해 관리합니다.
Google은 Adobe와 Peloton, Experian 등 50개 이상의 파트너 연동이 이미 Gemini 앱에서 동작하고 있다고 밝혔습니다.

실무 관점​

MTS 앱에 적용한다면, 노출할 함수의 범위를 정하는 일이 구현보다 먼저입니다.
주문이나 이체 같은 자금 이동 기능은 에이전트 호출 경로에 두지 않는 것이 안전합니다.
시세 조회나 관심 종목 확인처럼 읽기 전용 기능부터 베타 단계에서 검증하는 순서가 적절합니다.
아직 베타와 알파 단계라 API가 바뀔 수 있으므로, 노출 함수는 별도 모듈로 분리해 교체 비용을 낮추는 것이 좋습니다.

마치며​

AppFunctions는 앱을 화면의 집합이 아니라 에이전트가 호출할 수 있는 기능의 집합으로 바꾸는 시도입니다.
A2UI와 온디바이스 Agentic API가 함께 갖춰지면서, 앱 안에서의 에이전트 경험이 텍스트 응답을 넘어 실제 화면 동작으로 이어지게 되었습니다.

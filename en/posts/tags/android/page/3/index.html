Media3 1.12.0 알파 — 플래그 레지스트리와 Play services 이펙트

October 27, 2026 · 3 min read
Way
Android Developer

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.
2026년 10월 21일의 alpha01과 10월 26일의 alpha02로 공개된 Media3 1.12.0 알파 변경 사항에 대해 설명해드리겠습니다.

배경​

Media3는 ExoPlayer를 중심으로 재생, 세션, 변환, 이펙트를 묶은 미디어 라이브러리입니다.
현재 안정 버전은 1.11.1이며, 1.12.0은 알파 단계에서 다음 변경을 준비하고 있습니다.
공식 Media3 릴리스 노트를 기준으로 실무에 닿는 변경만 정리합니다.
알파 API는 정식 출시 전에 바뀔 수 있으므로, 적용 전에 변경 범위를 확인하는 것이 중요합니다.

Media3 1.12 알파에서 달라진 것​

중앙 플래그 레지스트리​

alpha01에서 실험적 기능 플래그를 관리하는 중앙 Flags 레지스트리가 추가되었습니다.
기존에 흩어져 있던 실험적 API를 플래그 API로 단계적으로 전환하는 기반이 됩니다.
카나리아 모드를 켜는 진입점도 함께 제공되어, 실험 기능을 단계적으로 공개하는 흐름을 만들 수 있습니다.
플래그가 늘어날수록 어떤 실험이 켜져 있는지 한곳에서 파악할 수 있다는 점이 실무적으로 의미가 있습니다.

Display P3 색 공간 지원​

C.COLOR_SPACE_DISPLAY_P3가 추가되고, MediaFormatUtil과 ColorInfo의 ISO 색상 매핑에서 Display P3가 지원됩니다.
광색역 콘텐츠를 다루는 화면에서는 색 공간 정보가 형식 변환 과정에서 유지되는지 확인해 볼 만합니다.
Ultra HDR 프레임 추출 시 BT.2020 색상이 sRGB로 잘리던 문제도 함께 개선되었습니다.
범위를 벗어난 색은 자르는 대신 부드럽게 압축되어 SDR 기본 이미지에 담깁니다.

재생 목록 메타데이터 확장​

MediaMetadata에 재생 목록 식별자와 카테고리가 추가되었습니다.
재생 목록 단위로 식별하고 분류하는 정보가 메타데이터 자체에 들어간다는 뜻입니다.
세션 쪽에서는 재생 목록 식별자, 제목, 아트워크, 카테고리를 채우는 엑스트라 키도 함께 추가되었습니다.

val metadata = MediaMetadata.Builder()
    .setPlaylistId("playlist-market-briefing")
    .setCategories(listOf("market", "briefing"))
    .build()

기본 동작 변경​

setLoadOnlySelectedTracks(true)가 기본값이 되었습니다.
선택되지 않은 비디오와 이미지 트랙은 로드하지 않으므로 메모리가 절약됩니다.
오디오와 텍스트 트랙은 항상 로드되어, 끊김 없는 트랙 전환을 유지합니다.
재생 중 선택되지 않았던 비디오 트랙을 새로 켜면 추가 버퍼링이 생길 수 있다는 점은 주의해야 합니다.
DASH 다중 기간 재생에서 다음 기간의 첫 청크 로드가 실패하면 재생이 멈추던 문제도 수정되었습니다.

Play services 이펙트 모듈​

alpha02에서는 새로운 media3-effect-play-services 모듈이 추가되었습니다.
비디오 향상 기능을 제공하는 EnhancementSessionDecorator와 음원 분리 기능을 제공하는 StudioSoundAudioProcessor가 포함됩니다.
이펙트 쪽에서는 스튜디오 사운드 기반 음원 분리 프로세서 구현도 함께 들어갔습니다.
Play services 모듈에 의존하는 기능이라, 단말의 Play services 제공 여부를 전제로 설계해야 합니다.

알파를 적용하는 의존성 선언은 다음과 같습니다.

dependencies {
    implementation("androidx.media3:media3-exoplayer:1.12.0-alpha02")
    implementation("androidx.media3:media3-effect-play-services:1.12.0-alpha02")
}

실무 관점​

알파 라이브러리는 프로덕션 모듈에 바로 올리기보다 별도 브랜치에서 검증하는 것이 안전합니다.
트랙 로드 기본값 변경은 재생 화면의 메모리와 전환 동작에 직접 영향을 주므로, 기존 재생 시나리오로 회귀 테스트를 먼저 돌려보는 것이 좋습니다.
자막 시간 오프셋 기능은 사이드로드 자막의 싱크를 맞추는 용도로, 재생을 중단하지 않고 교체할 수 있습니다.
MTS처럼 미디어가 부가 기능인 앱에서는, 재생 모듈 전체를 올리기보다 필요한 아티팩트만 골라 적용하는 편이 의존성 부담을 줄입니다.

마치며​

Media3 1.12 알파는 새 재생 기능보다 플래그 관리 체계와 색 공간, 메타데이터 같은 기반 정리에 무게가 실려 있습니다.
Play services 이펙트 모듈은 알파 단계의 새로운 축이라, 정식 출시 과정을 지켜보며 검증 범위를 정하는 것이 좋습니다.

Palette 1.1.0 — 이미지 대표 색 추출과 palette-ktx 통합

October 27, 2026 · 3 min read
Way
Android Developer

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.
2026년 10월 21일에 공개된 Palette 1.1.0과 이미지 대표 색 추출 방법에 대해 설명해드리겠습니다.

배경​

Palette는 이미지에서 대표 색상을 추출하는 Jetpack 라이브러리입니다.
배너 이미지나 종목 대표 이미지에서 배경색과 텍스트 색을 뽑아 화면 테마에 맞추는 용도로 사용됩니다.
1.0.0 이후 오랜만에 공개된 1.1.0은 기능 추가보다 정리 성격이 강합니다.
공식 Palette 릴리스 노트를 기준으로 변경 사항과 사용법을 정리합니다.

Palette 살펴보기​

대표 색 추출 방식​

Palette는 비트맵의 픽셀을 양자화해 색상 군집을 만든 뒤 대표 스와치를 계산합니다.
동기 생성은 메인 스레드를 막을 수 있으므로, 실무에서는 비동기 생성이나 백그라운드 스레드에서 실행하는 것이 안전합니다.
추출할 색상 개수는 빌더에서 조절할 수 있으며, 기본값은 16개입니다.

val palette = Palette.from(bitmap)
    .maximumColorCount(24)
    .generate()

스와치 종류​

추출 결과는 용도별로 나뉜 스와치로 제공됩니다.
getVibrantSwatch는 생동감 있는 대표 색, getMutedSwatch는 차분한 대표 색을 돌려줍니다.
각각 밝은 버전과 어두운 버전이 있으며, getDominantSwatch는 이미지에서 가장 큰 비중을 차지하는 색을 돌려줍니다.
스와치는 null을 돌려줄 수 있으므로, 사용할 때는 반드시 대체 색을 함께 준비해야 합니다.

val vibrant = palette.getVibrantSwatch()
val muted = palette.getMutedSwatch()
val dominant = palette.getDominantSwatch()

val backgroundRgb = vibrant?.rgb ?: muted?.rgb ?: 0xFF1A1A1A.toInt()
val titleTextRgb = vibrant?.titleTextColor ?: 0xFFFFFFFF.toInt()

Compose에서 사용하기​

Palette는 뷰 시스템 시절 라이브러리라 Compose 전용 API를 제공하지 않습니다.
비트맵을 받아 백그라운드에서 생성한 뒤, 결과 색을 Compose의 Color로 변환해 상태로 보관하는 방식이 일반적입니다.
이미지마다 한 번씩만 생성하고 결과를 캐시하면, 스크롤 화면에서도 반복 계산을 피할 수 있습니다.

@Composable
fun rememberPaletteColor(bitmap: Bitmap?): Color {
    var themeColor by remember { mutableStateOf(Color.Transparent) }
    LaunchedEffect(bitmap) {
        if (bitmap == null) return@LaunchedEffect
        val palette = withContext(Dispatchers.Default) {
            Palette.from(bitmap).generate()
        }
        val swatch = palette.getVibrantSwatch() ?: palette.getDominantSwatch()
        if (swatch != null) {
            themeColor = Color(swatch.rgb)
        }
    }
    return themeColor
}

1.1.0에서 달라진 것​

1.1.0의 가장 큰 변경은 JSpecify nullability 어노테이션 채택입니다.
Kotlin에서 엄격한 null 검사를 적용하려면 컴파일러 인자를 함께 설정해야 합니다.
또 하나의 변경은 palette-ktx 통합입니다.
Kotlin 확장 함수가 모두 메인 아티팩트로 들어갔고, palette-ktx는 호환 유지를 위한 빈 아티팩트로 남았습니다.
신규 프로젝트에서는 palette만 의존하면 되며, 기존 프로젝트에서는 palette-ktx 의존성을 정리할 수 있습니다.

dependencies {
    implementation("androidx.palette:palette:1.1.0")
}
kotlinOptions {
    freeCompilerArgs += listOf(
        "-Xjspecify-annotations=strict",
        "-Xtype-enhancement-improvements-strict-mode",
    )
}

실무 관점​

이미지에서 뽑은 색을 그대로 텍스트 배경에 쓰면 가독성이 깨질 수 있습니다.
스와치가 제공하는 제목 텍스트 색과 본문 텍스트 색을 함께 사용해야 대비가 유지됩니다.
서버 이미지 색이 매번 달라지는 화면에서는, 색 추출 실패 시 기본 테마로 떨어지는 분기를 먼저 만들어 두는 것이 안전합니다.
MTS처럼 정보 밀도가 높은 화면에서는 전체 테마를 바꾸기보다, 배너 카드 내부 강조색 정도로 범위를 제한하는 편이 무난합니다.

마치며​

Palette 1.1.0은 새 기능보다 nullability 정리와 아티팩트 통합에 초점이 맞춰져 있습니다.
기존 코드를 크게 바꾸지 않고 의존성만 정리할 수 있는 안정적인 업데이트입니다.

Android 17 QPR3 Beta 2 살펴보기

October 26, 2026 · 4 min read
Way
Android Developer

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.
2026년 10월 20일에 공개된 Android 17 QPR3 Beta 2에 대해 설명해드리겠습니다.

배경​

QPR은 Quarterly Platform Release의 약자입니다.
Android 17의 초기 릴리스 이후 분기 단위로 수정 사항과 개선 사항을 제공하는 업데이트 방식입니다.
QPR은 AOSP와 Pixel 기기의 Feature Drop으로 함께 제공됩니다.
앱에 영향을 주는 API 변경은 포함하지 않는 것이 특징입니다.
그럼에도 Google은 최신 QPR 베타 빌드의 이미지를 제공합니다.
앱에 영향을 줄 수 있는 변화가 있는지 미리 테스트해 볼 수 있도록 하기 위함입니다.
공식 Android 17 QPR3 릴리스 노트를 기준으로 정리합니다.

Beta 2 살펴보기​

빌드 정보​

Beta 2의 릴리스 날짜는 2026년 10월 20일입니다.
빌드는 DP11.261002.005이며, 보안 패치 수준은 2026-10-05입니다.
Google Play 서비스 버전은 26.36.33입니다.
에뮬레이터는 x86 64비트와 ARM v8-A를 지원합니다.
테스트 기기나 에뮬레이터에서 빌드를 확인하는 방법은 다음과 같습니다.

adb shell getprop ro.build.display.id

Beta 2에서 수정된 주요 이슈​

Beta 2의 수정 목록은 대부분 기기 동작과 시스템 UI에 집중되어 있습니다.
앱 개발 관점에서 눈여겨볼 만한 항목은 다음과 같습니다.

  • 기기가 간헐적으로 충돌하고 재부팅되는 문제
  • 모바일 데이터 사용 중 인터넷 퀵 세팅 타일에 텍스트가 계속 표시되는 문제
  • 외부 오디오 기기 연결 시 미디어 출력 대화상자가 모노크롬 시스템 테마를 무시하는 문제
  • 공유 시트에서 고정된 앱 옆 핀 아이콘 위치가 어긋나는 문제
  • 내부 PublishedApi 선언이 API lint와 소스 호환성 검사 오류를 유발하는 문제
  • WhatsApp 영상 통화 중 기기가 예기치 않게 종료되는 문제
  • 잠금 화면 진행 중 알림이 다른 UI 요소와 겹치고 패널 애니메이션이 끊기는 문제
  • 화면 회전 후 화면 녹화가 멈추고 프레임 캡처가 중단되는 문제
  • 표시 크기와 무관하게 시스템 UI, 글꼴, 앱이 비정상적으로 작게 렌더링되는 문제
  • 통화 종료 후 화면이 검게 변하고 응답하지 않는 문제
  • Face Unlock이나 카메라 사용 후 모션 센서가 계속 활성 상태로 남아 배터리가 소모되는 문제
  • Bluetooth 페어링 시간 초과로 페어링이 실패하는 문제
  • 앱 서랍에서 키보드 언어 전환 시 앱 서랍이 예기치 않게 닫히는 문제

Beta 1에서 이미 수정된 내용​

Beta 1은 2026년 10월 2일에 공개되었습니다.
빌드는 DP11.260918.005와 DP11.260918.006입니다.
앱 동작과 직접 연결되는 수정 사항도 포함되어 있습니다.

  • 미디어 컨트롤이 없는 앱에서 오디오 재생 중 출력 기기를 전환할 수 없던 문제
  • 퀵 세팅 타일에서 포그라운드 서비스를 시작할 때 앱이 충돌하던 문제
  • NFC 서비스가 첫 태그 스캔 후 DeadObjectException으로 충돌하고 태그 감지를 중단하던 문제
  • 지문 센서 잠금 해제 시 기기가 멈추고 응답하지 않던 문제
  • 눈을 뜬 상태 요구 옵션 선택 시 기기가 충돌하던 문제
  • ASCII가 아닌 오디오 속성 태그 처리 시 MediaPlayer가 충돌하던 문제
  • 앱 실행 시 멈추고 ANR이 발생하던 문제
  • 데스크톱 모드에서 외부 디스플레이를 사용하는 영상 통화 앱의 카메라 피드가 90도 회전하던 문제

실무 관점​

QPR 베타는 API 변경이 없는 업데이트입니다.
그래서 신규 API 대응보다는 기존 기능의 회귀 테스트가 중심이 됩니다.

Compose Runtime 1.13.0-beta02 — computedStateOf 계산 블록 읽기 전용 강제

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.
2026년 10월 21일에 공개된 Compose Runtime 1.13.0-beta02와 10월 7일의 beta01 변경 사항에 대해 설명해드리겠습니다.

배경​

Compose Runtime은 Compose의 상태 모델과 컴파일러 플러그인이 대상으로 하는 핵심 런타임입니다.
1.13 버전은 10월 7일에 beta01, 10월 21일에 beta02가 공개되었습니다.
이번 글은 Material3의 변경이 아니라 런타임의 상태 계산 규칙 변화에 초점을 맞춥니다.
공식 Compose Runtime 릴리스 노트를 기준으로 실무에 닿는 변경만 정리합니다.

Runtime 1.13 베타에서 달라진 것​

computedStateOf 계산 블록 읽기 전용 강제​

가장 주의해야 할 변경은 beta01에 들어갔습니다.
computedStateOf의 계산 블록은 이제 읽기 전용으로 강제됩니다.
계산 블록 안에서 상태를 쓰면 IllegalStateException이 발생합니다.
이전에는 계산 블록 안의 쓰기가 조용히 잘못 동작했습니다.
그 결과 예측하기 어려운 무효화 연쇄와 리컴포지션 루프가 생길 수 있었습니다.
이제 프레임워크가 잘못된 코드를 바로 가리켜 줍니다.
derivedStateOf도 같은 계산 블록 규칙을 사용하므로 동일한 주의가 필요합니다.

// 변경 전 — 계산 블록 안에서 상태를 쓰면 IllegalStateException이 발생합니다.
val totalPrice = remember {
    derivedStateOf {
        // 아래와 같은 쓰기는 1.13 베타부터 허용되지 않습니다.
        // discountApplied.value = true
        cartItems.sumOf { it.price }
    }
}

// 권장 방식 — 상태 변경은 이벤트 핸들러에서 수행합니다.
fun onItemAdded(item: CartItem) {
    cartItems.add(item)
}

val totalPrice = remember {
    derivedStateOf { cartItems.sumOf { it.price } }
}

ComputedState 메모리 누수 수정​

beta02에서는 ComputedState와 관련된 수정이 들어갔습니다.
기록된 상태 값이 해제되지 않던 메모리 누수가 수정되었습니다.
계산 블록이 Snapshot.withoutReadObservation을 호출할 때 무효화가 제대로 되지 않던 문제도 함께 수정되었습니다.
파생 상태를 많이 사용하는 화면에서는 메모리와 무효화 동작을 함께 점검해 볼 만합니다.

그 밖의 beta01 변경​

  • CompositionObserver는 한 컴포지션 패스당 한 번만 해석됩니다.
  • 진행 중인 컴포지션에서 setObserver를 호출하면 다음 패스부터 적용됩니다.
  • Movable content 삽입 시 onBeginComposition과 onEndComposition이 보고됩니다.
  • LinkComposer에서 movable content를 이동할 때 래퍼 그룹 슬롯을 유지하던 누수가 수정되었습니다.
  • lifecycle-runtime이 2.10.0으로 업데이트되었습니다.
  • 해당 버전은 AGP 9.5.0-alpha04 이상에서 번들된 lifecycle runtime lint 검사가 동작하는 데 필요합니다.
  • ComposeTracer가 메인 스레드 밖에서도 사용할 수 있게 되었습니다.
  • Float.NaN이나 Double.NaN을 @Composable 함수에 전달하면 리컴포지션 스킵이 되지 않던 문제가 수정되었습니다.
  • Dp.Unspecified이 Float.NaN 기반이라 이 수정과 직접 연결됩니다.
  • 라이브러리가 Kotlin 2.2를 대상으로 하며 kotlinc 2.2가 요구됩니다.

베타를 적용하는 의존성 선언은 다음과 같습니다.

dependencies {
    implementation("androidx.compose.runtime:runtime:1.13.0-beta02")
}

실무 관점​

MTS 앱처럼 파생 상태를 많이 쓰는 코드에서는 계산 블록 안의 쓰기부터 점검하는 것이 좋습니다.
계산 블록은 순수한 계산만 담당하고, 상태 변경은 클릭이나 콜백 같은 이벤트 핸들러에서 수행합니다.
베타는 디버그 빌드에서 먼저 적용하고, 스테이블 전환 전에 회귀 테스트를 거치는 것이 안전합니다.
Dp.Unspecified 관련 스킵 수정은 레이아웃 측정 코드의 리컴포지션 횟수에도 영향을 줄 수 있습니다.

마치며​

1.13 베타는 상태 계산 블록의 규칙을 명확히 하고 누수를 정리하는 업데이트입니다.
계산 블록 안의 쓰기를 찾아내는 것만으로도 스테이블 전환 전에 한 가지 위험을 줄일 수 있습니다.

AI 에이전트가 만드는 네이티브 UI: Jetpack Compose A2UI 렌더러 살펴보기

October 25, 2026 · 3 min read
Way
Android Developer

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.
2026년 10월 21일 공개된 A2UI 1.0.0-alpha02에 대해 설명해드리겠습니다.

배경​

AI 에이전트는 이제 작업을 추론하고 도구를 호출하고 대화를 이어갈 수 있습니다.
그런데도 에이전트가 사용자에게 네이티브 화면을 보여주는 일은 여전히 어렵습니다.
에이전트는 앱이 어떤 컴포넌트를 가지고 있는지 모르기 때문에, 날짜 선택기나 확인 버튼 같은 실제 UI를 건네줄 수 없습니다.
A2UI는 이 간극을 메우기 위한 프로토콜입니다.

A2UI 살펴보기​

A2UI의 핵심 아이디어는 단순합니다.
에이전트가 임의의 UI 코드를 만들어내는 대신, 클라이언트가 미리 정해둔 카탈로그 안에서만 UI를 조합합니다.

카탈로그가 계약이 됩니다​

모든 A2UI 인터페이스는 컴포넌트 카탈로그를 중심으로 동작합니다.
카탈로그는 에이전트가 사용할 수 있는 UI 요소와 속성, 함수를 선언합니다.
에이전트는 카탈로그에 등록되지 않은 컴포넌트를 만들어낼 수 없으므로, 렌더링 결과가 예측 가능한 범위를 벗어나지 않습니다.

임의 코드 실행이 없습니다​

A2UI 렌더러의 가장 중요한 성질은 임의 코드를 실행하지 않는다는 점입니다.
에이전트는 구조화된 데이터를 보내고, 클라이언트는 그 데이터를 네이티브 Compose 컴포넌트로 렌더링합니다.
서버에서 온 설명이 앱 안에서 코드로 실행되는 일이 없으므로, 신뢰 경계를 넘는 UI도 안전하게 다룰 수 있습니다.

Jetpack A2UI 렌더러의 구조​

Jetpack의 A2UI 렌더러는 디자인 시스템과 무관한 렌더링 엔진과 구체적인 카탈로그 구현을 분리합니다.
데이터 계층인 a2ui-model과 a2ui-engine이 프로토콜 메시지를 파싱하고 처리합니다.
UI 계층인 compose-runtime과 compose-ui가 앱과 카탈로그를 위한 API를 제공합니다.
Material 3 컴포넌트로 구성된 기본 카탈로그도 함께 제공되어, 별도 카탈로그 없이 바로 시작할 수 있습니다.

dependencies {
    implementation("androidx.a2ui:a2ui-engine:1.0.0-alpha02")
    implementation("androidx.a2ui:a2ui-model:1.0.0-alpha02")
    implementation("androidx.a2ui.compose:compose-runtime:1.0.0-alpha02")
    implementation("androidx.a2ui.compose:compose-ui:1.0.0-alpha02")
}

alpha02에서 바뀐 점​

이번 alpha02에서는 기본 카탈로그의 함수 목록이 인터페이스로 바뀌었습니다.
구현체는 openUrl만 구현하면 되고, 나머지 함수는 기본 구현을 쓰거나 개별적으로 재정의할 수 있습니다.
클라이언트가 렌더링할 수 있는 카탈로그를 먼저 알리는 기능도 추가되어, 에이전트와 렌더러 사이의 capability 협상이 가능해졌습니다.

val catalog = materialA2uiBasicCatalogV1(
    functions = A2uiBasicCatalogV1.Functions(context)
)

실무 관점​

아직 알파 단계이므로, 프로덕션 화면에 바로 적용할 라이브러리는 아닙니다.
다만 MTS의 챗봇이나 상담 흐름처럼, 에이전트가 화면을 제시해야 하는 기능에는 참고할 만한 설계입니다.
카탈로그를 계약으로 삼는 방식은, 에이전트 출력이 화면을 망가뜨리는 위험을 구조적으로 줄여줍니다.
도입을 검토한다면, 렌더링할 컴포넌트 목록을 카탈로그로 먼저 정리하는 것부터 시작하는 편이 좋습니다.

마치며​

A2UI는 에이전트에게 화면을 맡기되, 그릴 수 있는 범위는 앱이 먼저 정한다는 발상입니다.
알파 단계이지만, AI와 네이티브 UI가 만나는 지점을 어떻게 설계해야 하는지 보여주는 좋은 출발점입니다.

AppFunctions 1.0.0-beta01 살펴보기​

앱 메타데이터 이름 변경​

AppFunctionAppMetadata의 description이 instructions로 바뀌었습니다.
XML 속성 이름도 함께 바뀌었습니다.
MCP의 명명 관례에 맞추기 위한 변경입니다.
앱 수준의 동작 방식과 제약을 에이전트에게 전달하는 필드이므로, 이름을 보고 역할을 짐작하기가 더 쉬워졌습니다.
기존 메타데이터를 쓰고 있었다면 이번 베타에서 이름을 함께 바꿔야 합니다.

isDescribedByKDoc 기본값 제거​

AppFunctionDeclaration, AppFunctionSerializable, AppFunctionSignature에서 isDescribedByKDoc의 기본값이 제거되었습니다.
이제 값을 반드시 명시적으로 지정해야 합니다.
이 값은 KDoc 주석을 에이전트가 읽는 설명으로 쓸지를 결정합니다.
기본값이 사라졌다는 것은, 설명 방식을 개발자가 의식적으로 선택하라는 뜻으로 읽힙니다.
KDoc을 대충 쓰면 에이전트가 함수를 잘못 이해할 수 있으니, 주석이 곧 스키마라는 점을 염두에 두어야 합니다.

@RequiresApi(36)
@AppFunctionServiceEntryPoint(
    serviceName = "PortfolioAppFunctionService",
    appFunctionXmlFileName = "portfolio_app_function_service"
)
abstract class BasePortfolioAppFunctionService : AppFunctionService() {

    /**
     * 보유 종목의 요약 정보를 반환합니다.
     *
     * @param accountId 조회할 계좌의 식별자입니다.
     */
    @AppFunctionDeclaration(isDescribedByKDoc = true)
    suspend fun getPortfolioSummary(
        accountId: String
    ): PortfolioSummary = withContext(Dispatchers.IO) {
        portfolioRepository.getSummary(accountId)
    }
}

위 예시에서 함수는 기본적으로 메인 스레드에서 실행됩니다.
그래서 블로킹 작업이 있다면 suspend 함수로 만들고 백그라운드 디스패처로 전환해야 합니다.
공식 API 레퍼런스에서도 같은 주의사항을 강조하고 있습니다.

그 밖의 API 변경​

AppFunctionName이 androidx.appfunctions.metadata 패키지에서 androidx.appfunctions 패키지로 이동했습니다.
임포트 경로를 정리하지 않으면 컴파일이 깨지니, 베타로 올릴 때 임포트부터 확인하는 편이 좋습니다.
AppFunctionResourceContainer와 AppFunctionTextResource는 실험적 API로 표시되었습니다.
@AppFunctionStringValueConstraint의 정규식 패턴은 android.os.PatternMatcher 기반의 패턴 매처로 대체되었습니다.
테스트 쪽에서는 AppFunctionTestRule이 AppFunctionServiceEntryPoint를 지원하게 되었습니다.
테스트에서 엔트리 포인트를 직접 다룰 수 있게 된 만큼, 함수 단위 검증이 조금 수월해졌습니다.

버그 수정​

자바 라이브러리 디슈가링을 켠 앱에서 java.time 파라미터 타입의 역직렬화가 실패하던 문제가 수정되었습니다.
생성되는 파일 이름에 특정 운영체제에서 허용되지 않는 문자가 들어갈 수 있던 문제도 수정되었습니다.
SDK 37 이상에서 URI 권한이 두 번 부여되던 문제도 함께 수정되었습니다.
어느 하나 거창한 기능은 아니지만, 실무에서 마주치면 원인을 찾기 어려운 유형의 수정입니다.

실무 관점​

MTS 앱에 적용한다면, 노출 범위를 좁게 잡는 것이 먼저입니다.
조회처럼 부작용이 없는 함수부터 시작하고, 주문이나 이체처럼 돈이 움직이는 동작은 에이전트 호출 대상으로 두지 않는 편이 안전합니다.
에이전트는 함수 이름과 KDoc만 보고 호출을 결정하므로, 모호한 이름과 부실한 설명은 오호출로 이어질 수 있습니다.

그 전에 내부 빌드에서 KDoc 품질과 호출 범위를 먼저 다듬어 두는 편이 좋습니다.

WebView에 stable API로 온 allowlist — WebKit 1.18.0 살펴보기

October 24, 2026 · 3 min read
Way
Android Developer

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.
2026년 10월 21일에 공개된 WebKit 1.18.0의 릴리스 노트를 정리해드리겠습니다.

현재 상황​

지난 글에서는 WebView v156의 cross-origin isolation allowlist 개념을 정리한 바 있습니다.
당시에는 개념과 정책 방향이 중심이었습니다.
이번에는 그 기능이 Jetpack WebKit의 stable API로 확정된 내용을 정리합니다.
MTS 앱처럼 WebView를 많이 쓰는 앱에서는 웹 콘텐츠의 성능 기능과 보안 정책을 함께 다뤄야 합니다.
SharedArrayBuffer처럼 cross-origin isolation을 요구하는 API는 그동안 전부 아니면 전무에 가까웠습니다.
1.18.0은 신뢰하는 origin만 골라 허용하는 길을 stable API로 열어줍니다.

WebKit 1.18.0 살펴보기​

cross-origin isolated allowlist API​

핵심은 Profile 수준의 API입니다.
Profile#setCrossOriginIsolatedAllowlist와 Profile#getCrossOriginIsolatedAllowlist가 stable로 제공됩니다.
allowlist에 오른 origin에서는 완전히 cross-origin isolated 상태가 아니어도 SharedArrayBuffer 같은 API를 쓸 수 있습니다.
다만 웹 페이지 쪽에서도 Document-Isolation-Policy 헤더로 적절히 옵트인해야 합니다.
앱 API만 켠다고 끝나는 기능이 아니라, 웹 측 헤더와 함께 동작하는 기능입니다.

// 이미 확보한 Profile이라고 가정합니다
if (WebViewFeature.isFeatureSupported(WebViewFeature.CROSS_ORIGIN_ISOLATED_ALLOWLIST)) {
    profile.setCrossOriginIsolatedAllowlist(
        setOf("https://trusted.example.com")
    )
}

사용 전에 반드시 기능 지원 여부를 확인해야 합니다.
지원되지 않는 단말에서 호출하면 예외가 발생합니다.
공식 API 레퍼런스에서도 사용 전 확인을 강조하고 있습니다.
또한 기본값은 비활성화 상태입니다.
WebView는 렌더러 프로세스 격리를 지원하지 않기 때문에, 이 API를 호출한다는 것은 보안 보장을 완화하겠다는 뜻이 됩니다.
그래서 신뢰하는 origin만 등록해야 하고, 와일드카드 패턴은 피해야 합니다.
이미 로드된 페이지에도 이 설정이 적용된다는 점도 염두에 두어야 합니다.

prefetch 큐 비우기 여부 확인​

WebViewFeature에 WEBVIEW_NAVIGATE_DRAIN_PREFETCH 상수가 추가되었습니다.
이 상수로 Navigation#navigate가 이동 전에 prefetch 큐를 비우는지 확인할 수 있습니다.
prefetch를 쓰는 앱에서는 이동 시점에 어떤 요청이 남는지 예측하기가 한결 쉬워집니다.
단순한 상수 추가처럼 보이지만, 동작 예측 가능성을 높이는 변경입니다.

if (WebViewFeature.isFeatureSupported(WebViewFeature.WEBVIEW_NAVIGATE_DRAIN_PREFETCH)) {
    // Navigation#navigate가 prefetch 큐를 비우는지 확인할 수 있습니다
}

API 정리와 이름 변경​

PrefetchParameters#isJavaScriptEnabled는 includeClientHints로 이름이 바뀌었습니다.
기존 메서드는 deprecated 처리되었습니다.
Profile#addQuicHints는 preferQuicFor로 이름이 바뀌었습니다.
이름만 바뀐 변경이지만, 기존 이름을 그대로 쓰던 코드가 있다면 마이그레이션 목록에 올려두어야 합니다.
deprecated 경고를 방치하면 나중에 버전 올릴 때 한꺼번에 정리해야 합니다.

의존성 선언​

[versions]
webkit = "1.18.0"

[libraries]
webkit = { module = "androidx.webkit:webkit", version.ref = "webkit" }
dependencies {
    implementation(libs.webkit)
}

실무 관점​

MTS 앱에서 WebView allowlist를 쓴다면, 등록 대상은 자사 도메인처럼 확실히 신뢰하는 origin으로 한정해야 합니다.
외부 제휴 페이지나 광고성 페이지를 넓게 허용하면, 보안 보장을 완화한 대가를 치르게 됩니다.
적용 전에는 기능 지원 여부 확인, 헤더 설정, 기존 페이지 동작을 함께 테스트하는 편이 좋습니다.
이미 로드된 페이지에도 적용되므로, 설정 시점에 따라 동작이 달라질 수 있다는 점도 테스트 항목에 넣어야 합니다.
stable 릴리스인 만큼, 기존에 쓰던 이름 변경부터 정리하고 단계적으로 적용하는 것이 안전합니다.

마치며​

이번 stable은 allowlist라는 보안 기능을 실제 API로 쓸 수 있게 만든 릴리스입니다.
신뢰하는 origin만 좁게 허용한다는 원칙만 지키면, WebView의 성능 기능을 보다 안전하게 활용할 수 있습니다.

Google Sign-In deprecated, 이제는 Credential Manager로 옮기기

October 23, 2026 · 4 min read
Way
Android Developer

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.
오랫동안 사용해 온 Google Sign-In for Android의 deprecated 선언과 Credential Manager로의 이전 방법에 대해 설명해드리겠습니다.

현재 상황​

Android에서 Google 계정으로 로그인하는 방법은 오랫동안 play-services-auth의 GoogleSignInClient와 GoogleSignInOptions였습니다.
하지만 Android Developers 문서에 따르면 Google Sign-In for Android는 deprecated 상태이며, Google Play services Auth SDK의 향후 릴리스에서는 제거될 예정이라고 명시되어 있습니다.
후계자로는 Credential Manager가 공식 권장되고 있습니다.
제거 시기는 아직 정해지지 않았지만 제거가 예고된 만큼, 인증 흐름을 손보는 시점에 함께 이전하는 것이 안전합니다.

Credential Manager 살펴보기​

Credential Manager는 패스키, 비밀번호, Google을 포함한 연합 로그인 방식을 하나의 통합 API로 처리하는 Jetpack API입니다.
Android 4.4(API 19) 이상에서 동작하며 모바일, Android XR, Wear OS를 포함한 다양한 폼 팩터를 지원합니다.
공식 마이그레이션 가이드에서는 새 API의 이점을 하나의 통합 지점, 표준 Sign in with Google 버튼 지원, 원탭 자동 로그인, 패스키 내장 보안으로 정리하고 있습니다.

의존성 추가하기​

구현 가이드에 따르면 다음 세 가지 의존성을 추가합니다.

dependencies {
    implementation("androidx.credentials:credentials:1.7.0-alpha03")
    implementation("androidx.credentials:credentials-play-services-auth:1.7.0-alpha03")
    implementation("com.google.android.libraries.identity.googleid:googleid:<latest version>")
}

바텀 시트 플로우 만들기​

Credential Manager의 바텀 시트는 패스키, 비밀번호, Google 로그인에 모두 동일한 경험을 제공하는 내장 UI입니다.
기존처럼 별도의 로그인 화면을 만들 필요가 없습니다.
먼저 이전에 인증된 계정을 조회하는 요청을 만듭니다.

val googleIdOption: GetGoogleIdOption = GetGoogleIdOption.Builder()
    .setFilterByAuthorizedAccounts(true)
    .setServerClientId(WEB_CLIENT_ID)
    .setAutoSelectEnabled(true)
    .setNonce(generateSecureRandomNonce())
    .build()

setFilterByAuthorizedAccounts(true)는 이 앱에서 이전에 사용한 계정만 보여 줍니다.
setAutoSelectEnabled(true)와 함께 사용하면 기존 silentSignIn과 유사한 자동 로그인을 구현할 수 있습니다.
단, 자동 로그인이 동작하려면 디바이스에 승인된 계정이 하나뿐이고, 이전 세션에서 명시적으로 로그아웃하지 않았으며, 사용자가 Google 계정 설정에서 자동 로그인을 끄지 않은 조건을 만족해야 합니다.

이어서 요청을 실행합니다.

val request: GetCredentialRequest = GetCredentialRequest.Builder()
    .addCredentialOption(googleIdOption)
    .build()

val result = credentialManager.getCredential(
    request = request,
    context = mutableContext
)
handleSignIn(result)

승인된 계정이 하나도 없으면 NoCredentialException이 발생하므로, 이 경우에는 setFilterByAuthorizedAccounts(false)로 필터를 풀고 다시 요청하면 됩니다.
보안을 위해 setNonce로 재생 공격을 방지할 것을 권장합니다.
공식 문서는 SecureRandom으로 생성한 32바이트 난수를 Base64 URL-safe 방식으로 인코딩해 전달하는 함수를 예시로 제시합니다.

fun generateSecureRandomNonce(byteLength: Int = 32): String {
    val randomBytes = ByteArray(byteLength)
    SecureRandom().nextBytes(randomBytes)
    return Base64.encodeToString(randomBytes, Base64.NO_WRAP or Base64.URL_SAFE or Base64.NO_PADDING)
}

버튼 플로우 만들기​

Google은 바텀 시트와 함께 Sign in with Google 버튼을 둘 다 구현할 것을 권장합니다.
사용자가 바텀 시트를 닫았거나, 디바이스에 Google 계정이 없거나, 기존 계정이 재인증을 요구하는 경우에 버튼이 필요하기 때문입니다.
버튼용 요청은 GetSignInWithGoogleOption으로 만듭니다.

val signInWithGoogleOption: GetSignInWithGoogleOption = GetSignInWithGoogleOption.Builder(
    serverClientId = WEB_CLIENT_ID
).setNonce(generateSecureRandomNonce())
    .build()

로그인 응답 처리하기​

응답은 CustomCredential 형태로 반환됩니다.
타입이 GoogleIdTokenCredential.TYPE_GOOGLE_ID_TOKEN_CREDENTIAL인지 확인한 뒤 파싱합니다.

fun handleSign(result: GetCredentialResponse) {
    val credential = result.credential
    if (credential is CustomCredential &&
        credential.type == GoogleIdTokenCredential.TYPE_GOOGLE_ID_TOKEN_CREDENTIAL
    ) {
        val googleIdTokenCredential = GoogleIdTokenCredential.createFrom(credential.data)
        // idToken을 서버로 보내 검증합니다
    }
}

인증과 인가가 분리되는 점​

기존 SDK는 인증과 인가를 한 번의 호출로 처리할 수 있었지만, 새 방식에서는 명확히 분리됩니다.
인증은 Credential Manager가, Drive 접근 같은 특정 데이터 권한 요청은 AuthorizationClient API가 맡습니다.
사용자 흐름을 사용자 의도에 맞게 매핑하는 데 도움이 된다고 문서는 설명합니다.
로그아웃 시에는 clearCredentialState()를 호출해 모든 인증 정보 제공자의 세션을 정리해야, 다음 로그인에서 전체 로그인 옵션을 다시 볼 수 있습니다.

실무 관점​

MTS처럼 계정 기반의 금융 앱에서는 로그인과 권한 요청을 분리할 수 있다는 점이 오히려 장점입니다.
전제 조건으로는 Google Cloud 프로젝트의 웹 클라이언트 ID(setServerClientId에 전달) 설정이 필요하고, 동의 화면에 앱 이름을 표시하려면 브랜드 검증도 마쳐야 합니다.
서버 측에서는 ID 토큰과 함께 nonce를 검증하는 로직을 추가하는 것을 권장합니다.

마치며​

Google Sign-In for Android의 제거는 시점만 남았을 뿐 확정된 흐름입니다.
Credential Manager는 패스키까지 아우르는 통합 API이므로, 로그인 UI를 손보는 김에 함께 이전하는 것을 권장합니다.

CameraX로 1만 8천 종 기기에서 본인 확인하기

November 14, 2026 · 4 min read
Way
Android Developer

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.

2026년 11월 11일 Android Developers Blog에 공개된 SmileID의 CameraX 도입 사례에 대해 설명해드리겠습니다.

배경​

본인 확인 앱은 은행 계좌 개설과 SIM 등록에 사용됩니다.
선명한 고해상도 얼굴 촬영이 필요하고 위조와 딥페이크를 가려내야 합니다.
저사양 기기에서 충돌 없이 동작하는 것도 필수 조건입니다.

SmileID는 아프리카 지역의 본인 확인 SDK를 제공하는 회사입니다.
대상 기기에서 Android 점유율은 85%에 달합니다.
저가형 스마트폰과 지역 전용 모델, POS 단말까지 아우르는 환경입니다.
이 사례는 파편화된 기기 환경에서 카메라를 어떻게 안정화했는지 보여줍니다.

CameraX 도입 전의 문제​

기존 구현은 Camera1과 저수준 Camera2 API를 직접 사용했습니다.
세 가지 문제가 반복되었습니다.

미리보기 왜곡과 회전 문제​

제조사마다 카메라 센서 방향을 다르게 보고했습니다.
미리보기가 회전되거나 얼굴 촬영이 잘못된 방향으로 저장되었습니다.
저가형 기기에서는 요청한 프레임 크기가 맞지 않아 미리보기가 늘어났습니다.
얼굴이 일그러지면 생체 인증 자체가 무용지물이 됩니다.

메모리 부족 충돌​

RAM 1GB 이하인 기기에서 고해상도 이미지를 처리하면 메모리 부족 충돌이 발생했습니다.
실시간 생체 확인을 포기하고 정적 사진을 REST API로 업로드하는 방식으로 돌아가야 했습니다.
그 결과 SDK 도입 성장률은 연간 2배에서 3배 수준에 머물렀습니다.

CameraX 살펴보기​

SmileID는 모바일 SDK를 처음부터 다시 만들며 CameraX로 이전했습니다.
CameraX는 기기 차이를 추상화하고 수명 주기를 인식하는 인터페이스를 제공합니다.
Android 5.0(API 21)부터 지원되며 기존 기기의 98% 이상을 커버합니다.

Preview와 ImageAnalysis 파이프라인​

두 가지 유스 케이스를 함께 묶어 이중 목적 파이프라인을 구성했습니다.
Preview는 사용자를 안내하는 실시간 미리보기를 담당합니다.
ImageAnalysis는 프레임을 실시간으로 분석해 얼굴 위치 확인과 생체 여부를 판단합니다.
검증된 셀피 프레임도 같은 파이프라인에서 추출합니다.

ResolutionSelector로 해상도 제어하기​

고해상도 촬영과 메모리 부족 충돌을 함께 해결한 핵심은 ResolutionSelector입니다.
목표 해상도를 지정하고 해당 크기를 지원하지 않는 기기에서의 대체 규칙을 선택합니다.
선명도를 우선하면 FALLBACK_RULE_CLOSEST_HIGHER_THEN_LOWER를 사용합니다.
메모리 사용량을 제한하면 FALLBACK_RULE_CLOSEST_LOWER_THEN_HIGHER를 사용합니다.
백프레셔 전략은 STRATEGY_KEEP_ONLY_LATEST로 지정해 이전 프레임 분석이 끝나지 않았으면 오래된 프레임을 버립니다.

val resolutionSelector = ResolutionSelector.Builder()
    .setResolutionStrategy(
        ResolutionStrategy(
            Size(1200, 900),
            ResolutionStrategy.FALLBACK_RULE_CLOSEST_HIGHER_THEN_LOWER
        )
    )
    .setAspectRatioStrategy(AspectRatioStrategy.RATIO_4_3_FALLBACK_AUTO_STRATEGY)
    .build()

val imageAnalysis = ImageAnalysis.Builder()
    .setResolutionSelector(resolutionSelector)
    .setBackpressureStrategy(ImageAnalysis.STRATEGY_KEEP_ONLY_LATEST)
    .build()

imageAnalysis.setAnalyzer(executor, analyzer)

val preview = Preview.Builder().build().also {
    it.surfaceProvider = surfaceProvider
}

cameraProvider.bindToLifecycle(
    lifecycleOwner,
    CameraSelector.DEFAULT_FRONT_CAMERA,
    preview,
    imageAnalysis
)

고밀도 픽셀 프레임을 요청하고 단말에서 처리한 결과 셀피 해상도가 4배 증가했습니다.
얼굴 영역만 단말에서 압축해 전송하므로 네트워크 업로드 용량은 이전과 동일하게 유지되었습니다.
모델에 더 선명한 데이터를 제공하면서 사용자의 데이터 비용은 늘지 않았습니다.

호환성을 지탱하는 두 가지 계층​

첫 번째 계층은 Google의 Camera and Media Test Lab입니다.
190종이 넘는 실물 기기에서 자동 테스트가 매일 실행됩니다.
칩셋과 OS 버전, 하드웨어 사양이 다른 기기를 순환하며 검증합니다.
회귀가 발생하면 프로덕션 코드에 영향을 주기 전에 잡아냅니다.

두 번째 계층은 기기별 결함에 대한 자동 우회 처리입니다.
일부 기기는 노출 설정을 적용하지 못하거나 특정 종횡비에서 이미지를 뒤집어 보고합니다.
CameraX는 DeviceQuirks와 CameraQuirks 같은 내부 클래스로 알려진 문제를 감지합니다.
감지된 기기에는 맞는 우회 처리를 자동으로 적용합니다.
SmileID는 기기별 패치 없이 1만 8천 종이 넘는 기기에서 SDK를 동작시켰습니다.

도입 결과​

도입 결과는 수치로 확인됩니다.
SDK 도입 성장률은 2년 차에 20배에 도달했습니다.
검증 통과율은 SDK를 사용하는 앱 기준으로 20% 증가했습니다.
누적 본인 확인 건수는 1억 6천만 건을 넘어섰습니다.

실무 관점​

MTS에서도 신분증 촬영과 본인 확인 같은 카메라 기능이 필요합니다.
저사양 기기까지 고려한다면 해상도는 요청만으로 끝나지 않습니다.
대체 규칙과 백프레셔 전략까지 함께 설계해야 메모리 문제를 피할 수 있습니다.
기기별 분기는 직접 작성하기보다 CameraX의 우회 처리에 맡기는 편이 유지보수에 유리합니다.
다만 ResolutionSelector의 대체 규칙은 촬영 품질과 메모리 사용량 사이의 선택입니다.
서비스 성격에 따라 선명도 우선과 메모리 제한 중 어느 쪽을 택할지 먼저 정하는 것이 좋습니다.
AI 코딩 에이전트를 사용한다면 CameraX Skill을 활용할 수 있습니다.
android skills add camerax 명령으로 추가하면 마이그레이션과 수명 주기 바인딩에 현재 패턴을 적용할 수 있습니다.

마치며​

CameraX 도입은 파편화된 기기 환경의 문제를 SDK의 강점으로 바꾸었습니다.
카메라 기능을 직접 구현하기 전에 라이브러리가 제공하는 호환성 계층을 먼저 검토하는 것이 좋습니다.

CameraX 1.7.0-rc02 살펴보기 — Kotlin DSL 빌더와 미러 모드

November 8, 2026 · 3 min read
Way
Android Developer

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.
2026년 11월 4일에 공개된 CameraX 1.7.0-rc02에 대해 설명해드리겠습니다.
1.7.0은 릴리스 후보 단계에 들어섰으며, Kotlin DSL 빌더와 Camera2Interop 정리가 포함되어 있습니다.

배경​

CameraX는 지금까지 빌더 패턴으로 유스케이스를 만들었습니다.
Preview.Builder와 ImageCapture.Builder에 설정을 하나씩 쌓는 방식은 익숙했지만, 코드가 길어지고 설정 위치를 찾기 어려웠습니다.
Camera2의 세부 설정을 직접 다뤄야 할 때는 레거시 Interop API를 거쳐야 했고, 미러 모드는 실험적 애너테이션이 붙은 상태였습니다.
1.7.0은 이 세 지점을 함께 정리합니다.

CameraX 1.7.0 살펴보기​

Kotlin DSL 빌더로 유스케이스 만들기​

1.7.0-alpha03부터 preview, imageCapture, imageAnalysis, videoCapture DSL 빌더가 추가되었습니다.
빌더 객체를 직접 다루지 않고, 람다 안에서 설정을 모아 유스케이스를 만들 수 있습니다.

val preview = preview {
    // Preview 설정을 여기에 작성합니다.
}

val imageCapture = imageCapture {
    // ImageCapture 설정을 여기에 작성합니다.
}

cameraProvider.bindToLifecycle(
    lifecycleOwner, cameraSelector, preview, imageCapture
)

기존 빌더 방식과 비교하면 설정 코드가 한곳에 모이고, 유스케이스 생성 의도가 더 분명해집니다.

Camera2Interop 정리하기​

레거시 Camera2Interop API가 정리되었습니다.
Camera2Interop.Extender와 Camera2CameraControl, Camera2CameraInfo, CaptureRequestOptions는 deprecated 되었고, 대신 설정자 팩토리 메서드와 Kotlin 확장 함수를 사용합니다.
camera2Interop 확장 블록을 DSL 빌더 안에서 직접 쓸 수 있습니다.

val preview = preview {
    camera2Interop {
        // Camera2 설정을 직접 지정합니다.
    }
}

Camera2Interop에는 forUseCase와 forImageCapture, forSessionConfig, forCameraControl 팩토리 메서드가 추가되었습니다.
CameraInfo.cameraId와 CameraInfo.cameraCharacteristics 확장 프로퍼티로 Camera2의 카메라 ID와 특성을 바로 조회할 수 있으며, String.toCameraSelector()로 문자열에서 셀렉터를 만들 수 있습니다.
CameraControl.applyCamera2InteropAsync 확장 함수도 함께 제공됩니다.

미러 모드와 물리 카메라​

Preview.setMirrorMode와 VideoCapture.setMirrorMode가 정식 API가 되었습니다.
기존에 붙어 있던 ExperimentalMirrorMode 애너테이션은 제거되었습니다.
물리 카메라 지원도 넓어졌습니다.
CameraInfo.getPhysicalCameraInfos()로 물리 카메라 정보를 얻고, 물리 카메라용 CameraSelector로 유스케이스를 바인딩할 수 있습니다.
물리 카메라의 CameraInfo로 조회하면 논리 카메라가 아니라 물리 카메라 정보가 반환됩니다.

rc02에서 수정된 내용​

1.7.0-rc02 자체는 기능 추가가 아니라 버그 수정 릴리스입니다.
API 30에서 SYSTEM_ALERT_WINDOW 권한을 가진 앱이 카메라 유스케이스를 반복 바인딩할 때 발생하던 UnsupportedOperationException이 수정되었습니다.
VideoCapture를 언바인드할 때 미디어 프레임워크 스레드 하나가 남던 네이티브 스레드 누수도 수정되었습니다.
저조도 부스트 동작도 개선되었습니다.
저조도 부스트와 토치는 마지막 설정이 이기는 방식으로 동작하며, 저조도 부스트가 켜진 상태에서도 이미지 캡처 시 플래시가 동작합니다.

실무 관점​

RC 단계라 API 표면은 사실상 확정된 상태입니다.
정식 릴리스 전에 레거시 Camera2Interop 사용처가 있는지 점검하고, DSL 빌더로의 전환 범위를 정해 두는 것이 좋습니다.
미러 모드를 이미 실험적 API로 쓰고 있다면 애너테이션 제거에 맞춰 정식 API로 교체해야 합니다.
저조도 부스트와 토치의 동작이 바뀐 만큼, 야간 촬영이나 QR 인식처럼 두 기능을 함께 쓰는 화면이 있다면 동작을 다시 확인해야 합니다.

마치며​

CameraX 1.7.0은 카메라 코드를 짧게 쓰는 방향으로 정리되고 있습니다.
정식 릴리스가 나오면 DSL 빌더와 Interop 정리를 실제 화면에 적용해 볼 만합니다.

네이티브 크래시를 잡는 릴리스 — CameraX 1.7.0-rc01 들여다보기

October 22, 2026 · 3 min read
Way
Android Developer

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.
2026년 10월 21일에 공개된 CameraX 1.7.0-rc01의 릴리스 노트를 정리해드리겠습니다.

현재 상황​

CameraX는 카메라 기능을 단말 파편화 없이 구현할 수 있게 돕는 Jetpack 라이브러리입니다.
신분증 촬영, 얼굴 인증처럼 금융 앱에서도 카메라 기능은 흔하게 쓰입니다.
반면 카메라 파이프라인의 네이티브 영역에서 발생하는 크래시는 재현이 어렵고 대응 비용이 큽니다.
이번 rc는 그런 네이티브 크래시 수정과 API 정리에 무게가 실린 릴리스입니다.

CameraX 1.7.0-rc01 살펴보기​

네이티브 SIGSEGV 크래시 수정​

SurfaceProcessor가 입력 SurfaceTexture를 해제하는 시점에, 연결된 SurfaceRequest가 먼저 가비지 컬렉션되면 네이티브 SIGSEGV가 발생하던 버그가 수정되었습니다.
타이밍에 의존하는 문제라 특정 단말과 특정 시나리오에서만 나타나고, 주로 크래시 리포트에서만 보이는 유형입니다.
이펙트나 필터로 SurfaceProcessor를 직접 다루는 앱이라면 이번 수정이 반가울 것입니다.

Surface 누수와 OpenGL 크래시 수정​

CameraEffect의 executor나 HandlerThread가 SurfaceOutput이 닫히기 전에 종료되면, Surface 누수와 네이티브 OpenGL 크래시가 발생하던 문제가 수정되었습니다.
카메라 파이프라인의 종료 순서가 리소스 정리와 직결된다는 점을 보여주는 사례입니다.

Camera2Interop — 인터페이스에서 추상 클래스로 전환​

UseCaseCamera2Interop, ImageCaptureCamera2Interop, SessionConfigCamera2Interop, CameraControlCamera2Interop이 인터페이스에서 추상 클래스로 바뀌었습니다.
소스 호환성에 영향을 줄 수 있는 변경이니, interop 클래스를 직접 참조하는 코드가 있다면 1.7.0 적용 전에 컴파일을 확인해야 합니다.
한편 1.7.0-alpha03부터는 Kotlin DSL 확장 블록으로 interop을 쓰는 방식이 권장되고 있습니다.

// 1.7.0-alpha03부터 권장되는 방식 — Kotlin DSL 확장 블록
val preview = preview {
    camera2Interop {
        // Camera2 설정을 이 블록 안에 지정합니다
    }
}

Low Light Boost와 Torch — last setting wins​

저조도 부스트와 토치를 동시에 켜려고 하면 요청이 거부되던 동작이 바뀌었습니다.
이제는 마지막에 설정한 쪽이 이기는 방식으로 동작합니다. 하나를 켜면 다른 하나가 자동으로 꺼집니다.
저조도 부스트가 켜진 상태에서도 촬영 시 플래시가 터지도록 함께 개선되었습니다.

물리 카메라에 UseCase 바인딩​

CameraInfo.getPhysicalCameraInfos()에서 얻은 물리 카메라의 CameraSelector로 UseCase를 바인딩할 수 있게 되었습니다.
물리 CameraSelector로 CameraInfo를 조회하면 논리 카메라가 아닌 물리 카메라의 정보가 반환됩니다.
멀티 카메라 단말에서 특정 렌즈를 직접 다루는 기능에 활용할 수 있습니다.

의존성 선언​

[versions]
camerax = "1.7.0-rc01"

[libraries]
camerax-core = { module = "androidx.camera:camera-core", version.ref = "camerax" }
camerax-camera2 = { module = "androidx.camera:camera-camera2", version.ref = "camerax" }
camerax-lifecycle = { module = "androidx.camera:camera-lifecycle", version.ref = "camerax" }

androidx.lifecycle:lifecycle-runtime 의존성은 2.10.0으로 올라갔습니다.
번들로 제공되는 lifecycle runtime lint 검사가 AGP 9.5.0-alpha04 이상에서 동작하려면 이 버전이 필요합니다.

실무 관점​

신분증 촬영이나 얼굴 인증 흐름이 있는 MTS 앱에서는 네이티브 크래시 수정이 안정성 지표에 직결됩니다.
interop 클래스 변경은 컴파일 단계에서 바로 드러나니, Camera2를 직접 건드리는 코드가 있다면 마이그레이션 계획을 먼저 세우는 편이 좋습니다.
아직 rc 단계이므로 프로덕션 적용은 stable 승격을 기다리는 것이 안전합니다.

마치며​

이번 rc는 기능 추가보다 안정화와 API 정리에 무게가 실린 릴리스입니다.
카메라 기능을 쓰는 앱이라면 릴리스 노트를 한 번 읽어두는 것만으로도 대응 비용을 줄일 수 있습니다.

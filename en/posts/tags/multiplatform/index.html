Kotlin 2.5.0-RC의 KMP 분리 컴파일과 새 발행 형식 살펴보기

November 19, 2026 · 5 min read
Way
Android Developer

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.
11월 11일에 공개된 Kotlin 2.5.0-RC의 KMP 변경 사항에 대해 설명해드리겠습니다.

배경​

Kotlin Multiplatform 프로젝트에서는 IDE 분석과 컴파일러의 판단이 어긋나는 경우가 있습니다.
IDE에서는 빨간 줄이 그어지는 코드가 컴파일은 통과하거나, 반대로 IDE에서는 문제가 없어 보이는데 JVM 컴파일이 실패하기도 합니다.
원인은 컴파일 방식에 있습니다.
공통 코드가 컴파일될 때 의존성의 플랫폼 아티팩트를 함께 보기 때문입니다.
Kotlin 2.5.0-RC는 이 문제를 해결하는 실험적인 분리 컴파일 방식을 도입했습니다.
아울러 멀티플랫폼 라이브러리의 발행 형식을 새로 바꿔, 발행물 크기를 크게 줄였습니다.
두 변경 사항 모두 아직 실험 단계이며, 기본값은 꺼져 있습니다.

KMP 분리 컴파일 살펴보기​

기존 컴파일 방식의 문제​

KMP 모듈은 보통 commonMain 같은 공통 소스셋과 jvmMain 같은 플랫폼 소스셋으로 구성됩니다.
컴파일러는 각 플랫폼 소스셋에 대한 플랫폼 아티팩트를 만들고, 공통 소스셋에 대한 메타데이터 KLIB를 만듭니다.
메타데이터 KLIB에는 선언만 들어 있고 구현 본문은 들어 있지 않습니다.
문제는 플랫폼 소스셋을 컴파일할 때 공통 코드까지 의존성의 플랫폼 아티팩트에 대해 함께 컴파일된다는 점입니다.
그래서 commonMain 코드가 의존성 라이브러리의 플랫폼 전용 선언을 암묵적으로 참조할 수 있습니다.
IntelliJ IDEA는 메타데이터 KLIB만 본다고 가정하므로, 같은 코드를 미해결 참조로 표시합니다.
IDE에서는 빨간 줄인데 컴파일은 통과하는 어긋남이 여기서 생깁니다.
commonTest도 같은 문제를 겪습니다.
테스트 코드가 jvmMain의 플랫폼 선언을 호출하는데, IDE는 이를 미해결 참조로 표시합니다.

// lib/jvmMain
class Foo

// app/commonMain
fun main() {
    Foo() // IDE에서는 미해결 참조, 컴파일은 통과
}

오버로드와 타입 추론의 어긋남​

오버로드 선택에서도 IDE와 컴파일러가 다른 결론에 도달합니다.
라이브러리의 commonMain과 jvmMain에 같은 이름의 함수가 여러 개 선언된 경우를 예로 들 수 있습니다.

// lib/commonMain
fun foo(x: Any) = "common"

// lib/jvmMain
fun foo(x: String) = "platform"

// app/commonMain
fun main() {
    println(foo(""))
}

IDE는 foo("") 호출을 lib/commonMain의 fun foo(x: Any)로 해석합니다.
공통 코드는 공통 선언에만 의존할 수 있다고 가정하기 때문입니다.
그러나 실제 컴파일에서는 두 선언이 모두 보이고, 더 구체적인 fun foo(x: String)이 선택됩니다.
실행 결과로 "platform"이 출력됩니다.
타입 추론에서도 비슷한 문제가 생깁니다.
actual 클래스가 expect 클래스와 다른 상위 타입을 선언하면, IDE는 Event로 추론하는데 JVM 컴파일은 Any로 추론해 .name 참조에서 실패할 수 있습니다.

분리 컴파일이 바꾸는 것​

분리 컴파일은 공통 소스셋을 컴파일할 때 메타데이터 KLIB의 선언만으로 엄격하게 해석합니다.
IDE가 가정하던 방식과 컴파일러의 동작이 일치합니다.
앞의 예제 코드는 분리 컴파일을 켜면 컴파일 오류가 됩니다.
해결 방법은 명시적인 연결을 만드는 것입니다.
라이브러리의 commonMain에 expect class를 선언하고, 플랫폼 쪽을 actual class로 만듭니다.

// lib/commonMain
expect class Foo()

// lib/jvmMain
actual class Foo

// app/commonMain
fun main() {
    Foo() // 정상 동작
}

오버로드 예제에서는 호출이 lib/commonMain의 fun foo(x: Any)로 해석되어 실행 결과로 "common"이 출력됩니다.
타입 추론 예제에서는 공통 코드가 이미 Event 반환 타입으로 추론된 상태로 JVM 컴파일이 별도로 진행되므로, 컴파일이 정상적으로 끝납니다.
기존 코드 중에는 엄격해진 검사에 걸려 수정이 필요한 부분이 생길 수 있습니다.
대신 공통 소스셋에 대한 증분 컴파일이 가능해진다는 부수적인 이득도 있습니다.

분리 컴파일 켜기​

분리 컴파일은 실험 기능이며 기본값은 꺼져 있습니다.
gradle.properties 파일에 다음 속성을 추가하면 켤 수 있습니다.

kotlin.kmp.separateCompilation=true

알려진 문제도 있습니다.
분리 컴파일이 제대로 동작하려면 멀티플랫폼 라이브러리가 메타데이터 KLIB을 발행해야 합니다.
KMP Gradle 플러그인의 기본 발행 동작이므로 대부분은 해당하지 않지만, 이 조건이 이제는 필수입니다.
C 상호 운용을 쓰는 프로젝트에서는 cinterop 공통화 관련 문제에 주의해야 합니다.
공통 소스셋이 있고 선언된 타겟이 하나뿐인 모듈은 현재 분리 컴파일의 영향을 받지 않습니다.

새 발행 형식 .kar​

Kotlin 2.5.0-RC는 멀티플랫폼 라이브러리의 새 발행 형식도 도입했습니다.
JVM과 Android을 제외한 플랫폼 아티팩트를 하나의 .kar 아카이브로 발행합니다.
.kar 파일은 ZIP 아카이브를 XZ로 한 번 더 압축한 형태입니다.
이 변경의 배경은 Maven Central에 최근 도입된 발행 크기 제한입니다.
새 형식에서는 타겟을 추가해도 새 파일이 생기지 않으므로, 발행물 크기가 크게 늘지 않습니다.
경우에 따라서는 기존의 단일 타겟 발행물보다 전체 크기가 작아지기도 합니다.
공식 문서의 예시에서는 cryptography-kotlin 라이브러리의 발행물이 7,539개 파일, 91MB에서 1,036개 파일, 23MB로 줄었습니다.
모듈별로 켜려면 빌드 스크립트에 다음과 같이 설정합니다.

kotlin {
    publishing {
        publicationFormat.set(KotlinPublicationFormat.KOTLIN_ARCHIVE)
    }
}

프로젝트 전체에 적용하려면 gradle.properties 파일에 다음 속성을 추가합니다.

kotlin.publicationFormat=KOTLIN_ARCHIVE

새 형식으로 발행하는 기능은 아직 실험 단계입니다.
다만 .kar 형식의 아티팩트를 소비하는 기능은 모든 프로젝트에서 이미 사용할 수 있습니다.
이 변경 사항은 라이브러리 작성자에게만 해당하며, 최종 애플리케이션 개발자에게는 영향을 주지 않습니다.

실무 관점​

국내 MTS 프로젝트에 적용한다면, 분리 컴파일은 먼저 켜서 컴파일해 보는 것부터 시작하는 것이 좋습니다.
기존 코드가 플랫폼 선언에 암묵적으로 의존하고 있었다면, 켜는 즉시 컴파일 오류로 드러납니다.
이 오류는 숨어 있던 의존성을 명시적인 expect와 actual 선언으로 바꾸라는 신호입니다.
KMP 라이브러리를 직접 발행한다면 .kar 형식도 검토할 만합니다.
타겟이 늘어날수록 발행물 크기가 커지는 부담이 줄기 때문입니다.
다만 발행 기능이 실험 단계이므로, 발행 파이프라인은 별도로 검증한 뒤에 적용하는 것이 안전합니다.
두 기능 모두 실험 단계라는 점을 감안해, 정식 출시 전까지는 운영 빌드에 바로 적용하기보다 평가용으로 써 보는 것이 좋습니다.

마치며​

분리 컴파일은 IDE와 컴파일러의 판단을 일치시켜 KMP 개발을 예측 가능하게 만듭니다.
새 발행 형식은 라이브러리 발행물의 크기를 크게 줄여줍니다.

KMP 모듈에 Swift 패키지 의존성 추가하기

November 17, 2026 · 4 min read
Way
Android Developer

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.
Kotlin 2.5.0-RC에서 시도해 볼 수 있는 KMP 모듈의 SwiftPM import 기능에 대해 설명해드리겠습니다.

배경​

KMP 프로젝트에서 iOS 쪽 네이티브 SDK를 쓰려면 지금까지 CocoaPods 의존성을 연결하거나 cinterop 정의를 직접 작성해야 했습니다.
CocoaPods 방식은 별도 설정이 많고, Swift 패키지를 그대로 가져오는 방법이 마땅하지 않았습니다.
Kotlin 2.5.0-RC부터는 SwiftPM import 기능을 이용해 Swift 패키지를 Gradle 빌드 스크립트에서 직접 선언할 수 있습니다.
SwiftPM 의존성의 Objective-C API를 Kotlin 코드에서 바로 호출할 수 있게 됩니다.

SwiftPM import 살펴보기​

플러그인 버전 설정하기​

SwiftPM import를 쓰려면 Kotlin Multiplatform Gradle 플러그인 2.5.0-RC가 필요합니다.
Version Catalog에서는 다음과 같이 버전을 지정합니다.

[versions]
kotlin = "2.5.0-RC"

[plugins]
kotlin-multiplatform = { id = "org.jetbrains.kotlin.multiplatform", version.ref = "kotlin" }

Swift 패키지 선언하기​

SwiftPM 의존성은 Apple 타겟을 선언한 build.gradle.kts 안의 swiftPMDependencies 블록에 추가합니다.
예시로 FirebaseAnalytics를 가져오는 설정은 다음과 같습니다.

kotlin {
    iosArm64()
    iosSimulatorArm64()
    swiftPMDependencies {
        // FirebaseAnalytics를 Kotlin 코드로 가져옵니다
        swiftPackage(
            url = url("https://github.com/firebase/firebase-ios-sdk.git"),
            version = from("12.5.0"),
            products = listOf(product("FirebaseAnalytics")),
        )
    }
}

버전은 from으로 시작 버전을 지정하거나, exact로 정확한 버전을 지정할 수 있습니다.
브랜치나 특정 리비전을 지정하는 방식도 함께 제공됩니다.

Clang 모듈 가져오기​

SwiftPM import는 Clang 모듈을 가져오는 방식으로 동작합니다.
기본값으로는 지정한 Swift 패키지 안의 Clang 모듈을 자동으로 찾아 Kotlin 코드에서 쓸 수 있게 합니다.
자동 탐색을 끄려면 discoverClangModulesImplicitly를 false로 바꾸고, 제품 이름을 Clang 모듈 이름으로 씁니다.
모듈 이름이 제품 이름과 다르면 importedClangModules로 직접 지정합니다.
예를 들어 FirebaseFirestore의 Objective-C API는 FirebaseFirestoreInternal 모듈에 들어 있습니다.

kotlin {
    swiftPMDependencies {
        discoverClangModulesImplicitly = false
        swiftPackage(
            url = url("https://github.com/firebase/firebase-ios-sdk.git"),
            version = from("12.5.0"),
            products = listOf(
                product("FirebaseAnalytics"),
                product("FirebaseFirestore"),
            ),
            importedClangModules = listOf(
                "FirebaseAnalytics",
                "FirebaseFirestoreInternal",
            ),
        )
    }
}

플랫폼 제한 두기​

일부 SwiftPM 의존성은 모든 타겟에서 빌드되지 않습니다.
예를 들어 Google Maps SDK는 현재 iOS 타겟만 지원합니다.
iOS만 타겟으로 한다면 따로 지정할 필요가 없지만, macOS 같은 타겟을 추가하면 제품마다 플랫폼을 지정해야 합니다.

kotlin {
    iosArm64()
    iosSimulatorArm64()
    macosArm64()
    swiftPMDependencies {
        swiftPackage(
            url = url("https://github.com/googlemaps/ios-maps-sdk.git"),
            version = exact("10.3.0"),
            products = listOf(
                product(
                    "GoogleMaps",
                    platforms = setOf(iOS()),
                ),
            ),
        )
    }
}

Xcode 프로젝트와 연결하기​

SwiftPM 의존성을 처음 추가하면 Xcode 프로젝트와 생성된 패키지를 연결해야 합니다.
다음 Gradle 태스크를 실행하면 SwiftPM 패키지가 생성되고 Xcode 프로젝트가 함께 변경됩니다.

XCODEPROJ_PATH='/path/to/project/iosApp/iosApp.xcodeproj' ./gradlew :kotlin-library:integrateLinkagePackage

생성된 패키지와 변경된 Xcode 프로젝트는 저장소에 함께 커밋합니다.
그 뒤로는 의존성 목록이나 버전이 바뀔 때마다 합성 패키지가 자동으로 갱신됩니다.

Kotlin 코드에서 호출하기​

가져온 Objective-C API는 swiftPMImport로 시작하는 네임스페이스에 들어 있습니다.
네임스페이스는 Gradle 그룹 이름과 프로젝트 이름을 이어서 만듭니다.
iosMain 소스 세트에서 Firebase API를 쓰는 예시는 다음과 같습니다.

import swiftPMImport.groupName.subproject.FIRAnalytics
import swiftPMImport.groupName.subproject.FIRApp

fun logAppOpen() {
    FIRApp.configure()
    FIRAnalytics.logEventWithName("app_open", parameters = null)
}

버전 잠금 파일 관리하기​

SwiftPM import 도구는 의존성 버전을 고정하기 위해 Package.resolved 파일을 만듭니다.
기본값으로는 모든 서브프로젝트의 잠금 파일이 .swiftpm-locks/default/swiftImport 안의 하나의 파일로 합쳐집니다.
잠금 파일은 저장소에 커밋해 모든 빌드가 같은 버전을 쓰게 합니다.
서브프로젝트별로 잠금 파일을 나누려면 packageResolvedSynchronization에 그룹 식별자를 지정합니다.
잠금 파일을 강제로 갱신하려면 빌드 디렉터리와 기존 Package.resolved 파일을 지운 뒤 다음 태스크를 실행합니다.

./gradlew :yourModuleName:fetchSyntheticImportProjectPackages

알고 있어야 할 제한 사항​

동적 Kotlin/Native 프레임워크를 만들 때는 SwiftPM import가 모든 경우를 지원하지 않습니다.
빌드 오류나 런타임 경고가 나오면 프레임워크 연결 방식을 정적으로 바꾸는 것이 일반적인 해결 방법입니다.

kotlin {
    listOf(
        iosArm64(),
        iosSimulatorArm64()
    ).forEach { iosTarget ->
        iosTarget.binaries.framework {
            baseName = "Shared"
            isStatic = true
        }
    }
}

실무 관점​

MTS 앱에 적용한다면, iOS 쪽에서만 쓰는 SDK부터 SwiftPM import로 옮겨 보는 것이 안전합니다.
CocoaPods 의존성을 함께 쓰고 있다면, 두 방식이 같은 SDK를 중복으로 가져오지 않는지 먼저 확인해야 합니다.
Package.resolved 잠금 파일과 생성된 패키지는 저장소에 커밋해 팀 빌드와 CI 빌드가 같은 버전을 쓰게 합니다.
Kotlin 2.5.0-RC는 정식 출시 전 단계이므로, 프로덕션 적용보다 별도 브랜치에서의 검증이 먼저입니다.

마치며​

SwiftPM import를 쓰면 Swift 패키지를 Gradle 빌드 스크립트에서 직접 선언해 KMP 모듈에서 쓸 수 있습니다.
CocoaPods 설정과 cinterop 정의를 줄이고, 버전 잠금까지 Gradle 안에서 관리할 수 있게 됩니다.

AppState StateStore 첫 알파, Compose 상태를 앱 계층으로 끌어올리기

October 30, 2026 · 2 min read
Way
Android Developer

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.
2026년 10월 28일에 첫 알파로 공개된 AppState StateStore에 대해 설명해드리겠습니다.

배경​

Compose 상태는 보통 화면이나 ViewModel 안에 머무릅니다.
앱 전역에서 공유해야 하는 상태는 계층을 옮길 때마다 전달 코드가 늘어납니다.
상태를 앱 계층으로 끌어올리면 공유와 저장이 한곳에서 관리됩니다.
StateStore는 이 역할을 맡기 위해 새로 공개된 라이브러리입니다.

StateStore 살펴보기​

Compose 런타임 기반의 상태 저장소​

StateStore는 Compose 런타임을 기반으로 동작합니다.
스냅샷 상태를 앱 계층으로 끌어올려 커스텀 연동을 제공하는 래퍼입니다.
화면이 사라져도 상태의 수명을 앱 수준에서 유지할 수 있습니다.

DataStore 연동으로 상태 유지하기​

statestore-datastore 아티팩트는 상태 영속성을 제공합니다.
syncToDataStore로 스냅샷 상태를 DataStore 파일과 동기화할 수 있습니다.
앱을 다시 시작해도 이전 상태를 복원할 수 있습니다.

class MyApplication : Application() {
    val stateStore = StateStore()
    private val scope = CoroutineScope(SupervisorJob() + Dispatchers.Default)

    override fun onCreate() {
        super.onCreate()
        scope.launch {
            launch {
                try {
                    stateStore.syncToDataStore(
                        dataStoreFile("settings").absolutePath,
                        this
                    )
                } catch (e: Exception) {
                    e.printStackTrace()
                }
            }
        }
    }
}

의존성 추가하기​

Android 타깃 기준 의존성은 다음과 같습니다.

dependencies {
    implementation("androidx.appstate.statestore:statestore:1.0.0-alpha01")
    implementation("androidx.appstate.statestore:statestore-datastore:1.0.0-alpha01")
}

함께 공개된 Transform​

같은 날짜에 appstate-transform 아티팩트도 첫 알파로 공개되었습니다.
이 글에서는 StateStore의 개념과 저장 연동에 집중합니다.
Transform의 구체적인 활용은 후속 릴리스 노트에서 확인한 뒤 다루는 것이 좋습니다.

실무 관점​

첫 알파 단계이므로 운영 코드에 바로 도입하지 않는 것이 좋습니다.
상태를 앱 계층으로 올리면 수명과 동기화 시점을 직접 설계해야 합니다.
동기화 중 예외가 나면 상태가 저장되지 않으므로 실패 처리 경로를 함께 둡니다.
MTS처럼 세션과 설정 상태가 많은 앱에서는 저장 단위부터 나누는 것이 안전합니다.

마치며​

StateStore는 Compose 상태를 앱 계층에서 관리하는 새로운 선택지입니다.
DataStore 연동까지 함께 보면 상태 공유와 영속성을 한 구조로 정리할 수 있습니다.

DataStore 1.3.0이 준비 중인 것들 — Tink 암호화와 새로운 Builder API

October 21, 2026 · 4 min read
Way
Android Developer

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.
최근 30일 내 릴리스 중 하나를 골라 심화 해설을 하겠습니다.
DataStore 1.3.0-rc01(2026년 10월 12일)까지 이어진 1.3.0 라인의 변경 사항을 정리해드리겠습니다.

현재 상황​

DataStore 1.2.1은 안정 채널의 최신입니다.
그 위로 1.3.0 라인이 alpha 단계를 거치며 2026년 10월 12일 rc01에 도달했습니다.
rc01 자체는 버그 수정 위주이지만, 1.3.0이 안정으로 오면 두 가지 큰 변화가 함께 옵니다.
Tink 기반 암호화 지원과 새로운 Builder API입니다.
두 기능 모두 alpha07(2026년 3월 11일)에 이미 확정된 내용입니다.

DataStore 1.3.0 살펴보기​

datastore-tink 아티팩트와 AeadSerializer​

새 아티팩트 androidx.datastore:datastore-tink가 추가되었습니다.
핵심 클래스는 AeadSerializer로, 기존 Serializer<T>를 감싸는 래퍼입니다.
내부는 Tink의 AEAD(Authenticated Encryption with Associated Data)로 암호화·복호화를 수행합니다.
JVM과 Android 타깃 모두에서 사용할 수 있습니다.
공식 문서의 사용 순서는 세 단계입니다.

// 1. Tink API로 키 생성
val keysetHandle =
    AndroidKeysetManager.Builder()
        .withSharedPref(applicationContext, "keyset", "keyset_prefs")
        .withKeyTemplate(KeyTemplate.createFrom(PredefinedAeadParameters.AES256_GCM))
        .withMasterKeyUri("android-keystore://master_key")
        .build()
        .keysetHandle

// 2. 기존 serializer를 감싸는 AeadSerializer 생성
val aeadSerializer = AeadSerializer(
    aead = keysetHandle.getPrimitive(
        RegistryConfiguration.get(),
        Aead::class.java,
    ),
    wrappedSerializer = ExistingSerializer,
    // ciphertext swapping 공격 방지를 위한 고유 이름
    associatedData = "settings.json".encodeToByteArray(),
)

// 3. 기존 serializer 대신 aeadSerializer로 DataStore 생성
val dataStore = dataStore(
    fileName = "settings.json",
    serializer = aeadSerializer,
    scope = scope,
)

마스터 키는 Android Keystore에 두는 패턴이 권장됩니다.
associatedData에는 파일마다 고유한 이름을 넣어, 암호문을 서로 바꿔치기하는 공격을 막습니다.
alpha10에서는 GeneralSecurityException이 CorruptionException으로 감싸지도록 바뀌었습니다.
암호화 실패가 DataStore의 CorruptionHandler 흐름에 자연스럽게 녹아들게 된 것입니다.

DataStore.Builder<T> — DataStoreFactory의 후계자​

DataStore.Builder<T>가 DataStoreFactory의 공식 대체 API로 도입되었습니다.
공식 릴리스 노트는 모든 사용자에게 Builder로의 마이그레이션을 권장합니다.
가장 큰 차이는 스코프 전달 방식입니다.
Builder는 CoroutineScope가 아니라 CoroutineContext를 요구합니다.
호출자가 viewModelScope 같은 짧은 생명주기의 스코프를 넘겨도, DataStore가 그 생명주기에 묶이지 않게 하려는 설계입니다.
구조적 동시성(structured concurrency) 관점에서 올바른 방향입니다.
또한 setCorruptionHandler로 손상 시 처리 로직을 직접 주입할 수 있게 되었습니다.
alpha09에서는 ReThrowCorruptionHandler가 public으로 공개되기도 했습니다.

웹 플랫폼 지원 (alpha08)​

DataStore가 웹 타깃 지원을 넓혔습니다.
WebOpfsStorage로 OPFS(Origin Private File System)를 지원합니다.
크로스탭 알림은 BroadcastChannel, 분산 락은 Web Locks API를 씁니다.
WebLocalStorage와 WebSessionStorage API로 저장소 타입도 명시적으로 관리할 수 있습니다.

rc01에서 바뀐 것​

1.3.0-rc01의 API 변경은 소규모입니다.
EdgeToEdge#enable() 대신 WindowCompat#enableEdgeToEdge(Window)를 쓰도록 정리되었습니다.
lifecycle-runtime 의존성이 2.10.0으로 올라갔는데, 이는 AGP 9.5.0-alpha04 이상에서 번들된 lifecycle lint 검사가 동작하기 위한 요구사항입니다.

의존성 선언​

# libs.versions.toml 예시
[versions]
datastore = "1.3.0-rc01"

[libraries]
datastore = { module = "androidx.datastore:datastore", version.ref = "datastore" }
datastore-tink = { module = "androidx.datastore:datastore-tink", version.ref = "datastore" }

실무 관점​

Builder에 넘기는 CoroutineContext에는 반드시 Job이 있어야 하고, 애플리케이션 스코프여야 합니다.
공식 문서의 Warning에도 명시된 대로, 컨텍스트가 취소되면 DataStore 내부 동작이 중간에 멈춥니다.
viewModelScope를 그대로 넘기는 실수를 하지 않도록 주의해야 합니다.
Tink 도입 시에는 associatedData를 파일명과 일치시켜 관리하는 규칙을 팀에 정해 두는 것이 좋습니다.
민감 데이터 저장소가 늘어나면 키 로테이션 정책도 함께 논의해야 합니다.

마치며​

DataStore 1.3.0은 저장(암호화)과 생성(Builder API) 두 축을 한 번에 끌어올립니다.
안정 릴리스 전에 Tink 암호화 대상 데이터와 Builder 전환 범위를 정리해 두시기 바랍니다.

SharedPreferences에서 DataStore로 옮기고 숫자로 증명하기 — 대규모 앱의 마이그레이션 실측 사례

October 11, 2026 · 4 min read
Way
Android Developer

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.
대규모 앱의 DataStore 마이그레이션 실측 사례에 대해 설명해드리겠습니다.

배경​

SharedPreferences를 DataStore로 옮기고 싶은데 성능이 나빠지지는 않을까 망설이는 팀이 많습니다.
이번 ProAndroidDev 커뮤니티 글은 대규모 앱의 스토리지 기반을 통째로 갈아엎고, 영향을 숫자로 증명한 사례입니다.
한 대규모 앱 팀이 핵심 로컬 데이터를 SharedPreferences에서 Jetpack DataStore로 이전했습니다.
다른 변경의 영향이 섞이지 않도록 빌드를 3개로 나눠 측정한 결과, DataStore 자체의 런타임 비용은 측정 오차 범위 안이었습니다.
콜드 스타트, CPU, 메모리 모두 마찬가지입니다.
기존 사용자 데이터 마이그레이션은 백그라운드 스레드에서 1회 실행되며 수십 ms에 끝납니다.
저사양 기기 업데이트 시나리오에서도 첫 실행이 느려지지 않았습니다.

마이그레이션 사례 살펴보기​

왜 SharedPreferences를 떠났나​

글쓴이가 꼽은 SharedPreferences의 한계는 다섯 가지입니다.

  1. 첫 읽기가 동기식이라 메인 스레드에서 호출하면 화면이 같이 기다립니다.
  2. apply()는 비동기처럼 보이지만 Activity 종료 시점에 밀린 쓰기를 모두 기다립니다. 저장소가 느린 기기에서는 ANR로 이어질 수 있습니다.
  3. 쓰기 실패가 조용히 묻힙니다. apply()는 성공 여부를 알려주지 않습니다.
  4. 변경을 관찰하기 어렵습니다. 리스너 방식은 누수 나기 쉽고 코루틴/Flow와도 어울리지 않습니다.
  5. 타입이 강제되지 않습니다. Int로 저장한 걸 Long으로 읽으면 런타임에 ClassCastException으로 터집니다.

DataStore는 정확히 이 지점들을 겨냥한 설계이니, 왜 옮기는지에 대한 답은 비교적 명확합니다.

측정 방법이 인상적인 부분​

제일 배울 점은 측정 설계입니다.
이번 릴리스에는 DataStore 말고도 다른 변경이 많았기 때문에, 팀은 빌드를 3개로 나눠서 쟀습니다.

  • 이전 릴리스
  • 이번 릴리스에서 DataStore만 뺀 빌드
  • 실제로 배포한 이번 릴리스

두 번째와 세 번째의 차이가 곧 DataStore의 순수 비용입니다.
Xiaomi Redmi Note 9 Pro(Snapdragon 720G, 6GB RAM)에서 24분짜리 단일 세션에 몰아넣어 빌드당 10회 콜드 스타트를 연달아 쟀습니다.
결과는 모든 차이가 같은 빌드 내 변동 폭 안에 들었습니다.
오히려 CPU만은 B 화면 아이들 상태에서 2.6포인트 일관되게 내려갔고, 이건 두 번의 별도 측정 세션에서 모두 재현됐습니다.

저사양 기기 업데이트 시나리오​

마이그레이션이 실제로 도는 건 기존 사용자가 업데이트할 때라서, Galaxy A15에서 구버전 데이터를 깔아둔 상태로 10회씩 쟀습니다(Perfetto).
10회 콜드 스타트와 10회 웜 스타트 모두 새 APK가 빨랐고, 마이그레이션이 도는 첫 실행(7.04초)도 평균보다 느리지 않았습니다.
즉 마이그레이션이 기존 사용자를 붙잡지 않습니다.

실무에서 주의할 점​

  • "DataStore로 옮기면 느려진다"는 선입견을 깨는 수치입니다. 측정 오차 범위 안에 든다는 건, 실무적으로는 비용이 없다는 뜻입니다.
  • 하지만 이 팀의 결론은 "DataStore가 앱을 빠르게 했다"가 아닙니다. 같은 릴리스에서 Galaxy A55 기준 첫 화면이 0.7초 빨라진 건 팀 전체의 작업 덕분이고, DataStore는 그 발목을 잡지 않았을 뿐입니다. 숫자를 읽을 때 귀속 관계를 헷갈리면 안 됩니다.
  • 마이그레이션 소요 시간은 텔레메트리로 잡았습니다. 백그라운드에서 수십 ms에 끝난다는 주장이 "느낌"이 아니라 측정값인 게 이 글의 신뢰도를 올립니다.
  • 글쓴이 본인도 경고합니다. 모든 숫자는 물리 기기에서 직접 잰 내부 측정값이라, 내 앱·내 기기에서는 값이 다를 수 있습니다.

적용 패턴은 다음과 같습니다.
DataStore Preferences로 옮길 때 기존 SharedPreferences 데이터를 살리는 표준 패턴입니다.

// 기존 prefs 데이터를 잃지 않고 DataStore로 1회 마이그레이션
val Context.dataStore by preferencesDataStore(
    name = "settings",
    produceMigrations = { context ->
        listOf(SharedPreferencesMigration(context, "old_prefs"))
    }
)

// 읽기: 코루틴/Flow에 자연스럽게 연결
val darkMode = context.dataStore.data
    .map { prefs -> prefs[DARK_MODE_KEY] ?: false }

이 사례에서 가져갈 교훈은 두 가지입니다.
첫째, 성능을 우려하는 대규모 변경은 변경만 뺀 비교 빌드를 하나 더 만들어 측정하는 것입니다.
둘째, 마이그레이션 소요 시간을 텔레메트리 이벤트로 남겨서 운영 중에도 실제 숫자를 볼 수 있게 하는 것입니다.
이 두 가지만 해도 느려진 것 아니냐는 질문에 감이 아니라 숫자로 답할 수 있습니다.

마치며​

스토리지 마이그레이션은 사용자에게 보이지 않는 게 성공입니다.
유실도 없고, 중간에 끊긴 세션도 없고, 느려진 앱도 없는 것, 그걸 숫자로 증명한 사례가 나왔다는 점에서 아직 SharedPreferences에 머물러 있는 팀에게 한 번쯤 읽어볼 만한 글입니다.

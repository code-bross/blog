안드로이드 개발자에게 열린 Gemini 4 Argon — 자가 복구 빌드와 AGSL 셰이더

October 15, 2026 · 4 min read
Way
Android Developer

안녕하세요, 한국투자증권 한투 앱 개발자 way입니다.

구글이 10월 13일 Android Developers Blog에서 최신 플래그십 모델 Gemini 4 Argon을 안드로이드 개발 표면에 개방한다고 발표했습니다. 지난주에 다뤘던 Android CLI/디바이스 스트리밍, BYOA(원하는 에이전트 쓰기) 흐름의 연장선이라 함께 보면 좋습니다. 모델 자체보다 "에이전트가 빌드를 스스로 고치고, 셰이더까지 짜준다"는 부분에 주목해서 정리합니다.

핵심 요약​

  • 접근 경로 3가지: ① Google Antigravity(AI Ultra 구독, 데스크톱 앱·CLI·Android Studio Canary 내) ② Android Studio(Gemini API 유료 티어) ③ Google AI Studio(Playground/Build, AI Ultra 또는 Gemini API 유료 티어)
  • 클라이언트 인앱 AI: Firebase AI Logic 경유로 Gemini API 유료 티어 개발자가 앱 안에서 Gemini 4 Argon을 직접 쓸 수 있습니다.
  • Self-Healing Build Loops: 빌드 실패 시 Antigravity 하네스가 Gradle 데몬·Kotlin 컴파일러 로그를 모델에 그대로 피드백하고, 근본 원인을 반복 진단해 수정안을 냅니다. 편집 라운드마다 가설을 일관되게 유지하고 AST 인지를 활용해 표면 증상이 아닌 진짜 원인에 도달하도록 훈련됐다는 설명입니다.
  • Compose 셰이더 생성: AGSL(Android Graphics Shading Language)을 Compose Modifier.graphicsLayer나 셰이더 브러시에 직접 작성합니다. 120fps Compose 애니메이션과 함께 도는 경량 GPU 셰이더(프로스트드 글래스·동적 조명·파문 등)를 벡터·렌더링 수학까지 처리해 뽑아낸다고 합니다.
  • 인트로 가격 적용은 2026년 11월 30일까지입니다.

무엇이 달라졌는지​

지금까지 에이전트 코딩은 "코드 자동완성의 연장"에 가까웠습니다. 이번 발표가 말하는 방향은 클로즈드 루프 실행입니다. 빌드 → 실패 로그 수집 → 원인 진단 → 수정 → 재빌드를 사람이 아니라 하네스+모델이 돌리는 구조죠. Gradle 데몬과 Kotlin 컴파일러의 에러 스트림을 그대로 먹는다는 점이 핵심입니다. 로그를 읽는 사람이 아니라 빌드 시스템을 읽는 에이전트인 셈입니다.

UI 쪽도 눈에 띕니다. Compose 셰이더는 실무에서 진입 장벽이 높은 영역인데(AGSL 문법 + 렌더링 수학 + 성능 예산), 모델이 이를 "프로덕션급"으로 뽑아낸다는 주장입니다. 120fps 애니메이션과 공존하는 경량 셰이더라는 표현에서 타깃이 명확합니다. 검증은 직접 해봐야겠지만, 셰이더 브러시까지 에이전트에게 맡기는 워크플로가 생긴다는 건 디자인 시스템 팀에겐 의미 있는 변화입니다.

터미널 에이전트 연결은 공식 Android CLI 플러그인이 맡습니다. android init 한 줄이면 어떤 터미널 에이전트든 로컬 Android 도구와 연결되고, Antigravity라면 플러그인 설치로 끝납니다.

실무 영향 / 주의점​

  • 빌드 로그가 곧 에이전트의 입력입니다. Self-Healing이 위력을 내려면 빌드 실패 로그가 잘 읽혀야 합니다. 난독화된 멀티모듈 빌드에서 에이전트가 원인에 닿으려면, 지금부터라도 Gradle 빌드 스크립트와 에러 메시지를 사람이 읽을 수 있게 정리해 두는 게 이득입니다.
  • 비용 구조를 확인하세요. Antigravity는 AI Ultra 구독 전제, API 경로는 Gemini API 유료 티어 전제입니다. 인트로 가격(2026-11-30까지) 이후 정가를 모르면 팀 도입 판단이 어렵습니다. 도입 전에 Console에서 실제 과금을 먼저 확인하세요.
  • 셰이더 코드는 리뷰가 필수입니다. "프로덕션급"이라는 표현은 모델 벤더의 주장일 뿐, AGSL 셰이더는 GPU·디바이스별로 동작이 달라 실기 검증 없이는 못 씁니다. 에이전트가 짠 셰이더는 초안으로 보고 프레임 타임·배터리부터 재세요.
  • Firebase AI Logic 경로는 인앱 기능용입니다. 개발 워크플로(빌드 복구·코드 생성)와 앱 내 AI 기능(사용자 대면)은 접근 경로가 다릅니다. 팀에서 둘을 혼동하면 과금·권한 설계가 꼬입니다.

내 코드에서는 이렇게 적용할 생각입니다​

일단 터미널 에이전트에 Android CLI를 붙이는 것부터 시작해 볼 만합니다. 발표에서 안내한 명령 그대로입니다.

# 어떤 터미널 에이전트에서든: 로컬 Android 도구와 연결
android init

# Antigravity를 쓴다면: 공식 Android CLI 플러그인 설치
agy plugin install android-cli-plugin

Firebase AI Logic으로 인앱에 붙일 때는 모델 선택만 새 모델로 바꾸는 구조라, 기존 Vertex AI / Gemini Developer API 연동 코드의 모델명 교체 수준에서 검토가 가능합니다. 정확한 모델 식별자는 Firebase AI Logic 문서를 확인하고, 릴리스 직후에는 SDK 업데이트가 필요할 수 있습니다.

샘플 프로젝트도 함께 공개됐으니, 에이전트 워크플로를 팀에 도입하기 전에 퀵스타트로 감을 잡는 게 좋습니다.

Google Play에서 바이브코딩한 개인 앱을 바로 실행할 수 있게 됐다

October 14, 2026 · 2 min read
Way
Android Developer

안녕하세요, 한국투자증권 한투 앱 개발자 way입니다.

구글이 10월 13일 Google Play 업데이트를 발표했습니다. 여러 게임·발견 기능 소식이 함께 나왔는데, 개발자 입장에서 가장 눈여겨볼 건 Google AI Studio에서 바이브코딩으로 만든 커스텀 Android 앱을 Google Play를 통해 개인 앱(personal app)으로 바로 실행할 수 있게 된 소식입니다.

핵심 요약​

  • Google AI Studio에서 만든 앱을 Google Play에서 개인 앱으로 자신의 기기에 실행 가능
  • 별도의 개발자 계정 없이 일반 Google 계정으로 가능
  • 개인 앱은 공개 스토어 카탈로그와 분리되어 private하고 안전하게 유지
  • 10월 13일부터 선별 시장에 롤아웃 (미국 포함, 18세 이상)
  • 향후 몇 달 내 친구·가족과의 소규모 공유 지원 예정

무엇이 달라졌는지​

예전에는 AI로 뚝딱 만든 앱을 실기기에 올리려면 APK를 직접 빌드해서 설치하거나, 내부 테스트 트랙용으로 Play Console에 올리는 절차가 필요했습니다. 이제 그 과정을 Play가 직접 감싸줍니다. "there's an app for that"에서 "there's an app for me"로,라는 게 구글의 표현입니다.

정식으로 세상에 공개하고 싶어지면 프로 개발자 계정으로 전환하면 되고, 그 시점부터는 다른 앱들과 동일한 Trust & Safety 리뷰와 품질 기준이 적용됩니다. 즉, 실험 구간과 배포 구간의 경계가 명확해졌다는 뜻입니다.

실무 영향 / 주의점​

  • 기획·QA용 내부 실험 빌드 경로가 더 가벼워질 여지가 있습니다. 내부 테스트 트랙보다도 진입 장벽이 낮은 개인 실행 경로가 생긴 셈입니다.
  • 공개 스토어 리뷰와 완전히 분리되므로, 실험적인 기능을 개인 기기에서 빠르게 돌려보는 용도로 적합합니다.
  • 단, 아직은 선별 시장 중심 롤아웃이라 한국에서 바로 사용할 수 있는지는 확인이 필요합니다.
  • 프로 계정 전환 시점의 리뷰는 기존과 동일하니, "일단 올리고 보자"식 접근은 여전히 통하지 않습니다.

함께 발표된 내용​

  • Ask Play: 질문에 맞는 앱 추천 + 앱 간 비교(주요 차이점, 사용자 반응) 생성
  • Play in Gemini: Gemini 대화 안에서 Play 앱·게임·개발자 콘텐츠 접근
  • Game Finder: 플레이 취향 분석(Gamer DNA) 기반 게임 추천, 미국 영어 사용자에게 먼저 제공
  • 게임 관련: 48시간 미니 챌린지 Sprints, Sidekick 오버레이의 30초 Playbacks 녹화, 게임 상세 페이지의 Community Posts
  • Family Link를 통한 연령대 정보 공유로 연령에 맞는 경험 제공

ML Drift 오픈소스 공개 — LiteRT GPU 가속의 새 엔진, TFLite GPU delegate의 뒤를 잇다

October 10, 2026 · 5 min read
Way
Android Developer

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.
2026년 10월 8일, Google AI Edge 팀이 온디바이스 GPU 추론을 위한 새 엔진 ML Drift를 Apache 2.0 라이선스로 공개했습니다. LiteRT 안에서 GPU 가속을 맡는 중심 엔진이기도 하고, 따로 떼어내어 커스텀 그래픽이나 추론 런타임을 만들 때 쓰는 독립 라이브러리로도 쓸 수 있습니다.

핵심 요약​

  • ML Drift는 기기마다 다른 GPU 환경을 한 층으로 감싸는 크로스 플랫폼 GPU 컴퓨트 엔진입니다. 뒤쪽에서는 OpenGL ES, OpenCL, Metal, WebGPU 같은 서로 다른 그래픽 경로를 다룹니다.
  • 기존 TensorFlow Lite GPU delegate가 맡던 자리를 이어받는 방향이며, 앞으로 그 예전 경로는 새 기능을 더 받지 않습니다. 이동 경로는 LiteRT의 ML Drift GPU 가속 경로입니다.
  • 고전적인 비전 모델뿐 아니라, 기기에서 도는 생성형 모델까지 함께 노린 구조 개편이 들어갔습니다.

서버에서는 비슷한 가속기가 줄지어 있지만, 휴대폰은 칩과 드라이버와 그래픽 경로가 제각각입니다. 이 다양성을 앱 개발자가 직접 메우지 않게 하는 것이 이 엔진이 풀려는 문제입니다.

무엇이 달라졌는지​

텐서를 바라보는 방식을 바꿨다​

예전 방식에서는 텐서가 GPU의 텍스처나 버퍼 같은 실제 자원에 어떻게 붙는지를 백엔드마다 따로 적어 두는 일이 많았습니다. ML Drift는 여기서 한 단계 추상화를 넣었습니다. 논리적인 텐서와 실제 GPU 배치를 분리해 두고, 초기 설정 단계에서 셰이더가 그 연결을 풀어내는 구조입니다. 덕분에 백엔드마다 셰이더를 따로 유지하는 부담을 줄이면서도 실행 중 부담은 작게 가져가려 했다는 설명입니다.

5차원 텐서와 시공간 모델​

예전 GPU 경로는 4차원 텐서를 전제로 짜여 있어, 그보다 복잡한 모양이 필요하면 우회로를 만들어야 했습니다. 새 엔진에서는 5차원 텐서를 기본으로 다룰 수 있게 되면서, 3차원 합성곱이나 영상처럼 시간 축이 붙은 모델을 기기 GPU에서 바로 돌리는 길이 넓어졌습니다.

LLM 단계에 따라 커널을 바꾼다​

기기에서 도는 언어 모델은 한 번에 길게 읽어 들이는 구간과, 토큰을 하나씩 이어 붙이는 구간의 성격이 다릅니다. 앞쪽은 연산량에, 뒤쪽은 메모리 이동에 더 묶입니다. ML Drift는 지금이 어느 단계인지에 따라 커널과 배치를 바꾸고, KV 캐시 쪽에도 전용 배치를 적용해 불필요한 왕복을 줄이는 방향을 택했습니다.

커스텀 연산과 데스크톱 확장​

모델에 특이한 블록이 있으면 개발자가 낮은 수준의 셰이딩 언어로 직접 연산을 등록할 수 있는 길도 새로 정리됐습니다. 흥미로운 부분은, 코딩 에이전트가 이 커스텀 셰이더를 만들고 검증하는 과정을 돕는 안내 파일까지 함께 제공된다는 점입니다. 또 WebGPU 경로를 바탕으로 브라우저 밖 Windows와 Linux에서도 같은 코드를 돌리는 미리보기가 소개됐고, macOS에서는 Metal 경로가 이를 받칩니다.

실제 서비스에서의 쓰임도 함께 소개됐습니다. 영상 효과, 사진 보정, 브라우저 안 온디바이스 모델, 사진 편집 앱의 피사체 선택 같은 작업에서 기존 GPU 경로보다 지연이 줄었다는 사례가 실렸습니다. 숫자는 모델과 기기마다 다르니, 결국 내 모델로 재보는 수밖에 없습니다.

실무 영향 / 주의점​

  • TFLite GPU delegate를 직접 쓰고 있다면 이동 계획을 세울 때입니다. 새 기능이 그쪽으로 더 오지 않는다고 못 박은 만큼, 지금 당장 끊기지는 않더라도 다음 모델 교체나 성능 개선 시점에 LiteRT 경로로 벤치마크를 한 번은 돌려봐야 합니다.
  • 벤치마크는 모델 전체 평균만 보면 안 됩니다. 언어 모델이라면 읽어 들이는 구간과 토큰을 만드는 구간의 속도가 따로 움직입니다. 두 구간을 나눠 재지 않으면 병목이 어디인지 놓치기 쉽습니다.
  • GPU 벤더별 확인은 여전히 필요합니다. 추상화가 좋아졌다고 해도 실제 속도는 칩과 드라이버에서 갈립니다. 플래그십 한 대에서만 재고 끝내면 중저가 기기에서 체감이 다르게 나올 수 있습니다.
  • 커스텀 연산은 강력하지만 유지 비용이 붙습니다. 직접 짠 셰이더는 모델을 바꿀 때마다 다시 봐야 합니다. 꼭 필요한 블록에만 쓰고, 나머지는 기본 연산으로 두는 편이 운영에 낫습니다.

금융 앱 관점에서는, 사진을 읽어 문서를 인식하거나 기기 안에서 작은 모델로 분류하는 작업을 서버로 보내지 않고 끝낼 수 있을 때 의미가 큽니다. 데이터를 기기 밖으로 내보내지 않는 구조는 개인정보와 네트워크 비용 양쪽에서 이득이 있기 때문입니다. 다만 그 전제는 결국 속도인데, 이번 개편은 그 속도를 벤더 중립적으로 끌어올리려는 시도라고 읽힙니다.

내 코드에서는 이렇게 재볼 생각입니다​

저라면 기존에 GPU delegate로 돌리던 모델을 LiteRT 경로로 바꿔 같은 기기에서 나란히 재는 것부터 시작하겠습니다. 아래는 개념을 잡기 위한 예시 흐름입니다.

// 같은 모델을 CPU와 GPU 경로로 각각 준비해 지연을 나눠 재는 벤치마크 뼈대
data class BenchResult(
    val backend: String,
    val warmupMs: Double,
    val steadyMs: Double,
)

fun benchmarkModel(backend: String): BenchResult {
    // 1) LiteRT 모델을 backend 옵션으로 연다 (GPU면 ML Drift 가속 경로)
    // 2) warm-up을 충분히 돌린 뒤, 입력 모양별로 지연을 측정한다
    // 3) 언어 모델이면 prefill과 decode를 분리해서 기록한다
    return BenchResult(backend, warmupMs = 0.0, steadyMs = 0.0)
}

val results = listOf("CPU", "GPU").map { benchmarkModel(it) }
results.forEach { println("${it.backend}: steady=${it.steadyMs}ms") }

여기에 기기 이름과 칩 정보, 모델 버전을 함께 남겨 두면 나중에 "어떤 폰에서 느려졌는지"를 추적하기가 훨씬 쉬워집니다. 커스텀 연산은 이 기본 측정이 끝난 뒤, 프로파일에서 실제로 뜨거운 블록이 보일 때만 손대는 순서가 좋겠습니다.

독립 라이브러리 쪽이 궁금하다면 공개 저장소에서 Android용 OpenCL 시작 가이드부터 볼 수 있습니다.

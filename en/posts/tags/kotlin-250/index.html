Kotlin 2.5.0-RC2에서 컴파일러 실행에 JDK 17이 필수가 됩니다

November 27, 2026 · 3 min read
Way
Android Developer

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.
2026년 11월 25일에 공개된 Kotlin 2.5.0-RC2의 JDK 17 최소 요구사항과 Java 28 바이트코드 지원에 대해 설명해드리겠습니다.
이번 변경은 컴파일러를 실행하는 JDK 버전과 직접 관련이 있어, 빌드 환경을 먼저 점검해야 합니다.

배경​

Kotlin 컴파일러는 그동안 JDK 8에서도 실행할 수 있었습니다.
2.5.0-Beta1부터 JDK 17보다 오래된 버전으로 컴파일러를 실행하면 경고가 나왔습니다.
2.5.0-RC2부터는 경고가 아니라 오류가 발생합니다.
컴파일러를 실행하는 JDK의 최소 버전이 17로 올라간 것입니다.
JetBrains는 새 Java 라이브러리를 활용하고 Gradle과 Maven과의 호환성을 유지하기 위해 최소 버전을 올렸다고 설명했습니다.

Kotlin 2.5.0-RC2의 JDK 요구사항 살펴보기​

컴파일러 실행에 JDK 17 이상이 필요합니다​

Kotlin 2.5.0-RC2부터 JDK 17보다 오래된 JDK로 Kotlin 컴파일러를 실행하면 빌드가 오류로 멈춥니다.
대상은 앱이 실행될 때 쓰는 런타임 JDK가 아니라, 컴파일러 자체를 실행하는 JDK입니다.
기존 프로젝트가 JDK 8이나 JDK 11로 빌드되고 있었다면, Kotlin 버전을 올리는 시점에 함께 확인해야 합니다.
이 변경은 2.5.0 정식 릴리스에서도 그대로 이어질 예정입니다.

일시적으로 오류를 피하는 방법​

아직 JDK를 올릴 수 없는 프로젝트에서는 -Xallow-pre-17-runtime-jdk 컴파일러 옵션을 추가하면 오류를 피할 수 있습니다.
이 옵션은 임시 방편이며, Kotlin 2.5.20이나 2.6.0에서는 제거될 예정입니다.
따라서 옵션을 넣는 것으로 끝내지 말고, JDK 17 이상으로 올리는 일정을 함께 잡는 것이 좋습니다.

kotlin {
    compilerOptions {
        freeCompilerArgs.add("-Xallow-pre-17-runtime-jdk")
    }
}

Java 28 바이트코드 생성 지원​

Kotlin 2.5.0-RC2부터 컴파일러는 Java 28 바이트코드를 포함하는 클래스를 생성할 수 있습니다.
JVM 타깃 버전을 높이는 프로젝트에서는 새로운 바이트코드 버전을 선택할 수 있게 되었습니다.
다만 Java 28 자체는 아직 정식 출시 전이므로, 당장 운영 코드의 타깃을 올리기보다는 지원 범위가 넓어졌다는 점으로 이해하는 것이 좋습니다.

프로젝트의 JDK 확인하기​

Gradle 프로젝트에서는 Kotlin DSL의 jvmToolchain으로 컴파일에 쓸 JDK 버전을 지정할 수 있습니다.
다음과 같이 지정하면 컴파일러가 JDK 17로 실행됩니다.

kotlin {
    jvmToolchain(17)
}

현재 빌드에 쓰이는 JDK는 ./gradlew -version 명령으로 확인할 수 있습니다.
출력되는 JVM 항목이 17보다 낮다면, gradle.properties의 org.gradle.java.home 설정이나 CI 에이전트에 설치된 JDK를 확인해야 합니다.
Android Studio는 내장 JDK를 함께 제공하므로, 로컬 빌드와 CI 빌드의 JDK가 다를 수 있다는 점도 함께 점검해야 합니다.

실무 관점​

MTS처럼 규모가 큰 프로젝트에서는 로컬 환경보다 CI 에이전트의 JDK 버전을 먼저 확인하는 것이 좋습니다.
에이전트 이미지에 JDK 8이나 JDK 11만 설치되어 있다면, Kotlin 2.5.0으로 올리는 순간 빌드가 멈춥니다.
옵트아웃 옵션은 마이그레이션 기간에만 쓰고, 정식 릴리스 전에 JDK 17 이상으로 전환하는 일정을 잡는 것이 안전합니다.
RC 버전이므로 릴리스 브랜치에는 적용하지 않고, 별도 브랜치에서 동작을 확인하는 것이 좋습니다.

마치며​

Kotlin 2.5.0-RC2부터 컴파일러 실행에는 JDK 17 이상이 필요합니다.
빌드 환경을 먼저 점검하고, Java 28 바이트코드 지원과 함께 정식 릴리스를 준비하는 것이 좋습니다.

Kotlin 2.5.0-RC2의 KMP 새 컴파일 방식과 게시 포맷 살펴보기

November 27, 2026 · 3 min read
Way
Android Developer

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.
2026년 11월 25일에 공개된 Kotlin 2.5.0-RC2의 Kotlin Multiplatform 새 컴파일 방식과 새 게시 포맷에 대해 설명해드리겠습니다.
두 변경 모두 실험적 기능이지만, 멀티플랫폼 프로젝트의 빌드와 게시 방식을 바꿀 수 있는 내용입니다.

배경​

Kotlin Multiplatform 프로젝트에서는 공통 소스셋의 코드를 컴파일러와 IDE가 다르게 해석하는 경우가 있었습니다.
오버로드 해석이나 타입 추론에서 IDE 분석과 컴파일러 판단이 달라지면, IDE에서는 되던 코드가 빌드에서 실패하기도 합니다.
게시 측면에서는 타깃을 추가할 때마다 게시 파일이 늘어나 Maven Central의 게시 크기 제한에 걸리는 문제도 있었습니다.
이번 릴리스에서는 이 두 가지 문제를 다루는 실험적 기능이 함께 공개되었습니다.

KMP 새 컴파일 방식과 게시 포맷 살펴보기​

공통 소스셋을 따로 컴파일하는 새 방식​

Kotlin 2.5.0-RC2에서는 Kotlin Multiplatform을 위한 새로운 실험적 컴파일 방식이 추가되었습니다.
이 방식에서는 컴파일러가 공통 소스셋을 IDE와 같은 기준으로 처리합니다.
공통 코드가 플랫폼 전용 선언으로 잘못 해석되는 일을 막고, 오버로드 해석과 타입 추론의 일관성을 높입니다.
공통 소스셋에 대한 증분 컴파일을 구현하는 기반도 됩니다.
자세한 내용은 Kotlin 2.5.0-RC2 변경 사항에서 확인할 수 있습니다.

.kar 아카이브 게시 포맷​

Kotlin 2.5.0-RC2에서는 멀티플랫폼 라이브러리를 위한 새로운 실험적 게시 포맷이 추가되었습니다.
새 포맷은 JVM과 Android을 제외한 플랫폼 아티팩트를 하나의 .kar 아카이브로 게시합니다.
.kar 파일은 ZIP 아카이브를 XZ로 한 번 더 압축한 형태입니다.
타깃을 추가해도 새 파일이 생기지 않으므로, 게시물 전체 크기가 크게 늘어나지 않습니다.
JetBrains가 예시로 든 cryptography-kotlin 라이브러리에서는 게시 파일이 7,539개에서 1,036개로, 전체 크기가 91MB에서 23MB로 줄었습니다.

모듈 단위로 새 포맷을 켜려면 빌드 스크립트에 다음과 같이 설정합니다.

kotlin {
    publishing {
        publicationFormat.set(KotlinPublicationFormat.KOTLIN_ARCHIVE)
    }
}

프로젝트의 모든 모듈에 적용하려면 gradle.properties에 다음 속성을 추가합니다.

kotlin.publicationFormat=KOTLIN_ARCHIVE

새 포맷으로 게시하는 기능은 아직 실험적이지만, 새 포맷으로 게시된 아티팩트를 가져다 쓰는 기능은 모든 프로젝트에서 이미 사용할 수 있습니다.
이 변경은 라이브러리를 게시하는 쪽에만 해당하며, 최종 앱을 만드는 개발자에게는 직접적인 영향이 없습니다.

실무 관점​

새 컴파일 방식은 공통 소스셋의 동작을 바꾸는 실험적 기능입니다.
적용하기 전에는 별도 브랜치에서 기존 테스트가 그대로 통과하는지 확인하는 것이 좋습니다.
.kar 게시 포맷은 MTS처럼 최종 앱을 만드는 프로젝트보다는, 내부 공용 라이브러리를 Maven에 게시하는 경우에 의미가 있습니다.
게시 크기가 제한에 걸려 타깃 추가를 미루고 있었다면, 새 포맷을 검토해 볼 만합니다.
두 기능 모두 실험적이므로, 정식 릴리스에서 동작이 바뀔 수 있다는 점을 고려해야 합니다.

마치며​

Kotlin 2.5.0-RC2의 새 컴파일 방식은 공통 소스셋의 해석을 IDE와 일치시키는 방향으로 나아가고 있습니다.
새 게시 포맷은 멀티플랫폼 라이브러리의 게시 크기를 크게 줄여, 타깃 확장의 부담을 덜어줍니다.

Kotlin 2.5.0-RC2의 새로운 표준 라이브러리 함수 살펴보기

November 26, 2026 · 5 min read
Way
Android Developer

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.

2026년 11월 25일에 공개된 Kotlin 2.5.0-RC2의 새로운 표준 라이브러리 함수에 대해 설명해드리겠습니다.
이번 릴리스에서는 이름 기반 구조 분해와 미사용 반환값 검사기가 안정화되었습니다.
이 글에서는 앞선 글에서 다루지 않은 표준 라이브러리의 새 함수와 엄격한 동등성 검사, Java 28 지원을 살펴보겠습니다.

배경​

if 표현식은 Kotlin에서 조건에 따라 값을 반환하는 가장 기본적인 방법입니다.
기존에는 조건이 참일 때만 부수 효과를 실행하거나, 조건에 따라 널이 될 수 있는 결과를 반환하려면 else 분기를 직접 써야 했습니다.
이번 릴리스에서는 이런 반복적인 패턴을 줄이는 실험적 함수가 표준 라이브러리에 추가되었습니다.
함께 공개된 유니코드 코드 포인트 지원과 구조적 클래스에 대한 엄격한 동등성 검사도 살펴볼 만한 변경입니다.

새로운 표준 라이브러리 함수 살펴보기​

onTrue()와 onFalse()​

onTrue()는 Boolean 값에 대한 확장 함수입니다.
값이 true일 때 지정한 코드 블록을 실행하고, 원래의 Boolean 값을 그대로 반환합니다.
onFalse()는 값이 false일 때 같은 방식으로 동작합니다.
반환값을 그대로 유지하므로, 메서드 호출 결과에 이어서 부수 효과를 붙이는 형태로 사용할 수 있습니다.

@OptIn(ExperimentalStdlibApi::class)
fun main() {
    val tags = mutableSetOf("kotlin", "jvm")

    // add()가 true를 반환하면 메시지를 출력합니다.
    val added = tags.add("wasm").onTrue {
        println("Tag added")
    }
    println(added) // Tag added
    // true

    // remove()가 false를 반환하면 메시지를 출력합니다.
    val removed = tags.remove("native").onFalse {
        println("Tag not found")
    }
    println(removed) // Tag not found
    // false
}

ifOrNull()​

ifOrNull()은 조건이 true일 때 코드 블록을 실행해 그 결과를 반환하는 최상위 함수입니다.
조건이 false이면 블록을 실행하지 않고 null을 반환합니다.
if 표현식과 else 분기로 null을 반환하던 패턴을 한 줄로 줄일 수 있습니다.

@OptIn(ExperimentalStdlibApi::class)
fun main() {
    val tags = mutableSetOf("kotlin", "jvm", "wasm")

    val message = ifOrNull("wasm" in tags) {
        "Wasm tag is available"
    }
    println(message) // Wasm tag is available

    val missing = ifOrNull("native" in tags) {
        "Native tag is available"
    }
    println(missing) // null
}

세 함수는 모두 실험적 기능입니다.
사용하려면 @OptIn(ExperimentalStdlibApi::class) 애너테이션을 붙이거나, -opt-in=kotlin.ExperimentalStdlibApi 컴파일러 옵션을 추가해야 합니다.

CodePoint와 유니코드 코드 포인트 지원​

Char는 UTF-16 코드 단위 하나를 나타냅니다.
일부 유니코드 코드 포인트는 서로게이트 쌍이라 불리는 Char 두 개로 표현됩니다.
문자열을 Char 단위로 순회하면 서로게이트 쌍의 절반씩을 별개의 요소로 처리하게 됩니다.
이번 릴리스에서는 kotlin.text.unicode 패키지에 CodePoint 인라인 값 클래스와 관련 API가 실험적으로 추가되었습니다.
CodePoint는 Int를 내부 타입으로 사용하며, 코드 포인트의 UTF-16 코드 단위 수, 유니코드 범주, 문자·숫자·공백 여부를 확인할 수 있습니다.
코드 포인트를 세고 순회하거나, 대소문자를 변환하고, 텍스트에 추가·삽입·교체·삭제하는 API도 함께 제공됩니다.
이 API는 실험적 기능이며, @OptIn(ExperimentalUnicodeApi::class) 애너테이션이나 -opt-in=kotlin.text.unicode.ExperimentalUnicodeApi 컴파일러 옵션을 통한 옵트인이 필요합니다.
자세한 내용은 해당 기능의 KEEP에서 확인할 수 있습니다.

구조적 클래스에 대한 엄격한 동등성 검사​

Kotlin 2.5.0-RC2에서는 데이터 클래스, 데이터 객체, final 값 클래스, enum 클래스를 묶어 구조적 클래스라고 부릅니다.
새로운 검사 기능은 이런 클래스 사이의 동등성 비교를 분석해, 항상 false가 되는 == 비교나 항상 true가 되는 != 비교를 진단합니다.
프로퍼티가 같아도 타입이 다른 두 클래스를 비교하는 실수를 컴파일 시점에 잡을 수 있습니다.

data class Point(val x: Double, val y: Double) {
    companion object {
        val ZERO: Point = Point(0.0, 0.0)
    }
}

data class Vector(val x: Double, val y: Double)

fun normalize(v: Vector) {
    if (v == Point.ZERO) {
        // 진단: 이 비교는 항상 false입니다.
        // Vector와 Point를 비교하고 있습니다.
    }
}

이 검사를 사용하려면 -Xstrict-equality-for-structural-classes 컴파일러 옵션을 추가해야 합니다.
자세한 내용은 해당 기능의 KEEP에서 확인할 수 있습니다.

Java 28 지원​

Kotlin 2.5.0-RC2부터 컴파일러는 Java 28 바이트코드를 포함하는 클래스를 생성할 수 있습니다.

Kotlin 2.5.0-RC2의 companion extensions와 full value classes

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.

2026년 11월 25일에 공개된 Kotlin 2.5.0-RC2의 새로운 실험적 기능에 대해 설명해드리겠습니다.

이번 릴리스에서는 이름 기반 구조 분해와 미사용 반환값 검사기가 안정화되었습니다.
이와 함께 companion extensions와 companion blocks, full value classes가 실험적 기능으로 추가되었습니다.
두 기능 모두 기존에 작성하던 코드를 더 간결하게 바꿀 수 있는 방향입니다.

배경​

기존에는 타입 이름으로 접근하는 확장 함수나 프로퍼티를 선언하려면 해당 타입에 companion object가 필요했습니다.
companion object가 없는 타입에는 타입 이름을 통한 확장을 붙일 수 없었습니다.
또한 여러 프로퍼티를 묶은 값 타입을 만들려면 일반 클래스나 data class를 사용해야 했습니다.
data class는 참조 식별성을 가지므로, 값 자체만으로 동등성을 다루기에는 한계가 있었습니다.

Kotlin 2.5.0-RC2 살펴보기​

companion extensions와 companion blocks​

companion extensions는 companion object가 없는 타입에도 타입 이름을 통한 확장을 선언할 수 있게 합니다.
최상위 확장에 companion 수식어를 붙이면 됩니다.
companion block은 클래스나 인터페이스 안에 객체 인스턴스를 만들지 않고 함수와 프로퍼티를 선언하는 블록입니다.
JVM에서는 정적 멤버로 생성되므로 @JvmStatic 애너테이션을 붙일 필요가 없습니다.

// companion extension으로 UnitX 선언
companion val Vector.UnitX get() = Vector(1.0, 0.0)

data class Vector(val x: Double, val y: Double) {
    companion {
        // companion block으로 Zero 선언
        val Zero: Vector get() = Vector(0.0, 0.0)
    }
}

fun main() {
    println(Vector.UnitX) // Vector(x=1.0, y=0.0)
    println(Vector.Zero) // Vector(x=0.0, y=0.0)
}

이 기능은 실험적 기능입니다.
사용하려면 빌드 파일에 다음 컴파일러 옵션을 추가합니다.

kotlin {
    compilerOptions {
        freeCompilerArgs.add("-Xcompanion-blocks-and-extensions")
    }
}

full value classes​

기존의 inline value class는 하나의 값만 감쌀 수 있었습니다.
여러 프로퍼티가 필요한 값 타입은 일반 클래스나 data class로 만들어야 했습니다.
full value classes는 여러 프로퍼티를 가진 값 타입을 정의할 수 있게 합니다.
인스턴스의 식별성은 중요하지 않고, 프로퍼티들의 조합이 곧 값입니다.

value class Complex(val real: Double, val imaginary: Double)

컴파일러는 data class와 마찬가지로 equals()와 hashCode(), toString()을 자동 생성합니다.
다만 componentN() 함수는 생성되지 않습니다.
대신 이름 기반 구조 분해를 사용합니다.
copy() 함수도 제공되지 않으며, 향후 copy vars로 대체될 예정입니다.

value class Complex(val real: Double, val imaginary: Double)

fun main() {
    val (val real, val imaginary) = Complex(1.0, 2.0)
    println(real) // 1.0
    println(imaginary) // 2.0
}

이 기능도 실험적 기능입니다.
사용하려면 빌드 파일에 다음 컴파일러 옵션을 추가합니다.

kotlin {
    compilerOptions {
        freeCompilerArgs.add("-Xfull-value-classes")
    }
}

value objects와 추상 value class​

프로퍼티가 없는 full value class는 value object라고 부릅니다.
상태나 토큰처럼 가능한 값이 하나뿐인 타입을 표현할 때 사용합니다.

sealed interface UserResponse

value class UserFound(val user: User) : UserResponse

value object UserUnknown : UserResponse

full value class는 추상 클래스로도 선언할 수 있습니다.
인터페이스와 달리 모든 하위 클래스가 실행하는 초기화 로직을 정의할 수 있습니다.

sealed value class OrderedInterval<T : Comparable<T>> protected constructor(
    start: T,
    end: T,
) {
    init {
        require(start <= end)
    }
}

value class IntInterval(
    val start: Int,
    val end: Int
) : OrderedInterval<Int>(start, end)

구조적 클래스에 대한 엄격한 동등성 검사​

이번 릴리스에서는 data class, data object, final value class, enum class를 구조적 클래스라고 부릅니다.
컴파일러는 이 클래스들에 대해 엄격한 동등성 검사를 수행합니다.
타입이 달라 항상 false가 되는 비교를 진단으로 알려줍니다.

data class Point(val x: Double, val y: Double) {
    companion object {
        val ZERO: Point = Point(0.0, 0.0)
    }
}

data class Vector(val x: Double, val y: Double)

fun normalize(v: Vector) {
    if (v == Point.ZERO) {
        // 진단: 이 비교는 항상 false입니다.
        // Vector를 Point와 비교하고 있습니다.
    }
}

이 검사는 다음 컴파일러 옵션으로 활성화합니다.

kotlin {
    compilerOptions {
        freeCompilerArgs.add("-Xstrict-equality-for-structural-classes")
    }
}

실무 관점​

두 기능 모두 아직 실험적 기능이므로 운영 코드에 바로 적용하기는 이릅니다.
RC 버전은 정식 릴리스 직전 단계이므로, 별도 브랜치에서 기능을 미리 확인해 보는 용도로 적합합니다.
특히 MTS처럼 규모가 큰 프로젝트에서는 컴파일러 옵션을 전역으로 켜기 전에 영향 범위를 먼저 확인해야 합니다.
실험적 기능은 정식 릴리스에서 문법이나 옵션이 바뀔 수 있다는 점도 함께 고려해야 합니다.

마치며​

companion extensions와 full value classes는 Kotlin의 값 표현 방식을 한층 넓혀주는 기능입니다.

Kotlin 2.5.0-RC 살펴보기 — 이름으로 꺼내는 구조 분해

Way

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.
11월 11일에 공개된 Kotlin 2.5.0-RC에서 안정화된 이름 기반 구조 분해에 대해 설명해드리겠습니다.

배경​

구조 분해는 객체를 여러 변수로 한 번에 나누는 문법입니다.
데이터 클래스의 값을 꺼낼 때 자주 사용합니다.
지금까지의 구조 분해는 위치 기반이었습니다.
변수는 프로퍼티 순서대로 componentN() 함수의 결과와 연결되었습니다.
이 방식에서는 변수 이름과 프로퍼티 이름이 달라도 컴파일러가 아무런 경고를 내지 않았습니다.
순서만 맞으면 이름이 뒤바뀐 채로 값이 들어가도 그대로 동작했습니다.
프로퍼티 순서가 바뀌면 받는 쪽 코드도 함께 바꿔야 했습니다.
이름 기반 구조 분해는 이 문제를 해결하기 위해 도입되었습니다.
변수를 위치가 아니라 프로퍼티 이름으로 연결하는 방식입니다.

이름 기반 구조 분해 살펴보기​

이름 기반 구조 분해는 Kotlin 2.5.0-RC에서 only-syntax 모드로 안정화되었습니다.
only-syntax 모드는 이제 기본값이므로, 별도의 컴파일러 옵션을 지정하지 않아도 새 문법을 사용할 수 있습니다.
기존 문법의 동작은 그대로 유지됩니다.
하나씩 살펴보겠습니다.

기존 방식의 문제​

위치 기반 구조 분해에서는 변수가 선언된 순서대로 값이 들어갑니다.
다음 예시에서 email 변수에는 username 값이 들어갑니다.

data class User(val username: String, val email: String)

fun main() {
    val user = User("alice", "alice@example.com")

    val (email, username) = user
    println(email) // alice
    println(username) // alice@example.com
}

email이라는 이름으로 username 값을 받는 코드가 컴파일됩니다.
실행 결과도 오류가 아니라 잘못된 값으로 나옵니다.
이런 실수는 코드 리뷰에서도 놓치기 쉽습니다.

새 문법​

이름 기반 구조 분해는 변수 앞에 val을 붙이는 명시적 형식을 사용합니다.
변수는 프로퍼티 이름과 연결됩니다.
이름을 바꿔서 받고 싶으면 =으로 새 이름을 지정할 수 있습니다.

data class User(val username: String, val email: String)

fun main() {
    val user = User("alice", "alice@example.com")

    (val mail = email, val name = username) = user
    println(name) // alice
    println(mail) // alice@example.com
}

mail 변수에는 email 프로퍼티 값이 들어갑니다.
name 변수에는 username 프로퍼티 값이 들어갑니다.
선언 순서와 프로퍼티 순서는 달라도 됩니다.
이름이 기준이 되므로, 프로퍼티 순서가 바뀌어도 받는 쪽 코드는 그대로 동작합니다.

세 가지 모드​

이름 기반 구조 분해의 동작은 컴파일러 옵션 -Xname-based-destructuring으로 조절할 수 있습니다.
모드는 세 가지입니다.
only-syntax 모드는 명시적 형식만 허용하고, 기존 구조 분해의 동작은 바꾸지 않습니다.
2.5.0-RC에서는 이 모드가 기본값입니다.
name-mismatch 모드는 위치 기반 구조 분해에서 변수 이름이 프로퍼티 이름과 다르면 경고를 냅니다.
complete 모드는 괄호 짧은 형식을 이름 기반으로 바꾸고, 위치 기반은 대괄호 문법으로 옮깁니다.

val point = Pair(10, 20)

// complete 모드에서 위치 기반 구조 분해는 대괄호를 사용합니다.
val [x, y] = point

대괄호 문법은 순서가 중요한 타입에 사용합니다.
Pair나 Triple, 리스트 같은 타입이 그 예입니다.
complete 모드는 아직 실험 단계이므로, 당장은 기본값인 only-syntax 모드로 시작하는 것이 안전합니다.

Full Value Class와 함께 쓰기​

Kotlin 2.5.0-RC에는 실험 기능인 full value class도 함께 들어왔습니다.
full value class에는 componentN() 함수가 없습니다.
그래서 위치 기반 구조 분해는 사용할 수 없고, 이름 기반 구조 분해로 값을 꺼냅니다.

value class Complex(val real: Double, val imaginary: Double)

fun main() {
    val value = Complex(1.0, 2.0)

    (val real, val imaginary) = value
    println(real) // 1.0
    println(imaginary) // 2.0
}

이름 기반 구조 분해는 full value class의 값을 꺼내는 기본 수단이 됩니다.
데이터 클래스와 full value class를 같은 방식으로 다룰 수 있습니다.

적용하기​

Kotlin 2.5.0-RC는 Version Catalog에서 Kotlin 버전을 교체하면 적용할 수 있습니다.

[versions]
kotlin = "2.5.0-RC"

[plugins]
kotlin-android = { id = "org.jetbrains.kotlin.android", version.ref = "kotlin" }

RC는 정식 출시 직전 단계이므로, 새 기능이 동결되고 안정화 작업이 중심이 됩니다.
only-syntax 모드는 안정화된 기능이지만, RC 버전 자체는 정식 버전이 아닙니다.
새 문법은 브랜치에서 먼저 사용해 보고, 정식 출시 이후에 본 코드에 적용하는 것이 안전합니다.

실무 관점​

국내 MTS 프로젝트에 적용한다면, API 응답 모델처럼 프로퍼티가 많은 데이터 클래스부터 살펴보는 것이 좋습니다.
서버 응답 필드 순서가 바뀌어도 이름으로 꺼내면 받는 쪽이 영향을 받지 않습니다.
다만 새 문법을 팀 전체가 같은 기준으로 써야 합니다.
일부는 위치 기반, 일부는 이름 기반으로 섞어 쓰면 코드가 읽기 어려워집니다.
complete 모드는 아직 실험 단계이므로, 기본값인 only-syntax 모드로 시작하고 정식 출시를 기다리는 것이 좋습니다.
기존 코드는 동작이 그대로 유지되므로, 마이그레이션 부담 없이 새 코드부터 적용할 수 있습니다.

마치며​

이름 기반 구조 분해는 변수와 값을 이름으로 연결해 순서 실수를 줄여주는 기능입니다.
기본값으로 안정화되었으므로, 새 코드부터 명시적 형식으로 적용해 보는 것을 권합니다.

Kotlin 2.5.0-RC 살펴보기 — 버려지는 반환값을 잡아주는 미사용 반환값 검사

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.

배경​

불변 API를 쓸 때는 반환값을 받는 것이 연산 그 자체입니다.
원본을 바꾸는 대신 새 값을 돌려주는 함수가 많기 때문입니다.
반환값을 받지 않으면 연산은 실행되지 않은 것과 같습니다.
그런데 지금까지는 반환값을 버려도 컴파일러가 아무런 경고를 내지 않았습니다.
코드는 정상적으로 컴파일되고, 테스트도 조용히 지나갔습니다.
화면에는 아무 변화가 없어야 할 변화가 없어도, 원인을 찾기까지 시간이 걸렸습니다.
미사용 반환값 검사는 이런 실수를 컴파일 시점에 잡아주는 기능입니다.
반환값을 써야 하는 호출의 결과를 무시하면 경고를 냅니다.

미사용 반환값 검사 살펴보기​

미사용 반환값 검사는 Kotlin 2.5.0-RC에서 안정화되고 기본으로 활성화되었습니다.
검사 대상은 Unit이 아닌 값을 돌려주는 표현식입니다.
결과를 변수에 담지 않고 그냥 호출만 하면 경고가 나옵니다.
하나씩 살펴보겠습니다.

어떤 경우에 경고가 나오는지​

가장 흔한 예는 컬렉션 변환 함수를 호출만 하고 결과를 쓰지 않는 경우입니다.
다음 코드는 원본 리스트를 바꾸지 않고 새 리스트를 돌려줍니다.
결과를 받지 않으면 아무 일도 일어나지 않습니다.

fun process(postalCodes: List<String>) {
    postalCodes.map { it.uppercase() } // 경고: Unused return value of 'map'
}

이진 연산의 결과를 무시하는 경우에도 경고가 나옵니다.
계산만 하고 결과를 어디에도 쓰지 않으면, 연산 자체가 의미가 없습니다.
다만 ++나 -- 같은 증감 연산은 경고 대상이 아닙니다.
condition || return처럼 오른쪽 식이 함수를 빠져나가는 단축 평가도 경고가 나오지 않습니다.

Check 모드와 Full 모드​

검사의 동작은 컴파일러 옵션 -Xreturn-value-checker로 조절할 수 있습니다.
모드는 세 가지입니다.
disable 모드는 검사를 끕니다.
check 모드는 표시된 함수의 반환값을 검사합니다.
표준 라이브러리의 대부분 함수가 이미 표시되어 있습니다.
2.5.0-RC에서는 check 모드가 기본값입니다.
full 모드는 프로젝트 안의 모든 함수를 검사 대상으로 봅니다.

// build.gradle.kts
kotlin {
    compilerOptions {
        freeCompilerArgs.add("-Xreturn-value-checker=check")
    }
}

기본값이 check 모드이므로, 별도 설정 없이도 표준 라이브러리 호출에 대한 검사가 동작합니다.
full 모드는 검사 범위가 넓어지므로, 팀에서 기준을 정한 뒤에 적용하는 것이 좋습니다.

내 함수에 표시하기​

검사 대상은 애너테이션으로 직접 지정할 수도 있습니다.
반환값을 반드시 써야 하는 함수에는 @MustUseReturnValues를 붙입니다.
반대로 반환값을 무시해도 되는 함수에는 @IgnorableReturnValue를 붙여 경고를 막습니다.

@MustUseReturnValues
fun calculateFee(amount: Long): Long {
    return amount * 3 / 100
}

@IgnorableReturnValue
fun tryRefresh(): Boolean {
    return true
}

calculateFee의 결과를 받지 않으면 경고가 나옵니다.
tryRefresh는 결과를 무시해도 경고가 나오지 않습니다.
라이브러리를 만드는 쪽에서는 이 표시가 호출하는 쪽의 실수를 막아줍니다.

의도적인 무시는 명시하기​

반환값을 일부러 쓰지 않는 경우도 있습니다.
함수를 부작용 때문에 호출하는 경우가 그 예입니다.
이럴 때는 val _ =으로 결과를 받는다고 명시하면 경고가 나오지 않습니다.

expr.apply {
    // 부작용을 위해 호출한다는 점을 명시합니다.
    val _ = computeResult()
}

스코프 함수와 함께 쓸 때는 주의가 필요합니다.
apply는 람다 결과를 Unit으로 바꾸므로, 안에서 호출한 함수의 반환값은 경고 대상이 됩니다.
let은 반환값의 무시 가능성을 그대로 전파합니다.
그래서 let 안에서는 전체 let 식의 결과를 무시할 때만 경고가 나옵니다.

expr.let {
    it.computeResult() // 전체 let 식의 결과를 무시할 때만 경고가 나옵니다.
}

적용하기​

Kotlin 2.5.0-RC는 Version Catalog에서 Kotlin 버전을 교체하면 적용할 수 있습니다.

[versions]
kotlin = "2.5.0-RC"

[plugins]
kotlin-android = { id = "org.jetbrains.kotlin.android", version.ref = "kotlin" }

RC는 정식 출시 직전 단계이므로, 새 기능이 동결되고 안정화 작업이 중심이 됩니다.
검사 기능 자체는 안정화되었지만, RC 버전은 정식 버전이 아닙니다.
기존 프로젝트에 올릴 때는 브랜치에서 먼저 빌드해 경고가 얼마나 나오는지 확인하는 것이 안전합니다.

실무 관점​

국내 MTS 프로젝트에 적용한다면, 기존 코드에서 경고가 얼마나 나오는지 먼저 확인하는 것이 좋습니다.
규모가 큰 프로젝트에서는 경고가 한 번에 많이 나올 수 있습니다.
경고마다 실제 버그인지 먼저 확인하고, 억제 애너테이션부터 붙이지 않는 것이 좋습니다.
경고가 실제 버그였던 경우는 그 자리에서 고치는 것이 목적에 맞습니다.
새로 작성하는 코드부터 검사를 기준으로 삼으면, 경고 목록을 조금씩 줄여나갈 수 있습니다.
full 모드는 팀 기준을 정한 뒤에 적용하고, 당장은 기본값인 check 모드로 시작하는 것이 좋습니다.

마치며​

미사용 반환값 검사는 버려지는 연산 결과를 컴파일 시점에 잡아주는 기능입니다.
기본값으로 활성화되었으므로, 경고가 나오면 억제하기 전에 실제 버그인지 먼저 확인하는 것을 권합니다.

Kotlin 2.5.0-RC 표준 라이브러리 살펴보기 — if 식을 줄여주는 onTrue, onFalse, ifOrNull

November 23, 2026 · 4 min read
Way
Android Developer

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.
11월 11일에 공개된 Kotlin 2.5.0-RC의 표준 라이브러리에 새로 들어온 if 식 관련 함수에 대해 설명해드리겠습니다.

배경​

Boolean 값을 검사한 뒤 분기하는 코드는 안드로이드 개발에서 자주 등장합니다.
검사 결과가 참일 때만 로그를 남기거나, 거짓일 때만 안내 문구를 보여주는 경우가 그 예입니다.
지금까지는 이런 패턴을 쓰려면 if 식과 else 분기를 매번 직접 작성해야 했습니다.
검사 결과가 필요 없는 경우에도 분기 구조가 남았고, 코드가 길어질수록 의도가 잘 보이지 않았습니다.
Kotlin 2.5.0-RC에는 이런 반복 패턴을 줄여주는 표준 라이브러리 함수가 새로 들어왔습니다.
onTrue와 onFalse, ifOrNull이 그 주인공입니다.

새 함수 살펴보기​

세 함수는 모두 Kotlin 2.5.0-RC에서 실험 API로 제공됩니다.
사용하려면 @OptIn(ExperimentalStdlibApi::class) 애너테이션을 붙이거나, 컴파일러 옵션으로 -opt-in=kotlin.ExperimentalStdlibApi를 지정해야 합니다.
함수마다 동작이 다르므로, 하나씩 살펴보겠습니다.

onTrue​

onTrue는 Boolean 값이 true일 때만 지정한 블록을 실행합니다.
블록을 실행한 뒤에는 원래의 Boolean 값을 그대로 돌려줍니다.
반환값을 그대로 돌려주기 때문에, 호출 결과를 변수에 담거나 체이닝을 이어갈 수 있습니다.

@OptIn(ExperimentalStdlibApi::class)
fun main() {
    val tags = mutableSetOf("kotlin", "jvm")

    // add()가 true를 돌려줄 때만 메시지를 출력합니다.
    val added = tags.add("wasm").onTrue {
        println("Tag added")
    }
    println(added) // Tag added
    // true
}

Set.add처럼 성공 여부를 Boolean으로 돌려주는 API와 함께 쓰면, 결과 확인과 로그를 한 줄로 묶을 수 있습니다.

onFalse​

onFalse는 Boolean 값이 false일 때만 지정한 블록을 실행합니다.
onTrue와 마찬가지로 원래의 Boolean 값을 그대로 돌려줍니다.
실패했을 때만 처리하고 싶은 경우에 사용합니다.

@OptIn(ExperimentalStdlibApi::class)
fun main() {
    val tags = mutableSetOf("kotlin", "jvm")

    // remove()가 false를 돌려줄 때만 메시지를 출력합니다.
    val removed = tags.remove("native").onFalse {
        println("Tag not found")
    }
    println(removed)
    // Tag not found
    // false
}

onTrue와 onFalse를 함께 쓰면, 성공과 실패 분기를 각각 한 줄씩 표현할 수 있습니다.

ifOrNull​

ifOrNull은 Boolean 값이 true일 때만 블록을 실행하고 그 결과를 돌려줍니다.
Boolean 값이 false이면 블록을 실행하지 않고 null을 돌려줍니다.
onTrue와 onFalse가 Boolean에 붙는 확장 함수인 것과 달리, ifOrNull은 Boolean을 인자로 받는 함수입니다.

@OptIn(ExperimentalStdlibApi::class)
fun main() {
    val tags = mutableSetOf("kotlin", "jvm", "wasm")

    // "wasm"이 tags 안에 있을 때만 메시지를 돌려줍니다.
    val message = ifOrNull("wasm" in tags) {
        "Wasm tag is available"
    }
    println(message)
    // Wasm tag is available
}

조건이 거짓이면 null이 나오므로, 엘비스 연산자나 널 안전 호출과 자연스럽게 이어집니다.
조건에 따라 값이 있을 수도 없을 수도 있는 경우에 if 식과 else 분기를 직접 쓰지 않아도 됩니다.

적용하기​

세 함수는 Kotlin 2.5.0-RC부터 사용할 수 있습니다.
Version Catalog에서 Kotlin 버전을 교체하면 RC를 적용할 수 있습니다.

[versions]
kotlin = "2.5.0-RC"

[plugins]
kotlin-android = { id = "org.jetbrains.kotlin.android", version.ref = "kotlin" }

RC는 정식 출시 직전 단계이므로, 새 기능이 동결되고 안정화 작업이 중심이 됩니다.
실험 API라는 점도 함께 고려해야 합니다.
정식 출시 전에 API 형태가 바뀔 수 있으므로, 핵심 로직보다는 주변 코드부터 적용하는 것이 안전합니다.

실무 관점​

국내 MTS 프로젝트에 적용한다면, 반환값을 그대로 돌려준다는 점을 활용하는 것이 좋습니다.
onTrue와 onFalse는 검사 결과를 그대로 이어주기 때문에, 기존 체이닝 구조를 바꾸지 않고 끼워 넣을 수 있습니다.
다만 블록 안에 무거운 로직을 넣으면 안 됩니다.
이 함수들은 조건부 실행을 짧게 표현하는 용도이지, 분기 로직 자체를 대신하는 용도가 아닙니다.
ifOrNull은 조건에 따라 값이 없을 수 있는 경우에만 쓰고, 조건이 복잡해지면 기존 if 식이 더 읽기 쉽습니다.
실험 API이므로, 적용한 위치를 목록으로 남겨 두면 정식 출시 때 확인하기 편합니다.

마치며​

onTrue와 onFalse, ifOrNull은 짧은 분기 패턴을 한 줄로 줄여주는 함수입니다.
조건 검사와 결과 처리를 분리하지 않고 묶을 수 있어, 작은 코드가 모이는 곳에서 효과가 큽니다.

Kotlin 2.5.0-RC 살펴보기: 동반자 객체 없이 쓰는 동반자 블록과 확장

November 16, 2026 · 3 min read
Way
Android Developer

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.

11월 11일에 공개된 Kotlin 2.5.0-RC의 동반자 블록과 동반자 확장에 대해 설명해드리겠습니다.
동반자 블록과 동반자 확장은 Kotlin 2.5.0-RC의 새로운 기능에 포함된 실험적 기능입니다.

배경​

타입 이름으로 접근하는 멤버를 선언하려면 동반자 객체가 필요했습니다.
동반자 객체가 없는 타입에는 이런 멤버를 확장으로 추가할 방법이 없었습니다.
팩토리 함수나 상수를 타입 이름 아래에 두고 싶어도 동반자 객체를 먼저 만들어야 했습니다.
동반자 블록과 동반자 확장은 이 제약을 없애는 기능입니다.

동반자 블록과 확장 살펴보기​

동반자 블록​

동반자 블록은 클래스나 인터페이스 안에 companion 블록을 직접 작성하는 방식입니다.
별도의 객체 인스턴스를 만들지 않고 멤버를 선언할 수 있습니다.
JVM에서는 정적 멤버로 생성되므로 JvmStatic 애너테이션이 필요 없습니다.

data class Vector(val x: Double, val y: Double) {
    companion {
        val Zero: Vector get() = Vector(0.0, 0.0)
    }
}

fun main() {
    println(Vector.Zero) // Vector(x=0.0, y=0.0)
}

동반자 확장​

동반자 확장은 최상위 확장에 companion 변경자를 붙이는 방식입니다.
확장 대상 타입에 동반자 객체가 없어도 타입 이름으로 접근하는 멤버를 선언할 수 있습니다.
타입을 직접 제어하지 않는 경우에도 멤버를 추가할 수 있습니다.

import kotlin.math.cos
import kotlin.math.sin

companion val Vector.UnitX get() = Vector(1.0, 0.0)

companion fun Vector.unit(angle: Double) = Vector(cos(angle), sin(angle))

fun main() {
    println(Vector.UnitX) // Vector(x=1.0, y=0.0)
}

사용 설정​

실험적 기능이므로 컴파일러 옵션을 추가해야 합니다.
동반자 블록만 쓰려면 다음 옵션을 사용합니다.

kotlin {
    compilerOptions {
        freeCompilerArgs.add("-Xcompanion-blocks")
    }
}

동반자 확장까지 쓰려면 다음 옵션을 사용합니다.

kotlin {
    compilerOptions {
        freeCompilerArgs.add("-Xcompanion-blocks-and-extensions")
    }
}

동반자 확장을 사용하면 컴파일러가 정식 출시 전 바이너리를 생성합니다.
그래서 동반자 확장을 쓰는 라이브러리는 기능이 정식화되기 전까지 의존성으로 소비할 수 없습니다.
설계 배경은 동반자 블록과 확장 소개 글에서 확인할 수 있습니다.

실무 관점​

MTS에서는 화면 상태나 요청 파라미터를 타입 이름 아래의 팩토리 함수로 만드는 경우가 많습니다.
동반자 블록을 쓰면 동반자 객체 선언 없이 이런 팩토리를 정리할 수 있습니다.
다만 실험적 기능이므로 앱 모듈에서 먼저 검증하고, 라이브러리 모듈에는 적용하지 않는 것이 좋습니다.
특히 동반자 확장은 바이너리 호환성에 영향을 주므로 공유 모듈에서는 피해야 합니다.

마치며​

동반자 블록과 동반자 확장은 동반자 객체 없이 타입 이름으로 접근하는 멤버를 선언하는 방식을 제공합니다.

Kotlin 2.5.0-RC 살펴보기: 여러 프로퍼티를 갖는 전체 값 클래스

November 16, 2026 · 3 min read
Way
Android Developer

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.

11월 11일에 공개된 Kotlin 2.5.0-RC의 전체 값 클래스에 대해 설명해드리겠습니다.
전체 값 클래스는 실험적 기능으로, 여러 프로퍼티를 하나의 값으로 묶는 방식을 제공합니다.

배경​

기존 인라인 값 클래스는 하나의 프로퍼티만 가질 수 있었습니다.
여러 값을 묶어야 할 때는 일반 클래스나 데이터 클래스를 사용해야 했습니다.
데이터 클래스는 같은 데이터를 가진 인스턴스라도 참조가 다르면 별개로 구분될 수 있습니다.
값 자체가 본질인 타입에서는 이 참조 구분이 불필요한 제약이 됩니다.
전체 값 클래스는 이런 경우를 위해 프로퍼티 전체가 값이 되는 타입을 제공합니다.

전체 값 클래스 살펴보기​

기본 선언​

전체 값 클래스는 value class 키워드로 선언합니다.
프로퍼티를 여러 개 가질 수 있고, 컴파일러가 equals와 hashCode, toString을 자동으로 생성합니다.
이 점은 데이터 클래스와 비슷합니다.
다만 componentN 함수는 생성되지 않습니다.
대신 이름 기반 구조 분해를 사용합니다.
copy 함수는 제공되지 않으며, 향후 복사 변수 기능으로 대체될 예정입니다.

value class Complex(val real: Double, val imaginary: Double)

fun main() {
    val complex = Complex(1.0, 2.0)
    val (val real, val imaginary) = complex
    println(real)
    println(imaginary)
}

이름 기반 구조 분해에서는 변수 이름이 프로퍼티 이름과 일치해야 합니다.
순서가 바뀌어도 이름이 같으면 올바른 값이 들어갑니다.
이 문법은 2.5.0-RC에서 기본 동작이 되었습니다.

추상 값 클래스​

전체 값 클래스는 추상 클래스로 선언할 수도 있습니다.
인터페이스와 달리 모든 하위 클래스가 실행하는 초기화 로직을 정의할 수 있습니다.
다음 예시에서는 시작 값이 끝 값보다 크지 않은지 생성 단계에서 검증합니다.

sealed value class OrderedInterval<T : Comparable<T>> protected constructor(
    start: T,
    end: T,
) {
    init {
        require(start <= end)
    }
}

value class IntInterval(
    val start: Int,
    val end: Int
) : OrderedInterval<Int>(start, end)

값 객체​

프로퍼티가 없는 전체 값 클래스는 값 객체라고 부릅니다.
하나의 값만 가질 수 있는 상태를 표현할 때 사용합니다.
다음 예시에서는 조회 결과를 찾음과 찾지 못함으로 나눕니다.

sealed interface UserResponse

value class UserFound(val userName: String) : UserResponse
value object UserUnknown : UserResponse

사용 설정​

전체 값 클래스는 실험적 기능이므로 컴파일러 옵션을 추가해야 합니다.
build.gradle.kts에 다음과 같이 작성합니다.

kotlin {
    compilerOptions {
        freeCompilerArgs.add("-Xfull-value-classes")
    }
}

자세한 내용은 Kotlin 2.5.0-RC의 새로운 기능에서 확인할 수 있습니다.

실무 관점​

MTS에서는 금액과 통화를 함께 다루는 타입이 많습니다.
이런 복합 값을 전체 값 클래스로 표현하면 참조 구분에 의존하는 실수를 줄일 수 있습니다.
다만 아직 실험적 기능이고 RC 단계이므로, 프로덕션 모듈에 바로 적용하기보다는 별도 브랜치에서 검증하는 것이 좋습니다.
정식 출시 이후 안정화 여부를 다시 확인해야 합니다.

마치며​

전체 값 클래스는 여러 프로퍼티를 하나의 값으로 묶는 방식을 제공합니다.
데이터 클래스와 비슷하지만 참조 구분이 없는 점이 다릅니다.

Kotlin 2.5.0-RC 살펴보기: 이름 기반 구조 분해와 정식 출시 전 점검 사항

November 12, 2026 · 3 min read
Way
Android Developer

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.

11월 11일에 공개된 Kotlin 2.5.0-RC에 대해 설명해드리겠습니다.

배경​

Kotlin 2.5.0은 12월 정식 출시를 앞두고 있습니다.
10월 21일에 나온 Beta2에 이어 11월 11일에 RC가 공개되었습니다.
RC는 정식 출시 직전 단계로, 새 기능이 동결되고 안정화 작업이 중심이 됩니다.
이번 RC에서 가장 주목할 변화는 이름 기반 구조 분해의 안정화입니다.

Kotlin 2.5.0-RC 살펴보기​

이름 기반 구조 분해​

기존 구조 분해는 위치 기반으로 동작했습니다.
데이터 클래스의 프로퍼티 순서가 바뀌면 변수에 들어가는 값이 함께 바뀌었습니다.
이름 기반 구조 분해에서는 변수 이름이 프로퍼티 이름과 일치해야 합니다.
순서가 바뀌어도 이름이 같으면 올바른 값이 들어갑니다.

data class Person(val name: String, val age: Int)

val person = Person("way", 33)
val (name, age) = person
val (age, name) = person // 순서가 달라도 이름으로 매칭됩니다

2.5.0에서는 새 문법을 추가 설정 없이 사용할 수 있습니다.
컴파일러는 기존 위치 기반 코드에 대해 마이그레이션 힌트도 함께 제공합니다.
위치 기반이 꼭 필요한 경우에는 대괄호 문법을 사용합니다.

val pair = "way" to 33
val [first, second] = pair

미사용 반환값 검사​

반환값을 무시한 호출을 찾아주는 검사가 추가되었습니다.
실수로 결과를 확인하지 않은 호출을 컴파일 단계에서 발견할 수 있습니다.
Json.encodeToString 같은 호출의 결과를 쓰지 않고 넘기는 경우에 경고를 받을 수 있습니다.

JDK 17 요구 사항​

Beta2부터 JDK 17보다 낮은 버전으로 컴파일러를 실행하면 오류가 발생합니다.
Android Studio는 이미 JDK 17을 내장하고 있어 대부분은 영향이 없습니다.
CI 환경에서 별도 JDK를 지정하고 있다면 버전을 확인해야 합니다.

그 외 변경 사항​

Java 28을 지원합니다.
Swift Export가 새로운 DSL과 함께 베타 단계에 들어갔습니다.
Kotlin/Native 증분 컴파일이 Apple 타겟에서 기본으로 활성화되었습니다.
멀티 필드 값 클래스가 알파 단계로 추가되었습니다.
Lombok의 @Builder 애너테이션은 Kotlin 코드에서 비활성화되었습니다.
Android 프로젝트의 kotlin 블록 안에서 sourceSets를 쓰는 기존 방식이 deprecation 대상으로 지정되었습니다.

RC 적용하기​

Version Catalog에서 Kotlin 버전을 교체하면 RC를 적용할 수 있습니다.

[versions]
kotlin = "2.5.0-RC"

[plugins]
kotlin-android = { id = "org.jetbrains.kotlin.android", version.ref = "kotlin" }

실무 관점​

RC는 프로덕션 적용 대상이 아닙니다.
별도 브랜치에서 빌드와 테스트를 먼저 확인하는 것이 좋습니다.
JDK 버전과 KAPT 사용 여부를 함께 점검해야 합니다.
KAPT를 사용하는 프로젝트라면 릴리스 노트에 정리된 변경 사항을 함께 확인하는 것이 좋습니다.
정식 출시는 12월로 예정되어 있습니다.

마치며​

Kotlin 2.5.0-RC는 이름 기반 구조 분해를 안정화하고, 정식 출시를 위한 마지막 점검 단계에 들어갔습니다.
12월 정식 출시 전에 미리 적용해 보고, JDK 17 요구 사항과 마이그레이션 힌트를 확인해 두는 것이 좋습니다.

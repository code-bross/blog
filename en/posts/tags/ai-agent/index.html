AppFunctions 1.0.0-rc01 살펴보기 — 앱 기능을 AI 에이전트에 연결하기

November 7, 2026 · 2 min read
Way
Android Developer

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.
2026년 11월 4일에 공개된 AppFunctions 1.0.0-rc01에 대해 설명해드리겠습니다.

배경​

AppFunctions는 앱의 기능을 AI 에이전트가 호출할 수 있게 노출하는 Jetpack 라이브러리입니다.
Android Dev Summit 2026에서 베타로 발표됐고, 11월 4일 RC 단계에 들어갔습니다.
RC는 API 표면이 확정된 예비 stable 릴리스입니다.
에이전트는 기능을 직접 실행하는 대신, 앱이 선언한 설명을 보고 호출합니다.

AppFunctions 1.0.0-rc01 살펴보기​

의존성을 추가합니다​

dependencies {
    implementation("androidx.appfunctions:appfunctions:1.0.0-rc01")
    ksp("androidx.appfunctions:appfunctions-compiler:1.0.0-rc01")
}

테스트용 아티팩트도 같은 버전으로 제공됩니다.
Android 16(API 36) 이상에서 동작하며, compileSdk 36이 필요합니다.

기능을 선언합니다​

@AppFunctionServiceEntryPoint
class MarketFunctions {

    /**
     * 보유 종목의 현재가를 조회합니다.
     *
     * @param symbol 종목 코드입니다.
     * @return 현재가 정보입니다.
     */
    @AppFunctionDeclaration(isDescribedByKDoc = true)
    suspend fun getStockPrice(symbol: String): StockPrice {
        return withContext(Dispatchers.IO) {
            stockRepository.getPrice(symbol)
        }
    }
}

선언은 @AppFunctionServiceEntryPoint가 붙은 서비스 클래스 안에 둡니다.
@AppFunctionDeclaration이 붙은 함수는 외부 앱이 호출할 수 있습니다.
KSP 컴파일러가 함수 설명을 XML로 만들어 assets에 넣고, 시스템이 이를 색인합니다.
isDescribedByKDoc은 KDoc을 에이전트용 설명으로 쓸지 정합니다.
beta01부터 기본값이 없어 반드시 지정해야 합니다.

기본적으로 메인 스레드에서 실행됩니다​

선언한 함수는 기본적으로 메인 스레드에서 실행됩니다.
네트워크나 파일 작업이 있으면 suspend 함수로 만들고 디스패처를 바꿉니다.
호출자는 EXECUTE_APP_FUNCTIONS 권한이 필요합니다.
사용자 정의 타입을 주고받을 때는 직렬화 규칙을 따라야 합니다.

RC01 변경점​

버전이 RC로 올라갔고, 기존 집계 컴파일러 옵션이 제거됐습니다.
Java 라이브러리 desugaring을 켠 앱에서 java.time 파라미터 역직렬화가 실패하던 문제가 수정됐습니다.
테스트는 Android 17 기기나 에뮬레이터에서 adb shell cmd app_function 명령으로 할 수 있습니다.

실무 관점​

노출하는 기능은 읽기 전용 조회부터 시작하는 것이 안전합니다.
주문처럼 돈이 움직이는 기능은 에이전트에 노출하지 않습니다.
프로덕션 배포는 Connected Apps Platform 프리뷰 등록이 별도로 필요합니다.
설명 문구는 에이전트가 기능을 선택하는 기준이 되므로, KDoc을 정확히 씁니다.

마치며​

AppFunctions가 RC에 들어서면서 에이전트 연동 준비가 한결 가까워졌습니다.
조회 기능부터 작은 범위로 적용해보고, 안정 버전에서 범위를 넓히겠습니다.

터미널에서 에이전트와 함께 개발하기 Android CLI 공식 플러그인

November 2, 2026 · 4 min read
Way
Android Developer

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.
최근 Android Dev Summit 2026에서 공개된 Android CLI 공식 에이전트 플러그인에 대해 설명해드리겠습니다.

배경​

최근 Android 개발 환경에서는 AI 코딩 에이전트의 역할이 빠르게 커지고 있습니다.
Android Studio Rabbit 2에서는 IDE 안에서 원하는 에이전트를 고르는 Bring Your Own Agent가 안정화되었습니다.
그런데 모든 개발자가 IDE 안에서만 에이전트를 쓰는 것은 아닙니다.
터미널에서 작업하는 에이전트, CI 파이프라인에서 동작하는 자동화 흐름도 함께 고려해야 합니다.
이번에 공개된 Android CLI 공식 에이전트 플러그인은 바로 이 지점을 겨냥합니다.
터미널에 상주하는 에이전트에게 Android 개발 도구를 직접 쥐여주는 방식입니다.

Android CLI 공식 플러그인 살펴보기​

플러그인은 Claude Code, OpenAI Codex, Google Antigravity에 공식으로 제공됩니다.
플러그인을 설치하면 에이전트에게 android-cli 스킬이 추가됩니다.
이 스킬을 통해 에이전트는 프로젝트 생성, 가상 기기 관리, 실시간 UI 레이아웃 검사, Journeys 실행, 공식 Android Knowledge Base 검색을 수행합니다.

설치하기​

각 에이전트마다 설치 명령이 조금씩 다릅니다.
Claude Code에서는 마켓플레이스를 추가한 뒤 플러그인을 설치합니다.

claude plugin marketplace add android/android-cli-plugin
claude plugin install android-cli@android-cli-plugin

Codex에서는 두 번째 명령의 동사가 add라는 점이 다릅니다.

codex plugin marketplace add android/android-cli-plugin
codex plugin add android-cli@android-cli-plugin

Antigravity에서는 전용 마켓플레이스 경로로 설치합니다.

agy plugin install android-cli-plugin@antigravity-plugins-official

설치가 끝나면 에이전트 세션 안에서 Android CLI를 바로 사용할 수 있습니다.
먼저 android init으로 에이전트 설정을 마치고, android skills list로 제공되는 스킬 목록을 확인하는 흐름이 안내됩니다.

Compose 프리뷰와 기기 스트리밍​

터미널 기반 에이전트의 약점은 화면을 직접 보지 못한다는 점이었습니다.
Android CLI는 이 약점을 두 가지 기능으로 보완합니다.
첫 번째는 Compose 프리뷰 렌더링입니다.
에뮬레이터를 띄우거나 APK를 설치하지 않고도 프리뷰를 렌더링해 UI 변경을 즉시 시각적으로 검증합니다.
두 번째는 Android Device Streaming입니다.
Firebase 기반으로 원격 실기기를 연결해 기기별 이슈를 직접 확인합니다.
구글은 내부 테스트 기준으로 android preview를 활용한 에이전트가 UI 작업을 더 빠르게 마쳤다고 밝혔습니다.
이 수치는 구글 자체 테스트 결과이므로, 참고용 지표로 받아들이는 편이 좋습니다.

프로파일링과 분석​

Android CLI에는 성능 분석 도구도 함께 들어 있습니다.
Perfetto 기반 시스템 트레이스를 수집해 콜드 스타트 지연, UI 끊김, 백그라운드 깨어남을 살펴봅니다.
메모리 누수 탐지에는 오픈소스 LeakCanary가 내장되어 있습니다.
analyze 기능은 앱 번들과 라이브러리를 검사해 난독화, 최적화, 축소 점수를 확인합니다.
Google Play에 업로드하기 전에 스토어와 같은 기준으로 품질 신호를 미리 점검하는 용도입니다.

30개 이상의 Android 스킬​

플러그인과 함께 제공되는 Android 스킬은 30개 이상이며, 20개 이상의 영역을 다룹니다.
권한 보안, Glance 위젯 레이아웃, Compose 성능 최적화 같은 주제가 포함됩니다.
에이전트가 범용 지식만으로 추측하지 않고, Android 공식 가이드에 근거해 작업하도록 돕는 장치입니다.
필요한 스킬만 골라 추가하는 방식이라, 프로젝트 성격에 맞게 범위를 조절할 수 있습니다.

실무 관점​

MTS처럼 보안과 정확성이 중요한 프로젝트에서 에이전트 도구를 쓸 때는 범위를 좁게 잡는 편이 좋습니다.
에이전트에게는 프리뷰 렌더링, 레이아웃 검사, 트레이스 수집 같은 확인 작업부터 맡기고, 실제 반영은 사람이 검토하는 구조가 안전합니다.
실기기 검증은 원격 스트리밍으로 1차 확인하고, 최종 검증은 내부 테스트 트랙과 실기기에서 마치는 편이 좋습니다.
에이전트가 생성한 코드는 빌드와 테스트를 통과했는지, 기존 아키텍처와 어긋나지 않는지 별도로 확인해야 합니다.

마치며​

Android CLI 공식 플러그인은 에이전트의 작업 공간을 IDE 밖으로 넓혔습니다.
터미널과 CI에서도 프리뷰, 기기, 프로파일링 도구를 같은 방식으로 쓸 수 있게 되었습니다.

AI 에이전트가 만드는 네이티브 UI: Jetpack Compose A2UI 렌더러 살펴보기

October 25, 2026 · 3 min read
Way
Android Developer

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.
2026년 10월 21일 공개된 A2UI 1.0.0-alpha02에 대해 설명해드리겠습니다.

배경​

AI 에이전트는 이제 작업을 추론하고 도구를 호출하고 대화를 이어갈 수 있습니다.
그런데도 에이전트가 사용자에게 네이티브 화면을 보여주는 일은 여전히 어렵습니다.
에이전트는 앱이 어떤 컴포넌트를 가지고 있는지 모르기 때문에, 날짜 선택기나 확인 버튼 같은 실제 UI를 건네줄 수 없습니다.
A2UI는 이 간극을 메우기 위한 프로토콜입니다.

A2UI 살펴보기​

A2UI의 핵심 아이디어는 단순합니다.
에이전트가 임의의 UI 코드를 만들어내는 대신, 클라이언트가 미리 정해둔 카탈로그 안에서만 UI를 조합합니다.

카탈로그가 계약이 됩니다​

모든 A2UI 인터페이스는 컴포넌트 카탈로그를 중심으로 동작합니다.
카탈로그는 에이전트가 사용할 수 있는 UI 요소와 속성, 함수를 선언합니다.
에이전트는 카탈로그에 등록되지 않은 컴포넌트를 만들어낼 수 없으므로, 렌더링 결과가 예측 가능한 범위를 벗어나지 않습니다.

임의 코드 실행이 없습니다​

A2UI 렌더러의 가장 중요한 성질은 임의 코드를 실행하지 않는다는 점입니다.
에이전트는 구조화된 데이터를 보내고, 클라이언트는 그 데이터를 네이티브 Compose 컴포넌트로 렌더링합니다.
서버에서 온 설명이 앱 안에서 코드로 실행되는 일이 없으므로, 신뢰 경계를 넘는 UI도 안전하게 다룰 수 있습니다.

Jetpack A2UI 렌더러의 구조​

Jetpack의 A2UI 렌더러는 디자인 시스템과 무관한 렌더링 엔진과 구체적인 카탈로그 구현을 분리합니다.
데이터 계층인 a2ui-model과 a2ui-engine이 프로토콜 메시지를 파싱하고 처리합니다.
UI 계층인 compose-runtime과 compose-ui가 앱과 카탈로그를 위한 API를 제공합니다.
Material 3 컴포넌트로 구성된 기본 카탈로그도 함께 제공되어, 별도 카탈로그 없이 바로 시작할 수 있습니다.

dependencies {
    implementation("androidx.a2ui:a2ui-engine:1.0.0-alpha02")
    implementation("androidx.a2ui:a2ui-model:1.0.0-alpha02")
    implementation("androidx.a2ui.compose:compose-runtime:1.0.0-alpha02")
    implementation("androidx.a2ui.compose:compose-ui:1.0.0-alpha02")
}

alpha02에서 바뀐 점​

이번 alpha02에서는 기본 카탈로그의 함수 목록이 인터페이스로 바뀌었습니다.
구현체는 openUrl만 구현하면 되고, 나머지 함수는 기본 구현을 쓰거나 개별적으로 재정의할 수 있습니다.
클라이언트가 렌더링할 수 있는 카탈로그를 먼저 알리는 기능도 추가되어, 에이전트와 렌더러 사이의 capability 협상이 가능해졌습니다.

val catalog = materialA2uiBasicCatalogV1(
    functions = A2uiBasicCatalogV1.Functions(context)
)

실무 관점​

아직 알파 단계이므로, 프로덕션 화면에 바로 적용할 라이브러리는 아닙니다.
다만 MTS의 챗봇이나 상담 흐름처럼, 에이전트가 화면을 제시해야 하는 기능에는 참고할 만한 설계입니다.
카탈로그를 계약으로 삼는 방식은, 에이전트 출력이 화면을 망가뜨리는 위험을 구조적으로 줄여줍니다.
도입을 검토한다면, 렌더링할 컴포넌트 목록을 카탈로그로 먼저 정리하는 것부터 시작하는 편이 좋습니다.

마치며​

A2UI는 에이전트에게 화면을 맡기되, 그릴 수 있는 범위는 앱이 먼저 정한다는 발상입니다.
알파 단계이지만, AI와 네이티브 UI가 만나는 지점을 어떻게 설계해야 하는지 보여주는 좋은 출발점입니다.

챗봇을 넘어서 — Google ADK for Kotlin 1.0으로 앱에 AI 에이전트 붙이기

October 18, 2026 · 5 min read
Way
Android Developer

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.
최근 1.0이 공개된 Google의 Agent Development Kit(ADK) for Kotlin에 대해 설명해드리겠습니다.

배경​

앱에 AI를 넣는다는 것은 그동안 프롬프트를 보내고 텍스트를 받아 화면에 보여주는 것과 같은 의미였습니다.
챗봇은 그렇게 만들 수 있지만, 모델이 직접 앱의 데이터를 조회하고 API를 호출하는 것은 다른 차원의 일입니다.
민감한 작업을 실행하기 전에 사용자에게 확인까지 받는 구조가 필요하기 때문입니다.
ADK for Kotlin은 2026년 9월에 1.0이 공개되었고, 공식 블로그 발표는 9월 9일에 올라왔습니다.
이 글에서는 공식 발표와 10월 14일 Medium에 올라온 Sagar Singh의 튜토리얼을 함께 정리합니다.

ADK for Kotlin 살펴보기​

에이전트와 도구​

에이전트는 도구를 사용할 수 있는 모델을 말합니다.
ADK는 모델이 어떤 도구를 언제 호출할지 스스로 결정하는 루프를 프레임워크가 대신 실행해 주는 오픈소스 도구킷입니다.
개발자는 도구와 설명만 작성하면 됩니다. 도구는 그냥 코틀린 함수입니다.
도구에는 @Tool 어노테이션을 붙이고, KSP가 빌드 타임에 도구 설명을 생성합니다.
런타임 리플렉션이 없기 때문에 폰에서 시작 속도가 빠릅니다.
실행 결과는 코루틴 Flow로 돌아오므로 ViewModel에 자연스럽게 연결됩니다.

다섯 가지 구성 요소​

  • LlmAgent: 이름, 모델, 지시문, 도구 목록을 정의하는 에이전트입니다.
  • Model: 두뇌 역할을 하며, Firebase AI의 Gemini나 온디바이스 모델을 사용합니다.
  • Tools: @Tool 어노테이션을 붙인 함수들입니다.
  • Runner: 루프를 실행하고 이벤트 Flow를 반환합니다.
  • Session: 대화를 기억합니다.

1.0에서 달라진 점​

0.1.0은 I/O 2026에서 공개된 실험적인 버전이었습니다.
1.0은 ADK 1.0 Core(Python/Java)와 기능 동등성(feature parity)을 달성했고, 프로덕션용 도구킷을 표방합니다.
코어는 Kotlin Multiplatform으로 구성되어 백엔드 코틀린에서도 사용할 수 있고, 안드로이드 모듈은 별도 아티팩트로 붙습니다.
안드로이드 전용 확장으로 온디바이스(LiteRT-LM, ML Kit 베타), 하이브리드(Firebase AI Logic), 프로세스가 종료되어도 이어지는 세션(Room), 시맨틱 메모리(AppSearch)가 포함됩니다.

모델 백엔드 선택​

모델 백엔드는 한 줄로 교체할 수 있고, 종류는 다음과 같습니다.

백엔드아티팩트위치도구 호출
Firebase AI (Gemini)google-adk-kotlin-firebase-android클라우드가능
LiteRT-LM (예: Gemma)google-adk-kotlin-litertlm온디바이스가능
ML Kit (Gemini Nano)google-adk-kotlin-mlkit-android (베타)온디바이스아직 불가

적용 예시​

주문 상태를 물어보면 직접 조회해서 답하는 지원 에이전트를 한투 앱 문맥으로 옮기면 뼈대는 다음과 같습니다.

// 1. 도구는 그냥 suspend 함수 + 어노테이션. Retrofit/Room 호출이 자연스럽다.
class OrderTools(private val repo: OrderRepository) {
    @Tool(description = "고객 주문의 현재 배송 상태를 반환한다.")
    suspend fun getOrderStatus(
        @Param("주문번호, 예: ORD-1042") orderId: String,
    ): Map<String, String> {
        val o = repo.getOrder(orderId) // 실제 레포지토리 호출
        return mapOf("orderId" to o.id, "status" to o.status, "eta" to o.eta)
    }
}

// 2. ViewModel은 Runner의 Flow만 collect한다.
//    "언제 도구를 호출할지"를 결정하는 if문은 내가 쓰지 않는다.
fun send(message: String) {
    viewModelScope.launch {
        runner.runAsync(
            userId = "local-user",
            sessionId = sessionId, // 같은 세션을 재사용하면 이전 대화를 기억한다
            newMessage = Content.fromText(Role.USER, message),
        ).catch { e -> _reply.value = "오류: ${e.message}" }
         .collect { event ->
            event.content?.parts?.firstOrNull()?.text
                ?.takeIf { it.isNotBlank() }
                ?.let { _reply.value = it }
        }
    }
}

빌드 한 번 돌리면 KSP가 OrderTools().generatedTools() 확장 함수를 만들어줍니다.
빨간 줄이 보이면 빌드를 한 번 돌리라는 것이 원문 튜토리얼의 팁입니다.

실무에서 주의할 점​

  • 세션은 기본이 인메모리입니다. InMemoryRunner의 대화는 프로세스가 종료되면 사라집니다. 재시작 후에도 대화를 이어가려면 Room 기반 RoomSessionService를 러너에 넘겨야 합니다. 금융 앱의 상담 흐름에서는 필수 요건입니다.
  • 민감한 작업은 확인을 강제할 수 있습니다. @Tool(requireConfirmation = true)로 선언하면 에이전트가 함수를 실행하기 전에 멈춰서 사용자의 승인을 기다립니다. 주문 취소나 이체 같은 작업의 안전장치가 프레임워크에 내장되어 있습니다.
  • Gemini Nano는 아직 도구 호출을 지원하지 않습니다. ML Kit 백엔드는 함수 호출 파트를 제외하므로, 도구를 사용하는 에이전트라면 첫 선택은 Firebase AI가 됩니다.
  • GenAI SDK의 Gemini 모델 클래스는 안드로이드 앱용이 아닙니다. README에서 안드로이드에서의 API 키와 크리덴셜 사용을 차단하고 Firebase AI를 권장합니다. 비밀 키는 APK에 넣으면 안 되므로, 이는 제약이 아니라 올바른 방향입니다.
  • 튜토리얼의 버전을 확인해야 합니다. 0.1.0(5월)에서 1.0.0(9월)으로 네 달 만에 올라오면서 의존성 이름과 셋업 단계가 바뀌었습니다. 오래된 글을 보고 1.0.0 아티팩트(com.google.adk:google-adk-kotlin-core:1.0.0 등)와 섞어 쓰면 빌드가 깨집니다. 공식 Android 가이드의 요구사항은 compileSdk 34 이상, minSdk 24 이상입니다.
  • 도구 설명이 곧 스펙입니다. 모델은 @Tool과 @Param의 description을 읽고 호출 여부를 결정합니다. 모호한 설명은 모호한 호출을 만듭니다. 지시문(instruction)도 마찬가지입니다.

마치며​

ADK for Kotlin 1.0을 적용하면, 도구를 사용하는 AI 에이전트를 코틀린 코드 안에서 구성할 수 있습니다.
세션 저장 방식과 확인 절차만 먼저 정해 두면, 금융 앱의 상담 흐름에도 단계적으로 도입할 수 있습니다.

구글북 리눅스 터미널 프리뷰 — AI 에이전트에게 sudo를 줘도 되는 VM 샌드박스

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.
2026년 10월 12일 Android Developers Blog에 공개된 구글북 리눅스 터미널 프리뷰에 대해 설명해드리겠습니다.

배경​

구글북(Googlebook)은 Android와 Chrome OS를 합친 새 노트북 카테고리입니다.
이번에 공개된 내용은 구글북에 Debian 기반 리눅스 터미널이 프리뷰로 들어온다는 소식입니다.
핵심은 AI 에이전트에게 sudo를 줘도 시스템이 망가지지 않는 구조입니다.
자세한 내용은 Android Developers Blog 원문에서 확인할 수 있습니다.

구글북 리눅스 터미널 살펴보기​

VM 기반 격리 구조​

  • 모든 터미널 명령은 격리된 Linux VM 안에서만 실행됩니다.
  • Antigravity 같은 AI 에이전트에 sudo 권한을 줘도 호스트 OS나 개인 파일이 오염되지 않습니다.
  • VM에 공개하는 디렉터리는 사용자가 명시적으로 허용한 것만 마운트됩니다.
  • 구글북 OS는 defense-in-depth 원칙으로 설계되었고, VM 경계가 호스트 OS와 마운트되지 않은 파일을 보호합니다.

파일 유지와 원클릭 리셋​

  • 원클릭 VM 리셋으로 실험 환경을 초기화할 수 있습니다.
  • VM을 초기화해도 파일은 호스트 파일 시스템에 그대로 유지됩니다.
  • 리눅스 파일은 구글북 파일 앱에서도 보입니다.
  • 에이전트에게 과감하게 권한을 주고, 망가지면 리셋하면 되는 구조입니다.

개발자에게 익숙한 Debian 환경​

  • apt, git, ssh, 컴파일러·런타임 같은 익숙한 워크플로우가 그대로 들어옵니다.
  • Node.js, Python, Ruby, Go, Rust 같은 모던 런타임을 지원합니다.
  • localhost 포트 자동 포워딩으로 호스트 브라우저에서 바로 확인할 수 있습니다.
  • VM에 할당하는 메모리는 워크로드에 맞게 조절할 수 있습니다.
  • 구글 엔지니어들도 구글북으로 리눅스 커널을 빌드하고 플랫폼 엔지니어링에 터미널을 사용하고 있다고 합니다.

로드맵​

  • Linux GUI 앱 지원이 예정되어 있습니다. 터미널을 넘어 GUI 앱까지 품으면 Android Studio 같은 도구를 VM에 올리는 시나리오도 열립니다.
  • USB 패스스루와 ADB over USB가 지원될 예정입니다. 현재는 네트워크 패스스루와 무선 ADB가 있고, USB 패스스루가 오면 Linux VM과 Antigravity에서 직접 로컬 기기 디버깅이 가능해집니다.
  • GPU/NPU 하드웨어 가속이 예정되어 있습니다. 40 TOPS급 NPU를 단 구글북 스펙과 맞물리는 부분입니다.
  • VM 메모리·스토리지 동적 스케일링과 VM 지속성, 터미널 창 분리가 포함되어 있습니다. 장시간 도는 에이전트 작업을 위한 전제 조건입니다.

실무에서 주의할 점​

아직 프리뷰 단계이므로 당장 개발 머신으로 사용하기는 이릅니다.
GUI 앱 지원과 USB ADB는 로드맵에 있는 항목입니다.
다만 보안 모델은 주목할 만합니다.
sudo를 줘도 되는 VM 샌드박스와 디렉터리별 명시적 마운트 허가, 원클릭 리셋은 사내에서 AI 코딩 에이전트 도입을 검토할 때 레퍼런스 아키텍처로 쓸 수 있습니다.
Antigravity가 구글북용으로 따로 나온다는 점과 결합하면, 구글은 노트북을 에이전트와 함께 일하는 머신으로 그리고 있습니다.
10월 2일 공개된 Device Streaming and Android skills 흐름과 같은 방향입니다.
또한 9월 22일에 올라온 "Land your apps on Googlebook with adaptive development" 글과 함께 보면, 구글북은 Android 앱의 새 타깃 폼팩터이기도 합니다.
아직 구글북 실물이 없어 코드 실험은 못 하지만, 지금 당장 할 수 있는 정리는 다음과 같습니다.

# 1) 프로젝트에 에이전트용 가이드가 있는지 점검 (Android CLI skills 흐름과 연결)
ls .agent/ AGENTS.md CLAUDE.md 2>/dev/null

# 2) 무선 ADB로 에이전트가 기기를 만질 수 있는지 확인

adb shell settings get global adb_wifi_enabled

마치며​

구글북 리눅스 터미널은 에이전트에게 권한을 과감하게 줄 수 있는 개발 환경의 방향을 보여줍니다.
실물이 들어오면 터미널에서 빌드와 디버깅을 직접 확인하고, VM 리셋까지 실측해 다시 정리하겠습니다.

Android CLI에 실기기 스트리밍이 붙었다 — 에이전트가 원격 단말에서 직접 확인하는 흐름

October 9, 2026 · 5 min read
Way
Android Developer

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.
2026년 10월 2일 공개된 Android CLI 업데이트에 대해 설명해드리겠습니다.

배경​

Android CLI는 특정 AI 모델에 묶이지 않고, 다양한 코딩 에이전트와 함께 프로젝트 생성, 빌드, 테스트, 에뮬레이터 실행을 돕는 커맨드라인 도구입니다.
실기기에서만 재현되는 하드웨어/OS 이슈는 에뮬레이터로 놓치기 쉽지만, 필요한 단말이 항상 책상 위에 있는 것도 아닙니다.
이번 업데이트의 핵심은 두 가지입니다.
원격 실기기에 붙는 Device Streaming을 CLI에서 쓸 수 있게 됐고, 에이전트용 Android skills가 20개를 넘어섰습니다.
자세한 내용은 Android Developers Blog 원문에서 확인할 수 있습니다.

무엇이 달라졌는지​

Device Streaming을 에이전트가 직접 쓴다​

CLI를 통해 Android Device Streaming에 접속하면, 손에 없는 실기기라도 원격으로 앱을 올리고 로그와 트레이스를 수집하고 스크린샷까지 찍을 수 있습니다.
에이전트가 보안이 적용된 ADB over SSL 연결을 통해 원격 단말을 마치 USB로 연결한 것처럼 다룰 수 있게 됐습니다.
가능한 작업은 대략 다음과 같습니다.

  • 원격 단말 깨우기, 빌드 배포
  • 로그/트레이스 수집
  • 헤드리스 스크린샷 캡처
  • 터미널 안에서 기기 목록을 보고 어떤 단말을 쓸지 선택

코드를 고쳤으니 실제 단말에서 눌러보고 결과를 가져오는 흐름을, 사람이 중간에 끼지 않고도 시도할 수 있는 기반이 생긴 것입니다.

Android skills가 실무형으로 늘어났다​

Android skills는 SKILL.md 형태의 구조화된 지침 모음입니다.
모델의 학습 시점에 기대지 않고, 공식 가이드 기준으로 에이전트에게 맥락을 주입하는 방식입니다.
공식 skills 저장소에는 이제 20개가 넘는 스킬이 있고, 성격도 꽤 실무적입니다.

  • 제출 전 Play 정책 준수 점검(매니페스트, 권한, 타깃 SDK, 개인정보 고지)
  • Credential Manager 기반 복원 로그인(Restore Credentials) 구현
  • 암시적 인텐트 탈취 같은 인텐트 보안 점검
  • 프로파일러로 프레임 드롭 원인을 찾고 PerfettoSQL로 트레이스 질의
  • 구형 Camera1/Camera2 코드를 CameraX로 이전
  • Leanback 기반 TV 화면을 Compose for TV로 전환
  • Media3 재생 상태와 Cast 수신기 동기화
  • 테스트 전략(단위 테스트, Compose UI 테스트, 스크린샷 테스트) 세팅
  • R8 설정 감사

이번 글에서는 Wear OS용 Compose Material 3 스킬이 스포트라이트로 소개됐습니다.
둥근 화면, 회전 입력, 저전력, TransformingLazyColumn, AppScaffold/ScreenScaffold 같은 Wear 특유의 패턴을 에이전트가 놓치지 않게 잡아주는 스킬입니다.
FotMob 팀이 기존 Wear 앱의 리스트 여러 개를 이 패턴으로 옮기면서 레거시 래퍼와 회전/포커스 보일러플레이트를 걷어냈다는 사례도 함께 실렸습니다.

스킬 관리가 CLI에 붙었다​

스킬은 프로젝트마다, 또 에이전트마다 디렉터리가 달라서 관리가 번거로울 수 있는데, 흐름은 비교적 단순하게 정리돼 있습니다.

# 공식 스킬 목록 확인
android skills list

# 필요한 스킬만 프로젝트에 추가 (예: Wear Compose M3)
android skills add wear-compose-m3 --project=.

# 나중에 일괄 업데이트
android skills update --all

이 스킬들은 특정 환경 전용이 아니라는 점이 중요합니다.
Android Studio, 다른 코드 에디터, 서드파티 에이전트 환경에서도 같은 스킬을 재사용하는 방향으로 설계됐다고 합니다.

실무에서 주의할 점​

금융 앱처럼 단말 파편화와 보안 정책이 중요한 환경에서는, 에이전트가 실기기 결과를 직접 확인하는 흐름이 매력적입니다.
다만 바로 운영 파이프라인에 넣기 전에 확인할 것도 있습니다.

  • 권한과 보안 연결: 원격 단말 접속은 ADB over SSL 기반이라지만, 사내 네트워크 정책과 단말 접근 통제 범위 안에서 써야 합니다. 어떤 프로젝트를 링크하고, 어떤 로그가 외부로 나가는지 먼저 정리가 필요합니다.
  • 스킬은 정답지가 아니라 맥락입니다: 스킬이 있어도 최종 판단은 코드 리뷰와 테스트가 해야 합니다. 특히 Play 정책, 권한, 인텐트 보안처럼 심사/보안과 닿은 영역은 스킬 결과를 그대로 믿지 말고 체크리스트로 한 번 더 확인하는 것이 좋습니다.
  • 비용이 드는 반복 실행 주의: 단말 확인을 에이전트 루프에 넣으면, 사람이 할 때보다 훨씬 자주 실행하게 됩니다. 테스트 단말 시간, 네트워크, CI 분(minute)을 먹는 구조인지 먼저 작은 작업으로 측정해 보시기 바랍니다.

장점도 분명합니다.
지금까지는 에이전트가 코드만 보고 추측했다면, 이제는 실행 결과(로그, 스크린샷, 트레이스)를 근거로 다음 패치를 제안하는 루프를 만들 수 있습니다.
UI 회귀나 단말별 렌더링 차이를 잡는 데 특히 도움이 될 만합니다.
거창하게 시작하기보다 스킬 한 개와 단말 한 대로 작은 실험부터 해 보는 것이 좋습니다.

# 1) 지금 프로젝트에 테스트 전략 스킬을 붙여 현재 테스트 구성을 점검
android skills add testing-strategy --project=.

# 2) 에이전트에게 요청하는 프롬프트 예시
# "이 모듈의 Compose UI 테스트가 비어 있는 화면을 찾아서,
#  Device Streaming 단말에서 스크린샷까지 확인한 뒤 결과를 보고해줘"

스크린샷 테스트가 약한 화면부터 에이전트에게 맡겨보면, 사람이 놓친 레이아웃 깨짐을 얼마나 잡아내는지, 반대로 오탐이 얼마나 나오는지 금방 감이 옵니다.
그 다음에 R8 감사나 CameraX 이전처럼 범위가 넓은 스킬로 확장해도 늦지 않습니다.

마치며​

이번 업데이트의 방향은 에이전트가 코드를 더 잘 쓰는 것에서, 에이전트가 실행 결과까지 확인하며 일하는 것으로 한 발 나간 것입니다.
CLI와 skills를 한 번쯤 직접 만져보면서, 내 프로젝트에서 자동으로 확인할 수 있는 일이 무엇인지 목록을 만들어보는 것만으로도 가치가 있을 것입니다.

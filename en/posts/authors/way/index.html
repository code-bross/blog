KMP 플러그인의 Swift IDE 지원 종료 — 2026.3부터 Swift 작업은 Xcode로 나눠야 한다

October 10, 2026 · 4 min read
Way
Android Developer

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.
2026년 10월 5일, JetBrains가 Kotlin Multiplatform(KMP) 플러그인에서 제공하던 Swift 언어 IDE 기능을 앞으로 중단한다고 알렸습니다. 적용 시점은 IntelliJ IDEA 2026.3과 Android Studio Rabbit 2 | 2026.2.2부터입니다.

핵심 요약​

  • 없어지는 것은 Swift 파일을 같은 IDE 안에서 편집하고, 문법 강조를 받고, Swift와 Kotlin 사이를 오가며 이동하던 기능입니다.
  • iOS 앱을 실행하는 일과 iOS에서 Kotlin 코드를 디버깅하는 일은 계속 지원됩니다.
  • Kotlin/Native 쪽 기능도 그대로입니다. Swift로 내보내는 Swift Export나, Swift 패키지를 Kotlin 프로젝트로 가져오는 흐름은 이번 결정과 별개입니다.
  • 예전 버전의 IDE와 플러그인에서는 기존 Swift 기능을 계속 쓸 수 있지만, 거기에 새 업데이트가 붙지는 않습니다.

쉽게 말하면, 도구가 하나로 합쳐지던 방향에서 다시 각자 잘하는 쪽으로 역할을 나누는 선택입니다.

무엇이 달라졌는지​

그동안 KMP 플러그인 안에서는 Kotlin 코드와 Swift 코드를 한 창에서 보는 경험이 가능했습니다. 이제 그 경계가 다시 IDE 밖으로 나갑니다. SwiftUI 화면이나 iOS 전용 코드는 Xcode에서, 공유 로직과 Compose Multiplatform 코드는 IntelliJ나 Android Studio에서 보는 흐름이 기본이 됩니다.

JetBrains가 밝힌 배경을 제 말로 줄이면 이렇습니다. 원래 이 Swift 지원은 과거 AppCode 시절의 기술을 바탕으로 만들어졌고, 이후 여러 제품을 거치며 KMP 플러그인까지 이어졌습니다. 그런데 실제 사용은 꾸준히 줄었고, KMP를 쓰는 iOS 개발자 상당수는 Swift 작업만큼은 Xcode를 선호했다고 합니다. 반대로 플러그인 안에서 일하는 팀은 Kotlin과 Compose Multiplatform 비중이 점점 커졌습니다. Swift와 Xcode, IntelliJ 플랫폼이 계속 바뀌는 상황에서 이 연결을 유지하는 비용이 실제 쓰임에 비해 컸다는 판단입니다.

대체 기능을 새로 만들 계획은 현재로서는 없다고도 했습니다. 앞으로는 Kotlin 도구 자체와 iOS 개발자를 위한 KMP 경험을 다듬는 데 힘을 쏟겠다는 방향입니다.

실무 영향 / 주의점​

Android만 만드는 팀이라면 체감 변화는 거의 없습니다. 영향은 KMP로 iOS까지 같이 보는 팀에서 생깁니다.

  • Swift 파일을 Android Studio에서 고치던 습관이 있다면 작업 동선을 나눠야 합니다. 특히 iosApp 쪽 SwiftUI 진입점, 권한이나 딥링크처럼 iOS에 붙은 얇은 층을 누가 어느 IDE에서 고칠지 팀 안에서 정해두는 게 좋습니다.
  • 구버전에 머무는 선택은 임시 방편입니다. Swift 이동 기능이 꼭 필요해서 IntelliJ IDEA 2026.3 이전에 머무를 수는 있지만, 그 사이 Kotlin 플러그인과 Android Studio의 다른 개선을 못 받게 됩니다. 보안과 빌드 도구 호환까지 같이 보면 오래 버티는 전략은 아닙니다.
  • 공유 경계를 더 얇게 가져갈 이유가 생겼습니다. Swift 쪽에 로직이 많이 남아 있으면 IDE를 오갈 때마다 맥락이 끊깁니다. 반대로 Swift를 화면 진입과 플랫폼 연결 정도로 얇게 두고, 상태와 규칙을 Kotlin에 두면 이번 변화의 마찰이 작아집니다.

저는 이 소식을 KMP 자체가 약해졌다는 신호로 보지는 않습니다. 오히려 JetBrains가 잘 쓰이지 않는 통합을 걷어내고, 실제로 많이 쓰이는 Kotlin 쪽 경험에 집중하겠다는 쪽에 가깝습니다.

내 코드에서는 이렇게 나눠볼 생각입니다​

새로 KMP를 시작한다면 처음부터 Swift 층을 얇게 잡는 구성이 안전해 보입니다. 예를 들면 iOS 진입점은 Compose 화면을 감싸는 역할만 하고, 나머지는 공유 모듈이 맡는 식입니다.

// iosApp: Swift는 진입점만 담당하고, 화면과 상태는 공유 모듈에 둔다
import SwiftUI
import Shared

struct ContentView: View {
    var body: some View {
        ComposeView()
            .ignoresSafeArea()
    }
}

struct ComposeView: UIViewControllerRepresentable {
    func makeUIViewController(context: Context) -> UIViewController {
        MainViewControllerKt.MainViewController()
    }
    func updateUIViewController(_ uiViewController: UIViewController, context: Context) {}
}
// shared: iOS와 Android가 같이 쓰는 화면 진입점
fun MainViewController() = ComposeUIViewController {
    App()
}

이렇게 두면 Swift를 수정할 일이 생겨도 Xcode에서 보는 범위가 작고, 대부분의 변경은 Kotlin 쪽에서 끝납니다. 이미 Swift에 로직이 많이 들어가 있는 프로젝트라면, 한 번에 옮기기보다 새로 만드는 화면부터 이 경계를 적용해 보는 것도 방법입니다.

마치며​

KMP를 쓰는 팀이라면 IDE를 올리기 전에 한 번만 점검해 보면 좋겠습니다. Swift 파일을 지금 어느 도구에서 고치고 있는지, 그 흐름이 새 버전에서도 이어지는지 확인하는 것만으로 업그레이드 뒤의 혼란을 줄일 수 있습니다.

ML Drift 오픈소스 공개 — LiteRT GPU 가속의 새 엔진, TFLite GPU delegate의 뒤를 잇다

October 10, 2026 · 5 min read
Way
Android Developer

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.
2026년 10월 8일, Google AI Edge 팀이 온디바이스 GPU 추론을 위한 새 엔진 ML Drift를 Apache 2.0 라이선스로 공개했습니다. LiteRT 안에서 GPU 가속을 맡는 중심 엔진이기도 하고, 따로 떼어내어 커스텀 그래픽이나 추론 런타임을 만들 때 쓰는 독립 라이브러리로도 쓸 수 있습니다.

핵심 요약​

  • ML Drift는 기기마다 다른 GPU 환경을 한 층으로 감싸는 크로스 플랫폼 GPU 컴퓨트 엔진입니다. 뒤쪽에서는 OpenGL ES, OpenCL, Metal, WebGPU 같은 서로 다른 그래픽 경로를 다룹니다.
  • 기존 TensorFlow Lite GPU delegate가 맡던 자리를 이어받는 방향이며, 앞으로 그 예전 경로는 새 기능을 더 받지 않습니다. 이동 경로는 LiteRT의 ML Drift GPU 가속 경로입니다.
  • 고전적인 비전 모델뿐 아니라, 기기에서 도는 생성형 모델까지 함께 노린 구조 개편이 들어갔습니다.

서버에서는 비슷한 가속기가 줄지어 있지만, 휴대폰은 칩과 드라이버와 그래픽 경로가 제각각입니다. 이 다양성을 앱 개발자가 직접 메우지 않게 하는 것이 이 엔진이 풀려는 문제입니다.

무엇이 달라졌는지​

텐서를 바라보는 방식을 바꿨다​

예전 방식에서는 텐서가 GPU의 텍스처나 버퍼 같은 실제 자원에 어떻게 붙는지를 백엔드마다 따로 적어 두는 일이 많았습니다. ML Drift는 여기서 한 단계 추상화를 넣었습니다. 논리적인 텐서와 실제 GPU 배치를 분리해 두고, 초기 설정 단계에서 셰이더가 그 연결을 풀어내는 구조입니다. 덕분에 백엔드마다 셰이더를 따로 유지하는 부담을 줄이면서도 실행 중 부담은 작게 가져가려 했다는 설명입니다.

5차원 텐서와 시공간 모델​

예전 GPU 경로는 4차원 텐서를 전제로 짜여 있어, 그보다 복잡한 모양이 필요하면 우회로를 만들어야 했습니다. 새 엔진에서는 5차원 텐서를 기본으로 다룰 수 있게 되면서, 3차원 합성곱이나 영상처럼 시간 축이 붙은 모델을 기기 GPU에서 바로 돌리는 길이 넓어졌습니다.

LLM 단계에 따라 커널을 바꾼다​

기기에서 도는 언어 모델은 한 번에 길게 읽어 들이는 구간과, 토큰을 하나씩 이어 붙이는 구간의 성격이 다릅니다. 앞쪽은 연산량에, 뒤쪽은 메모리 이동에 더 묶입니다. ML Drift는 지금이 어느 단계인지에 따라 커널과 배치를 바꾸고, KV 캐시 쪽에도 전용 배치를 적용해 불필요한 왕복을 줄이는 방향을 택했습니다.

커스텀 연산과 데스크톱 확장​

모델에 특이한 블록이 있으면 개발자가 낮은 수준의 셰이딩 언어로 직접 연산을 등록할 수 있는 길도 새로 정리됐습니다. 흥미로운 부분은, 코딩 에이전트가 이 커스텀 셰이더를 만들고 검증하는 과정을 돕는 안내 파일까지 함께 제공된다는 점입니다. 또 WebGPU 경로를 바탕으로 브라우저 밖 Windows와 Linux에서도 같은 코드를 돌리는 미리보기가 소개됐고, macOS에서는 Metal 경로가 이를 받칩니다.

실제 서비스에서의 쓰임도 함께 소개됐습니다. 영상 효과, 사진 보정, 브라우저 안 온디바이스 모델, 사진 편집 앱의 피사체 선택 같은 작업에서 기존 GPU 경로보다 지연이 줄었다는 사례가 실렸습니다. 숫자는 모델과 기기마다 다르니, 결국 내 모델로 재보는 수밖에 없습니다.

실무 영향 / 주의점​

  • TFLite GPU delegate를 직접 쓰고 있다면 이동 계획을 세울 때입니다. 새 기능이 그쪽으로 더 오지 않는다고 못 박은 만큼, 지금 당장 끊기지는 않더라도 다음 모델 교체나 성능 개선 시점에 LiteRT 경로로 벤치마크를 한 번은 돌려봐야 합니다.
  • 벤치마크는 모델 전체 평균만 보면 안 됩니다. 언어 모델이라면 읽어 들이는 구간과 토큰을 만드는 구간의 속도가 따로 움직입니다. 두 구간을 나눠 재지 않으면 병목이 어디인지 놓치기 쉽습니다.
  • GPU 벤더별 확인은 여전히 필요합니다. 추상화가 좋아졌다고 해도 실제 속도는 칩과 드라이버에서 갈립니다. 플래그십 한 대에서만 재고 끝내면 중저가 기기에서 체감이 다르게 나올 수 있습니다.
  • 커스텀 연산은 강력하지만 유지 비용이 붙습니다. 직접 짠 셰이더는 모델을 바꿀 때마다 다시 봐야 합니다. 꼭 필요한 블록에만 쓰고, 나머지는 기본 연산으로 두는 편이 운영에 낫습니다.

금융 앱 관점에서는, 사진을 읽어 문서를 인식하거나 기기 안에서 작은 모델로 분류하는 작업을 서버로 보내지 않고 끝낼 수 있을 때 의미가 큽니다. 데이터를 기기 밖으로 내보내지 않는 구조는 개인정보와 네트워크 비용 양쪽에서 이득이 있기 때문입니다. 다만 그 전제는 결국 속도인데, 이번 개편은 그 속도를 벤더 중립적으로 끌어올리려는 시도라고 읽힙니다.

내 코드에서는 이렇게 재볼 생각입니다​

저라면 기존에 GPU delegate로 돌리던 모델을 LiteRT 경로로 바꿔 같은 기기에서 나란히 재는 것부터 시작하겠습니다. 아래는 개념을 잡기 위한 예시 흐름입니다.

// 같은 모델을 CPU와 GPU 경로로 각각 준비해 지연을 나눠 재는 벤치마크 뼈대
data class BenchResult(
    val backend: String,
    val warmupMs: Double,
    val steadyMs: Double,
)

fun benchmarkModel(backend: String): BenchResult {
    // 1) LiteRT 모델을 backend 옵션으로 연다 (GPU면 ML Drift 가속 경로)
    // 2) warm-up을 충분히 돌린 뒤, 입력 모양별로 지연을 측정한다
    // 3) 언어 모델이면 prefill과 decode를 분리해서 기록한다
    return BenchResult(backend, warmupMs = 0.0, steadyMs = 0.0)
}

val results = listOf("CPU", "GPU").map { benchmarkModel(it) }
results.forEach { println("${it.backend}: steady=${it.steadyMs}ms") }

여기에 기기 이름과 칩 정보, 모델 버전을 함께 남겨 두면 나중에 "어떤 폰에서 느려졌는지"를 추적하기가 훨씬 쉬워집니다. 커스텀 연산은 이 기본 측정이 끝난 뒤, 프로파일에서 실제로 뜨거운 블록이 보일 때만 손대는 순서가 좋겠습니다.

독립 라이브러리 쪽이 궁금하다면 공개 저장소에서 Android용 OpenCL 시작 가이드부터 볼 수 있습니다.

마치며​

온디바이스 추론은 이제 실험 기능이 아니라, 영상과 사진과 생성형 기능이 실제로 도는 바닥이 되고 있습니다. 그 바닥의 GPU 층이 오픈소스로 열리고 예전 경로의 종료 방향까지 정해진 만큼, 관련 기능을 가진 팀이라면 한 번은 현재 스택을 점검해 볼 시점입니다.

Android CLI에 실기기 스트리밍이 붙었다 — 에이전트가 원격 단말에서 직접 확인하는 흐름

October 9, 2026 · 4 min read
Way
Android Developer

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.
2026년 10월 2일, Android Developers Blog를 통해 Android CLI 업데이트가 공개됐습니다. 핵심은 두 가지입니다. 원격 실기기에 붙는 Device Streaming을 CLI에서 쓸 수 있게 됐고, 에이전트용 Android skills가 20개를 넘어섰습니다.

핵심 요약​

  • Android CLI는 특정 AI 모델에 묶이지 않고, 다양한 코딩 에이전트와 함께 프로젝트 생성, 빌드, 테스트, 에뮬레이터 실행을 돕는 커맨드라인 도구입니다.
  • 이제 CLI를 통해 Android Device Streaming에 접속하면, 손에 없는 실기기라도 원격으로 앱을 올리고 로그와 트레이스를 수집하고 스크린샷까지 찍을 수 있습니다.
  • Android skills는 SKILL.md 형태의 구조화된 지침 모음입니다. 모델의 학습 시점에 기대지 않고, 공식 가이드 기준으로 에이전트에게 맥락을 주입하는 방식입니다.

무엇이 달라졌는지​

1) Device Streaming을 에이전트가 직접 쓴다​

실기기에서만 재현되는 하드웨어/OS 이슈는 에뮬레이터로 놓치기 쉽지만, 필요한 단말이 항상 책상 위에 있는 것도 아닙니다. 이번 업데이트로 에이전트가 보안이 적용된 ADB over SSL 연결을 통해 원격 단말을 마치 USB로 연결한 것처럼 다룰 수 있게 됐습니다.

가능한 작업은 대략 이렇습니다.

  • 원격 단말 깨우기, 빌드 배포
  • 로그/트레이스 수집
  • 헤드리스 스크린샷 캡처
  • 터미널 안에서 기기 목록을 보고 어떤 단말을 쓸지 선택

즉, “코드를 고쳤으니 실제 단말에서 눌러보고 결과를 가져와” 같은 흐름을 사람이 중간에 끼지 않고도 시도할 수 있는 기반이 생긴 셈입니다.

2) Android skills가 실무형으로 늘어났다​

공식 skills 저장소에는 이제 20개가 넘는 스킬이 있고, 성격도 꽤 실무적입니다. 원문에서 소개한 예시를 제 말로 줄이면 다음과 같습니다.

  • 제출 전 Play 정책 준수 점검(매니페스트, 권한, 타깃 SDK, 개인정보 고지)
  • Credential Manager 기반 복원 로그인(Restore Credentials) 구현
  • 암시적 인텐트 탈취 같은 인텐트 보안 점검
  • 프로파일러로 프레임 드롭 원인을 찾고 PerfettoSQL로 트레이스 질의
  • 구형 Camera1/Camera2 코드를 CameraX로 이전
  • Leanback 기반 TV 화면을 Compose for TV로 전환
  • Media3 재생 상태와 Cast 수신기 동기화
  • 테스트 전략(단위 테스트, Compose UI 테스트, 스크린샷 테스트) 세팅
  • R8 설정 감사

이번 글에서는 Wear OS용 Compose Material 3 스킬이 스포트라이트로 소개됐습니다. 둥근 화면, 회전 입력, 저전력, TransformingLazyColumn, AppScaffold/ScreenScaffold 같은 Wear 특유의 패턴을 에이전트가 놓치지 않게 잡아주는 스킬인데, FotMob 팀이 기존 Wear 앱의 리스트 여러 개를 이 패턴으로 옮기면서 레거시 래퍼와 회전/포커스 보일러플레이트를 걷어냈다는 사례도 함께 실렸습니다.

3) 스킬 관리가 CLI에 붙었다​

스킬은 프로젝트마다, 또 에이전트마다 디렉터리가 달라서 관리가 번거로울 수 있는데, 흐름은 비교적 단순하게 정리돼 있습니다.

# Android CLI 설치 후 android-cli 스킬 세팅
android init

# 공식 스킬 목록 확인
android skills list

# 필요한 스킬만 프로젝트에 추가 (예: Wear Compose M3)
android skills add wear-compose-m3 --project=.

# 나중에 일괄 업데이트
android skills update --all

중요한 건 이 스킬들이 특정 환경 전용이 아니라는 점입니다. Android Studio, 다른 코드 에디터, 서드파티 에이전트 환경에서도 같은 스킬을 재사용하는 방향으로 설계됐다고 합니다.

실무 영향 / 주의점​

금융 앱처럼 단말 파편화와 보안 정책이 중요한 환경에서는, 에이전트가 실기기 결과를 직접 확인하는 흐름이 매력적입니다. 다만 바로 운영 파이프라인에 넣기 전에 확인할 것도 있습니다.

  • 권한과 보안 연결: 원격 단말 접속은 ADB over SSL 기반이라지만, 사내 네트워크 정책과 단말 접근 통제 범위 안에서 써야 합니다. 어떤 프로젝트를 링크하고, 어떤 로그가 외부로 나가는지 먼저 정리가 필요합니다.
  • 스킬은 정답지가 아니라 맥락이다: 스킬이 있어도 최종 판단은 코드 리뷰와 테스트가 해야 합니다. 특히 Play 정책, 권한, 인텐트 보안처럼 심사/보안과 닿은 영역은 스킬 결과를 그대로 믿지 말고 체크리스트로 한 번 더 확인하는 게 좋습니다.
  • 비용이 드는 반복 실행 주의: “단말에서 확인해봐”를 에이전트 루프에 넣으면, 사람이 할 때보다 훨씬 자주 실행하게 됩니다. 테스트 단말 시간, 네트워크, CI 분(minute)을 먹는 구조인지 먼저 작은 작업으로 측정해 보길 권합니다.

장점도 분명합니다. 지금까지는 에이전트가 코드만 보고 추측했다면, 이제는 실행 결과(로그, 스크린샷, 트레이스)를 근거로 다음 패치를 제안하는 루프를 만들 수 있습니다. UI 회귀나 단말별 렌더링 차이를 잡는 데 특히 도움이 될 만합니다.

내 코드에서 이렇게 써볼 생각입니다​

저는 거창하게 시작하기보다, 스킬 한 개 + 단말 한 대로 작은 실험부터 해볼 생각입니다.

# 1) 지금 프로젝트에 테스트 전략 스킬을 붙여 현재 테스트 구성을 점검
android skills add testing-strategy --project=.

# 2) 에이전트에게 요청하는 프롬프트 예시
# "이 모듈의 Compose UI 테스트가 비어 있는 화면을 찾아서,
#  Device Streaming 단말에서 스크린샷까지 확인한 뒤 결과를 보고해줘"

스크린샷 테스트가 약한 화면부터 에이전트에게 맡겨보면, 사람이 놓친 레이아웃 깨짐을 얼마나 잡아내는지, 반대로 오탐이 얼마나 나오는지 금방 감이 옵니다. 그 다음에 R8 감사나 CameraX 이전처럼 범위가 넓은 스킬로 확장해도 늦지 않습니다.

마치며​

이번 업데이트의 방향은 “에이전트가 코드를 더 잘 쓰는 것”에서 “에이전트가 실행 결과까지 확인하며 일하는 것”으로 한 발 나간 느낌입니다. Android 개발자라면 CLI와 skills를 한 번쯤 직접 만져보면서, 내 프로젝트에서 자동으로 확인할 수 있는 일이 무엇인지 목록을 만들어보는 것만으로도 가치가 있을 것 같습니다.

IntelliJ의 Kotlin 인텔리전스가 VS Code로 왔다 — Java and Kotlin 확장 RC 공개

October 9, 2026 · 3 min read
Way
Android Developer

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.
2026년 10월 6일, JetBrains가 Java and Kotlin by IntelliJ IDEA 확장의 Release Candidate를 공개했습니다. 프리뷰를 시작한 지 약 두 달 만이고, 정식 1.0이 임박했다는 신호입니다.

핵심 요약​

  • IntelliJ IDEA가 가진 Java/Kotlin 코드 이해 능력을 LSP(Language Server Protocol) 서버 형태로 뽑아내, VS Code와 Cursor 같은 외부 에디터에서 쓸 수 있게 한 확장입니다.
  • 이번 RC는 마지막 EAP 빌드입니다. 이후 정식 버전이 나오면 신규 사용자는 30일 체험 후 IntelliJ IDEA Ultimate 구독이 필요합니다.
  • 마켓플레이스 누적 다운로드는 2만 건을 넘겼고, JetBrains 내부에서도 IntelliJ 기반 IDE를 만드는 대형 저장소에 직접 적용해 검증했다고 합니다.

무엇이 달라졌는지​

프리뷰 단계에서는 완성도와 안정성을 다듬는 업데이트가 이어졌고, RC에서는 “에디터 밖 워크플로까지 IntelliJ의 이해도를 가져간다”는 방향이 더 또렷해졌습니다.

제 기준으로 실무에 닿는 부분만 추리면 이렇습니다.

  • 핵심 코딩 지원: 스마트 자동완성, 코드 내비게이션, 인스펙션, 퀵픽스, 정적 분석 같은 기본기가 LSP를 통해 제공됩니다.
  • 한 단계 위 기능: 프로젝트 전역 리팩터링, DAP 기반 디버깅, Maven/Gradle/Bazel 프로젝트 모델 이해, 내장 테스트 러너, Spring 도구 연동까지 포함됩니다.
  • 에이전트 연동: Cursor에 설치하면 Cursor Agent가 같은 언어 서버를 활용해 의미 기반 검색, 이동, 분석을 수행합니다. 텍스트 검색만으로 코드를 뒤지는 것보다 빠르고 결정적인 결과를 기대할 수 있는 구조입니다.

원문에서 강조하는 것도 결국 “다른 에디터에 IntelliJ 기능을 복제”하는 게 아니라, 개발자와 도구가 어디서 일하든 JVM 코드 이해도를 재사용하게 만드는 쪽에 가깝습니다.

실무 영향 / 주의점​

Android 개발자 입장에서 이 확장이 당장 Android Studio를 대체하진 않습니다. 에뮬레이터, 프로파일러, Compose 프리뷰, AGP 특화 도구처럼 Android Studio 안에 깊게 붙은 기능은 여전히 Studio 쪽이 본진입니다.

대신 이런 상황에서 꽤 유용합니다.

  • 평소 Cursor나 VS Code로 AI 에이전트와 함께 코드를 만지는데, Kotlin/Java 이해도가 아쉬웠던 경우
  • 멀티모듈 Gradle 프로젝트에서 “정의로 이동”이나 “사용처 찾기”가 부정확해 에이전트가 엉뚱한 파일을 고치는 일이 잦았던 경우
  • 백엔드(Spring) + Android를 오가며 한 에디터에서 작업하고 싶은 경우

다만 라이선스는 미리 봐두는 게 좋습니다. RC는 EAP 조건으로 30일간 라이선스 없이 쓸 수 있고, 정식 이후에는 체험 기간이 끝나면 Ultimate 구독이 필요하다고 안내돼 있습니다. 팀에서 이미 Ultimate을 쓰고 있다면 추가 비용이 없지만, 무료 에디터 + 무료 확장 조합으로 생각했다면 정식 이후 정책을 확인해야 합니다.

또 하나, RC는 어디까지나 정식 직전 단계입니다. 사내 핵심 저장소에 바로 붙이기보다, 사이드 프로젝트나 작은 모듈에서 리팩터링 정확도와 인덱싱 속도를 먼저 체감해 보는 쪽이 안전합니다.

내 코드에서 이렇게 써볼 생각입니다​

저는 Cursor에서 에이전트에게 모듈 간 이동이 많은 작업을 시킬 때를 노려보고 있습니다. 예를 들어 피처 모듈의 공개 API를 바꾸는 작업은, 에이전트가 호출부를 정확히 찾아내지 못하면 컴파일이 깨진 상태로 남기 쉽습니다.

1) VS Code / Cursor에 Java and Kotlin by IntelliJ IDEA (RC) 설치
2) 한투 앱의 작은 Gradle 모듈부터 열어 인덱싱이 끝날 때까지 대기
3) 에이전트에게 요청: "이 인터페이스의 구현체와 호출부를 모두 찾아서 시그니처 변경 영향 범위를 먼저 보고해줘"
4) 결과를 Android Studio의 Find Usages와 대조해 정확도 확인

이 대조를 몇 번 해보면, 에이전트에게 리팩터링을 어디까지 맡길 수 있는지 감이 잡힙니다. 언어 서버가 프로젝트 모델을 제대로 쥐고 있으면, 에이전트의 첫 패치가 훨씬 덜 헤맵니다.

마치며​

Kotlin Toolchain이 CLI 쪽에서 프로젝트 시작 경험을 다듬고 있다면, 이 확장은 에디터 쪽에서 “IntelliJ의 뇌”를 밖으로 꺼내는 시도입니다. Android Studio가 본진인 건 변하지 않지만, AI 에이전트와 함께 일하는 비중이 늘어날수록 정확한 언어 서버의 가치는 더 커질 거라고 봅니다.

Compose 1.13.0-beta01 정리 — Dp.Unspecified가 리컴포지션을 막던 버그 수정

October 8, 2026 · 2 min read
Way
Android Developer

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.
2026년 10월 7일, Compose 1.13.0-beta01이 릴리스됐습니다. stable 채널의 최신은 1.12.1입니다.
runtime 기준으로 실무에 닿는 변경만 추려서 정리합니다.

Kotlin 2.2 타깃으로 상향​

1.13부터 Compose 라이브러리는 Kotlin 2.2를 타깃으로 빌드되고, kotlinc 2.2가 필요합니다.
버전 카탈로그에서 Compose BOM만 올리는 습관이 있다면, Kotlin 플러그인 버전이 뒤처진 모듈에서 먼저 걸릴 수 있으니 함께 확인하는 게 좋습니다.

Dp.Unspecified를 받는 컴포저블이 스킵되지 않던 버그​

개인적으로 이번 베타에서 가장 반가운 수정입니다.
Float.NaN이나 Double.NaN을 인자로 받는 @Composable은 인자가 그대로여도 스킵되지 않고 매번 리컴포지션되는 버그가 있었습니다. Dp.Unspecified가 내부적으로 Float.NaN 기반이라, 선택적 간격이나 크기를 Dp.Unspecified 기본값으로 받는 공용 컴포넌트가 조용히 리컴포지션 비용을 치르고 있었던 셈입니다.

// 이런 공용 컴포넌트가 인자 변화가 없어도 스킵되지 않을 수 있었다
@Composable
fun PriceRow(
    label: String,
    topPadding: Dp = Dp.Unspecified
) { /* ... */ }

사내 디자인 시스템처럼 공용 컴포넌트에 Dp.Unspecified 기본값이 흔한 코드베이스라면, 1.13 stable이 나올 때 체감 성능이 좋아질 수 있습니다.

computedStateOf 계산 블록은 읽기 전용으로 강제​

computedStateOf의 계산 블록 안에서 상태에 쓰면 이제 IllegalStateException이 발생합니다.
기존에 계산 블록 안에서 쓰기까지 하던 코드가 있었다면 런타임에서 바로 드러나니, 베타를 올리는 모듈부터 확인이 필요합니다.

그 외 버그 픽스​

  • CompositionObserver가 컴포지션 패스마다 한 번만 해석되고, 교체는 다음 패스부터 적용됩니다. movable content 삽입 시에도 begin/end 콜백이 보고됩니다.
  • movableContent 이동 시 래퍼 그룹 슬롯이 남아 있던 LinkComposer 메모리 누수를 고쳤습니다.
  • lifecycle-runtime 의존성이 2.10.0으로 올라갔습니다. 번들된 lifecycle lint 검사는 AGP 9.5.0-alpha04 이상과 맞물려 있으니, AGP 베타 채널을 쓰는 프로젝트는 같이 보는 게 좋습니다.
  • ComposeTracer를 메인 스레드 밖에서도 쓸 수 있게 됐습니다.

올릴까 말까​

1.12.1 stable은 1.12.0에서 변경이 없는 버전이라, 운영 앱은 stable 유지가 무난합니다.
베타는 성능 검증이 필요한 화면(공용 컴포넌트를 많이 쓰는 MTS 특성상 리컴포지션 이슈가 체감되는 곳) 위주로 먼저 올려 보고, 앱 전체 확대는 stable 이후가 안전해 보입니다.

Kotlin Toolchain 0.13 — 새 KMP 프로젝트는 kotlin new로 시작하기

October 8, 2026 · 3 min read
Way
Android Developer

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.
JetBrains가 Kotlin Toolchain 0.13을 공개하면서, 신규 Kotlin Multiplatform(KMP) 프로젝트의 출발점으로 이 툴체인을 공식 추천하기 시작했습니다.
Gradle 설정 파일을 손으로 짜는 대신 kotlin CLI 하나로 환경을 맞추는 방식이 어떤 모습인지 정리해 보겠습니다.

Kotlin Toolchain이 뭔가요​

Kotlin Toolchain은 JVM·Android·iOS·멀티플랫폼·서버 앱을 하나의 CLI 진입점으로 만들고, 빌드하고, 테스트하고, 배포하는 도구입니다.
JDK나 Android SDK 같은 필수 도구들을 선언적 설정에 맞춰 자동으로 내려받아 주기 때문에, "새 노트북에서 KMP 프로젝트 처음 열었더니 SDK가 없어서 동기화 실패" 같은 온보딩 마찰이 크게 줄어듭니다.
이번 0.13부터는 신규 KMP 프로젝트에 이 툴체인을 쓰는 것이 JetBrains의 권장 경로가 됐습니다.

kotlin new: 대화형 프로젝트 생성​

0.13의 핵심은 kotlin new 명령입니다. 웹의 KMP Wizard처럼 앱 유형을 고르고 타깃 플랫폼을 선택하면 프로젝트가 생성됩니다.
기존 kotlin init도 같은 흐름으로 맞췄는데, 차이는 kotlin init이 현재 디렉터리에 바로 파일을 만든다는 점입니다.

# 새 프로젝트 생성 (대화형)
kotlin new

# 이미 설치돼 있다면 업데이트
kotlin update

Android 개발자 관점에서 반가운 부분​

  • Android SDK 자동 프로비저닝이 IDE까지 확장: 이전에는 kotlin build/kotlin run 때만 SDK가 자동 설치돼서, 빌드 전에 IDE로 먼저 열면 SDK 누락 오류가 났습니다. 이제 프로젝트 import 시점에도 누락된 SDK 컴포넌트를 자동으로 받아 줍니다.
  • namespace/applicationId 검증 강화: com.example.app 같은 샘플 ID로 실수로 배포 빌드를 만드는 실수를 막아 줍니다.
  • 다운로드 진행 표시: JDK, Android SDK, iOS 런타임, 컴파일러 다운로드가 CLI에 진행 바로 표시됩니다.

Swift Package Manager 의존성 지원​

Apple 타깃에서 SPM 패키지를 선언적으로 가져올 수 있게 됐습니다. 설정 파일에 저장소와 버전을 적으면 됩니다.

dependencies:
  - swiftPackage:
      repository: "https://github.com/firebase/firebase-ios-sdk.git"
      version: "12.17.0"
      products: ["FirebaseCore", "FirebaseFirestore", "FirebaseAnalytics"]

가져온 Objective-C API는 swiftPMImport 접두사로 네임스페이스가 붙어, Kotlin 코드에서 명시적으로 구분됩니다. 로컬 SPM 패키지는 localSwiftPackage 키로 연결할 수 있습니다.

빌드 속도: Kotlin/Native 컴파일러 캐시​

Kotlin/Native 재빌드가 빨라집니다. 컴파일된 네이티브 의존성을 빌드 간, 심지어 프로젝트 간에 캐시로 재사용하고, 프로젝트 코드는 파일 단위 캐시로 링크 시 바뀐 부분만 다시 컴파일합니다.
기존 settings.kotlin.compileIncrementally 설정을 그대로 쓰고, .klib 컴파일 자체는 전체로 수행됩니다.

그 외​

  • IDE 동기화 상태를 에디터에서 확인할 수 있게 됐습니다.
  • 멀티플랫폼 라이브러리 배포 시 Compose Resources와 SwiftPM 의존성 메타데이터가 아티팩트와 함께 게시되고, 서드파티 멀티플랫폼 라이브러리의 Compose Resources도 해석됩니다.
  • AI 에이전트 연동도 강화됐습니다. Compose Hot Reload MCP 서버와 Kotlin용 에이전트 스킬(npx skills add kotlin/kotlin-agent-skills)이 제공됩니다.
  • IDE 기능은 IntelliJ IDEA 2026.2.3 또는 Android Studio Rabbit 1(2026.2.1) 이상에서 최신 Kotlin Toolchain 플러그인과 함께 쓸 수 있습니다.

마치며​

기존 Gradle 기반 프로젝트를 당장 마이그레이션하라는 얘기는 아닙니다. JetBrains도 로드맵에서 Gradle 프로젝트의 공백을 먼저 메우는 데 집중하겠다고 밝혔습니다.
다만 새로 KMP를 시작한다면 kotlin new 한 번으로 Android·iOS 환경을 한 번에 맞추는 경험은 꽤 매력적입니다. 다음에 사이드 프로젝트로 KMP를 만질 일이 있으면 이 경로로 시작해 볼 생각입니다.

국내 MTS에 Gradle Convention Plugin 도입하기

December 5, 2025 · 2 min read
Way
Android Developer

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.
국내 MTS 프로젝트에 적용하게 된 Gradle Convention Plugin에 대해 설명해드리겠습니다.

배경​

Multi Module을 적용하면서, 각 모듈의 build.gradle.kts 파일에 중복되는 설정들이 많아졌습니다.
이를 해결하기 위해 Gradle Convention Plugin을 도입하여 공통 설정을 중앙에서 관리하기로 했습니다.
기존 build.gradle.kts 파일들은 다음과 같은 구조를 가지고 있었습니다.

//A module
plugins {
    alias(libs.plugins.android.application)
    alias(libs.plugins.kotlin.android)
}

android {
    namespace = "com.example.module-a"
    compileSdk = libs.versions.compile.sdk.get().toInt()
    dependencies {
        implementation(libs.bundles.kotlin)
    }
}

//B module

plugins {
    alias(libs.plugins.android.application)
    alias(libs.plugins.kotlin.android)
}

android {
    namespace = "com.example.module-b"
    compileSdk = libs.versions.compile.sdk.get().toInt()
    dependencies {
        implementation(libs.bundles.kotlin)
    }
}

Gradle Convention Plugin 도입​

위와 같이 중복되는 설정들을 Gradle Convention Plugin으로 분리하여 관리하면, 각 모듈의 build.gradle.kts 파일이 훨씬 간결해집니다.
다음은 Convention Plugin을 적용한 후의 예시입니다.

build-logic/convention/build.gradle.kts​


plugins {
    `kotlin-dsl`
    `kotlin-dsl-precompiled-script-plugins`
}

group = "com.sample.buildlogic"

dependencies {
    compileOnly(libs.android.gradle.plugin)
    compileOnly(libs.kotlin.gradle.plugin)
    compileOnly(libs.gradle.plugin.ktlint.compose)
    compileOnly(libs.gradle.plugin.detekt)
    compileOnly(libs.gradle.plugin.ksp)
}

gradlePlugin {
    plugins {
        register("sample.android.library") {
            id = "sample.android.library"
            implementationClass = "AndroidLibrarySampleConventionPlugin"
        }
    }
}

build-logic/src/main/kotlin/AndroidLibrarySampleConventionPlugin.kt​

class AndroidLibrarySampleConventionPlugin : Plugin<Project> {
    override fun apply(target: Project) {
        with(target) {
            with(pluginManager) {
                apply("com.android.library")
                apply("kotlin-android")
                apply("koreainvestment.kotlinx.serialization")
            }
            extensions.getByType<VersionCatalogsExtension>().named("libs").apply {
                extensions.configure<LibraryExtension> {
                    configureKotlinAndroid(this)
                    defaultConfig.targetSdk =
                        findVersion("target-sdk").get().requiredVersion.toInt()
                    configureFlavors(this)
                    defaultConfig.vectorDrawables.useSupportLibrary = true
                }
            }
        }
    }
}

build-logic/convention/build.gradle.kts​

//A module
plugins {
    id("sample.android.library")
}

android {
    namespace = "com.example.module-a"
}

//B module

plugins {
    id("sample.android.library")
}

android {
    namespace = "com.example.module-b"
}

마치며​

위와 같이 Convention Plugin을 도입하면, 공통 설정이 중앙에서 관리되어 유지보수가 용이해집니다.
또한, 새로운 모듈을 추가할 때도 Convention Plugin만 적용하면 되므로 개발 속도도 향상됩니다.

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.
국내 MTS 프로젝트에 적용하게 된 Multi Module에 대해 설명해드리겠습니다.

현재 프로젝트 구조​

프로젝트에 여러 모듈이 존재하지만, 3rd party 라이브러리들이 다수이고, 각 Feature들을 재사용하기에 적합하지 않은 상태였습니다.
이를 해결하기 위해 Multi Module 구조로 전환하는 작업을 진행했습니다.
대략적인 프로젝트 구조는 대략 다음과 같습니다.

.
├── app
├── 3rd_party_library_1
├── 3rd_party_library_2
├── 3rd_party_library_3
├── 3rd_party_library_4
└── formdeCore

MultiModule 적용​

Multi Module 구조로 전환하면서, 모듈의 상단 명칭을 core, library, features, plugins, resources 등으로 구분하여 관리하기로 했습니다.
구체적인 디렉토리 구조는 다음과 같습니다.

.
├── app/
├── core/
│   ├── analytics/
│   ├── asset-file/
│   ├── autorization/
│   ├── common/
│   ├── database/
│   ├── datastore/
│   ├── encrypt/
│   ├── network/
│   ├── on-foreground-service/
│   ├── push/
│   ├── remote-file/
│   ├── state-viewmodel/
│   ├── testing/
│   ├── ui/
│   └── ui-xml/
├── features/
│   ├── common/
│   │   ├── ui/
│   │   └── logic/
│   ├── community/
│   │   ├── ui/
│   │   └── logic/
│   ├── developer/
│   │   ├── ui/
│   │   └── logic/
│   ├── event/
│   │   ├── ui/
│   │   └── logic/

│   │   ├── ui/
│   │   └── logic/
│   ├── my-assets/
│   │   ├── ui/
│   │   └── logic/

│       ├── ui/
│       └── logic/

app​

  • 최종적으로 빌드되는 어플리케이션 모듈입니다.

core​

  • 프로젝트 전반에서 공통으로 사용되는 기능들을 포함하는 모듈입니다.
    예를 들어, 네트워크 통신, 데이터베이스 관리, 인증 처리 등의 기능들이 여기에 속합니다.

features​

  • 실제 어플리케이션의 기능 단위들을 모듈화한 것입니다.
    각 기능은 독립적으로 개발 및 테스트가 가능하도록 구성되어 있습니다.
    예를 들어, 커뮤니티, 이벤트, 메뉴 관리 등의 기능들이 여기에 속합니다.

  • logic

    • 각 기능 모듈 내에서 비즈니스 로직을 담당하는 부분입니다.
      해당 모듈에서는 기능에 필요한 모델과 비즈니스 로직을 구현합니다. 이를 통해 UI와의 분리를 유지하고, 다른 feature 모듈에서도 재사용할 수 있도록 합니다.

  • ui

    • 각 기능 모듈 내에서 사용자 인터페이스를 담당하는 부분입니다.

library​

  • 3rd party 라이브러리나 공통으로 사용되는 라이브러리들을 관리하는 모듈입니다.

plugins​

  • 프로젝트에 적용되는 Gradle 플러그인들을 관리하는 모듈입니다.
    예를 들어, 커스텀 Lint 검사기나 어노테이션 프로세서 등이 여기에 속합니다.

resources​

  • 이미지, 문자열, 레이아웃 파일 등과 같은 리소스 파일들을 관리하는 모듈입니다.

마치며​

이와 같은 Multi Module 구조를 도입함으로써, 코드의 재사용성이 향상되고, 각 모듈 간의 의존성을 명확히 관리할 수 있게 되었습니다.
또한, 각 모듈을 독립적으로 개발하고 테스트할 수 있어 개발 효율도 크게 증가했습니다.

국내 MTS에 Version Catalog 도입하기

December 3, 2025 · 2 min read
Way
Android Developer

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.

국내 MTS 프로젝트에 적용하게 된 Version Catalog에 대해 설명해드리겠습니다.
안드로이드는 gradle을 빌드 시스템으로 사용하며, groovy 또는 kotlin DSL을 통해 의존성 관리를 수행합니다.
기존 프로젝트에서는 여러 모듈에서 각기 다른 라이브러리 버전을 사용하고 있어, 우선 이들을 일관되게 관리하는 방법으로 Version Catalog 적용을 검토하게 되었습니다.

현재 프로젝트 구조​

app에 지나치게 의존적이고 3rd party 라이브러리가 산재해 있어 유지보수가 어려운 상황이었습니다.
이를 해결하기 위해 Multi Module 구조로 전환하는 작업을 진행했고, 그 과정에서 Version Catalog를 도입하게 되었습니다.
대략적인 프로젝트 구조는 다음과 같습니다.

.
├── app
├── 3rd_party_library_1
├── 3rd_party_library_2
├── 3rd_party_library_3
├── 3rd_party_library_4
└── formdeCore

Version Catalog 도입하기​

Gradle의 Version Catalog를 도입해 모듈 간 라이브러리 버전을 중앙에서 관리하도록 변경했습니다.
구체적으로는 gradle/libs.versions.toml 파일을 만들고, 각 모듈의 build.gradle.kts에서 해당 카탈로그를 참조하도록 했습니다.

versions​

  • 각 모듈의 라이브러리 버전을 정의합니다.
  • 패키징되어있는 라이브러리들의 경우 버전이 동일한 경우가 많기 때문에 버전을 공통으로 관리하면 편리합니다.

libraries​

  • 각 모듈에서 사용할 라이브러리와 해당 버전을 정의합니다.

plugins​

  • 각 모듈에서 사용할 플러그인과 해당 버전을 정의합니다.

bundles​

  • 관련된 라이브러리들을 묶어서 한 번에 참조할 수 있도록 정의합니다.
  • 필요한 라이브러리들을 패키징하여 한 번에 추가할 수 있어 편리합니다.

예시로 사용한 libs.versions.toml은 다음과 같습니다.

[versions]
kotlin = "2.0.21"
target-sdk = "36"
jvm = "17"
min-sdk = "26"
compile-sdk = "36"
android-gradle-plugin = "8.3.2"
.
.
.

[plugins]
android-application = { id = "com.android.application", version.ref = "android-gradle-plugin" }
.
.
.

[libraries]
android-gradle-plugin = { module = "com.android.tools.build:gradle", version.ref = "android-gradle-plugin" }
.
.
.
[bundles]
kotlin = ["kotlin-stdlib", "kotlin-reflect"]

그리고 각 모듈의 build.gradle.kts에서 다음과 같이 플러그인과 버전을 참조하도록 변경했습니다.

plugins {
    alias(libs.plugins.android.application)
    alias(libs.plugins.kotlin.android)
}

android {
    compileSdk = libs.versions.compile.sdk.get().toInt()

    defaultConfig {
        applicationId = "com.example.app"
        minSdk = libs.versions.min.sdk.get().toInt()
        targetSdk = libs.versions.target.sdk.get().toInt()
        versionCode = 1
        versionName = "1.0"
    }
    dependencies {
        implementation(libs.bundles.kotlin)
    }
}

마치며​

이와 같이 Version Catalog를 적용하면, 라이브러리 버전 관리가 일관화되어 업데이트나 충돌 해결이 훨씬 수월해집니다.
또한, 새로운 라이브러리를 추가할 때도 중앙 파일만 수정하면 되므로 유지보수가 간편해집니다.

Cursor·VS Code에서 IntelliJ급 Kotlin 분석이 온다 — "Java and Kotlin by IntelliJ IDEA" 1.0

October 16, 2026 · 4 min read
Way
Android Developer

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.
최근 정식 릴리스된 JetBrains의 LSP 기반 확장 "Java and Kotlin by IntelliJ IDEA" 1.0에 대해 설명해드리겠습니다.

배경​

Kotlin 코드를 Android Studio가 아닌 에디터에서 작성하면, IntelliJ 수준의 코드 분석 기능을 그대로 쓰기 어렵다는 아쉬움이 있었습니다.
10주 전 프리뷰로 공개됐던 JetBrains의 LSP 기반 확장이 드디어 1.0 정식 릴리스를 맞았습니다.
이번 릴리스로 VS Code와 Cursor에서도 IntelliJ IDEA 데스크톱 IDE의 Java·Kotlin 분석 엔진을 그대로 쓸 수 있게 됐습니다.
자세한 내용은 JetBrains의 발표 글 IntelliJ IDEA's Java and Kotlin for Cursor and VS Code Hits 1.0에서 확인할 수 있습니다.

"Java and Kotlin by IntelliJ IDEA" 1.0 살펴보기​

LSP 기반 분석 엔진​

  • IntelliJ IDEA의 Java·Kotlin 언어 지능을 LSP(언어 서버 프로토콜)로 뽑아내 VS Code와 Cursor에 그대로 올린 확장입니다. Cursor 팀과 함께 협업해 개발됐습니다.
  • 핵심 아이디어는 단순합니다. 언어 지원을 한 번만 구현하고, 어떤 에디터에서든 재사용하는 것입니다.
  • 에이전트가 LSP를 직접 호출하면 더 빠르고 결정적인 결과를 얻고, 토큰 소모도 줄일 수 있습니다.
  • 앞으로는 Cursor와 VS Code의 Agents 뷰에서 에이전트가 LSP를 직접 호출해 코드를 작성하는 흐름까지 열릴 예정이라고 합니다.
  • 터미널 기반 에이전트(Claude Code, Codex 등)가 IntelliJ의 Kotlin 이해를 직접 호출하는 실험도 병행 중입니다.

1.0에서 제공하는 기능​

  • Java·Kotlin·혼합 언어 프로젝트를 지원합니다.
  • 스마트 완성, 이동, 코드 분석과 리팩터링을 제공합니다.
  • Maven, Gradle, Bazel 빌드를 지원합니다.
  • 대규모 프로젝트와 모노레포에서도 빠른 성능을 냅니다.
  • JUnit 테스트 러너를 제공합니다.
  • 에뮬레이트 브레이크포인트와 비동기 스택 트레이스를 지원하는 디버깅을 제공합니다.
  • Cursor에서는 Agents Window 전용 지원이 있습니다. 에이전트 윈도우가 자체 Language Server 인스턴스를 띄워 IntelliJ 인스펙션 기반 분석(JSpecify 널러빌리티, Spring 특화 분석 포함)을 수행합니다.

라이선스​

  • 프리뷰 기간의 무료가 끝나고 라이선스가 유료로 전환됐습니다.
  • 30일 평가판을 지나면 IntelliJ IDEA Ultimate 구독이 필요합니다.
  • 같은 라이선스로 데스크톱 IDE와 VS Code 계열 에디터를 모두 커버합니다.
  • 공지에서 흥미로운 대목이 하나 있습니다. 이 라이선스는 인간 사용을 전제로 설계됐으며, 순수 에이전트 용도(purely agentic use)의 라이선스 모델은 별도로 발표하겠다고 했습니다.

권장 설정​

  • 설치는 Visual Studio Marketplace 또는 Open VSX Registry에서 합니다.
  • Red Hat과 Oracle의 Java 확장과 분석 기능이 겹치므로, JetBrains는 해당 확장을 끄고 쓸 것을 권장합니다.
// .vscode/settings.json — JetBrains 확장과 함께 쓸 때 권장 설정
{
  // Red Hat Java 확장과 분석이 중복되므로 비활성화 (정확한 ID는 설치 목록에서 확인)
  // "redhat.java" 확장을 끄고 "Java and Kotlin by IntelliJ IDEA"만 켭니다.
}
  • 팀 위키에 "Kotlin 분석은 JetBrains 확장으로 통일"이라는 한 줄만 적어둬도 온보딩 혼란이 줄어듭니다.

실무에서 주의할 점​

  • 기존 Java 확장과 충돌합니다. Red Hat의 Java 확장을 켠 채로 쓰면 분석 결과가 중복되거나 엇갈립니다. 조직 단위로 도입한다면 settings 수준에서 비활성화 정책을 같이 배포하는 것이 좋습니다.
  • 10주 동안 무료 프리뷰로 쓰던 팀이 있다면 이제 구독 비용을 예산에 넣어야 합니다. 개인 취미용으로 Cursor에서 Kotlin을 건드리던 개발자에게는 다소 부담스러운 가격 정책입니다. 다만 이미 Ultimate를 쓰는 개발자에게는 추가 비용 없이 에디터 선택지가 늘어나는 셈입니다.
  • 빌드 서버나 CI 에이전트에 이 확장을 깔아 코드 분석을 돌릴 계획이라면, 순수 에이전트 용도 라이선스 모델이 발표될 때까지 기다렸다가 확인하는 쪽이 안전합니다.
  • Android 개발자 입장에서는 주 에디터가 Android Studio라 당장 바꿀 이유는 없습니다. 다만 공유 Kotlin 모듈(멀티플랫폼 common 코드, 서버 코드)을 Cursor나 VS Code에서 만지는 일이 있다면, 이제 IDE 기능이 떨어진다는 이유로 IntelliJ를 따로 열 필요가 없어집니다.
  • Gradle과 Bazel 기반 프로젝트를 자동으로 임포트하므로, 기존 IntelliJ 프로젝트를 VS Code에서 여는 마이그레이션 비용은 낮은 편입니다.

마치며​

에디터마다 달랐던 Kotlin 분석 품질이 하나의 엔진으로 통일되는 흐름입니다.
이미 IntelliJ IDEA Ultimate를 구독 중이라면, 추가 비용 없이 VS Code와 Cursor에서도 같은 분석 환경을 구성할 수 있습니다.

Kotlin Toolchain 0.13 — 새 KMP 프로젝트는 kotlin new로 시작하기

October 8, 2026 · 3 min read
Way
Android Developer

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.
JetBrains가 공개한 Kotlin Toolchain 0.13에 대해 설명해드리겠습니다.

배경​

신규 Kotlin Multiplatform(KMP) 프로젝트를 시작할 때는 Gradle 설정 파일을 손으로 짜는 것부터 시작하는 경우가 많았습니다.
JDK나 Android SDK 같은 필수 도구가 갖춰져 있지 않으면, 새 노트북에서 프로젝트를 처음 열었을 때 동기화부터 실패하곤 했습니다.
이번 0.13부터 JetBrains는 신규 KMP 프로젝트에 이 툴체인을 쓰는 것을 공식 권장 경로로 제시했습니다.
자세한 내용은 Kotlin 블로그 원문에서 확인할 수 있습니다.

Kotlin Toolchain 살펴보기​

Kotlin Toolchain은 JVM·Android·iOS·멀티플랫폼·서버 앱을 하나의 CLI 진입점으로 만들고, 빌드하고, 테스트하고, 배포하는 도구입니다.
필수 도구들을 선언적 설정에 맞춰 자동으로 내려받아 주기 때문에 온보딩 과정의 마찰이 크게 줄어듭니다.

kotlin new: 대화형 프로젝트 생성​

0.13의 핵심은 kotlin new 명령입니다.
웹의 KMP Wizard처럼 앱 유형을 고르고 타깃 플랫폼을 선택하면 프로젝트가 생성됩니다.
기존 kotlin init도 같은 흐름으로 맞췄는데, 차이는 kotlin init이 현재 디렉터리에 바로 파일을 만든다는 점입니다.

# 새 프로젝트 생성 (대화형)
kotlin new

# 이미 설치돼 있다면 업데이트
kotlin update

Android 개발자 관점에서 달라진 부분​

  • Android SDK 자동 프로비저닝이 IDE까지 확장: 이전에는 kotlin build/kotlin run 때만 SDK가 자동 설치돼서, 빌드 전에 IDE로 먼저 열면 SDK 누락 오류가 났습니다. 이제 프로젝트 import 시점에도 누락된 SDK 컴포넌트를 자동으로 받아 줍니다.
  • namespace/applicationId 검증 강화: com.example.app 같은 샘플 ID로 실수로 배포 빌드를 만드는 실수를 막아 줍니다.
  • 다운로드 진행 표시: JDK, Android SDK, iOS 런타임, 컴파일러 다운로드가 CLI에 진행 바로 표시됩니다.

Swift Package Manager 의존성 지원​

Apple 타깃에서 SPM 패키지를 선언적으로 가져올 수 있게 됐습니다.
설정 파일에 저장소와 버전을 적으면 됩니다.

dependencies:
  - swiftPackage:
      repository: "https://github.com/firebase/firebase-ios-sdk.git"
      version: "12.17.0"
      products: ["FirebaseCore", "FirebaseFirestore", "FirebaseAnalytics"]

가져온 Objective-C API는 swiftPMImport 접두사로 네임스페이스가 붙어, Kotlin 코드에서 명시적으로 구분됩니다.
로컬 SPM 패키지는 localSwiftPackage 키로 연결할 수 있습니다.

빌드 속도: Kotlin/Native 컴파일러 캐시​

Kotlin/Native 재빌드가 빨라집니다.
컴파일된 네이티브 의존성을 빌드 간, 심지어 프로젝트 간에 캐시로 재사용하고, 프로젝트 코드는 파일 단위 캐시로 링크 시 바뀐 부분만 다시 컴파일합니다.
기존 settings.kotlin.compileIncrementally 설정을 그대로 쓰고, .klib 컴파일 자체는 전체로 수행됩니다.

그 외 변경 사항​

  • IDE 동기화 상태를 에디터에서 확인할 수 있게 됐습니다.
  • 멀티플랫폼 라이브러리 배포 시 Compose Resources와 SwiftPM 의존성 메타데이터가 아티팩트와 함께 게시되고, 서드파티 멀티플랫폼 라이브러리의 Compose Resources도 해석됩니다.
  • AI 에이전트 연동도 강화됐습니다. Compose Hot Reload MCP 서버와 Kotlin용 에이전트 스킬(npx skills add kotlin/kotlin-agent-skills)이 제공됩니다.
  • IDE 기능은 IntelliJ IDEA 2026.2.3 또는 Android Studio Rabbit 1(2026.2.1) 이상에서 최신 Kotlin Toolchain 플러그인과 함께 쓸 수 있습니다.

실무에서 주의할 점​

기존 Gradle 기반 프로젝트를 당장 마이그레이션해야 하는 것은 아닙니다.
JetBrains도 로드맵에서 Gradle 프로젝트의 공백을 먼저 메우는 데 집중하겠다고 밝혔습니다.
따라서 운영 중인 프로젝트는 기존 흐름을 유지하고, 신규 프로젝트나 사이드 프로젝트부터 적용해 보는 것이 안전합니다.

마치며​

새로 KMP를 시작한다면 kotlin new 한 번으로 Android·iOS 환경을 한 번에 맞추는 경험은 꽤 매력적입니다.
다음에 KMP 프로젝트를 시작할 일이 있으면 이 경로로 시작해 보시기 바랍니다.

안드로이드 개발자에게 열린 Gemini 4 Argon — 자가 복구 빌드와 AGSL 셰이더

October 15, 2026 · 4 min read
Way
Android Developer

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.
안드로이드 개발자에게 개방된 Gemini 4 Argon에 대해 설명해드리겠습니다.

배경​

구글은 10월 13일 Android Developers Blog에서 최신 플래그십 모델 Gemini 4 Argon을 안드로이드 개발 표면에 개방한다고 발표했습니다.
자세한 내용은 원문 글(Jason Buchel)에서 확인할 수 있습니다.
지난주에 다뤘던 Android CLI와 디바이스 스트리밍, BYOA(원하는 에이전트 쓰기) 흐름의 연장선에 있는 발표입니다.
모델 자체보다 에이전트가 빌드를 스스로 고치고 셰이더까지 작성한다는 부분에 주목할 필요가 있습니다.

Gemini 4 Argon 살펴보기​

접근 경로​

  • Google Antigravity에서 사용할 수 있습니다. AI Ultra 구독이 전제이고, 데스크톱 앱·CLI·Android Studio Canary 안에 포함됩니다.
  • Android Studio에서는 Gemini API 유료 티어로 사용할 수 있습니다.
  • Google AI Studio의 Playground와 Build에서도 사용할 수 있습니다. AI Ultra 또는 Gemini API 유료 티어가 필요합니다.
  • 클라이언트 인앱 AI는 Firebase AI Logic 경유로 제공됩니다. Gemini API 유료 티어 개발자가 앱 안에서 Gemini 4 Argon을 직접 쓸 수 있습니다.

Self-Healing Build Loops​

  • 빌드 실패 시 Antigravity 하네스가 Gradle 데몬과 Kotlin 컴파일러 로그를 모델에 그대로 피드백합니다.
  • 모델은 근본 원인을 반복 진단해 수정안을 냅니다.
  • 편집 라운드마다 가설을 일관되게 유지하고 AST 인지를 활용해 표면 증상이 아닌 진짜 원인에 도달하도록 훈련되었다는 설명입니다.
  • 지금까지의 에이전트 코딩이 코드 자동완성의 연장에 가까웠다면, 이번 방향은 빌드 → 실패 로그 수집 → 원인 진단 → 수정 → 재빌드를 하네스와 모델이 돌리는 클로즈드 루프 실행입니다.

Compose 셰이더 생성​

  • AGSL(Android Graphics Shading Language)을 Compose Modifier.graphicsLayer나 셰이더 브러시에 직접 작성합니다.
  • 120fps Compose 애니메이션과 함께 도는 경량 GPU 셰이더를 생성합니다. 프로스트드 글래스, 동적 조명, 파문 같은 효과가 예시입니다.
  • 벡터·렌더링 수학까지 처리해 뽑아낸다고 합니다.
  • Compose 셰이더는 AGSL 문법과 렌더링 수학, 성능 예산 때문에 실무에서 진입 장벽이 높은 영역입니다.

터미널 에이전트 연결​

  • 터미널 에이전트 연결은 공식 Android CLI 플러그인이 맡습니다.
  • android init 한 줄이면 어떤 터미널 에이전트든 로컬 Android 도구와 연결됩니다.
  • Antigravity라면 플러그인 설치로 끝납니다.

실무에서 주의할 점​

빌드 로그가 곧 에이전트의 입력입니다.
Self-Healing이 동작하려면 빌드 실패 로그가 잘 읽혀야 합니다.
난독화된 멀티모듈 빌드에서 에이전트가 원인에 닿으려면, 지금부터라도 Gradle 빌드 스크립트와 에러 메시지를 사람이 읽을 수 있게 정리해 두는 것이 이득입니다.
비용 구조도 확인해야 합니다.
Antigravity는 AI Ultra 구독 전제이고, API 경로는 Gemini API 유료 티어 전제입니다.

SQL LIKE '%검색어%'가 앱을 느리게 한다 — Room @Fts4로 검색 9.4배 빠르게

October 15, 2026 · 4 min read
Way
Android Developer

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.
최근 ProAndroidDev에 소개된 Room @Fts4 기반 검색 최적화 사례에 대해 설명해드리겠습니다.

배경​

종목 메모, 공지 목록, 최근 본 상품 같은 오프라인 검색을 로컬 DB의 LIKE '%쿼리%'로 구현하는 경우가 많습니다.
개발 중에는 더미 데이터가 몇십 건 수준이라 0.1초도 걸리지 않아 그대로 넘어가기 쉽습니다.
Scaling Android Search: Room @Fts4 vs SQL LIKE에서는 이 방식을 실측 수치로 비교합니다.
5,000건 기준으로 LIKE는 63.8ms, FTS4는 6.8ms가 걸려 9.4배의 차이가 났습니다.

Room @Fts4 살펴보기​

왜 LIKE가 느린지​

  • B-Tree 인덱스는 접두사를 알 때만 사용할 수 있습니다.
  • WHERE sender LIKE 'alice%'는 인덱스를 타지만, 실제 검색 UI는 중간 매칭이 필요해 WHERE body LIKE '%architecture%' 형태가 됩니다.
  • 검색어 앞에 %를 붙이는 순간 인덱스는 무력화되고 전체 테이블 스캔으로 떨어집니다.
  • 실측에서는 2,000건만 돼도 LIKE가 약 30ms로 60Hz 프레임 예산인 16.6ms를 훌쩍 넘겼습니다.
  • 또한 LIKE는 단어 경계를 모르고("cat" 검색에 "catalog", "scatter"까지 걸립니다), 어간 추출이 안 되며("optimize"로 "optimized"를 못 찾습니다), 관련도 순위도 없습니다.

FTS4와 역인덱스​

  • FTS4는 쿼리 시점이 아니라 INSERT 시점에 일을 합니다.
  • 토크나이저가 텍스트를 단어로 쪼개고 대소문자를 정규화해, "단어 → 문서 ID 목록" 형태의 역인덱스를 만듭니다.
Token        | DocIDs (Posting List)
architecture | [1, 14, 108, 492]
benchmark    | [1, 7, 22, 108, 305]
  • MATCH 'benchmark*' 같은 쿼리가 들어오면 토큰 딕셔너리에서 단어를 찾아 docid 목록을 바로 뽑아냅니다.
  • 관계없는 텍스트는 한 바이트도 읽지 않으므로, 행이 100개든 10만 개든 조회는 밀리초 단위로 끝납니다.

contentEntity 패턴​

  • 원본 테이블은 그대로 두고, 검색용 FTS 가상 테이블을 contentEntity로 붙이는 패턴이 표준입니다.
@Entity(tableName = "notices")
data class NoticeEntity(
    @PrimaryKey(autoGenerate = true) val id: Long = 0,
    val title: String,
    val body: String,
    val pinned: Boolean = false,
)

@Entity(tableName = "notices_fts")
@Fts4(contentEntity = NoticeEntity::class)
data class NoticeFtsEntity(
    val title: String,
    val body: String,
)
  • contentEntity를 지정하면 FTS 테이블은 역인덱스 구조만 갖고, 실제 텍스트는 원본 notices 테이블에서 가져오므로 데이터 중복이 없습니다.
  • Room이 AFTER INSERT/UPDATE/DELETE 트리거를 자동 생성해서, 원본에 쓰기만 하면 인덱스가 자동으로 반영됩니다.
  • DAO에서는 docid로 조인해 MATCH를 사용합니다.
@Dao
interface NoticeDao {
    @Query("""
        SELECT notices.* FROM notices
        JOIN notices_fts ON notices.id = notices_fts.docid
        WHERE notices_fts MATCH :query
        ORDER BY notices.pinned DESC
    """)
    suspend fun searchNoticesFts(query: String): List<NoticeEntity>
}
  • 기존 테이블에 FTS를 붙이는 작업은 DB 버전 업과 AutoMigration 또는 수동 마이그레이션으로 처리합니다.
  • 가상 테이블은 원본 스키마 변경과 독립적이라 마이그레이션 부담도 크지 않습니다.

실무에서 주의할 점​

  • LIKE는 프로토타입용입니다. 메시지, 문서, 메모, 상품 카탈로그처럼 사람이 입력하는 텍스트 검색이라면 데이터가 수천 건으로 자라기 전에 FTS로 옮기는 것이 맞습니다.
  • 쓰기 비용은 있습니다. FTS 테이블은 INSERT와 UPDATE 때마다 인덱스를 갱신하므로, 쓰기가 빈번하고 읽기가 드문 워크로드라면 이득이 줄어듭니다.
  • 쿼리 위생이 필수입니다. MATCH에 사용자 입력을 그대로 넣으면 따옴표 같은 특수문자가 쿼리 문법을 깨뜨립니다. 입력에서 따옴표를 제거하고, as-you-type 검색을 위해 토큰마다 접미사 *를 붙이는 sanitize 함수를 따로 두어야 합니다.
// "삼성 전자" -> "삼성* 전자*" : 토큰별 접두사 매칭으로 자동완성 느낌의 검색
fun sanitizeFtsQuery(raw: String): String =
    raw.replace("\"", "").replace("'", "").trim()
        .split("\\s+".toRegex())
        .filter { it.isNotEmpty() }
        .joinToString(" ") { "$it*" }
  • 한국어는 토크나이저를 골라야 합니다. FTS4 기본 토크나이저(simple)는 공백 기준이라 한국어 조사가 붙은 단어("검색어를")는 토큰 하나가 됩니다. 영어 위주 앱이 아니라면 unicode61 계열 토크나이저로 바꾸거나, 형태소 분석이 필요하면 별도 토크나이저를 검토해야 합니다. Porter stemmer도 영어용이라는 점을 잊지 마시기 바랍니다.

마치며​

검색 속도는 데이터가 쌓인 뒤에 손대면 마이그레이션 비용까지 함께 커집니다.
검색 대상이 텍스트이고 건수가 늘어날 구조라면, 처음부터 @Fts4와 contentEntity 패턴으로 시작하는 편이 유지보수에 유리합니다.

Compose에서 Flow 수집의 진화 — collectAsState()에서 collectAsStateWithLifecycle()까지

October 14, 2026 · 2 min read
Way
Android Developer

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.
Compose에서 Flow를 수집하는 API가 어떻게 진화해 왔는지 설명해드리겠습니다.

배경​

Compose에서 UI 상태는 주로 Flow로 노출되고, 화면에서는 이를 State로 변환해 수집합니다.
문제는 수집 API가 라이프사이클을 모르면 액티비티가 백그라운드로 가도 수집이 계속된다는 점입니다.
실무에서는 여전히 collectAsState()를 관성으로 쓰는 코드가 많습니다.
10월 ProAndroidDev에 올라온 The Evolution of Flow Collection in Jetpack Compose 글(chanzmao)이 이 진화 과정을 정리했습니다.

Flow 수집 API의 진화​

1단계: collectAsState()​

  • Compose 1.0(2021년 7월)에 도입된 가장 단순한 수집 방법입니다.
  • Flow를 State로 바꾸고, 새 값이 emit될 때마다 관련 UI를 리컴포즈합니다.
  • 라이프사이클을 모르기 때문에 STARTED 아래로 내려가도 수집을 자동으로 멈추지 않습니다.
  • composition이 살아 있는 한 백그라운드에서도 계속 수집합니다.
val uiState by viewModel.uiState.collectAsState()

2단계: collectAsStateWithLifecycle()​

  • lifecycle-runtime-compose가 제공하는 라이프사이클 인식 API입니다.
  • 기본 minActiveState는 STARTED입니다.
  • 화면이 보이지 않으면 수집을 멈추고, 다시 보이면 재개합니다.
  • 지금의 정답에 해당하는 방법입니다.
val uiState by viewModel.uiState.collectAsStateWithLifecycle()

3단계: 일회성 이벤트는 다른 패턴으로​

  • 상태가 아니라 이벤트(네비게이션, 스낵바 등)를 소비할 때는 collectAsState 계열이 맞지 않습니다.
  • LaunchedEffect와 repeatOnLifecycle 조합을 사용합니다.
val lifecycle = LocalLifecycleOwner.current.lifecycle
LaunchedEffect(lifecycle) {
    lifecycle.repeatOnLifecycle(Lifecycle.State.STARTED) {
        viewModel.events.collect { event ->
            // 네비게이션, 스낵바 등 일회성 이벤트 처리
        }
    }
}

실무에서 주의할 점​

ViewModel의 uiState 같은 StateFlow는 collectAsStateWithLifecycle()를 기본값으로 두는 것이 안전합니다.
collectAsState()는 upstream이 가벼우면 문제가 없지만, 소켓·위치·센서처럼 비싼 작업을 하는 Flow면 백그라운드에서 리소스를 낭비합니다.
minActiveState 파라미터로 기준을 RESUMED까지 올릴 수도 있으니, 화면 요구사항에 맞게 조정해야 합니다.
SharedFlow 기반 일회성 이벤트에 collectAsState를 붙이는 실수는 여전히 흔하므로, 이벤트면 수집 패턴을 바꿔야 합니다.

마치며​

Flow 수집은 단순한 API 선택이 아니라 라이프사이클과 리소스 관리의 문제입니다.
상태는 collectAsStateWithLifecycle()로, 일회성 이벤트는 repeatOnLifecycle로 구분해 사용하는 것이 좋겠습니다.

구글북 리눅스 터미널 살펴보기​

VM 기반 격리 구조​

파일 유지와 원클릭 리셋​

  • 리눅스 파일은 구글북 파일 앱에서도 보입니다.
  • 에이전트에게 과감하게 권한을 주고, 망가지면 리셋하면 되는 구조입니다.

Kotlin 2.5.0에 companion 블록이 온다 — companion object와 무엇이 다른가

October 13, 2026 · 4 min read
Way
Android Developer

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.
Kotlin 2.5.0에 실험 기능으로 들어오는 companion 블록과 companion 확장에 대해 설명해드리겠습니다.

배경​

TAG 하나, newInstance() 하나를 선언할 때마다 companion object를 만들고 Companion 싱글턴이 따라붙는 구조가 반복되어 왔습니다.
JetBrains는 2026년 9월 30일 발표한 The Companions to Come 글에서 이 구조를 개선하는 실험 기능을 공개했습니다.
companion 블록은 companion object와 문법은 거의 같지만 컴파일 방식이 근본적으로 다릅니다.
전체 설계는 KEEP-0449 제안서에 정리되어 있습니다.

companion 블록과 확장 살펴보기​

companion 블록​

  • companion object에서 object 키워드를 뺀 형태입니다.
  • Kotlin 2.5.0-Beta1부터 실험 기능으로 사용할 수 있습니다.
  • 컴파일러 플래그 -Xcompanion-blocks(블록만) 또는 -Xcompanion-blocks-and-extensions(둘 다)를 넘겨야 합니다.
  • JVM에서는 진짜 static 멤버로 컴파일됩니다.
data class Vector(val x: Double, val y: Double) {
    companion {
        val ZERO = Vector(0.0, 0.0)
    }
}

// 사용은 똑같이
val v = Vector.ZERO

companion object는 실제 객체라서 인터페이스 구현이나 값으로 전달하는 것이 가능합니다.
반면 자바에서 호출하면 Vector.Companion.getZERO() 같은 이름이 드러나고, 리플렉션과 바이트코드 크기에도 흔적이 남습니다.
companion 블록은 컴파일 전략을 다른 플랫폼의 static 멤버처럼 바꿔서, JVM에서는 순수 static 멤버가 됩니다.

companion 확장​

  • 내가 만든 클래스가 아니어도 "클래스 멤버처럼" 선언할 수 있는 새 문법입니다.
  • Java 클래스에도 쓸 수 있고, 원래 companion object가 없어도 됩니다.
  • 라이브러리에서 내려준 클래스에 팩토리 함수를 붙이고 싶을 때, 유틸 오브젝트를 따로 만들지 않고도 SomeClass.myFactory() 형태로 붙일 수 있습니다.
companion fun Vector.unit(angle: Double) = Vector(cos(angle), sin(angle))

기존 companion object와의 관계​

  • 기존 companion object는 그대로 지원되고 강제 마이그레이션은 없습니다.
  • 인터페이스를 구현해야 하는 companion은 여전히 object만 가능합니다. 블록은 객체가 아니기 때문입니다.
  • 새 코드에서 단순 상수와 팩토리는 블록을 선호하는 방향이 되겠지만, 서두를 이유는 없습니다.

KMP와의 연결​

  • companion 블록 멤버는 KMP에서 expect로 선언할 수 있습니다.
  • Java 클래스의 static 멤버로 actualize할 수 있습니다.
  • 멀티플랫폼 라이브러리에서 플랫폼 네이티브 static API를 companion 멤버로 감싸던 패턴이 언어 차원에서 정식으로 지원됩니다.

실무에서 주의할 점​

실험 기능이므로 지금 당장 실무에 적용할 단계는 아닙니다.
특히 companion 확장을 쓴 라이브러리는 pre-release 바이너리가 되어 안정화될 때까지 의존성으로 소비할 수 없습니다.
companion 블록은 이 제한이 없지만, 소비하는 쪽도 플래그를 켜야 합니다.
사내 공통 모듈에 실험 문법을 넣으면 그 모듈을 쓰는 모든 프로젝트에 플래그가 전파됩니다.
마이그레이션할 때는 object 키워드를 지우는 것으로 대부분 충분하지만, 프로젝트와 의존하는 코드 전체를 다시 컴파일해야 합니다.
R8/ProGuard 규칙에서 Companion을 참조하던 룰이 있다면 함께 점검해야 합니다.
생태계 툴링이 아직 블록을 인식하지 못할 수 있다는 점도 발표에서 언급되었습니다.
Android 관점에서는 Activity와 Fragment의 newInstance, TAG 상수, CREATOR 같은 상용구의 바이트코드가 깔끔해집니다.
다만 DEX 메서드 수나 APK 크기에서 큰 변화는 기대하지 않는 것이 좋습니다.
실험 플래그를 켜는 방법은 다음과 같습니다.

// app/build.gradle.kts (Kotlin DSL)
kotlin {
    compilerOptions {
        // companion 블록만 허용
        freeCompilerArgs.add("-Xcompanion-blocks")
        // 블록 + 확장을 모두 허용
        // freeCompilerArgs.add("-Xcompanion-blocks-and-extensions")
    }
}
// 실험해 볼 후보 1: Fragment 팩토리
class DetailFragment : Fragment() {
    companion {
        private const val ARG_ID = "arg_id"
        fun newInstance(id: String) = DetailFragment().apply {
            arguments = bundleOf(ARG_ID to id)
        }
    }
}

// 실험해 볼 후보 2: 인터페이스 구현이 필요하면 object 유지
class AnalyticsTracker {
    companion object : EventSink {  // 블록으로는 안 됨
        override fun sink(event: Event) { /* ... */ }
    }
}

마치며​

companion 블록은 겉보기에는 object 한 단어 차이이지만, 바이트코드 관점에서는 static 멤버로 컴파일되는 큰 변화입니다.
실험 기능인 만큼 테스트 모듈에서 먼저 확인하고, 안정화 이후에 새 코드부터 적용하는 것이 좋겠습니다.

Remote Compose 1.0.0-alpha21 — 10월 AndroidX 릴리스에서 본 서버 구동 UI의 현재 위치

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.
최근 공개된 Remote Compose 1.0.0-alpha21을 중심으로 10월 AndroidX 릴리스를 설명해드리겠습니다.

배경​

2026년 10월 7일, AndroidX 정기 릴리스 배치가 나왔습니다.
그중에서도 눈에 띄는 건 remote-compose 1.0.0-alpha21과 compose.remote.foundation 1.0.0-alpha04입니다.
Remote Compose는 서버 구동 UI(Server-Driven UI)를 위한 Jetpack 라이브러리이며, 에이전트가 만든 UI를 앱 업데이트 없이 내려받아 그리는 흐름과 맞닿아 있습니다.
같은 배치의 Compose 1.13.0-beta01은 이제 Kotlin 2.2를 타깃으로 하며 kotlinc 2.2를 요구합니다.
appfunctions 1.0.0-alpha13은 API 리네임이 있어, AppFunction 어노테이션이 AppFunctionDeclaration으로 바뀌었습니다.
collection 1.7.0 스테이블에는 ScatterMap 성능 개선과 원시 타입 리스트 정렬/이진 탐색 추가가 있습니다.

Remote Compose 1.0.0-alpha21 살펴보기​

테마 인식 원격 색상​

RemoteColor.Companion에 createThemedRemoteColor가 추가됐습니다.
서버에서 내려받은 문서가 클라이언트의 라이트/다크 테마를 따라 색상을 바꿀 수 있게 되는 것입니다.
서버 구동 UI에서 가장 자주 요구되는 다크 모드 대응을 플레이어 쪽이 해결해 주니, 문서 생성 로직에서 분기할 필요가 줄어듭니다.

텍스트 측정 API​

RemoteTextMeasurer와 rememberRemoteTextMeasurer가 새로 들어왔습니다.
Remote Compose 문서 안에서 텍스트의 실제 렌더링 크기를 잴 수 있게 된 것으로, 문서 생성 시점에 텍스트 길이에 따라 레이아웃을 조정해야 하는 경우(예: 배지, 동적 라벨) 유용합니다.
Float.rsp/RemoteFloat.rsp 확장 프로퍼티도 추가돼서 Sp 단위의 RemoteTextUnit을 리터럴이나 동적 표현식에서 바로 만들 수 있습니다.

문서 생성·미리보기 개선​

  • RemoteDocumentPreview에 profile 파라미터가 생겼습니다. 문서 버퍼를 팽창시키기 전에 설정을 조정할 수 있어, 테스트·디버깅 환경에서 문서 생성을 세밀하게 제어할 수 있습니다.
  • 플레이어와 테스트 프로파일이 DrawTextOnCircle을 지원합니다. 원형 경로에 텍스트를 그리는 연출이 이제 원격 문서에서도 깨지지 않습니다.
  • DEFLATE로 압축된 문서를 플레이어가 로드할 수 있게 됐습니다. 문서 크기가 크다면 전송량을 줄이는 방향으로 설계할 여지가 생깁니다.
  • captureSingleRemoteDocument/captureRemoteDocument의 라이프사이클과 스냅샷 처리가 다져졌고, 수집 속도가 리컴포지션을 따라가지 못할 때 업데이트가 조용히 누락되던 버그도 수정됐습니다. 서버 구동 UI에서 가끔 화면이 안 바뀌는 식의 간헐적 이슈가 줄어들 것으로 보입니다.
  • 커스텀 진입/종료 가시성 애니메이션 지원, 스프링 애니메이션의 스냅·범위 이탈 버그 수정 등 렌더링 품질 쪽도 여러 건 잡혔습니다.

compose.remote.foundation 1.0.0-alpha04​

같은 배치에 androidx.compose.remote.foundation의 새 알파가 같이 나왔습니다.
의존성은 다음과 같이 선언합니다.

dependencies {
    implementation("androidx.compose.remote.foundation:foundation:1.0.0-alpha04")
}

같이 나온 것들​

  • Compose 1.13.0-beta01 (animation/foundation/material/runtime): 이번 배치부터 라이브러리들이 Kotlin 2.2를 타깃으로 하고 kotlinc 2.2를 요구합니다. 베타를 올릴 때는 Kotlin 버전을 2.2 이상으로 올려야 컴파일이 됩니다.
  • appfunctions 1.0.0-alpha13: @AppFunction → @AppFunctionDeclaration, ObserveAppFunctionsEvent → AppFunctionsChangeEvent로 리네임됐고, 접근 레벨 제한을 위한 @AppFunctionAccessLevel이 추가됐습니다. 에이전트·Gemini 시대의 앱 기능 노출 인터페이스라 실험 중이라면 이름 바뀐 것만 확인하면 됩니다.
  • collection 1.7.0 (스테이블): toOrderedScatterSet() 확장(빈 소스에선 할당 없는 싱글턴 반환), ScatterMap.getOrPut() 최적화, Float 키 해시 충돌 개선, 원시 타입 리스트(IntList/LongList 등)에 sortWith/sortBy/binarySearch 추가. 퍼포먼스에 민감한 데이터 구조를 쓰는 팀은 별도 변경 없이 이득을 볼 수 있습니다.
  • benchmark 1.6.0-alpha01: :lockClocks 태스크가 root 없이도 고정 성능 모드를 쓸 수 있게 돼서, 더 많은 실기기에서 안정적인 마이크로벤치마크가 가능합니다. 힙 프로파일링용 MemoryProfilingConfig도 추가됐습니다.

실무에서 주의할 점​

  • Remote Compose는 아직 알파입니다. API가 바뀔 수 있다는 전제로 실험·프로토타입 수준에서 접근하는 게 맞습니다. 다만 테마 인식, 텍스트 측정, 압축 문서 로딩처럼 운영에 쓰려면 꼭 있어야 할 기능들이 차례로 들어오고 있어서, 방향성 자체는 꽤 진지하게 보입니다.
  • 에이전트 시대의 SDUI: 최근 Android CLI와 에이전트 스킬 흐름과 맞물려, 에이전트가 생성한 UI를 어떻게 앱에 그릴 것인가가 실무 질문이 되고 있습니다. Remote Compose는 그 답 중 하나입니다. 당장 도입하지 않더라도 개념과 플레이어 구조는 한 번 훑어둘 만합니다.
  • Compose 1.13 베타 + Kotlin 2.2: 컴파일러 버전 요구사항이 같이 올라간 릴리스라서, 버전만 올렸다가 빌드가 깨지는 경우가 생길 수 있습니다. 베타를 쓸 거면 libs.versions.toml의 Kotlin 버전도 함께 올립니다.
  • appfunctions 리네임: 알파 실험 중이라면 컴파일 에러가 나는 게 정상이니, 이름만 바꿔 주면 됩니다.

당장은 프로덕션 도입이 아니라 관측 모드입니다.
스프린트 사이에 작은 실험 프로젝트 하나로 Remote Compose 플레이어에 문서 하나 띄워 보는 것 정도가 적당합니다.
관전 포인트는 두 가지입니다.

  1. 서버에서 보낸 문서가 다크 테마에서 깨지지 않는지 (createThemedRemoteColor 사용)
  2. 텍스트 길이 가변적인 배지 UI를 RemoteTextMeasurer로 제대로 그릴 수 있는지
// gradle/libs.versions.toml
[versions]
androidxRemoteCompose = "1.0.0-alpha21"
composeRemoteFoundation = "1.0.0-alpha04"

에이전트가 UI를 만드는 시대가 오고 있는데, 어떻게 그릴 것인가는 여전히 앱 개발자의 몫입니다.
Remote Compose가 그 몫을 나눠 가질 후보 중 하나라는 점에서, 이번 릴리스는 지켜볼 가치가 있습니다.

마치며​

10월 AndroidX 배치는 UI를 코드가 아니라 문서로 다루는 쪽으로 축이 이동하고 있음을 보여줍니다.
Remote Compose 알파21의 변경점 대부분이 렌더링 품질과 운영 편의(테마, 압축, 측정)에 집중돼 있다는 점이 그 신호이며, 다음에 SDUI를 고민할 때 선택지에 넣어두기 좋은 타이밍입니다.

Play 타깃 API 36 제출 차단이 현실화됐다 — 11월 1일 연장 신청과 대응 체크리스트

October 12, 2026 · 5 min read
Way
Android Developer

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.
Google Play 타깃 API 36 요구사항과 대응 체크리스트를 설명해드리겠습니다.

배경​

2026년 8월 31일을 기점으로, Google Play에 제출되는 신규 앱과 앱 업데이트는 Android 16(API 36) 타깃이 필수 조건이 됐습니다.
경고로 끝나는 줄 알았던 마감일이 이제는 실제로 업로드를 막는 단계에 들어왔습니다.
한 줄짜리 크래시 핫픽스도 targetSdk를 36으로 올리기 전까지는 콘솔에 올라가지 않습니다.
이미 스토어에 있는 앱은 API 35 이상을 타깃해야 타깃보다 높은 OS를 쓰는 신규 사용자에게 계속 노출됩니다.
API 34 이하에 머물면 신규 사용자 설치가 조용히 막힙니다.
아직 대응 전이라면 11월 1일까지 한 번의 연장을 신청할 수 있는데, 이것도 자동으로 주어지는 건 아닙니다.

타깃 API 요구사항 살펴보기​

자세한 기준은 Google Play의 타깃 API 레벨 요구사항에서 확인할 수 있습니다.

규칙은 제출 시점에 막는다​

이 요구사항의 포인트는 심사가 아니라 제출 단계에서 걸린다는 점입니다.
Play Console에 AAB를 올리는 순간 타깃 API 검사가 먼저 돌아가고, 조건을 못 맞추면 업로드 자체가 거부됩니다.
즉, 심사 지연이 아니라 아예 리뷰 대기열에 들어가지도 못합니다.
한참 전에 만들어 둔 빌드를 그냥 올리려던 팀은 여기서 바로 발목이 잡힙니다.

세 가지 상태, 세 가지 기준​

Google의 타깃 API 정책은 앱의 상태를 이렇게 구분합니다.

앱 상태적용 기준
신규 앱(아직 게시 안 됨)첫 제출부터 API 36 이상 (휴대폰·태블릿·폴더블 기준)
기존 앱의 업데이트 제출대체 버전 제출 시 API 36 이상
기존 앱(업데이트 안 함)API 35 이상이어야 신규 사용자에게 노출 유지

여기서 착각하기 쉬운 부분이 있습니다.
업데이트를 한 번이라도 제출하면 그 순간부터 신규 앱과 같은 API 36 기준이 적용됩니다.
API 35는 아무것도 안 하고 놔둬도 스토어에서 사라지지는 않게 해주는 완충선일 뿐, 업데이트 면제권이 아닙니다.
참고로 Wear OS·Android Automotive는 API 35, Android TV·Android XR은 API 34가 기준입니다.

연장 신청: 11월 1일까지, 한 번​

Play Console에서 해당 앱의 타깃 API 경고 화면으로 들어가면 연장 신청 양식을 찾을 수 있습니다.
신청이 받아들여지면 기한이 2026년 11월 1일로 미뤄집니다.
중요한 건 이 연장이 자동도 아니고 반복도 안 된다는 점입니다.
11월 1일 이후에는 다시 기준이 원상복귀됩니다.
신청 안 하고 버티면 하루라도 늦은 날부터 제출이 막히니, 대응 일정이 빠듯하다면 일단 신청부터 해두고 개발을 진행하는 게 합리적입니다.

실무에서 주의할 점​

  • 숫자 바꾸는 건 1분, 동작 변경 대응이 본게임: 2026년 10월 초에 세 개 앱을 API 36으로 올린 개발자의 회고에 따르면, build.gradle.kts의 숫자 변경은 1분이면 되지만 이후 작업에 이틀이 걸렸다고 합니다. Android 16에서는 엣지 투 엣지(Edge-to-Edge)가 의무화되고, 태블릿·폴더블에서는 방향 고정(orientation lock)이 무시되는 등 실제 동작이 바뀌는 지점이 있습니다. UI가 화면 끝까지 그려지는지, 인셋 처리가 깨지지 않는지 확인이 필요합니다.
  • API 34 이하에 머무르면 "조용히" 죽는다: 앱이 스토어에서 갑자기 삭제되는 게 아니라, 타깃보다 높은 OS 버전을 쓰는 신규 사용자에게만 노출이 중단됩니다. 설치율이 이유 없이 떨어지는 것처럼 보이기 때문에, 모니터링만 보고 있으면 원인 파악이 늦어집니다. 우리 앱의 현재 targetSdk를 Play Console 앱 대시보드에서 먼저 확인해 보세요.
  • 연장은 계획이 아니다: 연장을 신청하면 6주 남짓의 시간을 버는 것뿐이고, 작업량은 그대로입니다. 연장 승인이 났다는 이유로 회귀 테스트를 줄이면 나중에 더 아픕니다.
  • 연관 게이트도 같이 확인: 같은 시기, Play Billing을 쓰는 앱은 Billing Library 8.0.0 이상이 동반 요구되고, 네이티브 코드를 포함하는 앱은 2027년 2월 1일부터 16 KB 페이지 사이즈 지원 없이는 업로드가 거부됩니다. targetSdk 올릴 때 같이 점검하면 일정을 한 번으로 합칠 수 있습니다.

대응 순서는 다음과 같습니다.
급한 순서대로 정리한 체크리스트입니다.

// app/build.gradle.kts (Kotlin DSL)
android {
    compileSdk = 36
    defaultConfig {
        minSdk = 24
        targetSdk = 36   // ← 이 숫자. 8월 31일 이후 제출 조건
    }
}
  1. Play Console → 해당 앱 → 정책/타깃 API 경고 화면에서 현재 상태 확인
  2. 아직 36이 아니면 연장 신청 폼부터 제출 (11월 1일까지, 한 번)
  3. compileSdk/targetSdk 36으로 올리고 엣지 투 엣지·인셋·방향 처리 회귀 테스트
  4. Billing Library 버전(8.0.0+)과 16 KB 페이지 사이즈 대응 여부도 같은 패스에 확인

템플릿이나 프레임워크가 아직 35를 기본값으로 쓰고 있는 경우가 많으니, 신규 프로젝트라면 프로젝트 생성 직후 이 숫자부터 확인하는 습관을 들이는 게 좋습니다.

마치며​

타깃 API 마감일은 매년 오는 행사지만, 올해는 제출 차단이라는 점에서 체감 강도가 다릅니다.
특히 API 34 이하에 머무는 앱은 신규 사용자 노출이 조용히 막히기 때문에, 별다른 이상 없이 설치 지표가 떨어지는 상황이면 targetSdk를 먼저 의심해 보길 권합니다.

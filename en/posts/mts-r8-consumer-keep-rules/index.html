R8 Consumer Keep Rules 살펴보기 — DEX 코드 최적화와 라이브러리 규칙 정리

November 22, 2026 · 6 min read
Way
Android Developer

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.
2026년 11월 17일에 공개된 Ship smarter keep rules에 대해 설명해드리겠습니다.

배경​

R8은 Android 앱 최적화 도구입니다.
사용하지 않는 코드를 제거하고, 남은 코드를 최적화하고 난독화합니다.
Google Play는 2027년 2월부터 DEX 코드 최적화 기준을 적용합니다.
DEX 코드가 10MB를 초과하는 앱은 난독화와 최적화, 축소 지표가 각각 25% 이상이어야 합니다.
기준에 미치지 못하면 앱 노출과 게시 기능에 영향을 받을 수 있습니다.
이 기준은 앱만의 문제가 아닙니다.
R8은 주어진 규칙 안에서만 최적화할 수 있습니다.
규칙에는 앱이 의존하는 라이브러리에 포함된 규칙도 들어갑니다.
국내 MTS처럼 규모가 큰 앱은 서드파티 SDK를 많이 사용합니다.
라이브러리가 넓은 규칙을 함께 보내면 앱 전체의 최적화 여지가 줄어듭니다.

R8 Consumer Keep Rules 살펴보기​

Consumer Keep Rules란​

Consumer Keep Rules는 라이브러리 안에 포함된 규칙입니다.
앱 수준 컴파일 과정에서 R8이 최적화하지 말아야 할 부분을 지정합니다.
리플렉션 대상과 네이티브 인터페이스가 제거되지 않도록 보호하는 역할을 합니다.
앱 개발자가 직접 규칙을 찾지 않아도 라이브러리를 그대로 쓸 수 있습니다.
의도적으로 좁게 작성된 규칙은 라이브러리와 앱 모두에 도움이 됩니다.
반대로 넓은 규칙은 사용하지 않는 코드까지 남겨 앱 성능에 영향을 줍니다.
Play Console에 추가된 DEX 코드 최적화 지표는 앱과 라이브러리 규칙의 합산 영향을 보여줍니다.

넓은 규칙이 문제가 되는 이유​

라이브러리 제공자는 SDK가 리플렉션으로 인한 충돌을 일으키지 않기를 바랍니다.
그래서 패키지 전체를 보존하는 넓은 규칙을 넣는 경우가 많습니다.
그러나 넓은 규칙은 R8의 전체 프로그램 최적화를 크게 제한합니다.
시작 시간과 다운로드 크기, 메모리 사용량, ANR 발생률에 영향을 줍니다.
성능을 중시하는 앱은 라이브러리 규칙을 직접 대체하는 규칙을 작성하기도 합니다.
이 경우 라이브러리 업데이트를 받아들이기 어려워지는 부작용도 생깁니다.

진입점만 보호하는 좁은 규칙​

리플렉션을 피할 수 없다면, 규칙은 실제로 리플렉션으로 접근하는 진입점만 지정하면 됩니다.
R8은 진입점을 기준으로 참조 그래프를 만들고, 참조되지 않는 클래스와 메서드, 필드를 제거합니다.
라이브러리를 이미 최적화하거나 난독화한 경우에도 같은 원칙이 적용됩니다.
앱 컴파일 단계에서 R8이 실제 사용되는 부분을 기준으로 다시 최적화하기 때문입니다.
서드파티 의존성에 대한 규칙도 좁게 작성해야 합니다.
대표적인 넓은 규칙 예시는 다음과 같습니다.

-keep public class com.google.android.gms.** { *; }

이 규칙은 앱이 다른 GMS 라이브러리에 대해 좁은 규칙을 갖고 있어도 이를 덮어씁니다.
많은 라이브러리가 이미 자체 Consumer Keep Rules를 제공하므로, 패키지 단위 규칙은 그 규칙까지 무력화할 수 있습니다.

리플렉션 대신 코드 생성 사용하기​

리플렉션은 컴파일 시점에 R8이 코드 사용 여부를 알 수 없게 만듭니다.
그래서 충돌을 막으려면 Keep Rules가 필요합니다.
가능하면 코드 생성을 사용하는 것이 좋습니다.
직렬화와 역직렬화, 의존성 주입이 대표적인 적용 대상입니다.
Hilt는 코드 생성을 사용하는 라이브러리입니다.
다만 모든 경우에 코드 생성이 맞는 것은 아닙니다.
선택적 의존성처럼 리플렉션이 필요한 패턴도 있습니다.
이 경우에는 필요한 진입점만 보호하는 좁은 규칙과 함께 사용합니다.

Jetpack Keep 어노테이션으로 규칙 생성하기​

Jetpack Keep 어노테이션은 현재 알파 단계입니다.
리플렉션 사용 위치에 어노테이션을 붙이면 빌드 시점에 Keep Rules를 생성합니다.
생성되는 규칙은 조건부 규칙입니다.
리플렉션을 호출하는 코드가 R8에 의해 남아야만 대상도 함께 남습니다.
사용하지 않는 기능의 규칙이 앱을 비대하게 만들지 않습니다.
AGP 8.7 이상에서 사용할 수 있고, 라이브러리와 플러그인 버전은 1.0.0-alpha01입니다.
설정은 libs.versions.toml에 다음과 같이 추가합니다.

[versions]
annotationKeep = "1.0.0-alpha01"

[libraries]
androidx-annotation-keep = { group = "androidx.annotation.keep", name = "keep", version.ref = "annotationKeep" }

[plugins]
androidx-annotation-keep = { id = "androidx.annotation.keep", version.ref = "annotationKeep" }

리플렉션으로 생성자를 호출하는 경우에는 @UsesReflectionToConstruct 어노테이션을 사용합니다.
다음 예시는 이름으로만 아는 클래스를 생성하는 함수입니다.

@UsesReflectionToConstruct(
    className = "com.example.ResourceLocatorImpl",
    parameterTypes = [],
)
fun loadResourceLocator(): ResourceLocator {
    val implClass = Class.forName("com.example.ResourceLocatorImpl")
    return implClass.getDeclaredConstructor().newInstance() as ResourceLocator
}

Lint가 어노테이션이 없는 리플렉션 호출을 찾아주고, 상당수는 자동으로 추가할 수도 있습니다.

조건부 Keep Rules로 선택적 기능 보호하기​

광고 미디에이션 어댑터처럼 선택적으로 포함되는 모듈에는 조건부 Keep Rules를 사용합니다.
앱에 해당 어댑터가 포함된 경우에만 기능을 보존합니다.
포함되지 않은 형식과 기능은 축소 대상이 됩니다.
Jetpack Keep 어노테이션을 쓰면 이런 조건부 규칙도 자동으로 생성할 수 있습니다.

규칙은 문서가 아니라 라이브러리에 포함하기​

Consumer Keep Rules는 라이브러리와 함께 배포해야 합니다.
문서에 규칙을 적어두면 앱 개발자가 직접 추가해야 하고 유지보수 부담이 생깁니다.
라이브러리를 업데이트하면서 클래스 이름이나 리플렉션 사용 방식이 바뀌면 문서도 함께 바꿔야 합니다.
버전을 거듭하면 앱에 더 이상 필요 없는 규칙이 쌓여 코드가 비대해집니다.

R8 Configuration Analyzer로 규칙 점검하기​

샘플 앱에서 R8을 활성화하고 핵심 사용자 여정을 테스트합니다.
R8 Configuration Analyzer는 축소와 최적화, 난독화 점수를 보여줍니다.
앱뿐 아니라 라이브러리에서 온 비효율적인 규칙도 함께 확인할 수 있습니다.
AGP 9.3 이상에서는 다음 태스크로 보고서를 만들 수 있습니다.

./gradlew :app:analyzeReleaseR8Config

보고서는 app/build/reports/r8/r8-config-analyzer-release.html 경로에 생성됩니다.
Android CLI의 analyze 명령은 AAR이나 JAR의 최적화 상태를 평가합니다.
보존된 메서드와 클래스, 필드를 확인하고 릴리스마다 비교하면 회귀를 잡을 수 있습니다.

android analyze --analysis=optimization -f json library.aar

Play SDK Console에서는 라이브러리 버전 사용량과 충돌도 함께 확인합니다.

릴리스 스택 트레이스는 난독화를 풀지 않고 읽기​

난독화된 스택 트레이스를 읽기 어렵다고 해서 keepnames를 쓰는 것은 권장되지 않습니다.
keepnames는 축소는 허용하지만 이름 변경 같은 추가 최적화를 막습니다.
Firebase Crashlytics와 Play Console, Android Studio Logcat은 스택 트레이스를 자동으로 복원합니다.
매핑 파일을 SDK Console에 업로드하면 SDK Console에서도 복원된 스택 트레이스를 볼 수 있습니다.

실무 관점​

국내 MTS는 서드파티 SDK가 많은 대형 앱입니다.
DEX 코드가 10MB를 초과할 가능성이 높고, 2027년 2월 기준이 직접 적용될 수 있습니다.
먼저 Play Console의 DEX 코드 최적화 지표와 R8 Configuration Analyzer 보고서를 확인합니다.
넓은 규칙을 보내는 라이브러리가 있다면 유지보수 담당자에게 보고서 수치와 함께 전달합니다.
앱 내부 규칙도 패키지 단위가 아니라 리플렉션 진입점 단위로 좁혀 나갑니다.
AGP 9.3 이상으로 올린다면 optimization 블록과 .keep 파일 형식도 함께 검토합니다.

마치며​

DEX 코드 최적화 기준은 앱과 라이브러리가 함께 지켜야 하는 기준입니다.
Consumer Keep Rules를 좁게 유지하면 앱은 더 작고 빨라집니다.

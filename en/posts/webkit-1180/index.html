WebView에 stable API로 온 allowlist — WebKit 1.18.0 살펴보기

October 24, 2026 · 3 min read
Way
Android Developer

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.
2026년 10월 21일에 공개된 WebKit 1.18.0의 릴리스 노트를 정리해드리겠습니다.

현재 상황​

지난 글에서는 WebView v156의 cross-origin isolation allowlist 개념을 정리한 바 있습니다.
당시에는 개념과 정책 방향이 중심이었습니다.
이번에는 그 기능이 Jetpack WebKit의 stable API로 확정된 내용을 정리합니다.
MTS 앱처럼 WebView를 많이 쓰는 앱에서는 웹 콘텐츠의 성능 기능과 보안 정책을 함께 다뤄야 합니다.
SharedArrayBuffer처럼 cross-origin isolation을 요구하는 API는 그동안 전부 아니면 전무에 가까웠습니다.
1.18.0은 신뢰하는 origin만 골라 허용하는 길을 stable API로 열어줍니다.

WebKit 1.18.0 살펴보기​

cross-origin isolated allowlist API​

핵심은 Profile 수준의 API입니다.
Profile#setCrossOriginIsolatedAllowlist와 Profile#getCrossOriginIsolatedAllowlist가 stable로 제공됩니다.
allowlist에 오른 origin에서는 완전히 cross-origin isolated 상태가 아니어도 SharedArrayBuffer 같은 API를 쓸 수 있습니다.
다만 웹 페이지 쪽에서도 Document-Isolation-Policy 헤더로 적절히 옵트인해야 합니다.
앱 API만 켠다고 끝나는 기능이 아니라, 웹 측 헤더와 함께 동작하는 기능입니다.

// 이미 확보한 Profile이라고 가정합니다
if (WebViewFeature.isFeatureSupported(WebViewFeature.CROSS_ORIGIN_ISOLATED_ALLOWLIST)) {
    profile.setCrossOriginIsolatedAllowlist(
        setOf("https://trusted.example.com")
    )
}

사용 전에 반드시 기능 지원 여부를 확인해야 합니다.
지원되지 않는 단말에서 호출하면 예외가 발생합니다.
공식 API 레퍼런스에서도 사용 전 확인을 강조하고 있습니다.
또한 기본값은 비활성화 상태입니다.
WebView는 렌더러 프로세스 격리를 지원하지 않기 때문에, 이 API를 호출한다는 것은 보안 보장을 완화하겠다는 뜻이 됩니다.
그래서 신뢰하는 origin만 등록해야 하고, 와일드카드 패턴은 피해야 합니다.
이미 로드된 페이지에도 이 설정이 적용된다는 점도 염두에 두어야 합니다.

prefetch 큐 비우기 여부 확인​

WebViewFeature에 WEBVIEW_NAVIGATE_DRAIN_PREFETCH 상수가 추가되었습니다.
이 상수로 Navigation#navigate가 이동 전에 prefetch 큐를 비우는지 확인할 수 있습니다.
prefetch를 쓰는 앱에서는 이동 시점에 어떤 요청이 남는지 예측하기가 한결 쉬워집니다.
단순한 상수 추가처럼 보이지만, 동작 예측 가능성을 높이는 변경입니다.

if (WebViewFeature.isFeatureSupported(WebViewFeature.WEBVIEW_NAVIGATE_DRAIN_PREFETCH)) {
    // Navigation#navigate가 prefetch 큐를 비우는지 확인할 수 있습니다
}

API 정리와 이름 변경​

PrefetchParameters#isJavaScriptEnabled는 includeClientHints로 이름이 바뀌었습니다.
기존 메서드는 deprecated 처리되었습니다.
Profile#addQuicHints는 preferQuicFor로 이름이 바뀌었습니다.
이름만 바뀐 변경이지만, 기존 이름을 그대로 쓰던 코드가 있다면 마이그레이션 목록에 올려두어야 합니다.
deprecated 경고를 방치하면 나중에 버전 올릴 때 한꺼번에 정리해야 합니다.

의존성 선언​

[versions]
webkit = "1.18.0"

[libraries]
webkit = { module = "androidx.webkit:webkit", version.ref = "webkit" }
dependencies {
    implementation(libs.webkit)
}

실무 관점​

MTS 앱에서 WebView allowlist를 쓴다면, 등록 대상은 자사 도메인처럼 확실히 신뢰하는 origin으로 한정해야 합니다.
외부 제휴 페이지나 광고성 페이지를 넓게 허용하면, 보안 보장을 완화한 대가를 치르게 됩니다.
적용 전에는 기능 지원 여부 확인, 헤더 설정, 기존 페이지 동작을 함께 테스트하는 편이 좋습니다.
이미 로드된 페이지에도 적용되므로, 설정 시점에 따라 동작이 달라질 수 있다는 점도 테스트 항목에 넣어야 합니다.
stable 릴리스인 만큼, 기존에 쓰던 이름 변경부터 정리하고 단계적으로 적용하는 것이 안전합니다.

마치며​

이번 stable은 allowlist라는 보안 기능을 실제 API로 쓸 수 있게 만든 릴리스입니다.
신뢰하는 origin만 좁게 허용한다는 원칙만 지키면, WebView의 성능 기능을 보다 안전하게 활용할 수 있습니다.

트레이스 루트는 HTTP 호출이 아니라 비즈니스 연산이다 — KMP 모듈 OpenTelemetry 실전

October 17, 2026 · 5 min read
Way
Android Developer

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.
최근 ProAndroidDev에 소개된 KMP 모듈의 OpenTelemetry 트레이싱 적용 사례에 대해 설명해드리겠습니다.

배경​

"주문이 안 들어갔어요"라는 문의가 오면, 개발자는 주문 요청 하나를 처음부터 끝까지 추적해야 합니다.
그런데 실제 앱에서는 주문 하나가 토큰 갱신, 재시도, 여러 API 호출로 흩어져 있습니다.
각 호출의 시작과 끝 시간만 찍힌 납작한 로그로는 무엇이 무엇의 자식인지 알 수 없습니다.
Tracing Business Operations, Not HTTP Calls — Part 2는 라이브 쇼핑 앱 Tilt에서 KMP 모듈에 OpenTelemetry 분산 트레이싱을 붙인 실전 기록입니다.
2부작 중 2부로, 1부의 파이프라인 프레임워크 위에 트레이싱을 올리는 이야기입니다.

트레이싱 적용 살펴보기​

트레이스 단위는 비즈니스 연산​

  • 트레이스 단위는 HTTP 호출 1개가 아니라 비즈니스 연산 1개입니다.
  • 주문 넣기, 홈 피드 로드, 인증번호 전송 같은 연산 하나가 앱에서 시작해 마지막 백엔드 서비스까지 도달하는 단일 waterfall이 하나의 트레이스가 됩니다.
  • 레포지토리의 함수 하나는 종종 여러 쿼리와 구독을 합쳐놓습니다. GraphQL 호출 하나씩만 트레이싱하면 정확한 숫자를 틀린 것에 대해 구하게 되고, 앱 세션 전체를 트레이스로 묶으면 아무도 분석할 수 없는 거대한 트레이스가 됩니다.
  • 그래서 트레이스 루트는 경계가 있는 비즈니스 연산으로 잡아야 합니다.
  • 개발자용 API는 단순합니다. 파이프라인의 종료 지점인 buildOnce에 타입화된 연산 하나를 인자로 넘기는 것이 전부이며, 스팬을 어디서 열고 닫을지 신경 쓸 필요가 없습니다.

타입화된 연산 카탈로그​

  • 이 설계의 핵심은 타입화된 연산 카탈로그에 있습니다.
  • ShopperTracedOperation.MakeBid처럼 연산 이름과 속성(roomId, auctionId, bidValue)이 클래스 하나로 묶여 있습니다.
  • 속성 키는 상수 객체에 모아두어, 한 곳은 room_id, 다른 곳은 room.id로 쓰는 식의 조용한 Grafana 쿼리 깨짐을 막습니다.
  • 숫자 타입도 유지돼 TraceQL에서 숫자 비교가 됩니다.

SDK 격리와 결함 우회​

  • KMP SDK인 opentelemetry-kotlin은 알파 상태였습니다.
  • 글쓴이는 얇은 래퍼(Tracer, Span, SpanContext)로 SDK를 격리한 뒤, 실제 마주친 결함 3가지를 자체 코드에서 우회했습니다.
  • 오프라인 내보내기 크래시, 비-protobuf 에러 바디 크래시, 배치 스팬 프로세서의 스레드 안전성 문제가 그 대상입니다.

백엔드와의 연결​

  • 모바일에서 시작한 스팬과 백엔드 스팬은 W3C traceparent 헤더로 하나의 트레이스로 합쳐집니다.
  • 조회는 Grafana Tempo와 TraceQL로 합니다.
  • 로컬 개발용으로는 grafana/otel-lgtm 컨테이너 하나면 충분합니다.

실무에서 주의할 점​

  • 재시도는 별도 스팬으로 나눠야 합니다. 재시도 로직 위에 스팬을 열면 개별 재시도가 보이지 않습니다. 글쓴이는 Apollo 인터셉터를 재시도와 인증 아래에 둬서 물리적 요청마다 스팬을 열고, 각 요청에 traceparent를 주입했습니다.
  • 복구된 실패는 실패가 아닙니다. 재시도 성공 시 자식 스팬에는 에러가 남지만 루트 스팬은 성공입니다. 에러율 집계를 자식 스팬 기준으로 하면 모든 재시도가 오경보를 내므로, 에러율은 루트 스팬 상태 기준으로만 봐야 합니다.
  • 취소는 성공도 아닙니다. 화면을 이탈해 취소된 주문이 초기에는 트레이스 목록에서 성공처럼 보였습니다. 지금은 루트 스팬에 명시적인 cancelled 마커를 답니다.
  • 스트림은 다르게 다뤄야 합니다. 라이브 룸 같은 구독은 한 시간도 갑니다. 구독당 하나의 긴 스팬은 닫히지 않는 루트라는 세션 트레이스 안티패턴입니다. 대신 수집 시작 시 루트를 열고 첫 번째 실제 결합 상태, 즉 화면이 보여줄 데이터가 생긴 순간에 닫는 bounded root를 씁니다. 트레이싱 대상은 셋업 시간이며, emission마다 트레이스를 만들지 않는 것은 의도된 설계입니다.
  • 부모 스팬 전달은 코루틴 컨텍스트로 하지 않는 편이 좋습니다. 첫 버전은 flow 블록 안에서 withContext로 부모 스팬을 넘겼고 단위 테스트는 통과했지만, 실기기에서 "Flow invariant is violated"로 크래시했습니다. flow는 내부에서 컨텍스트를 바꿀 수 없어서, 지금은 Apollo의 ExecutionContext로 전달합니다.
  • 폰의 시계는 믿을 게 못 됩니다. 첫 E2E 트레이스에서 백엔드 스팬이 원인이 된 클라이언트 스팬보다 늦게 시작된 것처럼 보였는데, 디바이스 시계 드리프트 때문이었습니다. 앱에 있던 서버 동기화 시계를 SDK에 넘기는 방식으로 해결했습니다.
  • 알파 SDK에는 메트릭이 없습니다. SDK에 Meter 뼈대는 있지만 인스트루먼트와 내보내기가 없어서, 메트릭은 Collector의 spanmetrics 커넥터 쪽으로 넘겼습니다.
  • 운영 측면에서는 트레이싱을 앱 쪽 피처 플래그로 사용자별로 켜고, 모듈은 tracingEnabled 람다만 받습니다. 플래그는 첫 스팬 때 읽어 프로세스에 캐시하므로 트레이스 도중에 뒤집히지 않고, 엔드포인트가 없으면 트레이서는 no-op이라 SDK도 생성되지 않습니다.
  • 디바이스에서 샘플링하지 않습니다. 폰에서 샘플링하면 나중에 Collector 쪽에서 특정 사용자를 잡아내 샘플링할 수 없기 때문입니다. 볼륨은 플래그를 켠 사용자 수로 조절했고, Android부터 단계적으로 올렸습니다.
  • 두 앱은 같은 service.name으로 보고하고 플랫폼은 속성으로 둡니다. 트레이싱 대상은 거의 항상 백엔드까지 이어지기 때문입니다.
  • 알림은 페이저가 아니라 일간 다이제스트로 받습니다. 네트워크가 끊긴 한 명의 사용자가 슬로우와 행 알림을 울려 노이즈가 되기 때문입니다.

적용 예시​

한투 앱의 "주문 넣기" 연산을 트레이스 루트로 잡는다면 다음과 같이 시작할 수 있습니다.

// 1. 타입화된 연산 카탈로그 — 속성 키는 한 객체에 상수로 모은다
class PlaceOrder(accountNo: String, stockCode: String, qty: Int) :
    TracedOperation(
        name = "placeOrder",
        attributes = mapOf(
            TraceAttributes.ACCOUNT_NO to accountNo,
            TraceAttributes.STOCK_CODE to stockCode,
            TraceAttributes.QUANTITY to qty,
        ),
    )

// 2. 레포지토리 종료 지점에서 인자 하나로 옵트인 — 스팬 위치는 신경 쓰지 않는다
suspend fun placeOrder(...): Result<Order> =
    source(accountStore.account)
        .transformToSource { acct -> source(orderApi.place(acct, req)) }
        .buildOnce(TracedOperation.PlaceOrder(accountNo, stockCode, qty))

개발자가 매일 새 쿼리를 추가하는 환경이라면, 추가 가이드를 읽지 않고도 트레이스를 볼 수 있게 만드는 것이 완성 기준이 됩니다.
트레이싱 가이드를 문서화하고, 붙여넣기 바로 가능한 TraceQL 쿼리를 주는 것까지가 프로젝트의 범위에 들어갑니다.
1부의 파이프라인 프레임워크 이야기는 Everything Is a Source — Part 1에서도 확인할 수 있습니다.

마치며​

트레이싱의 단위를 HTTP 호출이 아니라 비즈니스 연산으로 잡으면, 장애 추적이 로그 뒤지기에서 waterfall 읽기로 바뀝니다.
KMP 모듈에 적용할 때도 연산 카탈로그와 속성 키 상수화부터 정리해두면, 조회 단계에서의 혼란을 크게 줄일 수 있습니다.

init { load() }을 지우는 법 — stateIn으로 ViewModel UI 상태를 선언적으로

October 17, 2026 · 4 min read
Way
Android Developer

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.
최근 ProAndroidDev에 소개된 stateIn 기반 ViewModel 상태 선언 방식에 대해 설명해드리겠습니다.

배경​

ViewModel을 열면 거의 항상 비슷한 패턴이 나옵니다.
private val _uiState = MutableStateFlow(UiState())를 선언하고, init에서 load()를 호출하고, 데이터가 오면 .update로 복사하는 방식입니다.
틀린 코드는 아닙니다. 그런데 화면이 커질수록 이 수동 동기화 코드가 어딘가에서는 반드시 어긋나기 시작합니다.
The Power of stateIn in ViewModel에서는 이 문제를 명령(command)과 상태(state)의 구분으로 풀어냅니다.

stateIn으로 상태 선언하기​

핵심 요약​

  • init에서 로드하고 수동으로 _uiState를 갱신하는 패턴은, 상태가 어떻게 도출되는지가 아니라 언제 복사했는지를 코드에 남깁니다.
  • 입력이 하나만 있을 때는 괜찮지만, 검색어와 필터와 새로고침처럼 입력이 늘어나면 동기화 누락이 생깁니다.
  • 핵심 원칙은 하나입니다. MutableStateFlow는 수정 가능한 입력에만 두고, 파생 상태는 Flow 연산자로 표현해 stateIn으로 StateFlow로 노출합니다.
  • stateIn 자체는 데이터를 가져오지 않습니다. 상류 Flow가 뱉은 값을 공유하고 유지할 뿐이며, SharingStarted.WhileSubscribed(5_000) 같은 공유 전략은 화면 생명주기에 맞춰 선택해야 합니다.

명령과 상태의 구분​

  • 명령(commands)은 무슨 일이 일어나야 하는지를 뜻합니다. "제출해라", "삭제해라", "새로고침해라"처럼 사용자의 명시적 동작에 대한 반응입니다.
  • 상태(state)는 지금 무엇이 사실인지를 뜻합니다. "보이는 목록은 items와 query로부터 도출된다"처럼 관계가 코드에 선언됩니다.
  • 문제는 명령으로 상태를 동기화하려고 할 때 생깁니다.
  • 레포지토리가 이미 val items: Flow<List<Item>>을 들고 있는데도 ViewModel이 collect 해서 _uiState에 복사하고, 쿼리가 바뀌면 또 복사하는 구조에서는, 보이는 목록을 다시 계산해야 하는 모든 장소를 사람이 기억해야 합니다.

stateIn으로 바뀌는 코드​

  • 입력은 그대로 두되, 파생 UI 상태는 연산자로 표현합니다.
class PortfolioViewModel(repository: HoldingRepository) : ViewModel() {

    // 입력: 사용자가 바꾸는 검색어 — MutableStateFlow가 맞다
    private val query = MutableStateFlow("")

    // 파생 상태: 레포지토리 데이터 + 검색어로 도출 — map/combine이 관계다
    val uiState: StateFlow<PortfolioUiState> =
        combine(repository.holdings, query) { holdings, query ->
            PortfolioUiState(
                holdings = holdings.filter { it.matches(query) },
                query = query,
            )
        }.stateIn(
            scope = viewModelScope,
            started = SharingStarted.WhileSubscribed(5_000),
            initialValue = PortfolioUiState(),
        )

    fun onQueryChanged(query: String) {
        this.query.value = query // UI 액션은 입력만 바꾼다
    }
}
  • 사라지는 것들을 세어보면 명확해집니다. 수동 _uiState, init 블록, 복사용 load(), 레포지토리와 UI 모델 사이의 수동 동기화가 모두 없어집니다.
  • UI 액션인 onQueryChanged는 uiState를 직접 건드리지 않고 입력만 바꿉니다.
  • 양쪽 입력 중 하나라도 바뀌면 파생 상태가 자동으로 갱신됩니다.

공유 전략은 생명주기를 보고 고르기​

  • WhileSubscribed(5_000)는 첫 구독자가 생기면 상류를 수집하고, 마지막 구독자가 사라진 지 5초 후에 수집이 멈춥니다.
  • 타임아웃은 화면 회전 같은 짧은 구독 공백에서 상류 스트림이 끊겼다 다시 붙는 것을 막아줍니다.
  • 단, 글쓴이가 경고하는 함정이 있습니다. 수집이 멈췄다가 재개된다고 네트워크 요청이 반드시 다시 나가는 것은 아닙니다.
  • 그 동작은 상류 Flow가 어떻게 구현됐느냐에 달렸습니다. 레포지토리의 캐시와 공유 전략이 실제 동작을 결정합니다.
  • 공유 전략은 관성처럼 쓰는 관용구가 아니라, 원하는 생명주기 동작을 보고 선택해야 합니다.

실무에서 주의할 점​

  • **LaunchedEffect(Unit) { viewModel.load() }**로 화면에 들어갈 때마다 다시 로드하는 패턴은 "명령으로 상태를 동기화"하는 전형적인 예입니다. 그 데이터가 이미 레포지토리의 Flow로 존재한다면 stateIn 파생으로 바꾸는 것이 낫습니다.
  • 명시적 명령이 정당한 경우도 있습니다. 폼 제출, 삭제, 사용자가 누른 새로고침처럼 이벤트에 대한 반응은 명령으로 두어야 합니다. 모든 것을 Flow로 감싸지 않는 것이 중요합니다. 제거 대상은 "파생 상태를 동기화하기 위한 명령"뿐입니다.
  • 테스트가 쉬워집니다. 파생 로직은 순수 함수인 map과 combine 변환이라 ViewModel 전체를 띄우지 않고도 검증할 수 있습니다.
  • SharingStarted 선택은 코드 리뷰 포인트로 남겨두는 것이 좋습니다. WhileSubscribed와 Eagerly의 차이는 상류 비용(소켓, 폴링, 가격 스트리밍)을 누가 내는가와 직결됩니다.
  • 가격 스트리밍처럼 상류가 비싼 Flow라면, 파생 전에 레포지토리 단에서 공유를 정리하는 방식이 좋습니다.
// Repository: 비싼 상류를 여기서 공유 — ViewModel은 몰라도 된다
val holdings: Flow<List<Holding>> = priceSocket.stream()
    .map(::toHoldings)
    .shareIn(
        scope = externalScope,
        started = SharingStarted.WhileSubscribed(5_000),
        replay = 1,
    )
  • 이렇게 두면 ViewModel은 combine(holdings, query) 하나로 "검색어에 맞는 보유종목"이라는 관계를 선언합니다.
  • 소켓 구독 시점과 구독 종료 시점 같은 생명주기 판단은 공유 전략 선언 한 곳에서만 일어납니다.
  • 화면이 두 개로 늘어나도 동기화 코드를 복사해 붙여넣지 않아도 됩니다.

마치며​

상태를 명령으로 동기화하는 코드를 걷어내면, ViewModel에는 입력과 도출 관계만 남습니다.
입력은 MutableStateFlow로, 파생 상태는 연산자와 stateIn으로 선언하는 기준을 팀 규칙으로 정해두면 화면이 커져도 동기화 누락을 막을 수 있습니다.

Kotlin Toolchain 0.13 — 새 KMP 프로젝트는 kotlin new로 시작하기

October 8, 2026 · 3 min read
Way
Android Developer

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.
JetBrains가 공개한 Kotlin Toolchain 0.13에 대해 설명해드리겠습니다.

배경​

신규 Kotlin Multiplatform(KMP) 프로젝트를 시작할 때는 Gradle 설정 파일을 손으로 짜는 것부터 시작하는 경우가 많았습니다.
JDK나 Android SDK 같은 필수 도구가 갖춰져 있지 않으면, 새 노트북에서 프로젝트를 처음 열었을 때 동기화부터 실패하곤 했습니다.
이번 0.13부터 JetBrains는 신규 KMP 프로젝트에 이 툴체인을 쓰는 것을 공식 권장 경로로 제시했습니다.
자세한 내용은 Kotlin 블로그 원문에서 확인할 수 있습니다.

Kotlin Toolchain 살펴보기​

Kotlin Toolchain은 JVM·Android·iOS·멀티플랫폼·서버 앱을 하나의 CLI 진입점으로 만들고, 빌드하고, 테스트하고, 배포하는 도구입니다.
필수 도구들을 선언적 설정에 맞춰 자동으로 내려받아 주기 때문에 온보딩 과정의 마찰이 크게 줄어듭니다.

kotlin new: 대화형 프로젝트 생성​

0.13의 핵심은 kotlin new 명령입니다.
웹의 KMP Wizard처럼 앱 유형을 고르고 타깃 플랫폼을 선택하면 프로젝트가 생성됩니다.
기존 kotlin init도 같은 흐름으로 맞췄는데, 차이는 kotlin init이 현재 디렉터리에 바로 파일을 만든다는 점입니다.

# 새 프로젝트 생성 (대화형)
kotlin new

# 이미 설치돼 있다면 업데이트
kotlin update

Android 개발자 관점에서 달라진 부분​

  • Android SDK 자동 프로비저닝이 IDE까지 확장: 이전에는 kotlin build/kotlin run 때만 SDK가 자동 설치돼서, 빌드 전에 IDE로 먼저 열면 SDK 누락 오류가 났습니다. 이제 프로젝트 import 시점에도 누락된 SDK 컴포넌트를 자동으로 받아 줍니다.
  • namespace/applicationId 검증 강화: com.example.app 같은 샘플 ID로 실수로 배포 빌드를 만드는 실수를 막아 줍니다.
  • 다운로드 진행 표시: JDK, Android SDK, iOS 런타임, 컴파일러 다운로드가 CLI에 진행 바로 표시됩니다.

Swift Package Manager 의존성 지원​

Apple 타깃에서 SPM 패키지를 선언적으로 가져올 수 있게 됐습니다.
설정 파일에 저장소와 버전을 적으면 됩니다.

dependencies:
  - swiftPackage:
      repository: "https://github.com/firebase/firebase-ios-sdk.git"
      version: "12.17.0"
      products: ["FirebaseCore", "FirebaseFirestore", "FirebaseAnalytics"]

가져온 Objective-C API는 swiftPMImport 접두사로 네임스페이스가 붙어, Kotlin 코드에서 명시적으로 구분됩니다.
로컬 SPM 패키지는 localSwiftPackage 키로 연결할 수 있습니다.

빌드 속도: Kotlin/Native 컴파일러 캐시​

Kotlin/Native 재빌드가 빨라집니다.
컴파일된 네이티브 의존성을 빌드 간, 심지어 프로젝트 간에 캐시로 재사용하고, 프로젝트 코드는 파일 단위 캐시로 링크 시 바뀐 부분만 다시 컴파일합니다.
기존 settings.kotlin.compileIncrementally 설정을 그대로 쓰고, .klib 컴파일 자체는 전체로 수행됩니다.

그 외 변경 사항​

  • IDE 동기화 상태를 에디터에서 확인할 수 있게 됐습니다.
  • 멀티플랫폼 라이브러리 배포 시 Compose Resources와 SwiftPM 의존성 메타데이터가 아티팩트와 함께 게시되고, 서드파티 멀티플랫폼 라이브러리의 Compose Resources도 해석됩니다.
  • AI 에이전트 연동도 강화됐습니다. Compose Hot Reload MCP 서버와 Kotlin용 에이전트 스킬(npx skills add kotlin/kotlin-agent-skills)이 제공됩니다.
  • IDE 기능은 IntelliJ IDEA 2026.2.3 또는 Android Studio Rabbit 1(2026.2.1) 이상에서 최신 Kotlin Toolchain 플러그인과 함께 쓸 수 있습니다.

실무에서 주의할 점​

기존 Gradle 기반 프로젝트를 당장 마이그레이션해야 하는 것은 아닙니다.
JetBrains도 로드맵에서 Gradle 프로젝트의 공백을 먼저 메우는 데 집중하겠다고 밝혔습니다.
따라서 운영 중인 프로젝트는 기존 흐름을 유지하고, 신규 프로젝트나 사이드 프로젝트부터 적용해 보는 것이 안전합니다.

마치며​

새로 KMP를 시작한다면 kotlin new 한 번으로 Android·iOS 환경을 한 번에 맞추는 경험은 꽤 매력적입니다.
다음에 KMP 프로젝트를 시작할 일이 있으면 이 경로로 시작해 보시기 바랍니다.

SQL LIKE '%검색어%'가 앱을 느리게 한다 — Room @Fts4로 검색 9.4배 빠르게

October 15, 2026 · 4 min read
Way
Android Developer

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.
최근 ProAndroidDev에 소개된 Room @Fts4 기반 검색 최적화 사례에 대해 설명해드리겠습니다.

배경​

종목 메모, 공지 목록, 최근 본 상품 같은 오프라인 검색을 로컬 DB의 LIKE '%쿼리%'로 구현하는 경우가 많습니다.
개발 중에는 더미 데이터가 몇십 건 수준이라 0.1초도 걸리지 않아 그대로 넘어가기 쉽습니다.
Scaling Android Search: Room @Fts4 vs SQL LIKE에서는 이 방식을 실측 수치로 비교합니다.
5,000건 기준으로 LIKE는 63.8ms, FTS4는 6.8ms가 걸려 9.4배의 차이가 났습니다.

Room @Fts4 살펴보기​

왜 LIKE가 느린지​

  • B-Tree 인덱스는 접두사를 알 때만 사용할 수 있습니다.
  • WHERE sender LIKE 'alice%'는 인덱스를 타지만, 실제 검색 UI는 중간 매칭이 필요해 WHERE body LIKE '%architecture%' 형태가 됩니다.
  • 검색어 앞에 %를 붙이는 순간 인덱스는 무력화되고 전체 테이블 스캔으로 떨어집니다.
  • 실측에서는 2,000건만 돼도 LIKE가 약 30ms로 60Hz 프레임 예산인 16.6ms를 훌쩍 넘겼습니다.
  • 또한 LIKE는 단어 경계를 모르고("cat" 검색에 "catalog", "scatter"까지 걸립니다), 어간 추출이 안 되며("optimize"로 "optimized"를 못 찾습니다), 관련도 순위도 없습니다.

FTS4와 역인덱스​

  • FTS4는 쿼리 시점이 아니라 INSERT 시점에 일을 합니다.
  • 토크나이저가 텍스트를 단어로 쪼개고 대소문자를 정규화해, "단어 → 문서 ID 목록" 형태의 역인덱스를 만듭니다.
Token        | DocIDs (Posting List)
architecture | [1, 14, 108, 492]
benchmark    | [1, 7, 22, 108, 305]
  • MATCH 'benchmark*' 같은 쿼리가 들어오면 토큰 딕셔너리에서 단어를 찾아 docid 목록을 바로 뽑아냅니다.
  • 관계없는 텍스트는 한 바이트도 읽지 않으므로, 행이 100개든 10만 개든 조회는 밀리초 단위로 끝납니다.

contentEntity 패턴​

  • 원본 테이블은 그대로 두고, 검색용 FTS 가상 테이블을 contentEntity로 붙이는 패턴이 표준입니다.
@Entity(tableName = "notices")
data class NoticeEntity(
    @PrimaryKey(autoGenerate = true) val id: Long = 0,
    val title: String,
    val body: String,
    val pinned: Boolean = false,
)

@Entity(tableName = "notices_fts")
@Fts4(contentEntity = NoticeEntity::class)
data class NoticeFtsEntity(
    val title: String,
    val body: String,
)
  • contentEntity를 지정하면 FTS 테이블은 역인덱스 구조만 갖고, 실제 텍스트는 원본 notices 테이블에서 가져오므로 데이터 중복이 없습니다.
  • Room이 AFTER INSERT/UPDATE/DELETE 트리거를 자동 생성해서, 원본에 쓰기만 하면 인덱스가 자동으로 반영됩니다.
  • DAO에서는 docid로 조인해 MATCH를 사용합니다.
@Dao
interface NoticeDao {
    @Query("""
        SELECT notices.* FROM notices
        JOIN notices_fts ON notices.id = notices_fts.docid
        WHERE notices_fts MATCH :query
        ORDER BY notices.pinned DESC
    """)
    suspend fun searchNoticesFts(query: String): List<NoticeEntity>
}
  • 기존 테이블에 FTS를 붙이는 작업은 DB 버전 업과 AutoMigration 또는 수동 마이그레이션으로 처리합니다.
  • 가상 테이블은 원본 스키마 변경과 독립적이라 마이그레이션 부담도 크지 않습니다.

실무에서 주의할 점​

  • LIKE는 프로토타입용입니다. 메시지, 문서, 메모, 상품 카탈로그처럼 사람이 입력하는 텍스트 검색이라면 데이터가 수천 건으로 자라기 전에 FTS로 옮기는 것이 맞습니다.
  • 쓰기 비용은 있습니다. FTS 테이블은 INSERT와 UPDATE 때마다 인덱스를 갱신하므로, 쓰기가 빈번하고 읽기가 드문 워크로드라면 이득이 줄어듭니다.
  • 쿼리 위생이 필수입니다. MATCH에 사용자 입력을 그대로 넣으면 따옴표 같은 특수문자가 쿼리 문법을 깨뜨립니다. 입력에서 따옴표를 제거하고, as-you-type 검색을 위해 토큰마다 접미사 *를 붙이는 sanitize 함수를 따로 두어야 합니다.
// "삼성 전자" -> "삼성* 전자*" : 토큰별 접두사 매칭으로 자동완성 느낌의 검색
fun sanitizeFtsQuery(raw: String): String =
    raw.replace("\"", "").replace("'", "").trim()
        .split("\\s+".toRegex())
        .filter { it.isNotEmpty() }
        .joinToString(" ") { "$it*" }
  • 한국어는 토크나이저를 골라야 합니다. FTS4 기본 토크나이저(simple)는 공백 기준이라 한국어 조사가 붙은 단어("검색어를")는 토큰 하나가 됩니다. 영어 위주 앱이 아니라면 unicode61 계열 토크나이저로 바꾸거나, 형태소 분석이 필요하면 별도 토크나이저를 검토해야 합니다. Porter stemmer도 영어용이라는 점을 잊지 마시기 바랍니다.

마치며​

검색 속도는 데이터가 쌓인 뒤에 손대면 마이그레이션 비용까지 함께 커집니다.
검색 대상이 텍스트이고 건수가 늘어날 구조라면, 처음부터 @Fts4와 contentEntity 패턴으로 시작하는 편이 유지보수에 유리합니다.

Compose에서 Flow 수집의 진화 — collectAsState()에서 collectAsStateWithLifecycle()까지

October 14, 2026 · 2 min read
Way
Android Developer

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.
Compose에서 Flow를 수집하는 API가 어떻게 진화해 왔는지 설명해드리겠습니다.

배경​

Compose에서 UI 상태는 주로 Flow로 노출되고, 화면에서는 이를 State로 변환해 수집합니다.
문제는 수집 API가 라이프사이클을 모르면 액티비티가 백그라운드로 가도 수집이 계속된다는 점입니다.
실무에서는 여전히 collectAsState()를 관성으로 쓰는 코드가 많습니다.
10월 ProAndroidDev에 올라온 The Evolution of Flow Collection in Jetpack Compose 글(chanzmao)이 이 진화 과정을 정리했습니다.

Flow 수집 API의 진화​

1단계: collectAsState()​

  • Compose 1.0(2021년 7월)에 도입된 가장 단순한 수집 방법입니다.
  • Flow를 State로 바꾸고, 새 값이 emit될 때마다 관련 UI를 리컴포즈합니다.
  • 라이프사이클을 모르기 때문에 STARTED 아래로 내려가도 수집을 자동으로 멈추지 않습니다.
  • composition이 살아 있는 한 백그라운드에서도 계속 수집합니다.
val uiState by viewModel.uiState.collectAsState()

2단계: collectAsStateWithLifecycle()​

  • lifecycle-runtime-compose가 제공하는 라이프사이클 인식 API입니다.
  • 기본 minActiveState는 STARTED입니다.
  • 화면이 보이지 않으면 수집을 멈추고, 다시 보이면 재개합니다.
  • 지금의 정답에 해당하는 방법입니다.
val uiState by viewModel.uiState.collectAsStateWithLifecycle()

3단계: 일회성 이벤트는 다른 패턴으로​

  • 상태가 아니라 이벤트(네비게이션, 스낵바 등)를 소비할 때는 collectAsState 계열이 맞지 않습니다.
  • LaunchedEffect와 repeatOnLifecycle 조합을 사용합니다.
val lifecycle = LocalLifecycleOwner.current.lifecycle
LaunchedEffect(lifecycle) {
    lifecycle.repeatOnLifecycle(Lifecycle.State.STARTED) {
        viewModel.events.collect { event ->
            // 네비게이션, 스낵바 등 일회성 이벤트 처리
        }
    }
}

실무에서 주의할 점​

ViewModel의 uiState 같은 StateFlow는 collectAsStateWithLifecycle()를 기본값으로 두는 것이 안전합니다.
collectAsState()는 upstream이 가벼우면 문제가 없지만, 소켓·위치·센서처럼 비싼 작업을 하는 Flow면 백그라운드에서 리소스를 낭비합니다.
minActiveState 파라미터로 기준을 RESUMED까지 올릴 수도 있으니, 화면 요구사항에 맞게 조정해야 합니다.
SharedFlow 기반 일회성 이벤트에 collectAsState를 붙이는 실수는 여전히 흔하므로, 이벤트면 수집 패턴을 바꿔야 합니다.

마치며​

Flow 수집은 단순한 API 선택이 아니라 라이프사이클과 리소스 관리의 문제입니다.
상태는 collectAsStateWithLifecycle()로, 일회성 이벤트는 repeatOnLifecycle로 구분해 사용하는 것이 좋겠습니다.

구글북 리눅스 터미널 프리뷰 — AI 에이전트에게 sudo를 줘도 되는 VM 샌드박스

2026년 10월 12일 Android Developers Blog에 공개된 구글북 리눅스 터미널 프리뷰에 대해 설명해드리겠습니다.

배경​

구글북(Googlebook)은 Android와 Chrome OS를 합친 새 노트북 카테고리입니다.
이번에 공개된 내용은 구글북에 Debian 기반 리눅스 터미널이 프리뷰로 들어온다는 소식입니다.
핵심은 AI 에이전트에게 sudo를 줘도 시스템이 망가지지 않는 구조입니다.
자세한 내용은 Android Developers Blog 원문에서 확인할 수 있습니다.

구글북 리눅스 터미널 살펴보기​

VM 기반 격리 구조​

  • 모든 터미널 명령은 격리된 Linux VM 안에서만 실행됩니다.
  • Antigravity 같은 AI 에이전트에 sudo 권한을 줘도 호스트 OS나 개인 파일이 오염되지 않습니다.
  • VM에 공개하는 디렉터리는 사용자가 명시적으로 허용한 것만 마운트됩니다.
  • 구글북 OS는 defense-in-depth 원칙으로 설계되었고, VM 경계가 호스트 OS와 마운트되지 않은 파일을 보호합니다.

파일 유지와 원클릭 리셋​

  • 원클릭 VM 리셋으로 실험 환경을 초기화할 수 있습니다.
  • VM을 초기화해도 파일은 호스트 파일 시스템에 그대로 유지됩니다.
  • 리눅스 파일은 구글북 파일 앱에서도 보입니다.
  • 에이전트에게 과감하게 권한을 주고, 망가지면 리셋하면 되는 구조입니다.

개발자에게 익숙한 Debian 환경​

  • apt, git, ssh, 컴파일러·런타임 같은 익숙한 워크플로우가 그대로 들어옵니다.
  • Node.js, Python, Ruby, Go, Rust 같은 모던 런타임을 지원합니다.
  • localhost 포트 자동 포워딩으로 호스트 브라우저에서 바로 확인할 수 있습니다.
  • VM에 할당하는 메모리는 워크로드에 맞게 조절할 수 있습니다.
  • 구글 엔지니어들도 구글북으로 리눅스 커널을 빌드하고 플랫폼 엔지니어링에 터미널을 사용하고 있다고 합니다.

로드맵​

  • Linux GUI 앱 지원이 예정되어 있습니다. 터미널을 넘어 GUI 앱까지 품으면 Android Studio 같은 도구를 VM에 올리는 시나리오도 열립니다.
  • USB 패스스루와 ADB over USB가 지원될 예정입니다. 현재는 네트워크 패스스루와 무선 ADB가 있고, USB 패스스루가 오면 Linux VM과 Antigravity에서 직접 로컬 기기 디버깅이 가능해집니다.
  • GPU/NPU 하드웨어 가속이 예정되어 있습니다. 40 TOPS급 NPU를 단 구글북 스펙과 맞물리는 부분입니다.
  • VM 메모리·스토리지 동적 스케일링과 VM 지속성, 터미널 창 분리가 포함되어 있습니다. 장시간 도는 에이전트 작업을 위한 전제 조건입니다.

실무에서 주의할 점​

아직 프리뷰 단계이므로 당장 개발 머신으로 사용하기는 이릅니다.
GUI 앱 지원과 USB ADB는 로드맵에 있는 항목입니다.
다만 보안 모델은 주목할 만합니다.
sudo를 줘도 되는 VM 샌드박스와 디렉터리별 명시적 마운트 허가, 원클릭 리셋은 사내에서 AI 코딩 에이전트 도입을 검토할 때 레퍼런스 아키텍처로 쓸 수 있습니다.

Kotlin 2.5.0에 companion 블록이 온다 — companion object와 무엇이 다른가

October 13, 2026 · 4 min read
Way
Android Developer

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.
Kotlin 2.5.0에 실험 기능으로 들어오는 companion 블록과 companion 확장에 대해 설명해드리겠습니다.

배경​

TAG 하나, newInstance() 하나를 선언할 때마다 companion object를 만들고 Companion 싱글턴이 따라붙는 구조가 반복되어 왔습니다.
JetBrains는 2026년 9월 30일 발표한 The Companions to Come 글에서 이 구조를 개선하는 실험 기능을 공개했습니다.
companion 블록은 companion object와 문법은 거의 같지만 컴파일 방식이 근본적으로 다릅니다.
전체 설계는 KEEP-0449 제안서에 정리되어 있습니다.

companion 블록과 확장 살펴보기​

companion 블록​

  • companion object에서 object 키워드를 뺀 형태입니다.
  • Kotlin 2.5.0-Beta1부터 실험 기능으로 사용할 수 있습니다.
  • 컴파일러 플래그 -Xcompanion-blocks(블록만) 또는 -Xcompanion-blocks-and-extensions(둘 다)를 넘겨야 합니다.
  • JVM에서는 진짜 static 멤버로 컴파일됩니다.
data class Vector(val x: Double, val y: Double) {
    companion {
        val ZERO = Vector(0.0, 0.0)
    }
}

// 사용은 똑같이
val v = Vector.ZERO

companion object는 실제 객체라서 인터페이스 구현이나 값으로 전달하는 것이 가능합니다.
반면 자바에서 호출하면 Vector.Companion.getZERO() 같은 이름이 드러나고, 리플렉션과 바이트코드 크기에도 흔적이 남습니다.
companion 블록은 컴파일 전략을 다른 플랫폼의 static 멤버처럼 바꿔서, JVM에서는 순수 static 멤버가 됩니다.

companion 확장​

  • 내가 만든 클래스가 아니어도 "클래스 멤버처럼" 선언할 수 있는 새 문법입니다.
  • Java 클래스에도 쓸 수 있고, 원래 companion object가 없어도 됩니다.
  • 라이브러리에서 내려준 클래스에 팩토리 함수를 붙이고 싶을 때, 유틸 오브젝트를 따로 만들지 않고도 SomeClass.myFactory() 형태로 붙일 수 있습니다.
companion fun Vector.unit(angle: Double) = Vector(cos(angle), sin(angle))

기존 companion object와의 관계​

  • 기존 companion object는 그대로 지원되고 강제 마이그레이션은 없습니다.
  • 인터페이스를 구현해야 하는 companion은 여전히 object만 가능합니다. 블록은 객체가 아니기 때문입니다.
  • 새 코드에서 단순 상수와 팩토리는 블록을 선호하는 방향이 되겠지만, 서두를 이유는 없습니다.

KMP와의 연결​

  • companion 블록 멤버는 KMP에서 expect로 선언할 수 있습니다.
  • Java 클래스의 static 멤버로 actualize할 수 있습니다.
  • 멀티플랫폼 라이브러리에서 플랫폼 네이티브 static API를 companion 멤버로 감싸던 패턴이 언어 차원에서 정식으로 지원됩니다.

실무에서 주의할 점​

실험 기능이므로 지금 당장 실무에 적용할 단계는 아닙니다.
특히 companion 확장을 쓴 라이브러리는 pre-release 바이너리가 되어 안정화될 때까지 의존성으로 소비할 수 없습니다.
companion 블록은 이 제한이 없지만, 소비하는 쪽도 플래그를 켜야 합니다.
사내 공통 모듈에 실험 문법을 넣으면 그 모듈을 쓰는 모든 프로젝트에 플래그가 전파됩니다.
마이그레이션할 때는 object 키워드를 지우는 것으로 대부분 충분하지만, 프로젝트와 의존하는 코드 전체를 다시 컴파일해야 합니다.
R8/ProGuard 규칙에서 Companion을 참조하던 룰이 있다면 함께 점검해야 합니다.
생태계 툴링이 아직 블록을 인식하지 못할 수 있다는 점도 발표에서 언급되었습니다.
Android 관점에서는 Activity와 Fragment의 newInstance, TAG 상수, CREATOR 같은 상용구의 바이트코드가 깔끔해집니다.
다만 DEX 메서드 수나 APK 크기에서 큰 변화는 기대하지 않는 것이 좋습니다.
실험 플래그를 켜는 방법은 다음과 같습니다.

// app/build.gradle.kts (Kotlin DSL)
kotlin {
    compilerOptions {
        // companion 블록만 허용
        freeCompilerArgs.add("-Xcompanion-blocks")
        // 블록 + 확장을 모두 허용
        // freeCompilerArgs.add("-Xcompanion-blocks-and-extensions")
    }
}
// 실험해 볼 후보 1: Fragment 팩토리
class DetailFragment : Fragment() {
    companion {
        private const val ARG_ID = "arg_id"
        fun newInstance(id: String) = DetailFragment().apply {
            arguments = bundleOf(ARG_ID to id)
        }
    }
}

// 실험해 볼 후보 2: 인터페이스 구현이 필요하면 object 유지
class AnalyticsTracker {
    companion object : EventSink {  // 블록으로는 안 됨
        override fun sink(event: Event) { /* ... */ }
    }
}

마치며​

companion 블록은 겉보기에는 object 한 단어 차이이지만, 바이트코드 관점에서는 static 멤버로 컴파일되는 큰 변화입니다.
실험 기능인 만큼 테스트 모듈에서 먼저 확인하고, 안정화 이후에 새 코드부터 적용하는 것이 좋겠습니다.

DataStore 1.3.0이 준비 중인 것들 — Tink 암호화와 새로운 Builder API

October 21, 2026 · 4 min read
Way
Android Developer

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.
최근 30일 내 릴리스 중 하나를 골라 심화 해설을 하겠습니다.
DataStore 1.3.0-rc01(2026년 10월 12일)까지 이어진 1.3.0 라인의 변경 사항을 정리해드리겠습니다.

현재 상황​

DataStore 1.2.1은 안정 채널의 최신입니다.
그 위로 1.3.0 라인이 alpha 단계를 거치며 2026년 10월 12일 rc01에 도달했습니다.
rc01 자체는 버그 수정 위주이지만, 1.3.0이 안정으로 오면 두 가지 큰 변화가 함께 옵니다.
Tink 기반 암호화 지원과 새로운 Builder API입니다.
두 기능 모두 alpha07(2026년 3월 11일)에 이미 확정된 내용입니다.

DataStore 1.3.0 살펴보기​

datastore-tink 아티팩트와 AeadSerializer​

새 아티팩트 androidx.datastore:datastore-tink가 추가되었습니다.
핵심 클래스는 AeadSerializer로, 기존 Serializer<T>를 감싸는 래퍼입니다.
내부는 Tink의 AEAD(Authenticated Encryption with Associated Data)로 암호화·복호화를 수행합니다.
JVM과 Android 타깃 모두에서 사용할 수 있습니다.
공식 문서의 사용 순서는 세 단계입니다.

// 1. Tink API로 키 생성
val keysetHandle =
    AndroidKeysetManager.Builder()
        .withSharedPref(applicationContext, "keyset", "keyset_prefs")
        .withKeyTemplate(KeyTemplate.createFrom(PredefinedAeadParameters.AES256_GCM))
        .withMasterKeyUri("android-keystore://master_key")
        .build()
        .keysetHandle

// 2. 기존 serializer를 감싸는 AeadSerializer 생성
val aeadSerializer = AeadSerializer(
    aead = keysetHandle.getPrimitive(
        RegistryConfiguration.get(),
        Aead::class.java,
    ),
    wrappedSerializer = ExistingSerializer,
    // ciphertext swapping 공격 방지를 위한 고유 이름
    associatedData = "settings.json".encodeToByteArray(),
)

// 3. 기존 serializer 대신 aeadSerializer로 DataStore 생성
val dataStore = dataStore(
    fileName = "settings.json",
    serializer = aeadSerializer,
    scope = scope,
)

마스터 키는 Android Keystore에 두는 패턴이 권장됩니다.
associatedData에는 파일마다 고유한 이름을 넣어, 암호문을 서로 바꿔치기하는 공격을 막습니다.
alpha10에서는 GeneralSecurityException이 CorruptionException으로 감싸지도록 바뀌었습니다.
암호화 실패가 DataStore의 CorruptionHandler 흐름에 자연스럽게 녹아들게 된 것입니다.

DataStore.Builder<T> — DataStoreFactory의 후계자​

DataStore.Builder<T>가 DataStoreFactory의 공식 대체 API로 도입되었습니다.
공식 릴리스 노트는 모든 사용자에게 Builder로의 마이그레이션을 권장합니다.
가장 큰 차이는 스코프 전달 방식입니다.
Builder는 CoroutineScope가 아니라 CoroutineContext를 요구합니다.
호출자가 viewModelScope 같은 짧은 생명주기의 스코프를 넘겨도, DataStore가 그 생명주기에 묶이지 않게 하려는 설계입니다.
구조적 동시성(structured concurrency) 관점에서 올바른 방향입니다.
또한 setCorruptionHandler로 손상 시 처리 로직을 직접 주입할 수 있게 되었습니다.
alpha09에서는 ReThrowCorruptionHandler가 public으로 공개되기도 했습니다.

웹 플랫폼 지원 (alpha08)​

DataStore가 웹 타깃 지원을 넓혔습니다.
WebOpfsStorage로 OPFS(Origin Private File System)를 지원합니다.
크로스탭 알림은 BroadcastChannel, 분산 락은 Web Locks API를 씁니다.
WebLocalStorage와 WebSessionStorage API로 저장소 타입도 명시적으로 관리할 수 있습니다.

rc01에서 바뀐 것​

1.3.0-rc01의 API 변경은 소규모입니다.
EdgeToEdge#enable() 대신 WindowCompat#enableEdgeToEdge(Window)를 쓰도록 정리되었습니다.
lifecycle-runtime 의존성이 2.10.0으로 올라갔는데, 이는 AGP 9.5.0-alpha04 이상에서 번들된 lifecycle lint 검사가 동작하기 위한 요구사항입니다.

의존성 선언​

# libs.versions.toml 예시
[versions]
datastore = "1.3.0-rc01"

[libraries]
datastore = { module = "androidx.datastore:datastore", version.ref = "datastore" }
datastore-tink = { module = "androidx.datastore:datastore-tink", version.ref = "datastore" }

실무 관점​

Builder에 넘기는 CoroutineContext에는 반드시 Job이 있어야 하고, 애플리케이션 스코프여야 합니다.
공식 문서의 Warning에도 명시된 대로, 컨텍스트가 취소되면 DataStore 내부 동작이 중간에 멈춥니다.
viewModelScope를 그대로 넘기는 실수를 하지 않도록 주의해야 합니다.
Tink 도입 시에는 associatedData를 파일명과 일치시켜 관리하는 규칙을 팀에 정해 두는 것이 좋습니다.
민감 데이터 저장소가 늘어나면 키 로테이션 정책도 함께 논의해야 합니다.

마치며​

DataStore 1.3.0은 저장(암호화)과 생성(Builder API) 두 축을 한 번에 끌어올립니다.
안정 릴리스 전에 Tink 암호화 대상 데이터와 Builder 전환 범위를 정리해 두시기 바랍니다.

전체를 잠그지 말고 신뢰하는 origin만 허용하기 — WebView v156의 cross-origin isolation allowlist

October 21, 2026 · 4 min read
Way
Android Developer

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.
이번 10월 Google System Updates에서 공개된 Android WebView v156의 새 API에 대해 설명해드리겠습니다.

배경​

SharedArrayBuffer는 웹 스레드 간 메모리를 공유하는 기능입니다.
멀티스레드 Wasm이나 고성능 웹 렌더링에서 핵심이 되는 API이기도 합니다.
그런데 Spectre 계열 취약점 이후, 이 기능은 cross-origin isolation이라는 울타리 뒤로 들어갔습니다.
페이지 전체에 Cross-Origin-Opener-Policy와 Cross-Origin-Embedder-Policy를 걸지 않으면 쓸 수 없는 구조가 되었습니다.
웹에서는 이해할 만한 조치였지만, WebView를 쓰는 하이브리드 앱에서는 이야기가 다릅니다.
하나의 WebView 안에서 인증·광고·외부 위젯 등 신뢰 수준이 다른 origin이 함께 도는 경우가 많기 때문입니다.
전체 페이지를 격리하면 다른 콘텐츠가 깨지고, 격리를 안 하면 멀티스레드 Wasm을 못 쓰는 딜레마가 생겼습니다.

WebView v156의 allowlist API 살펴보기​

2026년 10월 7일에 릴리스된 Android WebView v156의 변경 로그에 새 API가 등장했습니다.
"신뢰할 수 있는 origin에 대해 SharedArrayBuffer 같은 cross-origin isolated 기능을 선택적으로 허용하는, 설정 가능한 allowlist를 이용한 새 Android WebView API"라는 설명입니다.
격리 단위를 "페이지 전체"에서 "지정한 origin 목록"으로 낮춘 셈입니다.

Cross-Origin Isolation이 요구되는 이유​

SharedArrayBuffer는 프로세스 간에 공유되는 고해상도 타이머 역할을 할 수 있습니다.
공격자가 이를 이용해 캐시 타이밍을 재면 Spectre 계열의 부채널 공격이 가능해집니다.
그래서 브라우저들은 COOP: same-origin과 COEP: require-corp 헤더를 함께 요구해 왔습니다.
두 헤더가 있으면 해당 문서는 다른 origin 프로세스와 메모리를 공유하지 않음이 보장됩니다.

기존 WebView에서의 선택지​

기존에는 크게 두 가지 선택지만 있었습니다.
첫째, 모든 콘텐츠를 격리 상태로 올리는 방법입니다.
신뢰할 수 없는 서드파티 iframe까지 같은 격리 정책을 따라야 해서 현실적이지 않았습니다.
둘째, 아예 SharedArrayBuffer를 포기하는 방법입니다.
멀티스레드 Wasm을 쓰는 차트 라이브러리나 문서 렌더러가 싱글스레드로 떨어졌습니다.

Allowlist가 바꾸는 것​

allowlist 방식에서는 격리를 포기하지 않습니다.
대신 개발자가 "이 origin만큼은 격리된 것으로 취급해도 된다"고 명시하는 allowlist를 둡니다.
신뢰하는 자사 도메인의 Wasm 차트 모듈만 허용하고, 광고 iframe은 그대로 두는 설계가 가능해집니다.
보안 모델을 이분법에서 세밀한 제어로 바꾼 것입니다.

응답 헤더 복습 (개념 예시)​

allowlist는 WebView 클라이언트 측 설정이지만, 기본이 되는 격리 헤더는 서버에서 내려줍니다.
아래는 웹 표준의 일반적인 헤더 조합입니다.

Cross-Origin-Opener-Policy: same-origin
Cross-Origin-Embedder-Policy: require-corp

두 헤더가 모두 있어야 브라우저가 해당 문서를 cross-origin isolated 상태로 표시합니다.
allowlist API는 이 위에 "어떤 origin을 신뢰 목록에 넣을지"를 얹는 개념입니다.
정확한 클래스명과 메서드명은 아직 공식 WebView 문서에 공개되지 않았습니다.
변경 로그에도 "Some features may be experimental"이라는 주의 문구가 붙어 있습니다.
따라서 실제 도입 전에는 WebView 릴리스 노트와 Chromium 문서를 다시 확인해야 합니다.

실무 관점​

allowlist는 "신뢰 경계"를 코드로 표현하는 작업입니다.
목록에 넣는 origin 하나하나가 공격 표면이 되므로, 목록은 최소 단위로 유지하는 것이 원칙입니다.
MTS처럼 WebView로 시세·차트를 보여주는 앱이라면, 차트 모듈 origin만 허용하고 나머지는 기존 정책을 유지하는 방식이 현실적입니다.
allowlist가 적용되는 WebView 버전 범위를 앱에서 미리 확인해 두는 것도 필요합니다.
구형 WebView에서는 API 자체가 없어 기능이 조용히 비활성화될 수 있기 때문입니다.

마치며​

WebView v156의 allowlist API는 보안과 성능 사이의 이분법을 깨는 첫 공식 경로입니다.
전체 격리가 부담스러웠던 하이브리드 앱이라면, 신뢰 origin 목록 설계부터 시작해 보시기 바랍니다.

Android Developers Blog가 Blogger를 떠나 developer.android.com으로 — RSS·북마크 갱신 안내

October 20, 2026 · 3 min read
Way
Android Developer

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.
Android Developers Blog가 developer.android.com으로 이전한 소식에 대해 설명해드리겠습니다.

배경​

2026년 10월 15일, Android Developers Team은 공식 소식 채널의 이전을 발표했습니다.
앞으로 모든 공식 소식과 엔지니어링 인사이트는 Blogger(android-developers.googleblog.com)가 아니라 developer.android.com/blog에 올라옵니다.
팀은 이 장을 닫고 모든 공식 소식과 엔지니어링 인사이트를 developer.android.com/blog로 옮긴다고 밝혔습니다.
새 소식이 올라가는 자리를 따라가려면 구독 설정을 바꿔야 하는, 실무 루틴에 직접 닿는 변경이라 짧게 정리합니다.

무엇이 달라졌는지​

게시 위치와 구독 경로​

달라진 것은 게시 위치와 구독 경로뿐입니다.
발표일 기준 새 블로그에 글이 이미 정상적으로 올라오고 있고, 구글이 앞으로의 공식 소식을 전부 새 위치에 올리겠다고 명시했습니다.
하지만 기존 주소가 언제 닫히는지, 아카이브가 어떻게 유지되는지는 언급이 없어서 당장은 양쪽을 함께 두는 전환기로 보입니다.
독자에게는 북마크와 RSS를 오늘 업데이트하라고 직접 요청했습니다.
기존 Blogger 주소의 종료 시점과 아카이브 처리 방침은 아직 발표되지 않았습니다.

새 블로그의 구성​

새 블로그는 글을 Product News, Case Studies, How-tos, Events & Programs 카테고리로 분류합니다.
장점으로는 더 나은 포맷, 개발자 사이트의 기술 콘텐츠와의 긴밀한 통합, 쉬운 탐색을 꼽았습니다.
이전 이후 첫 글들(10월 13일~19일)로는 프론티어 모델의 Android 개발자 지원, Google Play 디스커버리·참여 기능, 그리고 Grab의 R8 최적화 사례(ANR −32%, 콜드스타트 −35%)가 게시되었습니다.

실무에서 바로 할 일​

  1. RSS 리더(Feedly, Inoreader 등)의 피드 URL을 새 주소로 갱신합니다. 발표문에 RSS 업데이트 요청이 명시되어 있습니다. 구 Blogger 피드를 그대로 두면 새 소식이 들어오지 않습니다.
  2. 사내 공지와 위키의 소식 링크를 갱신합니다. 팀에 Android 공식 소식은 이제 developer.android.com/blog라는 한 줄을 남겨 두면, 이후 실무 글이 새 위치에 올라왔을 때 놓치지 않습니다.

확인용 체크리스트는 다음과 같습니다.

[ ] RSS 리더에서 android-developers.googleblog.com 피드 제거
[ ] https://developer.android.com/blog 피드 구독 추가
[ ] 팀 위키의 "Android 공식 소식" 링크를 developer.android.com/blog로 교체
[ ] 구 Blogger 글 북마크는 종료 공지가 나올 때까지 유지

실무에서 주의할 점​

  • 정보 누락을 방지해야 합니다. 구독 설정을 바꾸지 않으면 구글의 공식 릴리스와 사례 글이 사각지대에 들어갑니다. 특히 새 블로그에 이미 실무급 사례(Grab R8)가 올라온 만큼, 이전 시점(2026년 10월 15일) 이후 글은 새 위치에서만 찾아야 합니다.
  • 아카이브 링크에 주의해야 합니다. 기존 Blogger 주소의 종료 시점이 미정이므로, 위키에 남긴 구 Blogger 글 링크는 당분간 유효하겠지만 언젠가는 정리가 필요할 수 있습니다.
  • 긍정적인 면도 있습니다. 문서와 같은 사이트 안으로 들어오면서 예제 코드와 가이드 문서와의 연결이 쉬워질 가능성이 있습니다. 새 블로그 첫 글들이 AI 에이전트와 성능 케이스스터디 중심으로 올라오는 것도 실무 접점이 높습니다.
  • 발표 내용은 WebProNews 보도에서도 확인할 수 있습니다.

마치며​

공식 소식을 받아보는 자리만 새 주소로 바꿔 두면, 이전으로 인한 정보 누락은 막을 수 있습니다.
RSS와 위키 링크를 오늘 중으로 갱신해 두는 것을 권장합니다.

Grab이 R8와 프로파일 기반 최적화로 ANR 32%·콜드스타트 35%를 줄인 방법

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.
Grab이 R8와 프로파일 기반 최적화로 ANR과 콜드스타트를 줄인 사례에 대해 설명해드리겠습니다.

배경​

2026년 10월 19일, 새 Android Developers Blog(developer.android.com/blog)에 Grab의 성능 최적화 사례가 올라왔습니다.
조건은 10년 된 코드베이스, 1,000만 줄이 넘는 코드, 수백 개의 서드파티 라이브러리였습니다.
Grab이 겪던 문제는 새 버전 릴리스 직후마다 ANR이 급증하는 것이었습니다.
원인은 많은 DEX 파일을 읽는 초기화 오버헤드였습니다.
플레이의 클라우드 프로파일은 일반적인 흐름은 최적화해 주지만, Dagger 그래프 초기화 같은 앱 고유의 시작 경로는 커버하지 못합니다.
이런 경로는 JIT 컴파일과 백그라운드 최적화에 며칠간 의존하게 되고, 그 사이 사용자가 ANR을 겪는 구조였습니다.
해법은 R8 최적화와 베이스라인·스타트업 프로파일을 3단계로 나눈 점진 도입이었습니다.
최종 결과는 사용자 체감 ANR −32.5%, 앱 다운로드 크기 −30.4%, 콜드스타트 −35%입니다.
핵심은 Dagger 의존성 그래프 초기화 같은 핵심 사용자 여정을 베이스라인 프로파일에 직접 담아, 설치 즉시 머신 코드로 컴파일되게 만든 것입니다.

3단계 점진 도입​

1단계 — R8 Compat 모드와 프로파일 (2025년 출시)​

레거시 ProGuard 기본 파일에서 proguard-android-optimize.txt로 옮기며 R8 최적화를 켰습니다.
10년 된 코드베이스라 레거시 설정과 리플렉션 사용을 손봐야 했습니다.
동시에 베이스라인 프로파일과 스타트업 프로파일을 합친 릴리스를 냈습니다.
결과는 사용자 체감 ANR −25%, 다운로드 크기 −16%, 콜드스타트 −27% 개선이었고, 릴리스 직후 ANR 급증 현상이 사라졌습니다.

2단계 — R8 Full Mode 전환 (2026년 출시)​

1단계 출시 9개월 뒤의 일입니다.
여기에 ANR −10%p, 크기 −14%p, 콜드스타트 −10%p가 추가로 얹혔습니다.
Retrofit, Firebase, Jetpack Compose 같은 표준 라이브러리는 내장 룰 덕분에 문제없이 통과했습니다.
반면 거대한 자체 코드의 리플렉션 구간은 하나씩 해결해야 했습니다.
대표적인 사례가 두 가지입니다.
최신 Gson 릴리스의 consumer keep rules를 적용해 JSON 파싱을 지켰습니다.
자바 동적 프록시는 런타임에 리플렉션으로 인터페이스 구현체를 생성하는 구조라 R8이 컴파일 시점에 사용을 감지하지 못해 크래시가 나는 구간이 있었습니다.
이는 폭넓은 예외가 아니라 해당 클래스에만 좁게 적용하는 타깃 킵룰로 처리했습니다.
크기를 불리지 않으면서 안정성을 지킨 방식입니다.

3단계 — 킵룰 거버넌스 (진행 중)​

R8 Configuration Analyzer로 킵룰 위생을 수치화하고 있습니다.
Optimizations 점수는 72%에서 78.2%로, Shrinking은 73%에서 79.1%로, Obfuscation은 79.6%에서 81.7%로 올랐습니다.
다운로드 크기는 추가로 약 3.6% 감소했습니다.
새 킵룰은 정당화와 리뷰를 요구하는 사전 머지 CI 가드레일을 붙이는 중입니다.
최적화 점수를 CI 대시보드에서 추적해 회귀를 병합 전에 잡겠다는 계획입니다.

테스트와 빌드 운영​

수백만 줄을 전부 테스트할 수 없으니, 킵룰을 좁히는 범위에 해당하는 코드에 테스트를 집중하고 반복적으로 정제하는 방식을 택했습니다.
하이브리드 빌드(Bazel로 디버그, Gradle로 R8 릴리스)라 R8 실험에 원격 CI가 최대 2시간 걸렸습니다.
데일리 QA 빌드를 프로덕션 R8 동작과 맞춰 격차를 메웠습니다.
mapping.txt와 configuration.txt 수집·업로드(Firebase Crashlytics에 자동 업로드, Play Console용 디오보스케이션 매핑 번들링)를 자동화해 디버깅 사이클을 줄였습니다.

내 코드 예시​

Grab 1단계에 해당하는 R8 기본 세팅은 다음과 같습니다.

// app/build.gradle.kts — Grab 1단계에 해당하는 R8 기본 세팅
android {
    buildTypes {
        release {
            isMinifyEnabled = true
            isShrinkResources = true
            proguardFiles(
                getDefaultProguardFile("proguard-android-optimize.txt"), // ← 레거시 파일에서 교체
                "proguard-rules.pro"
            )
        }
    }
}

핵심 여정을 프로파일에 담는 Macrobenchmark 테스트는 다음과 같습니다.

// baselineprofile 모듈 — 핵심 여정을 프로파일에 담는 Macrobenchmark 테스트
@OptIn(ExperimentalBaselineProfilesApi::class)
class StartupBaselineProfileGenerator {
    @get:Rule
    val baselineProfileRule = BaselineProfileRule()

    @Test
    fun startup() = baselineProfileRule.collect("com.example.app") {
        // 시작부터 홈 진입까지: Grab이 Dagger 그래프 초기화 경로를
        // 프로파일에 담은 것과 같은 원리
        startActivityAndWait()
    }
}

동적 프록시 구간을 지키는 킵룰은 다음과 같습니다.

# proguard-rules.pro — 동적 프록시 구간은 좁은 범위로만 킵 (Grab 2단계 방식)
-keep class com.example.net.ProxyService
-keepclassmembers class com.example.net.ProxyService { *; }

실무에서 주의할 점​

  • R8 Full Mode는 킵룰 정리 없이는 갈 수 없습니다. Grab도 1단계를 2025년에, 2단계를 그 9개월 후에 출시했습니다. 릴리스 빌드에 isMinifyEnabled = true만 켜면 끝나는 것이 아니라, 리플렉션 사용 구간(동적 프록시, Gson 리플렉션 어댑터, 난독화-민감 API)을 좁은 범위의 킵룰로 지키는 작업이 본체입니다.
  • 베이스라인 프로파일은 우리 앱의 핫패스를 직접 정하는 것입니다. 플레이 클라우드 프로파일이 앱 시작 경로를 커버하지 못하면 매주 릴리스 때마다 ANR이 급증합니다. 매크로벤치마크로 핵심 여정을 프로파일에 담으면 설치 즉시 AOT 컴파일되니, 시작 경로 최적화의 1순위로 둘 만합니다.
  • 킵룰은 CI로 지켜야 합니다. 한 번 최적화한 뒤에는 Configuration Analyzer 점수를 CI 대시보드에 띄우고, 킵룰 추가를 리뷰 대상으로 삼는 것이 장기 전략입니다.
  • 동적 프록시와 리플렉션 구간에 대한 과도한 -keep은 앱 크기를 불립니다. Grab이 그랬듯 클래스 단위로 좁혀 적용하고, 테스트는 킵룰 변경 범위에 집중하는 것이 효율적입니다.

마치며​

R8와 프로파일 기반 최적화는 한 번에 전환하는 것이 아니라 단계로 나눠 숫자로 확인하며 도입하는 것이 핵심입니다.
킵룰을 CI로 관리하는 거버넌스까지 갖춰야 최적화 효과가 유지됩니다.

베타 미리 보기 — Compose 1.13.0-beta01과 Material3 1.5.0-beta01의 소스 브레이킹 변경

October 19, 2026 · 5 min read
Way
Android Developer

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.
2026년 10월 7일에 공개된 Compose 1.13.0-beta01과 Material3 1.5.0-beta01의 변경 사항에 대해 설명해드리겠습니다.

배경​

2026년 10월 7일, Compose BOM의 두 축이 베타로 나왔습니다.
androidx.compose.runtime:runtime:1.13.0-beta01와 androidx.compose.material3:material3:1.5.0-beta01입니다.
같은 날 stable도 runtime 1.12.1과 material3 1.4.0으로 함께 릴리스되었습니다.
둘 다 아직 베타지만 소스 브레이킹 변경이 포함되어 있어, 지금 미리 파악해 두면 나중에 스테이블로 올릴 때 수월합니다.
공식 AndroidX 릴리스 노트(Material3, Runtime)를 기준으로 실무에 닿는 변경만 정리합니다.
참고로 이 글은 최근 30일 이내 릴리스를 다루는 심화 해설입니다.

무엇이 달라졌는지​

Slider와 RangeSlider의 상태 분리​

가장 큰 소스 브레이킹 변경입니다.
Material3 1.5.0-alpha29에서 Slider와 RangeSlider의 onValueChange가 필수 파라미터가 되었고, 파라미터 순서도 바뀌었습니다.
무상태(stateless) 오버로드는 deprecated(일부는 hidden) 처리되었고, 상태를 별도 객체로 분리하는 방식으로 이관이 권장됩니다.

// 기존 방식 (1.5.0에서 deprecated)
var value by remember { mutableFloatStateOf(0.5f) }
Slider(value = value, onValueChange = { value = it })

// 새 방식 — 상태를 별도 객체로 분리
val state = remember { SliderState(value = 0.5f) }
Slider(state = state)

var range by remember { mutableStateOf(0.2f..0.8f) }
RangeSlider(value = range, onValueChange = { range = it })
// → val state = remember { RangeSliderState(startValue = 0.2f, endValue = 0.8f) }
//   RangeSlider(state = state)

함께 바뀐 사항은 다음과 같습니다.

  • RangeSliderState의 activeRangeStart와 activeRangeEnd가 startValue와 endValue로 개명되었습니다.
  • SliderState는 더 이상 공개적으로 DraggableState를 구현하지 않습니다. 바이너리 호환 유지를 위해 DraggableState는 SliderState에 복원되었고, onValueChange가 nullable인 오버로드는 hidden deprecated로 유지됩니다.

소스 코드는 고쳐야 하지만 이미 빌드된 바이너리는 깨지지 않게 설계된 셈입니다.

computedStateOf의 읽기 전용 강제​

runtime 1.13.0-beta01부터 computedStateOf의 계산 블록 안에서 state에 쓰면 IllegalStateException이 던져집니다.
이전에도 쓰면 안 되는 패턴이었지만 실제로는 조용히 넘어가거나 이상한 무효화(invalidation)를 일으키곤 했습니다.
이는 외부 기여로 들어온 SnapshotStateObserver 읽기 시 예상 밖 무효화 수정과 같은 맥락입니다.
계산 블록은 순수하게 읽고 반환만 한다는 규칙이 강제됩니다.

Kotlin 2.2와 AGP 요구사항​

Compose 라이브러리들이 Kotlin 2.2를 타깃으로 빌드되고, kotlinc 2.2가 필요합니다.
또 androidx.lifecycle:lifecycle-runtime:2.10.0 의존성 업데이트 때문에, 번들된 lifecycle lint 체크가 동작하려면 AGP 9.5.0-alpha04 이상이 필요합니다.
툴체인 전체가 2.2와 37.1 라인으로 움직이고 있다는 신호입니다.

compileSdk 37.1 전이적 요구​

Compose 라이브러리의 compileSdk가 37.1로 올라갔습니다.
이는 Compose를 쓰는 모든 앱과 라이브러리도 compileSdk를 37.1로 올려야 한다는 뜻입니다.
Android 17(targetSdk 37) 대응을 아직 하지 않았다면, Compose 1.13과 1.5 스테이블로 올라가는 시점이 강제 마이그레이션 시점이 됩니다.

그 외 변경 사항​

  • 비밀번호 필드의 기본 난독화 방식이 RevealLastTyped에서 TextObfuscationMode.System으로 바뀝니다. SecureTextField와 OutlinedSecureTextField의 기본값 변경입니다.
  • Float.NaN 관련 리컴포지션 스킵 버그가 수정되었습니다. Dp.Unspecified(내부적으로 Float.NaN 기반)를 인자로 받은 컴포저블이 인자가 변하지 않았는데도 리컴포지션을 스킵하지 못하던 문제입니다.
  • BottomAppBar와 연관 API가 스테이블로 승격되었고, BasicAlertDialog가 Experimental을 졸업했습니다.
  • LocalMotionScheme이 제거되고 MaterialTheme.motionScheme으로 교체되었습니다.
  • ExposedDropdownMenu가 멤버 함수에서 ExposedDropdownMenuBoxScope의 확장 함수로 변경되어 import를 새로 잡아야 합니다.
  • 새로운 material3-ripple 라이브러리가 추가되었습니다. 기존 material-ripple의 대체이며 inset focus ring을 지원합니다.
  • DatePicker가 월 이동 가용성을 표시 월 인덱스에서 직접 계산해 1프레임에 해결되도록 개선되었습니다.
  • TopAppBarDefaults.enterAlwaysScrollBehavior의 reverseLayout 오버로드가 1.4 호환을 위해 deprecated(경고)로 복원되었습니다.
  • HorizontalCenteredHeroCarousel의 maxItemWidth가 preferredItemWidth로 개명되었고, 멀티애스펙트 캐러셀 API가 전역 carouselParallaxScrollEffect 모디파이어로 단순화되었습니다.
  • runtime에서는 movableContent 이동 시 wrapper 슬롯을 들고 있던 LinkComposer 메모리 누수가 수정되었고, CompositionObserver가 패스당 1회 해결되도록 변경되었으며, 오프-메인 스레드 ComposeTracer가 지원됩니다.

실무에서 주의할 점​

  • Slider 사용처를 전수 조사해야 합니다. 금융 앱에 수수료 슬라이더나 투자 금액 조절 같은 Slider와 RangeSlider가 있다면 1.5.0 스테이블 전에 상태 분리 방식으로 바꿔 두는 것이 좋습니다. onValueChange 필수화는 컴파일 에러로 드러나지만, 파라미터 순서가 바뀐 오버로드는 시그니처 자체가 바뀌어 에러가 나거나 deprecated로 걸리므로 리뷰는 한 번씩 필요합니다.
  • computedStateOf와 derivedStateOf 블록 안에서 값을 쓰는 코드가 있는지 검사해야 합니다. IllegalStateException은 런타임에 발생하므로, 코드 검색으로 계산 블록 안에 대입이 있는지 미리 확인하는 것이 안전합니다.
  • Kotlin 2.2와 AGP, compileSdk 37.1은 묶어서 계획해야 합니다. Compose 1.13은 Kotlin 2.2를, lint는 AGP 9.5.0-alpha04 이상을, Compose는 compileSdk 37.1을 각각 요구하므로 서로 의존합니다. 하나씩 따로 올리기보다 한 스프린트에 묶어 CI에서 함께 검증하는 편이 낫습니다.
  • 비밀번호 입력 UX 변경은 기획과 디자인 부서와 공유해야 합니다. 기본값이 System으로 바뀌면 타이핑 중 마지막 글자를 잠깐 보여주는 동작이 사라집니다. 보안 정책상 환영할 변화지만, 릴리스 노트 한 줄로 바뀌는 UX라 미리 공유하지 않으면 버그 문의가 들어올 수 있습니다.
  • 베타 릴리스이므로 스테이블 전에 API가 또 바뀔 수 있습니다. 이 글에서 다룬 내용은 베타 시점에 확정된 변경 기준입니다.

마치며​

Compose 1.13과 Material3 1.5는 베타 단계에서 미리 확인해 두면 스테이블 상향이 훨씬 수월해집니다.
특히 Slider의 상태 분리와 툴체인 요구사항은 일정을 잡아 미리 준비하는 것이 좋습니다.

불법 상태는 컴파일러가 막는다 — KotlinConf 2026 결제 시스템 토크가 준 10가지 타입 설계 패턴

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.
KotlinConf 2026에서 발표된 Verifone의 타입 기반 결제 시스템 설계 사례에 대해 설명해드리겠습니다.

배경​

금융 앱을 만들다 보면 이 값은 절대 null이면 안 된다는 규칙을 코드 리뷰와 주석에 의존해 두곤 합니다.
Verifone의 아키텍트 Yuri Geronimus는 KotlinConf 2026 강연 "Kotlin as a Safety Net: Type-Driven Reliability in the Finance Industry"에서 다른 접근을 이야기했습니다.
규칙을 문서가 아니라 타입 시스템에 새기는 것, 즉 잘못된 상태는 만들 수 없게 만드는 방식입니다.
이 글은 2026년 10월 14일 JetBrains 블로그에 올라온 강연 리캡을 실무 관점에서 정리한 것입니다.
발단은 실제 결제 장애 사례 여섯 가지였습니다.
다른 계좌로 입금된 돈, 혹시 모르니 nullable로 두었다가 터미널 일부가 먹통이 된 필드, 로그에 찍힌 카드번호, 이미 되돌린 건을 또 환불해 가맹점이 두 번 청구된 사례, 타임아웃과 동시에 성공한 승인 등이었습니다.
공통 원인은 스펙이 말하는 단어와 코드가 말하는 단어의 불일치였고, 어느 곳에서도 강제로 드러나지 않았다는 점입니다.

도입 결과​

스펙의 명사를 타입으로 표현하고, 잘못된 사용은 컴파일이 되지 않게 만들었습니다.
핵심은 규율(discipline)이 아니라 컴파일러에게 맡긴다는 것입니다.
20개 팀이 세계 각지에서 일하는 규모에서는 리뷰어의 성실함이 균일하지 않지만, 컴파일 체크는 항상 동일하게 적용됩니다.
결과는 개발 속도 2.7배, 인증은 단 1건의 결함으로 첫 시도에 통과, 코드베이스는 30% 축소였습니다.
코드리뷰는 누락된 상태 체크 찾기에서 스펙 문장과 코드의 문장 대조로 바뀌었습니다.
신규 입사자가 5,000페이지 분량의 스펙을 다 이해하기 전에 며칠 만에 첫 프로덕션 PR을 열 수 있었다고 합니다.

10가지 타입 설계 패턴​

  1. 스펙의 명사는 value class로 표현합니다. 가맹점 ID, 단말 ID, 가맹정산 ID는 형식이 규제로 동일해 보이는데, plain String이면 복사-붙여넣기나 리팩터링에서 순서가 바뀌어도 컴파일이 됩니다. @JvmInline value class를 붙여 단위까지 분리하면 인자 순서가 바뀌는 실수가 빌드 에러가 됩니다.
  2. 경계에서는 sealed 팩토리로 파싱합니다. 외부에서 들어오는 필드는 모두 untyped string입니다. Result<T>로 감싸거나 runCatching으로 삼키는 대신, sealed interface 결과(예: Valid, WrongLength, NotNumeric)로 즉시 파싱합니다. when에서 else 없이 exhaustive하게 처리하면 도메인이 숨지 않습니다.
  3. 필수 필드는 nullable로 만들지 않습니다. 혹시 모르니라는 nullable이 침묵의 폴백을 만들고 진짜 원인을 숨깁니다. 경계에서 requireNotNull(raw.tvr) { "TVR null - firmware contract violated" }처럼 한 곳에서 크게 실패시키면, 모니터링 가능한 한 지점에서 터지고 하류에서는 다시는 조용히 무너지지 않습니다.
  4. 민감 정보는 기본적으로 마스킹합니다. 카드번호는 로그와 스택트레이스에 평문으로 흘러다니기 쉽고, 이는 공개 의무(disclosure obligation)로 이어집니다. private 생성자와 toString() 오버라이드로 PAN[****]가 기본값이 되게 하고, 진짜 값은 toNetwork()처럼 명시적이고 검색 가능한(grep-able) 호출로만 꺼냅니다.
  5. 상태마다 별도의 클래스를 둡니다. status 필드를 가진 가변 Transaction 하나에 의존하면 환불 가능 여부를 모든 호출자가 매번 확인해야 합니다. Captured, FullyRefunded, Reversed를 각각의 data class로 두면, 되돌려진 건을 다시 환불하는 전이가 컴파일러에 의해 차단됩니다.
  6. 불변으로 두고 전이에 이름을 붙입니다. 비즈니스 데이터를 불변으로 두고, 전이 메서드에 스펙의 동사 이름을 붙입니다. 호출될 수 없는 메서드는 아예 존재하지 않게 됩니다. @ConsistentCopyVisibility로 data class의 private 생성자를 일관되게 유지하는 것도 이 맥락입니다(Kotlin 2.0.20+).
  7. else를 지웁니다. 스펙이 모든 케이스를 명시했는데 그 외가 없다면, 코드의 else는 스펙에 없는 경우를 만들어내는 것입니다. 부분 환불이 새로 생겼을 때 예전 else는 조용히 삼켜 테스트도 통과하고 프로덕션에서만 틀립니다. else를 지우면 새 케이스 추가가 변경이 필요한 모든 지점을 가리키는 컴파일 에러가 됩니다. 분기마다 스펙이 바뀌는 결제 환경에서는 이것이 드리프트 대응의 전부입니다.
  8. 코루틴 스코프는 스펙이 정합니다. 승인, 리스크, 부정거래 체크를 각자 try/catch로 돌리다가, 부하가 걸린 부정거래 체크가 조용히 실패하고 승인만 난 사례가 있었습니다. coroutineScope는 실패 시 전부 취소(fail-fast)되어 부분 성공이 곧 장애이고, supervisorScope는 격리되어 부분 성공이 목표입니다. 어떤 것이 관용적인지가 아니라, 스펙이 한 갈래가 실패했을 때 무엇을 해야 하는지를 묻고 답해야 합니다.
  9. 타임아웃은 예외가 아니라 도메인 결과입니다. 게이트웨이 타임아웃은 아무 일도 없었다가 아니라 뭔가 일어났는데 응답을 못 들었다일 수 있습니다. 예외로 뭉개면 아무 일도 안 일어남과 일어났는데 불확실함의 차이가 사라집니다. AuthorizationOutcome의 TimedOut을 일급 결과로 모델링하면, 재시도 대신 정산 조회(reconciliation)로 갈아탈 수 있습니다. 타임아웃 후 무지성 재시도가 이중 청구를 만드는 이유입니다.
  10. 테스트는 규제기관이 읽을 수 있게 작성합니다. 인증 테스트 1,000개에 각 200줄이면 아키텍트도 읽기 어렵습니다. Kotlin DSL로 쓰면 코틀린을 모르는 인증 전문가도 스펙과 대조해 직접 서명할 수 있습니다. 테스트가 테스트 엔지니어만 검증 가능한 아티팩트에서 비즈니스가 검토할 수 있는 스펙이 됩니다.

레거시 모더니제이션​

강연자의 입장은 분명합니다. 마이그레이션은 리라이트 프로젝트로 만들지 않는 것입니다.
25년 된 Java와 C++가 매초 실거래를 처리하고 다운타임이 허용되지 않는 환경에서 리라이트는 선택지가 아닙니다.
네 개의 트랙을 순차가 아니라 병렬로 진행합니다.

  • 언어는 건드리지 않고 기존 코드베이스 구조부터 정리합니다.
  • 단위 테스트가 아니라 인수 테스트를 중심으로 둡니다.
  • 마이그레이션 내내 적합도 함수(fitness function)를 돌립니다.
  • 새 어댑터부터 점진적으로 이관합니다.

Kotlin과 Java의 상호운용이 이 점진 경로를 가능하게 합니다.
마이그레이션은 언어 취향이 아니라 투자 결정이라는 대목은 국내 증권사 앱을 운영하는 입장에서도 공감이 갑니다.

내 코드 예시​

주식 주문의 체결 상태를 enum 하나로 관리하다 환불과 취소 전이가 꼬이는 상황을 가정해 5번과 7번 패턴을 결합합니다.

// 체결 상태는 enum 문자열이 아니라 별도 타입으로
sealed interface FillStatus {
    data class Partial(val filledQty: Long, val remainingQty: Long) : FillStatus
    data class Filled(val avgPrice: Long, val at: Instant) : FillStatus
    data class Cancelled(val reason: CancelReason) : FillStatus
    data class CancelPending(val remainingQty: Long, val reason: CancelReason) : FillStatus
}

// 전이: Partial에서만 Cancel 가능. Filled/Cancelled에서는 메서드 자체가 없다
fun FillStatus.Partial.requestCancel(reason: CancelReason): FillStatus =
    if (filledQty == 0L) {
        // 체결 전 취소 요청이면 전체 취소로 전이
        FillStatus.Cancelled(reason)
    } else {
        // 이미 체결된 잔량은 확정, 남은 물량만 취소 → 잔량 취소 상태로 전이
        FillStatus.CancelPending(remainingQty, reason)
    }

fun onFillEvent(status: FillStatus): String = when (status) {
    is FillStatus.Partial -> "부분체결 ${status.filledQty}주 잔여 ${status.remainingQty}주"
    is FillStatus.Filled -> "전량체결 ${status.avgPrice}원"
    is FillStatus.Cancelled -> "취소: ${status.reason}"
    is FillStatus.CancelPending -> "잔량 ${status.remainingQty}주 취소 요청 중"
    // else 없음 — 새 상태가 추가되면 여기가 컴파일 에러로 깨진다
}

원문 예시처럼 인자 순서 실수를 막는 것도 즉시 적용 가능합니다.
주문번호, 계좌번호, 종목코드가 모두 String인 기존 코드에 value class를 적용하면 다음과 같습니다.

@JvmInline value class AccountNo(val value: String)
@JvmInline value class OrderNo(val value: String)
@JvmInline value class StockCode(val value: String)

fun requestCancel(account: AccountNo, order: OrderNo) { /* ... */ }
// requestCancel(orderNo, accountNo) — 이제 컴파일이 안 된다

이 정도만 해도 혹시 모르니의 nullable과 String 남발이 빚는 장애의 상당 부분을 빌드 타임으로 끌어올릴 수 있습니다.

실무에서 주의할 점​

  • 이 패턴들은 결제만의 이야기가 아닙니다. 주문 접수, 체결 상태 머신, 입출금 같은 국내 금융 앱의 도메인에도 그대로 적용됩니다. status: String과 조건문으로 상태를 비교하는 코드가 있다면 5번 패턴이 가장 먼저 쓸모 있습니다.
  • Kotlin Multiplatform 시나리오에도 붙습니다. 강연자는 디바이스 팀과 백엔드 팀 사이를 엔지니어가 오갈 수 있게 된 점을 언급하는데, 이는 언어 2개로 갈라진 코드베이스에서는 불가능했던 효과입니다. KMP를 도입한 조직에서 도메인 모델을 commonMain에 둘 때 정확히 이 방식으로 타입 경계를 세울 수 있습니다.
  • 오버엔지니어링 경계에 주의해야 합니다. 1번과 5번 패턴은 스펙의 명사가 있을 때 빛나지만, 단순 CRUD 화면까지 씌우면 읽기만 나빠집니다. 돈이 움직이거나 상태 전이가 되돌릴 수 없는 경계부터 적용하는 것이 실무적입니다.
  • 강연에서 언급된 22페이지짜리 엔터프라이즈 도입 플레이북(강연 이틀 전 JetBrains 사이트에 공개)은 마이그레이션의 비즈니스 케이스와 운영 모델을 다룹니다. 레거시 전환을 설득해야 하는 리더라면 원문 리캡 하단의 링크를 따라가 볼 만합니다.

마치며​

규칙을 리뷰어의 주의력에 맡기지 않고 타입에 새기면, 잘못된 상태는 코드가 되기 전에 막을 수 있습니다.
돈이 움직이는 도메인부터 작은 경계 하나씩 적용해 나가는 것이 현실적인 시작입니다.

챗봇을 넘어서 — Google ADK for Kotlin 1.0으로 앱에 AI 에이전트 붙이기

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.
최근 1.0이 공개된 Google의 Agent Development Kit(ADK) for Kotlin에 대해 설명해드리겠습니다.

배경​

앱에 AI를 넣는다는 것은 그동안 프롬프트를 보내고 텍스트를 받아 화면에 보여주는 것과 같은 의미였습니다.
챗봇은 그렇게 만들 수 있지만, 모델이 직접 앱의 데이터를 조회하고 API를 호출하는 것은 다른 차원의 일입니다.
민감한 작업을 실행하기 전에 사용자에게 확인까지 받는 구조가 필요하기 때문입니다.
ADK for Kotlin은 2026년 9월에 1.0이 공개되었고, 공식 블로그 발표는 9월 9일에 올라왔습니다.
이 글에서는 공식 발표와 10월 14일 Medium에 올라온 Sagar Singh의 튜토리얼을 함께 정리합니다.

ADK for Kotlin 살펴보기​

에이전트와 도구​

에이전트는 도구를 사용할 수 있는 모델을 말합니다.
ADK는 모델이 어떤 도구를 언제 호출할지 스스로 결정하는 루프를 프레임워크가 대신 실행해 주는 오픈소스 도구킷입니다.
개발자는 도구와 설명만 작성하면 됩니다. 도구는 그냥 코틀린 함수입니다.
도구에는 @Tool 어노테이션을 붙이고, KSP가 빌드 타임에 도구 설명을 생성합니다.
런타임 리플렉션이 없기 때문에 폰에서 시작 속도가 빠릅니다.
실행 결과는 코루틴 Flow로 돌아오므로 ViewModel에 자연스럽게 연결됩니다.

다섯 가지 구성 요소​

  • LlmAgent: 이름, 모델, 지시문, 도구 목록을 정의하는 에이전트입니다.
  • Model: 두뇌 역할을 하며, Firebase AI의 Gemini나 온디바이스 모델을 사용합니다.
  • Tools: @Tool 어노테이션을 붙인 함수들입니다.
  • Runner: 루프를 실행하고 이벤트 Flow를 반환합니다.
  • Session: 대화를 기억합니다.

1.0에서 달라진 점​

0.1.0은 I/O 2026에서 공개된 실험적인 버전이었습니다.
1.0은 ADK 1.0 Core(Python/Java)와 기능 동등성(feature parity)을 달성했고, 프로덕션용 도구킷을 표방합니다.
코어는 Kotlin Multiplatform으로 구성되어 백엔드 코틀린에서도 사용할 수 있고, 안드로이드 모듈은 별도 아티팩트로 붙습니다.
안드로이드 전용 확장으로 온디바이스(LiteRT-LM, ML Kit 베타), 하이브리드(Firebase AI Logic), 프로세스가 종료되어도 이어지는 세션(Room), 시맨틱 메모리(AppSearch)가 포함됩니다.

적용 예시​

주문 상태를 물어보면 직접 조회해서 답하는 지원 에이전트를 한투 앱 문맥으로 옮기면 뼈대는 다음과 같습니다.

// 1. 도구는 그냥 suspend 함수 + 어노테이션. Retrofit/Room 호출이 자연스럽다.
class OrderTools(private val repo: OrderRepository) {
    @Tool(description = "고객 주문의 현재 배송 상태를 반환한다.")
    suspend fun getOrderStatus(
        @Param("주문번호, 예: ORD-1042") orderId: String,
    ): Map<String, String> {
        val o = repo.getOrder(orderId) // 실제 레포지토리 호출
        return mapOf("orderId" to o.id, "status" to o.status, "eta" to o.eta)
    }
}

// 2. ViewModel은 Runner의 Flow만 collect한다.
//    "언제 도구를 호출할지"를 결정하는 if문은 내가 쓰지 않는다.
fun send(message: String) {
    viewModelScope.launch {
        runner.runAsync(
            userId = "local-user",
            sessionId = sessionId, // 같은 세션을 재사용하면 이전 대화를 기억한다
            newMessage = Content.fromText(Role.USER, message),
        ).catch { e -> _reply.value = "오류: ${e.message}" }
         .collect { event ->
            event.content?.parts?.firstOrNull()?.text
                ?.takeIf { it.isNotBlank() }
                ?.let { _reply.value = it }
        }
    }
}

빌드 한 번 돌리면 KSP가 OrderTools().generatedTools() 확장 함수를 만들어줍니다.
빨간 줄이 보이면 빌드를 한 번 돌리라는 것이 원문 튜토리얼의 팁입니다.

실무에서 주의할 점​

  • 세션은 기본이 인메모리입니다. InMemoryRunner의 대화는 프로세스가 종료되면 사라집니다. 재시작 후에도 대화를 이어가려면 Room 기반 RoomSessionService를 러너에 넘겨야 합니다. 금융 앱의 상담 흐름에서는 필수 요건입니다.
  • 민감한 작업은 확인을 강제할 수 있습니다. @Tool(requireConfirmation = true)로 선언하면 에이전트가 함수를 실행하기 전에 멈춰서 사용자의 승인을 기다립니다. 주문 취소나 이체 같은 작업의 안전장치가 프레임워크에 내장되어 있습니다.
  • Gemini Nano는 아직 도구 호출을 지원하지 않습니다. ML Kit 백엔드는 함수 호출 파트를 제외하므로, 도구를 사용하는 에이전트라면 첫 선택은 Firebase AI가 됩니다.
  • GenAI SDK의 Gemini 모델 클래스는 안드로이드 앱용이 아닙니다. README에서 안드로이드에서의 API 키와 크리덴셜 사용을 차단하고 Firebase AI를 권장합니다. 비밀 키는 APK에 넣으면 안 되므로, 이는 제약이 아니라 올바른 방향입니다.
  • 튜토리얼의 버전을 확인해야 합니다. 0.1.0(5월)에서 1.0.0(9월)으로 네 달 만에 올라오면서 의존성 이름과 셋업 단계가 바뀌었습니다. 오래된 글을 보고 1.0.0 아티팩트(com.google.adk:google-adk-kotlin-core:1.0.0 등)와 섞어 쓰면 빌드가 깨집니다. 공식 Android 가이드의 요구사항은 compileSdk 34 이상, minSdk 24 이상입니다.
  • 도구 설명이 곧 스펙입니다. 모델은 @Tool과 @Param의 description을 읽고 호출 여부를 결정합니다. 모호한 설명은 모호한 호출을 만듭니다. 지시문(instruction)도 마찬가지입니다.

마치며​

ADK for Kotlin 1.0을 적용하면, 도구를 사용하는 AI 에이전트를 코틀린 코드 안에서 구성할 수 있습니다.
세션 저장 방식과 확인 절차만 먼저 정해 두면, 금융 앱의 상담 흐름에도 단계적으로 도입할 수 있습니다.

3년 묵은 앱을 Android 17로 올리는 32개 커밋 — 마이그레이션 실전 기록

October 18, 2026 · 5 min read
Way
Android Developer

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.
3년 동안 빌드를 만지지 않은 앱을 Android 17로 올린 마이그레이션 사례에 대해 설명해드리겠습니다.

배경​

"돌아가니까 건드리지 마"는 잘 돌아갈 때만 맞는 말입니다.
오픈소스 앱 NoFlix는 2023년 중반 이후 빌드를 만지지 않은 상태였습니다.
2026년 10월, 이 앱이 한 번에 3년을 따라잡는 마이그레이션을 진행했습니다.
AGP는 8.0에서 9.4.1로, Kotlin은 1.7에서 2.4.21로, targetSdk는 33에서 37로 올렸고 16KB 페이지 대응까지 포함되었습니다.
10월 17일 Medium에 올라온 Zobaer Hossain의 케이스 스터디를 실무 관점에서 정리합니다.
가장 비싼 교훈은 업그레이드가 찾아낸 버그 4개가 마이그레이션 전부터 프로덕션에 있었다는 것입니다.

마이그레이션 순서와 안전망​

순서는 의존성 그래프를 따릅니다​

빌드 도구, SDK, 라이브러리 순으로 올립니다.
AGP 9에서 에러가 되는 항목은 마지막 AGP 8 릴리스인 8.13에서 경고로 나옵니다.
그래서 8.13.2를 디딤돌로 먼저 밟고 올라가는 방식을 사용했습니다.

안전망은 동작을 테스트합니다​

기존 유닛 테스트는 플레이스홀더뿐이었습니다.
그래서 아무것도 바꾸기 전에 Maestro UI 테스트 스위트를 바뀌지 않은 앱에 맞춰 먼저 그린으로 만들었습니다.
페이지가 스와이프된다, 당겨서 새로고침이 된다 같은 동작 기반 테스트는 Accompanist에서 Foundation으로, M2에서 M3로 구현을 교체해도 살아남았습니다.

kapt에서 KSP로​

AGP 9의 내장 Kotlin은 kotlin-kapt를 지원하지 않습니다.
Room과 Hilt는 KSP로 쉽게 옮겼지만, 유지보수가 중단된 라이브러리(Mezzanine, Anko, Edsuns HttpRequest)는 아예 교체 대상이었습니다.
이 과정에서 JitPack과 JCenter 의존성도 함께 정리되었습니다.

16KB 페이지 대응​

16KB 호환성은 APK 전체의 속성입니다.
NDK r28 이상으로 자체 네이티브 코드를 고쳐도 경고 다이얼로그가 사라지지 않았습니다.
원인은 DataStore 1.1.0-alpha04 안에 들어 있던 libdatastore_shared_counter.so 하나였습니다.
DataStore를 1.2.1로 올리니 해결되었습니다.
그래서 검사는 CI에서 모든 .so 파일을 대상으로 합니다.

# APK 안의 모든 64비트 .so가 16KB(2**14) 이상 정렬됐는지 확인
"$tools/zipalign" -c -P 16 -v 4 NoFlix.apk > /dev/null
for so in "$libs"/lib/*/*.so; do
  if "$objdump" -p "$so" | grep LOAD | grep -qv 'align 2\*\*1[4-9]'; then
    echo "::error::${so} is not 16 KB aligned"; exit 1
  fi
done

참고로 32비트 .so는 4KB 정렬을 그대로 두어도 됩니다. 16KB 페이지는 64비트 전용입니다.

targetSdk 단계별 상향​

targetSdk는 한 레벨씩, 한 커밋씩 올렸습니다.
API 35에서는 엣지투엣지가 강제되고, API 36에서는 predictive back이 기본값이 되며 600dp 이상에서 오리엔테이션 락이 무시됩니다.
API 37에서는 CT와 ECH가 기본으로 활성화됩니다.
각 단계마다 전체 테스트 스위트를 실행했습니다. 대부분은 확인 작업이었지만, 확인 자체가 일이었습니다.

AGP 9의 classpath 함정​

새 Kotlin에서 TextFieldDefaults.colors가 잡히지 않는 빌드 실패가 발생했습니다.
원인은 의존성 선언이 아니라 AGP 9가 android.dependency.useConstraints 기본값을 false로 바꾼 것이었습니다.
이전에는 전이(transitive) 제약이 선언한 Compose BOM(2023.05.00)을 컴파일과 런타임 classpath 양쪽에서 조용히 2023.06.00으로 올려 주었습니다.
AGP 9에서는 런타임에만 올라가고 컴파일은 옛날 Material 3(1.1.0과 1.0.1 불일치)를 보게 됩니다.
교훈은 명확합니다. AGP 9부터는 실제로 출하하는 버전을 직접 선언하고, 업그레이드 때마다 컴파일과 런타임 classpath를 diff로 비교해야 합니다.

minSdk는 정직해야 합니다​

기존 minSdk는 24였지만 Android 7.0 에뮬레이터에서 실행 1초 만에 NoClassDefFoundError: java/time/LocalDate로 종료되었습니다.
kotlinx-datetime이 API 26부터 있는 java.time에 의존했기 때문이고, 마이그레이션 전 빌드도 똑같이 종료되었습니다.
Core desugaring으로 고칠 수 있었지만, 같은 7.x에서 필터 호스트의 Let's Encrypt 체인이 루트 스토어에 없고 WebView 플레이어도 뜨지 않는 것이 확인되었습니다.
플레이어가 목적인 앱에서 이는 타협할 수 없는 문제라서, minSdk를 26으로 올리고 desugaring은 다시 제거했습니다.

업그레이드가 찾아낸 기존 버그​

4개의 구 버그 중 하나는 WorkManager 데드락입니다.
워커 생성자에서 AdFilter.get(context)가 싱글톤 락을 잡고, 그 초기화가 WorkManager 직렬 executor 뒤에 줄 선 getWorkInfosForUniqueWork(id).get()을 블로킹으로 기다립니다.
그런데 바로 그 executor 앞에는 자기 워커가 있어서 영원히 풀리지 않습니다.
필터 다운로드 중 앱을 종료했다가 플레이어를 열면 메인 스레드까지 같은 락을 기다려 ANR(5초)이 선언됩니다.
수정은 단순합니다. 워커가 AdFilter 전체가 아니라 데이터 스토어만 직접 열도록 BinaryDataStore.of(context)로 바꿨습니다.
이 버그는 모든 안드로이드 버전에 있었고, 7.x에서는 다운로드 자체가 되지 않아 보이지 않았을 뿐입니다.

실무에서 주의할 점​

  • targetSdk를 한 단계 올릴 때 한 레벨, 한 커밋, 전체 UI 테스트 그린 규칙은 릴리스 주기가 촘촘한 앱에도 그대로 가져갈 만합니다.
  • 엣지투엣지에는 회귀가 숨어 있습니다. enableEdgeToEdge()만 호출하면 API 29~34의 3버튼 내비게이션 뒤에 흰색 스크림(contrast enforcement)이 깔려 예전 배경과 달라집니다.
// enableEdgeToEdge()만 호출하면 API 29~34의 3버튼 내비게이션 뒤에
// 흰색 스크림(contrast enforcement)이 깔려 예전 배경과 달라진다.
enableEdgeToEdge(
    navigationBarStyle = SystemBarStyle.auto(Color.TRANSPARENT, Color.TRANSPARENT)
)
if (Build.VERSION.SDK_INT >= Build.VERSION_CODES.Q) {
    window.isNavigationBarContrastEnforced = false
}

API 35 단말에서는 강제 엣지투엣지라 문제가 없는데, 구버전 단말에서만 스크림이 튀어나오는 비대칭 회귀입니다.
원문 저자는 Android 11 에뮬레이터에서 이를 잡아냈습니다.
오래된 단말 매트릭스를 UI 테스트에 넣어두지 않으면 이런 문제는 스토어 리뷰에서 발견됩니다.
마이그레이션 대상인 NoFlix의 소스는 GitHub에서 확인할 수 있습니다.

마치며​

3년 묵은 앱도 순서를 지키고 동작 기반 테스트를 먼저 갖추면 한 번에 따라잡을 수 있습니다.
업그레이드 과정에서 드러나는 기존 버그까지 포함하면, 마이그레이션은 비용이 아니라 점검의 기회입니다.

트레이스 루트는 HTTP 호출이 아니라 비즈니스 연산이다 — KMP 모듈 OpenTelemetry 실전

October 17, 2026 · 5 min read
Way
Android Developer

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.
최근 ProAndroidDev에 소개된 KMP 모듈의 OpenTelemetry 트레이싱 적용 사례에 대해 설명해드리겠습니다.

배경​

"주문이 안 들어갔어요"라는 문의가 오면, 개발자는 주문 요청 하나를 처음부터 끝까지 추적해야 합니다.
그런데 실제 앱에서는 주문 하나가 토큰 갱신, 재시도, 여러 API 호출로 흩어져 있습니다.
각 호출의 시작과 끝 시간만 찍힌 납작한 로그로는 무엇이 무엇의 자식인지 알 수 없습니다.
Tracing Business Operations, Not HTTP Calls — Part 2는 라이브 쇼핑 앱 Tilt에서 KMP 모듈에 OpenTelemetry 분산 트레이싱을 붙인 실전 기록입니다.
2부작 중 2부로, 1부의 파이프라인 프레임워크 위에 트레이싱을 올리는 이야기입니다.

트레이싱 적용 살펴보기​

트레이스 단위는 비즈니스 연산​

  • 트레이스 단위는 HTTP 호출 1개가 아니라 비즈니스 연산 1개입니다.
  • 주문 넣기, 홈 피드 로드, 인증번호 전송 같은 연산 하나가 앱에서 시작해 마지막 백엔드 서비스까지 도달하는 단일 waterfall이 하나의 트레이스가 됩니다.
  • 레포지토리의 함수 하나는 종종 여러 쿼리와 구독을 합쳐놓습니다. GraphQL 호출 하나씩만 트레이싱하면 정확한 숫자를 틀린 것에 대해 구하게 되고, 앱 세션 전체를 트레이스로 묶으면 아무도 분석할 수 없는 거대한 트레이스가 됩니다.
  • 그래서 트레이스 루트는 경계가 있는 비즈니스 연산으로 잡아야 합니다.
  • 개발자용 API는 단순합니다. 파이프라인의 종료 지점인 buildOnce에 타입화된 연산 하나를 인자로 넘기는 것이 전부이며, 스팬을 어디서 열고 닫을지 신경 쓸 필요가 없습니다.

타입화된 연산 카탈로그​

  • 이 설계의 핵심은 타입화된 연산 카탈로그에 있습니다.
  • ShopperTracedOperation.MakeBid처럼 연산 이름과 속성(roomId, auctionId, bidValue)이 클래스 하나로 묶여 있습니다.
  • 속성 키는 상수 객체에 모아두어, 한 곳은 room_id, 다른 곳은 room.id로 쓰는 식의 조용한 Grafana 쿼리 깨짐을 막습니다.
  • 숫자 타입도 유지돼 TraceQL에서 숫자 비교가 됩니다.

SDK 격리와 결함 우회​

  • KMP SDK인 opentelemetry-kotlin은 알파 상태였습니다.
  • 글쓴이는 얇은 래퍼(Tracer, Span, SpanContext)로 SDK를 격리한 뒤, 실제 마주친 결함 3가지를 자체 코드에서 우회했습니다.
  • 오프라인 내보내기 크래시, 비-protobuf 에러 바디 크래시, 배치 스팬 프로세서의 스레드 안전성 문제가 그 대상입니다.

백엔드와의 연결​

  • 모바일에서 시작한 스팬과 백엔드 스팬은 W3C traceparent 헤더로 하나의 트레이스로 합쳐집니다.
  • 조회는 Grafana Tempo와 TraceQL로 합니다.
  • 로컬 개발용으로는 grafana/otel-lgtm 컨테이너 하나면 충분합니다.

실무에서 주의할 점​

  • 재시도는 별도 스팬으로 나눠야 합니다. 재시도 로직 위에 스팬을 열면 개별 재시도가 보이지 않습니다. 글쓴이는 Apollo 인터셉터를 재시도와 인증 아래에 둬서 물리적 요청마다 스팬을 열고, 각 요청에 traceparent를 주입했습니다.
  • 복구된 실패는 실패가 아닙니다. 재시도 성공 시 자식 스팬에는 에러가 남지만 루트 스팬은 성공입니다. 에러율 집계를 자식 스팬 기준으로 하면 모든 재시도가 오경보를 내므로, 에러율은 루트 스팬 상태 기준으로만 봐야 합니다.
  • 취소는 성공도 아닙니다. 화면을 이탈해 취소된 주문이 초기에는 트레이스 목록에서 성공처럼 보였습니다. 지금은 루트 스팬에 명시적인 cancelled 마커를 답니다.
  • 스트림은 다르게 다뤄야 합니다. 라이브 룸 같은 구독은 한 시간도 갑니다. 구독당 하나의 긴 스팬은 닫히지 않는 루트라는 세션 트레이스 안티패턴입니다. 대신 수집 시작 시 루트를 열고 첫 번째 실제 결합 상태, 즉 화면이 보여줄 데이터가 생긴 순간에 닫는 bounded root를 씁니다. 트레이싱 대상은 셋업 시간이며, emission마다 트레이스를 만들지 않는 것은 의도된 설계입니다.
  • 부모 스팬 전달은 코루틴 컨텍스트로 하지 않는 편이 좋습니다. 첫 버전은 flow 블록 안에서 withContext로 부모 스팬을 넘겼고 단위 테스트는 통과했지만, 실기기에서 "Flow invariant is violated"로 크래시했습니다. flow는 내부에서 컨텍스트를 바꿀 수 없어서, 지금은 Apollo의 ExecutionContext로 전달합니다.
  • 폰의 시계는 믿을 게 못 됩니다. 첫 E2E 트레이스에서 백엔드 스팬이 원인이 된 클라이언트 스팬보다 늦게 시작된 것처럼 보였는데, 디바이스 시계 드리프트 때문이었습니다. 앱에 있던 서버 동기화 시계를 SDK에 넘기는 방식으로 해결했습니다.
  • 알파 SDK에는 메트릭이 없습니다. SDK에 Meter 뼈대는 있지만 인스트루먼트와 내보내기가 없어서, 메트릭은 Collector의 spanmetrics 커넥터 쪽으로 넘겼습니다.
  • 운영 측면에서는 트레이싱을 앱 쪽 피처 플래그로 사용자별로 켜고, 모듈은 tracingEnabled 람다만 받습니다. 플래그는 첫 스팬 때 읽어 프로세스에 캐시하므로 트레이스 도중에 뒤집히지 않고, 엔드포인트가 없으면 트레이서는 no-op이라 SDK도 생성되지 않습니다.
  • 디바이스에서 샘플링하지 않습니다. 폰에서 샘플링하면 나중에 Collector 쪽에서 특정 사용자를 잡아내 샘플링할 수 없기 때문입니다. 볼륨은 플래그를 켠 사용자 수로 조절했고, Android부터 단계적으로 올렸습니다.
  • 두 앱은 같은 service.name으로 보고하고 플랫폼은 속성으로 둡니다. 트레이싱 대상은 거의 항상 백엔드까지 이어지기 때문입니다.
  • 알림은 페이저가 아니라 일간 다이제스트로 받습니다. 네트워크가 끊긴 한 명의 사용자가 슬로우와 행 알림을 울려 노이즈가 되기 때문입니다.

적용 예시​

한투 앱의 "주문 넣기" 연산을 트레이스 루트로 잡는다면 다음과 같이 시작할 수 있습니다.

// 1. 타입화된 연산 카탈로그 — 속성 키는 한 객체에 상수로 모은다
class PlaceOrder(accountNo: String, stockCode: String, qty: Int) :
    TracedOperation(
        name = "placeOrder",
        attributes = mapOf(
            TraceAttributes.ACCOUNT_NO to accountNo,
            TraceAttributes.STOCK_CODE to stockCode,
            TraceAttributes.QUANTITY to qty,
        ),
    )

// 2. 레포지토리 종료 지점에서 인자 하나로 옵트인 — 스팬 위치는 신경 쓰지 않는다
suspend fun placeOrder(...): Result<Order> =
    source(accountStore.account)
        .transformToSource { acct -> source(orderApi.place(acct, req)) }
        .buildOnce(TracedOperation.PlaceOrder(accountNo, stockCode, qty))

개발자가 매일 새 쿼리를 추가하는 환경이라면, 추가 가이드를 읽지 않고도 트레이스를 볼 수 있게 만드는 것이 완성 기준이 됩니다.
트레이싱 가이드를 문서화하고, 붙여넣기 바로 가능한 TraceQL 쿼리를 주는 것까지가 프로젝트의 범위에 들어갑니다.
1부의 파이프라인 프레임워크 이야기는 Everything Is a Source — Part 1에서도 확인할 수 있습니다.

마치며​

트레이싱의 단위를 HTTP 호출이 아니라 비즈니스 연산으로 잡으면, 장애 추적이 로그 뒤지기에서 waterfall 읽기로 바뀝니다.
KMP 모듈에 적용할 때도 연산 카탈로그와 속성 키 상수화부터 정리해두면, 조회 단계에서의 혼란을 크게 줄일 수 있습니다.

init { load() }을 지우는 법 — stateIn으로 ViewModel UI 상태를 선언적으로

October 17, 2026 · 4 min read
Way
Android Developer

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.
최근 ProAndroidDev에 소개된 stateIn 기반 ViewModel 상태 선언 방식에 대해 설명해드리겠습니다.

배경​

ViewModel을 열면 거의 항상 비슷한 패턴이 나옵니다.
private val _uiState = MutableStateFlow(UiState())를 선언하고, init에서 load()를 호출하고, 데이터가 오면 .update로 복사하는 방식입니다.
틀린 코드는 아닙니다. 그런데 화면이 커질수록 이 수동 동기화 코드가 어딘가에서는 반드시 어긋나기 시작합니다.
The Power of stateIn in ViewModel에서는 이 문제를 명령(command)과 상태(state)의 구분으로 풀어냅니다.

stateIn으로 상태 선언하기​

핵심 요약​

  • init에서 로드하고 수동으로 _uiState를 갱신하는 패턴은, 상태가 어떻게 도출되는지가 아니라 언제 복사했는지를 코드에 남깁니다.
  • 입력이 하나만 있을 때는 괜찮지만, 검색어와 필터와 새로고침처럼 입력이 늘어나면 동기화 누락이 생깁니다.
  • 핵심 원칙은 하나입니다. MutableStateFlow는 수정 가능한 입력에만 두고, 파생 상태는 Flow 연산자로 표현해 stateIn으로 StateFlow로 노출합니다.
  • stateIn 자체는 데이터를 가져오지 않습니다. 상류 Flow가 뱉은 값을 공유하고 유지할 뿐이며, SharingStarted.WhileSubscribed(5_000) 같은 공유 전략은 화면 생명주기에 맞춰 선택해야 합니다.

명령과 상태의 구분​

  • 명령(commands)은 무슨 일이 일어나야 하는지를 뜻합니다. "제출해라", "삭제해라", "새로고침해라"처럼 사용자의 명시적 동작에 대한 반응입니다.
  • 상태(state)는 지금 무엇이 사실인지를 뜻합니다. "보이는 목록은 items와 query로부터 도출된다"처럼 관계가 코드에 선언됩니다.
  • 문제는 명령으로 상태를 동기화하려고 할 때 생깁니다.
  • 레포지토리가 이미 val items: Flow<List<Item>>을 들고 있는데도 ViewModel이 collect 해서 _uiState에 복사하고, 쿼리가 바뀌면 또 복사하는 구조에서는, 보이는 목록을 다시 계산해야 하는 모든 장소를 사람이 기억해야 합니다.

stateIn으로 바뀌는 코드​

  • 입력은 그대로 두되, 파생 UI 상태는 연산자로 표현합니다.
class PortfolioViewModel(repository: HoldingRepository) : ViewModel() {

    // 입력: 사용자가 바꾸는 검색어 — MutableStateFlow가 맞다
    private val query = MutableStateFlow("")

    // 파생 상태: 레포지토리 데이터 + 검색어로 도출 — map/combine이 관계다
    val uiState: StateFlow<PortfolioUiState> =
        combine(repository.holdings, query) { holdings, query ->
            PortfolioUiState(
                holdings = holdings.filter { it.matches(query) },
                query = query,
            )
        }.stateIn(
            scope = viewModelScope,
            started = SharingStarted.WhileSubscribed(5_000),
            initialValue = PortfolioUiState(),
        )

    fun onQueryChanged(query: String) {
        this.query.value = query // UI 액션은 입력만 바꾼다
    }
}
  • 사라지는 것들을 세어보면 명확해집니다. 수동 _uiState, init 블록, 복사용 load(), 레포지토리와 UI 모델 사이의 수동 동기화가 모두 없어집니다.
  • UI 액션인 onQueryChanged는 uiState를 직접 건드리지 않고 입력만 바꿉니다.
  • 양쪽 입력 중 하나라도 바뀌면 파생 상태가 자동으로 갱신됩니다.

공유 전략은 생명주기를 보고 고르기​

  • WhileSubscribed(5_000)는 첫 구독자가 생기면 상류를 수집하고, 마지막 구독자가 사라진 지 5초 후에 수집이 멈춥니다.
  • 타임아웃은 화면 회전 같은 짧은 구독 공백에서 상류 스트림이 끊겼다 다시 붙는 것을 막아줍니다.
  • 단, 글쓴이가 경고하는 함정이 있습니다. 수집이 멈췄다가 재개된다고 네트워크 요청이 반드시 다시 나가는 것은 아닙니다.
  • 그 동작은 상류 Flow가 어떻게 구현됐느냐에 달렸습니다. 레포지토리의 캐시와 공유 전략이 실제 동작을 결정합니다.
  • 공유 전략은 관성처럼 쓰는 관용구가 아니라, 원하는 생명주기 동작을 보고 선택해야 합니다.

실무에서 주의할 점​

  • **LaunchedEffect(Unit) { viewModel.load() }**로 화면에 들어갈 때마다 다시 로드하는 패턴은 "명령으로 상태를 동기화"하는 전형적인 예입니다. 그 데이터가 이미 레포지토리의 Flow로 존재한다면 stateIn 파생으로 바꾸는 것이 낫습니다.
  • 명시적 명령이 정당한 경우도 있습니다. 폼 제출, 삭제, 사용자가 누른 새로고침처럼 이벤트에 대한 반응은 명령으로 두어야 합니다. 모든 것을 Flow로 감싸지 않는 것이 중요합니다. 제거 대상은 "파생 상태를 동기화하기 위한 명령"뿐입니다.
  • 테스트가 쉬워집니다. 파생 로직은 순수 함수인 map과 combine 변환이라 ViewModel 전체를 띄우지 않고도 검증할 수 있습니다.
  • SharingStarted 선택은 코드 리뷰 포인트로 남겨두는 것이 좋습니다. WhileSubscribed와 Eagerly의 차이는 상류 비용(소켓, 폴링, 가격 스트리밍)을 누가 내는가와 직결됩니다.
  • 가격 스트리밍처럼 상류가 비싼 Flow라면, 파생 전에 레포지토리 단에서 공유를 정리하는 방식이 좋습니다.
// Repository: 비싼 상류를 여기서 공유 — ViewModel은 몰라도 된다
val holdings: Flow<List<Holding>> = priceSocket.stream()
    .map(::toHoldings)
    .shareIn(
        scope = externalScope,
        started = SharingStarted.WhileSubscribed(5_000),
        replay = 1,
    )
  • 이렇게 두면 ViewModel은 combine(holdings, query) 하나로 "검색어에 맞는 보유종목"이라는 관계를 선언합니다.
  • 소켓 구독 시점과 구독 종료 시점 같은 생명주기 판단은 공유 전략 선언 한 곳에서만 일어납니다.
  • 화면이 두 개로 늘어나도 동기화 코드를 복사해 붙여넣지 않아도 됩니다.

마치며​

상태를 명령으로 동기화하는 코드를 걷어내면, ViewModel에는 입력과 도출 관계만 남습니다.
입력은 MutableStateFlow로, 파생 상태는 연산자와 stateIn으로 선언하는 기준을 팀 규칙으로 정해두면 화면이 커져도 동기화 누락을 막을 수 있습니다.

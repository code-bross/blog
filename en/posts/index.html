Java와 Kotlin by IntelliJ IDEA 1.0, VS Code와 Cursor에서 쓰는 IntelliJ의 언어 지능

October 31, 2026 · 4 min read
Way
Android Developer

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.
2026년 10월에 정식 1.0으로 공개된 Java and Kotlin by IntelliJ IDEA에 대해 설명해드리겠습니다.

배경​

에이전트가 구현을 맡는 비중이 커지면서 개발자의 편집 방식도 바뀌고 있습니다.
직접 코드를 길게 쓰는 시간보다 선언으로 이동하고 참조를 찾고 이름을 바꾸는 시간이 늘었습니다.
이런 기능은 Language Server Protocol이 태어난 이유와 정확히 맞닿아 있습니다.
언어 지원을 한 번 구현하면 LSP를 지원하는 어떤 에디터에서도 재사용할 수 있습니다.
JetBrains은 이런 흐름에 맞춰 IntelliJ IDEA의 JVM 언어 지능을 IDE 밖으로 꺼냈습니다.
프리뷰 공개 약 10주 뒤, VS Code와 Cursor용 확장 기능이 1.0에 도달했습니다.

Java and Kotlin by IntelliJ IDEA 1.0 살펴보기​

1.0에 담긴 기능​

1.0은 IntelliJ IDEA 데스크톱 IDE와 같은 Java와 Kotlin 언어 기술을 사용합니다.
Java와 Kotlin, 혼합 언어 프로젝트를 지원합니다.
스마트 코드 완성과 탐색, 코드 분석을 제공합니다.
리팩터링과 에디터 보조 기능도 포함되어 있습니다.
Maven과 Gradle, Bazel 빌드 도구를 지원합니다.
대규모 프로젝트와 모노레포에서도 빠른 성능을 목표로 합니다.
테스트 러너는 현재 JUnit을 지원합니다.
디버깅은 에뮬레이션된 중단점과 비동기 스택 트레이스를 포함합니다.

설치 방법​

확장 기능은 Visual Studio Marketplace나 Open VSX Registry에서 받을 수 있습니다.
에디터 안에서는 명령 팔레트에 아래 명령을 붙여넣는 방식으로 설치합니다.
Cursor에서는 IDE 모드로 전환한 뒤 같은 명령을 사용합니다.

.ext install JetBrains.intellij-server

설치가 끝나면 프로젝트를 열 때 빌드 파일을 기준으로 가져오기가 진행됩니다.
Maven과 Gradle, Bazel 중 프로젝트에 맞는 빌드 파일을 자동으로 인식합니다.
가져오기가 끝나면 Java와 Kotlin 언어 기능이 에디터에서 활성화됩니다.

Cursor 전용 지원​

Cursor에서는 Agents Window 전용 지원이 따로 마련되어 있습니다.
Agents Window는 자체 언어 서버 인스턴스를 이용해 분석 기능을 제공할 수 있습니다.
JSpecify 기반 널 가능성 지원과 Spring Framework 특화 분석이 포함됩니다.
이 출시는 Cursor 팀과의 긴밀한 협업으로 만들어졌다고 JetBrains은 설명합니다.

팀에서 함께 쓰기 위한 설정​

팀원 모두가 같은 확장을 쓰도록 권장 목록 파일로 공유할 수 있습니다.
프로젝트 루트에 아래 파일을 두면 VS Code가 확장 설치를 권합니다.

{
  "recommendations": [
    "JetBrains.intellij-server"
  ]
}

충돌 주의 사항​

Red Hat이나 Oracle의 Java 확장과는 코드 분석과 빠른 수정 기능이 겹칩니다.
동작이 중복되거나 충돌할 수 있으므로 함께 쓸 때는 해당 확장을 비활성화하는 것이 권장됩니다.
Spring 팀의 Spring Tools와는 함께 잘 동작하도록 맞춰져 있습니다.

라이선스 변경 사항​

1.0부터는 프리뷰 단계의 무료 제공이 끝났습니다.
30일 평가판 이후에는 IntelliJ IDEA Ultimate 구독이 필요합니다.
하나의 라이선스로 데스크톱 IDE와 VS Code 계열 에디터를 함께 쓸 수 있습니다.
라이선스는 인간 사용을 기준으로 설계되었습니다.
순수 에이전트 사용을 위한 라이선스 모델은 추후 안내될 예정입니다.

실무 관점​

Android Studio가 주 IDE인 팀이라면 이 확장이 주 IDE를 대체하지는 않습니다.
Cursor나 VS Code에서 코드 리뷰나 에이전트 작업을 할 때 IntelliJ 수준의 분석을 빌려오는 용도가 맞습니다.
Gradle 프로젝트는 빌드 파일 기준으로 가져오기가 진행되므로 모듈 구조가 복잡하면 초기 인덱싱 시간을 봐야 합니다.
팀 단위로 도입하기 전에는 Ultimate 구독 비용과 평가판 종료 시점을 먼저 확인하는 것이 좋습니다.
기존 Java 확장을 끄는 설정까지 권장 파일에 함께 정리해 두면 온보딩 마찰이 줄어듭습니다.

마치며​

Java와 Kotlin by IntelliJ IDEA 1.0은 IDE 밖에서도 IntelliJ의 언어 지능을 쓸 수 있게 한 릴리스입니다.
에이전트 시대의 편집 방식에 맞춰 탐색과 리팩터링 같은 핵심 기능에 집중한 구성이 돋보입니다.

Kotlin Toolchain 0.13 — 새 KMP 프로젝트는 kotlin new로 시작하기

October 8, 2026 · 3 min read
Way
Android Developer

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.
JetBrains가 공개한 Kotlin Toolchain 0.13에 대해 설명해드리겠습니다.

배경​

신규 Kotlin Multiplatform(KMP) 프로젝트를 시작할 때는 Gradle 설정 파일을 손으로 짜는 것부터 시작하는 경우가 많았습니다.
JDK나 Android SDK 같은 필수 도구가 갖춰져 있지 않으면, 새 노트북에서 프로젝트를 처음 열었을 때 동기화부터 실패하곤 했습니다.
이번 0.13부터 JetBrains는 신규 KMP 프로젝트에 이 툴체인을 쓰는 것을 공식 권장 경로로 제시했습니다.
자세한 내용은 Kotlin 블로그 원문에서 확인할 수 있습니다.

Kotlin Toolchain 살펴보기​

Kotlin Toolchain은 JVM·Android·iOS·멀티플랫폼·서버 앱을 하나의 CLI 진입점으로 만들고, 빌드하고, 테스트하고, 배포하는 도구입니다.
필수 도구들을 선언적 설정에 맞춰 자동으로 내려받아 주기 때문에 온보딩 과정의 마찰이 크게 줄어듭니다.

kotlin new: 대화형 프로젝트 생성​

0.13의 핵심은 kotlin new 명령입니다.
웹의 KMP Wizard처럼 앱 유형을 고르고 타깃 플랫폼을 선택하면 프로젝트가 생성됩니다.
기존 kotlin init도 같은 흐름으로 맞췄는데, 차이는 kotlin init이 현재 디렉터리에 바로 파일을 만든다는 점입니다.

# 새 프로젝트 생성 (대화형)
kotlin new

# 이미 설치돼 있다면 업데이트
kotlin update

Android 개발자 관점에서 달라진 부분​

  • Android SDK 자동 프로비저닝이 IDE까지 확장: 이전에는 kotlin build/kotlin run 때만 SDK가 자동 설치돼서, 빌드 전에 IDE로 먼저 열면 SDK 누락 오류가 났습니다. 이제 프로젝트 import 시점에도 누락된 SDK 컴포넌트를 자동으로 받아 줍니다.
  • namespace/applicationId 검증 강화: com.example.app 같은 샘플 ID로 실수로 배포 빌드를 만드는 실수를 막아 줍니다.
  • 다운로드 진행 표시: JDK, Android SDK, iOS 런타임, 컴파일러 다운로드가 CLI에 진행 바로 표시됩니다.

Swift Package Manager 의존성 지원​

Apple 타깃에서 SPM 패키지를 선언적으로 가져올 수 있게 됐습니다.
설정 파일에 저장소와 버전을 적으면 됩니다.

dependencies:
  - swiftPackage:
      repository: "https://github.com/firebase/firebase-ios-sdk.git"
      version: "12.17.0"
      products: ["FirebaseCore", "FirebaseFirestore", "FirebaseAnalytics"]

가져온 Objective-C API는 swiftPMImport 접두사로 네임스페이스가 붙어, Kotlin 코드에서 명시적으로 구분됩니다.
로컬 SPM 패키지는 localSwiftPackage 키로 연결할 수 있습니다.

빌드 속도: Kotlin/Native 컴파일러 캐시​

Kotlin/Native 재빌드가 빨라집니다.
컴파일된 네이티브 의존성을 빌드 간, 심지어 프로젝트 간에 캐시로 재사용하고, 프로젝트 코드는 파일 단위 캐시로 링크 시 바뀐 부분만 다시 컴파일합니다.
기존 settings.kotlin.compileIncrementally 설정을 그대로 쓰고, .klib 컴파일 자체는 전체로 수행됩니다.

그 외 변경 사항​

  • IDE 동기화 상태를 에디터에서 확인할 수 있게 됐습니다.
  • 멀티플랫폼 라이브러리 배포 시 Compose Resources와 SwiftPM 의존성 메타데이터가 아티팩트와 함께 게시되고, 서드파티 멀티플랫폼 라이브러리의 Compose Resources도 해석됩니다.
  • AI 에이전트 연동도 강화됐습니다. Compose Hot Reload MCP 서버와 Kotlin용 에이전트 스킬(npx skills add kotlin/kotlin-agent-skills)이 제공됩니다.
  • IDE 기능은 IntelliJ IDEA 2026.2.3 또는 Android Studio Rabbit 1(2026.2.1) 이상에서 최신 Kotlin Toolchain 플러그인과 함께 쓸 수 있습니다.

실무에서 주의할 점​

기존 Gradle 기반 프로젝트를 당장 마이그레이션해야 하는 것은 아닙니다.
JetBrains도 로드맵에서 Gradle 프로젝트의 공백을 먼저 메우는 데 집중하겠다고 밝혔습니다.
따라서 운영 중인 프로젝트는 기존 흐름을 유지하고, 신규 프로젝트나 사이드 프로젝트부터 적용해 보는 것이 안전합니다.

마치며​

새로 KMP를 시작한다면 kotlin new 한 번으로 Android·iOS 환경을 한 번에 맞추는 경험은 꽤 매력적입니다.
다음에 KMP 프로젝트를 시작할 일이 있으면 이 경로로 시작해 보시기 바랍니다.

AppState StateStore 첫 알파, Compose 상태를 앱 계층으로 끌어올리기

October 30, 2026 · 2 min read
Way
Android Developer

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.
2026년 10월 28일에 첫 알파로 공개된 AppState StateStore에 대해 설명해드리겠습니다.

배경​

Compose 상태는 보통 화면이나 ViewModel 안에 머무릅니다.
앱 전역에서 공유해야 하는 상태는 계층을 옮길 때마다 전달 코드가 늘어납니다.
상태를 앱 계층으로 끌어올리면 공유와 저장이 한곳에서 관리됩니다.
StateStore는 이 역할을 맡기 위해 새로 공개된 라이브러리입니다.

StateStore 살펴보기​

Compose 런타임 기반의 상태 저장소​

StateStore는 Compose 런타임을 기반으로 동작합니다.
스냅샷 상태를 앱 계층으로 끌어올려 커스텀 연동을 제공하는 래퍼입니다.
화면이 사라져도 상태의 수명을 앱 수준에서 유지할 수 있습니다.

DataStore 연동으로 상태 유지하기​

statestore-datastore 아티팩트는 상태 영속성을 제공합니다.
syncToDataStore로 스냅샷 상태를 DataStore 파일과 동기화할 수 있습니다.
앱을 다시 시작해도 이전 상태를 복원할 수 있습니다.

class MyApplication : Application() {
    val stateStore = StateStore()
    private val scope = CoroutineScope(SupervisorJob() + Dispatchers.Default)

    override fun onCreate() {
        super.onCreate()
        scope.launch {
            launch {
                try {
                    stateStore.syncToDataStore(
                        dataStoreFile("settings").absolutePath,
                        this
                    )
                } catch (e: Exception) {
                    e.printStackTrace()
                }
            }
        }
    }
}

의존성 추가하기​

Android 타깃 기준 의존성은 다음과 같습니다.

dependencies {
    implementation("androidx.appstate.statestore:statestore:1.0.0-alpha01")
    implementation("androidx.appstate.statestore:statestore-datastore:1.0.0-alpha01")
}

함께 공개된 Transform​

같은 날짜에 appstate-transform 아티팩트도 첫 알파로 공개되었습니다.
이 글에서는 StateStore의 개념과 저장 연동에 집중합니다.
Transform의 구체적인 활용은 후속 릴리스 노트에서 확인한 뒤 다루는 것이 좋습니다.

실무 관점​

첫 알파 단계이므로 운영 코드에 바로 도입하지 않는 것이 좋습니다.
상태를 앱 계층으로 올리면 수명과 동기화 시점을 직접 설계해야 합니다.
동기화 중 예외가 나면 상태가 저장되지 않으므로 실패 처리 경로를 함께 둡니다.
MTS처럼 세션과 설정 상태가 많은 앱에서는 저장 단위부터 나누는 것이 안전합니다.

마치며​

StateStore는 Compose 상태를 앱 계층에서 관리하는 새로운 선택지입니다.
DataStore 연동까지 함께 보면 상태 공유와 영속성을 한 구조로 정리할 수 있습니다.

Kotlin 2.5.0-Beta2, 이름 기반 구조 분해와 반환값 검사기

October 30, 2026 · 3 min read
Way
Android Developer

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.
2026년 10월 21일에 공개된 Kotlin 2.5.0-Beta2에 대해 설명해드리겠습니다.

배경​

기존 구조 분해는 위치를 기준으로 동작했습니다.
프로퍼티 순서가 바뀌면 구조 분해 결과도 함께 바뀌는 문제가 있었습니다.
반환값을 무시하고 호출해도 컴파일러가 이를 지적하지 않는 경우도 있었습니다.
이번 베타는 이런 지점을 언어 차원에서 다듬은 릴리스입니다.

Kotlin 2.5.0-Beta2 살펴보기​

이름 기반 구조 분해​

이름 기반 구조 분해는 only-syntax 모드에서 정식 기능이 되었습니다.
기존 문법 val (name, age)는 위치 기반 동작을 그대로 유지합니다.
새 문법 (val name, val age)는 이름을 기준으로 값을 꺼냅니다.
순서와 무관하게 프로퍼티 이름으로 매칭되므로 리팩터링에 안전합니다.

data class User(val name: String, val age: Int)

fun printUser(user: User) {
    (val age, val name) = user
    println("$name, $age")
}

반환값 검사기​

반환값 검사기는 이번 릴리스에서 기본으로 활성화됩니다.
의미 있는 반환값을 버리고 호출하면 컴파일러가 경고를 냅니다.
검사 강도는 -Xreturn-value-checker 옵션으로 조절할 수 있습니다.
자체 함수에는 MustUseReturnValues 애너테이션으로 검사 대상을 표시할 수 있습니다.

kotlin {
    compilerOptions {
        freeCompilerArgs.add("-Xreturn-value-checker=check")
    }
}

Java 28 지원과 JDK 17 요구 사항​

Kotlin/JVM은 Java 28을 지원합니다.
컴파일러 실행에는 JDK 17 이상이 필요합니다.
Beta1에서는 오래된 JDK에서 경고만 나왔습니다.
Beta2와 정식 2.5.0에서는 오류가 나며, 임시 플래그로만 구버전 사용을 이어갈 수 있습니다.
2.5.20-Beta1부터는 JDK 17 이상이 필수입니다.
CI 머신의 JDK 버전을 먼저 확인하는 것이 좋습니다.

Swift Export와 네이티브 개선​

Swift Export는 새 DSL과 함께 베타 단계에 들어갔습니다.
Kotlin/Native 증분 컴파일은 Apple 타깃에서 기본으로 활성화됩니다.
멀티플랫폼 프로젝트의 iOS 빌드 시간이 줄어들 것으로 기대됩니다.

버전 적용 예시는 다음과 같습니다.

kotlin = "2.5.0-Beta2"

베타 릴리스이므로 운영 모듈에 바로 적용하지 않는 것이 좋습니다.
별도 브랜치에서 컴파일과 테스트를 먼저 통과시키는 것이 안전합니다.
이름 기반 구조 분해는 신규 코드부터 점진적으로 적용할 수 있습니다.
JDK 버전이 낮은 CI가 있다면 릴리스 전에 교체 계획을 세워야 합니다.

마치며​

JDK 요구 사항까지 함께 확인하면 베타 검증이 한결 수월해집니다.

AppFunctions 베타와 A2UI 알파, 앱이 에이전트와 연결되는 방법

October 29, 2026 · 3 min read
Way
Android Developer

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.
2026년 10월 28일에 열린 Android Dev Summit 2026에서 공개된 AppFunctions의 베타와 A2UI, ML Kit Agentic API에 대해 설명해드리겠습니다.

배경​

사용자는 앱의 화면을 하나씩 눌러 가며 작업을 마치는 대신, 말로 요청하고 결과를 받는 방식에 익숙해지고 있습니다.
기존 앱은 화면 중심이라, 에이전트가 앱의 기능을 호출할 공식 경로가 없었습니다.
화면 자동화 방식은 깨지기 쉽고, 앱이 의도하지 않은 동작까지 허용할 위험이 있습니다.
AppFunctions는 앱이 스스로 공개한 기능만을 에이전트가 호출하게 만드는 구조입니다.

AppFunctions와 에이전트 API 살펴보기​

AppFunctions 베타​

AppFunctions는 앱의 기능을 온디바이스 또는 시스템 에이전트에 노출하는 통합 도구 호출 계층입니다.
연결 방식은 Model Context Protocol 기반의 Android MCP이며, Android 16 이상 기기에서 동작합니다.
Jetpack 라이브러리는 2026년 10월 21일 기준 1.0.0-beta01이 공개되어 있습니다.
함수는 AppFunction 어노테이션으로 선언하고, KDoc 설명이 도구의 스키마로 함께 전달됩니다.
에이전트는 앱이 공개한 함수만 발견하고 실행하므로, 노출 범위를 앱 개발자가 직접 정할 수 있습니다.

dependencies {
    implementation("androidx.appfunctions:appfunctions:1.0.0-beta01")
    ksp("androidx.appfunctions:appfunctions-compiler:1.0.0-beta01")
}
@AppFunction(isDescribedByKDoc = true)
suspend fun getFavoriteStockPrice(
    symbol: String
): StockPrice {
    // 관심 종목의 현재 시세를 조회하는 함수입니다.
    return repository.getPrice(symbol)
}

A2UI 알파​

에이전트의 답변이 텍스트로만 나오면, 사용자는 다시 앱 화면으로 돌아가 확인해야 합니다.
A2UI는 에이전트가 앱 자체의 컴포넌트로 만든 인터랙티브 화면을 그대로 보여주는 방식입니다.
Jetpack Compose용 네이티브 렌더러가 포함되어 있어, 에이전트 응답이 앱의 UI로 자연스럽게 이어집니다.
현재 알파 단계이며, AppFunctions와 함께 앱의 에이전트 경험을 구성하는 한 축입니다.

ML Kit Agentic API 알파​

온디바이스에서 동작하는 에이전트 기능은 ML Kit의 Agentic API가 담당합니다.
Gemini Nano 4를 기반으로 하며, 함수 실행과 대화 기록 저장, 오케스트레이션 루프 관리, 자동 가드레일을 함께 제공합니다.
앱 안에서 도구를 실행하는 에이전트를 만들 때, 호출과 기록과 안전장치를 직접 구현하지 않아도 됩니다.
AppFunctions로 공개된 기능도 이 API를 통해 발견하고 실행할 수 있습니다.

Connected Apps Platform 프리뷰​

앱의 서비스를 Gemini와 검색까지 연결하는 통로는 Connected Apps Platform 프리뷰가 담당합니다.
Android MCP나 원격 MCP 서버로 연동하고, Google Connected Console에서 등록해 관리합니다.
Google은 Adobe와 Peloton, Experian 등 50개 이상의 파트너 연동이 이미 Gemini 앱에서 동작하고 있다고 밝혔습니다.

실무 관점​

MTS 앱에 적용한다면, 노출할 함수의 범위를 정하는 일이 구현보다 먼저입니다.
주문이나 이체 같은 자금 이동 기능은 에이전트 호출 경로에 두지 않는 것이 안전합니다.
시세 조회나 관심 종목 확인처럼 읽기 전용 기능부터 베타 단계에서 검증하는 순서가 적절합니다.
아직 베타와 알파 단계라 API가 바뀔 수 있으므로, 노출 함수는 별도 모듈로 분리해 교체 비용을 낮추는 것이 좋습니다.

마치며​

AppFunctions는 앱을 화면의 집합이 아니라 에이전트가 호출할 수 있는 기능의 집합으로 바꾸는 시도입니다.
A2UI와 온디바이스 Agentic API가 함께 갖춰지면서, 앱 안에서의 에이전트 경험이 텍스트 응답을 넘어 실제 화면 동작으로 이어지게 되었습니다.

PhotoPicker 1.0.0-alpha03 — 임베디드 사진 선택기와 아티팩트 개명

October 28, 2026 · 3 min read
Way
Android Developer

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.
2026년 10월 21일에 공개된 PhotoPicker 1.0.0-alpha03에 대해 설명해드리겠습니다.

배경​

기존 사진 선택은 시스템 사진 선택기를 별도 화면으로 띄워서 결과를 돌려받는 방식이었습니다.
작성 중인 화면을 벗어났다가 돌아오는 흐름이라, 채팅이나 게시물 작성처럼 맥락이 중요한 화면에서는 흐름이 끊기기 쉬웠습니다.
임베디드 사진 선택기는 선택기 자체를 앱 화면 안에 직접 내장하는 방식입니다.
사용자는 작성 화면을 벗어나지 않고 사진을 고를 수 있습니다.

PhotoPicker 1.0.0-alpha03 살펴보기​

아티팩트 개명​

이번 버전에서 아티팩트 이름이 정리되었습니다.
photopicker는 photopicker-embedded로, Compose용 아티팩트는 photopicker-embedded-compose로, 테스트용 아티팩트는 photopicker-embedded-testing으로 바뀌었습니다.
패키지도 androidx.photopicker.embedded 계열로 함께 이동했습니다.
이름에 임베디드라는 목적이 드러나면서, 시스템 선택기용 계약과의 구분이 명확해졌습니다.

dependencies {
    implementation("androidx.photopicker:photopicker-embedded-compose:1.0.0-alpha03")
    implementation("androidx.photopicker:photopicker-embedded:1.0.0-alpha03")
}

위치 메타데이터 접근 요청​

사진 요청에 위치 메타데이터 접근을 함께 요청할 수 있게 되었습니다.
PickVisualMediaRequest에 setLocationMetadataAccessRequested가 추가되었고, 시스템 폴백 선택기용으로 위치 메타데이터 접근 요청을 전달하는 엑스트라도 추가되었습니다.
임베디드 선택기가 동작하지 않아 시스템 선택기로 떨어지는 경우에도, 같은 요청 의도가 이어지도록 만든 변경입니다.

// 사진 요청에 위치 메타데이터 접근을 함께 요청합니다
request.setLocationMetadataAccessRequested(true)

상태 리셋은 key 블록으로​

rememberEmbeddedPhotoPickerState에서 inputs 파라미터가 제거되었습니다.
입력 값이 바뀌었을 때 상태를 초기화하려면, 호출부를 key 블록으로 감싸는 방식으로 바뀌었습니다.
상태 초기화 조건이 호출부에서 눈에 보이게 되므로, 언제 리셋되는지 파악하기 쉬워졌습니다.

key(selectedAlbumId) {
    val state = rememberEmbeddedPhotoPickerState()
    EmbeddedPhotoPicker(state = state)
}

상태 API 정리​

EmbeddedPhotoPickerState도 정리되었습니다.
surfacePackage와 notifyVisibilityChanged가 노출되었고, onError 콜백이 추가되었습니다.
선택기 표면의 가시성 변화를 앱이 직접 통지할 수 있게 되었고, 실패 상황도 콜백으로 받아 처리할 수 있습니다.

최소 SDK와 호출 가능 버전​

두 라이브러리의 최소 SDK가 23으로 낮아졌습니다.
다만 관련 API 호출은 여전히 API 34부터 필요합니다.

실무 관점​

2026년 10월 21일에 공개된 Room 3.1.0-alpha03에 대해 설명해드리겠습니다.

배경​

Room 3.0은 패키지를 androidx.room3으로 바꾸고 Kotlin Multiplatform을 중심으로 다시 설계된 버전입니다.
3.1.0-alpha01에서는 연결 풀 타임아웃 설정과 프로퍼티 중심 어노테이션, kotlin.uuid.Uuid 컨버터 같은 변경이 먼저 들어왔습니다.

Room 3.1.0-alpha03 살펴보기​

손상된 데이터베이스 복구​

RoomDatabase.Builder에 allowDataLossOnRecovery()가 추가되었습니다.
데이터베이스 열기나 손상 복구에 실패했을 때, 데이터 손실을 감수하고 복구를 시도하도록 허용하는 설정입니다.
앱이 아예 실행되지 않는 상황보다는, 일부 데이터를 잃더라도 다시 동작하는 편이 나은 화면에서 의미가 있습니다.

// 데이터베이스 열기 실패 시 데이터 손실을 감수하고 복구를 시도합니다
builder.allowDataLossOnRecovery()

복구가 동작했다는 사실 자체가 데이터가 온전하지 않을 수 있다는 신호입니다.
복구 뒤에는 서버에서 다시 내려받을 수 있는지를 먼저 확인하는 흐름이 필요합니다.

준비된 문장 캐시 크기 설정​

setPreparedStatementCacheSize(maxCacheSize)가 RoomDatabase.Builder에 추가되었습니다.
연결마다 유지하는 준비된 문장 캐시의 크기를 직접 정하거나, 비활성화할 수 있게 되었습니다.
자주 반복되는 쿼리가 많은 화면에서는 캐시를 키우고, 메모리가 빠듯한 환경에서는 크기를 줄이는 식으로 조절할 수 있습니다.

// 연결당 준비된 문장 캐시의 크기를 직접 지정합니다
builder.setPreparedStatementCacheSize(64)

캐시를 무조건 크게 잡는 것이 정답은 아닙니다.
한 번만 실행되는 쿼리가 많은 앱에서는 캐시가 메모리만 차지하고 끝날 수 있습니다.

Kotlin 2.2 요구 사항​

3.1.0-alpha03부터 라이브러리는 Kotlin 2.2을 대상으로 빌드되고, kotlinc 2.2가 필요합니다.
프로젝트의 Kotlin 버전이 그보다 낮다면, Room을 올리기 전에 Kotlin부터 먼저 올려야 합니다.
버전 올림 순서를 바꾸면 빌드 오류의 원인을 찾기 어려워지므로, Kotlin과 Room의 변경은 따로 커밋하는 편이 안전합니다.

비결정적 절과 @Relation 재실행 수정​

ORDER BY RANDOM() LIMIT :count 같은 비결정적 절을 @Relation 쿼리와 함께 쓰면, 문장 리셋 시 쿼리가 다시 실행되어 관계 매핑이 실패하는 문제가 있었습니다.
이번 버전에서 해당 문제가 수정되었습니다.
랜덤 샘플링처럼 결과가 매번 달라지는 쿼리는, 관계 매핑과 섞기 전에 단독으로 먼저 검증하는 습관이 여전히 필요합니다.

프로퍼티 중심 어노테이션​

alpha01에서 이어지는 변경으로, @ColumnInfo와 @PrimaryKey, @Relation, @Embedded, @Ignore, @ColumnTypeConverters에 프로퍼티 대상이 추가되었습니다.
백킹 필드가 없는 프로퍼티도 엔티티 컬럼이나 쿼리 결과 컬럼으로 사용할 수 있게 되었습니다.
다만 사용할 수 있는 getter와, 사용할 수 있는 setter 또는 주 생성자 포함이 여전히 필요합니다.

@Entity
data class Holding(
    @PrimaryKey val symbol: String,
    @ColumnInfo val quantity: Int,
    val market: String,
)

실무 관점​

알파 버전이므로 운영 앱에 바로 적용하기보다는 별도 브랜치에서 먼저 검증하는 것이 안전합니다.
allowDataLossOnRecovery()는 이름 그대로 데이터 손실을 허용하는 설정이므로, 계좌나 주문 같은 핵심 데이터에는 적용하지 않는 것이 좋습니다.
캐시성 데이터나 서버에서 다시 내려받을 수 있는 데이터부터 적용 범위를 정하는 편이 무난합니다.
복구가 실제로 동작했는지는 로그로 남겨 두어야, 이후 고객 문의와 원인을 연결할 수 있습니다.

마치며​

Room 3.1.0-alpha03은 새 쿼리 기능보다, 데이터베이스가 망가졌을 때와 반복 쿼리가 많을 때를 다루는 실무적인 손잡이를 더한 업데이트입니다.

Media3 1.12 알파에서 달라진 것​

중앙 플래그 레지스트리​

alpha01에서 실험적 기능 플래그를 관리하는 중앙 Flags 레지스트리가 추가되었습니다.

플래그가 늘어날수록 어떤 실험이 켜져 있는지 한곳에서 파악할 수 있다는 점이 실무적으로 의미가 있습니다.

Display P3 색 공간 지원​

C.COLOR_SPACE_DISPLAY_P3가 추가되고, MediaFormatUtil과 ColorInfo의 ISO 색상 매핑에서 Display P3가 지원됩니다.

범위를 벗어난 색은 자르는 대신 부드럽게 압축되어 SDR 기본 이미지에 담깁니다.

재생 목록 메타데이터 확장​

MediaMetadata에 재생 목록 식별자와 카테고리가 추가되었습니다.
재생 목록 단위로 식별하고 분류하는 정보가 메타데이터 자체에 들어간다는 뜻입니다.
세션 쪽에서는 재생 목록 식별자, 제목, 아트워크, 카테고리를 채우는 엑스트라 키도 함께 추가되었습니다.

val metadata = MediaMetadata.Builder()
    .setPlaylistId("playlist-market-briefing")
    .setCategories(listOf("market", "briefing"))
    .build()

기본 동작 변경​

setLoadOnlySelectedTracks(true)가 기본값이 되었습니다.
선택되지 않은 비디오와 이미지 트랙은 로드하지 않으므로 메모리가 절약됩니다.
오디오와 텍스트 트랙은 항상 로드되어, 끊김 없는 트랙 전환을 유지합니다.
재생 중 선택되지 않았던 비디오 트랙을 새로 켜면 추가 버퍼링이 생길 수 있다는 점은 주의해야 합니다.
DASH 다중 기간 재생에서 다음 기간의 첫 청크 로드가 실패하면 재생이 멈추던 문제도 수정되었습니다.

alpha02에서는 새로운 media3-effect-play-services 모듈이 추가되었습니다.
비디오 향상 기능을 제공하는 EnhancementSessionDecorator와 음원 분리 기능을 제공하는 StudioSoundAudioProcessor가 포함됩니다.
이펙트 쪽에서는 스튜디오 사운드 기반 음원 분리 프로세서 구현도 함께 들어갔습니다.
Play services 모듈에 의존하는 기능이라, 단말의 Play services 제공 여부를 전제로 설계해야 합니다.

dependencies {

Palette 1.1.0 — 이미지 대표 색 추출과 palette-ktx 통합

October 27, 2026 · 3 min read
Way
Android Developer

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.
2026년 10월 21일에 공개된 Palette 1.1.0과 이미지 대표 색 추출 방법에 대해 설명해드리겠습니다.

배경​

Palette는 이미지에서 대표 색상을 추출하는 Jetpack 라이브러리입니다.
배너 이미지나 종목 대표 이미지에서 배경색과 텍스트 색을 뽑아 화면 테마에 맞추는 용도로 사용됩니다.
1.0.0 이후 오랜만에 공개된 1.1.0은 기능 추가보다 정리 성격이 강합니다.
공식 Palette 릴리스 노트를 기준으로 변경 사항과 사용법을 정리합니다.

Palette 살펴보기​

대표 색 추출 방식​

Palette는 비트맵의 픽셀을 양자화해 색상 군집을 만든 뒤 대표 스와치를 계산합니다.
동기 생성은 메인 스레드를 막을 수 있으므로, 실무에서는 비동기 생성이나 백그라운드 스레드에서 실행하는 것이 안전합니다.
추출할 색상 개수는 빌더에서 조절할 수 있으며, 기본값은 16개입니다.

val palette = Palette.from(bitmap)
    .maximumColorCount(24)
    .generate()

스와치 종류​

추출 결과는 용도별로 나뉜 스와치로 제공됩니다.
getVibrantSwatch는 생동감 있는 대표 색, getMutedSwatch는 차분한 대표 색을 돌려줍니다.
각각 밝은 버전과 어두운 버전이 있으며, getDominantSwatch는 이미지에서 가장 큰 비중을 차지하는 색을 돌려줍니다.
스와치는 null을 돌려줄 수 있으므로, 사용할 때는 반드시 대체 색을 함께 준비해야 합니다.

val vibrant = palette.getVibrantSwatch()
val muted = palette.getMutedSwatch()
val dominant = palette.getDominantSwatch()

val backgroundRgb = vibrant?.rgb ?: muted?.rgb ?: 0xFF1A1A1A.toInt()
val titleTextRgb = vibrant?.titleTextColor ?: 0xFFFFFFFF.toInt()

Compose에서 사용하기​

Palette는 뷰 시스템 시절 라이브러리라 Compose 전용 API를 제공하지 않습니다.
비트맵을 받아 백그라운드에서 생성한 뒤, 결과 색을 Compose의 Color로 변환해 상태로 보관하는 방식이 일반적입니다.
이미지마다 한 번씩만 생성하고 결과를 캐시하면, 스크롤 화면에서도 반복 계산을 피할 수 있습니다.

@Composable
fun rememberPaletteColor(bitmap: Bitmap?): Color {
    var themeColor by remember { mutableStateOf(Color.Transparent) }
    LaunchedEffect(bitmap) {
        if (bitmap == null) return@LaunchedEffect
        val palette = withContext(Dispatchers.Default) {
            Palette.from(bitmap).generate()
        }
        val swatch = palette.getVibrantSwatch() ?: palette.getDominantSwatch()
        if (swatch != null) {
            themeColor = Color(swatch.rgb)
        }
    }
    return themeColor
}

1.1.0에서 달라진 것​

1.1.0의 가장 큰 변경은 JSpecify nullability 어노테이션 채택입니다.
Kotlin에서 엄격한 null 검사를 적용하려면 컴파일러 인자를 함께 설정해야 합니다.
또 하나의 변경은 palette-ktx 통합입니다.
Kotlin 확장 함수가 모두 메인 아티팩트로 들어갔고, palette-ktx는 호환 유지를 위한 빈 아티팩트로 남았습니다.
신규 프로젝트에서는 palette만 의존하면 되며, 기존 프로젝트에서는 palette-ktx 의존성을 정리할 수 있습니다.

dependencies {
    implementation("androidx.palette:palette:1.1.0")
}
kotlinOptions {
    freeCompilerArgs += listOf(
        "-Xjspecify-annotations=strict",
        "-Xtype-enhancement-improvements-strict-mode",
    )
}

실무 관점​

이미지에서 뽑은 색을 그대로 텍스트 배경에 쓰면 가독성이 깨질 수 있습니다.
스와치가 제공하는 제목 텍스트 색과 본문 텍스트 색을 함께 사용해야 대비가 유지됩니다.
서버 이미지 색이 매번 달라지는 화면에서는, 색 추출 실패 시 기본 테마로 떨어지는 분기를 먼저 만들어 두는 것이 안전합니다.
MTS처럼 정보 밀도가 높은 화면에서는 전체 테마를 바꾸기보다, 배너 카드 내부 강조색 정도로 범위를 제한하는 편이 무난합니다.

마치며​

Palette 1.1.0은 새 기능보다 nullability 정리와 아티팩트 통합에 초점이 맞춰져 있습니다.
기존 코드를 크게 바꾸지 않고 의존성만 정리할 수 있는 안정적인 업데이트입니다.

Android 17 QPR2 정식 릴리스 살펴보기

November 14, 2026 · 4 min read
Way
Android Developer

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.

2026년 11월 10일에 정식 릴리스된 Android 17 QPR2에 대해 설명해드리겠습니다.

배경​

QPR은 분기마다 배포되는 플랫폼 릴리스입니다.
메이저 버전 사이의 공백을 메우며 기능 개선과 보안 패치를 함께 전달합니다.

이번 QPR2는 일정보다 한 달 앞당겨 배포되었습니다.
작년 Android 16 QPR2가 12월에 배포된 것과 비교하면 이례적인 일정입니다.
11월 Pixel Drop과 2026년 11월 5일 보안 패치 수준이 함께 적용되었습니다.

대상 기기는 Pixel 6a부터 Pixel 11 시리즈까지 23종입니다.
Pixel Fold와 Pixel Tablet도 포함됩니다.
Pixel 6과 Pixel 6 Pro는 이번 릴리스 대상에서 제외되었습니다.
두 기기의 5년 업데이트 지원 기간이 2026년 10월에 종료되었기 때문입니다.

Android 17 QPR2 살펴보기​

지원 기기와 빌드 번호​

대부분의 기기에는 CP4A.261105.040.A1 빌드가 배포됩니다.
Pixel 11 시리즈는 지역에 따라 빌드 번호가 나뉩니다.
미국 모델은 CP4A.261105.040.D1, 캐나다 모델은 CP4A.261105.040.B2입니다.
배포는 단계적으로 진행되며 일주일 정도에 걸쳐 전 기기에 도달합니다.

단말에 적용된 보안 패치 수준은 코드에서도 확인할 수 있습니다.

val securityPatch = Build.VERSION.SECURITY_PATCH
// 기대값: 2026-11-05

또는 adb 명령으로 확인할 수 있습니다.

adb shell getprop ro.build.version.security_patch

맞춤 설정과 블러 효과​

시스템 색상을 직접 조절하는 슬라이더가 추가되었습니다.
강도는 Neutral, Soft, Bright, Bold 네 단계로 나뉩니다.
라이트 모드와 다크 모드에 각각 대응하는 적응형 배경화면도 지원됩니다.

개발자는 앱 안에서 새로운 블러 효과를 사용할 수 있습니다.
미디어 위에서 동작하는 오버레이에 적합한 형태로 개선되었습니다.
잠금 화면 위젯 편집 화면과 전원 메뉴의 블러 표현도 함께 다듬어졌습니다.

상태 표시줄과 빠른 설정​

상태 표시줄 옵션이 새로 추가되었습니다.
표시할 알림 종류와 시스템 모드 표시 여부를 선택할 수 있습니다.
빠른 설정에서는 앱이 실행 중일 때도 화면 밝기를 조절할 수 있습니다.
키보드 전환 버튼과 프린터 전송 시의 Live Updates 표시도 추가되었습니다.

음성 브로드캐스트와 블루투스​

Voice broadcast 기능이 추가되었습니다.
음성을 Auracast 수신 기기로 직접 스트리밍할 수 있습니다.
빠른 설정에 오디오 스트림 항목이 생겼고 Live Caption과 번역을 함께 사용할 수 있습니다.
블루투스 오디오에서 Gemini 음성과 미디어 음량 차이도 완화되었습니다.
암호화 DNS 서버 지원과 공유 시트 개선도 포함되었습니다.

보안과 개인정보 보호​

Private Compute Core logging 기능이 추가되었습니다.
AI 앱이 단말 데이터에 접근한 내역을 사용자가 직접 확인할 수 있습니다.
연락처 편집 권한 체계도 변경되었습니다.
기존처럼 권한만으로 연락처를 직접 수정하는 방식에서 벗어납니다.
통화 착신 전환을 이용한 사기 시도를 막는 보호 기능이 추가되었습니다.
멀티 SIM을 지원하는 SIM 보안 타임라인 뷰어도 제공됩니다.
사이드로딩 시 권한을 부여하는 절차도 간소화되었습니다.

멀티태스킹과 접근성​

폴더블 기기의 멀티태스킹이 개선되었습니다.
앱 핸들이 상단에 배치되고 분할 화면 전환이 부드러워졌습니다.
Bubbles의 위치 조정과 전체 화면 전환, 실행 동작도 개선되었습니다.
Linux Terminal에서는 실행 중인 리눅스 세션의 파일을 앱에서 탐색할 수 있습니다.
USB 웹캠으로 사용할 때의 화면과 화면 녹화 기본 동작도 변경되었습니다.
색상 인식 관련 조정과 블루투스 보청기 잠금 화면 제어 기능이 추가되었습니다.
선호하는 홈 시간대 설정과 키보드 진동 강도 조절 슬라이더도 제공됩니다.

실무 관점​

QPR 릴리스는 OS 동작이 바뀌는 지점이라 실무 앱에 미치는 영향을 먼저 확인해야 합니다.
연락처 편집 권한 변경처럼 타깃 SDK와 무관하게 적용되는 변경이 포함될 수 있습니다.
Pixel 실기기가 있다면 보안 패치 수준부터 확인하고 주요 플로우를 회귀 테스트하는 것이 좋습니다.
베타 기간에 테스트했던 Quick Settings 레이아웃 편집 기능은 정식 릴리스에서 빠졌습니다.
베타에서 확인한 기능이 정식에 그대로 포함된다고 단정하지 않는 것이 좋습니다.
다음 분기 릴리스인 QPR3는 이미 베타가 진행 중이며 내년 봄 배포가 예상됩니다.

마치며​

Android 17 QPR2는 맞춤 설정과 보안, 멀티태스킹을 함께 개선한 분기 릴리스입니다.
Pixel 6a 이후 기기를 사용 중이라면 단계적 배포 일정에 따라 순차적으로 받아볼 수 있습니다.

CameraX로 1만 8천 종 기기에서 본인 확인하기

November 14, 2026 · 4 min read
Way
Android Developer

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.

2026년 11월 11일 Android Developers Blog에 공개된 SmileID의 CameraX 도입 사례에 대해 설명해드리겠습니다.

배경​

본인 확인 앱은 은행 계좌 개설과 SIM 등록에 사용됩니다.
선명한 고해상도 얼굴 촬영이 필요하고 위조와 딥페이크를 가려내야 합니다.
저사양 기기에서 충돌 없이 동작하는 것도 필수 조건입니다.

SmileID는 아프리카 지역의 본인 확인 SDK를 제공하는 회사입니다.
대상 기기에서 Android 점유율은 85%에 달합니다.
저가형 스마트폰과 지역 전용 모델, POS 단말까지 아우르는 환경입니다.
이 사례는 파편화된 기기 환경에서 카메라를 어떻게 안정화했는지 보여줍니다.

CameraX 도입 전의 문제​

기존 구현은 Camera1과 저수준 Camera2 API를 직접 사용했습니다.
세 가지 문제가 반복되었습니다.

미리보기 왜곡과 회전 문제​

제조사마다 카메라 센서 방향을 다르게 보고했습니다.
미리보기가 회전되거나 얼굴 촬영이 잘못된 방향으로 저장되었습니다.
저가형 기기에서는 요청한 프레임 크기가 맞지 않아 미리보기가 늘어났습니다.
얼굴이 일그러지면 생체 인증 자체가 무용지물이 됩니다.

메모리 부족 충돌​

RAM 1GB 이하인 기기에서 고해상도 이미지를 처리하면 메모리 부족 충돌이 발생했습니다.
실시간 생체 확인을 포기하고 정적 사진을 REST API로 업로드하는 방식으로 돌아가야 했습니다.
그 결과 SDK 도입 성장률은 연간 2배에서 3배 수준에 머물렀습니다.

CameraX 살펴보기​

SmileID는 모바일 SDK를 처음부터 다시 만들며 CameraX로 이전했습니다.
CameraX는 기기 차이를 추상화하고 수명 주기를 인식하는 인터페이스를 제공합니다.
Android 5.0(API 21)부터 지원되며 기존 기기의 98% 이상을 커버합니다.

Preview와 ImageAnalysis 파이프라인​

두 가지 유스 케이스를 함께 묶어 이중 목적 파이프라인을 구성했습니다.
Preview는 사용자를 안내하는 실시간 미리보기를 담당합니다.
ImageAnalysis는 프레임을 실시간으로 분석해 얼굴 위치 확인과 생체 여부를 판단합니다.
검증된 셀피 프레임도 같은 파이프라인에서 추출합니다.

ResolutionSelector로 해상도 제어하기​

고해상도 촬영과 메모리 부족 충돌을 함께 해결한 핵심은 ResolutionSelector입니다.
목표 해상도를 지정하고 해당 크기를 지원하지 않는 기기에서의 대체 규칙을 선택합니다.
선명도를 우선하면 FALLBACK_RULE_CLOSEST_HIGHER_THEN_LOWER를 사용합니다.
메모리 사용량을 제한하면 FALLBACK_RULE_CLOSEST_LOWER_THEN_HIGHER를 사용합니다.
백프레셔 전략은 STRATEGY_KEEP_ONLY_LATEST로 지정해 이전 프레임 분석이 끝나지 않았으면 오래된 프레임을 버립니다.

val resolutionSelector = ResolutionSelector.Builder()
    .setResolutionStrategy(
        ResolutionStrategy(
            Size(1200, 900),
            ResolutionStrategy.FALLBACK_RULE_CLOSEST_HIGHER_THEN_LOWER
        )
    )
    .setAspectRatioStrategy(AspectRatioStrategy.RATIO_4_3_FALLBACK_AUTO_STRATEGY)
    .build()

val imageAnalysis = ImageAnalysis.Builder()
    .setResolutionSelector(resolutionSelector)
    .setBackpressureStrategy(ImageAnalysis.STRATEGY_KEEP_ONLY_LATEST)
    .build()

imageAnalysis.setAnalyzer(executor, analyzer)

val preview = Preview.Builder().build().also {
    it.surfaceProvider = surfaceProvider
}

cameraProvider.bindToLifecycle(
    lifecycleOwner,
    CameraSelector.DEFAULT_FRONT_CAMERA,
    preview,
    imageAnalysis
)

고밀도 픽셀 프레임을 요청하고 단말에서 처리한 결과 셀피 해상도가 4배 증가했습니다.
얼굴 영역만 단말에서 압축해 전송하므로 네트워크 업로드 용량은 이전과 동일하게 유지되었습니다.
모델에 더 선명한 데이터를 제공하면서 사용자의 데이터 비용은 늘지 않았습니다.

호환성을 지탱하는 두 가지 계층​

첫 번째 계층은 Google의 Camera and Media Test Lab입니다.
190종이 넘는 실물 기기에서 자동 테스트가 매일 실행됩니다.
칩셋과 OS 버전, 하드웨어 사양이 다른 기기를 순환하며 검증합니다.
회귀가 발생하면 프로덕션 코드에 영향을 주기 전에 잡아냅니다.

두 번째 계층은 기기별 결함에 대한 자동 우회 처리입니다.
일부 기기는 노출 설정을 적용하지 못하거나 특정 종횡비에서 이미지를 뒤집어 보고합니다.
CameraX는 DeviceQuirks와 CameraQuirks 같은 내부 클래스로 알려진 문제를 감지합니다.
감지된 기기에는 맞는 우회 처리를 자동으로 적용합니다.
SmileID는 기기별 패치 없이 1만 8천 종이 넘는 기기에서 SDK를 동작시켰습니다.

도입 결과​

도입 결과는 수치로 확인됩니다.
SDK 도입 성장률은 2년 차에 20배에 도달했습니다.
검증 통과율은 SDK를 사용하는 앱 기준으로 20% 증가했습니다.
누적 본인 확인 건수는 1억 6천만 건을 넘어섰습니다.

실무 관점​

MTS에서도 신분증 촬영과 본인 확인 같은 카메라 기능이 필요합니다.
저사양 기기까지 고려한다면 해상도는 요청만으로 끝나지 않습니다.
대체 규칙과 백프레셔 전략까지 함께 설계해야 메모리 문제를 피할 수 있습니다.
기기별 분기는 직접 작성하기보다 CameraX의 우회 처리에 맡기는 편이 유지보수에 유리합니다.
다만 ResolutionSelector의 대체 규칙은 촬영 품질과 메모리 사용량 사이의 선택입니다.
서비스 성격에 따라 선명도 우선과 메모리 제한 중 어느 쪽을 택할지 먼저 정하는 것이 좋습니다.
AI 코딩 에이전트를 사용한다면 CameraX Skill을 활용할 수 있습니다.
android skills add camerax 명령으로 추가하면 마이그레이션과 수명 주기 바인딩에 현재 패턴을 적용할 수 있습니다.

마치며​

CameraX 도입은 파편화된 기기 환경의 문제를 SDK의 강점으로 바꾸었습니다.
카메라 기능을 직접 구현하기 전에 라이브러리가 제공하는 호환성 계층을 먼저 검토하는 것이 좋습니다.

Compose 1.13의 Grid와 이름 있는 영역 살펴보기 — 커스텀 Layout 코드를 줄이는 방법

November 13, 2026 · 3 min read
Way
Android Developer

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.

11월 4일에 공개된 Compose 1.13.0-rc01에 안정화된 상태로 들어 있는 Grid에 대해 설명해드리겠습니다.

배경​

헤더와 사이드바, 본문, 푸터로 이뤄진 화면은 흔한 구조입니다.
문제는 이 구조가 2차원이라는 점입니다.
Column과 Row는 한 방향으로만 쌓는 1차원 레이아웃입니다.
두 방향을 함께 다루려면 Layout 블록을 직접 작성하거나 중첩을 쌓아야 했습니다.
측정과 배치 로직이 한 파일에 모이면서 나중에 손대기 어려운 코드가 되기 쉽습니다.
Grid는 행과 열을 선언만으로 정의하는 2차원 레이아웃입니다.
Grid API는 1.11.0에서 들어온 뒤 1.13.0-alpha02에서 stable로 승격되었습니다.
이름 있는 영역 기능은 1.12.0-beta01에서 추가되었습니다.

Compose 1.13의 Grid 살펴보기​

트랙 정의하기​

Grid는 config 블록에서 열과 행을 정의합니다.
트랙 크기는 Fixed와 Flex, Auto, Percentage, MinMax로 지정합니다.
1.fr처럼 비율 단위를 쓰면 남은 공간을 비율대로 나눕니다.
gap으로 트랙 사이의 간격을 한 번에 정합니다.

Grid(
    config = {
        // 열 2개: 고정 200dp 사이드바, 남은 공간을 차지하는 본문
        columns(200.dp, 1.fr)
        // 행 3개: 내용 크기 헤더, 남은 공간 본문, 고정 60dp 푸터
        rows(Auto, 1.fr, 60.dp)
        gap(8.dp)
    },
    modifier = Modifier.fillMaxSize()
) {
    // ...
}

아이템 배치하기​

자식은 Modifier.gridItem으로 위치와 크기를 정합니다.
행과 열 인덱스는 1부터 시작합니다.
rowSpan과 columnSpan으로 여러 셀에 걸치게 둘 수 있습니다.
gridItem을 붙이지 않은 자식은 GridFlow에 따라 다음 빈 셀에 자동 배치됩니다.

Box(
    modifier = Modifier
        .gridItem(row = 1, column = 1, columnSpan = 2)
        .background(Color.Blue)
        .fillMaxSize(),
    contentAlignment = Alignment.Center
) {
    Text("Header")
}

이름 있는 영역으로 의미 분리하기​

config 블록에서 area로 영역을 정의하고, 자식에서는 gridItem에 영역 이름을 넘깁니다.
레이아웃 구조가 바뀌어도 자식 코드는 그대로 둘 수 있습니다.
영역 식별자는 String이나 enum처럼 안정적인 equals와 hashCode를 가진 값을 써야 합니다.

Grid(
    config = {
        columns(200.dp, 1.fr)
        rows(Auto, 1.fr, 60.dp)
        gap(8.dp)
        area("header", row = 1, column = 1, columnSpan = 2)
        area("sidebar", row = 2, column = 1)
        area("content", row = 2, column = 2)
        area("footer", row = 3, column = 1, columnSpan = 2)
    },
    modifier = Modifier.fillMaxSize()
) {
    Header(Modifier.gridItem("header"))
    Sidebar(Modifier.gridItem("sidebar"))
    Content(Modifier.gridItem("content"))
    Footer(Modifier.gridItem("footer"))

행과 열 인덱스가 1부터 시작한다는 점을 먼저 확인하는 것이 좋습니다.
0부터 시작한다고 착각하면 배치가 어긋나거나 IllegalArgumentException이 발생합니다.
config 블록은 측정 패스에서 실행되므로 부수 효과를 넣지 않는 것이 좋습니다.
Grid는 개수가 정해진 레이아웃용입니다.
스크롤되는 긴 목록에는 LazyGrid를 쓰는 것이 맞습니다.

배경​

Media3 1.12.0은 10월 21일 alpha01, 10월 26일 alpha02를 거쳐 11월 11일 beta01에 도달했습니다.

Media3 1.12.0-beta01 살펴보기​

Transformer에 들어온 CodecDB​

Transformer에 androidx.media3.transformer.codecdb 패키지의 CodecDB가 추가되었습니다.

트랜스코딩 품질을 단말마다 일일이 튜닝하지 않아도 됩니다.
단말별 인코더 성능 편차가 큰 환경에서 유용합니다.

샘플 버퍼 메모리 사용량 절감​

C.DEFAULT_BUFFER_SEGMENT_SIZE가 65536에서 65520으로 줄었습니다.
버퍼 할당 하나가 바이트 배열 객체 헤더까지 포함해 OS 페이지 단위에 딱 맞게 들어갑니다.
4 KiB 페이지 단말에서는 샘플 버퍼 메모리가 약 6% 줄어듭니다.
16 KiB 페이지 단말에서는 약 20% 줄어듭니다.
재생 동작을 바꾸지 않고 메모리만 줄이는 변경입니다.

JSpecify 마이그레이션과 Kotlin 코드에 미치는 영향​

androidx.media3.common.util.NullableType이 JSpecify의 org.jspecify.annotations.Nullable로 교체되었습니다.
UnknownNull도 JSpecify 널니스 어노테이션으로 대체되어 제거되었습니다.
이 변경은 Kotlin 코드에도 직접 영향을 줍니다.
RunnableFutureTask를 상속받는 Kotlin 서브클래스는 결과 타입이 널 가능하면 타입 인자도 널 가능으로 명시해야 합니다.
예를 들어 RunnableFutureTask<Void?, Exception>처럼 씁니다.
CompositeMediaSource도 마찬가지이며, 널 가능한 자식 소스 ID를 쓰는 경우 CompositeMediaSource<Void?>처럼 명시합니다.
Media3 클래스를 상속해 쓰는 코드가 있다면 빌드 시점에 확인이 필요합니다.

Player.listen 스레드 문제 수정​

Player.listen이나 Player.listenTo를 플레이어의 애플리케이션 스레드가 아닌 스레드에서 취소하면 IllegalStateException이 발생했습니다.
오류 메시지는 "Player is accessed on the wrong thread."입니다.
Compose UI 테스트 종료 시점에 자주 마주치는 상황이었습니다.
이번 beta01에서 이 문제가 수정되었습니다.

Compose UI에 들어온 자막 슬롯​

ContentFrame과 Player에 subtitles 컴포저블 슬롯이 추가되었습니다.
media3-ui-compose-material3에서는 비트맵 자막과 가로 텍스트 자막 큐를 기본으로 렌더링합니다.
SubtitleView.setTextDirectionHeuristic도 추가되어 양방향 자막 텍스트의 줄 바꿈 기준을 바꿀 수 있습니다.
한편 Player의 모든 컨트롤 슬롯에 애니메이션이 적용되면서 PlayerDefaults.TopControls와 CenterControls, BottomControls에서 visible 파라미터가 제거되었습니다.
불안정한 API에 대한 변경이라 커스텀 컨트롤을 쓰는 화면은 빌드 확인이 필요합니다.

광고와 캐스트 변경점​

IMA 확장에서는 인터랙티브 광고가 재생 중 비디오 플레이어 뷰를 리사이즈할 수 있게 되었습니다.
AdViewProvider.getAdVideoView()가 광고 재생 중 크기를 바꿀 수 있는 비디오 컨테이너 뷰를 제공합니다.

RC는 정식 출시 직전 단계로, 새 기능이 동결되고 안정화 작업이 중심이 됩니다.

Kotlin 2.5.0-RC 살펴보기​

이름 기반 구조 분해​

기존 구조 분해는 위치 기반으로 동작했습니다.
데이터 클래스의 프로퍼티 순서가 바뀌면 변수에 들어가는 값이 함께 바뀌었습니다.
이름 기반 구조 분해에서는 변수 이름이 프로퍼티 이름과 일치해야 합니다.
순서가 바뀌어도 이름이 같으면 올바른 값이 들어갑니다.

data class Person(val name: String, val age: Int)

val person = Person("way", 33)
val (name, age) = person
val (age, name) = person // 순서가 달라도 이름으로 매칭됩니다

2.5.0에서는 새 문법을 추가 설정 없이 사용할 수 있습니다.
컴파일러는 기존 위치 기반 코드에 대해 마이그레이션 힌트도 함께 제공합니다.
위치 기반이 꼭 필요한 경우에는 대괄호 문법을 사용합니다.

val pair = "way" to 33
val [first, second] = pair

미사용 반환값 검사​

반환값을 무시한 호출을 찾아주는 검사가 추가되었습니다.
실수로 결과를 확인하지 않은 호출을 컴파일 단계에서 발견할 수 있습니다.
Json.encodeToString 같은 호출의 결과를 쓰지 않고 넘기는 경우에 경고를 받을 수 있습니다.

JDK 17 요구 사항​

Beta2부터 JDK 17보다 낮은 버전으로 컴파일러를 실행하면 오류가 발생합니다.
Android Studio는 이미 JDK 17을 내장하고 있어 대부분은 영향이 없습니다.
CI 환경에서 별도 JDK를 지정하고 있다면 버전을 확인해야 합니다.

그 외 변경 사항​

Java 28을 지원합니다.
Swift Export가 새로운 DSL과 함께 베타 단계에 들어갔습니다.
Kotlin/Native 증분 컴파일이 Apple 타겟에서 기본으로 활성화되었습니다.
멀티 필드 값 클래스가 알파 단계로 추가되었습니다.
Lombok의 @Builder 애너테이션은 Kotlin 코드에서 비활성화되었습니다.
Android 프로젝트의 kotlin 블록 안에서 sourceSets를 쓰는 기존 방식이 deprecation 대상으로 지정되었습니다.

Version Catalog에서 Kotlin 버전을 교체하면 RC를 적용할 수 있습니다.

정식 출시는 12월로 예정되어 있습니다.

마치며​

Kotlin 2.5.0-RC는 이름 기반 구조 분해를 안정화하고, 정식 출시를 위한 마지막 점검 단계에 들어갔습니다.

kotlinx.serialization 1.13.0 살펴보기​

1.12.0 예외 처리 변경 철회​

@Serializable

try {
    val account = Json.decodeFromString<Account>("""{"id": "A001"}""")
} catch (e: JsonException) {
    // 1.12.0에서는 대부분의 예외가 JsonException으로 감싸졌지만
    // 1.13.0에서는 이 변경이 철회되어 이전 동작으로 돌아갑니다
}

JsonElement.toString 성능 개선​

JsonElement.toString 구현이 새로 작성되었습니다.
일부 벤치마크에서는 기존보다 약 2배 빨라졌습니다.
서버 응답을 로그로 남기거나 디버깅용 문자열을 자주 만드는 코드에서 효과가 있습니다.

1.12.0에서 함께 안정화된 API​

1.13.0은 작은 릴리스이지만, 직전 버전인 1.12.0에서 안정화된 API를 함께 정리합니다.

kotlin.time.Instant와 kotlin.uuid.Uuid 직렬화도 실험 애너테이션이 제거되었습니다.
CBOR 포맷은 메모리 사용량이 줄었고, Protobuf 포맷은 알 수 없는 필드를 보관했다가 다시 전송하는 기능을 받았습니다.

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.

2026년 11월 4일에 안정화 버전으로 공개된 Core-telecom 1.1.0에 대해 설명해드리겠습니다.

배경​

VoIP 통화를 앱에 넣으려면 플랫폼 Telecom 프레임워크와 직접 연동해야 합니다.
Android 14부터는 트랜잭션 기반의 새 API가 기본이 되었고, 그 이전에는 ConnectionService 기반의 기존 API를 써야 했습니다.
두 가지 구현을 함께 지원하려다 보면 버전별 분기가 늘어나고, 오디오 라우팅 같은 기기별 동작 차이까지 직접 처리해야 합니다.
Core-telecom은 이 두 가지 구현을 하나의 API로 묶어 주는 Jetpack 라이브러리입니다.
1.1.0은 마이그레이션을 단계적으로 진행할 수 있는 장치를 추가하고, 통화 확장 기능을 안정화 API로 승격했습니다.

Core-telecom 1.1.0 살펴보기​

단계적 전환을 위한 롤아웃 제어​

CallsManager#registerAppWithTelecom에 선택 매개변수 backwardsCompatSdkLevel이 추가되었습니다.
기본값은 SDK 33이며, 이 값까지는 ConnectionService 기반 구현을 쓰고 그 위에서는 트랜잭션 API를 사용합니다.
기존에 플랫폼 ConnectionService를 직접 쓰던 앱은 익숙한 구현을 유지한 채 라이브러리를 먼저 도입할 수 있습니다.
이후 상한 값을 단계적으로 낮추면서 새 API로 전환하면 됩니다.
호출 관리 코드는 바꾸지 않아도 됩니다.

val callsManager = CallsManager(context)

// SDK 34까지는 ConnectionService 기반으로 유지하고,
// SDK 35부터 트랜잭션 API를 사용합니다.
callsManager.registerAppWithTelecom(
    capabilities = CallsManager.CAPABILITY_SUPPORTS_VIDEO_CALLING,
    backwardsCompatSdkLevel = 34
)

통화 확장 기능 안정화​

addCallWithExtensions와 InCallServiceCompat#connectExtensions, LocalCallSilenceExtension, ParticipantExtension, MeetingSummaryRemote가 안정화 API가 되었습니다.
기존에 필요했던 @ExperimentalAppActions 옵트인이 제거되었습니다.
통화 상태를 Android Auto나 Wear OS 같은 원격 화면과 동기화하는 기능을 정식 API로 쓸 수 있습니다.
LocalCallSilenceExtension에는 원격 음소거 제어 여부를 동적으로 바꾸는 updateCanUserUpdateSilence와 콜백 onCanUserUpdateSilence가 추가되었습니다.
수동적 참관자나 진행자에게 음소거된 회의 참가자처럼, 원격 화면에서 마이크 제어를 막아야 하는 경우에 사용합니다.

통화별 통화 기록 제외​

CallAttributesCompat에 선택 속성 isLogExcluded가 추가되었습니다.
시스템 통화 기록에 참여하도록 설정한 앱이 특정 통화만 기록에서 제외할 수 있습니다.
Android 16 QPR 이상에서 동작합니다.
VoIP 통화는 기본적으로 시스템 통화 기록에 남지 않으므로, 먼저 기록 참여를 설정한 앱에만 해당합니다.

val attributes = baseAttributes.copy(isLogExcluded = true)

프리미엄 네트워크 슬라이싱 제외​

CallsManager.CAPABILITY_OPT_OUT_OF_PREMIUM_NETWORK가 추가되었습니다.
음성·영상 통화 중에 플랫폼이 자동으로 프리미엄 네트워크 슬라이스를 요청하는 동작을 거부할 수 있습니다.
registerAppWithTelecom에 플래그를 전달해 설정합니다.

callsManager.registerAppWithTelecom(
    CallsManager.CAPABILITY_OPT_OUT_OF_PREMIUM_NETWORK
)

통화 중 음성·영상 전환 관찰​

CallControlScope#callTypeFlow와 CallControlScope#requestCallType이 추가되었습니다.
통화 중 오디오와 비디오 상태 변화를 흐름으로 관찰할 수 있습니다.
통화 종류를 세션 중간에 올리거나 내릴 수도 있습니다.

// 음성에서 영상으로 바뀌는 과정을 관찰합니다.
callControlScope.callTypeFlow()
    .onEach { callType ->
        // 바뀐 통화 종류에 맞게 화면을 갱신합니다.
    }
    .launchIn(scope)

// 영상 통화로 전환을 요청합니다.
callControlScope.requestCallType(CallAttributesCompat.CALL_TYPE_VIDEO_CALL)

끊김 없는 통화 설정과 오디오 라우팅​

통화 설정 경로가 빨라졌습니다.
오디오 엔드포인트 확인과 블루투스 안정화 과정이 addCall의 동기 경로에서 분리되어, CallControlScope 진입까지 최대 2초의 지연이 사라졌습니다.
겹치는 통화 설정 요청은 CallException으로 즉시 거부되어, 플랫폼 TransactionManager의 5초 타임아웃과 직렬 큐 교착을 막습니다.
오디오 라우팅 문제도 여러 건이 수정되었습니다.
SDK 34부터 36에서 음성 전용 수신 통화가 영상 통화로 잘못 인식되어 스피커폰으로 나가는 문제, 영상 통화 시작 시 유선 헤드셋이 연결되어 있는데도 스피커로 바뀌는 문제 등이 포함됩니다.
사용자가 미리 고른 오디오 엔드포인트도 통화 시작 시 기본값에 덮어쓰이지 않습니다.
BLUETOOTH_CONNECT 권한이 없어도 웨어러블 기기를 식별하는 대체 방법도 들어갔습니다.
SDK 38부터는 DisconnectCause.ERROR로 통화를 끊을 수 있고, 이전 버전에서는 자동으로 DisconnectCause.LOCAL로 바뀌어 버전 검사가 필요 없습니다.

실무 관점​

VoIP 기능이 있는 MTS 앱이라면 1.1.0은 바로 검토할 만한 버전입니다.
기존 ConnectionService 연동이 있다면 backwardsCompatSdkLevel로 상한을 높게 잡고 라이브러리를 먼저 도입하는 것이 안전합니다.
통화 설정 지연과 오디오 라우팅 수정은 사용자 체감과 직결되므로, 실기기에서 수신·발신·블루투스 전환을 직접 확인하는 것이 좋습니다.
isLogExcluded는 Android 16 QPR 이상에서만 동작하므로, 구형 단말에서는 아무런 효과가 없다는 점을 알아두어야 합니다.
네트워크 슬라이싱 제외는 통신사 과금과 연결될 수 있으니, 적용 전에 정책을 먼저 확인하는 것이 좋습니다.

마치며​

1.1.0은 단계적 전환 장치와 안정화된 통화 확장 기능으로 마이그레이션 부담을 낮췄습니다.
통화 설정과 오디오 라우팅의 고질적인 문제도 함께 정리되어, VoIP 품질이 한층 안정되었습니다.

WebView에 stable API로 온 allowlist — WebKit 1.18.0 살펴보기

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.
2026년 10월 21일에 공개된 WebKit 1.18.0의 릴리스 노트를 정리해드리겠습니다.

현재 상황​

지난 글에서는 WebView v156의 cross-origin isolation allowlist 개념을 정리한 바 있습니다.
당시에는 개념과 정책 방향이 중심이었습니다.
이번에는 그 기능이 Jetpack WebKit의 stable API로 확정된 내용을 정리합니다.
MTS 앱처럼 WebView를 많이 쓰는 앱에서는 웹 콘텐츠의 성능 기능과 보안 정책을 함께 다뤄야 합니다.
SharedArrayBuffer처럼 cross-origin isolation을 요구하는 API는 그동안 전부 아니면 전무에 가까웠습니다.
1.18.0은 신뢰하는 origin만 골라 허용하는 길을 stable API로 열어줍니다.

WebKit 1.18.0 살펴보기​

cross-origin isolated allowlist API​

핵심은 Profile 수준의 API입니다.
Profile#setCrossOriginIsolatedAllowlist와 Profile#getCrossOriginIsolatedAllowlist가 stable로 제공됩니다.
allowlist에 오른 origin에서는 완전히 cross-origin isolated 상태가 아니어도 SharedArrayBuffer 같은 API를 쓸 수 있습니다.
다만 웹 페이지 쪽에서도 Document-Isolation-Policy 헤더로 적절히 옵트인해야 합니다.
앱 API만 켠다고 끝나는 기능이 아니라, 웹 측 헤더와 함께 동작하는 기능입니다.

// 이미 확보한 Profile이라고 가정합니다
if (WebViewFeature.isFeatureSupported(WebViewFeature.CROSS_ORIGIN_ISOLATED_ALLOWLIST)) {
    profile.setCrossOriginIsolatedAllowlist(
        setOf("https://trusted.example.com")
    )
}

사용 전에 반드시 기능 지원 여부를 확인해야 합니다.
지원되지 않는 단말에서 호출하면 예외가 발생합니다.
공식 API 레퍼런스에서도 사용 전 확인을 강조하고 있습니다.
또한 기본값은 비활성화 상태입니다.
WebView는 렌더러 프로세스 격리를 지원하지 않기 때문에, 이 API를 호출한다는 것은 보안 보장을 완화하겠다는 뜻이 됩니다.
그래서 신뢰하는 origin만 등록해야 하고, 와일드카드 패턴은 피해야 합니다.
이미 로드된 페이지에도 이 설정이 적용된다는 점도 염두에 두어야 합니다.

prefetch 큐 비우기 여부 확인​

WebViewFeature에 WEBVIEW_NAVIGATE_DRAIN_PREFETCH 상수가 추가되었습니다.
이 상수로 Navigation#navigate가 이동 전에 prefetch 큐를 비우는지 확인할 수 있습니다.
prefetch를 쓰는 앱에서는 이동 시점에 어떤 요청이 남는지 예측하기가 한결 쉬워집니다.
단순한 상수 추가처럼 보이지만, 동작 예측 가능성을 높이는 변경입니다.

if (WebViewFeature.isFeatureSupported(WebViewFeature.WEBVIEW_NAVIGATE_DRAIN_PREFETCH)) {
    // Navigation#navigate가 prefetch 큐를 비우는지 확인할 수 있습니다
}

API 정리와 이름 변경​

PrefetchParameters#isJavaScriptEnabled는 includeClientHints로 이름이 바뀌었습니다.
기존 메서드는 deprecated 처리되었습니다.
Profile#addQuicHints는 preferQuicFor로 이름이 바뀌었습니다.
이름만 바뀐 변경이지만, 기존 이름을 그대로 쓰던 코드가 있다면 마이그레이션 목록에 올려두어야 합니다.
deprecated 경고를 방치하면 나중에 버전 올릴 때 한꺼번에 정리해야 합니다.

의존성 선언​

[versions]
webkit = "1.18.0"

[libraries]
webkit = { module = "androidx.webkit:webkit", version.ref = "webkit" }
dependencies {
    implementation(libs.webkit)
}

실무 관점​

MTS 앱에서 WebView allowlist를 쓴다면, 등록 대상은 자사 도메인처럼 확실히 신뢰하는 origin으로 한정해야 합니다.
외부 제휴 페이지나 광고성 페이지를 넓게 허용하면, 보안 보장을 완화한 대가를 치르게 됩니다.
적용 전에는 기능 지원 여부 확인, 헤더 설정, 기존 페이지 동작을 함께 테스트하는 편이 좋습니다.
이미 로드된 페이지에도 적용되므로, 설정 시점에 따라 동작이 달라질 수 있다는 점도 테스트 항목에 넣어야 합니다.
stable 릴리스인 만큼, 기존에 쓰던 이름 변경부터 정리하고 단계적으로 적용하는 것이 안전합니다.

마치며​

이번 stable은 allowlist라는 보안 기능을 실제 API로 쓸 수 있게 만든 릴리스입니다.
신뢰하는 origin만 좁게 허용한다는 원칙만 지키면, WebView의 성능 기능을 보다 안전하게 활용할 수 있습니다.

Canary 트랙의 위치 이해하기​

Canary는 베타보다 앞서 가는 월간 트랙입니다.
베타에 오르기 전의 작업이 먼저 들어오고, 거친 부분이 남아 있을 수 있습니다.
Canary에서 본 기능이 그대로 정식 릴리스에 이른다는 보장은 없습니다.
기능이 바뀌거나 미뤄지거나 아예 나오지 않을 수도 있습니다.
그래서 Canary는 일상 기기가 아니라 테스트 기기에서 쓰는 트랙입니다.
설치는 Android Flash Tool에서 할 수 있습니다.

App Lock 다시 살펴보기​

App Lock이 Canary 2611에 돌아왔습니다.
앱마다 잠금을 걸어 기기 인증 뒤에만 열리게 하는 기능입니다.
빌린 기기나 잠금 해제된 기기에서 민감한 앱이 그대로 열리는 일을 막습니다.
App Lock은 QPR2 베타에서 잠시 빠졌다가 다듬는 과정을 거쳤습니다.
10월 29일 QPR3 Beta 3에서 복귀했고, Canary 트랙에서도 같은 작업이 이어지고 있습니다.
12월 Pixel Feature Drop은 QPR2 기반이라, App Lock이 정식에 이를지는 그때 확인할 수 있습니다.

Recents 화면에서 버블로 실행하기​

Recents 화면에 앱을 버블로 여는 단축키가 새로 생겼습니다.
버블은 대화를 작은 떠 있는 창으로 유지하는 Android의 멀티태스킹 방식입니다.
Recents 드롭다운 메뉴에서 Bubble을 고르면 앱이 바로 버블에 들어갑니다.
설정을 뒤지거나 전체 앱 목록을 거치지 않아도 됩니다.
다른 앱을 쓰면서 대화를 곁에 두는 흐름이 짧아집니다.

Quick Settings 카메라 타일과 At a Glance 알람 표기​

Quick Settings에 카메라를 여는 전용 타일이 추가되었습니다.
화면을 쓸어내리고 타일 하나만 누르면 카메라가 열립니다.
앱 아이콘을 찾거나 잠금 화면 단축키를 거치는 일을 줄입니다.
잠금 화면의 At a Glance 위젯도 바뀌었습니다.
다가오는 알람 시간에 오전과 오후를 구분하는 접미사가 표시됩니다.
작은 표기지만, 알람 시간을 잘못 읽는 실수를 줄이는 변경입니다.

빌드 정보와 설치 방법 확인하기​

Canary 2611의 빌드 번호는 ZP11.261016.008입니다.
업데이트 크기는 약 1GB로 안내되었습니다.
설치 이미지는 Pixel 6a 이상 기기에 제공됩니다.
Pixel 11 시리즈까지 포함하고, Pixel Fold와 Pixel Tablet도 대상입니다.
업데이트 전에는 배터리를 50% 이상 충전하는 것이 좋습니다.
Canary에 올린 Pixel은 이후 매달 새 Canary 빌드로 자동 업데이트됩니다.

# Android Flash Tool에서 Canary 이미지를 설치합니다
# https://flash.android.com/ 에서 기기를 연결하고 안내를 따릅니다

실무 관점​

Canary는 정식 릴리스가 아니니 실무 기기에 바로 올리지 않는 것이 좋습니다.
테스트용 Pixel이 있다면 그 기기에서 먼저 확인하는 흐름이 맞습니다.
App Lock처럼 사용자에게 보이는 기능은 정식 일정이 정해지기 전까지 기획에 반영하지 않는 것이 좋습니다.
QPR3 Beta 3과 겹치는 변경은 베타 트랙의 동작을 Canary에서 미리 보는 용도로 이해하면 됩니다.
다음 안정적인 이정표는 12월 Pixel Feature Drop이며, QPR2 기반입니다.

마치며​

Canary 2611은 App Lock 복귀와 작은 단축키 추가로 월간 트랙의 리듬을 이어갑니다.
테스트 기기에서 먼저 확인하고, 정식 릴리스에 맞춰 대응을 정리해 두는 것이 좋습니다.

Kotlin Toolchain 0.13 — 새 KMP 프로젝트는 kotlin new로 시작하기

October 8, 2026 · 3 min read
Way
Android Developer

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.
JetBrains가 공개한 Kotlin Toolchain 0.13에 대해 설명해드리겠습니다.

배경​

신규 Kotlin Multiplatform(KMP) 프로젝트를 시작할 때는 Gradle 설정 파일을 손으로 짜는 것부터 시작하는 경우가 많았습니다.
JDK나 Android SDK 같은 필수 도구가 갖춰져 있지 않으면, 새 노트북에서 프로젝트를 처음 열었을 때 동기화부터 실패하곤 했습니다.
이번 0.13부터 JetBrains는 신규 KMP 프로젝트에 이 툴체인을 쓰는 것을 공식 권장 경로로 제시했습니다.
자세한 내용은 Kotlin 블로그 원문에서 확인할 수 있습니다.

Kotlin Toolchain 살펴보기​

Kotlin Toolchain은 JVM·Android·iOS·멀티플랫폼·서버 앱을 하나의 CLI 진입점으로 만들고, 빌드하고, 테스트하고, 배포하는 도구입니다.
필수 도구들을 선언적 설정에 맞춰 자동으로 내려받아 주기 때문에 온보딩 과정의 마찰이 크게 줄어듭니다.

kotlin new: 대화형 프로젝트 생성​

0.13의 핵심은 kotlin new 명령입니다.
웹의 KMP Wizard처럼 앱 유형을 고르고 타깃 플랫폼을 선택하면 프로젝트가 생성됩니다.
기존 kotlin init도 같은 흐름으로 맞췄는데, 차이는 kotlin init이 현재 디렉터리에 바로 파일을 만든다는 점입니다.

# 새 프로젝트 생성 (대화형)
kotlin new

# 이미 설치돼 있다면 업데이트
kotlin update

Android 개발자 관점에서 달라진 부분​

  • Android SDK 자동 프로비저닝이 IDE까지 확장: 이전에는 kotlin build/kotlin run 때만 SDK가 자동 설치돼서, 빌드 전에 IDE로 먼저 열면 SDK 누락 오류가 났습니다. 이제 프로젝트 import 시점에도 누락된 SDK 컴포넌트를 자동으로 받아 줍니다.
  • namespace/applicationId 검증 강화: com.example.app 같은 샘플 ID로 실수로 배포 빌드를 만드는 실수를 막아 줍니다.
  • 다운로드 진행 표시: JDK, Android SDK, iOS 런타임, 컴파일러 다운로드가 CLI에 진행 바로 표시됩니다.

Swift Package Manager 의존성 지원​

Apple 타깃에서 SPM 패키지를 선언적으로 가져올 수 있게 됐습니다.
설정 파일에 저장소와 버전을 적으면 됩니다.

dependencies:
  - swiftPackage:
      repository: "https://github.com/firebase/firebase-ios-sdk.git"
      version: "12.17.0"
      products: ["FirebaseCore", "FirebaseFirestore", "FirebaseAnalytics"]

가져온 Objective-C API는 swiftPMImport 접두사로 네임스페이스가 붙어, Kotlin 코드에서 명시적으로 구분됩니다.
로컬 SPM 패키지는 localSwiftPackage 키로 연결할 수 있습니다.

빌드 속도: Kotlin/Native 컴파일러 캐시​

Kotlin/Native 재빌드가 빨라집니다.
컴파일된 네이티브 의존성을 빌드 간, 심지어 프로젝트 간에 캐시로 재사용하고, 프로젝트 코드는 파일 단위 캐시로 링크 시 바뀐 부분만 다시 컴파일합니다.
기존 settings.kotlin.compileIncrementally 설정을 그대로 쓰고, .klib 컴파일 자체는 전체로 수행됩니다.

그 외 변경 사항​

  • IDE 동기화 상태를 에디터에서 확인할 수 있게 됐습니다.
  • 멀티플랫폼 라이브러리 배포 시 Compose Resources와 SwiftPM 의존성 메타데이터가 아티팩트와 함께 게시되고, 서드파티 멀티플랫폼 라이브러리의 Compose Resources도 해석됩니다.
  • AI 에이전트 연동도 강화됐습니다. Compose Hot Reload MCP 서버와 Kotlin용 에이전트 스킬(npx skills add kotlin/kotlin-agent-skills)이 제공됩니다.
  • IDE 기능은 IntelliJ IDEA 2026.2.3 또는 Android Studio Rabbit 1(2026.2.1) 이상에서 최신 Kotlin Toolchain 플러그인과 함께 쓸 수 있습니다.

실무에서 주의할 점​

기존 Gradle 기반 프로젝트를 당장 마이그레이션해야 하는 것은 아닙니다.
JetBrains도 로드맵에서 Gradle 프로젝트의 공백을 먼저 메우는 데 집중하겠다고 밝혔습니다.
따라서 운영 중인 프로젝트는 기존 흐름을 유지하고, 신규 프로젝트나 사이드 프로젝트부터 적용해 보는 것이 안전합니다.

마치며​

새로 KMP를 시작한다면 kotlin new 한 번으로 Android·iOS 환경을 한 번에 맞추는 경험은 꽤 매력적입니다.
다음에 KMP 프로젝트를 시작할 일이 있으면 이 경로로 시작해 보시기 바랍니다.

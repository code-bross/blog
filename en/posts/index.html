AppFunctions 1.0.0-rc01 살펴보기 — 앱 기능을 AI 에이전트에 연결하기

November 7, 2026 · 2 min read
Way
Android Developer

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.
2026년 11월 4일에 공개된 AppFunctions 1.0.0-rc01에 대해 설명해드리겠습니다.

배경​

AppFunctions는 앱의 기능을 AI 에이전트가 호출할 수 있게 노출하는 Jetpack 라이브러리입니다.
Android Dev Summit 2026에서 베타로 발표됐고, 11월 4일 RC 단계에 들어갔습니다.
RC는 API 표면이 확정된 예비 stable 릴리스입니다.
에이전트는 기능을 직접 실행하는 대신, 앱이 선언한 설명을 보고 호출합니다.

AppFunctions 1.0.0-rc01 살펴보기​

의존성을 추가합니다​

dependencies {
    implementation("androidx.appfunctions:appfunctions:1.0.0-rc01")
    ksp("androidx.appfunctions:appfunctions-compiler:1.0.0-rc01")
}

테스트용 아티팩트도 같은 버전으로 제공됩니다.
Android 16(API 36) 이상에서 동작하며, compileSdk 36이 필요합니다.

기능을 선언합니다​

@AppFunctionServiceEntryPoint
class MarketFunctions {

    /**
     * 보유 종목의 현재가를 조회합니다.
     *
     * @param symbol 종목 코드입니다.
     * @return 현재가 정보입니다.
     */
    @AppFunctionDeclaration(isDescribedByKDoc = true)
    suspend fun getStockPrice(symbol: String): StockPrice {
        return withContext(Dispatchers.IO) {
            stockRepository.getPrice(symbol)
        }
    }
}

선언은 @AppFunctionServiceEntryPoint가 붙은 서비스 클래스 안에 둡니다.
@AppFunctionDeclaration이 붙은 함수는 외부 앱이 호출할 수 있습니다.
KSP 컴파일러가 함수 설명을 XML로 만들어 assets에 넣고, 시스템이 이를 색인합니다.
isDescribedByKDoc은 KDoc을 에이전트용 설명으로 쓸지 정합니다.
beta01부터 기본값이 없어 반드시 지정해야 합니다.

기본적으로 메인 스레드에서 실행됩니다​

선언한 함수는 기본적으로 메인 스레드에서 실행됩니다.
네트워크나 파일 작업이 있으면 suspend 함수로 만들고 디스패처를 바꿉니다.
호출자는 EXECUTE_APP_FUNCTIONS 권한이 필요합니다.
사용자 정의 타입을 주고받을 때는 직렬화 규칙을 따라야 합니다.

RC01 변경점​

버전이 RC로 올라갔고, 기존 집계 컴파일러 옵션이 제거됐습니다.
Java 라이브러리 desugaring을 켠 앱에서 java.time 파라미터 역직렬화가 실패하던 문제가 수정됐습니다.
테스트는 Android 17 기기나 에뮬레이터에서 adb shell cmd app_function 명령으로 할 수 있습니다.

실무 관점​

노출하는 기능은 읽기 전용 조회부터 시작하는 것이 안전합니다.
주문처럼 돈이 움직이는 기능은 에이전트에 노출하지 않습니다.
프로덕션 배포는 Connected Apps Platform 프리뷰 등록이 별도로 필요합니다.
설명 문구는 에이전트가 기능을 선택하는 기준이 되므로, KDoc을 정확히 씁니다.

마치며​

AppFunctions가 RC에 들어서면서 에이전트 연동 준비가 한결 가까워졌습니다.
조회 기능부터 작은 범위로 적용해보고, 안정 버전에서 범위를 넓히겠습니다.

Kotlin 2.5.0-Beta2 살펴보기 — 이름 기반 구조 분해와 JDK 17 요구 사항

November 7, 2026 · 3 min read
Way
Android Developer

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.
2026년 10월 21일에 공개된 Kotlin 2.5.0-Beta2에 대해 설명해드리겠습니다.
안정 버전은 12월 공개가 목표입니다.

배경​

구조 분해는 data class의 프로퍼티를 순서대로 꺼내는 문법입니다.
프로퍼티 순서가 바뀌면 같은 타입의 값이 서로 뒤바뀌는 실수가 생깁니다.
이름으로 꺼내는 방식이 2.3.20부터 실험 기능으로 제공됐고, Beta2에서 안정화됐습니다.
컴파일러 실행에 JDK 17 이상이 필요해진 점도 함께 정리했습니다.

Kotlin 2.5.0-Beta2 살펴보기​

이름 기반 구조 분해가 안정화됐습니다​

only-syntax 모드에서 새 문법이 기본값이 됐습니다.
기존 문법은 위치 기준으로 동작합니다.
새 문법은 괄호 안에 val을 넣어 이름을 기준으로 꺼냅니다.
변수 이름은 프로퍼티 이름과 일치해야 하며, 순서는 달라도 됩니다.

data class Account(val owner: String, val balance: Long)

fun printAccount(account: Account) {
    // 기존 문법: 위치 기준으로 꺼냅니다
    val (owner, balance) = account
    println("$owner: $balance")
}

fun printAccountByName(account: Account) {
    // 새 문법: 이름 기준으로 꺼냅니다
    // 순서를 바꿔도 같은 프로퍼티가 들어갑니다
    (val balance, val owner) = account
    println("$owner: $balance")
}

향후 버전에서는 기존 괄호 문법도 이름 기준으로 동작할 예정입니다.
자세한 전환 계획은 The Road to Name-Based Destructuring에서 확인할 수 있습니다.

사용하지 않은 반환값 검사가 추가됐습니다​

반환값을 무시하고 함수를 호출하면 컴파일러가 이를 알려주는 검사가 들어갔습니다.
결과를 확인하지 않고 넘어가는 실수를 줄이는 목적입니다.
Beta 단계에서는 검사가 동작하는 범위를 확인하면서 적용하는 것이 좋습니다.

컴파일러 실행에 JDK 17이 필요합니다​

Beta1에서는 JDK 17보다 오래된 JDK로 컴파일러를 실행하면 경고가 나왔습니다.
Beta2부터는 오류가 발생합니다.
이전 JDK를 임시로 계속 쓰는 플래그가 제공됩니다.
MTS 빌드 환경의 JDK 버전을 먼저 확인합니다.

[versions]
kotlin = "2.5.0-Beta2"
kotlin {
    jvmToolchain(17)
}

그 밖의 변경점​

Java 28을 지원합니다.
Swift export가 새로운 DSL과 함께 Beta 단계에 들어갔습니다.
Kotlin/Native 증분 컴파일이 Apple 대상에서 기본으로 켜졌습니다.
컴파일 타임 상수가 개선됐고, companion 확장과 full value class가 실험 기능으로 들어왔습니다.
자세한 목록은 Kodee's Kotlin Roundup에서 확인할 수 있습니다.

실무 관점​

Beta 버전이므로 운영 코드에 바로 적용하지 않습니다.
이름 기반 구조 분해는 새 코드부터 적용해보고, 기존 구조 분해는 순서를 바꿀 때만 확인합니다.
CI의 JDK 버전을 17 이상으로 맞추지 않으면 빌드가 실패합니다.
안정 버전은 12월 공개가 목표이므로, 그때 다시 정리하겠습니다.

마치며​

이름 기반 구조 분해가 안정화돼 순서 실수를 줄일 수 있게 됐습니다.
JDK 17 요구 사항만 미리 확인하면 12월 안정 버전 전환이 수월해집니다.

Biometric 1.4.0-beta01 살펴보기 — Activity Result 패턴으로 바뀐 생체 인증

November 6, 2026 · 3 min read
Way
Android Developer

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.
2026년 11월 4일에 공개된 Biometric 1.4.0-beta01에 대해 설명해드리겠습니다.

배경​

Biometric의 현재 stable 버전은 1.1.0입니다.
1.4 라인은 2024년 5월 alpha01부터 이어져 왔고, 11월 4일 beta01에 들어섰습니다.
베타 단계는 API 표면이 기능적으로 완성된 상태입니다.
이번 1.4의 핵심은 기존 BiometricPrompt 콜백 방식을 Activity Result 패턴으로 바꾸는 것입니다.

Biometric 1.4.0-beta01 살펴보기​

registerForAuthenticationResult로 등록합니다​

1.4에서는 BiometricPrompt와 biometric-ktx 모듈을 대체하는 새로운 진입점이 도입되었습니다.
Activity Result API와 같은 방식으로 인증을 등록하고 실행합니다.
인증 입력은 AuthenticationRequest로, 결과는 AuthenticationResult로 받습니다.

private val auth = registerForAuthenticationResult { result ->
    when (result) {
        is AuthenticationResult.Success -> onAuthenticated()
        is AuthenticationResult.Error -> showError(result.errString)
        is AuthenticationResult.CustomFallbackSelected -> onFallbackSelected(result)
    }
}

AuthenticationRequest는 두 가지 종류가 있습니다.
생체 인증용 BiometricRequest는 강도(Strength)와 선택적인 Fallback을 지정합니다.
기기 자격 증명 전용 인증용 CredentialRequest도 함께 제공됩니다.
하나의 Activity나 Fragment에서 여러 인증 런처를 동시에 쓸 수도 있습니다.

biometric-compose에서 rememberAuthenticationLauncher를 사용합니다​

1.4.0-alpha05부터는 Compose 전용 biometric-compose 라이브러리도 함께 제공됩니다.
컴포저블 안에서 rememberAuthenticationLauncher로 인증 요청과 콜백을 처리합니다.

val auth = rememberAuthenticationLauncher { result ->
    when (result) {
        is AuthenticationResult.Success -> onAuthenticated()
        is AuthenticationResult.Error -> showError(result.errString)
        is AuthenticationResult.CustomFallbackSelected -> Unit
    }
}

의존성은 다음과 같이 추가합니다.

dependencies {
    implementation("androidx.biometric:biometric:1.4.0-beta01")
    implementation("androidx.biometric:biometric-compose:1.4.0-beta01")
}

Fallback 옵션을 여러 개 둘 수 있습니다​

Android 36.1(Baklava)부터는 생체 인증 프롬프트에서 최대 네 개의 커스텀 Fallback 옵션을 지원합니다.
기존의 단일 부정 버튼 대신, 아이콘을 함께 제공하는 여러 Fallback 옵션을 둘 수 있습니다.
Fallback 옵션은 AuthenticationRequest.Biometric.Fallback으로 제공합니다.
사용자가 Fallback을 선택하면 에러 코드가 아니라 AuthenticationResult.CustomFallbackSelected로 전달됩니다.

그 외 변경점​

BiometricPrompt.CryptoObject에 KeyAgreement 지원이 추가되었습니다.
기본 minSdk가 API 21에서 API 23으로 올라갔습니다.
라이브러리는 이제 JSpecify nullness 어노테이션을 사용합니다.
그 밖에 기기 회전 시 지문 아이콘이 사라지는 문제와 canAuthenticate()에서 잠금 오류를 잘못 반환하는 문제가 수정되었습니다.

실무 관점​

MTS의 로그인이나 이체 인증 화면에서 BiometricPrompt를 쓰고 있다면, 교체 설계는 지금 시작하는 것이 좋습니다.
다만 적용 시점은 stable 릴리스 이후로 잡는 편이 안전합니다.
베타 단계의 API는 기능적으로 완성되었지만, 변경 가능성이 남아 있기 때문입니다.
Fallback 옵션은 PIN이나 패턴 같은 기기 자격 증명 경로와 연결해 설계합니다.
minSdk 23 변경도 적용 대상 단말 목록과 함께 확인합니다.

마치며​

Biometric 1.4는 생체 인증을 Activity Result 패턴으로 바꾸고, Compose 전용 런처와 복수 Fallback 옵션을 함께 가져왔습니다.
인증 화면을 새로 만들거나 고칠 계획이 있다면, 1.4의 새 API를 기준으로 설계하는 것이 좋습니다.

Compose 1.13.0-rc01 살펴보기 — API가 확정된 1.13과 Slider 변경점

November 6, 2026 · 3 min read
Way
Android Developer

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.
2026년 11월 4일에 공개된 Compose 1.13.0-rc01과 Material3 1.5.0-rc01에 대해 설명해드리겠습니다.

배경​

현재 stable 버전은 Compose 1.12.1과 Material3 1.4.0입니다.
1.13 라인은 10월 7일 beta01, 10월 21일 beta02를 거쳐 11월 4일 RC 단계에 들어갔습니다.
RC는 API 표면이 확정된 예비 stable 릴리스입니다.
이 글은 10월 8일 beta01 글과 10월 26일 beta02 글의 후속으로, RC에서 확정된 변경점을 중심으로 정리했습니다.

Compose 1.13.0-rc01 살펴보기​

Kotlin 2.2가 필요합니다​

Compose 1.13 라이브러리는 Kotlin 2.2를 대상으로 빌드되며, 컴파일러도 2.2가 필요합니다.
업데이트 전에 libs.versions.toml의 Kotlin 버전을 먼저 확인합니다.

[versions]
kotlin = "2.2"

Slider에서 onValueChange이 필수가 되었습니다​

Slider, VerticalSlider, RangeSlider에서 onValueChange이 필수 파라미터가 되었습니다.
기존에 숨겨져 있던 deprecated API와 SliderState의 DraggableState 구현, 구형 Saver 오버로드가 제거되었습니다.
SliderState의 isVertical도 제거되었고, SliderDefaults.Thumb의 SliderState 오버로드는 isVertical 오버로드로 대체되었습니다.

var value by remember { mutableFloatStateOf(0.5f) }

Slider(
    value = value,
    onValueChange = { value = it },
)

기존 코드에서 onValueChange을 생략한 Slider가 있다면 컴파일 단계에서 바로 드러납니다.
값 변경을 받지 않는 표시 전용 슬라이더는 onValueChange에 빈 람다를 넘기는 대신, 읽기 전용 표시 방식을 검토하는 편이 낫습니다.

MediaQuery의 Posture가 WindowPosture로 바뀌었습니다​

MediaQuery의 Posture 클래스가 WindowPosture로 대체되었습니다.
WindowPosture는 물리적인 WindowFold를 FoldState와 FoldOrientation으로 노출합니다.
isTabletop과 isFlat 편의 프로퍼티가 추가되었고, 기존의 Book 자세 구분은 제거되었습니다.

if (posture.isTabletop) {
    // 접은 상태에서는 하단 화면에 컨트롤을 배치합니다.
} else if (posture.isFlat) {
    // 펼친 상태에서는 전체 화면 레이아웃을 사용합니다.
}

폴더블 대응 화면에서는 자세 판정 로직을 WindowPosture 기준으로 다시 확인합니다.

Progressive Blur API가 정리되었습니다​

1.13 alpha03에서 추가된 Modifier.blur { ... } API가 RC에서 정리되었습니다.
Modifier.blur의 radius 파라미터가 blurRadiusSpec으로 개명되었고, BlurScope.radius도 blurRadiusSpec으로 바뀌었습니다.
BlurStop.fraction에는 @FloatRange가 추가되었고, BlurRadiusSpec.radialGradient의 기본 fallOffRadius는 Dp.Unspecified로 변경되었습니다.

그 외 변경점​

VectorPainter가 같은 ImageVector를 여러 컴포저블에서 그릴 때 내부 그래픽 리소스를 공유합니다.
반복 아이콘을 쓰는 리스트에서 텍스처 업로드와 메모리 사용이 줄어듭니다.
이 최적화는 ComposeUiFlags.isVectorDrawCacheSharingEnabled 플래그로 끌 수 있습니다.
Modifier.border는 이제 아웃라인 크기를 기준으로 테두리를 그립니다.
문제가 생기면 ComposeFoundationFlags.isBorderMatchesOutlineBoundsFixEnabled 플래그로 이전 동작을 되돌릴 수 있습니다.
Material3 1.5.0-rc01에서는 ToggleButton의 눌림 상태 모양이 디자인 토큰을 따르도록 수정되었고, RangeSlider의 탭 시 값 미반영, 가로 스크롤 컨테이너 안에서의 스크롤 간섭, 이산 값 스냅 시 정밀도 손실이 수정되었습니다.
한편 1.13 alpha03부터 Compose 라이브러리의 compileSdk가 37.1로 올라갔습니다.
앱과 라이브러리의 compileSdk도 함께 올려야 합니다.

RC 단계에서는 프로덕션 적용보다 검증이 먼저입니다.
Slider를 쓰는 화면이 있다면 onValueChange 누락 여부를 컴파일로 확인하고, Kotlin 2.2와 compileSdk 37.1 변경은 별도 브랜치에서 빌드를 검증합니다.

에이전트 경험을 만드는 API 살펴보기​

앱이 에이전트의 도구가 되는 흐름도 이번 서밋의 한 축입니다.
AppFunctions는 앱 기능을 에이전트가 호출할 수 있게 만드는 통합 도구 호출 계층입니다.
이번 서밋에서 AppFunctions가 베타 단계에 들어섰습니다.
에이전트는 함수 이름과 설명만 보고 호출을 결정하므로, 이름과 KDoc이 곧 스키마라는 점을 염두에 두어야 합니다.

/**
 * 코스피 지수 요약 정보를 반환합니다.
 *
 * @param market 조회할 시장 코드입니다.
 */
@AppFunctionDeclaration(isDescribedByKDoc = true)
suspend fun getIndexSummary(
    market: String
): IndexSummary = withContext(Dispatchers.IO) {
    marketRepository.getIndexSummary(market)
}

A2UI for Jetpack Compose는 알파로 공개되었습니다.

Compose 1.13과 적응형 개발 살펴보기​

다가오는 Compose 1.13 stable에는 적응형 레이아웃 지원이 들어갑니다.
Grid와 Flexbox가 stable로 전환되고, Progressive Blur와 Formatted Text가 새로 추가됩니다.
Navigation 3 1.2는 딥 링크 지원과 함께 stable이 되었습니다.
AppState는 Compose의 반응형 모델을 상태 계층까지 확장하는 알파 단계의 building block입니다.
기기 설정이 바뀌어도 상태를 유지하는 구조를 앱과 AI 에이전트가 함께 쓸 수 있게 만드는 것이 목표입니다.

적응형 개발은 폰과 폴더블, 태블릿, 노트북, 차량, XR까지 한 코드베이스로 대응하는 방향으로 정리되었습니다.
Compose adaptive skill이 업데이트되어 기존 Compose UI를 감사하고 키보드 단축키와 커서, 호버 상태, 툴팁을 자동으로 구현합니다.
내비게이션 패턴 이전과 Grid, Flexbox, mediaQuery 기반의 레이아웃 이전도 skill이 다룹니다.
미디어와 카메라 화면을 폴더블의 테이블탑 레이아웃으로 바꾸는 최적화도 포함되었습니다.
내년부터 Google Play는 폴더블에서의 앱 동작을 자세히 살피고, 적응형으로 잘 만든 앱에 더 많은 노출 기회를 줄 예정입니다.
구체적인 스토어 요구사항은 올해 안에 발표될 예정입니다.

@Composable
fun AdaptiveStockList() {
    BoxWithConstraints {
        if (maxWidth > 600.dp) {
            StockGrid()
        } else {
            StockList()
        }
    }
}

XREAL과 함께 XREAL AURA가 공개되었습니다.
Android XR 기반의 첫 유선 XR 글라스입니다.
SceneCore와 ARCore for Jetpack XR, XR Runtime을 비롯한 핵심 Jetpack XR SDK 라이브러리가 stable이 되었습니다.

MTS 앱에 적용한다면, 단계를 나눠 접근하는 것이 안전합니다.

AppFunctions는 베타, A2UI와 ML Kit Agentic API는 알파 단계이므로 프로덕션 노출보다 내부 빌드에서의 검증이 먼저입니다.
AppFunctions에 노출할 함수는 조회처럼 부작용이 없는 것부터 시작하고, 주문이나 이체처럼 돈이 움직이는 동작은 대상에서 빼는 편이 안전합니다.
Compose 1.13의 적응형 기능은 폴더블 대응을 준비하는 팀이라면 미리 살펴볼 만합니다.

마치며​

이번 서밋은 에이전트를 IDE에 들이는 것과 앱을 에이전트에 연결하는 것, 두 방향을 동시에 제시했습니다.

IntelliJ IDEA 2026.3 살펴보기: Kotlin 개발자를 위한 수정 사항 정리

최근 공개된 IntelliJ IDEA 2026.3의 주요 수정 사항을 정리해드리겠습니다.

배경​

이번 릴리스는 1,000개가 넘는 버그 수정과 300개가 넘는 성능 수정을 담았습니다.
성능과 Java, Kotlin 코드 인텔리전스, 그리고 매일 쓰는 핵심 워크플로에 집중한 릴리스입니다.
수정 대부분은 사용자의 오류 보고와 UI 멈춤 보고를 바탕으로 우선순위가 정해졌습니다.
Android Studio를 매일 쓰는 개발자에게도 IDE 기반이 되는 IntelliJ 플랫폼의 변화는 바로 체감되는 부분입니다.

Kotlin 살펴보기​

CancellationException 검사​

새로운 검사는 suspend 코드에서 CancellationException을 잡고 다시 던지지 않는 경우를 경고합니다.
빠른 수정도 함께 제공됩니다.
코루틴 취소는 예외를 다시 던져야 전파되는 구조라, 잡아서 삼키면 취소가 조용히 사라집니다.
특히 네트워크 재시도나 리소스 정리 로직에서 흔히 만나는 실수입니다.

suspend fun loadQuotes() {
    try {
        quoteRepository.refresh()
    } catch (e: CancellationException) {
        throw e
    }
}

위처럼 취소 예외는 반드시 다시 던져야 합니다.
잡아서 로그만 남기고 끝내면 코루틴 취소가 전파되지 않습니다.

suspend 람다의 블로킹 호출 표시​

suspend 람다 안에서 블로킹 호출이 일어나면 이제 에디터에서 강조 표시됩니다.
suspend 함수 안에서 블로킹 I/O를 직접 호출하면 스레드를 점유한 채 멈추게 됩니다.
컴파일은 되지만 런타임에 성능 문제로 이어지는 유형이라, 에디터 단계에서 잡아주는 것이 도움이 됩니다.

suspend fun readCache(): String {
    return withContext(Dispatchers.IO) {
        fileReader.read()
    }
}

블로킹 작업은 위처럼 Dispatchers.IO로 전환해서 실행하는 것이 원칙입니다.

Java를 Kotlin으로 변환할 때 Lombok 처리​

Java를 Kotlin으로 변환할 때 @lombok.Data 클래스가 이제 data class로 변환됩니다.
기존에는 변환 뒤에 data class 정리를 손으로 다시 해야 하는 경우가 있었습니다.
서버 코드나 공유 모듈을 Kotlin으로 옮기는 팀이라면 변환 품질이 조금씩 나아지는 변화입니다.

프로젝트 가져오기 살펴보기​

대규모 Maven과 Gradle 프로젝트 가져오기가 최적화되었습니다.
Kotlin 저장소를 Gradle 9.7로 가져올 때 5분이 걸리던 과정이 대부분 오류 처리 시간이었다는 문제가 수정되었습니다.
원격 개발 호스트에서 가져오기 중 발생하던 데드락도 사라졌습니다.
IDE를 실행할 때 필요하지 않은 상황에서는 WSL이 더 이상 자동으로 시작되지 않습니다.
대형 멀티모듈 프로젝트를 여는 일이 잦은 팀일수록 체감 폭이 큰 수정입니다.

IDE 전반의 개선 살펴보기​

JaCoCo가 새로운 Java 실행 설정의 기본 커버리지 러너가 되었습니다.
Gradle과 Maven, CI 시스템, SonarQube가 이미 쓰는 러너라 IDE와 파이프라인의 커버리지 수치가 일치합니다.
Git worktree는 이제 멀티 루트 프로젝트에서도 동작하고, 별도의 worktree에서 머지 요청을 열 수 있습니다.
GitLab 계정은 개인 액세스 토큰을 붙여넣지 않고 브라우저 로그인으로 연결할 수 있게 되었습니다.
터미널은 ghostty 에뮬레이터를 도입했고 40개가 넘는 수정이 함께 들어갔습니다.
플러그인 관리 화면은 설치됨과 마켓플레이스 탭이 하나로 합쳐져 한 번의 검색으로 찾을 수 있게 되었습니다.
MCP 서버 포트도 설정에서 직접 바꿀 수 있게 되었습니다.

실무 관점​

MTS 앱에 적용한다면, CancellationException 검사가 가장 먼저 눈에 들어옵니다.
코루틴 취소 전파는 시세 갱신이나 주문 조회처럼 반복 호출되는 코드에서 조용히 틀어지기 쉬운 부분입니다.
이번 릴리스로 업데이트한 뒤에는 기존 suspend 코드에서 경고가 뜨는지 먼저 확인해 보는 것이 좋습니다.
JaCoCo 기본값 변경은 IDE와 CI의 커버리지 수치를 맞추는 데 도움이 됩니다.
Gradle 가져오기 개선은 멀티모듈 프로젝트를 매일 여닫는 팀이라면 업데이트할 이유가 됩니다.

마치며​

이번 릴리스는 새 기능보다 멈춤과 가져오기 속도, Kotlin 검사를 다듬는 데 무게가 실렸습니다.
IDE 업데이트를 미뤄 왔다면, 이번 2026.3은 부담 없이 올릴 만한 릴리스입니다.

2026년 11월 3일 Firebase 블로그에 공개된 FCM AndroidConfigV2에 대해 설명해드리겠습니다.

배경​

푸시 알림은 MTS에서 시세 알림과 체결 알림처럼 시간에 민감한 정보를 전달하는 통로입니다.
그런데 기존 FCM 구조에서는 알림이 제때 도착하지 않는 경우가 있었습니다.
원인은 기기 쪽의 배터리 절약 정책과 백그라운드 실행 제한이었습니다.
딥 도즈와 앱 대기 버킷 같은 단계가 메시지 전달을 늦추는 문턱으로 작용했습니다.
기존 방식은 메시지를 시스템 브로드캐스트로 전달했습니다.
앱은 onMessageReceived 콜백 하나에서 모든 메시지를 받았습니다.
이 콜백의 반환 타입이 void라서, 시스템은 알림이 제대로 표시됐는지 알 수 없었습니다.
서버 쪽에서도 우선순위 설정이 추측에 의존하는 경우가 많았습니다.
high와 normal 중 무엇을 골라야 하는지 기준이 명확하지 않았습니다.

AndroidConfigV2 살펴보기​

마이그레이션 문서에 따르면, 핵심 변화는 메시지를 의도 기준으로 나누는 것입니다.
우선순위를 숫자로 지정하는 대신, 메시지 타입 자체가 긴급도를 결정합니다.

두 가지 메시지 타입​

RemoteNotification은 긴급하고 사용자에게 보여야 하는 알림에 사용합니다.
이 타입은 도즈 제한과 배터리 배치 지연을 우회해 즉시 전달됩니다.
BackgroundSync는 긴급하지 않은 데이터 동기화에 사용합니다.
시세 캐시 갱신이나 앱 상태 동기화 같은 작업이 여기에 해당합니다.
이 타입은 배터리 최적화를 위해 배치가 되거나 지연될 수 있습니다.
사용자에게 보이는 알림을 이 타입으로 보내면 안 됩니다.

서버 전송 방식​

서버에서는 기존 android 블록 대신 android_v2 블록을 사용합니다.
그 안에 remote_notification 또는 background_sync 중 하나를 넣습니다.
ttl과 collapse_key 같은 공통 옵션은 그대로 함께 지정할 수 있습니다.
다음은 mutable_content를 켠 remote_notification 전송 예시입니다.

{
  "message": {
    "token": "<DEVICE_REGISTRATION_TOKEN>",
    "android_v2": {
      "ttl": "3600s",
      "collapse_key": "price_alerts",
      "remote_notification": {
        "mutable_content": true,
        "notification": {
          "title": "체결 알림",
          "body": "주문이 체결되었습니다.",
          "channel_id": "trade_alerts"
        }
      }
    }
  }
}

mutable_content가 false이면 기본값 동작으로 GMS Core가 서버 페이로드를 바로 표시합니다.
이 경우 앱의 백그라운드 코드를 깨우지 않습니다.
mutable_content가 true이면 GMS Core가 앱에 바인딩해 콜백을 호출합니다.
앱은 표시 전에 복호화나 이미지 첨부, 현지화 같은 가공을 할 수 있습니다.
이때도 notification 객체를 함께 보내는 것이 중요합니다.
콜백이 타임아웃되거나 충돌하면 이 페이로드가 폴백 알림으로 표시됩니다.

클라이언트 콜백​

클라이언트에서는 FirebaseMessagingService를 확장하는 서비스에 전용 콜백을 구현합니다.
onMessageReceived 하나로 받던 구조에서 역할별 콜백으로 나뉩니다.
onNotificationReceived는 NotificationResponse를 반환해야 합니다.
다음은 서버 알림을 가공해 반환하는 예시입니다.

class MyFirebaseMessagingService : FirebaseMessagingService() {

    override fun onNotificationReceived(message: RemoteMessage): NotificationResponse {
        val serverNotif = message.notification
        val channelId = serverNotif?.channelId ?: "default_channel"
        val builder = NotificationCompat.Builder(this, channelId)
            .setSmallIcon(R.drawable.ic_stat_notification)
            .setContentTitle(serverNotif?.title ?: "알림")
            .setContentText(decryptPayload(message.data["encrypted_content"]))
            .setPriority(NotificationCompat.PRIORITY_HIGH)
            .setAutoCancel(true)
        return NotificationResponse.create("trade_alert", 100, builder.build())
    }

    override fun onBackgroundSyncReceived(message: RemoteMessage) {
        // 사용자 알림을 표시하지 않고 데이터만 동기화합니다.
        syncMarketData(message.data)
    }
}

onNotificationReceived는 20초 안에 NotificationResponse를 반환해야 합니다.
시간을 초과하면 GMS Core가 서버 폴백 알림을 자동으로 표시합니다.
백그라운드 알림의 억제 비율에도 25% 상한이 있습니다.
이 상한을 넘기면 원래 알림이 자동으로 표시됩니다.
onDeletedMessages는 큐가 넘치거나 장기간 오프라인으로 메시지가 삭제된 경우에 호출됩니다.
이 콜백에서는 서버와 전체 상태를 다시 동기화하는 것이 안전합니다.

EAP 단계라는 점​

한 가지 실무적으로 중요한 사실이 있습니다.
클라이언트 SDK는 아직 EAP 단계입니다.
firebase-messaging 26.1.0-eap01은 공개 Maven 저장소가 아니라 로컬 m2repository 아카이브로 배포됩니다.
따라서 운영 앱에 바로 적용하기보다는 별도 브랜치에서 검증하는 것이 안전합니다.
서버 페이로드와 클라이언트 콜백은 독립적으로 업그레이드할 수 있게 설계됐습니다.
서버는 구버전 클라이언트에도 FCM이 자동 변환해 전달한다고 설명하고 있습니다.

실무 관점​

MTS에 적용한다면 메시지 분류부터 정리하는 것이 좋습니다.
체결 알림과 시세 급변 알림은 RemoteNotification으로 보냅니다.
관심종목 시세 동기화나 배지 갱신은 BackgroundSync로 보냅니다.
mutable_content는 복호화나 현지화가 필요할 때만 켜는 것이 좋습니다.
콜백을 거치면 20초 제한과 폴백 동작까지 함께 관리해야 하기 때문입니다.
폴백 페이로드는 항상 함께 보내서, 콜백 실패 시에도 빈 알림이 나가지 않게 합니다.
collapse_key는 오프라인 뒤 복귀 시 최신 페이로드 하나만 전달되게 정리합니다.

마치며​

AndroidConfigV2는 우선순위 추측을 메시지 의도 선언으로 바꾸는 변경입니다.
알림이 늦는 이유를 서버와 클라이언트가 함께 줄일 수 있는 구조가 됩니다.

Android Studio Rabbit 3 Canary 2 살펴보기

Way
Android Developer

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.
Canary 채널에 올라온 Android Studio Rabbit 3 Canary 2에 대해 설명해드리겠습니다.

배경​

Rabbit 2는 현재 Stable 채널에 있습니다.
다음 버전인 Rabbit 3은 Canary 채널에서 제공되고 있습니다.
Canary 빌드는 최신 기능을 먼저 써볼 수 있지만 가볍게 테스트된 단계입니다.
기능이 추가되거나 변경될 수 있다는 전제가 붙습니다.
Canary 2는 Android Gradle Plugin 9.6.0-alpha02와 함께 릴리스됐습니다.
프리뷰 버전의 Studio는 대응하는 프리뷰 AGP와 함께 쓰는 것이 원칙입니다.
이번 글에서는 Rabbit 3에 새로 들어온 기능 네 가지를 살펴보겠습니다.

Rabbit 3 살펴보기​

Compose Preview Screenshot Testing 도구​

Compose UI의 회귀를 막는 스크린샷 테스트 도구가 들어왔습니다.
이 도구는 Compose 프리뷰를 기준으로 스크린샷 테스트를 수행합니다.
결과는 HTML 리포트로 생성돼 UI 변화를 눈으로 확인할 수 있습니다.
디자인 시스템 컴포넌트처럼 화면이 자주 바뀌는 영역에 유용합니다.
스냅샷 비교를 수동 눈대중이 아니라 테스트로 고정할 수 있습니다.

Model Assignment​

AI 모델을 작업 종류별로 다르게 지정하는 기능입니다.
복잡한 추론이 필요한 Agent Mode에는 큰 규모의 모델을 지정할 수 있습니다.
커밋 메시지 생성이나 다음 편집 예측처럼 지연에 민감한 작업에는 가벼운 모델을 지정합니다.
이렇게 하면 품질과 속도, 쿼터 사용량을 작업별로 균형 있게 조절할 수 있습니다.
설정은 다음 경로에서 변경합니다.

File > Settings > Tools > AI > Model Providers > Model Assignment 탭

Agent Mode 패널의 모델 선택 드롭다운에서 직접 바꾸는 방법도 있습니다.
이 경우 Thinking 기능에 대한 Model Assignment 설정이 함께 업데이트됩니다.

iOS, Flutter, React Native 앱 마이그레이션​

기존 크로스 플랫폼 앱을 네이티브 Android 앱으로 바꾸는 도구가 들어왔습니다.
새 프로젝트 마법사에서 마이그레이션 어시스턴트를 호출합니다.
변환 대상은 iOS와 Flutter, React Native 프로젝트입니다.
결과물은 Kotlin과 Jetpack Compose 기반의 Android 앱입니다.
작업 계획과 코드 변환, 컴파일 검사가 통합 진행 UI로 보입니다.
결과물은 바로 테스트와 검증이 가능한 기능하는 프로젝트 형태입니다.

Publish to Google Play for testing​

Play Console 테스트 트랙에 IDE에서 바로 업로드하는 기능이 들어왔습니다.
서명된 앱 번들 생성 흐름이 끝나는 지점에서 이어서 선택합니다.
새 앱의 첫 릴리스는 내부 테스트 트랙에 업로드할 수 있습니다.
기존 앱은 다른 종류의 테스트 트랙에도 업로드할 수 있습니다.
이 기능을 쓰려면 Google Play Console에 등록돼 있어야 합니다.

실무 관점​

Canary는 Stable과 별도로 설치해 운영하는 것이 안전합니다.
운영 프로젝트의 빌드 환경을 Canary로 통째로 옮기는 것은 피하는 것이 좋습니다.
스크린샷 테스트는 전체 화면보다 디자인 시스템 컴포넌트부터 적용하는 것이 좋습니다.
Model Assignment는 쿼터가 소진되는 지점을 확인하면서 조정하는 것이 좋습니다.
Play 테스트 업로드는 내부 트랙부터 검증하고, 이후 트랙을 넓히는 순서가 안전합니다.
마이그레이션 도구는 자동 변환 결과를 그대로 운영에 쓰기보다 컴파일과 동작 검증 뒤에 적용합니다.

마치며​

Rabbit 3는 AI 모델 선택과 UI 회귀 방지, 마이그레이션, 테스트 배포를 한 번에 다룹니다.
Canary라는 전제를 지키면서, 팀에 맞는 기능부터 별도 환경에서 검증하는 것이 좋습니다.

테스트도 minSdk 24 시대로 — AndroidX Test 1.8.0-alpha03과 Espresso 3.8.0-alpha03 살펴보기

November 3, 2026 · 4 min read
Way
Android Developer

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.
2026년 10월 29일에 공개된 AndroidX Test 1.8.0-alpha03과 Espresso 3.8.0-alpha03 그룹 릴리스에 대해 설명해드리겠습니다.

배경​

Android 테스트 코드는 앱 코드만큼 오래 유지됩니다.
그런데 테스트 라이브러리가 지원하는 최소 SDK가 앱의 최소 SDK보다 낮으면, 테스트 코드 안에 오래된 SDK를 위한 분기 로직이 계속 남습니다.
이번 AndroidX Test 알파 그룹은 바로 이 지점을 정리합니다.
그룹 전체가 최소 SDK 24로 올라가며, SDK 24 미만을 위한 로직을 제거했습니다.
알파 버전이므로 운영 앱에 바로 적용하기보다는, 변경 내용을 미리 파악하고 테스트 모듈의 방향을 정하는 데 의미가 있습니다.

AndroidX Test 1.8.0-alpha03 살펴보기​

그룹 릴리스 구성​

2026년 10월 29일에는 테스트 그룹 전체가 함께 올라갔습니다.
Core는 1.8.0-alpha03, Espresso는 3.8.0-alpha03입니다.
Espresso Device는 1.2.0-alpha03, JUnit 확장은 1.4.0-alpha03, Truth 확장은 1.8.0-alpha03입니다.
Runner와 Rules도 1.8.0-alpha03, Orchestrator와 Services는 1.7.0-alpha03, Monitor는 1.9.0-alpha04입니다.
참고로 alpha03 항목 자체에는 별도의 변경 목록이 적혀 있지 않습니다.
실질적인 변경 내용은 직전 버전인 10월 15일의 alpha01에 담겨 있습니다.
따라서 이번 글에서는 alpha01의 변경을 중심으로 살펴보겠습니다.

dependencies {
    androidTestImplementation("androidx.test:core:1.8.0-alpha03")
    androidTestImplementation("androidx.test:core-ktx:1.8.0-alpha03")
    androidTestImplementation("androidx.test.espresso:espresso-core:3.8.0-alpha03")
    androidTestImplementation("androidx.test.ext:junit-ktx:1.4.0-alpha03")
}

최소 SDK 24로의 상향​

alpha01에서 그룹 전체의 최소 SDK가 24로 올라갔습니다.
Core와 Espresso, Espresso Device, JUnit 확장이 모두 같은 기준을 적용했습니다.
SDK 24는 Android 7.0에 해당합니다.
SDK 24 미만을 위한 로직이 제거되면서, 테스트 라이브러리 내부가 단순해졌습니다.
앱의 최소 SDK가 이미 24 이상이라면, 테스트 의존성만으로 인한 제약은 줄어듭니다.
반대로 앱의 최소 SDK가 24보다 낮다면, 이 알파 라인을 적용할 수 없습니다.
안정 버전은 여전히 Core 1.7.0과 Espresso 3.7.0이므로, 운영 모듈에서는 안정 버전을 유지하는 것이 안전합니다.

Espresso의 새로운 Intent 매처​

Espresso alpha01에는 IntentMatchers에 부정 매처가 추가되었습니다.
doesNotHaveFlag와 doesNotHaveFlags가 그 대상입니다.
Intent에 특정 플래그가 없어야 하는 경우를 검증할 때 사용합니다.
기존에는 플래그가 있는 경우를 확인하는 매처가 중심이었습니다.
부정 조건을 직접 표현할 수 있게 되면서, Intent 검증 코드가 읽기 쉬워집니다.
예를 들어 화면 전환 시 특정 플래그가 붙지 않아야 하는 정책을 테스트 코드로 남길 수 있습니다.

버그 수정 내용​

alpha01의 버그 수정도 함께 살펴볼 필요가 있습니다.
SDK 36 API를 사용할 때 TestLooperManagerCompat에서 불필요했던 리플렉션이 제거되었습니다.
dumpThreadStates가 예외를 던지는 경우, AppNotIdleException을 억누르지 않도록 수정되었습니다.
Espresso.onIdle의 트레이싱이 제거되었습니다.
UiControllerImpl의 NullPointerException이 수정되었습니다.
isDisplayingAtLeast 매처는 상위 뷰의 스케일을 반영하도록 수정되었습니다.
스케일이 적용된 상위 뷰 안에 있는 뷰의 표시 비율 판정이 더 정확해집니다.

@Test
fun detailScreen_showsTitle() {
    ActivityScenario.launch(MainActivity::class.java)
    onView(withId(R.id.title))
        .check(matches(isDisplayingAtLeast(90)))
}

실무에서 적용할 때​

알파 버전은 새로운 기능 확인용으로 사용하는 것이 좋습니다.

BaseViewModel을 상속하지 않고 조합하기 — Kotlin 위임과 Lifecycle 2.11 스코프 ViewModel

November 3, 2026 · 4 min read
Way
Android Developer

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.
최근 Medium에서 다뤄진 BaseViewModel의 위임 전환과 Lifecycle 2.11의 스코프 ViewModel을 함께 살펴보겠습니다.

배경​

대부분의 성숙한 Android 코드베이스에는 BaseViewModel 파일이 있습니다.
처음에는 일회성 메시지나 로딩 표시 같은 보일러플레이트를 줄이는 것이 목적입니다.
그런데 시간이 지나면 네트워크 검사, 분석 추적, 오류 다이얼로그, 페이지네이션, 세션 로그아웃까지 쌓입니다.
결국 정적인 화면까지 수백 줄짜리 베이스 클래스를 상속하게 됩니다.
두 가지 부분 동작이 함께 필요한 화면에서는 단일 상속이 한계에 부딪힙니다.
페이지네이션과 검색을 동시에 쓰는 화면이 대표적인 경우입니다.
이 문제를 상속으로 해결하려 하면 베이스 클래스는 더 커지고, 단위 테스트는 모킹 중심으로 어려워집니다.

위임으로 BaseViewModel 대체하기​

기능별 홀더 인터페이스 나누기​

대안은 상속이 아니라 조합입니다.
Kotlin의 인터페이스 위임 by를 사용하면, 필요한 기능만 골라서 붙일 수 있습니다.
먼저 메시지 표시와 로딩 표시를 각각의 인터페이스로 나눕니다.
각 인터페이스는 상태와 상태 변경 함수만 정의합니다.
구현 클래스는 순수한 상태 보관 역할만 맡습니다.
코루틴 스코프는 ViewModel이 소유하므로, 홀더 안에 스코프를 두지 않습니다.

interface MessageHolder {
    val message: StateFlow<String?>
    fun showMessage(text: String)
    fun clearMessage()
}

class DefaultMessageHolder : MessageHolder {
    private val _message = MutableStateFlow<String?>(null)
    override val message: StateFlow<String?> = _message

    override fun showMessage(text: String) {
        _message.value = text
    }

    override fun clearMessage() {
        _message.value = null
    }
}

interface LoadingHolder {
    val isLoading: StateFlow<Boolean>
    fun setLoading(loading: Boolean)
}

class DefaultLoadingHolder : LoadingHolder {
    private val _isLoading = MutableStateFlow(false)
    override val isLoading: StateFlow<Boolean> = _isLoading

    override fun setLoading(loading: Boolean) {
        _isLoading.value = loading
    }
}

ViewModel에서 필요한 것만 조합하기​

ViewModel은 필요한 홀더만 위임으로 가져옵니다.
메시지만 필요한 화면의 ViewModel은 메시지 홀더만 위임합니다.
로딩까지 필요한 화면은 두 홀더를 함께 위임합니다.
두 가지 부분 동작이 필요한 경우에도, 두 인터페이스를 함께 위임하면 해결됩니다.
단위 테스트에서는 실제 홀더를 그대로 쓰거나, 작은 가짜 구현으로 교체할 수 있습니다.
베이스 클래스 전체를 모킹할 필요가 없어집니다.

class HomeViewModel(
    private val repository: HomeRepository
) : ViewModel(),
    MessageHolder by DefaultMessageHolder(),
    LoadingHolder by DefaultLoadingHolder() {

    fun load() {
        viewModelScope.launch {
            setLoading(true)
            try {
                repository.refresh()
            } catch (e: Exception) {
                showMessage("데이터를 불러오지 못했습니다.")
            } finally {
                setLoading(false)
            }
        }
    }
}

Lifecycle 2.11의 스코프 ViewModel​

위임과 함께 살펴볼 기능이 Lifecycle 2.11의 스코프 ViewModel입니다.
2.11.0은 2026년 6월 17일에 공개되었습니다.
ViewModelStoreProvider와 rememberViewModelStoreProvider, rememberViewModelStoreOwner가 새로 들어갔습니다.
이 API들은 ViewModel을 특정 UI 스코프에 묶는 용도입니다.
예를 들어 Pager의 각 페이지마다 별도의 ViewModel을 유지할 수 있습니다.
스코프에 묶인 ViewModel은 구성 변경에도 살아남습니다.
해당 Composable이 계층에서 제거되면 자동으로 정리됩니다.
Navigation3 연동도 함께 강화되었습니다.
ViewModelStoreNavEntryDecorator가 ViewModelStoreOwner를 받아, 중첩된 ViewModel에 생성 정보와 팩토리를 전달합니다.
removeViewModelStoreOnPop은 deprecated 되었습니다.
위임으로 기능을 나누고 스코프로 수명을 나누면, 베이스 클래스에 의존하지 않는 구조가 됩니다.

실무에서 적용할 때​

기존 BaseViewModel을 한 번에 지우지 않는 것이 좋습니다.
신규 화면부터 홀더 위임 방식으로 만들고, 기존 화면은 리팩터링 대상으로 따로 관리합니다.
홀더가 Android 프레임워크 타입에 의존하지 않도록 유지합니다.
그래야 단위 테스트에서 홀더를 그대로 재사용할 수 있습니다.
스코프 ViewModel은 Pager처럼 화면 단위 수명이 필요한 곳부터 적용합니다.
MTS처럼 화면이 많은 앱에서는, 수명 범위를 먼저 정하고 나서 도입하는 것이 안전합니다.

마치며​

상속은 기능을 한 번에 물려주지만, 필요 없는 기능까지 함께 물려줍니다.
위임은 필요한 기능만 골라서 조합하게 하고, 스코프 ViewModel은 수명까지 화면에 맞게 나눠줍니다.

### 배경

푸시 알림은 MTS에서 시세 알림과 체결 알림처럼 시간에 민감한 정보를 전달하는 통로입니다.<br/>
그런데 기존 FCM 구조에서는 알림이 제때 도착하지 않는 경우가 있었습니다.<br/>
원인은 기기 쪽의 배터리 절약 정책과 백그라운드 실행 제한이었습니다.<br/>
딥 도즈와 앱 대기 버킷 같은 단계가 메시지 전달을 늦추는 문턱으로 작용했습니다.<br/>
기존 방식은 메시지를 시스템 브로드캐스트로 전달했습니다.<br/>
앱은 `onMessageReceived` 콜백 하나에서 모든 메시지를 받았습니다.<br/>
이 콜백의 반환 타입이 `void`라서, 시스템은 알림이 제대로 표시됐는지 알 수 없었습니다.<br/>
서버 쪽에서도 우선순위 설정이 추측에 의존하는 경우가 많았습니다.<br/>
`high`와 `normal` 중 무엇을 골라야 하는지 기준이 명확하지 않았습니다.<br/>

### AndroidConfigV2 살펴보기

[마이그레이션 문서](https://firebase.google.com/docs/cloud-messaging/send/v2-api)에 따르면, 핵심 변화는 메시지를 의도 기준으로 나누는 것입니다.<br/>
우선순위를 숫자로 지정하는 대신, 메시지 타입 자체가 긴급도를 결정합니다.<br/>

#### 두 가지 메시지 타입

`RemoteNotification`은 긴급하고 사용자에게 보여야 하는 알림에 사용합니다.<br/>
이 타입은 도즈 제한과 배터리 배치 지연을 우회해 즉시 전달됩니다.<br/>
`BackgroundSync`는 긴급하지 않은 데이터 동기화에 사용합니다.<br/>
시세 캐시 갱신이나 앱 상태 동기화 같은 작업이 여기에 해당합니다.<br/>
이 타입은 배터리 최적화를 위해 배치가 되거나 지연될 수 있습니다.<br/>
사용자에게 보이는 알림을 이 타입으로 보내면 안 됩니다.<br/>

#### 서버 전송 방식

서버에서는 기존 `android` 블록 대신 `android_v2` 블록을 사용합니다.<br/>
그 안에 `remote_notification` 또는 `background_sync` 중 하나를 넣습니다.<br/>
`ttl`과 `collapse_key` 같은 공통 옵션은 그대로 함께 지정할 수 있습니다.<br/>
다음은 `mutable_content`를 켠 `remote_notification` 전송 예시입니다.<br/>

```json
{
  "message": {
    "token": "<DEVICE_REGISTRATION_TOKEN>",
    "android_v2": {
      "ttl": "3600s",
      "collapse_key": "price_alerts",
      "remote_notification": {
        "mutable_content": true,
        "notification": {
          "title": "체결 알림",
          "body": "주문이 체결되었습니다.",
          "channel_id": "trade_alerts"
        }
      }
    }
  }
}
```

`mutable_content`가 `false`이면 기본값 동작으로 GMS Core가 서버 페이로드를 바로 표시합니다.<br/>
이 경우 앱의 백그라운드 코드를 깨우지 않습니다.<br/>
`mutable_content`가 `true`이면 GMS Core가 앱에 바인딩해 콜백을 호출합니다.<br/>
앱은 표시 전에 복호화나 이미지 첨부, 현지화 같은 가공을 할 수 있습니다.<br/>
이때도 `notification` 객체를 함께 보내는 것이 중요합니다.<br/>
콜백이 타임아웃되거나 충돌하면 이 페이로드가 폴백 알림으로 표시됩니다.<br/>

#### 클라이언트 콜백

클라이언트에서는 `FirebaseMessagingService`를 확장하는 서비스에 전용 콜백을 구현합니다.<br/>
`onMessageReceived` 하나로 받던 구조에서 역할별 콜백으로 나뉩니다.<br/>
`onNotificationReceived`는 `NotificationResponse`를 반환해야 합니다.<br/>
다음은 서버 알림을 가공해 반환하는 예시입니다.<br/>

```kotlin
class MyFirebaseMessagingService : FirebaseMessagingService() {

    override fun onNotificationReceived(message: RemoteMessage): NotificationResponse {
        val serverNotif = message.notification
        val channelId = serverNotif?.channelId ?: "default_channel"
        val builder = NotificationCompat.Builder(this, channelId)
            .setSmallIcon(R.drawable.ic_stat_notification)
            .setContentTitle(serverNotif?.title ?: "알림")
            .setContentText(decryptPayload(message.data["encrypted_content"]))
            .setPriority(NotificationCompat.PRIORITY_HIGH)
            .setAutoCancel(true)
        return NotificationResponse.create("trade_alert", 100, builder.build())
    }

    override fun onBackgroundSyncReceived(message: RemoteMessage) {
        // 사용자 알림을 표시하지 않고 데이터만 동기화합니다.
        syncMarketData(message.data)
    }
}
```

`onNotificationReceived`는 20초 안에 `NotificationResponse`를 반환해야 합니다.<br/>
시간을 초과하면 GMS Core가 서버 폴백 알림을 자동으로 표시합니다.<br/>
백그라운드 알림의 억제 비율에도 25% 상한이 있습니다.<br/>
이 상한을 넘기면 원래 알림이 자동으로 표시됩니다.<br/>
`onDeletedMessages`는 큐가 넘치거나 장기간 오프라인으로 메시지가 삭제된 경우에 호출됩니다.<br/>
이 콜백에서는 서버와 전체 상태를 다시 동기화하는 것이 안전합니다.<br/>

#### EAP 단계라는 점

한 가지 실무적으로 중요한 사실이 있습니다.<br/>
클라이언트 SDK는 아직 EAP 단계입니다.<br/>
`firebase-messaging` 26.1.0-eap01은 공개 Maven 저장소가 아니라 로컬 `m2repository` 아카이브로 배포됩니다.<br/>
따라서 운영 앱에 바로 적용하기보다는 별도 브랜치에서 검증하는 것이 안전합니다.<br/>
서버 페이로드와 클라이언트 콜백은 독립적으로 업그레이드할 수 있게 설계됐습니다.<br/>
서버는 구버전 클라이언트에도 FCM이 자동 변환해 전달한다고 설명하고 있습니다.<br/>

### 실무 관점

MTS에 적용한다면 메시지 분류부터 정리하는 것이 좋습니다.<br/>
체결 알림과 시세 급변 알림은 `RemoteNotification`으로 보냅니다.<br/>
관심종목 시세 동기화나 배지 갱신은 `BackgroundSync`로 보냅니다.<br/>
`mutable_content`는 복호화나 현지화가 필요할 때만 켜는 것이 좋습니다.<br/>
콜백을 거치면 20초 제한과 폴백 동작까지 함께 관리해야 하기 때문입니다.<br/>
폴백 페이로드는 항상 함께 보내서, 콜백 실패 시에도 빈 알림이 나가지 않게 합니다.<br/>
`collapse_key`는 오프라인 뒤 복귀 시 최신 페이로드 하나만 전달되게 정리합니다.<br/>

### 마치며

AndroidConfigV2는 우선순위 추측을 메시지 의도 선언으로 바꾸는 변경입니다.<br/>
알림이 늦는 이유를 서버와 클라이언트가 함께 줄일 수 있는 구조가 됩니다.<br/>

### 배경

"주문이 안 들어갔어요"라는 문의가 오면, 개발자는 주문 요청 하나를 처음부터 끝까지 추적해야 합니다.<br/>
그런데 실제 앱에서는 주문 하나가 토큰 갱신, 재시도, 여러 API 호출로 흩어져 있습니다.<br/>
각 호출의 시작과 끝 시간만 찍힌 납작한 로그로는 무엇이 무엇의 자식인지 알 수 없습니다.<br/>

### 트레이싱 적용 살펴보기

#### 트레이스 단위는 비즈니스 연산
- 트레이스 단위는 HTTP 호출 1개가 아니라 비즈니스 연산 1개입니다.
- 주문 넣기, 홈 피드 로드, 인증번호 전송 같은 연산 하나가 앱에서 시작해 마지막 백엔드 서비스까지 도달하는 단일 waterfall이 하나의 트레이스가 됩니다.
- 레포지토리의 함수 하나는 종종 여러 쿼리와 구독을 합쳐놓습니다. GraphQL 호출 하나씩만 트레이싱하면 정확한 숫자를 틀린 것에 대해 구하게 되고, 앱 세션 전체를 트레이스로 묶으면 아무도 분석할 수 없는 거대한 트레이스가 됩니다.
- 그래서 트레이스 루트는 경계가 있는 비즈니스 연산으로 잡아야 합니다.
- 개발자용 API는 단순합니다. 파이프라인의 종료 지점인 `buildOnce`에 타입화된 연산 하나를 인자로 넘기는 것이 전부이며, 스팬을 어디서 열고 닫을지 신경 쓸 필요가 없습니다.

#### 타입화된 연산 카탈로그
- 이 설계의 핵심은 타입화된 연산 카탈로그에 있습니다.
- `ShopperTracedOperation.MakeBid`처럼 연산 이름과 속성(roomId, auctionId, bidValue)이 클래스 하나로 묶여 있습니다.
- 속성 키는 상수 객체에 모아두어, 한 곳은 `room_id`, 다른 곳은 `room.id`로 쓰는 식의 조용한 Grafana 쿼리 깨짐을 막습니다.
- 숫자 타입도 유지돼 TraceQL에서 숫자 비교가 됩니다.

#### SDK 격리와 결함 우회
- KMP SDK인 `opentelemetry-kotlin`은 알파 상태였습니다.
- 글쓴이는 얇은 래퍼(`Tracer`, `Span`, `SpanContext`)로 SDK를 격리한 뒤, 실제 마주친 결함 3가지를 자체 코드에서 우회했습니다.
- 오프라인 내보내기 크래시, 비-protobuf 에러 바디 크래시, 배치 스팬 프로세서의 스레드 안전성 문제가 그 대상입니다.

#### 백엔드와의 연결
- 모바일에서 시작한 스팬과 백엔드 스팬은 W3C `traceparent` 헤더로 하나의 트레이스로 합쳐집니다.
- 조회는 Grafana Tempo와 TraceQL로 합니다.
- 로컬 개발용으로는 `grafana/otel-lgtm` 컨테이너 하나면 충분합니다.

### 실무에서 주의할 점

- 재시도는 별도 스팬으로 나눠야 합니다. 재시도 로직 위에 스팬을 열면 개별 재시도가 보이지 않습니다. 글쓴이는 Apollo 인터셉터를 재시도와 인증 아래에 둬서 물리적 요청마다 스팬을 열고, 각 요청에 `traceparent`를 주입했습니다.
- 복구된 실패는 실패가 아닙니다. 재시도 성공 시 자식 스팬에는 에러가 남지만 루트 스팬은 성공입니다. 에러율 집계를 자식 스팬 기준으로 하면 모든 재시도가 오경보를 내므로, 에러율은 루트 스팬 상태 기준으로만 봐야 합니다.
- 취소는 성공도 아닙니다. 화면을 이탈해 취소된 주문이 초기에는 트레이스 목록에서 성공처럼 보였습니다. 지금은 루트 스팬에 명시적인 `cancelled` 마커를 답니다.
- 스트림은 다르게 다뤄야 합니다. 라이브 룸 같은 구독은 한 시간도 갑니다. 구독당 하나의 긴 스팬은 닫히지 않는 루트라는 세션 트레이스 안티패턴입니다. 대신 수집 시작 시 루트를 열고 첫 번째 실제 결합 상태, 즉 화면이 보여줄 데이터가 생긴 순간에 닫는 bounded root를 씁니다. 트레이싱 대상은 셋업 시간이며, emission마다 트레이스를 만들지 않는 것은 의도된 설계입니다.
- 부모 스팬 전달은 코루틴 컨텍스트로 하지 않는 편이 좋습니다. 첫 버전은 `flow` 블록 안에서 `withContext`로 부모 스팬을 넘겼고 단위 테스트는 통과했지만, 실기기에서 "Flow invariant is violated"로 크래시했습니다. flow는 내부에서 컨텍스트를 바꿀 수 없어서, 지금은 Apollo의 `ExecutionContext`로 전달합니다.
- 폰의 시계는 믿을 게 못 됩니다. 첫 E2E 트레이스에서 백엔드 스팬이 원인이 된 클라이언트 스팬보다 늦게 시작된 것처럼 보였는데, 디바이스 시계 드리프트 때문이었습니다. 앱에 있던 서버 동기화 시계를 SDK에 넘기는 방식으로 해결했습니다.
- 알파 SDK에는 메트릭이 없습니다. SDK에 `Meter` 뼈대는 있지만 인스트루먼트와 내보내기가 없어서, 메트릭은 Collector의 `spanmetrics` 커넥터 쪽으로 넘겼습니다.
- 운영 측면에서는 트레이싱을 앱 쪽 피처 플래그로 사용자별로 켜고, 모듈은 `tracingEnabled` 람다만 받습니다. 플래그는 첫 스팬 때 읽어 프로세스에 캐시하므로 트레이스 도중에 뒤집히지 않고, 엔드포인트가 없으면 트레이서는 no-op이라 SDK도 생성되지 않습니다.
- 디바이스에서 샘플링하지 않습니다. 폰에서 샘플링하면 나중에 Collector 쪽에서 특정 사용자를 잡아내 샘플링할 수 없기 때문입니다. 볼륨은 플래그를 켠 사용자 수로 조절했고, Android부터 단계적으로 올렸습니다.
- 두 앱은 같은 `service.name`으로 보고하고 플랫폼은 속성으로 둡니다. 트레이싱 대상은 거의 항상 백엔드까지 이어지기 때문입니다.
- 알림은 페이저가 아니라 일간 다이제스트로 받습니다. 네트워크가 끊긴 한 명의 사용자가 슬로우와 행 알림을 울려 노이즈가 되기 때문입니다.

### 적용 예시

한투 앱의 "주문 넣기" 연산을 트레이스 루트로 잡는다면 다음과 같이 시작할 수 있습니다.

```kotlin
// 1. 타입화된 연산 카탈로그 — 속성 키는 한 객체에 상수로 모은다
class PlaceOrder(accountNo: String, stockCode: String, qty: Int) :
    TracedOperation(
        name = "placeOrder",
        attributes = mapOf(
            TraceAttributes.ACCOUNT_NO to accountNo,
            TraceAttributes.STOCK_CODE to stockCode,
            TraceAttributes.QUANTITY to qty,
        ),
    )

// 2. 레포지토리 종료 지점에서 인자 하나로 옵트인 — 스팬 위치는 신경 쓰지 않는다
suspend fun placeOrder(...): Result<Order> =
    source(accountStore.account)
        .transformToSource { acct -> source(orderApi.place(acct, req)) }
        .buildOnce(TracedOperation.PlaceOrder(accountNo, stockCode, qty))
```

개발자가 매일 새 쿼리를 추가하는 환경이라면, 추가 가이드를 읽지 않고도 트레이스를 볼 수 있게 만드는 것이 완성 기준이 됩니다.<br/>
트레이싱 가이드를 문서화하고, 붙여넣기 바로 가능한 TraceQL 쿼리를 주는 것까지가 프로젝트의 범위에 들어갑니다.<br/>

### 마치며

트레이싱의 단위를 HTTP 호출이 아니라 비즈니스 연산으로 잡으면, 장애 추적이 로그 뒤지기에서 waterfall 읽기로 바뀝니다.<br/>
KMP 모듈에 적용할 때도 연산 카탈로그와 속성 키 상수화부터 정리해두면, 조회 단계에서의 혼란을 크게 줄일 수 있습니다.

2026년 11월 16일에 공개된 [KEEP-0472](https://github.com/Kotlin/KEEP/blob/main/proposals/KEEP-0472-flexible-constructors.md)의 유연한 생성자 본문 설계 제안에 대해 설명해드리겠습니다.<br/>
이 제안은 생성자가 부모 생성자를 호출하기 전에 검증이나 전처리를 수행할 수 있도록 하는 내용을 담고 있습니다.<br/>
아직 설계 제안 단계이므로, 이 글은 확정된 기능이 아니라 공개 토론 중인 설계를 소개하는 글입니다.<br/>

### 배경

Kotlin에서 생성자는 가장 먼저 부모 생성자나 같은 클래스의 다른 생성자를 호출해야 합니다.<br/>
주 생성자에서는 부모 클래스를 지정하는 선언과 그 생성자에 넘길 인자가 한곳에 묶여 있습니다.<br/>
부 생성자에서는 헤더에 `this`나 `super`를 통한 위임 호출을 직접 적어야 합니다.<br/>
이 구조는 간결하지만, 인자를 계산하는 과정을 헤더 안에 그대로 적어야 한다는 제약을 만듭니다.<br/>
또한 인자에 대한 검증은 인스턴스가 만들어진 뒤에야 `init` 블록에서 수행할 수 있습니다.<br/>
검증이 늦어지면 문제가 있는 인자가 부모 생성자까지 전달된 뒤에야 오류가 드러납니다.<br/>
이 제안은 이런 제약을 풀어, 위임 호출 전에 문장을 실행할 수 있도록 하는 것이 목표입니다.<br/>
설계는 JVM의 [JEP 513](https://openjdk.org/jeps/513)과 같은 방향을 따르고 있습니다.<br/>

### 유연한 생성자 본문 살펴보기

#### 프롤로그와 에필로그

제안은 생성자를 프롤로그와 에필로그 두 구간으로 나눕니다.<br/>
프롤로그는 위임 생성자 호출과 그 인자를 포함한, 호출 이전의 문장들입니다.<br/>
에필로그는 위임 생성자 호출 이후의 문장들입니다.<br/>
위임 생성자 호출은 `this`나 `super`를 수신자로 하는 첫 번째 최상위 호출로, 문법만으로 판별합니다.<br/>
하나의 생성자에는 위임 호출이 최대 하나만 허용됩니다.<br/>
다음 예시는 제안 문서에 실린 것으로, 검증과 인자 계산을 위임 호출 앞으로 옮긴 형태입니다.<br/>

```kotlin
class Hammer(val size: String) : Thing {
    init {
        require(size.isNotEmpty())
        super("$size hammer")
    }

    constructor() : this("normal")

    constructor(sizeInCm: Int) {
        val size = if (sizeInCm > 10) "big" else "small"
        this(size)
    }
}
```

주 생성자를 가진 클래스에서는 `init` 블록 안에 `super` 호출을 둘 수 있습니다.<br/>
부 생성자에서는 본문 안에 `this`나 `super` 호출을 둘 수 있습니다.<br/>
위임 호출이 헤더에 그대로 남아 있는 기존 문법도 계속 사용할 수 있습니다.<br/>

#### 프롤로그의 제약

프롤로그에서는 아직 인스턴스가 만들어지지 않았습니다.<br/>
그래서 프롤로그 안에서는 만들고 있는 인스턴스를 `this`나 `super`로 참조할 수 없습니다.<br/>
프로퍼티를 읽을 수 없고, 프로퍼티 위임도 크게 제한됩니다.<br/>
호출할 수 있는 것은 동반 객체나 정적 메서드가 중심이 됩니다.<br/>
커스텀 세터와 open 세터도 프롤로그에서는 금지됩니다.<br/>
세터가 호출되면 만들어지는 중인 인스턴스를 간접적으로 참조할 수 있기 때문입니다.<br/>
다만 백킹 필드가 있고 커스텀이나 open이 아닌 세터는, 필드에 직접 값을 넣는 것과 같으므로 프롤로그에서 허용됩니다.<br/>
이 제약은 JEP 513의 조기 생성 컨텍스트와 같은 범위를 따릅니다.<br/>

#### 위임 호출의 위치

위임 생성자 호출은 세 곳에 둘 수 있습니다.<br/>
부 생성자 헤더의 `:` 뒤, `init` 블록 안, 부 생성자의 본문 안입니다.<br/>
주 생성자가 있는 클래스에서는 `init` 블록 안의 위임 호출이 반드시 `super`여야 합니다.<br/>
주 생성자가 없는 클래스에서 부 생성자 본문에 위임 호출을 두는 경우, 멤버 프로퍼티 초기화와 `init` 블록은 함께 둘 수 없습니다.<br/>
초기화가 언제 일어나는지 모호해지기 때문입니다.<br/>
이 규칙은 한 생성자의 초기화 순서를 하나로 유지하기 위한 장치입니다.<br/>

#### 값 클래스와의 관계

JVM에서는 값 클래스의 필드를 엄격하게 초기화해야 한다는 요구가 있습니다.<br/>
필드를 모두 초기화한 뒤에야 `super` 생성자를 호출할 수 있어야 합니다.<br/>
이 제안은 그런 순서 제약을 언어로 표현하는 체계적인 방법을 제공합니다.<br/>
다중 필드 값 클래스는 설계상 이 요구를 만족하지만, 제안은 이를 일반적인 생성자 규칙으로 확장하는 기반이 됩니다.<br/>
제안 문서에서는 일반적인 엄격 초기화를 해결하는 것은 아니라고 밝히고 있습니다.<br/>
값 클래스 인스턴스 외에 특정 프로퍼티를 엄격하게 초기화하도록 표시하는 방법은 포함하지 않았습니다.<br/>

### 실무 관점

KEEP-0472는 아직 공개 토론 중인 설계 제안입니다.<br/>
구현 일정이 정해지지 않았으므로, 현재 프로젝트에 적용할 수 있는 기능이 아닙니다.<br/>
다만 방향성은 실무와 직접 연결됩니다.<br/>
생성자 인자에 대한 검증이 인스턴스 생성 전에 가능해지면, 잘못된 인자가 부모 생성자까지 흘러가는 일을 줄일 수 있습니다.<br/>
MTS처럼 생성자에서 유효성을 검사하는 코드가 많은 프로젝트에서는, 검증 위치가 앞당겨지면 오류의 원인을 찾기 쉬워집니다.<br/>
프롤로그의 제약을 미리 이해해 두면, 향후 기능이 도입될 때 인스턴스 참조가 금지되는 구간을 헷갈리지 않고 코드를 짤 수 있습니다.<br/>
제안의 진행 상황은 [KEEP 저장소](https://github.com/Kotlin/KEEP/blob/main/proposals/KEEP-0472-flexible-constructors.md)에서 확인할 수 있습니다.<br/>

### 마치며

KEEP-0472는 생성자 위임 호출 전에 검증과 전처리를 허용하는 설계를 제안합니다.<br/>
아직 설계 단계이지만, 인스턴스 생성 순서를 명확히 하려는 방향은 실무 코드에도 시사하는 바가 큽니다.<br/>

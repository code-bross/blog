안녕하세요, 한국투자증권 [한투](https://play.google.com/store/apps/details?id=com.truefriend.neosmartpension&hl=ko) 앱 개발자 way입니다.

앱에 AI를 넣는다는 건 그동안 "프롬프트 보내고 텍스트 받아서 화면에 보여주기"와 동의어였습니다. 챗봇은 그렇게 만들지만, 모델이 직접 앱의 데이터를 조회하고 API를 호출하고, 민감한 작업 전엔 사용자에게 확인까지 받는 건 다른 차원의 일입니다. Google의 Agent Development Kit(ADK) for Kotlin이 2026년 9월 1.0(공식 블로그 발표는 9월 9일)을 찍으면서, 이 "에이전트"를 코틀린 안에서 만들 수 있게 됐습니다. 10월 14일 Medium에 올라온 Sagar Singh의 튜토리얼 "Your First AI Agent on Android"와 공식 발표를 엮어 실무 포인트만 추립니다.

### 핵심 요약

- **에이전트 = 도구를 쓸 수 있는 모델.** ADK는 "모델이 어떤 도구를 언제 호출할지 스스로 결정하는 루프"를 프레임워크가 대신 돌려주는 오픈소스 도구킷입니다. 개발자는 도구(그냥 코틀린 함수)와 설명만 씁니다.
- **Kotlin답게 설계됐습니다.** 에이전트·도구·러너가 전부 평범한 코틀린 클래스이고, 실행 결과는 코루틴 `Flow`로 돌아와 ViewModel에 자연스럽게 얹힙니다. `@Tool` 어노테이션 + KSP가 빌드 타임에 도구 설명을 생성해서 **런타임 리플렉션이 없습니다**. 폰에서 시작 속도가 빠른 이유입니다.
- **1.0의 의미는 두 가지**: ADK 1.0 Core(Python/Java)와 기능 동등성(feature parity) 달성, 그리고 안드로이드 전용 확장입니다. 온디바이스(LiteRT-LM, ML Kit 베타), 하이브리드(Firebase AI Logic), 프로세스가 죽어도 이어지는 세션(Room), 시맨틱 메모리(AppSearch)까지 앱 스택에 바로 붙습니다.
- **다섯 개의 블록**으로 구성됩니다. `LlmAgent`(이름·모델·지시문·도구 목록), `Model`(두뇌 — Firebase AI의 Gemini나 온디바이스 모델), `Tools`(`@Tool` 함수들), `Runner`(루프를 돌리고 이벤트 Flow를 반환), `Session`(대화 기억).

### 무엇이 달라졌는지

0.1.0(I/O 2026 공개) 시절엔 실험적이었지만, 1.0은 프로덕션용 툴킷을 표방합니다. 코어는 Kotlin Multiplatform이라 백엔드 코틀린에서도 쓸 수 있고, 안드로이드 모듈은 별도 아티팩트로 붙습니다. 모델 백엔드는 한 줄 교체입니다.

| 백엔드 | 아티팩트 | 위치 | 도구 호출 |
|---|---|---|---|
| Firebase AI (Gemini) | `google-adk-kotlin-firebase-android` | 클라우드 | 가능 |
| LiteRT-LM (예: Gemma) | `google-adk-kotlin-litertlm` | 온디바이스 | 가능 |
| ML Kit (Gemini Nano) | `google-adk-kotlin-mlkit-android` (베타) | 온디바이스 | 아직 불가 |

여기서 실무 함정이 두 개 나옵니다. 첫째, **Gemini Nano는 아직 도구 호출을 못 합니다.** ML Kit 백엔드는 함수 호출 파트를 떨구니, 도구를 쓰는 에이전트라면 첫 선택은 Firebase AI가 됩니다. 둘째, **GenAI SDK의 `Gemini` 모델 클래스는 안드로이드 앱용이 아닙니다.** README가 안드로이드에서 API 키·크리덴셜을 차단한다고 못 박고 Firebase AI를 권합니다. 어차피 비밀 키는 APK에 넣으면 안 되니, 이건 제약이 아니라 정답입니다.

### 실무 영향과 주의점

- **세션은 기본이 인메모리입니다.** `InMemoryRunner`의 대화는 프로세스가 죽으면 사라집니다. 1.0에 포함된 Room 기반 `RoomSessionService`를 러너에 넘겨야 재시작 후에도 대화가 이어집니다. 금융 앱의 상담 흐름이라면 이건 필수 요건입니다.
- **민감한 액션은 확인을 강제합니다.** `@Tool(requireConfirmation = true)`로 선언하면 에이전트가 함수를 실행하기 전에 멈춰서 사용자의 승인을 기다립니다. 주문 취소·이체 같은 작업의 안전장치가 프레임워크에 내장돼 있다는 뜻입니다.
- **튜토리얼의 버전을 확인하십시오.** 0.1.0(5월)에서 1.0.0(9월)으로 네 달 만에 올라오면서 의존성 이름과 셋업 단계가 바뀌었습니다. 오래된 글을 보고 `1.0.0` 아티팩트(`com.google.adk:google-adk-kotlin-core:1.0.0` 등)와 섞어 쓰면 빌드가 깨집니다. 공식 Android 가이드의 요구사항은 `compileSdk` 34 이상, `minSdk` 24 이상입니다.
- **도구 설명이 곧 스펙입니다.** 모델은 `@Tool`/`@Param`의 description을 읽고 호출 여부를 결정합니다. 모호한 설명은 모호한 호출을 낳습니다. 지시문(instruction)도 마찬가지입니다.

### 내 코드에서는 이렇게 적용할 생각입니다

"주문 상태를 물어보면 직접 조회해서 답하는" 지원 에이전트를 한투 앱 문맥으로 옮기면 뼈대는 이렇습니다.

```kotlin
// 1. 도구는 그냥 suspend 함수 + 어노테이션. Retrofit/Room 호출이 자연스럽다.
class OrderTools(private val repo: OrderRepository) {
    @Tool(description = "고객 주문의 현재 배송 상태를 반환한다.")
    suspend fun getOrderStatus(
        @Param("주문번호, 예: ORD-1042") orderId: String,
    ): Map<String, String> {
        val o = repo.getOrder(orderId) // 실제 레포지토리 호출
        return mapOf("orderId" to o.id, "status" to o.status, "eta" to o.eta)
    }
}

// 2. ViewModel은 Runner의 Flow만 collect한다.
//    "언제 도구를 호출할지"를 결정하는 if문은 내가 쓰지 않는다.
fun send(message: String) {
    viewModelScope.launch {
        runner.runAsync(
            userId = "local-user",
            sessionId = sessionId, // 같은 세션을 재사용하면 이전 대화를 기억한다
            newMessage = Content.fromText(Role.USER, message),
        ).catch { e -> _reply.value = "오류: ${e.message}" }
         .collect { event ->
            event.content?.parts?.firstOrNull()?.text
                ?.takeIf { it.isNotBlank() }
                ?.let { _reply.value = it }
        }
    }
}
```

빌드 한 번 돌리면 KSP가 `OrderTools().generatedTools()` 확장 함수를 만들어줍니다. 빨간 줄이 보이면 빌드를 한 번 돌리라는 게 원문 튜토리얼의 팁입니다.

안녕하세요, [한국투자증권](https://securities.koreainvestment.com/main/Main.jsp)에서 [한투-한국투자증권](https://play.google.com/store/apps/details?id=com.truefriend.neosmartarenewal&hl=ko) 개발을 담당하고 있는 way입니다.<br/>
SharedPreferences를 DataStore로 옮기고 싶은데 "성능이 나빠지진 않을까" 망설였던 팀이라면, 이번 ProAndroidDev 커뮤니티 글이 좋은 참고 자료입니다. 대규모 앱의 스토리지 기반을 통째로 갈아엎고, 영향을 숫자로 증명한 사례거든요.

### 핵심 요약

- 한 대규모 앱 팀이 핵심 로컬 데이터를 SharedPreferences에서 Jetpack DataStore로 이전했습니다.
- 다른 변경의 영향이 섞이지 않도록 빌드를 3개로 나눠 측정한 결과, **DataStore 자체의 런타임 비용은 측정 오차 범위 안이었습니다**. 콜드 스타트, CPU, 메모리 모두 마찬가지입니다.
- 기존 사용자 데이터 마이그레이션은 백그라운드 스레드에서 1회 실행되며 수십 ms에 끝납니다. 저사양 기기 업데이트 시나리오에서도 첫 실행이 느려지지 않았습니다.

### 무엇이 달라졌는지

#### 왜 SharedPreferences를 떠났나

글쓴이가 꼽은 SharedPreferences의 한계는 다섯 가지입니다.

1. 첫 읽기가 동기식이라 메인 스레드에서 호출하면 화면이 같이 기다립니다.
2. `apply()`는 비동기처럼 보이지만 Activity 종료 시점에 밀린 쓰기를 모두 기다립니다. 저장소가 느린 기기에서는 ANR로 이어질 수 있습니다.
3. 쓰기 실패가 조용히 묻힙니다. `apply()`는 성공 여부를 알려주지 않습니다.
4. 변경을 관찰하기 어렵습니다. 리스너 방식은 누수 나기 쉽고 코루틴/Flow와도 어울리지 않습니다.
5. 타입이 강제되지 않습니다. `Int`로 저장한 걸 `Long`으로 읽으면 런타임에 `ClassCastException`으로 터집니다.

DataStore는 정확히 이 지점들을 겨냥한 설계이니, "왜 옮기냐"에 대한 답은 비교적 명확합니다.

#### 측정 방법이 인상적인 부분

제일 배울 점은 측정 설계입니다. 이번 릴리스에는 DataStore 말고도 다른 변경이 많았기 때문에, 팀은 **빌드를 3개로 나눠서** 쟀습니다.

- 이전 릴리스
- 이번 릴리스에서 DataStore만 뺀 빌드
- 실제로 배포한 이번 릴리스

두 번째와 세 번째의 차이가 곧 DataStore의 순수 비용입니다. Xiaomi Redmi Note 9 Pro(Snapdragon 720G, 6GB RAM)에서 24분짜리 단일 세션에 몰아넣어 빌드당 10회 콜드 스타트를 연달아 쟀습니다. 결과는 모든 차이가 같은 빌드 내 변동 폭 안에 들었습니다. 오히려 CPU만은 B 화면 아이들 상태에서 2.6포인트 일관되게 내려갔고, 이건 두 번의 별도 측정 세션에서 모두 재현됐습니다.

#### 저사양 기기 업데이트 시나리오

마이그레이션이 실제로 도는 건 기존 사용자가 업데이트할 때라서, Galaxy A15에서 구버전 데이터를 깔아둔 상태로 10회씩 쟀습니다(Perfetto). 10회 콜드 스타트와 10회 웜 스타트 모두 새 APK가 빨랐고, 마이그레이션이 도는 첫 실행(7.04초)도 평균보다 느리지 않았습니다. 즉 **마이그레이션이 기존 사용자를 붙잡지 않습니다**.

### 실무 영향 / 주의점

- **"DataStore로 옮기면 느려진다"는 선입견을 깨는 수치입니다.** 측정 오차 범위 안에 든다는 건, 실무적으로는 비용이 없다는 뜻입니다.
- **하지만 이 팀의 결론은 "DataStore가 앱을 빠르게 했다"가 아닙니다.** 같은 릴리스에서 Galaxy A55 기준 첫 화면이 0.7초 빨라진 건 팀 전체의 작업 덕분이고, DataStore는 그 발목을 잡지 않았을 뿐입니다. 숫자를 읽을 때 귀속 관계를 헷갈리면 안 됩니다.
- **마이그레이션 소요 시간은 텔레메트리로 잡았습니다.** 백그라운드에서 수십 ms에 끝난다는 주장이 "느낌"이 아니라 측정값인 게 이 글의 신뢰도를 올립니다.
- 글쓴이 본인도 경고합니다. 모든 숫자는 물리 기기에서 직접 잰 내부 측정값이라, 내 앱·내 기기에서는 값이 다를 수 있습니다.

### 내 코드에서는 이렇게 적용할 생각입니다

DataStore Preferences로 옮길 때 기존 SharedPreferences 데이터를 살리는 표준 패턴은 이렇습니다.

```kotlin
// 기존 prefs 데이터를 잃지 않고 DataStore로 1회 마이그레이션
val Context.dataStore by preferencesDataStore(
    name = "settings",
    produceMigrations = { context ->
        listOf(SharedPreferencesMigration(context, "old_prefs"))
    }
)

// 읽기: 코루틴/Flow에 자연스럽게 연결
val darkMode = context.dataStore.data
    .map { prefs -> prefs[DARK_MODE_KEY] ?: false }
```

글에서 얻은 교훈을 우리 팀에 적용한다면 두 가지를 가져가고 싶습니다. 첫째, 성능을 우려하는 대규모 변경은 "변경만 뺀 비교 빌드"를 하나 더 만들어 측정하기. 둘째, 마이그레이션 소요 시간을 텔레메트리 이벤트로 남겨서 운영 중에도 실제 숫자를 볼 수 있게 하기. 이 두 가지만 해도 "느려진 거 아니야?"라는 질문에 감이 아니라 숫자로 답할 수 있습니다.

### 마치며

스토리지 마이그레이션은 사용자에게 보이지 않는 게 성공입니다. 유실도 없고, 중간에 끊긴 세션도 없고, 느려진 앱도 없는 것 — 그걸 숫자로 증명한 사례가 나왔다는 점에서, 아직 SharedPreferences에 머물러 있는 팀에게 한 번쯤 읽어볼 만한 글입니다.

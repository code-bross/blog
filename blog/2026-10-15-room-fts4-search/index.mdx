### 배경

종목 메모, 공지 목록, 최근 본 상품 같은 오프라인 검색을 로컬 DB의 `LIKE '%쿼리%'`로 구현하는 경우가 많습니다.<br/>
개발 중에는 더미 데이터가 몇십 건 수준이라 0.1초도 걸리지 않아 그대로 넘어가기 쉽습니다.<br/>
[Scaling Android Search: Room @Fts4 vs SQL LIKE](https://proandroiddev.com/scaling-android-search-room-fts4-vs-sql-like-b2a8232cbd12)에서는 이 방식을 실측 수치로 비교합니다.<br/>
5,000건 기준으로 LIKE는 63.8ms, FTS4는 6.8ms가 걸려 9.4배의 차이가 났습니다.

### Room @Fts4 살펴보기

#### 왜 LIKE가 느린지
- B-Tree 인덱스는 접두사를 알 때만 사용할 수 있습니다.
- `WHERE sender LIKE 'alice%'`는 인덱스를 타지만, 실제 검색 UI는 중간 매칭이 필요해 `WHERE body LIKE '%architecture%'` 형태가 됩니다.
- 검색어 앞에 `%`를 붙이는 순간 인덱스는 무력화되고 전체 테이블 스캔으로 떨어집니다.
- 실측에서는 2,000건만 돼도 LIKE가 약 30ms로 60Hz 프레임 예산인 16.6ms를 훌쩍 넘겼습니다.
- 또한 LIKE는 단어 경계를 모르고(`"cat"` 검색에 `"catalog"`, `"scatter"`까지 걸립니다), 어간 추출이 안 되며(`"optimize"`로 `"optimized"`를 못 찾습니다), 관련도 순위도 없습니다.

#### FTS4와 역인덱스
- FTS4는 쿼리 시점이 아니라 INSERT 시점에 일을 합니다.
- 토크나이저가 텍스트를 단어로 쪼개고 대소문자를 정규화해, "단어 → 문서 ID 목록" 형태의 역인덱스를 만듭니다.

```text
Token        | DocIDs (Posting List)
architecture | [1, 14, 108, 492]
benchmark    | [1, 7, 22, 108, 305]
```

- `MATCH 'benchmark*'` 같은 쿼리가 들어오면 토큰 딕셔너리에서 단어를 찾아 docid 목록을 바로 뽑아냅니다.
- 관계없는 텍스트는 한 바이트도 읽지 않으므로, 행이 100개든 10만 개든 조회는 밀리초 단위로 끝납니다.

#### contentEntity 패턴
- 원본 테이블은 그대로 두고, 검색용 FTS 가상 테이블을 `contentEntity`로 붙이는 패턴이 표준입니다.

```kotlin
@Entity(tableName = "notices")
data class NoticeEntity(
    @PrimaryKey(autoGenerate = true) val id: Long = 0,
    val title: String,
    val body: String,
    val pinned: Boolean = false,
)

@Entity(tableName = "notices_fts")
@Fts4(contentEntity = NoticeEntity::class)
data class NoticeFtsEntity(
    val title: String,
    val body: String,
)
```

- `contentEntity`를 지정하면 FTS 테이블은 역인덱스 구조만 갖고, 실제 텍스트는 원본 `notices` 테이블에서 가져오므로 데이터 중복이 없습니다.
- Room이 `AFTER INSERT/UPDATE/DELETE` 트리거를 자동 생성해서, 원본에 쓰기만 하면 인덱스가 자동으로 반영됩니다.
- DAO에서는 `docid`로 조인해 `MATCH`를 사용합니다.

```kotlin
@Dao
interface NoticeDao {
    @Query("""
        SELECT notices.* FROM notices
        JOIN notices_fts ON notices.id = notices_fts.docid
        WHERE notices_fts MATCH :query
        ORDER BY notices.pinned DESC
    """)
    suspend fun searchNoticesFts(query: String): List<NoticeEntity>
}
```

- 기존 테이블에 FTS를 붙이는 작업은 DB 버전 업과 `AutoMigration` 또는 수동 마이그레이션으로 처리합니다.
- 가상 테이블은 원본 스키마 변경과 독립적이라 마이그레이션 부담도 크지 않습니다.

### 실무에서 주의할 점

- LIKE는 프로토타입용입니다. 메시지, 문서, 메모, 상품 카탈로그처럼 사람이 입력하는 텍스트 검색이라면 데이터가 수천 건으로 자라기 전에 FTS로 옮기는 것이 맞습니다.
- 쓰기 비용은 있습니다. FTS 테이블은 INSERT와 UPDATE 때마다 인덱스를 갱신하므로, 쓰기가 빈번하고 읽기가 드문 워크로드라면 이득이 줄어듭니다.
- 쿼리 위생이 필수입니다. `MATCH`에 사용자 입력을 그대로 넣으면 따옴표 같은 특수문자가 쿼리 문법을 깨뜨립니다. 입력에서 따옴표를 제거하고, as-you-type 검색을 위해 토큰마다 접미사 `*`를 붙이는 sanitize 함수를 따로 두어야 합니다.

```kotlin
// "삼성 전자" -> "삼성* 전자*" : 토큰별 접두사 매칭으로 자동완성 느낌의 검색
fun sanitizeFtsQuery(raw: String): String =
    raw.replace("\"", "").replace("'", "").trim()
        .split("\\s+".toRegex())
        .filter { it.isNotEmpty() }
        .joinToString(" ") { "$it*" }
```

- 한국어는 토크나이저를 골라야 합니다. FTS4 기본 토크나이저(simple)는 공백 기준이라 한국어 조사가 붙은 단어("검색어를")는 토큰 하나가 됩니다. 영어 위주 앱이 아니라면 `unicode61` 계열 토크나이저로 바꾸거나, 형태소 분석이 필요하면 별도 토크나이저를 검토해야 합니다. Porter stemmer도 영어용이라는 점을 잊지 마시기 바랍니다.

### 마치며

검색 속도는 데이터가 쌓인 뒤에 손대면 마이그레이션 비용까지 함께 커집니다.<br/>
검색 대상이 텍스트이고 건수가 늘어날 구조라면, 처음부터 `@Fts4`와 `contentEntity` 패턴으로 시작하는 편이 유지보수에 유리합니다.

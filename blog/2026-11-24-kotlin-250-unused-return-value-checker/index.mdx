### 배경

불변 API를 쓸 때는 반환값을 받는 것이 연산 그 자체입니다.<br/>
원본을 바꾸는 대신 새 값을 돌려주는 함수가 많기 때문입니다.<br/>
반환값을 받지 않으면 연산은 실행되지 않은 것과 같습니다.<br/>
그런데 지금까지는 반환값을 버려도 컴파일러가 아무런 경고를 내지 않았습니다.<br/>
코드는 정상적으로 컴파일되고, 테스트도 조용히 지나갔습니다.<br/>
화면에는 아무 변화가 없어야 할 변화가 없어도, 원인을 찾기까지 시간이 걸렸습니다.<br/>
미사용 반환값 검사는 이런 실수를 컴파일 시점에 잡아주는 기능입니다.<br/>
반환값을 써야 하는 호출의 결과를 무시하면 경고를 냅니다.<br/>

### 미사용 반환값 검사 살펴보기

미사용 반환값 검사는 [Kotlin 2.5.0-RC](https://kotlinlang.org/docs/whatsnew-eap.html)에서 안정화되고 기본으로 활성화되었습니다.<br/>
검사 대상은 `Unit`이 아닌 값을 돌려주는 표현식입니다.<br/>
결과를 변수에 담지 않고 그냥 호출만 하면 경고가 나옵니다.<br/>
하나씩 살펴보겠습니다.<br/>

#### 어떤 경우에 경고가 나오는지

가장 흔한 예는 컬렉션 변환 함수를 호출만 하고 결과를 쓰지 않는 경우입니다.<br/>
다음 코드는 원본 리스트를 바꾸지 않고 새 리스트를 돌려줍니다.<br/>
결과를 받지 않으면 아무 일도 일어나지 않습니다.<br/>

```kotlin
fun process(postalCodes: List<String>) {
    postalCodes.map { it.uppercase() } // 경고: Unused return value of 'map'
}
```

이진 연산의 결과를 무시하는 경우에도 경고가 나옵니다.<br/>
계산만 하고 결과를 어디에도 쓰지 않으면, 연산 자체가 의미가 없습니다.<br/>
다만 `++`나 `--` 같은 증감 연산은 경고 대상이 아닙니다.<br/>
`condition || return`처럼 오른쪽 식이 함수를 빠져나가는 단축 평가도 경고가 나오지 않습니다.<br/>

#### Check 모드와 Full 모드

검사의 동작은 컴파일러 옵션 `-Xreturn-value-checker`로 조절할 수 있습니다.<br/>
모드는 세 가지입니다.<br/>
`disable` 모드는 검사를 끕니다.<br/>
`check` 모드는 표시된 함수의 반환값을 검사합니다.<br/>
표준 라이브러리의 대부분 함수가 이미 표시되어 있습니다.<br/>
2.5.0-RC에서는 `check` 모드가 기본값입니다.<br/>
`full` 모드는 프로젝트 안의 모든 함수를 검사 대상으로 봅니다.<br/>

```kotlin
// build.gradle.kts
kotlin {
    compilerOptions {
        freeCompilerArgs.add("-Xreturn-value-checker=check")
    }
}
```

기본값이 `check` 모드이므로, 별도 설정 없이도 표준 라이브러리 호출에 대한 검사가 동작합니다.<br/>
`full` 모드는 검사 범위가 넓어지므로, 팀에서 기준을 정한 뒤에 적용하는 것이 좋습니다.<br/>

#### 내 함수에 표시하기

검사 대상은 애너테이션으로 직접 지정할 수도 있습니다.<br/>
반환값을 반드시 써야 하는 함수에는 `@MustUseReturnValues`를 붙입니다.<br/>
반대로 반환값을 무시해도 되는 함수에는 `@IgnorableReturnValue`를 붙여 경고를 막습니다.<br/>

```kotlin
@MustUseReturnValues
fun calculateFee(amount: Long): Long {
    return amount * 3 / 100
}

@IgnorableReturnValue
fun tryRefresh(): Boolean {
    return true
}
```

`calculateFee`의 결과를 받지 않으면 경고가 나옵니다.<br/>
`tryRefresh`는 결과를 무시해도 경고가 나오지 않습니다.<br/>
라이브러리를 만드는 쪽에서는 이 표시가 호출하는 쪽의 실수를 막아줍니다.<br/>

#### 의도적인 무시는 명시하기

반환값을 일부러 쓰지 않는 경우도 있습니다.<br/>
함수를 부작용 때문에 호출하는 경우가 그 예입니다.<br/>
이럴 때는 `val _ =`으로 결과를 받는다고 명시하면 경고가 나오지 않습니다.<br/>

```kotlin
expr.apply {
    // 부작용을 위해 호출한다는 점을 명시합니다.
    val _ = computeResult()
}
```

스코프 함수와 함께 쓸 때는 주의가 필요합니다.<br/>
`apply`는 람다 결과를 `Unit`으로 바꾸므로, 안에서 호출한 함수의 반환값은 경고 대상이 됩니다.<br/>
`let`은 반환값의 무시 가능성을 그대로 전파합니다.<br/>
그래서 `let` 안에서는 전체 `let` 식의 결과를 무시할 때만 경고가 나옵니다.<br/>

```kotlin
expr.let {
    it.computeResult() // 전체 let 식의 결과를 무시할 때만 경고가 나옵니다.
}
```

#### 적용하기

Kotlin 2.5.0-RC는 Version Catalog에서 Kotlin 버전을 교체하면 적용할 수 있습니다.<br/>

```toml
[versions]
kotlin = "2.5.0-RC"

[plugins]
kotlin-android = { id = "org.jetbrains.kotlin.android", version.ref = "kotlin" }
```

RC는 정식 출시 직전 단계이므로, 새 기능이 동결되고 안정화 작업이 중심이 됩니다.<br/>
검사 기능 자체는 안정화되었지만, RC 버전은 정식 버전이 아닙니다.<br/>
기존 프로젝트에 올릴 때는 브랜치에서 먼저 빌드해 경고가 얼마나 나오는지 확인하는 것이 안전합니다.<br/>

### 실무 관점

국내 MTS 프로젝트에 적용한다면, 기존 코드에서 경고가 얼마나 나오는지 먼저 확인하는 것이 좋습니다.<br/>
규모가 큰 프로젝트에서는 경고가 한 번에 많이 나올 수 있습니다.<br/>
경고마다 실제 버그인지 먼저 확인하고, 억제 애너테이션부터 붙이지 않는 것이 좋습니다.<br/>
경고가 실제 버그였던 경우는 그 자리에서 고치는 것이 목적에 맞습니다.<br/>
새로 작성하는 코드부터 검사를 기준으로 삼으면, 경고 목록을 조금씩 줄여나갈 수 있습니다.<br/>
`full` 모드는 팀 기준을 정한 뒤에 적용하고, 당장은 기본값인 `check` 모드로 시작하는 것이 좋습니다.<br/>

### 마치며

미사용 반환값 검사는 버려지는 연산 결과를 컴파일 시점에 잡아주는 기능입니다.<br/>
기본값으로 활성화되었으므로, 경고가 나오면 억제하기 전에 실제 버그인지 먼저 확인하는 것을 권합니다.<br/>

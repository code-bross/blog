Kotlin 2.5.0-RC2의 KMP 새 컴파일 방식과 게시 포맷 살펴보기

2026년 11월 27일 · 약 3분
Way
Android Developer

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.
2026년 11월 25일에 공개된 Kotlin 2.5.0-RC2의 Kotlin Multiplatform 새 컴파일 방식과 새 게시 포맷에 대해 설명해드리겠습니다.
두 변경 모두 실험적 기능이지만, 멀티플랫폼 프로젝트의 빌드와 게시 방식을 바꿀 수 있는 내용입니다.

배경​

Kotlin Multiplatform 프로젝트에서는 공통 소스셋의 코드를 컴파일러와 IDE가 다르게 해석하는 경우가 있었습니다.
오버로드 해석이나 타입 추론에서 IDE 분석과 컴파일러 판단이 달라지면, IDE에서는 되던 코드가 빌드에서 실패하기도 합니다.
게시 측면에서는 타깃을 추가할 때마다 게시 파일이 늘어나 Maven Central의 게시 크기 제한에 걸리는 문제도 있었습니다.
이번 릴리스에서는 이 두 가지 문제를 다루는 실험적 기능이 함께 공개되었습니다.

KMP 새 컴파일 방식과 게시 포맷 살펴보기​

공통 소스셋을 따로 컴파일하는 새 방식​

Kotlin 2.5.0-RC2에서는 Kotlin Multiplatform을 위한 새로운 실험적 컴파일 방식이 추가되었습니다.
이 방식에서는 컴파일러가 공통 소스셋을 IDE와 같은 기준으로 처리합니다.
공통 코드가 플랫폼 전용 선언으로 잘못 해석되는 일을 막고, 오버로드 해석과 타입 추론의 일관성을 높입니다.
공통 소스셋에 대한 증분 컴파일을 구현하는 기반도 됩니다.
자세한 내용은 Kotlin 2.5.0-RC2 변경 사항에서 확인할 수 있습니다.

.kar 아카이브 게시 포맷​

Kotlin 2.5.0-RC2에서는 멀티플랫폼 라이브러리를 위한 새로운 실험적 게시 포맷이 추가되었습니다.
새 포맷은 JVM과 Android을 제외한 플랫폼 아티팩트를 하나의 .kar 아카이브로 게시합니다.
.kar 파일은 ZIP 아카이브를 XZ로 한 번 더 압축한 형태입니다.
타깃을 추가해도 새 파일이 생기지 않으므로, 게시물 전체 크기가 크게 늘어나지 않습니다.
JetBrains가 예시로 든 cryptography-kotlin 라이브러리에서는 게시 파일이 7,539개에서 1,036개로, 전체 크기가 91MB에서 23MB로 줄었습니다.

모듈 단위로 새 포맷을 켜려면 빌드 스크립트에 다음과 같이 설정합니다.

kotlin {
    publishing {
        publicationFormat.set(KotlinPublicationFormat.KOTLIN_ARCHIVE)
    }
}

프로젝트의 모든 모듈에 적용하려면 gradle.properties에 다음 속성을 추가합니다.

kotlin.publicationFormat=KOTLIN_ARCHIVE

새 포맷으로 게시하는 기능은 아직 실험적이지만, 새 포맷으로 게시된 아티팩트를 가져다 쓰는 기능은 모든 프로젝트에서 이미 사용할 수 있습니다.
이 변경은 라이브러리를 게시하는 쪽에만 해당하며, 최종 앱을 만드는 개발자에게는 직접적인 영향이 없습니다.

실무 관점​

새 컴파일 방식은 공통 소스셋의 동작을 바꾸는 실험적 기능입니다.
적용하기 전에는 별도 브랜치에서 기존 테스트가 그대로 통과하는지 확인하는 것이 좋습니다.
.kar 게시 포맷은 MTS처럼 최종 앱을 만드는 프로젝트보다는, 내부 공용 라이브러리를 Maven에 게시하는 경우에 의미가 있습니다.
게시 크기가 제한에 걸려 타깃 추가를 미루고 있었다면, 새 포맷을 검토해 볼 만합니다.
두 기능 모두 실험적이므로, 정식 릴리스에서 동작이 바뀔 수 있다는 점을 고려해야 합니다.

마치며​

Kotlin 2.5.0-RC2의 새 컴파일 방식은 공통 소스셋의 해석을 IDE와 일치시키는 방향으로 나아가고 있습니다.
새 게시 포맷은 멀티플랫폼 라이브러리의 게시 크기를 크게 줄여, 타깃 확장의 부담을 덜어줍니다.

Kotlin Toolchain 0.14 살펴보기 — TestFlight 게시와 에이전트 스킬

2026년 11월 20일 · 약 4분
Way
Android Developer

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.
2026년 11월 18일에 공개된 Kotlin Toolchain 0.14에 대해 설명해드리겠습니다.
이번 릴리스는 TestFlight 게시와 에이전트 워크플로 개선이 중심입니다.

배경​

Kotlin Multiplatform으로 iOS 앱을 만들면, 게시 단계에서 Xcode와 서명 설정을 따로 다뤄야 합니다.
Android 개발자가 iOS 게시를 처음 맡으면 App Store Connect와 서명 절차에서 시간을 쓰게 됩니다.
Kotlin Toolchain은 환경 설정부터 빌드와 테스트, 발행까지 한 곳에서 처리하는 단일 CLI입니다.
0.14에서는 TestFlight 게시 흐름이 쉬워졌고, 에이전트 워크플로와 Android desugaring, 의존성 해석도 함께 개선됐습니다.
최신 기능을 IDE에서 쓰려면 IntelliJ IDEA 2026.2.4 이후 버전이나 Android Studio Rabbit 1 | 2026.2.1 이후 버전에 최신 Kotlin Toolchain 플러그인을 설치해야 합니다.

Kotlin Toolchain 0.14 살펴보기​

kotlin publish testflight로 TestFlight 게시하기​

0.14에는 TestFlight 게시를 안내하는 쉬운 게시 흐름이 들어왔습니다.
다음 명령 하나가 게시를 위해 필요한 대부분의 설정과 단계를 안내합니다.

kotlin publish testflight

명령은 App Store Connect 액세스 토큰을 요청합니다.
토큰을 만들려면 Apple Developer Program 멤버십이 필요합니다.
Xcode 프로젝트에 접근해 수동 서명으로 게시를 설정하는 방법도 그대로 남아 있습니다.
자세한 게시 절차는 iOS 애플리케이션 게시 문서에서 확인할 수 있습니다.

에이전트 스킬로 토큰 사용량 줄이기​

Kotlin Toolchain 스킬이 Kotlin 에이전트 스킬 컬렉션의 일부로 추가됐습니다.
CLI 마법사가 프로젝트에 AGENTS.md 같은 관련 파일을 만들어 에이전트를 구성하도록 돕습니다.
이 파일들은 프로젝트 구조와 빌드, 테스트, 일반적인 문제 해결에 대한 권장 사항을 담고 있습니다.
스킬은 다음 명령으로 추가합니다.

npx skills add kotlin/kotlin-agent-skills

JetBrains의 AI 평가에서는 이 스킬을 쓰면 Kotlin Toolchain 기반 프로젝트를 다루는 토큰 사용량이 줄어드는 것으로 나타났습니다.
에이전트에게 프로젝트 규칙을 매번 설명하지 않아도 되는 점이 실무에서 가장 크게 체감됩니다.

Android Java 8+ API desugaring 네이티브 지원​

Android의 core library desugaring이 이제 Toolchain에서 네이티브로 지원됩니다.
module.yaml에 다음 한 줄을 추가하면 켜집니다.

desugaring: enabled

desugaring 라이브러리 자체는 library 옵션으로 재정의할 수 있습니다.
Gradle 프로젝트에서 쓰던 core library desugaring 설정을 Toolchain에서도 한 줄로 옮길 수 있게 됐습니다.
자세한 설정 항목은 공식 문서의 settings reference에서 확인할 수 있습니다.

의존성 해석 속도와 IDE 개선​

캐시 없이 Kotlin Toolchain 프로젝트를 처음 가져오는 import가 벤치마크 기준 3배 이상 빨라졌습니다.
업데이트된 해석기는 저장소에 대한 불필요한 요청을 줄이고, 더 많은 의존성을 병렬로 내려받습니다.
내려받은 파일이 모두 유효한지 확인하는 절차는 그대로 유지됩니다.
모듈에 템플릿을 적용하는 과정에서 생긴 오류나 경고는 이제 IDE가 모듈의 일부로 표시합니다.
템플릿 문제는 적용 시에만 드러나는 경우도 있는데, 이때는 템플릿에 오류 아이콘이 표시되고 아이콘을 클릭하면 별도 대화 상자에서 세부 내용을 볼 수 있습니다.
Toolchain이 내려받는 외부 도구의 다운로드 위치는 모두 문서화됐고, 환경 변수로 재정의할 수 있습니다.
내부 미러나 프록시로 다운로드를 라우팅하거나, Maven Central 속도 제한을 피하거나, 다운로드를 특정 신뢰 소스에 고정할 때 유용합니다.

실무 관점​

MTS는 Android 중심 프로젝트라 TestFlight 게시가 당장 쓰이는 흐름은 아닙니다.
다만 KMP로 iOS를 함께 다루는 팀이라면, 게시 단계가 CLI 하나로 줄어드는 점이 도입을 검토할 만한 변화입니다.
에이전트 스킬은 기존 프로젝트에도 바로 붙일 수 있어, 에이전트와 함께 작업하는 팀이라면 먼저 시도해 볼 만합니다.
desugaring 한 줄 설정은 Android 모듈을 Toolchain으로 옮길 때 Gradle 설정을 그대로 가져오는 부담을 줄여줍니다.
아직 0.x 버전이라, 기존 Gradle 프로젝트의 이주는 서두르지 않고 새 프로젝트나 실험용 모듈에서 먼저 확인하는 편이 안전합니다.

마치며​

Kotlin Toolchain 0.14는 iOS 게시와 에이전트 워크플로를 한 단계 실무에 가깝게 만들었습니다.
새 KMP 프로젝트를 시작한다면 TestFlight 게시와 에이전트 스킬부터 먼저 확인해 보시길 권합니다.

Kotlin 2.5.0-RC의 KMP 분리 컴파일과 새 발행 형식 살펴보기

2026년 11월 19일 · 약 5분
Way
Android Developer

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.
11월 11일에 공개된 Kotlin 2.5.0-RC의 KMP 변경 사항에 대해 설명해드리겠습니다.

배경​

Kotlin Multiplatform 프로젝트에서는 IDE 분석과 컴파일러의 판단이 어긋나는 경우가 있습니다.
IDE에서는 빨간 줄이 그어지는 코드가 컴파일은 통과하거나, 반대로 IDE에서는 문제가 없어 보이는데 JVM 컴파일이 실패하기도 합니다.
원인은 컴파일 방식에 있습니다.
공통 코드가 컴파일될 때 의존성의 플랫폼 아티팩트를 함께 보기 때문입니다.
Kotlin 2.5.0-RC는 이 문제를 해결하는 실험적인 분리 컴파일 방식을 도입했습니다.
아울러 멀티플랫폼 라이브러리의 발행 형식을 새로 바꿔, 발행물 크기를 크게 줄였습니다.
두 변경 사항 모두 아직 실험 단계이며, 기본값은 꺼져 있습니다.

KMP 분리 컴파일 살펴보기​

기존 컴파일 방식의 문제​

KMP 모듈은 보통 commonMain 같은 공통 소스셋과 jvmMain 같은 플랫폼 소스셋으로 구성됩니다.
컴파일러는 각 플랫폼 소스셋에 대한 플랫폼 아티팩트를 만들고, 공통 소스셋에 대한 메타데이터 KLIB를 만듭니다.
메타데이터 KLIB에는 선언만 들어 있고 구현 본문은 들어 있지 않습니다.
문제는 플랫폼 소스셋을 컴파일할 때 공통 코드까지 의존성의 플랫폼 아티팩트에 대해 함께 컴파일된다는 점입니다.
그래서 commonMain 코드가 의존성 라이브러리의 플랫폼 전용 선언을 암묵적으로 참조할 수 있습니다.
IntelliJ IDEA는 메타데이터 KLIB만 본다고 가정하므로, 같은 코드를 미해결 참조로 표시합니다.
IDE에서는 빨간 줄인데 컴파일은 통과하는 어긋남이 여기서 생깁니다.
commonTest도 같은 문제를 겪습니다.
테스트 코드가 jvmMain의 플랫폼 선언을 호출하는데, IDE는 이를 미해결 참조로 표시합니다.

// lib/jvmMain
class Foo

// app/commonMain
fun main() {
    Foo() // IDE에서는 미해결 참조, 컴파일은 통과
}

오버로드와 타입 추론의 어긋남​

오버로드 선택에서도 IDE와 컴파일러가 다른 결론에 도달합니다.
라이브러리의 commonMain과 jvmMain에 같은 이름의 함수가 여러 개 선언된 경우를 예로 들 수 있습니다.

// lib/commonMain
fun foo(x: Any) = "common"

// lib/jvmMain
fun foo(x: String) = "platform"

// app/commonMain
fun main() {
    println(foo(""))
}

IDE는 foo("") 호출을 lib/commonMain의 fun foo(x: Any)로 해석합니다.
공통 코드는 공통 선언에만 의존할 수 있다고 가정하기 때문입니다.
그러나 실제 컴파일에서는 두 선언이 모두 보이고, 더 구체적인 fun foo(x: String)이 선택됩니다.
실행 결과로 "platform"이 출력됩니다.
타입 추론에서도 비슷한 문제가 생깁니다.
actual 클래스가 expect 클래스와 다른 상위 타입을 선언하면, IDE는 Event로 추론하는데 JVM 컴파일은 Any로 추론해 .name 참조에서 실패할 수 있습니다.

분리 컴파일이 바꾸는 것​

분리 컴파일은 공통 소스셋을 컴파일할 때 메타데이터 KLIB의 선언만으로 엄격하게 해석합니다.
IDE가 가정하던 방식과 컴파일러의 동작이 일치합니다.
앞의 예제 코드는 분리 컴파일을 켜면 컴파일 오류가 됩니다.
해결 방법은 명시적인 연결을 만드는 것입니다.
라이브러리의 commonMain에 expect class를 선언하고, 플랫폼 쪽을 actual class로 만듭니다.

// lib/commonMain
expect class Foo()

// lib/jvmMain
actual class Foo

// app/commonMain
fun main() {
    Foo() // 정상 동작
}

오버로드 예제에서는 호출이 lib/commonMain의 fun foo(x: Any)로 해석되어 실행 결과로 "common"이 출력됩니다.
타입 추론 예제에서는 공통 코드가 이미 Event 반환 타입으로 추론된 상태로 JVM 컴파일이 별도로 진행되므로, 컴파일이 정상적으로 끝납니다.
기존 코드 중에는 엄격해진 검사에 걸려 수정이 필요한 부분이 생길 수 있습니다.
대신 공통 소스셋에 대한 증분 컴파일이 가능해진다는 부수적인 이득도 있습니다.

분리 컴파일 켜기​

분리 컴파일은 실험 기능이며 기본값은 꺼져 있습니다.
gradle.properties 파일에 다음 속성을 추가하면 켤 수 있습니다.

kotlin.kmp.separateCompilation=true

알려진 문제도 있습니다.
분리 컴파일이 제대로 동작하려면 멀티플랫폼 라이브러리가 메타데이터 KLIB을 발행해야 합니다.
KMP Gradle 플러그인의 기본 발행 동작이므로 대부분은 해당하지 않지만, 이 조건이 이제는 필수입니다.
C 상호 운용을 쓰는 프로젝트에서는 cinterop 공통화 관련 문제에 주의해야 합니다.
공통 소스셋이 있고 선언된 타겟이 하나뿐인 모듈은 현재 분리 컴파일의 영향을 받지 않습니다.

새 발행 형식 .kar​

Kotlin 2.5.0-RC는 멀티플랫폼 라이브러리의 새 발행 형식도 도입했습니다.
JVM과 Android을 제외한 플랫폼 아티팩트를 하나의 .kar 아카이브로 발행합니다.
.kar 파일은 ZIP 아카이브를 XZ로 한 번 더 압축한 형태입니다.
이 변경의 배경은 Maven Central에 최근 도입된 발행 크기 제한입니다.
새 형식에서는 타겟을 추가해도 새 파일이 생기지 않으므로, 발행물 크기가 크게 늘지 않습니다.
경우에 따라서는 기존의 단일 타겟 발행물보다 전체 크기가 작아지기도 합니다.
공식 문서의 예시에서는 cryptography-kotlin 라이브러리의 발행물이 7,539개 파일, 91MB에서 1,036개 파일, 23MB로 줄었습니다.
모듈별로 켜려면 빌드 스크립트에 다음과 같이 설정합니다.

kotlin {
    publishing {
        publicationFormat.set(KotlinPublicationFormat.KOTLIN_ARCHIVE)
    }
}

프로젝트 전체에 적용하려면 gradle.properties 파일에 다음 속성을 추가합니다.

kotlin.publicationFormat=KOTLIN_ARCHIVE

새 형식으로 발행하는 기능은 아직 실험 단계입니다.
다만 .kar 형식의 아티팩트를 소비하는 기능은 모든 프로젝트에서 이미 사용할 수 있습니다.
이 변경 사항은 라이브러리 작성자에게만 해당하며, 최종 애플리케이션 개발자에게는 영향을 주지 않습니다.

실무 관점​

국내 MTS 프로젝트에 적용한다면, 분리 컴파일은 먼저 켜서 컴파일해 보는 것부터 시작하는 것이 좋습니다.
기존 코드가 플랫폼 선언에 암묵적으로 의존하고 있었다면, 켜는 즉시 컴파일 오류로 드러납니다.
이 오류는 숨어 있던 의존성을 명시적인 expect와 actual 선언으로 바꾸라는 신호입니다.
KMP 라이브러리를 직접 발행한다면 .kar 형식도 검토할 만합니다.
타겟이 늘어날수록 발행물 크기가 커지는 부담이 줄기 때문입니다.
다만 발행 기능이 실험 단계이므로, 발행 파이프라인은 별도로 검증한 뒤에 적용하는 것이 안전합니다.
두 기능 모두 실험 단계라는 점을 감안해, 정식 출시 전까지는 운영 빌드에 바로 적용하기보다 평가용으로 써 보는 것이 좋습니다.

마치며​

분리 컴파일은 IDE와 컴파일러의 판단을 일치시켜 KMP 개발을 예측 가능하게 만듭니다.
새 발행 형식은 라이브러리 발행물의 크기를 크게 줄여줍니다.

KMP 모듈에 Swift 패키지 의존성 추가하기

2026년 11월 17일 · 약 4분
Way
Android Developer

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.
Kotlin 2.5.0-RC에서 시도해 볼 수 있는 KMP 모듈의 SwiftPM import 기능에 대해 설명해드리겠습니다.

배경​

KMP 프로젝트에서 iOS 쪽 네이티브 SDK를 쓰려면 지금까지 CocoaPods 의존성을 연결하거나 cinterop 정의를 직접 작성해야 했습니다.
CocoaPods 방식은 별도 설정이 많고, Swift 패키지를 그대로 가져오는 방법이 마땅하지 않았습니다.
Kotlin 2.5.0-RC부터는 SwiftPM import 기능을 이용해 Swift 패키지를 Gradle 빌드 스크립트에서 직접 선언할 수 있습니다.
SwiftPM 의존성의 Objective-C API를 Kotlin 코드에서 바로 호출할 수 있게 됩니다.

SwiftPM import 살펴보기​

플러그인 버전 설정하기​

SwiftPM import를 쓰려면 Kotlin Multiplatform Gradle 플러그인 2.5.0-RC가 필요합니다.
Version Catalog에서는 다음과 같이 버전을 지정합니다.

[versions]
kotlin = "2.5.0-RC"

[plugins]
kotlin-multiplatform = { id = "org.jetbrains.kotlin.multiplatform", version.ref = "kotlin" }

Swift 패키지 선언하기​

SwiftPM 의존성은 Apple 타겟을 선언한 build.gradle.kts 안의 swiftPMDependencies 블록에 추가합니다.
예시로 FirebaseAnalytics를 가져오는 설정은 다음과 같습니다.

kotlin {
    iosArm64()
    iosSimulatorArm64()
    swiftPMDependencies {
        // FirebaseAnalytics를 Kotlin 코드로 가져옵니다
        swiftPackage(
            url = url("https://github.com/firebase/firebase-ios-sdk.git"),
            version = from("12.5.0"),
            products = listOf(product("FirebaseAnalytics")),
        )
    }
}

버전은 from으로 시작 버전을 지정하거나, exact로 정확한 버전을 지정할 수 있습니다.
브랜치나 특정 리비전을 지정하는 방식도 함께 제공됩니다.

Clang 모듈 가져오기​

SwiftPM import는 Clang 모듈을 가져오는 방식으로 동작합니다.
기본값으로는 지정한 Swift 패키지 안의 Clang 모듈을 자동으로 찾아 Kotlin 코드에서 쓸 수 있게 합니다.
자동 탐색을 끄려면 discoverClangModulesImplicitly를 false로 바꾸고, 제품 이름을 Clang 모듈 이름으로 씁니다.
모듈 이름이 제품 이름과 다르면 importedClangModules로 직접 지정합니다.
예를 들어 FirebaseFirestore의 Objective-C API는 FirebaseFirestoreInternal 모듈에 들어 있습니다.

kotlin {
    swiftPMDependencies {
        discoverClangModulesImplicitly = false
        swiftPackage(
            url = url("https://github.com/firebase/firebase-ios-sdk.git"),
            version = from("12.5.0"),
            products = listOf(
                product("FirebaseAnalytics"),
                product("FirebaseFirestore"),
            ),
            importedClangModules = listOf(
                "FirebaseAnalytics",
                "FirebaseFirestoreInternal",
            ),
        )
    }
}

플랫폼 제한 두기​

일부 SwiftPM 의존성은 모든 타겟에서 빌드되지 않습니다.
예를 들어 Google Maps SDK는 현재 iOS 타겟만 지원합니다.
iOS만 타겟으로 한다면 따로 지정할 필요가 없지만, macOS 같은 타겟을 추가하면 제품마다 플랫폼을 지정해야 합니다.

kotlin {
    iosArm64()
    iosSimulatorArm64()
    macosArm64()
    swiftPMDependencies {
        swiftPackage(
            url = url("https://github.com/googlemaps/ios-maps-sdk.git"),
            version = exact("10.3.0"),
            products = listOf(
                product(
                    "GoogleMaps",
                    platforms = setOf(iOS()),
                ),
            ),
        )
    }
}

Xcode 프로젝트와 연결하기​

SwiftPM 의존성을 처음 추가하면 Xcode 프로젝트와 생성된 패키지를 연결해야 합니다.
다음 Gradle 태스크를 실행하면 SwiftPM 패키지가 생성되고 Xcode 프로젝트가 함께 변경됩니다.

XCODEPROJ_PATH='/path/to/project/iosApp/iosApp.xcodeproj' ./gradlew :kotlin-library:integrateLinkagePackage

생성된 패키지와 변경된 Xcode 프로젝트는 저장소에 함께 커밋합니다.
그 뒤로는 의존성 목록이나 버전이 바뀔 때마다 합성 패키지가 자동으로 갱신됩니다.

Kotlin 코드에서 호출하기​

가져온 Objective-C API는 swiftPMImport로 시작하는 네임스페이스에 들어 있습니다.
네임스페이스는 Gradle 그룹 이름과 프로젝트 이름을 이어서 만듭니다.
iosMain 소스 세트에서 Firebase API를 쓰는 예시는 다음과 같습니다.

import swiftPMImport.groupName.subproject.FIRAnalytics
import swiftPMImport.groupName.subproject.FIRApp

fun logAppOpen() {
    FIRApp.configure()
    FIRAnalytics.logEventWithName("app_open", parameters = null)
}

버전 잠금 파일 관리하기​

SwiftPM import 도구는 의존성 버전을 고정하기 위해 Package.resolved 파일을 만듭니다.
기본값으로는 모든 서브프로젝트의 잠금 파일이 .swiftpm-locks/default/swiftImport 안의 하나의 파일로 합쳐집니다.
잠금 파일은 저장소에 커밋해 모든 빌드가 같은 버전을 쓰게 합니다.
서브프로젝트별로 잠금 파일을 나누려면 packageResolvedSynchronization에 그룹 식별자를 지정합니다.
잠금 파일을 강제로 갱신하려면 빌드 디렉터리와 기존 Package.resolved 파일을 지운 뒤 다음 태스크를 실행합니다.

./gradlew :yourModuleName:fetchSyntheticImportProjectPackages

알고 있어야 할 제한 사항​

동적 Kotlin/Native 프레임워크를 만들 때는 SwiftPM import가 모든 경우를 지원하지 않습니다.
빌드 오류나 런타임 경고가 나오면 프레임워크 연결 방식을 정적으로 바꾸는 것이 일반적인 해결 방법입니다.

kotlin {
    listOf(
        iosArm64(),
        iosSimulatorArm64()
    ).forEach { iosTarget ->
        iosTarget.binaries.framework {
            baseName = "Shared"
            isStatic = true
        }
    }
}

실무 관점​

MTS 앱에 적용한다면, iOS 쪽에서만 쓰는 SDK부터 SwiftPM import로 옮겨 보는 것이 안전합니다.
CocoaPods 의존성을 함께 쓰고 있다면, 두 방식이 같은 SDK를 중복으로 가져오지 않는지 먼저 확인해야 합니다.
Package.resolved 잠금 파일과 생성된 패키지는 저장소에 커밋해 팀 빌드와 CI 빌드가 같은 버전을 쓰게 합니다.
Kotlin 2.5.0-RC는 정식 출시 전 단계이므로, 프로덕션 적용보다 별도 브랜치에서의 검증이 먼저입니다.

마치며​

SwiftPM import를 쓰면 Swift 패키지를 Gradle 빌드 스크립트에서 직접 선언해 KMP 모듈에서 쓸 수 있습니다.
CocoaPods 설정과 cinterop 정의를 줄이고, 버전 잠금까지 Gradle 안에서 관리할 수 있게 됩니다.

Kotlin Toolchain 0.13 — 새 KMP 프로젝트는 kotlin new로 시작하기

2026년 10월 8일 · 약 3분
Way
Android Developer

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.
JetBrains가 공개한 Kotlin Toolchain 0.13에 대해 설명해드리겠습니다.

배경​

신규 Kotlin Multiplatform(KMP) 프로젝트를 시작할 때는 Gradle 설정 파일을 손으로 짜는 것부터 시작하는 경우가 많았습니다.
JDK나 Android SDK 같은 필수 도구가 갖춰져 있지 않으면, 새 노트북에서 프로젝트를 처음 열었을 때 동기화부터 실패하곤 했습니다.
이번 0.13부터 JetBrains는 신규 KMP 프로젝트에 이 툴체인을 쓰는 것을 공식 권장 경로로 제시했습니다.
자세한 내용은 Kotlin 블로그 원문에서 확인할 수 있습니다.

Kotlin Toolchain 살펴보기​

Kotlin Toolchain은 JVM·Android·iOS·멀티플랫폼·서버 앱을 하나의 CLI 진입점으로 만들고, 빌드하고, 테스트하고, 배포하는 도구입니다.
필수 도구들을 선언적 설정에 맞춰 자동으로 내려받아 주기 때문에 온보딩 과정의 마찰이 크게 줄어듭니다.

kotlin new: 대화형 프로젝트 생성​

0.13의 핵심은 kotlin new 명령입니다.
웹의 KMP Wizard처럼 앱 유형을 고르고 타깃 플랫폼을 선택하면 프로젝트가 생성됩니다.
기존 kotlin init도 같은 흐름으로 맞췄는데, 차이는 kotlin init이 현재 디렉터리에 바로 파일을 만든다는 점입니다.

# 새 프로젝트 생성 (대화형)
kotlin new

# 이미 설치돼 있다면 업데이트
kotlin update

Android 개발자 관점에서 달라진 부분​

  • Android SDK 자동 프로비저닝이 IDE까지 확장: 이전에는 kotlin build/kotlin run 때만 SDK가 자동 설치돼서, 빌드 전에 IDE로 먼저 열면 SDK 누락 오류가 났습니다. 이제 프로젝트 import 시점에도 누락된 SDK 컴포넌트를 자동으로 받아 줍니다.
  • namespace/applicationId 검증 강화: com.example.app 같은 샘플 ID로 실수로 배포 빌드를 만드는 실수를 막아 줍니다.
  • 다운로드 진행 표시: JDK, Android SDK, iOS 런타임, 컴파일러 다운로드가 CLI에 진행 바로 표시됩니다.

Swift Package Manager 의존성 지원​

Apple 타깃에서 SPM 패키지를 선언적으로 가져올 수 있게 됐습니다.
설정 파일에 저장소와 버전을 적으면 됩니다.

dependencies:
  - swiftPackage:
      repository: "https://github.com/firebase/firebase-ios-sdk.git"
      version: "12.17.0"
      products: ["FirebaseCore", "FirebaseFirestore", "FirebaseAnalytics"]

가져온 Objective-C API는 swiftPMImport 접두사로 네임스페이스가 붙어, Kotlin 코드에서 명시적으로 구분됩니다.
로컬 SPM 패키지는 localSwiftPackage 키로 연결할 수 있습니다.

빌드 속도: Kotlin/Native 컴파일러 캐시​

Kotlin/Native 재빌드가 빨라집니다.
컴파일된 네이티브 의존성을 빌드 간, 심지어 프로젝트 간에 캐시로 재사용하고, 프로젝트 코드는 파일 단위 캐시로 링크 시 바뀐 부분만 다시 컴파일합니다.
기존 settings.kotlin.compileIncrementally 설정을 그대로 쓰고, .klib 컴파일 자체는 전체로 수행됩니다.

그 외 변경 사항​

  • IDE 동기화 상태를 에디터에서 확인할 수 있게 됐습니다.
  • 멀티플랫폼 라이브러리 배포 시 Compose Resources와 SwiftPM 의존성 메타데이터가 아티팩트와 함께 게시되고, 서드파티 멀티플랫폼 라이브러리의 Compose Resources도 해석됩니다.
  • AI 에이전트 연동도 강화됐습니다. Compose Hot Reload MCP 서버와 Kotlin용 에이전트 스킬(npx skills add kotlin/kotlin-agent-skills)이 제공됩니다.

JetBrains가 공개한 Kotlin Toolchain 0.13에 대해 설명해드리겠습니다.

배경​

신규 Kotlin Multiplatform(KMP) 프로젝트를 시작할 때는 Gradle 설정 파일을 손으로 짜는 것부터 시작하는 경우가 많았습니다.
JDK나 Android SDK 같은 필수 도구가 갖춰져 있지 않으면, 새 노트북에서 프로젝트를 처음 열었을 때 동기화부터 실패하곤 했습니다.
이번 0.13부터 JetBrains는 신규 KMP 프로젝트에 이 툴체인을 쓰는 것을 공식 권장 경로로 제시했습니다.
자세한 내용은 Kotlin 블로그 원문에서 확인할 수 있습니다.

Kotlin Toolchain 살펴보기​

Kotlin Toolchain은 JVM·Android·iOS·멀티플랫폼·서버 앱을 하나의 CLI 진입점으로 만들고, 빌드하고, 테스트하고, 배포하는 도구입니다.
필수 도구들을 선언적 설정에 맞춰 자동으로 내려받아 주기 때문에 온보딩 과정의 마찰이 크게 줄어듭니다.

kotlin new: 대화형 프로젝트 생성​

0.13의 핵심은 kotlin new 명령입니다.
웹의 KMP Wizard처럼 앱 유형을 고르고 타깃 플랫폼을 선택하면 프로젝트가 생성됩니다.
기존 kotlin init도 같은 흐름으로 맞췄는데, 차이는 kotlin init이 현재 디렉터리에 바로 파일을 만든다는 점입니다.

# 새 프로젝트 생성 (대화형)
kotlin new

# 이미 설치돼 있다면 업데이트
kotlin update

Android 개발자 관점에서 달라진 부분​

  • Android SDK 자동 프로비저닝이 IDE까지 확장: 이전에는 kotlin build/kotlin run 때만 SDK가 자동 설치돼서, 빌드 전에 IDE로 먼저 열면 SDK 누락 오류가 났습니다. 이제 프로젝트 import 시점에도 누락된 SDK 컴포넌트를 자동으로 받아 줍니다.
  • namespace/applicationId 검증 강화: com.example.app 같은 샘플 ID로 실수로 배포 빌드를 만드는 실수를 막아 줍니다.
  • 다운로드 진행 표시: JDK, Android SDK, iOS 런타임, 컴파일러 다운로드가 CLI에 진행 바로 표시됩니다.

Swift Package Manager 의존성 지원​

Apple 타깃에서 SPM 패키지를 선언적으로 가져올 수 있게 됐습니다.
설정 파일에 저장소와 버전을 적으면 됩니다.

dependencies:
  - swiftPackage:
      repository: "https://github.com/firebase/firebase-ios-sdk.git"
      version: "12.17.0"
      products: ["FirebaseCore", "FirebaseFirestore", "FirebaseAnalytics"]

가져온 Objective-C API는 swiftPMImport 접두사로 네임스페이스가 붙어, Kotlin 코드에서 명시적으로 구분됩니다.
로컬 SPM 패키지는 localSwiftPackage 키로 연결할 수 있습니다.

빌드 속도: Kotlin/Native 컴파일러 캐시​

Kotlin/Native 재빌드가 빨라집니다.
컴파일된 네이티브 의존성을 빌드 간, 심지어 프로젝트 간에 캐시로 재사용하고, 프로젝트 코드는 파일 단위 캐시로 링크 시 바뀐 부분만 다시 컴파일합니다.
기존 settings.kotlin.compileIncrementally 설정을 그대로 쓰고, .klib 컴파일 자체는 전체로 수행됩니다.

그 외 변경 사항​

  • IDE 동기화 상태를 에디터에서 확인할 수 있게 됐습니다.
  • 멀티플랫폼 라이브러리 배포 시 Compose Resources와 SwiftPM 의존성 메타데이터가 아티팩트와 함께 게시되고, 서드파티 멀티플랫폼 라이브러리의 Compose Resources도 해석됩니다.
  • AI 에이전트 연동도 강화됐습니다. Compose Hot Reload MCP 서버와 Kotlin용 에이전트 스킬(npx skills add kotlin/kotlin-agent-skills)이 제공됩니다.
  • IDE 기능은 IntelliJ IDEA 2026.2.3 또는 Android Studio Rabbit 1(2026.2.1) 이상에서 최신 Kotlin Toolchain 플러그인과 함께 쓸 수 있습니다.

실무에서 주의할 점​

기존 Gradle 기반 프로젝트를 당장 마이그레이션해야 하는 것은 아닙니다.
JetBrains도 로드맵에서 Gradle 프로젝트의 공백을 먼저 메우는 데 집중하겠다고 밝혔습니다.
따라서 운영 중인 프로젝트는 기존 흐름을 유지하고, 신규 프로젝트나 사이드 프로젝트부터 적용해 보는 것이 안전합니다.

JetBrains도 로드맵에서 Gradle 프로젝트의 공백을 먼저 메우는 데 집중하겠다고 밝혔습니다.
따라서 운영 중인 프로젝트는 기존 흐름을 유지하고, 신규 프로젝트나 사이드 프로젝트부터 적용해 보는 것이 안전합니다.

Kotlin 2.4.21 버그픽스 릴리스 — 2.4.x 라인 유지팀은 안전하게 올릴 시점

2026년 10월 11일 · 약 3분
Way
Android Developer

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.
최근 공개된 Kotlin 2.4.21에 대해 설명해드리겠습니다.

배경​

2026년 10월 8일, JetBrains가 Kotlin 2.4.21을 릴리스했습니다.
기능 추가 없는 버그픽스 릴리스라서 2.4.x 라인을 쓰고 있는 팀이라면 특별한 고민 없이 올릴 수 있는 버전입니다.

Kotlin 2.4.21 살펴보기​

K/Wasm: 조용한 트랩 대신 예외가 던져진다​

K/Wasm에서 잘못된 타입의 인자로 람다를 호출하면 트랩이 나던 문제가 고쳐졌습니다.
(T) -> R 형태의 람다에 T가 아닌 인자를 넣었을 때, 이전에는 Wasm 트랩이 발생해 무엇을 잘못한 것인지 알기 어려웠습니다.
이번 수정으로 ClassCastException이 정상적으로 던져집니다.
K/Wasm 타깃을 만지는 KMP 프로젝트라면, 기존에 트랩으로 죽던 경로가 이제 catch 가능한 예외로 바뀌는 것이니 예외 처리 로직을 한 번 확인해 볼 만합니다.

Kotlin/JS: 프로덕션 빌드에서 멤버 이름 유지​

Kotlin/JS 프로덕션 빌드에서 멤버 이름이 minify되지 않도록 되돌려졌습니다.
디버깅이나 런타임 이름 기반 처리에 영향을 받을 수 있는 프로젝트는 안심하고 올릴 수 있는 방향입니다.

리플렉션에서 K1 의존성 제거​

JVM 리플렉션의 KCallable 표현 방식이 K1 컴파일러 의존성을 제거하는 방향으로 바뀌었습니다.
겉으로는 드러나지 않지만, K2 컴파일러로 완전히 넘어가는 과정에서 남은 구형 의존성을 하나씩 걷어내는 작업입니다.
리플렉션을 쓰는 라이브러리의 내부 구현을 보는 편이라면 왜 이런 식으로 바뀌었는지의 맥락 정도로 이해하면 됩니다.

스크립트 관련 수정들​

Kotlin Script와 JSR-223 관련 수정이 여러 건 포함됐습니다.
Kotlin Script에서 전달 의존성이 있는 스크립트를 두 번째 실행하면 NoClassDefFoundError가 나던 문제, JSR-223에서 제네릭 Java 바인딩이 이후의 모든 eval() 호출을 깨뜨리던 문제가 수정됐습니다.
스크립트 엔진을 내장한 앱이라면 의미 있는 수정입니다.

그 밖의 수정​

  • @Serializable 제네릭 클래스에 클래스 상한(class upper bound)이 있을 때 잘못된 Wasm이 나오던 문제
  • K/N Gradle에서 SwiftPM import 시 로그가 넘쳐나던 문제

실무에서 주의할 점​

  • 2.4.x 라인 유지 중이라면 이번엔 올리면 됩니다. 새 기능이 아니라 버그픽스 묶음이라 동작 변경 리스크가 낮습니다.
  • K/Wasm을 쓰는 KMP 프로젝트는 예외 경로를 점검하세요. 트랩이 예외로 바뀌는 건 에러 처리 전략에 직접 영향을 줍니다.
  • Kotlin/JS는 minify 복원이라 큰 주의점은 없습니다. 오히려 이전 버전에서 이상 징후가 있었다면 해소 방향입니다.
  • 스크립트 엔진 내장 앱(서버 측 혹은 내부 도구)은 이번 릴리스가 제법 알찹니다. 스크립트 실행 관련 수정이 4건이나 들어 있습니다.

적용 방법은 다음과 같습니다.
버전 카탈로그 기준으로 버전만 바꾸는 게 전부입니다.
다만 올리고 나면 컴파일러가 바뀌는 만큼, 전체 빌드 한 번과 주요 화면 스모크 테스트 정도는 돌립니다.

// gradle/libs.versions.toml
[versions]
kotlin = "2.4.21" // 2.4.20 -> 2.4.21 (버그픽스, 동작 변경 없음 예상)

KMP 프로젝트에서 Wasm 타깃을 쓰는 경우, 릴리스 노트의 해당 항목이 내 코드 경로에 닿는지 빠르게 확인하는 스크립트를 CI에 걸어 두면 이후 릴리스에서도 부담이 없습니다.

마치며​

메이저 릴리스가 아니라서 화려하진 않지만, 이런 버그픽스 릴리스야말로 그냥 올리면 좋은 릴리스입니다.
2.4.x 라인에서 운영 중인 프로젝트가 있다면, 이번 주에 버전만 올리고 스모크 테스트 한 번 돌려 보길 권합니다.

KMP 플러그인의 Swift IDE 지원 종료 — 2026.3부터 Swift 작업은 Xcode로 나눠야 한다

2026년 10월 10일 · 약 4분
Way
Android Developer

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.
Kotlin Multiplatform(KMP) 플러그인의 Swift 언어 IDE 지원 종료 소식에 대해 설명해드리겠습니다.

배경​

2026년 10월 5일, JetBrains가 KMP 플러그인에서 제공하던 Swift 언어 IDE 기능을 앞으로 중단한다고 알렸습니다.
적용 시점은 IntelliJ IDEA 2026.3과 Android Studio Rabbit 2 | 2026.2.2부터입니다.
쉽게 말하면, 도구가 하나로 합쳐지던 방향에서 다시 각자 잘하는 쪽으로 역할을 나누는 선택입니다.
자세한 내용은 Kotlin 블로그 원문에서 확인할 수 있습니다.

무엇이 달라졌는지​

종료되는 기능​

없어지는 것은 Swift 파일을 같은 IDE 안에서 편집하고, 문법 강조를 받고, Swift와 Kotlin 사이를 오가며 이동하던 기능입니다.
그동안 KMP 플러그인 안에서는 Kotlin 코드와 Swift 코드를 한 창에서 보는 경험이 가능했지만, 이제 그 경계가 다시 IDE 밖으로 나갑니다.
SwiftUI 화면이나 iOS 전용 코드는 Xcode에서, 공유 로직과 Compose Multiplatform 코드는 IntelliJ나 Android Studio에서 보는 흐름이 기본이 됩니다.

계속 지원되는 기능​

iOS 앱을 실행하는 일과 iOS에서 Kotlin 코드를 디버깅하는 일은 계속 지원됩니다.
Kotlin/Native 쪽 기능도 그대로입니다.
Swift로 내보내는 Swift Export나, Swift 패키지를 Kotlin 프로젝트로 가져오는 흐름은 이번 결정과 별개입니다.
예전 버전의 IDE와 플러그인에서는 기존 Swift 기능을 계속 쓸 수 있지만, 거기에 새 업데이트가 붙지는 않습니다.

종료 배경​

원래 이 Swift 지원은 과거 AppCode 시절의 기술을 바탕으로 만들어졌고, 이후 여러 제품을 거치며 KMP 플러그인까지 이어졌습니다.
그런데 실제 사용은 꾸준히 줄었고, KMP를 쓰는 iOS 개발자 상당수는 Swift 작업만큼은 Xcode를 선호했다고 합니다.
반대로 플러그인 안에서 일하는 팀은 Kotlin과 Compose Multiplatform 비중이 점점 커졌습니다.
Swift와 Xcode, IntelliJ 플랫폼이 계속 바뀌는 상황에서 이 연결을 유지하는 비용이 실제 쓰임에 비해 컸다는 판단입니다.
대체 기능을 새로 만들 계획은 현재로서는 없다고도 했습니다.
앞으로는 Kotlin 도구 자체와 iOS 개발자를 위한 KMP 경험을 다듬는 데 힘을 쏟겠다는 방향입니다.

실무에서 주의할 점​

Android만 만드는 팀이라면 체감 변화는 거의 없습니다.
영향은 KMP로 iOS까지 같이 보는 팀에서 생깁니다.

  • Swift 파일을 Android Studio에서 고치던 습관이 있다면 작업 동선을 나눠야 합니다. 특히 iosApp 쪽 SwiftUI 진입점, 권한이나 딥링크처럼 iOS에 붙은 얇은 층을 누가 어느 IDE에서 고칠지 팀 안에서 정해두는 것이 좋습니다.
  • 구버전에 머무는 선택은 임시 방편입니다. Swift 이동 기능이 꼭 필요해서 IntelliJ IDEA 2026.3 이전에 머무를 수는 있지만, 그 사이 Kotlin 플러그인과 Android Studio의 다른 개선을 못 받게 됩니다. 보안과 빌드 도구 호환까지 같이 보면 오래 버티는 전략은 아닙니다.
  • 공유 경계를 더 얇게 가져갈 이유가 생겼습니다. Swift 쪽에 로직이 많이 남아 있으면 IDE를 오갈 때마다 맥락이 끊깁니다. 반대로 Swift를 화면 진입과 플랫폼 연결 정도로 얇게 두고, 상태와 규칙을 Kotlin에 두면 이번 변화의 마찰이 작아집니다.

이 소식을 KMP 자체가 약해졌다는 신호로 보기는 어렵습니다.
오히려 JetBrains가 잘 쓰이지 않는 통합을 걷어내고, 실제로 많이 쓰이는 Kotlin 쪽 경험에 집중하겠다는 쪽에 가깝습니다.
새로 KMP를 시작한다면 처음부터 Swift 층을 얇게 잡는 구성이 안전해 보입니다.
예를 들면 iOS 진입점은 Compose 화면을 감싸는 역할만 하고, 나머지는 공유 모듈이 맡는 식입니다.

// iosApp: Swift는 진입점만 담당하고, 화면과 상태는 공유 모듈에 둔다
import SwiftUI
import Shared

struct ContentView: View {
    var body: some View {
        ComposeView()
            .ignoresSafeArea()
    }
}

struct ComposeView: UIViewControllerRepresentable {
    func makeUIViewController(context: Context) -> UIViewController {
        MainViewControllerKt.MainViewController()
    }
    func updateUIViewController(_ uiViewController: UIViewController, context: Context) {}
}
// shared: iOS와 Android가 같이 쓰는 화면 진입점
fun MainViewController() = ComposeUIViewController {
    App()
}

이렇게 두면 Swift를 수정할 일이 생겨도 Xcode에서 보는 범위가 작고, 대부분의 변경은 Kotlin 쪽에서 끝납니다.
이미 Swift에 로직이 많이 들어가 있는 프로젝트라면, 한 번에 옮기기보다 새로 만드는 화면부터 이 경계를 적용해 보는 것도 방법입니다.

마치며​

KMP를 쓰는 팀이라면 IDE를 올리기 전에 한 번만 점검해 보시기 바랍니다.
Swift 파일을 지금 어느 도구에서 고치고 있는지, 그 흐름이 새 버전에서도 이어지는지 확인하는 것만으로 업그레이드 뒤의 혼란을 줄일 수 있습니다.

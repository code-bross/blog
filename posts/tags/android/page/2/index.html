Android Studio Rabbit 2 Patch 2 살펴보기 — AGP 9.5.2와 함께 온 두 가지 수정

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.
2026년 11월 20일에 공개된 Android Studio Rabbit 2 Patch 2에 대해 설명해드리겠습니다.

배경​

Android Studio Rabbit 2는 현재 안정 채널 버전입니다.
2026년 11월 20일에 Patch 2가 공개되었고, AGP 9.5.2와 함께 배포되었습니다.
이번 패치는 기능 추가가 아니라 두 가지 빌드 문제를 수정하는 릴리스입니다.
수정된 이슈 목록에서 확인할 수 있습니다.
이미 안정 채널을 쓰고 있다면 도움말 메뉴의 업데이트 확인으로 받을 수 있습니다.

이번 패치에서 수정된 내용​

Fat AAR의 Java 리소스 병합 실패 수정​

AGP 9.5부터 여러 개의 중첩된 JAR를 포함한 Fat AAR에서 Java 리소스 병합이 실패하는 문제가 있었습니다.
이번 패치에서 해당 문제가 수정되었습니다 (Issue #581925548).
Fat AAR는 여러 라이브러리를 하나의 AAR로 묶는 방식입니다.
서드파티 라이브러리를 묶어 배포하는 경우에 사용합니다.
리소스 병합이 실패하면 빌드 자체가 멈추므로, 해당 방식을 쓰는 프로젝트는 업데이트가 필요합니다.

Isolated Projects에서 implementation(project) 실패 수정​

Isolated Projects 환경에서 implementation(project(...))를 사용하는 앱이 실패하는 문제도 수정되었습니다 (Issue #582417470).
Isolated Projects는 Gradle이 각 프로젝트를 격리해서 구성하는 기능입니다.
멀티 모듈 프로젝트의 구성 속도와 캐시 활용에 영향을 줍니다.
이 기능을 켜서 쓰는 프로젝트는 이번 패치로 해당 문제를 피할 수 있습니다.

실무 관점​

국내 MTS는 멀티 모듈 구조로 전환을 진행한 프로젝트입니다.
Fat AAR 방식의 서드파티 라이브러리를 쓰고 있다면 AGP 9.5 계열에서 빌드 실패를 겪을 수 있습니다.
이번 패치는 해당 문제를 직접 수정하므로, AGP 9.5를 쓰고 있다면 업데이트를 검토합니다.
Isolated Projects는 아직 켜지 않은 기능이지만, 멀티 모듈 프로젝트의 빌드 속도 개선과 관련이 있습니다.
향후 적용을 검토한다면 수정된 버전에서 테스트하는 것이 안전합니다.

마치며​

이번 패치는 기능 추가가 없는 수정 릴리스입니다.
두 가지 빌드 문제를 해결하므로, 해당 환경이라면 업데이트할 가치가 있습니다.

R8 Consumer Keep Rules 살펴보기 — DEX 코드 최적화와 라이브러리 규칙 정리

2026년 11월 22일 · 약 6분
Way
Android Developer

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.
2026년 11월 17일에 공개된 Ship smarter keep rules에 대해 설명해드리겠습니다.

배경​

R8은 Android 앱 최적화 도구입니다.
사용하지 않는 코드를 제거하고, 남은 코드를 최적화하고 난독화합니다.
Google Play는 2027년 2월부터 DEX 코드 최적화 기준을 적용합니다.
DEX 코드가 10MB를 초과하는 앱은 난독화와 최적화, 축소 지표가 각각 25% 이상이어야 합니다.
기준에 미치지 못하면 앱 노출과 게시 기능에 영향을 받을 수 있습니다.
이 기준은 앱만의 문제가 아닙니다.
R8은 주어진 규칙 안에서만 최적화할 수 있습니다.
규칙에는 앱이 의존하는 라이브러리에 포함된 규칙도 들어갑니다.
국내 MTS처럼 규모가 큰 앱은 서드파티 SDK를 많이 사용합니다.
라이브러리가 넓은 규칙을 함께 보내면 앱 전체의 최적화 여지가 줄어듭니다.

R8 Consumer Keep Rules 살펴보기​

Consumer Keep Rules란​

Consumer Keep Rules는 라이브러리 안에 포함된 규칙입니다.
앱 수준 컴파일 과정에서 R8이 최적화하지 말아야 할 부분을 지정합니다.
리플렉션 대상과 네이티브 인터페이스가 제거되지 않도록 보호하는 역할을 합니다.
앱 개발자가 직접 규칙을 찾지 않아도 라이브러리를 그대로 쓸 수 있습니다.
의도적으로 좁게 작성된 규칙은 라이브러리와 앱 모두에 도움이 됩니다.
반대로 넓은 규칙은 사용하지 않는 코드까지 남겨 앱 성능에 영향을 줍니다.
Play Console에 추가된 DEX 코드 최적화 지표는 앱과 라이브러리 규칙의 합산 영향을 보여줍니다.

넓은 규칙이 문제가 되는 이유​

라이브러리 제공자는 SDK가 리플렉션으로 인한 충돌을 일으키지 않기를 바랍니다.
그래서 패키지 전체를 보존하는 넓은 규칙을 넣는 경우가 많습니다.
그러나 넓은 규칙은 R8의 전체 프로그램 최적화를 크게 제한합니다.
시작 시간과 다운로드 크기, 메모리 사용량, ANR 발생률에 영향을 줍니다.
성능을 중시하는 앱은 라이브러리 규칙을 직접 대체하는 규칙을 작성하기도 합니다.
이 경우 라이브러리 업데이트를 받아들이기 어려워지는 부작용도 생깁니다.

진입점만 보호하는 좁은 규칙​

리플렉션을 피할 수 없다면, 규칙은 실제로 리플렉션으로 접근하는 진입점만 지정하면 됩니다.
R8은 진입점을 기준으로 참조 그래프를 만들고, 참조되지 않는 클래스와 메서드, 필드를 제거합니다.
라이브러리를 이미 최적화하거나 난독화한 경우에도 같은 원칙이 적용됩니다.
앱 컴파일 단계에서 R8이 실제 사용되는 부분을 기준으로 다시 최적화하기 때문입니다.
서드파티 의존성에 대한 규칙도 좁게 작성해야 합니다.
대표적인 넓은 규칙 예시는 다음과 같습니다.

-keep public class com.google.android.gms.** { *; }

이 규칙은 앱이 다른 GMS 라이브러리에 대해 좁은 규칙을 갖고 있어도 이를 덮어씁니다.
많은 라이브러리가 이미 자체 Consumer Keep Rules를 제공하므로, 패키지 단위 규칙은 그 규칙까지 무력화할 수 있습니다.

리플렉션 대신 코드 생성 사용하기​

리플렉션은 컴파일 시점에 R8이 코드 사용 여부를 알 수 없게 만듭니다.
그래서 충돌을 막으려면 Keep Rules가 필요합니다.
가능하면 코드 생성을 사용하는 것이 좋습니다.
직렬화와 역직렬화, 의존성 주입이 대표적인 적용 대상입니다.
Hilt는 코드 생성을 사용하는 라이브러리입니다.
다만 모든 경우에 코드 생성이 맞는 것은 아닙니다.
선택적 의존성처럼 리플렉션이 필요한 패턴도 있습니다.
이 경우에는 필요한 진입점만 보호하는 좁은 규칙과 함께 사용합니다.

Jetpack Keep 어노테이션으로 규칙 생성하기​

Jetpack Keep 어노테이션은 현재 알파 단계입니다.
리플렉션 사용 위치에 어노테이션을 붙이면 빌드 시점에 Keep Rules를 생성합니다.
생성되는 규칙은 조건부 규칙입니다.
리플렉션을 호출하는 코드가 R8에 의해 남아야만 대상도 함께 남습니다.
사용하지 않는 기능의 규칙이 앱을 비대하게 만들지 않습니다.
AGP 8.7 이상에서 사용할 수 있고, 라이브러리와 플러그인 버전은 1.0.0-alpha01입니다.
설정은 libs.versions.toml에 다음과 같이 추가합니다.

[versions]
annotationKeep = "1.0.0-alpha01"

[libraries]
androidx-annotation-keep = { group = "androidx.annotation.keep", name = "keep", version.ref = "annotationKeep" }

[plugins]
androidx-annotation-keep = { id = "androidx.annotation.keep", version.ref = "annotationKeep" }

리플렉션으로 생성자를 호출하는 경우에는 @UsesReflectionToConstruct 어노테이션을 사용합니다.
다음 예시는 이름으로만 아는 클래스를 생성하는 함수입니다.

@UsesReflectionToConstruct(
    className = "com.example.ResourceLocatorImpl",
    parameterTypes = [],
)
fun loadResourceLocator(): ResourceLocator {
    val implClass = Class.forName("com.example.ResourceLocatorImpl")
    return implClass.getDeclaredConstructor().newInstance() as ResourceLocator
}

Lint가 어노테이션이 없는 리플렉션 호출을 찾아주고, 상당수는 자동으로 추가할 수도 있습니다.

조건부 Keep Rules로 선택적 기능 보호하기​

광고 미디에이션 어댑터처럼 선택적으로 포함되는 모듈에는 조건부 Keep Rules를 사용합니다.
앱에 해당 어댑터가 포함된 경우에만 기능을 보존합니다.
포함되지 않은 형식과 기능은 축소 대상이 됩니다.
Jetpack Keep 어노테이션을 쓰면 이런 조건부 규칙도 자동으로 생성할 수 있습니다.

규칙은 문서가 아니라 라이브러리에 포함하기​

Consumer Keep Rules는 라이브러리와 함께 배포해야 합니다.
문서에 규칙을 적어두면 앱 개발자가 직접 추가해야 하고 유지보수 부담이 생깁니다.
라이브러리를 업데이트하면서 클래스 이름이나 리플렉션 사용 방식이 바뀌면 문서도 함께 바꿔야 합니다.
버전을 거듭하면 앱에 더 이상 필요 없는 규칙이 쌓여 코드가 비대해집니다.

R8 Configuration Analyzer로 규칙 점검하기​

샘플 앱에서 R8을 활성화하고 핵심 사용자 여정을 테스트합니다.
R8 Configuration Analyzer는 축소와 최적화, 난독화 점수를 보여줍니다.
앱뿐 아니라 라이브러리에서 온 비효율적인 규칙도 함께 확인할 수 있습니다.
AGP 9.3 이상에서는 다음 태스크로 보고서를 만들 수 있습니다.

./gradlew :app:analyzeReleaseR8Config

보고서는 app/build/reports/r8/r8-config-analyzer-release.html 경로에 생성됩니다.
Android CLI의 analyze 명령은 AAR이나 JAR의 최적화 상태를 평가합니다.
보존된 메서드와 클래스, 필드를 확인하고 릴리스마다 비교하면 회귀를 잡을 수 있습니다.

android analyze --analysis=optimization -f json library.aar

Play SDK Console에서는 라이브러리 버전 사용량과 충돌도 함께 확인합니다.

릴리스 스택 트레이스는 난독화를 풀지 않고 읽기​

난독화된 스택 트레이스를 읽기 어렵다고 해서 keepnames를 쓰는 것은 권장되지 않습니다.
keepnames는 축소는 허용하지만 이름 변경 같은 추가 최적화를 막습니다.
Firebase Crashlytics와 Play Console, Android Studio Logcat은 스택 트레이스를 자동으로 복원합니다.
매핑 파일을 SDK Console에 업로드하면 SDK Console에서도 복원된 스택 트레이스를 볼 수 있습니다.

실무 관점​

국내 MTS는 서드파티 SDK가 많은 대형 앱입니다.
DEX 코드가 10MB를 초과할 가능성이 높고, 2027년 2월 기준이 직접 적용될 수 있습니다.
먼저 Play Console의 DEX 코드 최적화 지표와 R8 Configuration Analyzer 보고서를 확인합니다.
넓은 규칙을 보내는 라이브러리가 있다면 유지보수 담당자에게 보고서 수치와 함께 전달합니다.
앱 내부 규칙도 패키지 단위가 아니라 리플렉션 진입점 단위로 좁혀 나갑니다.
AGP 9.3 이상으로 올린다면 optimization 블록과 .keep 파일 형식도 함께 검토합니다.

마치며​

DEX 코드 최적화 기준은 앱과 라이브러리가 함께 지켜야 하는 기준입니다.
Consumer Keep Rules를 좁게 유지하면 앱은 더 작고 빨라집니다.

Android CLI 1.1 살펴보기 — 델타 설치와 Compose 트레이싱

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.
2026년 11월에 공개된 Android CLI 1.1.16919734에 대해 설명해드리겠습니다.

배경​

Android CLI는 터미널에서 Android 개발을 수행하는 공식 CLI입니다.
Android Studio를 열지 않고 빌드와 설치, 프로파일링, 기기 제어를 처리할 수 있습니다.
에이전트와 함께 쓰는 개발 흐름을 염두에 두고 만들어졌고, 스크립트와 CI에서도 그대로 쓸 수 있습니다.
2026년 11월 릴리스는 설치 속도와 프로파일링, 스크립트 친화성이 중심입니다.
새 명령이 추가된 릴리스가 아니라, 매일 쓰는 명령이 더 빠르고 정확해진 릴리스입니다.

Android CLI 1.1 살펴보기​

델타 설치로 재배치된 파일 재전송 방지​

android install과 android run은 변경되지 않은 파일을 다시 보내지 않습니다.
이번 릴리스에서는 APK 안에서 위치만 바뀐 파일도 재전송 대상에서 제외됩니다.
파일 내용이 그대로인데 위치만 이동한 경우, 설치 과정에서 다시 전송할 필요가 없어졌습니다.
반복 설치가 많은 개발 과정에서 체감되는 개선입니다.
기존 동작이 필요하면 --use-delta-install-instructions=COPY,DATA 옵션을 전달합니다.

android run
android install app-debug.apk

Compose 트레이싱으로 리컴포지션 원인 찾기​

android profiler systemtrace에 Compose 트레이싱이 들어왔습니다.
--enable=compose.composition을 전달하면 실행된 컴포저블 함수마다 슬라이스를 기록합니다.

adb install --fastdeploy 옵션이 폐기됐습니다.
대신 android install 명령을 쓰도록 안내하고 있습니다.

android install app-debug.apk

Fast Deploy는 당분간 다음 플래그로 계속 쓸 수 있습니다.

다만 이후 릴리스에서는 제거될 예정입니다.
빠른 설치를 스크립트나 별칭에 넣어 쓰고 있다면, 지금부터 android install로 바꿔 두는 편이 안전합니다.

libadbusb로 바뀌는 USB 백엔드​

Linux와 macOS에서 libadbusb 라이브러리가 기존 USB 백엔드를 대체합니다.
Linux에서는 USB 버스를 주기적으로 폴링하는 방식으로 바뀌었고, 기본 간격은 1000밀리초입니다.
간격은 다음 환경 변수로 바꿀 수 있습니다.

export ADB_USB_LINUX_POLL_INTERVAL_MS=500

이 변경은 제자리 USB 리셋 뒤나 start-server 명령이 동시에 실행될 때 단말을 놓치는 문제를 피하기 위한 것입니다.
기존 백엔드로 되돌리려면 다음 환경 변수를 1로 설정하면 됩니다.

export ADB_USB_LEGACY=1

macOS에서도 같은 환경 변수로 libadbusb를 끌 수 있습니다.
참고로 Linux에서는 36.0.2부터 불안정 보고 때문에 기존 백엔드가 기본값이었던 만큼, 이번 교체가 실제 단말 연결에서 어떻게 동작하는지는 업데이트 뒤에 직접 확인하는 편이 좋습니다.

        stops = listOf(
            BlurStop(fraction = 0f, radius = 0.dp),
            BlurStop(fraction = 0.5f, radius = 0.dp),
            BlurStop(fraction = 0.75f, radius = 14.dp),
            BlurStop(fraction = 1f, radius = 28.dp),
        ),
    )
}

DialogProperties와 PopupProperties에는 배경 블러 반경과 스크림 투명도를 직접 지정할 수 있게 되었습니다.
시스템의 창 간 블러 활성화 여부는 WindowInfo.isCrossWindowBlurEnabled로 조회합니다.

폴리곤 셰이프와 모핑​

PolygonShape과 MorphPolygonShape이 androidx.compose.foundation에 추가되었습니다.
기존에는 별이나 둥근 다각형을 쓰려면 graphics-shapes 의존성을 직접 추가하고 RoundedPolygon을 Path로 변환한 뒤 Shape을 직접 구현해야 했습니다.
PolygonShape은 일반 Compose Shape이라 Modifier.clip이나 컴포넌트의 shape 파라미터에 그대로 쓸 수 있습니다.
MorphPolygonShape은 리컴포지션 없이 진행률 람다를 읽어 두 도형 사이를 애니메이션합니다.

var recording by remember { mutableStateOf(false) }
val progress by animateFloatAsState(if (recording) 1f else 0f)
val shape = remember {
    MorphPolygonShape(
        start = PolygonShape.circle(),
        end = PolygonShape.star(
            numPoints = 9,
            innerRadiusRatio = 0.8f,
            outerRounding = CornerRounding.fraction(0.5f),
        ),
        progress = { progress },
    )
}

Box(
    Modifier
        .size(96.dp)
        .clip(shape)
        .background(MaterialTheme.colorScheme.primary)
        .clickable { recording = !recording }
)

Material 3 1.5.0과 Material 2 종료​

Material 3 1.5.0도 함께 정식 출시되었습니다.
Slider와 RangeSlider가 SliderState 기반의 상태 모델로 바뀌었습니다.
ToggleButtons와 물결 모양 프로그레스 인디케이터, 타임 피커 같은 익스프레시브 컴포넌트가 추가되었습니다.
실험 API 표기는 120개에서 58개로 줄었고, 대부분의 익스프레시브 컴포넌트가 정식으로 승격되었습니다.
Material 3가 나온 지 6년째가 되는 이번 릴리스에서 Compose Material 2는 deprecated 되었고, 더 이상 적극적으로 유지보수되지 않습니다.
Material 2를 쓰고 있다면 Material 3로의 이전을 계획해야 합니다.

상태 기반 텍스트 필드로의 이전​

값 기반 BasicTextField와 Material 2 TextField가 공식적으로 deprecated 되었습니다.
대신 TextFieldState 기반의 상태 기반 BasicTextField를 사용합니다.
Material 3의 값 기반 TextField 오버로드는 1.5.0에서 아직 deprecated 되지 않았지만, 공식 문서는 상태 기반 오버로드로의 이전을 권장합니다.
TextFieldState는 서식이 적용된 스타일의 저장과 복원을 기본으로 지원합니다.
동기식 상태 모델과 성능 개선이 장점입니다.
VisualTransformation도 이번 릴리스에서 deprecated 되었고, InputTransformation과 OutputTransformation이 그 자리를 대신합니다.

val textFieldState = rememberTextFieldState()

BasicTextField(
    state = textFieldState,
    modifier = Modifier.fillMaxWidth(),
)

computedStateOf​

런타임 1.13.0에는 computedStateOf라는 새로운 상태 계산 API가 들어왔습니다.
derivedStateOf의 가벼운 대안으로, 스크롤 위치나 애니메이션 임계값처럼 자주 바뀌는 상태에서 조건 검사나 필터링 결과를 계산할 때 사용합니다.
DerivedState는 계산 결과를 캐시하지만, ComputedState는 값을 읽을 때마다 계산을 다시 수행합니다.
계산이 무겁지 않다면 derivedStateOf보다 오버헤드가 적습니다.
두 API 모두 입력 상태가 바뀔 때가 아니라 계산 결과가 바뀔 때만 컴포지션을 무효화합니다.
무거운 계산이나 캐시가 필요한 경우에만 derivedStateOf를 쓰고, 그 외에는 computedStateOf를 쓰는 것이 권장됩니다.

val listState = rememberLazyListState()
val showTopBar by remember {
    computedStateOf { listState.firstVisibleItemIndex > 0 }
}

CapturedAnimatedVisibility​

AnimatedVisibility는 종료 애니메이션이 끝날 때까지 나가는 콘텐츠와 상태를 유지해야 합니다.
상세 화면을 닫으면서 선택 항목을 null로 지우면, 보여줄 내용이 없어 깜빡이거나 빈 화면이 나타납니다.
Compose 1.13의 CapturedAnimatedVisibility는 visible이 false가 되는 순간의 마지막 프레임을 스냅샷으로 캡처해 애니메이션합니다.
호출하는 쪽에서 상태를 즉시 지워도 종료 애니메이션은 화면에 남아 있던 모습 그대로 진행됩니다.
공식 벤치마크에서는 종료 시 프레임 시간이 AnimatedVisibility보다 7~8% 빠릅니다.
나가는 콘텐츠가 계속 살아 있어야 하거나 자식에 Modifier.animateEnterExit을 써야 할 때는 기존 AnimatedVisibility를 씁니다.

@Composable
fun TrackDetails(track: Track?) {
    CapturedAnimatedVisibility(
        visible = track != null,
        enter = fadeIn() + expandVertically(),
        exit = fadeOut(tween(800)) + shrinkVertically(tween(800)),
    ) {
        if (track != null) {
            TrackCard(track)
        }
    }
}

테스트 실패 진단​

UI 테스트가 실패한 순간의 화면 상태와 시맨틱 계층을 확인하는 기능이 Compose 1.13에 들어왔습니다.
ComposeUiTestConfig의 TestFailurePolicy로 실패 시 스크린샷과 UI 계층 구조를 자동으로 저장할 수 있습니다.
TestFailureHandler를 등록하면 실패 맥락과 생성된 아티팩트를 받아 외부 리포팅 도구로 전달할 수도 있습니다.
build.gradle.kts의 testInstrumentationRunnerArguments로 테스트 스위트 전체에 캡처를 켤 수도 있습니다.

val customConfig = ComposeUiTestConfig(
    failurePolicy = TestFailurePolicy(
        screenshotCaptureMode = TestFailurePolicy.CaptureMode.Enabled,
        uiHierarchyCaptureMode = TestFailurePolicy.CaptureMode.Enabled,
    )
)

@Test
fun myTest() = runComposeUiTest(config = customConfig) {
    // 테스트 내용
}

레이아웃과 동작 변경​

1.11.0에서 실험 API로 들어온 FlexBox와 Grid가 정식으로 승격되었습니다.
FlexBox에는 한 줄에 들어가는 항목 수를 제한하는 maxItemsInEachLine 설정이 추가되었습니다.
FlowRow와 FlowColumn 대신 새 코드에는 FlexBox를 쓰는 것이 권장됩니다.
반대로 Compose용 ConstraintLayout과 MotionLayout은 deprecated 되었습니다.
공유 요소 API 등 새로운 대안이 마련되었기 때문입니다.
Modifier.onFocusedBoundsChanged는 1.12에서 deprecated 된 뒤 1.13에서 구현이 제거되어 더 이상 동작하지 않습니다.
포커스된 요소의 영역이 필요하다면 FocusTargetModifierNode.getFocusedRect()를 사용합니다.
Modifier.clickable로 만든 클릭 요소는 이제 시스템 사운드 설정에 따라 표준 상호작용 효과음을 자동으로 재생합니다.

실무 관점​

국내 MTS 프로젝트에 적용한다면, 버전 업데이트와 마이그레이션을 분리해서 계획하는 것이 좋습니다.
BOM을 2026.11.01로 올리고 빌드가 통과하는지 먼저 확인합니다.
그 다음 Material 2 사용처와 값 기반 텍스트 필드, Compose용 ConstraintLayout 사용처를 목록으로 뽑습니다.
TextFieldState 기반 필드는 입력 처리와 서식 저장 방식이 달라지므로, 입력 화면부터 단계적으로 옮기는 것이 안전합니다.
computedStateOf는 스크롤 위치에 따라 앱바를 보이거나 숨기는 것처럼 자주 바뀌는 상태를 다루는 곳부터 적용해 볼 수 있습니다.
TestFailurePolicy는 CI에서 실패 원인을 찾는 시간을 줄여주므로, UI 테스트가 있는 모듈에 먼저 적용하는 것이 좋습니다.

마치며​

Compose 1.13은 새 기능보다 종료되는 API가 더 중요한 릴리스입니다.
프로그레시브 블러와 상태 기반 텍스트 필드, computedStateOf 같은 새 기능은 단계적으로 적용하면 됩니다.

Kotlin 2.5.0-RC의 KMP 분리 컴파일과 새 발행 형식 살펴보기

2026년 11월 19일 · 약 5분
Way
Android Developer

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.
11월 11일에 공개된 Kotlin 2.5.0-RC의 KMP 변경 사항에 대해 설명해드리겠습니다.

배경​

Kotlin Multiplatform 프로젝트에서는 IDE 분석과 컴파일러의 판단이 어긋나는 경우가 있습니다.
IDE에서는 빨간 줄이 그어지는 코드가 컴파일은 통과하거나, 반대로 IDE에서는 문제가 없어 보이는데 JVM 컴파일이 실패하기도 합니다.
원인은 컴파일 방식에 있습니다.
공통 코드가 컴파일될 때 의존성의 플랫폼 아티팩트를 함께 보기 때문입니다.
Kotlin 2.5.0-RC는 이 문제를 해결하는 실험적인 분리 컴파일 방식을 도입했습니다.
아울러 멀티플랫폼 라이브러리의 발행 형식을 새로 바꿔, 발행물 크기를 크게 줄였습니다.
두 변경 사항 모두 아직 실험 단계이며, 기본값은 꺼져 있습니다.

KMP 분리 컴파일 살펴보기​

기존 컴파일 방식의 문제​

KMP 모듈은 보통 commonMain 같은 공통 소스셋과 jvmMain 같은 플랫폼 소스셋으로 구성됩니다.
컴파일러는 각 플랫폼 소스셋에 대한 플랫폼 아티팩트를 만들고, 공통 소스셋에 대한 메타데이터 KLIB를 만듭니다.
메타데이터 KLIB에는 선언만 들어 있고 구현 본문은 들어 있지 않습니다.
문제는 플랫폼 소스셋을 컴파일할 때 공통 코드까지 의존성의 플랫폼 아티팩트에 대해 함께 컴파일된다는 점입니다.
그래서 commonMain 코드가 의존성 라이브러리의 플랫폼 전용 선언을 암묵적으로 참조할 수 있습니다.
IntelliJ IDEA는 메타데이터 KLIB만 본다고 가정하므로, 같은 코드를 미해결 참조로 표시합니다.
IDE에서는 빨간 줄인데 컴파일은 통과하는 어긋남이 여기서 생깁니다.
commonTest도 같은 문제를 겪습니다.
테스트 코드가 jvmMain의 플랫폼 선언을 호출하는데, IDE는 이를 미해결 참조로 표시합니다.

// lib/jvmMain
class Foo

// app/commonMain
fun main() {
    Foo() // IDE에서는 미해결 참조, 컴파일은 통과
}

오버로드와 타입 추론의 어긋남​

오버로드 선택에서도 IDE와 컴파일러가 다른 결론에 도달합니다.
라이브러리의 commonMain과 jvmMain에 같은 이름의 함수가 여러 개 선언된 경우를 예로 들 수 있습니다.

// lib/commonMain
fun foo(x: Any) = "common"

// lib/jvmMain
fun foo(x: String) = "platform"

// app/commonMain
fun main() {
    println(foo(""))
}

IDE는 foo("") 호출을 lib/commonMain의 fun foo(x: Any)로 해석합니다.
공통 코드는 공통 선언에만 의존할 수 있다고 가정하기 때문입니다.
그러나 실제 컴파일에서는 두 선언이 모두 보이고, 더 구체적인 fun foo(x: String)이 선택됩니다.
실행 결과로 "platform"이 출력됩니다.
타입 추론에서도 비슷한 문제가 생깁니다.
actual 클래스가 expect 클래스와 다른 상위 타입을 선언하면, IDE는 Event로 추론하는데 JVM 컴파일은 Any로 추론해 .name 참조에서 실패할 수 있습니다.

분리 컴파일이 바꾸는 것​

분리 컴파일은 공통 소스셋을 컴파일할 때 메타데이터 KLIB의 선언만으로 엄격하게 해석합니다.
IDE가 가정하던 방식과 컴파일러의 동작이 일치합니다.
앞의 예제 코드는 분리 컴파일을 켜면 컴파일 오류가 됩니다.
해결 방법은 명시적인 연결을 만드는 것입니다.
라이브러리의 commonMain에 expect class를 선언하고, 플랫폼 쪽을 actual class로 만듭니다.

// lib/commonMain
expect class Foo()

// lib/jvmMain
actual class Foo

// app/commonMain
fun main() {
    Foo() // 정상 동작
}

오버로드 예제에서는 호출이 lib/commonMain의 fun foo(x: Any)로 해석되어 실행 결과로 "common"이 출력됩니다.
타입 추론 예제에서는 공통 코드가 이미 Event 반환 타입으로 추론된 상태로 JVM 컴파일이 별도로 진행되므로, 컴파일이 정상적으로 끝납니다.
기존 코드 중에는 엄격해진 검사에 걸려 수정이 필요한 부분이 생길 수 있습니다.
대신 공통 소스셋에 대한 증분 컴파일이 가능해진다는 부수적인 이득도 있습니다.

분리 컴파일 켜기​

분리 컴파일은 실험 기능이며 기본값은 꺼져 있습니다.
gradle.properties 파일에 다음 속성을 추가하면 켤 수 있습니다.

kotlin.kmp.separateCompilation=true

알려진 문제도 있습니다.
분리 컴파일이 제대로 동작하려면 멀티플랫폼 라이브러리가 메타데이터 KLIB을 발행해야 합니다.
KMP Gradle 플러그인의 기본 발행 동작이므로 대부분은 해당하지 않지만, 이 조건이 이제는 필수입니다.
C 상호 운용을 쓰는 프로젝트에서는 cinterop 공통화 관련 문제에 주의해야 합니다.
공통 소스셋이 있고 선언된 타겟이 하나뿐인 모듈은 현재 분리 컴파일의 영향을 받지 않습니다.

새 발행 형식 .kar​

Kotlin 2.5.0-RC는 멀티플랫폼 라이브러리의 새 발행 형식도 도입했습니다.
JVM과 Android을 제외한 플랫폼 아티팩트를 하나의 .kar 아카이브로 발행합니다.
.kar 파일은 ZIP 아카이브를 XZ로 한 번 더 압축한 형태입니다.
이 변경의 배경은 Maven Central에 최근 도입된 발행 크기 제한입니다.
새 형식에서는 타겟을 추가해도 새 파일이 생기지 않으므로, 발행물 크기가 크게 늘지 않습니다.
경우에 따라서는 기존의 단일 타겟 발행물보다 전체 크기가 작아지기도 합니다.
공식 문서의 예시에서는 cryptography-kotlin 라이브러리의 발행물이 7,539개 파일, 91MB에서 1,036개 파일, 23MB로 줄었습니다.
모듈별로 켜려면 빌드 스크립트에 다음과 같이 설정합니다.

kotlin {
    publishing {
        publicationFormat.set(KotlinPublicationFormat.KOTLIN_ARCHIVE)
    }
}

프로젝트 전체에 적용하려면 gradle.properties 파일에 다음 속성을 추가합니다.

kotlin.publicationFormat=KOTLIN_ARCHIVE

새 형식으로 발행하는 기능은 아직 실험 단계입니다.
다만 .kar 형식의 아티팩트를 소비하는 기능은 모든 프로젝트에서 이미 사용할 수 있습니다.
이 변경 사항은 라이브러리 작성자에게만 해당하며, 최종 애플리케이션 개발자에게는 영향을 주지 않습니다.

실무 관점​

<network-security-config>

        </trust-anchors>

</network-security-config>

cleartextTrafficPermitted를 false로 두면 평문 통신이 차단됩니다.

공식 블로그에 소개된 생성 코드는 다음과 같습니다.

// Generated by Google AI Studio Build agent using Firebase AI Logic & Cloud Firestore
class WorkoutRepository(context: Context) {
    private val generativeModel by lazy {
        Firebase.ai(backend = GenerativeBackend.googleAI())
            .generativeModel("gemini-4-hydrogen")
    }

    private val db = FirebaseFirestore.getInstance(
        context.applicationContext.getString(R.string.firestore_database_id)
    )

    suspend fun generateAndSaveWorkout(goal: String, uid: String) {
        val response = generativeModel.generateContent("Create a 20-minute workout for: $goal")
        val workout = hashMapOf(
            "ownerId" to uid,
            "goal" to goal,
            "plan" to (response.text ?: ""),
            "createdAt" to FieldValue.serverTimestamp()
        )
        db.collection("workouts").add(workout).await()
    }
}

Firebase.ai로 생성 모델을 만들고, 응답 텍스트를 Firestore 컬렉션에 저장하는 구조입니다.

터미널 에이전트 연결​

  • 터미널 에이전트 연결은 공식 Android CLI 플러그인이 맡습니다.
  • android init 한 줄이면 어떤 터미널 에이전트든 로컬 Android 도구와 연결됩니다.
  • Antigravity라면 플러그인 설치로 끝납니다.

실무에서 주의할 점​

빌드 로그가 곧 에이전트의 입력입니다.
Self-Healing이 동작하려면 빌드 실패 로그가 잘 읽혀야 합니다.
난독화된 멀티모듈 빌드에서 에이전트가 원인에 닿으려면, 지금부터라도 Gradle 빌드 스크립트와 에러 메시지를 사람이 읽을 수 있게 정리해 두는 것이 이득입니다.
비용 구조도 확인해야 합니다.
Antigravity는 AI Ultra 구독 전제이고, API 경로는 Gemini API 유료 티어 전제입니다.
인트로 가격은 2026년 11월 30일까지 적용되므로, 이후 정가를 모르면 팀 도입 판단이 어렵습니다. 도입 전에 Console에서 실제 과금을 먼저 확인해야 합니다.
셰이더 코드는 리뷰가 필수입니다.
"프로덕션급"이라는 표현은 모델 벤더의 주장일 뿐이고, AGSL 셰이더는 GPU와 디바이스별로 동작이 달라 실기 검증 없이는 쓸 수 없습니다. 에이전트가 짠 셰이더는 초안으로 보고 프레임 타임과 배터리부터 측정해야 합니다.
Firebase AI Logic 경로는 인앱 기능용입니다.
개발 워크플로(빌드 복구·코드 생성)와 앱 내 AI 기능(사용자 대면)은 접근 경로가 다르므로, 팀에서 둘을 혼동하면 과금·권한 설계가 꼬입니다.
터미널 에이전트에 Android CLI를 붙이는 방법은 다음과 같습니다.

# 어떤 터미널 에이전트에서든: 로컬 Android 도구와 연결
android init

# Antigravity를 쓴다면: 공식 Android CLI 플러그인 설치
agy plugin install android-cli-plugin

Firebase AI Logic으로 인앱에 붙일 때는 모델 선택만 새 모델로 바꾸는 구조라, 기존 Vertex AI와 Gemini Developer API 연동 코드의 모델명 교체 수준에서 검토가 가능합니다.
정확한 모델 식별자는 Firebase AI Logic 문서를 확인해야 하고, 릴리스 직후에는 SDK 업데이트가 필요할 수 있습니다.
샘플 프로젝트 gemini-4-antigravity-quickstart도 함께 공개되었으니, 에이전트 워크플로를 팀에 도입하기 전에 퀵스타트로 확인하는 것이 좋습니다.

마치며​

Gemini 4 Argon의 핵심은 모델 성능보다 빌드와 셰이더까지 에이전트 워크플로에 들어왔다는 점입니다.
도입 전에 비용 구조와 실기 검증 절차부터 정리해 두는 것이 좋겠습니다.

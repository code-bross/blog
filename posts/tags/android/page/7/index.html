Google Play에서 바이브코딩한 개인 앱을 바로 실행할 수 있게 됐다

2026년 10월 14일 · 약 3분
Way
Android Developer

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.
Google Play를 통해 개인 앱을 바로 실행할 수 있게 된 10월 13일 업데이트에 대해 설명해드리겠습니다.

배경​

예전에는 AI로 만든 앱을 실기기에 올리려면 APK를 직접 빌드해서 설치하거나, 내부 테스트 트랙용으로 Play Console에 올리는 절차가 필요했습니다.
구글은 10월 13일 Google Play 업데이트를 발표하며 이 과정을 Play가 직접 감싸는 방식을 공개했습니다.
여러 게임·발견 기능 소식이 함께 나왔지만, 개발자 입장에서 가장 눈여겨볼 내용은 개인 앱 실행입니다.

개인 앱 실행 살펴보기​

개인 앱이란​

  • Google AI Studio에서 바이브코딩으로 만든 커스텀 Android 앱을 Google Play를 통해 개인 앱(personal app)으로 자신의 기기에 실행할 수 있습니다.
  • 별도의 개발자 계정 없이 일반 Google 계정으로 가능합니다.
  • 개인 앱은 공개 스토어 카탈로그와 분리되어 private하고 안전하게 유지됩니다.
  • 구글의 표현으로는 "there's an app for that"에서 "there's an app for me"로 바뀌는 변화입니다.

롤아웃과 공유 계획​

  • 10월 13일부터 선별 시장에 롤아웃됩니다. 미국이 포함되고 18세 이상이 대상입니다.
  • 향후 몇 달 내 친구·가족과의 소규모 공유 지원이 예정되어 있습니다.

정식 공개로 전환​

  • 정식으로 세상에 공개하고 싶어지면 프로 개발자 계정으로 전환하면 됩니다.
  • 그 시점부터는 다른 앱들과 동일한 Trust & Safety 리뷰와 품질 기준이 적용됩니다.
  • 실험 구간과 배포 구간의 경계가 명확해진 것입니다.

함께 발표된 내용​

  • Ask Play: 질문에 맞는 앱 추천과 앱 간 비교(주요 차이점, 사용자 반응)를 생성합니다.
  • Play in Gemini: Gemini 대화 안에서 Play 앱·게임·개발자 콘텐츠에 접근할 수 있습니다.
  • Game Finder: 플레이 취향 분석(Gamer DNA) 기반 게임 추천으로, 미국 영어 사용자에게 먼저 제공됩니다.
  • 게임 관련으로는 48시간 미니 챌린지 Sprints, Sidekick 오버레이의 30초 Playbacks 녹화, 게임 상세 페이지의 Community Posts가 포함되었습니다.
  • Family Link를 통한 연령대 정보 공유로 연령에 맞는 경험을 제공합니다.

실무에서 주의할 점​

기획·QA용 내부 실험 빌드 경로가 더 가벼워질 여지가 있습니다.
내부 테스트 트랙보다도 진입 장벽이 낮은 개인 실행 경로가 생긴 것입니다.
공개 스토어 리뷰와 완전히 분리되므로, 실험적인 기능을 개인 기기에서 빠르게 돌려보는 용도로 적합합니다.
다만 아직은 선별 시장 중심 롤아웃이라 한국에서 바로 사용할 수 있는지는 확인이 필요합니다.
프로 계정 전환 시점의 리뷰는 기존과 동일하므로, 일단 올리고 보는 식의 접근은 여전히 통하지 않습니다.

마치며​

개인 앱 실행은 AI로 만든 앱을 실기기에서 확인하는 절차를 크게 줄여줍니다.
실험은 가볍게, 공개는 기존 기준으로 진행되는 구조이므로 용도에 맞게 나눠 사용하는 것이 좋겠습니다.

구글북 리눅스 터미널 프리뷰 — AI 에이전트에게 sudo를 줘도 되는 VM 샌드박스

2026년 10월 13일 · 약 3분
Way
Android Developer

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.
2026년 10월 12일 Android Developers Blog에 공개된 구글북 리눅스 터미널 프리뷰에 대해 설명해드리겠습니다.

배경​

구글북(Googlebook)은 Android와 Chrome OS를 합친 새 노트북 카테고리입니다.
이번에 공개된 내용은 구글북에 Debian 기반 리눅스 터미널이 프리뷰로 들어온다는 소식입니다.
핵심은 AI 에이전트에게 sudo를 줘도 시스템이 망가지지 않는 구조입니다.
자세한 내용은 Android Developers Blog 원문에서 확인할 수 있습니다.

구글북 리눅스 터미널 살펴보기​

VM 기반 격리 구조​

  • 모든 터미널 명령은 격리된 Linux VM 안에서만 실행됩니다.
  • Antigravity 같은 AI 에이전트에 sudo 권한을 줘도 호스트 OS나 개인 파일이 오염되지 않습니다.
  • VM에 공개하는 디렉터리는 사용자가 명시적으로 허용한 것만 마운트됩니다.
  • 구글북 OS는 defense-in-depth 원칙으로 설계되었고, VM 경계가 호스트 OS와 마운트되지 않은 파일을 보호합니다.

파일 유지와 원클릭 리셋​

  • 원클릭 VM 리셋으로 실험 환경을 초기화할 수 있습니다.
  • VM을 초기화해도 파일은 호스트 파일 시스템에 그대로 유지됩니다.
  • 리눅스 파일은 구글북 파일 앱에서도 보입니다.
  • 에이전트에게 과감하게 권한을 주고, 망가지면 리셋하면 되는 구조입니다.

개발자에게 익숙한 Debian 환경​

  • apt, git, ssh, 컴파일러·런타임 같은 익숙한 워크플로우가 그대로 들어옵니다.
  • Node.js, Python, Ruby, Go, Rust 같은 모던 런타임을 지원합니다.
  • localhost 포트 자동 포워딩으로 호스트 브라우저에서 바로 확인할 수 있습니다.
  • VM에 할당하는 메모리는 워크로드에 맞게 조절할 수 있습니다.
  • 구글 엔지니어들도 구글북으로 리눅스 커널을 빌드하고 플랫폼 엔지니어링에 터미널을 사용하고 있다고 합니다.

로드맵​

  • Linux GUI 앱 지원이 예정되어 있습니다. 터미널을 넘어 GUI 앱까지 품으면 Android Studio 같은 도구를 VM에 올리는 시나리오도 열립니다.
  • USB 패스스루와 ADB over USB가 지원될 예정입니다. 현재는 네트워크 패스스루와 무선 ADB가 있고, USB 패스스루가 오면 Linux VM과 Antigravity에서 직접 로컬 기기 디버깅이 가능해집니다.
  • GPU/NPU 하드웨어 가속이 예정되어 있습니다. 40 TOPS급 NPU를 단 구글북 스펙과 맞물리는 부분입니다.
  • VM 메모리·스토리지 동적 스케일링과 VM 지속성, 터미널 창 분리가 포함되어 있습니다. 장시간 도는 에이전트 작업을 위한 전제 조건입니다.

실무에서 주의할 점​

아직 프리뷰 단계이므로 당장 개발 머신으로 사용하기는 이릅니다.
GUI 앱 지원과 USB ADB는 로드맵에 있는 항목입니다.
다만 보안 모델은 주목할 만합니다.
sudo를 줘도 되는 VM 샌드박스와 디렉터리별 명시적 마운트 허가, 원클릭 리셋은 사내에서 AI 코딩 에이전트 도입을 검토할 때 레퍼런스 아키텍처로 쓸 수 있습니다.
Antigravity가 구글북용으로 따로 나온다는 점과 결합하면, 구글은 노트북을 에이전트와 함께 일하는 머신으로 그리고 있습니다.
10월 2일 공개된 Device Streaming and Android skills 흐름과 같은 방향입니다.
또한 9월 22일에 올라온 "Land your apps on Googlebook with adaptive development" 글과 함께 보면, 구글북은 Android 앱의 새 타깃 폼팩터이기도 합니다.
아직 구글북 실물이 없어 코드 실험은 못 하지만, 지금 당장 할 수 있는 정리는 다음과 같습니다.

# 2) 무선 ADB로 에이전트가 기기를 만질 수 있는지 확인

마치며​

구글북 리눅스 터미널은 에이전트에게 권한을 과감하게 줄 수 있는 개발 환경의 방향을 보여줍니다.
실물이 들어오면 터미널에서 빌드와 디버깅을 직접 확인하고, VM 리셋까지 실측해 다시 정리하겠습니다.

Kotlin 2.5.0에 companion 블록이 온다 — companion object와 무엇이 다른가

2026년 10월 13일 · 약 4분
Way
Android Developer

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.
Kotlin 2.5.0에 실험 기능으로 들어오는 companion 블록과 companion 확장에 대해 설명해드리겠습니다.

배경​

TAG 하나, newInstance() 하나를 선언할 때마다 companion object를 만들고 Companion 싱글턴이 따라붙는 구조가 반복되어 왔습니다.
JetBrains는 2026년 9월 30일 발표한 The Companions to Come 글에서 이 구조를 개선하는 실험 기능을 공개했습니다.
companion 블록은 companion object와 문법은 거의 같지만 컴파일 방식이 근본적으로 다릅니다.
전체 설계는 KEEP-0449 제안서에 정리되어 있습니다.

companion 블록과 확장 살펴보기​

companion 블록​

  • companion object에서 object 키워드를 뺀 형태입니다.
  • Kotlin 2.5.0-Beta1부터 실험 기능으로 사용할 수 있습니다.
  • 컴파일러 플래그 -Xcompanion-blocks(블록만) 또는 -Xcompanion-blocks-and-extensions(둘 다)를 넘겨야 합니다.
  • JVM에서는 진짜 static 멤버로 컴파일됩니다.
data class Vector(val x: Double, val y: Double) {
    companion {
        val ZERO = Vector(0.0, 0.0)
    }
}

// 사용은 똑같이
val v = Vector.ZERO

companion object는 실제 객체라서 인터페이스 구현이나 값으로 전달하는 것이 가능합니다.
반면 자바에서 호출하면 Vector.Companion.getZERO() 같은 이름이 드러나고, 리플렉션과 바이트코드 크기에도 흔적이 남습니다.
companion 블록은 컴파일 전략을 다른 플랫폼의 static 멤버처럼 바꿔서, JVM에서는 순수 static 멤버가 됩니다.

companion 확장​

  • 내가 만든 클래스가 아니어도 "클래스 멤버처럼" 선언할 수 있는 새 문법입니다.
  • Java 클래스에도 쓸 수 있고, 원래 companion object가 없어도 됩니다.
  • 라이브러리에서 내려준 클래스에 팩토리 함수를 붙이고 싶을 때, 유틸 오브젝트를 따로 만들지 않고도 SomeClass.myFactory() 형태로 붙일 수 있습니다.
companion fun Vector.unit(angle: Double) = Vector(cos(angle), sin(angle))

기존 companion object와의 관계​

  • 기존 companion object는 그대로 지원되고 강제 마이그레이션은 없습니다.
  • 인터페이스를 구현해야 하는 companion은 여전히 object만 가능합니다. 블록은 객체가 아니기 때문입니다.
  • 새 코드에서 단순 상수와 팩토리는 블록을 선호하는 방향이 되겠지만, 서두를 이유는 없습니다.

KMP와의 연결​

  • companion 블록 멤버는 KMP에서 expect로 선언할 수 있습니다.
  • Java 클래스의 static 멤버로 actualize할 수 있습니다.
  • 멀티플랫폼 라이브러리에서 플랫폼 네이티브 static API를 companion 멤버로 감싸던 패턴이 언어 차원에서 정식으로 지원됩니다.

실무에서 주의할 점​

실험 기능이므로 지금 당장 실무에 적용할 단계는 아닙니다.
특히 companion 확장을 쓴 라이브러리는 pre-release 바이너리가 되어 안정화될 때까지 의존성으로 소비할 수 없습니다.
companion 블록은 이 제한이 없지만, 소비하는 쪽도 플래그를 켜야 합니다.
사내 공통 모듈에 실험 문법을 넣으면 그 모듈을 쓰는 모든 프로젝트에 플래그가 전파됩니다.
마이그레이션할 때는 object 키워드를 지우는 것으로 대부분 충분하지만, 프로젝트와 의존하는 코드 전체를 다시 컴파일해야 합니다.
R8/ProGuard 규칙에서 Companion을 참조하던 룰이 있다면 함께 점검해야 합니다.
생태계 툴링이 아직 블록을 인식하지 못할 수 있다는 점도 발표에서 언급되었습니다.
Android 관점에서는 Activity와 Fragment의 newInstance, TAG 상수, CREATOR 같은 상용구의 바이트코드가 깔끔해집니다.
다만 DEX 메서드 수나 APK 크기에서 큰 변화는 기대하지 않는 것이 좋습니다.
실험 플래그를 켜는 방법은 다음과 같습니다.

// app/build.gradle.kts (Kotlin DSL)
kotlin {
    compilerOptions {
        // companion 블록만 허용
        freeCompilerArgs.add("-Xcompanion-blocks")
        // 블록 + 확장을 모두 허용
        // freeCompilerArgs.add("-Xcompanion-blocks-and-extensions")
    }
}
// 실험해 볼 후보 1: Fragment 팩토리
class DetailFragment : Fragment() {
    companion {
        private const val ARG_ID = "arg_id"
        fun newInstance(id: String) = DetailFragment().apply {
            arguments = bundleOf(ARG_ID to id)
        }
    }
}

// 실험해 볼 후보 2: 인터페이스 구현이 필요하면 object 유지
class AnalyticsTracker {
    companion object : EventSink {  // 블록으로는 안 됨
        override fun sink(event: Event) { /* ... */ }
    }
}

마치며​

companion 블록은 겉보기에는 object 한 단어 차이이지만, 바이트코드 관점에서는 static 멤버로 컴파일되는 큰 변화입니다.
실험 기능인 만큼 테스트 모듈에서 먼저 확인하고, 안정화 이후에 새 코드부터 적용하는 것이 좋겠습니다.

Remote Compose 1.0.0-alpha21 — 10월 AndroidX 릴리스에서 본 서버 구동 UI의 현재 위치

2026년 10월 12일 · 약 5분
Way
Android Developer

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.
최근 공개된 Remote Compose 1.0.0-alpha21을 중심으로 10월 AndroidX 릴리스를 설명해드리겠습니다.

배경​

2026년 10월 7일, AndroidX 정기 릴리스 배치가 나왔습니다.
그중에서도 눈에 띄는 건 remote-compose 1.0.0-alpha21과 compose.remote.foundation 1.0.0-alpha04입니다.
Remote Compose는 서버 구동 UI(Server-Driven UI)를 위한 Jetpack 라이브러리이며, 에이전트가 만든 UI를 앱 업데이트 없이 내려받아 그리는 흐름과 맞닿아 있습니다.
같은 배치의 Compose 1.13.0-beta01은 이제 Kotlin 2.2를 타깃으로 하며 kotlinc 2.2를 요구합니다.
appfunctions 1.0.0-alpha13은 API 리네임이 있어, AppFunction 어노테이션이 AppFunctionDeclaration으로 바뀌었습니다.
collection 1.7.0 스테이블에는 ScatterMap 성능 개선과 원시 타입 리스트 정렬/이진 탐색 추가가 있습니다.

Remote Compose 1.0.0-alpha21 살펴보기​

테마 인식 원격 색상​

RemoteColor.Companion에 createThemedRemoteColor가 추가됐습니다.
서버에서 내려받은 문서가 클라이언트의 라이트/다크 테마를 따라 색상을 바꿀 수 있게 되는 것입니다.
서버 구동 UI에서 가장 자주 요구되는 다크 모드 대응을 플레이어 쪽이 해결해 주니, 문서 생성 로직에서 분기할 필요가 줄어듭니다.

텍스트 측정 API​

RemoteTextMeasurer와 rememberRemoteTextMeasurer가 새로 들어왔습니다.
Remote Compose 문서 안에서 텍스트의 실제 렌더링 크기를 잴 수 있게 된 것으로, 문서 생성 시점에 텍스트 길이에 따라 레이아웃을 조정해야 하는 경우(예: 배지, 동적 라벨) 유용합니다.
Float.rsp/RemoteFloat.rsp 확장 프로퍼티도 추가돼서 Sp 단위의 RemoteTextUnit을 리터럴이나 동적 표현식에서 바로 만들 수 있습니다.

문서 생성·미리보기 개선​

  • RemoteDocumentPreview에 profile 파라미터가 생겼습니다. 문서 버퍼를 팽창시키기 전에 설정을 조정할 수 있어, 테스트·디버깅 환경에서 문서 생성을 세밀하게 제어할 수 있습니다.
  • 플레이어와 테스트 프로파일이 DrawTextOnCircle을 지원합니다. 원형 경로에 텍스트를 그리는 연출이 이제 원격 문서에서도 깨지지 않습니다.
  • DEFLATE로 압축된 문서를 플레이어가 로드할 수 있게 됐습니다. 문서 크기가 크다면 전송량을 줄이는 방향으로 설계할 여지가 생깁니다.
  • captureSingleRemoteDocument/captureRemoteDocument의 라이프사이클과 스냅샷 처리가 다져졌고, 수집 속도가 리컴포지션을 따라가지 못할 때 업데이트가 조용히 누락되던 버그도 수정됐습니다. 서버 구동 UI에서 가끔 화면이 안 바뀌는 식의 간헐적 이슈가 줄어들 것으로 보입니다.
  • 커스텀 진입/종료 가시성 애니메이션 지원, 스프링 애니메이션의 스냅·범위 이탈 버그 수정 등 렌더링 품질 쪽도 여러 건 잡혔습니다.

compose.remote.foundation 1.0.0-alpha04​

같은 배치에 androidx.compose.remote.foundation의 새 알파가 같이 나왔습니다.
의존성은 다음과 같이 선언합니다.

dependencies {
    implementation("androidx.compose.remote.foundation:foundation:1.0.0-alpha04")
}

같이 나온 것들​

  • Compose 1.13.0-beta01 (animation/foundation/material/runtime): 이번 배치부터 라이브러리들이 Kotlin 2.2를 타깃으로 하고 kotlinc 2.2를 요구합니다. 베타를 올릴 때는 Kotlin 버전을 2.2 이상으로 올려야 컴파일이 됩니다.
  • appfunctions 1.0.0-alpha13: @AppFunction → @AppFunctionDeclaration, ObserveAppFunctionsEvent → AppFunctionsChangeEvent로 리네임됐고, 접근 레벨 제한을 위한 @AppFunctionAccessLevel이 추가됐습니다. 에이전트·Gemini 시대의 앱 기능 노출 인터페이스라 실험 중이라면 이름 바뀐 것만 확인하면 됩니다.
  • collection 1.7.0 (스테이블): toOrderedScatterSet() 확장(빈 소스에선 할당 없는 싱글턴 반환), ScatterMap.getOrPut() 최적화, Float 키 해시 충돌 개선, 원시 타입 리스트(IntList/LongList 등)에 sortWith/sortBy/binarySearch 추가. 퍼포먼스에 민감한 데이터 구조를 쓰는 팀은 별도 변경 없이 이득을 볼 수 있습니다.
  • benchmark 1.6.0-alpha01: :lockClocks 태스크가 root 없이도 고정 성능 모드를 쓸 수 있게 돼서, 더 많은 실기기에서 안정적인 마이크로벤치마크가 가능합니다. 힙 프로파일링용 MemoryProfilingConfig도 추가됐습니다.

실무에서 주의할 점​

  • Remote Compose는 아직 알파입니다. API가 바뀔 수 있다는 전제로 실험·프로토타입 수준에서 접근하는 게 맞습니다. 다만 테마 인식, 텍스트 측정, 압축 문서 로딩처럼 운영에 쓰려면 꼭 있어야 할 기능들이 차례로 들어오고 있어서, 방향성 자체는 꽤 진지하게 보입니다.
  • 에이전트 시대의 SDUI: 최근 Android CLI와 에이전트 스킬 흐름과 맞물려, 에이전트가 생성한 UI를 어떻게 앱에 그릴 것인가가 실무 질문이 되고 있습니다. Remote Compose는 그 답 중 하나입니다. 당장 도입하지 않더라도 개념과 플레이어 구조는 한 번 훑어둘 만합니다.
  • Compose 1.13 베타 + Kotlin 2.2: 컴파일러 버전 요구사항이 같이 올라간 릴리스라서, 버전만 올렸다가 빌드가 깨지는 경우가 생길 수 있습니다. 베타를 쓸 거면 libs.versions.toml의 Kotlin 버전도 함께 올립니다.
  • appfunctions 리네임: 알파 실험 중이라면 컴파일 에러가 나는 게 정상이니, 이름만 바꿔 주면 됩니다.

당장은 프로덕션 도입이 아니라 관측 모드입니다.
스프린트 사이에 작은 실험 프로젝트 하나로 Remote Compose 플레이어에 문서 하나 띄워 보는 것 정도가 적당합니다.
관전 포인트는 두 가지입니다.

  1. 서버에서 보낸 문서가 다크 테마에서 깨지지 않는지 (createThemedRemoteColor 사용)
  2. 텍스트 길이 가변적인 배지 UI를 RemoteTextMeasurer로 제대로 그릴 수 있는지
// gradle/libs.versions.toml
[versions]
androidxRemoteCompose = "1.0.0-alpha21"
composeRemoteFoundation = "1.0.0-alpha04"

에이전트가 UI를 만드는 시대가 오고 있는데, 어떻게 그릴 것인가는 여전히 앱 개발자의 몫입니다.
Remote Compose가 그 몫을 나눠 가질 후보 중 하나라는 점에서, 이번 릴리스는 지켜볼 가치가 있습니다.

마치며​

10월 AndroidX 배치는 UI를 코드가 아니라 문서로 다루는 쪽으로 축이 이동하고 있음을 보여줍니다.
Remote Compose 알파21의 변경점 대부분이 렌더링 품질과 운영 편의(테마, 압축, 측정)에 집중돼 있다는 점이 그 신호이며, 다음에 SDUI를 고민할 때 선택지에 넣어두기 좋은 타이밍입니다.

Play 타깃 API 36 제출 차단이 현실화됐다 — 11월 1일 연장 신청과 대응 체크리스트

2026년 10월 12일 · 약 5분
Way
Android Developer

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.
Google Play 타깃 API 36 요구사항과 대응 체크리스트를 설명해드리겠습니다.

배경​

2026년 8월 31일을 기점으로, Google Play에 제출되는 신규 앱과 앱 업데이트는 Android 16(API 36) 타깃이 필수 조건이 됐습니다.
경고로 끝나는 줄 알았던 마감일이 이제는 실제로 업로드를 막는 단계에 들어왔습니다.
한 줄짜리 크래시 핫픽스도 targetSdk를 36으로 올리기 전까지는 콘솔에 올라가지 않습니다.
이미 스토어에 있는 앱은 API 35 이상을 타깃해야 타깃보다 높은 OS를 쓰는 신규 사용자에게 계속 노출됩니다.
API 34 이하에 머물면 신규 사용자 설치가 조용히 막힙니다.
아직 대응 전이라면 11월 1일까지 한 번의 연장을 신청할 수 있는데, 이것도 자동으로 주어지는 건 아닙니다.

타깃 API 요구사항 살펴보기​

자세한 기준은 Google Play의 타깃 API 레벨 요구사항에서 확인할 수 있습니다.

규칙은 제출 시점에 막는다​

이 요구사항의 포인트는 심사가 아니라 제출 단계에서 걸린다는 점입니다.
Play Console에 AAB를 올리는 순간 타깃 API 검사가 먼저 돌아가고, 조건을 못 맞추면 업로드 자체가 거부됩니다.
즉, 심사 지연이 아니라 아예 리뷰 대기열에 들어가지도 못합니다.
한참 전에 만들어 둔 빌드를 그냥 올리려던 팀은 여기서 바로 발목이 잡힙니다.

세 가지 상태, 세 가지 기준​

Google의 타깃 API 정책은 앱의 상태를 이렇게 구분합니다.

앱 상태적용 기준
신규 앱(아직 게시 안 됨)첫 제출부터 API 36 이상 (휴대폰·태블릿·폴더블 기준)
기존 앱의 업데이트 제출대체 버전 제출 시 API 36 이상
기존 앱(업데이트 안 함)API 35 이상이어야 신규 사용자에게 노출 유지

여기서 착각하기 쉬운 부분이 있습니다.
업데이트를 한 번이라도 제출하면 그 순간부터 신규 앱과 같은 API 36 기준이 적용됩니다.
API 35는 아무것도 안 하고 놔둬도 스토어에서 사라지지는 않게 해주는 완충선일 뿐, 업데이트 면제권이 아닙니다.
참고로 Wear OS·Android Automotive는 API 35, Android TV·Android XR은 API 34가 기준입니다.

연장 신청: 11월 1일까지, 한 번​

Play Console에서 해당 앱의 타깃 API 경고 화면으로 들어가면 연장 신청 양식을 찾을 수 있습니다.
신청이 받아들여지면 기한이 2026년 11월 1일로 미뤄집니다.
중요한 건 이 연장이 자동도 아니고 반복도 안 된다는 점입니다.
11월 1일 이후에는 다시 기준이 원상복귀됩니다.
신청 안 하고 버티면 하루라도 늦은 날부터 제출이 막히니, 대응 일정이 빠듯하다면 일단 신청부터 해두고 개발을 진행하는 게 합리적입니다.

실무에서 주의할 점​

  • 숫자 바꾸는 건 1분, 동작 변경 대응이 본게임: 2026년 10월 초에 세 개 앱을 API 36으로 올린 개발자의 회고에 따르면, build.gradle.kts의 숫자 변경은 1분이면 되지만 이후 작업에 이틀이 걸렸다고 합니다. Android 16에서는 엣지 투 엣지(Edge-to-Edge)가 의무화되고, 태블릿·폴더블에서는 방향 고정(orientation lock)이 무시되는 등 실제 동작이 바뀌는 지점이 있습니다. UI가 화면 끝까지 그려지는지, 인셋 처리가 깨지지 않는지 확인이 필요합니다.
  • API 34 이하에 머무르면 "조용히" 죽는다: 앱이 스토어에서 갑자기 삭제되는 게 아니라, 타깃보다 높은 OS 버전을 쓰는 신규 사용자에게만 노출이 중단됩니다. 설치율이 이유 없이 떨어지는 것처럼 보이기 때문에, 모니터링만 보고 있으면 원인 파악이 늦어집니다. 우리 앱의 현재 targetSdk를 Play Console 앱 대시보드에서 먼저 확인해 보세요.
  • 연장은 계획이 아니다: 연장을 신청하면 6주 남짓의 시간을 버는 것뿐이고, 작업량은 그대로입니다. 연장 승인이 났다는 이유로 회귀 테스트를 줄이면 나중에 더 아픕니다.
  • 연관 게이트도 같이 확인: 같은 시기, Play Billing을 쓰는 앱은 Billing Library 8.0.0 이상이 동반 요구되고, 네이티브 코드를 포함하는 앱은 2027년 2월 1일부터 16 KB 페이지 사이즈 지원 없이는 업로드가 거부됩니다. targetSdk 올릴 때 같이 점검하면 일정을 한 번으로 합칠 수 있습니다.

대응 순서는 다음과 같습니다.
급한 순서대로 정리한 체크리스트입니다.

// app/build.gradle.kts (Kotlin DSL)
android {
    compileSdk = 36
    defaultConfig {
        minSdk = 24
        targetSdk = 36   // ← 이 숫자. 8월 31일 이후 제출 조건
    }
}
  1. Play Console → 해당 앱 → 정책/타깃 API 경고 화면에서 현재 상태 확인
  2. 아직 36이 아니면 연장 신청 폼부터 제출 (11월 1일까지, 한 번)
  3. compileSdk/targetSdk 36으로 올리고 엣지 투 엣지·인셋·방향 처리 회귀 테스트
  4. Billing Library 버전(8.0.0+)과 16 KB 페이지 사이즈 대응 여부도 같은 패스에 확인

템플릿이나 프레임워크가 아직 35를 기본값으로 쓰고 있는 경우가 많으니, 신규 프로젝트라면 프로젝트 생성 직후 이 숫자부터 확인하는 습관을 들이는 게 좋습니다.

마치며​

타깃 API 마감일은 매년 오는 행사지만, 올해는 제출 차단이라는 점에서 체감 강도가 다릅니다.
특히 API 34 이하에 머무는 앱은 신규 사용자 노출이 조용히 막히기 때문에, 별다른 이상 없이 설치 지표가 떨어지는 상황이면 targetSdk를 먼저 의심해 보길 권합니다.

대규모 앱의 DataStore 마이그레이션 실측 사례에 대해 설명해드리겠습니다.

배경​

SharedPreferences를 DataStore로 옮기고 싶은데 성능이 나빠지지는 않을까 망설이는 팀이 많습니다.
이번 ProAndroidDev 커뮤니티 글은 대규모 앱의 스토리지 기반을 통째로 갈아엎고, 영향을 숫자로 증명한 사례입니다.
한 대규모 앱 팀이 핵심 로컬 데이터를 SharedPreferences에서 Jetpack DataStore로 이전했습니다.
다른 변경의 영향이 섞이지 않도록 빌드를 3개로 나눠 측정한 결과, DataStore 자체의 런타임 비용은 측정 오차 범위 안이었습니다.
콜드 스타트, CPU, 메모리 모두 마찬가지입니다.
기존 사용자 데이터 마이그레이션은 백그라운드 스레드에서 1회 실행되며 수십 ms에 끝납니다.
저사양 기기 업데이트 시나리오에서도 첫 실행이 느려지지 않았습니다.

마이그레이션 사례 살펴보기​

왜 SharedPreferences를 떠났나​

글쓴이가 꼽은 SharedPreferences의 한계는 다섯 가지입니다.

  1. 첫 읽기가 동기식이라 메인 스레드에서 호출하면 화면이 같이 기다립니다.
  2. apply()는 비동기처럼 보이지만 Activity 종료 시점에 밀린 쓰기를 모두 기다립니다. 저장소가 느린 기기에서는 ANR로 이어질 수 있습니다.
  3. 쓰기 실패가 조용히 묻힙니다. apply()는 성공 여부를 알려주지 않습니다.
  4. 변경을 관찰하기 어렵습니다. 리스너 방식은 누수 나기 쉽고 코루틴/Flow와도 어울리지 않습니다.
  5. 타입이 강제되지 않습니다. Int로 저장한 걸 Long으로 읽으면 런타임에 ClassCastException으로 터집니다.

DataStore는 정확히 이 지점들을 겨냥한 설계이니, 왜 옮기는지에 대한 답은 비교적 명확합니다.

측정 방법이 인상적인 부분​

제일 배울 점은 측정 설계입니다.
이번 릴리스에는 DataStore 말고도 다른 변경이 많았기 때문에, 팀은 빌드를 3개로 나눠서 쟀습니다.

  • 이전 릴리스
  • 이번 릴리스에서 DataStore만 뺀 빌드
  • 실제로 배포한 이번 릴리스

두 번째와 세 번째의 차이가 곧 DataStore의 순수 비용입니다.
Xiaomi Redmi Note 9 Pro(Snapdragon 720G, 6GB RAM)에서 24분짜리 단일 세션에 몰아넣어 빌드당 10회 콜드 스타트를 연달아 쟀습니다.
결과는 모든 차이가 같은 빌드 내 변동 폭 안에 들었습니다.
오히려 CPU만은 B 화면 아이들 상태에서 2.6포인트 일관되게 내려갔고, 이건 두 번의 별도 측정 세션에서 모두 재현됐습니다.

저사양 기기 업데이트 시나리오​

마이그레이션이 실제로 도는 건 기존 사용자가 업데이트할 때라서, Galaxy A15에서 구버전 데이터를 깔아둔 상태로 10회씩 쟀습니다(Perfetto).
10회 콜드 스타트와 10회 웜 스타트 모두 새 APK가 빨랐고, 마이그레이션이 도는 첫 실행(7.04초)도 평균보다 느리지 않았습니다.
즉 마이그레이션이 기존 사용자를 붙잡지 않습니다.

실무에서 주의할 점​

  • "DataStore로 옮기면 느려진다"는 선입견을 깨는 수치입니다. 측정 오차 범위 안에 든다는 건, 실무적으로는 비용이 없다는 뜻입니다.
  • 하지만 이 팀의 결론은 "DataStore가 앱을 빠르게 했다"가 아닙니다. 같은 릴리스에서 Galaxy A55 기준 첫 화면이 0.7초 빨라진 건 팀 전체의 작업 덕분이고, DataStore는 그 발목을 잡지 않았을 뿐입니다. 숫자를 읽을 때 귀속 관계를 헷갈리면 안 됩니다.
  • 마이그레이션 소요 시간은 텔레메트리로 잡았습니다. 백그라운드에서 수십 ms에 끝난다는 주장이 "느낌"이 아니라 측정값인 게 이 글의 신뢰도를 올립니다.
  • 글쓴이 본인도 경고합니다. 모든 숫자는 물리 기기에서 직접 잰 내부 측정값이라, 내 앱·내 기기에서는 값이 다를 수 있습니다.

적용 패턴은 다음과 같습니다.
DataStore Preferences로 옮길 때 기존 SharedPreferences 데이터를 살리는 표준 패턴입니다.

// 기존 prefs 데이터를 잃지 않고 DataStore로 1회 마이그레이션
val Context.dataStore by preferencesDataStore(
    name = "settings",
    produceMigrations = { context ->
        listOf(SharedPreferencesMigration(context, "old_prefs"))
    }
)

// 읽기: 코루틴/Flow에 자연스럽게 연결
val darkMode = context.dataStore.data
    .map { prefs -> prefs[DARK_MODE_KEY] ?: false }

이 사례에서 가져갈 교훈은 두 가지입니다.
첫째, 성능을 우려하는 대규모 변경은 변경만 뺀 비교 빌드를 하나 더 만들어 측정하는 것입니다.
둘째, 마이그레이션 소요 시간을 텔레메트리 이벤트로 남겨서 운영 중에도 실제 숫자를 볼 수 있게 하는 것입니다.
이 두 가지만 해도 느려진 것 아니냐는 질문에 감이 아니라 숫자로 답할 수 있습니다.

마치며​

스토리지 마이그레이션은 사용자에게 보이지 않는 게 성공입니다.
유실도 없고, 중간에 끊긴 세션도 없고, 느려진 앱도 없는 것, 그걸 숫자로 증명한 사례가 나왔다는 점에서 아직 SharedPreferences에 머물러 있는 팀에게 한 번쯤 읽어볼 만한 글입니다.

Kotlin 2.4.21 버그픽스 릴리스 — 2.4.x 라인 유지팀은 안전하게 올릴 시점

2026년 10월 11일 · 약 3분
Way
Android Developer

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.
최근 공개된 Kotlin 2.4.21에 대해 설명해드리겠습니다.

배경​

2026년 10월 8일, JetBrains가 Kotlin 2.4.21을 릴리스했습니다.
기능 추가 없는 버그픽스 릴리스라서 2.4.x 라인을 쓰고 있는 팀이라면 특별한 고민 없이 올릴 수 있는 버전입니다.

Kotlin 2.4.21 살펴보기​

K/Wasm: 조용한 트랩 대신 예외가 던져진다​

K/Wasm에서 잘못된 타입의 인자로 람다를 호출하면 트랩이 나던 문제가 고쳐졌습니다.
(T) -> R 형태의 람다에 T가 아닌 인자를 넣었을 때, 이전에는 Wasm 트랩이 발생해 무엇을 잘못한 것인지 알기 어려웠습니다.
이번 수정으로 ClassCastException이 정상적으로 던져집니다.
K/Wasm 타깃을 만지는 KMP 프로젝트라면, 기존에 트랩으로 죽던 경로가 이제 catch 가능한 예외로 바뀌는 것이니 예외 처리 로직을 한 번 확인해 볼 만합니다.

Kotlin/JS: 프로덕션 빌드에서 멤버 이름 유지​

Kotlin/JS 프로덕션 빌드에서 멤버 이름이 minify되지 않도록 되돌려졌습니다.
디버깅이나 런타임 이름 기반 처리에 영향을 받을 수 있는 프로젝트는 안심하고 올릴 수 있는 방향입니다.

리플렉션에서 K1 의존성 제거​

JVM 리플렉션의 KCallable 표현 방식이 K1 컴파일러 의존성을 제거하는 방향으로 바뀌었습니다.
겉으로는 드러나지 않지만, K2 컴파일러로 완전히 넘어가는 과정에서 남은 구형 의존성을 하나씩 걷어내는 작업입니다.
리플렉션을 쓰는 라이브러리의 내부 구현을 보는 편이라면 왜 이런 식으로 바뀌었는지의 맥락 정도로 이해하면 됩니다.

스크립트 관련 수정들​

Kotlin Script와 JSR-223 관련 수정이 여러 건 포함됐습니다.
Kotlin Script에서 전달 의존성이 있는 스크립트를 두 번째 실행하면 NoClassDefFoundError가 나던 문제, JSR-223에서 제네릭 Java 바인딩이 이후의 모든 eval() 호출을 깨뜨리던 문제가 수정됐습니다.
스크립트 엔진을 내장한 앱이라면 의미 있는 수정입니다.

그 밖의 수정​

  • @Serializable 제네릭 클래스에 클래스 상한(class upper bound)이 있을 때 잘못된 Wasm이 나오던 문제
  • K/N Gradle에서 SwiftPM import 시 로그가 넘쳐나던 문제

실무에서 주의할 점​

  • 2.4.x 라인 유지 중이라면 이번엔 올리면 됩니다. 새 기능이 아니라 버그픽스 묶음이라 동작 변경 리스크가 낮습니다.
  • K/Wasm을 쓰는 KMP 프로젝트는 예외 경로를 점검하세요. 트랩이 예외로 바뀌는 건 에러 처리 전략에 직접 영향을 줍니다.
  • Kotlin/JS는 minify 복원이라 큰 주의점은 없습니다. 오히려 이전 버전에서 이상 징후가 있었다면 해소 방향입니다.
  • 스크립트 엔진 내장 앱(서버 측 혹은 내부 도구)은 이번 릴리스가 제법 알찹니다. 스크립트 실행 관련 수정이 4건이나 들어 있습니다.

적용 방법은 다음과 같습니다.
버전 카탈로그 기준으로 버전만 바꾸는 게 전부입니다.
다만 올리고 나면 컴파일러가 바뀌는 만큼, 전체 빌드 한 번과 주요 화면 스모크 테스트 정도는 돌립니다.

// gradle/libs.versions.toml
[versions]
kotlin = "2.4.21" // 2.4.20 -> 2.4.21 (버그픽스, 동작 변경 없음 예상)

KMP 프로젝트에서 Wasm 타깃을 쓰는 경우, 릴리스 노트의 해당 항목이 내 코드 경로에 닿는지 빠르게 확인하는 스크립트를 CI에 걸어 두면 이후 릴리스에서도 부담이 없습니다.

마치며​

메이저 릴리스가 아니라서 화려하진 않지만, 이런 버그픽스 릴리스야말로 그냥 올리면 좋은 릴리스입니다.
2.4.x 라인에서 운영 중인 프로젝트가 있다면, 이번 주에 버전만 올리고 스모크 테스트 한 번 돌려 보길 권합니다.

KMP 플러그인의 Swift IDE 지원 종료 — 2026.3부터 Swift 작업은 Xcode로 나눠야 한다

2026년 10월 10일 · 약 4분
Way
Android Developer

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.
Kotlin Multiplatform(KMP) 플러그인의 Swift 언어 IDE 지원 종료 소식에 대해 설명해드리겠습니다.

배경​

2026년 10월 5일, JetBrains가 KMP 플러그인에서 제공하던 Swift 언어 IDE 기능을 앞으로 중단한다고 알렸습니다.
적용 시점은 IntelliJ IDEA 2026.3과 Android Studio Rabbit 2 | 2026.2.2부터입니다.
쉽게 말하면, 도구가 하나로 합쳐지던 방향에서 다시 각자 잘하는 쪽으로 역할을 나누는 선택입니다.
자세한 내용은 Kotlin 블로그 원문에서 확인할 수 있습니다.

무엇이 달라졌는지​

종료되는 기능​

없어지는 것은 Swift 파일을 같은 IDE 안에서 편집하고, 문법 강조를 받고, Swift와 Kotlin 사이를 오가며 이동하던 기능입니다.
그동안 KMP 플러그인 안에서는 Kotlin 코드와 Swift 코드를 한 창에서 보는 경험이 가능했지만, 이제 그 경계가 다시 IDE 밖으로 나갑니다.
SwiftUI 화면이나 iOS 전용 코드는 Xcode에서, 공유 로직과 Compose Multiplatform 코드는 IntelliJ나 Android Studio에서 보는 흐름이 기본이 됩니다.

계속 지원되는 기능​

iOS 앱을 실행하는 일과 iOS에서 Kotlin 코드를 디버깅하는 일은 계속 지원됩니다.
Kotlin/Native 쪽 기능도 그대로입니다.
Swift로 내보내는 Swift Export나, Swift 패키지를 Kotlin 프로젝트로 가져오는 흐름은 이번 결정과 별개입니다.
예전 버전의 IDE와 플러그인에서는 기존 Swift 기능을 계속 쓸 수 있지만, 거기에 새 업데이트가 붙지는 않습니다.

종료 배경​

원래 이 Swift 지원은 과거 AppCode 시절의 기술을 바탕으로 만들어졌고, 이후 여러 제품을 거치며 KMP 플러그인까지 이어졌습니다.
그런데 실제 사용은 꾸준히 줄었고, KMP를 쓰는 iOS 개발자 상당수는 Swift 작업만큼은 Xcode를 선호했다고 합니다.
반대로 플러그인 안에서 일하는 팀은 Kotlin과 Compose Multiplatform 비중이 점점 커졌습니다.
Swift와 Xcode, IntelliJ 플랫폼이 계속 바뀌는 상황에서 이 연결을 유지하는 비용이 실제 쓰임에 비해 컸다는 판단입니다.
대체 기능을 새로 만들 계획은 현재로서는 없다고도 했습니다.
앞으로는 Kotlin 도구 자체와 iOS 개발자를 위한 KMP 경험을 다듬는 데 힘을 쏟겠다는 방향입니다.

실무에서 주의할 점​

Android만 만드는 팀이라면 체감 변화는 거의 없습니다.
영향은 KMP로 iOS까지 같이 보는 팀에서 생깁니다.

  • Swift 파일을 Android Studio에서 고치던 습관이 있다면 작업 동선을 나눠야 합니다. 특히 iosApp 쪽 SwiftUI 진입점, 권한이나 딥링크처럼 iOS에 붙은 얇은 층을 누가 어느 IDE에서 고칠지 팀 안에서 정해두는 것이 좋습니다.
  • 구버전에 머무는 선택은 임시 방편입니다. Swift 이동 기능이 꼭 필요해서 IntelliJ IDEA 2026.3 이전에 머무를 수는 있지만, 그 사이 Kotlin 플러그인과 Android Studio의 다른 개선을 못 받게 됩니다. 보안과 빌드 도구 호환까지 같이 보면 오래 버티는 전략은 아닙니다.
  • 공유 경계를 더 얇게 가져갈 이유가 생겼습니다. Swift 쪽에 로직이 많이 남아 있으면 IDE를 오갈 때마다 맥락이 끊깁니다. 반대로 Swift를 화면 진입과 플랫폼 연결 정도로 얇게 두고, 상태와 규칙을 Kotlin에 두면 이번 변화의 마찰이 작아집니다.

이 소식을 KMP 자체가 약해졌다는 신호로 보기는 어렵습니다.
오히려 JetBrains가 잘 쓰이지 않는 통합을 걷어내고, 실제로 많이 쓰이는 Kotlin 쪽 경험에 집중하겠다는 쪽에 가깝습니다.
새로 KMP를 시작한다면 처음부터 Swift 층을 얇게 잡는 구성이 안전해 보입니다.
예를 들면 iOS 진입점은 Compose 화면을 감싸는 역할만 하고, 나머지는 공유 모듈이 맡는 식입니다.

ML Drift 오픈소스 공개 — LiteRT GPU 가속의 새 엔진, TFLite GPU delegate의 뒤를 잇다

2026년 10월 10일 · 약 5분
Way
Android Developer

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.
최근 공개된 ML Drift에 대해 설명해드리겠습니다.

배경​

2026년 10월 8일, Google AI Edge 팀이 온디바이스 GPU 추론을 위한 새 엔진 ML Drift를 Apache 2.0 라이선스로 공개했습니다.
ML Drift는 LiteRT 안에서 GPU 가속을 맡는 중심 엔진이며, 따로 떼어내어 커스텀 그래픽이나 추론 런타임을 만들 때 쓰는 독립 라이브러리로도 사용할 수 있습니다.
서버에서는 비슷한 가속기가 줄지어 있지만, 휴대폰은 칩과 드라이버와 그래픽 경로가 제각각입니다.
이 다양성을 앱 개발자가 직접 메우지 않게 하는 것이 이 엔진이 풀려는 문제입니다.

ML Drift 살펴보기​

ML Drift는 기기마다 다른 GPU 환경을 한 층으로 감싸는 크로스 플랫폼 GPU 컴퓨트 엔진입니다.
뒤쪽에서는 OpenGL ES, OpenCL, Metal, WebGPU 같은 서로 다른 그래픽 경로를 다룹니다.
기존 TensorFlow Lite GPU delegate가 맡던 자리를 이어받는 방향이며, 앞으로 그 예전 경로는 새 기능을 더 받지 않습니다.
이동 경로는 LiteRT의 ML Drift GPU 가속 경로입니다.
고전적인 비전 모델뿐 아니라, 기기에서 도는 생성형 모델까지 함께 노린 구조 개편이 들어갔습니다.

텐서를 바라보는 방식을 바꿨다​

예전 방식에서는 텐서가 GPU의 텍스처나 버퍼 같은 실제 자원에 어떻게 붙는지를 백엔드마다 따로 적어 두는 일이 많았습니다.
ML Drift는 여기서 한 단계 추상화를 넣었습니다.
논리적인 텐서와 실제 GPU 배치를 분리해 두고, 초기 설정 단계에서 셰이더가 그 연결을 풀어내는 구조입니다.
덕분에 백엔드마다 셰이더를 따로 유지하는 부담을 줄이면서도 실행 중 부담은 작게 가져가려 했다는 설명입니다.

5차원 텐서와 시공간 모델​

예전 GPU 경로는 4차원 텐서를 전제로 짜여 있어, 그보다 복잡한 모양이 필요하면 우회로를 만들어야 했습니다.
새 엔진에서는 5차원 텐서를 기본으로 다룰 수 있게 되면서, 3차원 합성곱이나 영상처럼 시간 축이 붙은 모델을 기기 GPU에서 바로 돌리는 길이 넓어졌습니다.

LLM 단계에 따라 커널을 바꾼다​

기기에서 도는 언어 모델은 한 번에 길게 읽어 들이는 구간과, 토큰을 하나씩 이어 붙이는 구간의 성격이 다릅니다.
앞쪽은 연산량에, 뒤쪽은 메모리 이동에 더 묶입니다.
ML Drift는 지금이 어느 단계인지에 따라 커널과 배치를 바꾸고, KV 캐시 쪽에도 전용 배치를 적용해 불필요한 왕복을 줄이는 방향을 택했습니다.

커스텀 연산과 데스크톱 확장​

모델에 특이한 블록이 있으면 개발자가 낮은 수준의 셰이딩 언어로 직접 연산을 등록할 수 있는 길도 새로 정리됐습니다.
코딩 에이전트가 이 커스텀 셰이더를 만들고 검증하는 과정을 돕는 안내 파일까지 함께 제공된다는 점도 특징입니다.
또 WebGPU 경로를 바탕으로 브라우저 밖 Windows와 Linux에서도 같은 코드를 돌리는 미리보기가 소개됐고, macOS에서는 Metal 경로가 이를 받칩니다.

실제 서비스에서의 쓰임​

실제 서비스에서의 쓰임도 함께 소개됐습니다.
영상 효과, 사진 보정, 브라우저 안 온디바이스 모델, 사진 편집 앱의 피사체 선택 같은 작업에서 기존 GPU 경로보다 지연이 줄었다는 사례가 실렸습니다.
숫자는 모델과 기기마다 다르니, 결국 내 모델로 재보는 수밖에 없습니다.

실무에서 주의할 점​

  • TFLite GPU delegate를 직접 쓰고 있다면 이동 계획을 세울 때입니다. 새 기능이 그쪽으로 더 오지 않는다고 못 박은 만큼, 지금 당장 끊기지는 않더라도 다음 모델 교체나 성능 개선 시점에 LiteRT 경로로 벤치마크를 한 번은 돌려봐야 합니다.
  • 벤치마크는 모델 전체 평균만 보면 안 됩니다. 언어 모델이라면 읽어 들이는 구간과 토큰을 만드는 구간의 속도가 따로 움직입니다. 두 구간을 나눠 재지 않으면 병목이 어디인지 놓치기 쉽습니다.
  • GPU 벤더별 확인은 여전히 필요합니다. 추상화가 좋아졌다고 해도 실제 속도는 칩과 드라이버에서 갈립니다. 플래그십 한 대에서만 재고 끝내면 중저가 기기에서 체감이 다르게 나올 수 있습니다.
  • 커스텀 연산은 강력하지만 유지 비용이 붙습니다. 직접 짠 셰이더는 모델을 바꿀 때마다 다시 봐야 합니다. 꼭 필요한 블록에만 쓰고, 나머지는 기본 연산으로 두는 편이 운영에 낫습니다.

금융 앱 관점에서는, 사진을 읽어 문서를 인식하거나 기기 안에서 작은 모델로 분류하는 작업을 서버로 보내지 않고 끝낼 수 있을 때 의미가 큽니다.
데이터를 기기 밖으로 내보내지 않는 구조는 개인정보와 네트워크 비용 양쪽에서 이득이 있기 때문입니다.
다만 그 전제는 결국 속도인데, 이번 개편은 그 속도를 벤더 중립적으로 끌어올리려는 시도라고 읽힙니다.

측정을 시작한다면 기존에 GPU delegate로 돌리던 모델을 LiteRT 경로로 바꿔 같은 기기에서 나란히 재는 것부터 시작하는 것이 좋습니다.
아래는 개념을 잡기 위한 예시 흐름입니다.

// 같은 모델을 CPU와 GPU 경로로 각각 준비해 지연을 나눠 재는 벤치마크 뼈대
data class BenchResult(
    val backend: String,
    val warmupMs: Double,
    val steadyMs: Double,
)

fun benchmarkModel(backend: String): BenchResult {
    // 1) LiteRT 모델을 backend 옵션으로 연다 (GPU면 ML Drift 가속 경로)
    // 2) warm-up을 충분히 돌린 뒤, 입력 모양별로 지연을 측정한다
    // 3) 언어 모델이면 prefill과 decode를 분리해서 기록한다
    return BenchResult(backend, warmupMs = 0.0, steadyMs = 0.0)
}

val results = listOf("CPU", "GPU").map { benchmarkModel(it) }
results.forEach { println("${it.backend}: steady=${it.steadyMs}ms") }

여기에 기기 이름과 칩 정보, 모델 버전을 함께 남겨 두면 나중에 어떤 폰에서 느려졌는지를 추적하기가 훨씬 쉬워집니다.
커스텀 연산은 이 기본 측정이 끝난 뒤, 프로파일에서 실제로 뜨거운 블록이 보일 때만 손대는 순서가 좋겠습니다.
독립 라이브러리 쪽이 궁금하다면 ML Drift GitHub 저장소에서 Android용 OpenCL 시작 가이드부터 볼 수 있습니다.

마치며​

온디바이스 추론은 이제 실험 기능이 아니라, 영상과 사진과 생성형 기능이 실제로 도는 바닥이 되고 있습니다.
그 바닥의 GPU 층이 오픈소스로 열리고 예전 경로의 종료 방향까지 정해진 만큼, 관련 기능을 가진 팀이라면 한 번은 현재 스택을 점검해 볼 시점입니다.

Android CLI에 실기기 스트리밍이 붙었다 — 에이전트가 원격 단말에서 직접 확인하는 흐름

2026년 10월 2일 공개된 Android CLI 업데이트에 대해 설명해드리겠습니다.

배경​

Android CLI는 특정 AI 모델에 묶이지 않고, 다양한 코딩 에이전트와 함께 프로젝트 생성, 빌드, 테스트, 에뮬레이터 실행을 돕는 커맨드라인 도구입니다.
실기기에서만 재현되는 하드웨어/OS 이슈는 에뮬레이터로 놓치기 쉽지만, 필요한 단말이 항상 책상 위에 있는 것도 아닙니다.
이번 업데이트의 핵심은 두 가지입니다.
원격 실기기에 붙는 Device Streaming을 CLI에서 쓸 수 있게 됐고, 에이전트용 Android skills가 20개를 넘어섰습니다.
자세한 내용은 Android Developers Blog 원문에서 확인할 수 있습니다.

무엇이 달라졌는지​

Device Streaming을 에이전트가 직접 쓴다​

CLI를 통해 Android Device Streaming에 접속하면, 손에 없는 실기기라도 원격으로 앱을 올리고 로그와 트레이스를 수집하고 스크린샷까지 찍을 수 있습니다.
에이전트가 보안이 적용된 ADB over SSL 연결을 통해 원격 단말을 마치 USB로 연결한 것처럼 다룰 수 있게 됐습니다.
가능한 작업은 대략 다음과 같습니다.

  • 원격 단말 깨우기, 빌드 배포
  • 로그/트레이스 수집
  • 헤드리스 스크린샷 캡처
  • 터미널 안에서 기기 목록을 보고 어떤 단말을 쓸지 선택

코드를 고쳤으니 실제 단말에서 눌러보고 결과를 가져오는 흐름을, 사람이 중간에 끼지 않고도 시도할 수 있는 기반이 생긴 것입니다.

Android skills가 실무형으로 늘어났다​

Android skills는 SKILL.md 형태의 구조화된 지침 모음입니다.
모델의 학습 시점에 기대지 않고, 공식 가이드 기준으로 에이전트에게 맥락을 주입하는 방식입니다.
공식 skills 저장소에는 이제 20개가 넘는 스킬이 있고, 성격도 꽤 실무적입니다.

  • 제출 전 Play 정책 준수 점검(매니페스트, 권한, 타깃 SDK, 개인정보 고지)
  • Credential Manager 기반 복원 로그인(Restore Credentials) 구현
  • 암시적 인텐트 탈취 같은 인텐트 보안 점검
  • 프로파일러로 프레임 드롭 원인을 찾고 PerfettoSQL로 트레이스 질의
  • 구형 Camera1/Camera2 코드를 CameraX로 이전
  • Leanback 기반 TV 화면을 Compose for TV로 전환
  • Media3 재생 상태와 Cast 수신기 동기화
  • 테스트 전략(단위 테스트, Compose UI 테스트, 스크린샷 테스트) 세팅
  • R8 설정 감사

이번 글에서는 Wear OS용 Compose Material 3 스킬이 스포트라이트로 소개됐습니다.
둥근 화면, 회전 입력, 저전력, TransformingLazyColumn, AppScaffold/ScreenScaffold 같은 Wear 특유의 패턴을 에이전트가 놓치지 않게 잡아주는 스킬입니다.
FotMob 팀이 기존 Wear 앱의 리스트 여러 개를 이 패턴으로 옮기면서 레거시 래퍼와 회전/포커스 보일러플레이트를 걷어냈다는 사례도 함께 실렸습니다.

스킬 관리가 CLI에 붙었다​

스킬은 프로젝트마다, 또 에이전트마다 디렉터리가 달라서 관리가 번거로울 수 있는데, 흐름은 비교적 단순하게 정리돼 있습니다.

# Android CLI 설치 후 android-cli 스킬 세팅
android init

# 공식 스킬 목록 확인
android skills list

# 필요한 스킬만 프로젝트에 추가 (예: Wear Compose M3)
android skills add wear-compose-m3 --project=.

# 나중에 일괄 업데이트
android skills update --all

이 스킬들은 특정 환경 전용이 아니라는 점이 중요합니다.
Android Studio, 다른 코드 에디터, 서드파티 에이전트 환경에서도 같은 스킬을 재사용하는 방향으로 설계됐다고 합니다.

실무에서 주의할 점​

금융 앱처럼 단말 파편화와 보안 정책이 중요한 환경에서는, 에이전트가 실기기 결과를 직접 확인하는 흐름이 매력적입니다.
다만 바로 운영 파이프라인에 넣기 전에 확인할 것도 있습니다.

  • 권한과 보안 연결: 원격 단말 접속은 ADB over SSL 기반이라지만, 사내 네트워크 정책과 단말 접근 통제 범위 안에서 써야 합니다. 어떤 프로젝트를 링크하고, 어떤 로그가 외부로 나가는지 먼저 정리가 필요합니다.
  • 스킬은 정답지가 아니라 맥락입니다: 스킬이 있어도 최종 판단은 코드 리뷰와 테스트가 해야 합니다. 특히 Play 정책, 권한, 인텐트 보안처럼 심사/보안과 닿은 영역은 스킬 결과를 그대로 믿지 말고 체크리스트로 한 번 더 확인하는 것이 좋습니다.
  • 비용이 드는 반복 실행 주의: 단말 확인을 에이전트 루프에 넣으면, 사람이 할 때보다 훨씬 자주 실행하게 됩니다. 테스트 단말 시간, 네트워크, CI 분(minute)을 먹는 구조인지 먼저 작은 작업으로 측정해 보시기 바랍니다.

장점도 분명합니다.
지금까지는 에이전트가 코드만 보고 추측했다면, 이제는 실행 결과(로그, 스크린샷, 트레이스)를 근거로 다음 패치를 제안하는 루프를 만들 수 있습니다.
UI 회귀나 단말별 렌더링 차이를 잡는 데 특히 도움이 될 만합니다.
거창하게 시작하기보다 스킬 한 개와 단말 한 대로 작은 실험부터 해 보는 것이 좋습니다.

# 1) 지금 프로젝트에 테스트 전략 스킬을 붙여 현재 테스트 구성을 점검
android skills add testing-strategy --project=.

# 2) 에이전트에게 요청하는 프롬프트 예시
# "이 모듈의 Compose UI 테스트가 비어 있는 화면을 찾아서,
#  Device Streaming 단말에서 스크린샷까지 확인한 뒤 결과를 보고해줘"

스크린샷 테스트가 약한 화면부터 에이전트에게 맡겨보면, 사람이 놓친 레이아웃 깨짐을 얼마나 잡아내는지, 반대로 오탐이 얼마나 나오는지 금방 감이 옵니다.
그 다음에 R8 감사나 CameraX 이전처럼 범위가 넓은 스킬로 확장해도 늦지 않습니다.

마치며​

이번 업데이트의 방향은 에이전트가 코드를 더 잘 쓰는 것에서, 에이전트가 실행 결과까지 확인하며 일하는 것으로 한 발 나간 것입니다.
CLI와 skills를 한 번쯤 직접 만져보면서, 내 프로젝트에서 자동으로 확인할 수 있는 일이 무엇인지 목록을 만들어보는 것만으로도 가치가 있을 것입니다.

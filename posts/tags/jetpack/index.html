PhotoPicker 1.0.0-alpha03 — 임베디드 사진 선택기와 아티팩트 개명

2026년 10월 28일 · 약 3분
Way
Android Developer

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.
2026년 10월 21일에 공개된 PhotoPicker 1.0.0-alpha03에 대해 설명해드리겠습니다.

배경​

기존 사진 선택은 시스템 사진 선택기를 별도 화면으로 띄워서 결과를 돌려받는 방식이었습니다.
작성 중인 화면을 벗어났다가 돌아오는 흐름이라, 채팅이나 게시물 작성처럼 맥락이 중요한 화면에서는 흐름이 끊기기 쉬웠습니다.
임베디드 사진 선택기는 선택기 자체를 앱 화면 안에 직접 내장하는 방식입니다.
사용자는 작성 화면을 벗어나지 않고 사진을 고를 수 있습니다.

PhotoPicker 1.0.0-alpha03 살펴보기​

아티팩트 개명​

이번 버전에서 아티팩트 이름이 정리되었습니다.
photopicker는 photopicker-embedded로, Compose용 아티팩트는 photopicker-embedded-compose로, 테스트용 아티팩트는 photopicker-embedded-testing으로 바뀌었습니다.
패키지도 androidx.photopicker.embedded 계열로 함께 이동했습니다.
이름에 임베디드라는 목적이 드러나면서, 시스템 선택기용 계약과의 구분이 명확해졌습니다.

dependencies {
    implementation("androidx.photopicker:photopicker-embedded-compose:1.0.0-alpha03")
    implementation("androidx.photopicker:photopicker-embedded:1.0.0-alpha03")
}

위치 메타데이터 접근 요청​

사진 요청에 위치 메타데이터 접근을 함께 요청할 수 있게 되었습니다.
PickVisualMediaRequest에 setLocationMetadataAccessRequested가 추가되었고, 시스템 폴백 선택기용으로 위치 메타데이터 접근 요청을 전달하는 엑스트라도 추가되었습니다.
임베디드 선택기가 동작하지 않아 시스템 선택기로 떨어지는 경우에도, 같은 요청 의도가 이어지도록 만든 변경입니다.

// 사진 요청에 위치 메타데이터 접근을 함께 요청합니다
request.setLocationMetadataAccessRequested(true)

상태 리셋은 key 블록으로​

rememberEmbeddedPhotoPickerState에서 inputs 파라미터가 제거되었습니다.
입력 값이 바뀌었을 때 상태를 초기화하려면, 호출부를 key 블록으로 감싸는 방식으로 바뀌었습니다.
상태 초기화 조건이 호출부에서 눈에 보이게 되므로, 언제 리셋되는지 파악하기 쉬워졌습니다.

key(selectedAlbumId) {
    val state = rememberEmbeddedPhotoPickerState()
    EmbeddedPhotoPicker(state = state)
}

상태 API 정리​

EmbeddedPhotoPickerState도 정리되었습니다.
surfacePackage와 notifyVisibilityChanged가 노출되었고, onError 콜백이 추가되었습니다.
선택기 표면의 가시성 변화를 앱이 직접 통지할 수 있게 되었고, 실패 상황도 콜백으로 받아 처리할 수 있습니다.

최소 SDK와 호출 가능 버전​

두 라이브러리의 최소 SDK가 23으로 낮아졌습니다.
다만 관련 API 호출은 여전히 API 34부터 필요합니다.
낮은 버전 기기에서는 임베디드 선택기를 그대로 호출할 수 없으므로, 시스템 선택기로 떨어지는 분기를 함께 설계해야 합니다.

실무 관점​

알파 버전이므로 운영 화면에 바로 붙이기보다는, 프로필 이미지처럼 범위가 좁은 화면에서 먼저 검증하는 것이 안전합니다.
위치 메타데이터는 개인정보에 해당하므로, 요청하기 전에 왜 필요한지를 안내하고 동의를 받는 흐름이 먼저 필요합니다.
MTS처럼 금융 정보가 많은 앱에서는 사진 선택 화면과 계좌 정보 화면의 동선을 분리해 두는 편이 무난합니다.

마치며​

PhotoPicker 1.0.0-alpha03은 임베디드 선택기라는 방향을 유지하면서, 이름 정리와 위치 메타데이터 요청, 상태 리셋 방식까지 다듬은 업데이트입니다.
알파 단계에서 화면 내장 흐름을 먼저 검증해 두면, 정식 버전이 나왔을 때 적용 여부를 빠르게 판단할 수 있습니다.

Room 3.1.0-alpha03 — 손상 복구와 준비된 문장 캐시 설정

2026년 10월 28일 · 약 3분
Way
Android Developer

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.
2026년 10월 21일에 공개된 Room 3.1.0-alpha03에 대해 설명해드리겠습니다.

배경​

Room 3.0은 패키지를 androidx.room3으로 바꾸고 Kotlin Multiplatform을 중심으로 다시 설계된 버전입니다.
3.1.0-alpha01에서는 연결 풀 타임아웃 설정과 프로퍼티 중심 어노테이션, kotlin.uuid.Uuid 컨버터 같은 변경이 먼저 들어왔습니다.
이번 alpha03은 그 위에 데이터베이스 복구와 준비된 문장 캐시 설정이라는, 운영에서 직접 체감되는 두 가지 손잡이를 추가했습니다.

Room 3.1.0-alpha03 살펴보기​

손상된 데이터베이스 복구​

RoomDatabase.Builder에 allowDataLossOnRecovery()가 추가되었습니다.
데이터베이스 열기나 손상 복구에 실패했을 때, 데이터 손실을 감수하고 복구를 시도하도록 허용하는 설정입니다.
앱이 아예 실행되지 않는 상황보다는, 일부 데이터를 잃더라도 다시 동작하는 편이 나은 화면에서 의미가 있습니다.

// 데이터베이스 열기 실패 시 데이터 손실을 감수하고 복구를 시도합니다
builder.allowDataLossOnRecovery()

복구가 동작했다는 사실 자체가 데이터가 온전하지 않을 수 있다는 신호입니다.
복구 뒤에는 서버에서 다시 내려받을 수 있는지를 먼저 확인하는 흐름이 필요합니다.

준비된 문장 캐시 크기 설정​

setPreparedStatementCacheSize(maxCacheSize)가 RoomDatabase.Builder에 추가되었습니다.
연결마다 유지하는 준비된 문장 캐시의 크기를 직접 정하거나, 비활성화할 수 있게 되었습니다.
자주 반복되는 쿼리가 많은 화면에서는 캐시를 키우고, 메모리가 빠듯한 환경에서는 크기를 줄이는 식으로 조절할 수 있습니다.

// 연결당 준비된 문장 캐시의 크기를 직접 지정합니다
builder.setPreparedStatementCacheSize(64)

캐시를 무조건 크게 잡는 것이 정답은 아닙니다.
한 번만 실행되는 쿼리가 많은 앱에서는 캐시가 메모리만 차지하고 끝날 수 있습니다.

Kotlin 2.2 요구 사항​

3.1.0-alpha03부터 라이브러리는 Kotlin 2.2을 대상으로 빌드되고, kotlinc 2.2가 필요합니다.
프로젝트의 Kotlin 버전이 그보다 낮다면, Room을 올리기 전에 Kotlin부터 먼저 올려야 합니다.
버전 올림 순서를 바꾸면 빌드 오류의 원인을 찾기 어려워지므로, Kotlin과 Room의 변경은 따로 커밋하는 편이 안전합니다.

비결정적 절과 @Relation 재실행 수정​

ORDER BY RANDOM() LIMIT :count 같은 비결정적 절을 @Relation 쿼리와 함께 쓰면, 문장 리셋 시 쿼리가 다시 실행되어 관계 매핑이 실패하는 문제가 있었습니다.
이번 버전에서 해당 문제가 수정되었습니다.
랜덤 샘플링처럼 결과가 매번 달라지는 쿼리는, 관계 매핑과 섞기 전에 단독으로 먼저 검증하는 습관이 여전히 필요합니다.

프로퍼티 중심 어노테이션​

alpha01에서 이어지는 변경으로, @ColumnInfo와 @PrimaryKey, @Relation, @Embedded, @Ignore, @ColumnTypeConverters에 프로퍼티 대상이 추가되었습니다.
백킹 필드가 없는 프로퍼티도 엔티티 컬럼이나 쿼리 결과 컬럼으로 사용할 수 있게 되었습니다.
다만 사용할 수 있는 getter와, 사용할 수 있는 setter 또는 주 생성자 포함이 여전히 필요합니다.

@Entity
data class Holding(
    @PrimaryKey val symbol: String,
    @ColumnInfo val quantity: Int,
    val market: String,
)

실무 관점​

알파 버전이므로 운영 앱에 바로 적용하기보다는 별도 브랜치에서 먼저 검증하는 것이 안전합니다.
allowDataLossOnRecovery()는 이름 그대로 데이터 손실을 허용하는 설정이므로, 계좌나 주문 같은 핵심 데이터에는 적용하지 않는 것이 좋습니다.
캐시성 데이터나 서버에서 다시 내려받을 수 있는 데이터부터 적용 범위를 정하는 편이 무난합니다.
복구가 실제로 동작했는지는 로그로 남겨 두어야, 이후 고객 문의와 원인을 연결할 수 있습니다.

마치며​

Room 3.1.0-alpha03은 새 쿼리 기능보다, 데이터베이스가 망가졌을 때와 반복 쿼리가 많을 때를 다루는 실무적인 손잡이를 더한 업데이트입니다.
알파 단계에서 동작을 먼저 확인해 두면, 정식 버전이 나왔을 때 적용 범위를 빠르게 정할 수 있습니다.

Palette 1.1.0 — 이미지 대표 색 추출과 palette-ktx 통합

2026년 10월 27일 · 약 3분
Way
Android Developer

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.
2026년 10월 21일에 공개된 Palette 1.1.0과 이미지 대표 색 추출 방법에 대해 설명해드리겠습니다.

배경​

Palette는 이미지에서 대표 색상을 추출하는 Jetpack 라이브러리입니다.
배너 이미지나 종목 대표 이미지에서 배경색과 텍스트 색을 뽑아 화면 테마에 맞추는 용도로 사용됩니다.
1.0.0 이후 오랜만에 공개된 1.1.0은 기능 추가보다 정리 성격이 강합니다.
공식 Palette 릴리스 노트를 기준으로 변경 사항과 사용법을 정리합니다.

Palette 살펴보기​

대표 색 추출 방식​

Palette는 비트맵의 픽셀을 양자화해 색상 군집을 만든 뒤 대표 스와치를 계산합니다.
동기 생성은 메인 스레드를 막을 수 있으므로, 실무에서는 비동기 생성이나 백그라운드 스레드에서 실행하는 것이 안전합니다.
추출할 색상 개수는 빌더에서 조절할 수 있으며, 기본값은 16개입니다.

val palette = Palette.from(bitmap)
    .maximumColorCount(24)
    .generate()

스와치 종류​

추출 결과는 용도별로 나뉜 스와치로 제공됩니다.
getVibrantSwatch는 생동감 있는 대표 색, getMutedSwatch는 차분한 대표 색을 돌려줍니다.
각각 밝은 버전과 어두운 버전이 있으며, getDominantSwatch는 이미지에서 가장 큰 비중을 차지하는 색을 돌려줍니다.
스와치는 null을 돌려줄 수 있으므로, 사용할 때는 반드시 대체 색을 함께 준비해야 합니다.

val vibrant = palette.getVibrantSwatch()
val muted = palette.getMutedSwatch()
val dominant = palette.getDominantSwatch()

val backgroundRgb = vibrant?.rgb ?: muted?.rgb ?: 0xFF1A1A1A.toInt()
val titleTextRgb = vibrant?.titleTextColor ?: 0xFFFFFFFF.toInt()

Compose에서 사용하기​

Palette는 뷰 시스템 시절 라이브러리라 Compose 전용 API를 제공하지 않습니다.
비트맵을 받아 백그라운드에서 생성한 뒤, 결과 색을 Compose의 Color로 변환해 상태로 보관하는 방식이 일반적입니다.
이미지마다 한 번씩만 생성하고 결과를 캐시하면, 스크롤 화면에서도 반복 계산을 피할 수 있습니다.

@Composable
fun rememberPaletteColor(bitmap: Bitmap?): Color {
    var themeColor by remember { mutableStateOf(Color.Transparent) }
    LaunchedEffect(bitmap) {
        if (bitmap == null) return@LaunchedEffect
        val palette = withContext(Dispatchers.Default) {
            Palette.from(bitmap).generate()
        }
        val swatch = palette.getVibrantSwatch() ?: palette.getDominantSwatch()
        if (swatch != null) {
            themeColor = Color(swatch.rgb)
        }
    }
    return themeColor
}

1.1.0에서 달라진 것​

1.1.0의 가장 큰 변경은 JSpecify nullability 어노테이션 채택입니다.
Kotlin에서 엄격한 null 검사를 적용하려면 컴파일러 인자를 함께 설정해야 합니다.
또 하나의 변경은 palette-ktx 통합입니다.
Kotlin 확장 함수가 모두 메인 아티팩트로 들어갔고, palette-ktx는 호환 유지를 위한 빈 아티팩트로 남았습니다.
신규 프로젝트에서는 palette만 의존하면 되며, 기존 프로젝트에서는 palette-ktx 의존성을 정리할 수 있습니다.

dependencies {
    implementation("androidx.palette:palette:1.1.0")
}
kotlinOptions {
    freeCompilerArgs += listOf(
        "-Xjspecify-annotations=strict",
        "-Xtype-enhancement-improvements-strict-mode",
    )
}

실무 관점​

이미지에서 뽑은 색을 그대로 텍스트 배경에 쓰면 가독성이 깨질 수 있습니다.
스와치가 제공하는 제목 텍스트 색과 본문 텍스트 색을 함께 사용해야 대비가 유지됩니다.
서버 이미지 색이 매번 달라지는 화면에서는, 색 추출 실패 시 기본 테마로 떨어지는 분기를 먼저 만들어 두는 것이 안전합니다.
MTS처럼 정보 밀도가 높은 화면에서는 전체 테마를 바꾸기보다, 배너 카드 내부 강조색 정도로 범위를 제한하는 편이 무난합니다.

마치며​

Palette 1.1.0은 새 기능보다 nullability 정리와 아티팩트 통합에 초점이 맞춰져 있습니다.
기존 코드를 크게 바꾸지 않고 의존성만 정리할 수 있는 안정적인 업데이트입니다.

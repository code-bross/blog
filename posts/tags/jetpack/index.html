Core-telecom 1.1.0으로 VoIP 통화 안정화하기

2026년 11월 11일 · 약 4분
Way
Android Developer

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.

2026년 11월 4일에 안정화 버전으로 공개된 Core-telecom 1.1.0에 대해 설명해드리겠습니다.

배경​

VoIP 통화를 앱에 넣으려면 플랫폼 Telecom 프레임워크와 직접 연동해야 합니다.
Android 14부터는 트랜잭션 기반의 새 API가 기본이 되었고, 그 이전에는 ConnectionService 기반의 기존 API를 써야 했습니다.
두 가지 구현을 함께 지원하려다 보면 버전별 분기가 늘어나고, 오디오 라우팅 같은 기기별 동작 차이까지 직접 처리해야 합니다.
Core-telecom은 이 두 가지 구현을 하나의 API로 묶어 주는 Jetpack 라이브러리입니다.
1.1.0은 마이그레이션을 단계적으로 진행할 수 있는 장치를 추가하고, 통화 확장 기능을 안정화 API로 승격했습니다.

Core-telecom 1.1.0 살펴보기​

단계적 전환을 위한 롤아웃 제어​

CallsManager#registerAppWithTelecom에 선택 매개변수 backwardsCompatSdkLevel이 추가되었습니다.
기본값은 SDK 33이며, 이 값까지는 ConnectionService 기반 구현을 쓰고 그 위에서는 트랜잭션 API를 사용합니다.
기존에 플랫폼 ConnectionService를 직접 쓰던 앱은 익숙한 구현을 유지한 채 라이브러리를 먼저 도입할 수 있습니다.
이후 상한 값을 단계적으로 낮추면서 새 API로 전환하면 됩니다.
호출 관리 코드는 바꾸지 않아도 됩니다.

val callsManager = CallsManager(context)

// SDK 34까지는 ConnectionService 기반으로 유지하고,
// SDK 35부터 트랜잭션 API를 사용합니다.
callsManager.registerAppWithTelecom(
    capabilities = CallsManager.CAPABILITY_SUPPORTS_VIDEO_CALLING,
    backwardsCompatSdkLevel = 34
)

통화 확장 기능 안정화​

addCallWithExtensions와 InCallServiceCompat#connectExtensions, LocalCallSilenceExtension, ParticipantExtension, MeetingSummaryRemote가 안정화 API가 되었습니다.
기존에 필요했던 @ExperimentalAppActions 옵트인이 제거되었습니다.
통화 상태를 Android Auto나 Wear OS 같은 원격 화면과 동기화하는 기능을 정식 API로 쓸 수 있습니다.
LocalCallSilenceExtension에는 원격 음소거 제어 여부를 동적으로 바꾸는 updateCanUserUpdateSilence와 콜백 onCanUserUpdateSilence가 추가되었습니다.
수동적 참관자나 진행자에게 음소거된 회의 참가자처럼, 원격 화면에서 마이크 제어를 막아야 하는 경우에 사용합니다.

통화별 통화 기록 제외​

CallAttributesCompat에 선택 속성 isLogExcluded가 추가되었습니다.
시스템 통화 기록에 참여하도록 설정한 앱이 특정 통화만 기록에서 제외할 수 있습니다.
Android 16 QPR 이상에서 동작합니다.
VoIP 통화는 기본적으로 시스템 통화 기록에 남지 않으므로, 먼저 기록 참여를 설정한 앱에만 해당합니다.

val attributes = baseAttributes.copy(isLogExcluded = true)

프리미엄 네트워크 슬라이싱 제외​

CallsManager.CAPABILITY_OPT_OUT_OF_PREMIUM_NETWORK가 추가되었습니다.
음성·영상 통화 중에 플랫폼이 자동으로 프리미엄 네트워크 슬라이스를 요청하는 동작을 거부할 수 있습니다.
registerAppWithTelecom에 플래그를 전달해 설정합니다.

callsManager.registerAppWithTelecom(
    CallsManager.CAPABILITY_OPT_OUT_OF_PREMIUM_NETWORK
)

통화 중 음성·영상 전환 관찰​

CallControlScope#callTypeFlow와 CallControlScope#requestCallType이 추가되었습니다.
통화 중 오디오와 비디오 상태 변화를 흐름으로 관찰할 수 있습니다.
통화 종류를 세션 중간에 올리거나 내릴 수도 있습니다.

// 음성에서 영상으로 바뀌는 과정을 관찰합니다.
callControlScope.callTypeFlow()
    .onEach { callType ->
        // 바뀐 통화 종류에 맞게 화면을 갱신합니다.
    }
    .launchIn(scope)

// 영상 통화로 전환을 요청합니다.
callControlScope.requestCallType(CallAttributesCompat.CALL_TYPE_VIDEO_CALL)

끊김 없는 통화 설정과 오디오 라우팅​

통화 설정 경로가 빨라졌습니다.
오디오 엔드포인트 확인과 블루투스 안정화 과정이 addCall의 동기 경로에서 분리되어, CallControlScope 진입까지 최대 2초의 지연이 사라졌습니다.
겹치는 통화 설정 요청은 CallException으로 즉시 거부되어, 플랫폼 TransactionManager의 5초 타임아웃과 직렬 큐 교착을 막습니다.
오디오 라우팅 문제도 여러 건이 수정되었습니다.
SDK 34부터 36에서 음성 전용 수신 통화가 영상 통화로 잘못 인식되어 스피커폰으로 나가는 문제, 영상 통화 시작 시 유선 헤드셋이 연결되어 있는데도 스피커로 바뀌는 문제 등이 포함됩니다.
사용자가 미리 고른 오디오 엔드포인트도 통화 시작 시 기본값에 덮어쓰이지 않습니다.
BLUETOOTH_CONNECT 권한이 없어도 웨어러블 기기를 식별하는 대체 방법도 들어갔습니다.
SDK 38부터는 DisconnectCause.ERROR로 통화를 끊을 수 있고, 이전 버전에서는 자동으로 DisconnectCause.LOCAL로 바뀌어 버전 검사가 필요 없습니다.

실무 관점​

VoIP 기능이 있는 MTS 앱이라면 1.1.0은 바로 검토할 만한 버전입니다.
기존 ConnectionService 연동이 있다면 backwardsCompatSdkLevel로 상한을 높게 잡고 라이브러리를 먼저 도입하는 것이 안전합니다.
통화 설정 지연과 오디오 라우팅 수정은 사용자 체감과 직결되므로, 실기기에서 수신·발신·블루투스 전환을 직접 확인하는 것이 좋습니다.
isLogExcluded는 Android 16 QPR 이상에서만 동작하므로, 구형 단말에서는 아무런 효과가 없다는 점을 알아두어야 합니다.
네트워크 슬라이싱 제외는 통신사 과금과 연결될 수 있으니, 적용 전에 정책을 먼저 확인하는 것이 좋습니다.

마치며​

1.1.0은 단계적 전환 장치와 안정화된 통화 확장 기능으로 마이그레이션 부담을 낮췄습니다.
통화 설정과 오디오 라우팅의 고질적인 문제도 함께 정리되어, VoIP 품질이 한층 안정되었습니다.

Appstate Statestore와 Transform 살펴보기 — UI 밖에서 Compose 상태를 다루는 새 라이브러리

2026년 11월 8일 · 약 3분
Way
Android Developer

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.
2026년 11월 4일에 공개된 Appstate Statestore와 Appstate Transform 1.0.0-alpha02에 대해 설명해드리겠습니다.
두 라이브러리 모두 Compose 런타임을 기반으로 하며, UI 밖에서 상태를 다루기 위한 기능을 제공합니다.

배경​

Compose의 상태는 지금까지 화면과 강하게 묶여 있었습니다.
mutableStateOf로 만든 상태는 컴포저블 안에서 읽고 쓰는 것이 자연스러웠고, 화면을 벗어난 앱 레이어에서 같은 상태를 다루려면 별도의 장치가 필요했습니다.
앱 전역 설정이나 백그라운드에서 갱신되는 값을 Compose 상태로 유지하면서 영속화까지 하려면 ViewModel과 DataStore를 직접 엮어야 했습니다.
Appstate는 이 지점을 겨냥한 새 Jetpack 라이브러리입니다.
스냅샷 상태를 앱 레이어로 끌어올리는 StateStore와, UI 밖에서 컴포지션을 실행하는 Transform으로 구성됩니다.

Appstate 살펴보기​

StateStore로 상태를 앱 레이어에 두기​

StateStore는 Compose 스냅샷 상태를 감싸는 래퍼입니다.
상태를 Application 같은 앱 레이어로 호이스팅하면 화면 생명주기와 무관하게 값을 유지할 수 있습니다.
statestore-datastore 아티팩트를 함께 쓰면 syncToDataStore로 상태를 DataStore에 영속화할 수 있습니다.

class MyApplication : Application() {
    val stateStore = StateStore()

    private val scope = CoroutineScope(SupervisorJob() + Dispatchers.Default)

    override fun onCreate() {
        super.onCreate()
        scope.launch {
            launch {
                try {
                    stateStore.syncToDataStore(
                        dataStoreFile("settings").absolutePath,
                        this
                    )
                } catch (e: Exception) {
                    e.printStackTrace()
                }
            }
        }
    }
}

동기화는 자식 코루틴에서 실행해 바깥 스코프를 막지 않는 구조입니다.
예외가 발생해도 앱 시작이 중단되지 않도록 try catch로 감싸는 형태가 공식 예시에 포함되어 있습니다.

Transform으로 UI 밖에서 컴포지션 실행하기​

Transform은 컴포지션을 UI 밖에서 실행할 수 있게 합니다.
transform 헬퍼 함수에 초기값과 스코프를 넘기면, 소스 상태가 바뀔 때마다 람다가 다시 실행되어 결과를 갱신합니다.

val scope = CoroutineScope(SupervisorJob() + Dispatchers.Default)
var sourceState by mutableStateOf(0)

val state = transform(initialValue = 0, scope = scope) {
    sourceState
}

TransformScope를 직접 다루는 방식도 있습니다.
launchTransform으로 변환을 시작하고 run으로 실행하며, 사용이 끝나면 dispose로 정리합니다.

val transformScope = TransformScope()
var sourceState by mutableStateOf(0)

val state = transformScope.launchTransform(initialValue = 0) {
    sourceState
}

scope.launch {
    try {
        transformScope.run()
    } finally {
        state.dispose()
    }
}

테스트를 위한 transformTest API도 함께 제공됩니다.
transform-testing 아티팩트를 쓰면 테스트 디스패처와 백그라운드 스코프를 지정해 상태 변화를 단계별로 검증할 수 있습니다.

@Test
fun testStateUpdate() = transformTest {
    var sourceState by mutableStateOf(0)
    val state = transform(
        initialValue = 0, scope = backgroundScope, dispatcher = testDispatcher
    ) {
        sourceState
    }

    assertThat(state.value).isEqualTo(0)
    sourceState = 1
    advance()
    assertThat(state.value).isEqualTo(1)
}

의존성 추가하기​

두 라이브러리는 멀티플랫폼 아티팩트로 제공됩니다.
Android, 데스크톱, iOS, JS, Wasm 등 각 플랫폼용 아티팩트가 나뉘어 있습니다.

dependencies {
    implementation("androidx.appstate.statestore:statestore:1.0.0-alpha02")
    implementation("androidx.appstate.statestore:statestore-datastore:1.0.0-alpha02")
    implementation("androidx.appstate.transform:transform:1.0.0-alpha02")
}

실무 관점​

아직 알파 단계라 API가 바뀌거나 사라질 수 있습니다.
운영 중인 MTS 앱에 바로 도입하기보다는, 상태 영속화와 백그라운드 상태 갱신이 필요한 화면부터 작은 범위로 검증하는 것이 안전합니다.
syncToDataStore는 코루틴 스코프와 예외 처리를 함께 설계해야 하며, 앱 시작 경로에서 동기화 실패가 전체 시작을 막지 않는지 확인이 필요합니다.
Transform은 컴포지션을 UI 밖으로 꺼내는 만큼, 변환 람다가 무거운 작업을 하지 않는지, 정리 시점이 명확한지 살펴야 합니다.

마치며​

Appstate는 Compose 상태를 화면 밖으로 꺼내는 방향을 제시합니다.
상태를 앱 레이어에 두고 영속화까지 연결하는 구조가 정식 버전에서 어떻게 다듬어지는지 지켜볼 만합니다.

CameraX 1.7.0-rc02 살펴보기 — Kotlin DSL 빌더와 미러 모드

2026년 11월 8일 · 약 3분
Way
Android Developer

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.
2026년 11월 4일에 공개된 CameraX 1.7.0-rc02에 대해 설명해드리겠습니다.
1.7.0은 릴리스 후보 단계에 들어섰으며, Kotlin DSL 빌더와 Camera2Interop 정리가 포함되어 있습니다.

배경​

CameraX는 지금까지 빌더 패턴으로 유스케이스를 만들었습니다.
Preview.Builder와 ImageCapture.Builder에 설정을 하나씩 쌓는 방식은 익숙했지만, 코드가 길어지고 설정 위치를 찾기 어려웠습니다.
Camera2의 세부 설정을 직접 다뤄야 할 때는 레거시 Interop API를 거쳐야 했고, 미러 모드는 실험적 애너테이션이 붙은 상태였습니다.
1.7.0은 이 세 지점을 함께 정리합니다.

CameraX 1.7.0 살펴보기​

Kotlin DSL 빌더로 유스케이스 만들기​

1.7.0-alpha03부터 preview, imageCapture, imageAnalysis, videoCapture DSL 빌더가 추가되었습니다.
빌더 객체를 직접 다루지 않고, 람다 안에서 설정을 모아 유스케이스를 만들 수 있습니다.

val preview = preview {
    // Preview 설정을 여기에 작성합니다.
}

val imageCapture = imageCapture {
    // ImageCapture 설정을 여기에 작성합니다.
}

cameraProvider.bindToLifecycle(
    lifecycleOwner, cameraSelector, preview, imageCapture
)

기존 빌더 방식과 비교하면 설정 코드가 한곳에 모이고, 유스케이스 생성 의도가 더 분명해집니다.

Camera2Interop 정리하기​

레거시 Camera2Interop API가 정리되었습니다.
Camera2Interop.Extender와 Camera2CameraControl, Camera2CameraInfo, CaptureRequestOptions는 deprecated 되었고, 대신 설정자 팩토리 메서드와 Kotlin 확장 함수를 사용합니다.
camera2Interop 확장 블록을 DSL 빌더 안에서 직접 쓸 수 있습니다.

val preview = preview {
    camera2Interop {
        // Camera2 설정을 직접 지정합니다.
    }
}

Camera2Interop에는 forUseCase와 forImageCapture, forSessionConfig, forCameraControl 팩토리 메서드가 추가되었습니다.
CameraInfo.cameraId와 CameraInfo.cameraCharacteristics 확장 프로퍼티로 Camera2의 카메라 ID와 특성을 바로 조회할 수 있으며, String.toCameraSelector()로 문자열에서 셀렉터를 만들 수 있습니다.
CameraControl.applyCamera2InteropAsync 확장 함수도 함께 제공됩니다.

미러 모드와 물리 카메라​

Preview.setMirrorMode와 VideoCapture.setMirrorMode가 정식 API가 되었습니다.
기존에 붙어 있던 ExperimentalMirrorMode 애너테이션은 제거되었습니다.

손상된 데이터베이스 복구​

// 데이터베이스 열기 실패 시 데이터 손실을 감수하고 복구를 시도합니다
builder.allowDataLossOnRecovery()

자주 반복되는 쿼리가 많은 화면에서는 캐시를 키우고, 메모리가 빠듯한 환경에서는 크기를 줄이는 식으로 조절할 수 있습니다.

// 연결당 준비된 문장 캐시의 크기를 직접 지정합니다
builder.setPreparedStatementCacheSize(64)

캐시를 무조건 크게 잡는 것이 정답은 아닙니다.
한 번만 실행되는 쿼리가 많은 앱에서는 캐시가 메모리만 차지하고 끝날 수 있습니다.

ORDER BY RANDOM() LIMIT :count 같은 비결정적 절을 @Relation 쿼리와 함께 쓰면, 문장 리셋 시 쿼리가 다시 실행되어 관계 매핑이 실패하는 문제가 있었습니다.

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.
2026년 10월 21일에 공개된 Palette 1.1.0과 이미지 대표 색 추출 방법에 대해 설명해드리겠습니다.

배경​

Palette는 이미지에서 대표 색상을 추출하는 Jetpack 라이브러리입니다.
배너 이미지나 종목 대표 이미지에서 배경색과 텍스트 색을 뽑아 화면 테마에 맞추는 용도로 사용됩니다.

공식 Palette 릴리스 노트를 기준으로 변경 사항과 사용법을 정리합니다.

Palette 살펴보기​

대표 색 추출 방식​

Palette는 비트맵의 픽셀을 양자화해 색상 군집을 만든 뒤 대표 스와치를 계산합니다.
동기 생성은 메인 스레드를 막을 수 있으므로, 실무에서는 비동기 생성이나 백그라운드 스레드에서 실행하는 것이 안전합니다.
추출할 색상 개수는 빌더에서 조절할 수 있으며, 기본값은 16개입니다.

val palette = Palette.from(bitmap)
    .maximumColorCount(24)
    .generate()

스와치 종류​

추출 결과는 용도별로 나뉜 스와치로 제공됩니다.
getVibrantSwatch는 생동감 있는 대표 색, getMutedSwatch는 차분한 대표 색을 돌려줍니다.
각각 밝은 버전과 어두운 버전이 있으며, getDominantSwatch는 이미지에서 가장 큰 비중을 차지하는 색을 돌려줍니다.
스와치는 null을 돌려줄 수 있으므로, 사용할 때는 반드시 대체 색을 함께 준비해야 합니다.

val vibrant = palette.getVibrantSwatch()
val muted = palette.getMutedSwatch()
val dominant = palette.getDominantSwatch()

val backgroundRgb = vibrant?.rgb ?: muted?.rgb ?: 0xFF1A1A1A.toInt()
val titleTextRgb = vibrant?.titleTextColor ?: 0xFFFFFFFF.toInt()

Compose에서 사용하기​

Palette는 뷰 시스템 시절 라이브러리라 Compose 전용 API를 제공하지 않습니다.
비트맵을 받아 백그라운드에서 생성한 뒤, 결과 색을 Compose의 Color로 변환해 상태로 보관하는 방식이 일반적입니다.
이미지마다 한 번씩만 생성하고 결과를 캐시하면, 스크롤 화면에서도 반복 계산을 피할 수 있습니다.

@Composable
fun rememberPaletteColor(bitmap: Bitmap?): Color {
    var themeColor by remember { mutableStateOf(Color.Transparent) }
    LaunchedEffect(bitmap) {
        if (bitmap == null) return@LaunchedEffect
        val palette = withContext(Dispatchers.Default) {
            Palette.from(bitmap).generate()
        }
        val swatch = palette.getVibrantSwatch() ?: palette.getDominantSwatch()
        if (swatch != null) {
            themeColor = Color(swatch.rgb)
        }
    }
    return themeColor
}

1.1.0에서 달라진 것​

1.1.0의 가장 큰 변경은 JSpecify nullability 어노테이션 채택입니다.
Kotlin에서 엄격한 null 검사를 적용하려면 컴파일러 인자를 함께 설정해야 합니다.
또 하나의 변경은 palette-ktx 통합입니다.
Kotlin 확장 함수가 모두 메인 아티팩트로 들어갔고, palette-ktx는 호환 유지를 위한 빈 아티팩트로 남았습니다.
신규 프로젝트에서는 palette만 의존하면 되며, 기존 프로젝트에서는 palette-ktx 의존성을 정리할 수 있습니다.

dependencies {
    implementation("androidx.palette:palette:1.1.0")
}
kotlinOptions {
    freeCompilerArgs += listOf(
        "-Xjspecify-annotations=strict",
        "-Xtype-enhancement-improvements-strict-mode",
    )
}

실무 관점​

이미지에서 뽑은 색을 그대로 텍스트 배경에 쓰면 가독성이 깨질 수 있습니다.
스와치가 제공하는 제목 텍스트 색과 본문 텍스트 색을 함께 사용해야 대비가 유지됩니다.
서버 이미지 색이 매번 달라지는 화면에서는, 색 추출 실패 시 기본 테마로 떨어지는 분기를 먼저 만들어 두는 것이 안전합니다.
MTS처럼 정보 밀도가 높은 화면에서는 전체 테마를 바꾸기보다, 배너 카드 내부 강조색 정도로 범위를 제한하는 편이 무난합니다.

마치며​

Palette 1.1.0은 새 기능보다 nullability 정리와 아티팩트 통합에 초점이 맞춰져 있습니다.
기존 코드를 크게 바꾸지 않고 의존성만 정리할 수 있는 안정적인 업데이트입니다.

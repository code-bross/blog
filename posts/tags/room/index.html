SQL LIKE '%검색어%'가 앱을 느리게 한다 — Room @Fts4로 검색 9.4배 빠르게

2026년 10월 15일 · 약 4분
Way
Android Developer

안녕하세요, 한국투자증권 한투 앱 개발자 way입니다.

오프라인 검색(종목 메모, 공지 목록, 최근 본 상품 등)을 로컬 DB에 LIKE '%쿼리%'로 구현한 경험, 다들 한 번쯤 있을 겁니다. 개발 중에는 더미 데이터 몇십 건으로 0.1초도 안 걸려서 "된다"고 넘어가기 쉽습니다. 10월 ProAndroidDev에 올라온 글 "Scaling Android Search: Room @Fts4 vs SQL LIKE"가 이 안일함을 숫자로 깨줍니다. 5,000건 기준으로 LIKE는 63.8ms, FTS4는 6.8ms — 9.4배 차이입니다.

핵심 요약​

  • 검색어 앞에도 %를 붙이는 순간(LIKE '%검색어%'), SQLite의 B-Tree 인덱스는 완전히 무력화되고 전체 테이블 스캔으로 떨어집니다.
  • 글쓴이의 실측에서 2,000건만 돼도 LIKE는 약 30ms로 60Hz 프레임 예산(16.6ms)을 훌쩍 넘겼고, 5,000건에서는 FTS4 대비 9.4배 느렸습니다.
  • Room의 @Fts4 + contentEntity 패턴을 쓰면 데이터를 중복 저장하지 않고 역인덱스(inverted index)만 별도 가상 테이블에 유지할 수 있습니다. 트리거가 원본 테이블의 INSERT/UPDATE/DELETE를 인덱스에 자동 반영합니다.

왜 LIKE가 느린지​

B-Tree 인덱스는 "접두사"를 알 때만 쓸 수 있습니다. WHERE sender LIKE 'alice%'는 인덱스를 타지만, 실제 검색 UI는 중간 매칭이 필요하니 WHERE body LIKE '%architecture%' 형태가 됩니다. 선행 와일드카드가 들어가는 순간 옵티마이저는 인덱스를 버리고 모든 행을 바이트 단위로 훑습니다. 2,000통의 이메일에 본문 평균 1,500단어라면, 키스트로크 한 번에 최대 300만 단어를 문자 단위로 비교하는 셈입니다.

게다가 LIKE는 "멍청합니다". 단어 경계를 모릅니다("cat" 검색에 "catalog"·"scatter"까지 걸립니다). 어간 추출이 안 됩니다("optimize"로 "optimized"를 못 찾습니다). 관련도 순위가 없습니다(제목 매칭과 본문 4번째 문단 매칭이 동급입니다).

FTS4가 다른 이유: 역인덱스​

FTS4는 쿼리 시점이 아니라 INSERT 시점에 일을 합니다. 토크나이저가 텍스트를 단어로 쪼개고(토큰화), 대소문자를 정규화하고, "단어 → 문서 ID 목록"이라는 역인덱스를 만듭니다.

Token        | DocIDs (Posting List)
architecture | [1, 14, 108, 492]
benchmark    | [1, 7, 22, 108, 305]

MATCH 'benchmark*' 같은 쿼리가 들어오면 FTS4는 토큰 딕셔너리에서 단어를 찾아 docid 목록을 바로 뽑아냅니다. 관계없는 텍스트 한 바이트도 안 읽습니다. 행이 100개든 10만 개든 조회는 밀리초 단위로 끝납니다.

실무 영향 / 주의점​

  • LIKE는 프로토타입용입니다. 사람 말이 들어가는 텍스트 검색(메시지·문서·메모·상품 카탈로그)이면, 데이터가 수천 건으로 자라기 전에 FTS로 옮기는 게 맞습니다.
  • 쓰기 비용은 있습니다. FTS 테이블은 INSERT/UPDATE 때마다 인덱스를 갱신하니, 쓰기가 빈번하고 읽기가 드문 워크로드라면 이득이 줄어듭니다. 쓰기/읽기 비율을 보고 판단하세요.
  • 쿼리 위생이 필수입니다. MATCH에 사용자 입력을 그대로 넣으면 따옴표 같은 특수문자가 쿼리 문법을 깨뜨립니다. 입력에서 따옴표를 제거하고, as-you-type 검색을 위해 토큰마다 접미사 *를 붙이는 sanitize 함수를 따로 두세요.
  • 한국어는 토크나이저를 고르세요. FTS4 기본 토크나이저(simple)는 공백 기준이라 한국어 조사 붙은 단어("검색어를")는 토큰 하나가 됩니다. 영어 위주 앱이 아니라면 unicode61 계열 토크나이저로 바꾸거나, 형태소 분석이 필요하면 별도 토크나이저를 검토해야 합니다. Porter stemmer도 영어용이라는 점을 잊지 마세요.

내 코드에서는 이렇게 적용할 생각입니다​

원본 테이블은 그대로 두고, 검색용 FTS 가상 테이블을 contentEntity로 붙이는 패턴이 표준입니다.

@Entity(tableName = "notices")
data class NoticeEntity(
    @PrimaryKey(autoGenerate = true) val id: Long = 0,
    val title: String,
    val body: String,
    val pinned: Boolean = false,
)

@Entity(tableName = "notices_fts")
@Fts4(contentEntity = NoticeEntity::class)
data class NoticeFtsEntity(
    val title: String,
    val body: String,
)

contentEntity를 지정하면 FTS 테이블은 역인덱스 구조만 갖고, 실제 텍스트는 원본 notices 테이블에서 가져옵니다. 데이터 중복이 없습니다. Room이 AFTER INSERT/UPDATE/DELETE 트리거를 자동 생성해서, 원본에 쓰기만 하면 인덱스가 따라옵니다. DAO에서는 docid로 조인해 MATCH를 씁니다.

@Dao
interface NoticeDao {
    @Query("""
        SELECT notices.* FROM notices
        JOIN notices_fts ON notices.id = notices_fts.docid
        WHERE notices_fts MATCH :query
        ORDER BY notices.pinned DESC
    """)
    suspend fun searchNoticesFts(query: String): List<NoticeEntity>
}

as-you-type 검색이라면 입력 sanitize를 잊지 마세요.

// "삼성 전자" -> "삼성* 전자*" : 토큰별 접두사 매칭으로 자동완성 느낌의 검색
fun sanitizeFtsQuery(raw: String): String =
    raw.replace("\"", "").replace("'", "").trim()
        .split("\\s+".toRegex())
        .filter { it.isNotEmpty() }
        .joinToString(" ") { "$it*" }

기존 테이블에 FTS를 붙이는 건 DB 버전 업 + AutoMigration 또는 수동 마이그레이션으로 처리합니다. 가상 테이블은 원본 스키마 변경과 독립적이니, 마이그레이션 부담도 크지 않습니다.

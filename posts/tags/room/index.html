Room 3.1.0-alpha03 — 손상 복구와 준비된 문장 캐시 설정

2026년 10월 28일 · 약 3분
Way
Android Developer

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.
2026년 10월 21일에 공개된 Room 3.1.0-alpha03에 대해 설명해드리겠습니다.

배경​

Room 3.0은 패키지를 androidx.room3으로 바꾸고 Kotlin Multiplatform을 중심으로 다시 설계된 버전입니다.
3.1.0-alpha01에서는 연결 풀 타임아웃 설정과 프로퍼티 중심 어노테이션, kotlin.uuid.Uuid 컨버터 같은 변경이 먼저 들어왔습니다.
이번 alpha03은 그 위에 데이터베이스 복구와 준비된 문장 캐시 설정이라는, 운영에서 직접 체감되는 두 가지 손잡이를 추가했습니다.

Room 3.1.0-alpha03 살펴보기​

손상된 데이터베이스 복구​

RoomDatabase.Builder에 allowDataLossOnRecovery()가 추가되었습니다.
데이터베이스 열기나 손상 복구에 실패했을 때, 데이터 손실을 감수하고 복구를 시도하도록 허용하는 설정입니다.
앱이 아예 실행되지 않는 상황보다는, 일부 데이터를 잃더라도 다시 동작하는 편이 나은 화면에서 의미가 있습니다.

// 데이터베이스 열기 실패 시 데이터 손실을 감수하고 복구를 시도합니다
builder.allowDataLossOnRecovery()

복구가 동작했다는 사실 자체가 데이터가 온전하지 않을 수 있다는 신호입니다.
복구 뒤에는 서버에서 다시 내려받을 수 있는지를 먼저 확인하는 흐름이 필요합니다.

준비된 문장 캐시 크기 설정​

setPreparedStatementCacheSize(maxCacheSize)가 RoomDatabase.Builder에 추가되었습니다.
연결마다 유지하는 준비된 문장 캐시의 크기를 직접 정하거나, 비활성화할 수 있게 되었습니다.
자주 반복되는 쿼리가 많은 화면에서는 캐시를 키우고, 메모리가 빠듯한 환경에서는 크기를 줄이는 식으로 조절할 수 있습니다.

// 연결당 준비된 문장 캐시의 크기를 직접 지정합니다
builder.setPreparedStatementCacheSize(64)

캐시를 무조건 크게 잡는 것이 정답은 아닙니다.
한 번만 실행되는 쿼리가 많은 앱에서는 캐시가 메모리만 차지하고 끝날 수 있습니다.

Kotlin 2.2 요구 사항​

3.1.0-alpha03부터 라이브러리는 Kotlin 2.2을 대상으로 빌드되고, kotlinc 2.2가 필요합니다.
프로젝트의 Kotlin 버전이 그보다 낮다면, Room을 올리기 전에 Kotlin부터 먼저 올려야 합니다.
버전 올림 순서를 바꾸면 빌드 오류의 원인을 찾기 어려워지므로, Kotlin과 Room의 변경은 따로 커밋하는 편이 안전합니다.

비결정적 절과 @Relation 재실행 수정​

ORDER BY RANDOM() LIMIT :count 같은 비결정적 절을 @Relation 쿼리와 함께 쓰면, 문장 리셋 시 쿼리가 다시 실행되어 관계 매핑이 실패하는 문제가 있었습니다.
이번 버전에서 해당 문제가 수정되었습니다.
랜덤 샘플링처럼 결과가 매번 달라지는 쿼리는, 관계 매핑과 섞기 전에 단독으로 먼저 검증하는 습관이 여전히 필요합니다.

프로퍼티 중심 어노테이션​

alpha01에서 이어지는 변경으로, @ColumnInfo와 @PrimaryKey, @Relation, @Embedded, @Ignore, @ColumnTypeConverters에 프로퍼티 대상이 추가되었습니다.
백킹 필드가 없는 프로퍼티도 엔티티 컬럼이나 쿼리 결과 컬럼으로 사용할 수 있게 되었습니다.
다만 사용할 수 있는 getter와, 사용할 수 있는 setter 또는 주 생성자 포함이 여전히 필요합니다.

@Entity
data class Holding(
    @PrimaryKey val symbol: String,
    @ColumnInfo val quantity: Int,
    val market: String,
)

실무 관점​

알파 버전이므로 운영 앱에 바로 적용하기보다는 별도 브랜치에서 먼저 검증하는 것이 안전합니다.
allowDataLossOnRecovery()는 이름 그대로 데이터 손실을 허용하는 설정이므로, 계좌나 주문 같은 핵심 데이터에는 적용하지 않는 것이 좋습니다.
캐시성 데이터나 서버에서 다시 내려받을 수 있는 데이터부터 적용 범위를 정하는 편이 무난합니다.
복구가 실제로 동작했는지는 로그로 남겨 두어야, 이후 고객 문의와 원인을 연결할 수 있습니다.

마치며​

Room 3.1.0-alpha03은 새 쿼리 기능보다, 데이터베이스가 망가졌을 때와 반복 쿼리가 많을 때를 다루는 실무적인 손잡이를 더한 업데이트입니다.
알파 단계에서 동작을 먼저 확인해 두면, 정식 버전이 나왔을 때 적용 범위를 빠르게 정할 수 있습니다.

SQL LIKE '%검색어%'가 앱을 느리게 한다 — Room @Fts4로 검색 9.4배 빠르게

2026년 10월 15일 · 약 4분
Way
Android Developer

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.
최근 ProAndroidDev에 소개된 Room @Fts4 기반 검색 최적화 사례에 대해 설명해드리겠습니다.

배경​

종목 메모, 공지 목록, 최근 본 상품 같은 오프라인 검색을 로컬 DB의 LIKE '%쿼리%'로 구현하는 경우가 많습니다.
개발 중에는 더미 데이터가 몇십 건 수준이라 0.1초도 걸리지 않아 그대로 넘어가기 쉽습니다.
Scaling Android Search: Room @Fts4 vs SQL LIKE에서는 이 방식을 실측 수치로 비교합니다.
5,000건 기준으로 LIKE는 63.8ms, FTS4는 6.8ms가 걸려 9.4배의 차이가 났습니다.

Room @Fts4 살펴보기​

왜 LIKE가 느린지​

  • B-Tree 인덱스는 접두사를 알 때만 사용할 수 있습니다.
  • WHERE sender LIKE 'alice%'는 인덱스를 타지만, 실제 검색 UI는 중간 매칭이 필요해 WHERE body LIKE '%architecture%' 형태가 됩니다.
  • 검색어 앞에 %를 붙이는 순간 인덱스는 무력화되고 전체 테이블 스캔으로 떨어집니다.
  • 실측에서는 2,000건만 돼도 LIKE가 약 30ms로 60Hz 프레임 예산인 16.6ms를 훌쩍 넘겼습니다.
  • 또한 LIKE는 단어 경계를 모르고("cat" 검색에 "catalog", "scatter"까지 걸립니다), 어간 추출이 안 되며("optimize"로 "optimized"를 못 찾습니다), 관련도 순위도 없습니다.

FTS4와 역인덱스​

  • FTS4는 쿼리 시점이 아니라 INSERT 시점에 일을 합니다.
  • 토크나이저가 텍스트를 단어로 쪼개고 대소문자를 정규화해, "단어 → 문서 ID 목록" 형태의 역인덱스를 만듭니다.
Token        | DocIDs (Posting List)
architecture | [1, 14, 108, 492]
benchmark    | [1, 7, 22, 108, 305]
  • MATCH 'benchmark*' 같은 쿼리가 들어오면 토큰 딕셔너리에서 단어를 찾아 docid 목록을 바로 뽑아냅니다.
  • 관계없는 텍스트는 한 바이트도 읽지 않으므로, 행이 100개든 10만 개든 조회는 밀리초 단위로 끝납니다.

contentEntity 패턴​

  • 원본 테이블은 그대로 두고, 검색용 FTS 가상 테이블을 contentEntity로 붙이는 패턴이 표준입니다.
@Entity(tableName = "notices")
data class NoticeEntity(
    @PrimaryKey(autoGenerate = true) val id: Long = 0,
    val title: String,
    val body: String,
    val pinned: Boolean = false,
)

@Entity(tableName = "notices_fts")
@Fts4(contentEntity = NoticeEntity::class)
data class NoticeFtsEntity(
    val title: String,
    val body: String,
)
  • contentEntity를 지정하면 FTS 테이블은 역인덱스 구조만 갖고, 실제 텍스트는 원본 notices 테이블에서 가져오므로 데이터 중복이 없습니다.
  • Room이 AFTER INSERT/UPDATE/DELETE 트리거를 자동 생성해서, 원본에 쓰기만 하면 인덱스가 자동으로 반영됩니다.
  • DAO에서는 docid로 조인해 MATCH를 사용합니다.
@Dao
interface NoticeDao {
    @Query("""
        SELECT notices.* FROM notices
        JOIN notices_fts ON notices.id = notices_fts.docid
        WHERE notices_fts MATCH :query
        ORDER BY notices.pinned DESC
    """)
    suspend fun searchNoticesFts(query: String): List<NoticeEntity>
}
  • 기존 테이블에 FTS를 붙이는 작업은 DB 버전 업과 AutoMigration 또는 수동 마이그레이션으로 처리합니다.
  • 가상 테이블은 원본 스키마 변경과 독립적이라 마이그레이션 부담도 크지 않습니다.

실무에서 주의할 점​

  • LIKE는 프로토타입용입니다. 메시지, 문서, 메모, 상품 카탈로그처럼 사람이 입력하는 텍스트 검색이라면 데이터가 수천 건으로 자라기 전에 FTS로 옮기는 것이 맞습니다.
  • 쓰기 비용은 있습니다. FTS 테이블은 INSERT와 UPDATE 때마다 인덱스를 갱신하므로, 쓰기가 빈번하고 읽기가 드문 워크로드라면 이득이 줄어듭니다.
  • 쿼리 위생이 필수입니다. MATCH에 사용자 입력을 그대로 넣으면 따옴표 같은 특수문자가 쿼리 문법을 깨뜨립니다. 입력에서 따옴표를 제거하고, as-you-type 검색을 위해 토큰마다 접미사 *를 붙이는 sanitize 함수를 따로 두어야 합니다.
// "삼성 전자" -> "삼성* 전자*" : 토큰별 접두사 매칭으로 자동완성 느낌의 검색
fun sanitizeFtsQuery(raw: String): String =
    raw.replace("\"", "").replace("'", "").trim()
        .split("\\s+".toRegex())
        .filter { it.isNotEmpty() }
        .joinToString(" ") { "$it*" }
  • 한국어는 토크나이저를 골라야 합니다. FTS4 기본 토크나이저(simple)는 공백 기준이라 한국어 조사가 붙은 단어("검색어를")는 토큰 하나가 됩니다. 영어 위주 앱이 아니라면 unicode61 계열 토크나이저로 바꾸거나, 형태소 분석이 필요하면 별도 토크나이저를 검토해야 합니다. Porter stemmer도 영어용이라는 점을 잊지 마시기 바랍니다.

마치며​

검색 속도는 데이터가 쌓인 뒤에 손대면 마이그레이션 비용까지 함께 커집니다.
검색 대상이 텍스트이고 건수가 늘어날 구조라면, 처음부터 @Fts4와 contentEntity 패턴으로 시작하는 편이 유지보수에 유리합니다.

안드로이드 개발자에게 열린 Gemini 4 Argon — 자가 복구 빌드와 AGSL 셰이더

2026년 10월 15일 · 약 4분
Way
Android Developer

안녕하세요, 한국투자증권 한투 앱 개발자 way입니다.

구글이 10월 13일 Android Developers Blog에서 최신 플래그십 모델 Gemini 4 Argon을 안드로이드 개발 표면에 개방한다고 발표했습니다. 지난주에 다뤘던 Android CLI/디바이스 스트리밍, BYOA(원하는 에이전트 쓰기) 흐름의 연장선이라 함께 보면 좋습니다. 모델 자체보다 "에이전트가 빌드를 스스로 고치고, 셰이더까지 짜준다"는 부분에 주목해서 정리합니다.

핵심 요약​

  • 접근 경로 3가지: ① Google Antigravity(AI Ultra 구독, 데스크톱 앱·CLI·Android Studio Canary 내) ② Android Studio(Gemini API 유료 티어) ③ Google AI Studio(Playground/Build, AI Ultra 또는 Gemini API 유료 티어)
  • 클라이언트 인앱 AI: Firebase AI Logic 경유로 Gemini API 유료 티어 개발자가 앱 안에서 Gemini 4 Argon을 직접 쓸 수 있습니다.
  • Self-Healing Build Loops: 빌드 실패 시 Antigravity 하네스가 Gradle 데몬·Kotlin 컴파일러 로그를 모델에 그대로 피드백하고, 근본 원인을 반복 진단해 수정안을 냅니다. 편집 라운드마다 가설을 일관되게 유지하고 AST 인지를 활용해 표면 증상이 아닌 진짜 원인에 도달하도록 훈련됐다는 설명입니다.
  • Compose 셰이더 생성: AGSL(Android Graphics Shading Language)을 Compose Modifier.graphicsLayer나 셰이더 브러시에 직접 작성합니다. 120fps Compose 애니메이션과 함께 도는 경량 GPU 셰이더(프로스트드 글래스·동적 조명·파문 등)를 벡터·렌더링 수학까지 처리해 뽑아낸다고 합니다.
  • 인트로 가격 적용은 2026년 11월 30일까지입니다.

무엇이 달라졌는지​

지금까지 에이전트 코딩은 "코드 자동완성의 연장"에 가까웠습니다. 이번 발표가 말하는 방향은 클로즈드 루프 실행입니다. 빌드 → 실패 로그 수집 → 원인 진단 → 수정 → 재빌드를 사람이 아니라 하네스+모델이 돌리는 구조죠. Gradle 데몬과 Kotlin 컴파일러의 에러 스트림을 그대로 먹는다는 점이 핵심입니다. 로그를 읽는 사람이 아니라 빌드 시스템을 읽는 에이전트인 셈입니다.

UI 쪽도 눈에 띕니다. Compose 셰이더는 실무에서 진입 장벽이 높은 영역인데(AGSL 문법 + 렌더링 수학 + 성능 예산), 모델이 이를 "프로덕션급"으로 뽑아낸다는 주장입니다. 120fps 애니메이션과 공존하는 경량 셰이더라는 표현에서 타깃이 명확합니다. 검증은 직접 해봐야겠지만, 셰이더 브러시까지 에이전트에게 맡기는 워크플로가 생긴다는 건 디자인 시스템 팀에겐 의미 있는 변화입니다.

터미널 에이전트 연결은 공식 Android CLI 플러그인이 맡습니다. android init 한 줄이면 어떤 터미널 에이전트든 로컬 Android 도구와 연결되고, Antigravity라면 플러그인 설치로 끝납니다.

실무 영향 / 주의점​

  • 빌드 로그가 곧 에이전트의 입력입니다. Self-Healing이 위력을 내려면 빌드 실패 로그가 잘 읽혀야 합니다. 난독화된 멀티모듈 빌드에서 에이전트가 원인에 닿으려면, 지금부터라도 Gradle 빌드 스크립트와 에러 메시지를 사람이 읽을 수 있게 정리해 두는 게 이득입니다.
  • 비용 구조를 확인하세요. Antigravity는 AI Ultra 구독 전제, API 경로는 Gemini API 유료 티어 전제입니다. 인트로 가격(2026-11-30까지) 이후 정가를 모르면 팀 도입 판단이 어렵습니다. 도입 전에 Console에서 실제 과금을 먼저 확인하세요.
  • 셰이더 코드는 리뷰가 필수입니다. "프로덕션급"이라는 표현은 모델 벤더의 주장일 뿐, AGSL 셰이더는 GPU·디바이스별로 동작이 달라 실기 검증 없이는 못 씁니다. 에이전트가 짠 셰이더는 초안으로 보고 프레임 타임·배터리부터 재세요.
  • Firebase AI Logic 경로는 인앱 기능용입니다. 개발 워크플로(빌드 복구·코드 생성)와 앱 내 AI 기능(사용자 대면)은 접근 경로가 다릅니다. 팀에서 둘을 혼동하면 과금·권한 설계가 꼬입니다.

내 코드에서는 이렇게 적용할 생각입니다​

일단 터미널 에이전트에 Android CLI를 붙이는 것부터 시작해 볼 만합니다. 발표에서 안내한 명령 그대로입니다.

# 어떤 터미널 에이전트에서든: 로컬 Android 도구와 연결
android init

# Antigravity를 쓴다면: 공식 Android CLI 플러그인 설치
agy plugin install android-cli-plugin

Firebase AI Logic으로 인앱에 붙일 때는 모델 선택만 새 모델로 바꾸는 구조라, 기존 Vertex AI / Gemini Developer API 연동 코드의 모델명 교체 수준에서 검토가 가능합니다. 정확한 모델 식별자는 Firebase AI Logic 문서를 확인하고, 릴리스 직후에는 SDK 업데이트가 필요할 수 있습니다.

샘플 프로젝트도 함께 공개됐으니, 에이전트 워크플로를 팀에 도입하기 전에 퀵스타트로 감을 잡는 게 좋습니다.

Compose에서 Flow 수집의 진화 — collectAsState()에서 collectAsStateWithLifecycle()까지

2026년 10월 14일 · 약 2분
Way
Android Developer

안녕하세요, 한국투자증권 한투 앱 개발자 way입니다.

10월 ProAndroidDev에 올라온 글 "The Evolution of Flow Collection in Jetpack Compose"가, Compose에서 Flow를 수집하는 API가 어떻게 진화해 왔는지 깔끔하게 정리했습니다. 익숙한 내용이지만, 실무에서 여전히 collectAsState()를 관성으로 쓰는 코드가 많아서 이번 기회에 정리해 봅니다.

핵심 요약​

  • Compose 1.0(2021년 7월)의 collectAsState()는 Flow를 State로 바꾸는 가장 단순한 방법이지만, 라이프사이클을 모른다
  • 액티비티가 백그라운드로 가도 composition이 살아 있으면 수집이 계속된다
  • 지금의 정답은 collectAsStateWithLifecycle() — STARTED 미만이면 수집을 멈추고, 돌아오면 재개한다

무엇이 달라졌는지​

1단계: collectAsState() (Compose 1.0)​

val uiState by viewModel.uiState.collectAsState()

새 값이 emit될 때마다 Compose가 state를 업데이트하고 관련 UI를 리컴포즈합니다. 코드는 간단하지만, 중요한 차이가 하나 있습니다. collectAsState()는 라이프사이클이 STARTED 아래로 내려가도 수집을 자동으로 멈추지 않습니다. composition이 살아 있는 한 백그라운드에서도 계속 수집합니다.

2단계: collectAsStateWithLifecycle()​

lifecycle-runtime-compose가 제공하는 API로, 라이프사이클을 인식합니다. 기본 minActiveState는 STARTED라서, 화면이 보이지 않으면 수집을 멈췄다가 다시 보이면 재개합니다.

val uiState by viewModel.uiState.collectAsStateWithLifecycle()

3단계: 일회성 이벤트는 다른 패턴으로​

상태가 아니라 이벤트(네비게이션, 스낵바 등)를 소비할 때는 collectAsState* 계열이 아니라 LaunchedEffect + repeatOnLifecycle 조합이 맞습니다.

val lifecycle = LocalLifecycleOwner.current.lifecycle
LaunchedEffect(lifecycle) {
    lifecycle.repeatOnLifecycle(Lifecycle.State.STARTED) {
        viewModel.events.collect { event ->
            // 네비게이션, 스낵바 등 일회성 이벤트 처리
        }
    }
}

실무 영향 / 주의점​

  • 뷰모델의 uiState 같은 StateFlow는 collectAsStateWithLifecycle()를 기본값으로 두는 게 안전합니다
  • collectAsState()는 upstream이 가벼우면 문제가 없지만, 소켓·위치·센서처럼 비싼 작업을 하는 Flow면 백그라운드에서 리소스를 낭비합니다
  • minActiveState 파라미터로 기준을 RESUMED까지 올릴 수도 있으니, 화면 요구사항에 맞게 조정하세요
  • SharedFlow 기반 일회성 이벤트에 collectAsState를 붙이는 실수는 여전히 흔합니다. 이벤트면 수집 패턴을 바꾸세요

Remote Compose 1.0.0-alpha21 — 10월 AndroidX 릴리스에서 본 서버 구동 UI의 현재 위치

2026년 10월 12일 · 약 5분
Way
Android Developer

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.
2026년 10월 7일, AndroidX 정기 릴리스 배치가 나왔습니다. 그중에서도 눈에 띄는 건 remote-compose 1.0.0-alpha21과 compose.remote.foundation 1.0.0-alpha04입니다. Remote Compose는 서버 구동 UI(Server-Driven UI)를 위한 Jetpack 라이브러리인데, 릴리스 노트를 읽다 보면 "에이전트가 만든 UI를 앱 업데이트 없이 내려받아 그리는" 흐름이 점점 현실화되고 있다는 느낌을 받습니다. 이번 글에서는 Remote Compose 알파21의 변경점을 중심으로, 같이 묶여 나온 10월 배치의 실무 포인트를 정리합니다.

핵심 요약​

  • Remote Compose 1.0.0-alpha21: 라이트/다크 테마 인식 색상, 텍스트 크기 측정 API, RemoteDocumentPreview 설정 확장, 원형 텍스트 렌더링 지원, DEFLATE 압축 문서 로딩 등.
  • 새로 등장한 compose.remote.foundation 1.0.0-alpha04까지 합치면, "서버에서 UI 문서를 내려받아 그대로 그린다"는 그림이 Jetpack 레벨에서 정비되는 중입니다.
  • 같은 배치의 Compose 1.13.0-beta01은 이제 Kotlin 2.2를 타깃으로 하며 kotlinc 2.2를 요구합니다. 베타를 올릴 계획이라면 컴파일러 버전도 같이 봐야 합니다.
  • appfunctions 1.0.0-alpha13은 API 리네임이 있습니다. AppFunction 어노테이션이 AppFunctionDeclaration으로 바뀌었으니, 알파를 실험 중인 프로젝트는 릴리스 노트를 확인하고 올리세요.
  • collection 1.7.0 스테이블에는 ScatterMap 성능 개선과 원시 타입 리스트 정렬/이진 탐색 추가가 있습니다.

무엇이 달라졌는지​

Remote Compose 1.0.0-alpha21​

테마 인식 원격 색상

RemoteColor.Companion에 createThemedRemoteColor가 추가됐습니다. 서버에서 내려받은 문서가 클라이언트의 라이트/다크 테마를 따라 색상을 바꿀 수 있게 되는 겁니다. 서버 구동 UI에서 가장 자주 요구되는 "다크 모드 대응"을 플레이어 쪽이 해결해 주니, 문서 생성 로직에서 분기할 필요가 줄어듭니다.

텍스트 측정 API

RemoteTextMeasurer와 rememberRemoteTextMeasurer가 새로 들어왔습니다. Remote Compose 문서 안에서 텍스트의 실제 렌더링 크기를 잴 수 있게 된 것으로, 문서 생성 시점에 텍스트 길이에 따라 레이아웃을 조정해야 하는 경우(예: 배지, 동적 라벨) 유용합니다. Float.rsp/RemoteFloat.rsp 확장 프로퍼티도 추가돼서 Sp 단위의 RemoteTextUnit을 리터럴이나 동적 표현식에서 바로 만들 수 있습니다.

문서 생성·미리보기 개선

  • RemoteDocumentPreview에 profile 파라미터가 생겼습니다. 문서 버퍼를 팽창시키기 전에 설정을 조정할 수 있어, 테스트·디버깅 환경에서 문서 생성을 세밀하게 제어할 수 있습니다.
  • 플레이어와 테스트 프로파일이 DrawTextOnCircle을 지원합니다. 원형 경로에 텍스트를 그리는 연출이 이제 원격 문서에서도 깨지지 않습니다.
  • DEFLATE로 압축된 문서를 플레이어가 로드할 수 있게 됐습니다. 문서 크기가 크다면 전송량을 줄이는 방향으로 설계할 여지가 생깁니다.
  • captureSingleRemoteDocument/captureRemoteDocument의 라이프사이클과 스냅샷 처리가 다져졌고, 수집 속도가 리컴포지션을 따라가지 못할 때 업데이트가 조용히 누락되던 버그도 수정됐습니다. 서버 구동 UI에서 "가끔 화면이 안 바뀌는" 식의 간헐적 이슈가 줄어들 것으로 보입니다.
  • 커스텀 진입/종료 가시성 애니메이션 지원, 스프링 애니메이션의 스냅·범위 이탈 버그 수정 등 렌더링 품질 쪽도 여러 건 잡혔습니다.

compose.remote.foundation 1.0.0-alpha04

같은 배치에 androidx.compose.remote.foundation의 새 알파가 같이 나왔습니다. 의존성은 다음과 같이 선언합니다.

dependencies {
    implementation("androidx.compose.remote.foundation:foundation:1.0.0-alpha04")
}

같이 나온 것들​

  • Compose 1.13.0-beta01 (animation/foundation/material/runtime): 이번 배치부터 라이브러리들이 Kotlin 2.2를 타깃으로 하고 kotlinc 2.2를 요구합니다. 베타를 올릴 때는 Kotlin 버전을 2.2 이상으로 올려야 컴파일이 됩니다.
  • appfunctions 1.0.0-alpha13: @AppFunction → @AppFunctionDeclaration, ObserveAppFunctionsEvent → AppFunctionsChangeEvent로 리네임됐고, 접근 레벨 제한을 위한 @AppFunctionAccessLevel이 추가됐습니다. 에이전트·Gemini 시대의 앱 기능 노출 인터페이스라 실험 중이라면 이름 바뀐 것만 확인하면 됩니다.
  • collection 1.7.0 (스테이블): toOrderedScatterSet() 확장(빈 소스에선 할당 없는 싱글턴 반환), ScatterMap.getOrPut() 최적화, Float 키 해시 충돌 개선, 원시 타입 리스트(IntList/LongList 등)에 sortWith/sortBy/binarySearch 추가. 퍼포먼스에 민감한 데이터 구조를 쓰는 팀은 별도 변경 없이 이득을 볼 수 있습니다.
  • benchmark 1.6.0-alpha01: :lockClocks 태스크가 root 없이도 고정 성능 모드를 쓸 수 있게 돼서, 더 많은 실기기에서 안정적인 마이크로벤치마크가 가능합니다. 히프 프로파일링용 MemoryProfilingConfig도 추가됐습니다.

실무 영향 / 주의점​

  • Remote Compose는 아직 알파입니다. API가 바뀔 수 있다는 전제로 실험·프로토타입 수준에서 접근하는 게 맞습니다. 다만 테마 인식, 텍스트 측정, 압축 문서 로딩처럼 "운영에 쓰려면 꼭 있어야 할" 기능들이 차례로 들어오고 있어서, 방향성 자체는 꽤 진지하게 보입니다.
  • 에이전트 시대의 SDUI: 최근 Android CLI와 에이전트 스킬 흐름과 맞물려, "에이전트가 생성한 UI를 어떻게 앱에 그릴 것인가"가 실무 질문이 되고 있습니다. Remote Compose는 그 답 중 하나입니다. 당장 도입하지 않더라도 개념과 플레이어 구조는 한 번 훑어둘 만합니다.
  • Compose 1.13 베타 + Kotlin 2.2: 컴파일러 버전 요구사항이 같이 올라간 릴리스라서, 버전만 올렸다가 빌드가 깨지는 경우가 생길 수 있습니다. 베타를 쓸 거면 libs.versions.toml의 Kotlin 버전도 함께 올립니다.
  • appfunctions 리네임: 알파 실험 중이라면 컴파일 에러가 나는 게 정상이니, 이름만 바꿔 주면 됩니다.

내 코드에서 이렇게 써볼 생각입니다​

당장은 프로덕션 도입이 아니라 관측 모드입니다. SDK 36 대응 같은 급한 일에 밀려 손이 안 가겠지만, 스프린트 사이에 작은 실험 프로젝트 하나로 Remote Compose 플레이어에 문서 하나 띄워 보는 건 해볼 생각입니다. 관전 포인트는 두 가지입니다.

  1. 서버에서 보낸 문서가 다크 테마에서 깨지지 않는지 (createThemedRemoteColor 사용)
  2. 텍스트 길이 가변적인 배지 UI를 RemoteTextMeasurer로 제대로 그릴 수 있는지
// gradle/libs.versions.toml
[versions]
androidxRemoteCompose = "1.0.0-alpha21"
composeRemoteFoundation = "1.0.0-alpha04"

에이전트가 UI를 만드는 시대가 오고 있는데, "어떻게 그릴 것인가"는 여전히 앱 개발자의 몫입니다. Remote Compose가 그 몫을 나눠 가질 후보 중 하나라는 점에서, 이번 릴리스는 지켜볼 가치가 있습니다.

마치며​

10월 AndroidX 배치는 "UI를 코드가 아니라 문서로 다루는" 쪽으로 축이 이동하고 있음을 보여줍니다. Remote Compose 알파21의 변경점 대부분이 렌더링 품질과 운영 편의(테마, 압축, 측정)에 집중돼 있다는 점이 그 신호입니다. 바로 쓸 필요는 없지만, 다음에 SDUI를 고민할 때 선택지에 넣어두기 좋은 타이밍입니다.

Compose 1.13.0-beta01 정리 — Dp.Unspecified가 리컴포지션을 막던 버그 수정

2026년 10월 8일 · 약 2분
Way
Android Developer

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.
2026년 10월 7일, Compose 1.13.0-beta01이 릴리스됐습니다. stable 채널의 최신은 1.12.1입니다.
runtime 기준으로 실무에 닿는 변경만 추려서 정리합니다.

Kotlin 2.2 타깃으로 상향​

1.13부터 Compose 라이브러리는 Kotlin 2.2를 타깃으로 빌드되고, kotlinc 2.2가 필요합니다.
버전 카탈로그에서 Compose BOM만 올리는 습관이 있다면, Kotlin 플러그인 버전이 뒤처진 모듈에서 먼저 걸릴 수 있으니 함께 확인하는 게 좋습니다.

Dp.Unspecified를 받는 컴포저블이 스킵되지 않던 버그​

개인적으로 이번 베타에서 가장 반가운 수정입니다.
Float.NaN이나 Double.NaN을 인자로 받는 @Composable은 인자가 그대로여도 스킵되지 않고 매번 리컴포지션되는 버그가 있었습니다. Dp.Unspecified가 내부적으로 Float.NaN 기반이라, 선택적 간격이나 크기를 Dp.Unspecified 기본값으로 받는 공용 컴포넌트가 조용히 리컴포지션 비용을 치르고 있었던 셈입니다.

// 이런 공용 컴포넌트가 인자 변화가 없어도 스킵되지 않을 수 있었다
@Composable
fun PriceRow(
    label: String,
    topPadding: Dp = Dp.Unspecified
) { /* ... */ }

사내 디자인 시스템처럼 공용 컴포넌트에 Dp.Unspecified 기본값이 흔한 코드베이스라면, 1.13 stable이 나올 때 체감 성능이 좋아질 수 있습니다.

computedStateOf 계산 블록은 읽기 전용으로 강제​

computedStateOf의 계산 블록 안에서 상태에 쓰면 이제 IllegalStateException이 발생합니다.
기존에 계산 블록 안에서 쓰기까지 하던 코드가 있었다면 런타임에서 바로 드러나니, 베타를 올리는 모듈부터 확인이 필요합니다.

그 외 버그 픽스​

  • CompositionObserver가 컴포지션 패스마다 한 번만 해석되고, 교체는 다음 패스부터 적용됩니다. movable content 삽입 시에도 begin/end 콜백이 보고됩니다.
  • movableContent 이동 시 래퍼 그룹 슬롯이 남아 있던 LinkComposer 메모리 누수를 고쳤습니다.
  • lifecycle-runtime 의존성이 2.10.0으로 올라갔습니다. 번들된 lifecycle lint 검사는 AGP 9.5.0-alpha04 이상과 맞물려 있으니, AGP 베타 채널을 쓰는 프로젝트는 같이 보는 게 좋습니다.
  • ComposeTracer를 메인 스레드 밖에서도 쓸 수 있게 됐습니다.

올릴까 말까​

1.12.1 stable은 1.12.0에서 변경이 없는 버전이라, 운영 앱은 stable 유지가 무난합니다.
베타는 성능 검증이 필요한 화면(공용 컴포넌트를 많이 쓰는 MTS 특성상 리컴포지션 이슈가 체감되는 곳) 위주로 먼저 올려 보고, 앱 전체 확대는 stable 이후가 안전해 보입니다.

AppState StateStore 첫 알파, Compose 상태를 앱 계층으로 끌어올리기

2026년 10월 30일 · 약 2분
Way
Android Developer

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.
2026년 10월 28일에 첫 알파로 공개된 AppState StateStore에 대해 설명해드리겠습니다.

배경​

Compose 상태는 보통 화면이나 ViewModel 안에 머무릅니다.
앱 전역에서 공유해야 하는 상태는 계층을 옮길 때마다 전달 코드가 늘어납니다.
상태를 앱 계층으로 끌어올리면 공유와 저장이 한곳에서 관리됩니다.
StateStore는 이 역할을 맡기 위해 새로 공개된 라이브러리입니다.

StateStore 살펴보기​

Compose 런타임 기반의 상태 저장소​

StateStore는 Compose 런타임을 기반으로 동작합니다.
스냅샷 상태를 앱 계층으로 끌어올려 커스텀 연동을 제공하는 래퍼입니다.
화면이 사라져도 상태의 수명을 앱 수준에서 유지할 수 있습니다.

DataStore 연동으로 상태 유지하기​

statestore-datastore 아티팩트는 상태 영속성을 제공합니다.
syncToDataStore로 스냅샷 상태를 DataStore 파일과 동기화할 수 있습니다.
앱을 다시 시작해도 이전 상태를 복원할 수 있습니다.

class MyApplication : Application() {
    val stateStore = StateStore()
    private val scope = CoroutineScope(SupervisorJob() + Dispatchers.Default)

    override fun onCreate() {
        super.onCreate()
        scope.launch {
            launch {
                try {
                    stateStore.syncToDataStore(
                        dataStoreFile("settings").absolutePath,
                        this
                    )
                } catch (e: Exception) {
                    e.printStackTrace()
                }
            }
        }
    }
}

의존성 추가하기​

Android 타깃 기준 의존성은 다음과 같습니다.

dependencies {
    implementation("androidx.appstate.statestore:statestore:1.0.0-alpha01")
    implementation("androidx.appstate.statestore:statestore-datastore:1.0.0-alpha01")
}

함께 공개된 Transform​

같은 날짜에 appstate-transform 아티팩트도 첫 알파로 공개되었습니다.
이 글에서는 StateStore의 개념과 저장 연동에 집중합니다.
Transform의 구체적인 활용은 후속 릴리스 노트에서 확인한 뒤 다루는 것이 좋습니다.

실무 관점​

첫 알파 단계이므로 운영 코드에 바로 도입하지 않는 것이 좋습니다.
상태를 앱 계층으로 올리면 수명과 동기화 시점을 직접 설계해야 합니다.
동기화 중 예외가 나면 상태가 저장되지 않으므로 실패 처리 경로를 함께 둡니다.
MTS처럼 세션과 설정 상태가 많은 앱에서는 저장 단위부터 나누는 것이 안전합니다.

마치며​

StateStore는 Compose 상태를 앱 계층에서 관리하는 새로운 선택지입니다.
DataStore 연동까지 함께 보면 상태 공유와 영속성을 한 구조로 정리할 수 있습니다.

PhotoPicker 1.0.0-alpha03 — 임베디드 사진 선택기와 아티팩트 개명

Android Developer

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.
2026년 10월 21일에 공개된 PhotoPicker 1.0.0-alpha03에 대해 설명해드리겠습니다.

배경​

기존 사진 선택은 시스템 사진 선택기를 별도 화면으로 띄워서 결과를 돌려받는 방식이었습니다.
작성 중인 화면을 벗어났다가 돌아오는 흐름이라, 채팅이나 게시물 작성처럼 맥락이 중요한 화면에서는 흐름이 끊기기 쉬웠습니다.
임베디드 사진 선택기는 선택기 자체를 앱 화면 안에 직접 내장하는 방식입니다.
사용자는 작성 화면을 벗어나지 않고 사진을 고를 수 있습니다.

PhotoPicker 1.0.0-alpha03 살펴보기​

아티팩트 개명​

이번 버전에서 아티팩트 이름이 정리되었습니다.
photopicker는 photopicker-embedded로, Compose용 아티팩트는 photopicker-embedded-compose로, 테스트용 아티팩트는 photopicker-embedded-testing으로 바뀌었습니다.
패키지도 androidx.photopicker.embedded 계열로 함께 이동했습니다.
이름에 임베디드라는 목적이 드러나면서, 시스템 선택기용 계약과의 구분이 명확해졌습니다.

dependencies {
    implementation("androidx.photopicker:photopicker-embedded-compose:1.0.0-alpha03")
    implementation("androidx.photopicker:photopicker-embedded:1.0.0-alpha03")
}

위치 메타데이터 접근 요청​

사진 요청에 위치 메타데이터 접근을 함께 요청할 수 있게 되었습니다.
PickVisualMediaRequest에 setLocationMetadataAccessRequested가 추가되었고, 시스템 폴백 선택기용으로 위치 메타데이터 접근 요청을 전달하는 엑스트라도 추가되었습니다.
임베디드 선택기가 동작하지 않아 시스템 선택기로 떨어지는 경우에도, 같은 요청 의도가 이어지도록 만든 변경입니다.

// 사진 요청에 위치 메타데이터 접근을 함께 요청합니다
request.setLocationMetadataAccessRequested(true)

상태 리셋은 key 블록으로​

rememberEmbeddedPhotoPickerState에서 inputs 파라미터가 제거되었습니다.
입력 값이 바뀌었을 때 상태를 초기화하려면, 호출부를 key 블록으로 감싸는 방식으로 바뀌었습니다.
상태 초기화 조건이 호출부에서 눈에 보이게 되므로, 언제 리셋되는지 파악하기 쉬워졌습니다.

key(selectedAlbumId) {
    val state = rememberEmbeddedPhotoPickerState()
    EmbeddedPhotoPicker(state = state)
}

상태 API 정리​

EmbeddedPhotoPickerState도 정리되었습니다.
surfacePackage와 notifyVisibilityChanged가 노출되었고, onError 콜백이 추가되었습니다.
선택기 표면의 가시성 변화를 앱이 직접 통지할 수 있게 되었고, 실패 상황도 콜백으로 받아 처리할 수 있습니다.

최소 SDK와 호출 가능 버전​

두 라이브러리의 최소 SDK가 23으로 낮아졌습니다.
다만 관련 API 호출은 여전히 API 34부터 필요합니다.
낮은 버전 기기에서는 임베디드 선택기를 그대로 호출할 수 없으므로, 시스템 선택기로 떨어지는 분기를 함께 설계해야 합니다.

실무 관점​

알파 버전이므로 운영 화면에 바로 붙이기보다는, 프로필 이미지처럼 범위가 좁은 화면에서 먼저 검증하는 것이 안전합니다.
위치 메타데이터는 개인정보에 해당하므로, 요청하기 전에 왜 필요한지를 안내하고 동의를 받는 흐름이 먼저 필요합니다.
MTS처럼 금융 정보가 많은 앱에서는 사진 선택 화면과 계좌 정보 화면의 동선을 분리해 두는 편이 무난합니다.

마치며​

PhotoPicker 1.0.0-alpha03은 임베디드 선택기라는 방향을 유지하면서, 이름 정리와 위치 메타데이터 요청, 상태 리셋 방식까지 다듬은 업데이트입니다.
알파 단계에서 화면 내장 흐름을 먼저 검증해 두면, 정식 버전이 나왔을 때 적용 여부를 빠르게 판단할 수 있습니다.

Compose Runtime 1.13.0-beta02 — computedStateOf 계산 블록 읽기 전용 강제

2026년 10월 26일 · 약 3분
Way
Android Developer

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.
2026년 10월 21일에 공개된 Compose Runtime 1.13.0-beta02와 10월 7일의 beta01 변경 사항에 대해 설명해드리겠습니다.

배경​

Compose Runtime은 Compose의 상태 모델과 컴파일러 플러그인이 대상으로 하는 핵심 런타임입니다.
1.13 버전은 10월 7일에 beta01, 10월 21일에 beta02가 공개되었습니다.
이번 글은 Material3의 변경이 아니라 런타임의 상태 계산 규칙 변화에 초점을 맞춥니다.
공식 Compose Runtime 릴리스 노트를 기준으로 실무에 닿는 변경만 정리합니다.

Runtime 1.13 베타에서 달라진 것​

computedStateOf 계산 블록 읽기 전용 강제​

가장 주의해야 할 변경은 beta01에 들어갔습니다.
computedStateOf의 계산 블록은 이제 읽기 전용으로 강제됩니다.
계산 블록 안에서 상태를 쓰면 IllegalStateException이 발생합니다.
이전에는 계산 블록 안의 쓰기가 조용히 잘못 동작했습니다.
그 결과 예측하기 어려운 무효화 연쇄와 리컴포지션 루프가 생길 수 있었습니다.
이제 프레임워크가 잘못된 코드를 바로 가리켜 줍니다.
derivedStateOf도 같은 계산 블록 규칙을 사용하므로 동일한 주의가 필요합니다.

// 변경 전 — 계산 블록 안에서 상태를 쓰면 IllegalStateException이 발생합니다.
val totalPrice = remember {
    derivedStateOf {
        // 아래와 같은 쓰기는 1.13 베타부터 허용되지 않습니다.
        // discountApplied.value = true
        cartItems.sumOf { it.price }
    }
}

// 권장 방식 — 상태 변경은 이벤트 핸들러에서 수행합니다.
fun onItemAdded(item: CartItem) {
    cartItems.add(item)
}

val totalPrice = remember {
    derivedStateOf { cartItems.sumOf { it.price } }
}

ComputedState 메모리 누수 수정​

beta02에서는 ComputedState와 관련된 수정이 들어갔습니다.
기록된 상태 값이 해제되지 않던 메모리 누수가 수정되었습니다.
계산 블록이 Snapshot.withoutReadObservation을 호출할 때 무효화가 제대로 되지 않던 문제도 함께 수정되었습니다.
파생 상태를 많이 사용하는 화면에서는 메모리와 무효화 동작을 함께 점검해 볼 만합니다.

그 밖의 beta01 변경​

  • CompositionObserver는 한 컴포지션 패스당 한 번만 해석됩니다.
  • 진행 중인 컴포지션에서 setObserver를 호출하면 다음 패스부터 적용됩니다.
  • Movable content 삽입 시 onBeginComposition과 onEndComposition이 보고됩니다.
  • LinkComposer에서 movable content를 이동할 때 래퍼 그룹 슬롯을 유지하던 누수가 수정되었습니다.
  • lifecycle-runtime이 2.10.0으로 업데이트되었습니다.
  • 해당 버전은 AGP 9.5.0-alpha04 이상에서 번들된 lifecycle runtime lint 검사가 동작하는 데 필요합니다.
  • ComposeTracer가 메인 스레드 밖에서도 사용할 수 있게 되었습니다.
  • Float.NaN이나 Double.NaN을 @Composable 함수에 전달하면 리컴포지션 스킵이 되지 않던 문제가 수정되었습니다.
  • Dp.Unspecified이 Float.NaN 기반이라 이 수정과 직접 연결됩니다.
  • 라이브러리가 Kotlin 2.2를 대상으로 하며 kotlinc 2.2가 요구됩니다.

베타를 적용하는 의존성 선언은 다음과 같습니다.

dependencies {
    implementation("androidx.compose.runtime:runtime:1.13.0-beta02")
}

실무 관점​

MTS 앱처럼 파생 상태를 많이 쓰는 코드에서는 계산 블록 안의 쓰기부터 점검하는 것이 좋습니다.
계산 블록은 순수한 계산만 담당하고, 상태 변경은 클릭이나 콜백 같은 이벤트 핸들러에서 수행합니다.
베타는 디버그 빌드에서 먼저 적용하고, 스테이블 전환 전에 회귀 테스트를 거치는 것이 안전합니다.
Dp.Unspecified 관련 스킵 수정은 레이아웃 측정 코드의 리컴포지션 횟수에도 영향을 줄 수 있습니다.

마치며​

1.13 베타는 상태 계산 블록의 규칙을 명확히 하고 누수를 정리하는 업데이트입니다.
계산 블록 안의 쓰기를 찾아내는 것만으로도 스테이블 전환 전에 한 가지 위험을 줄일 수 있습니다.

AI 에이전트가 만드는 네이티브 UI: Jetpack Compose A2UI 렌더러 살펴보기

2026년 10월 25일 · 약 3분
Way
Android Developer

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.
2026년 10월 21일 공개된 A2UI 1.0.0-alpha02에 대해 설명해드리겠습니다.

배경​

AI 에이전트는 이제 작업을 추론하고 도구를 호출하고 대화를 이어갈 수 있습니다.
그런데도 에이전트가 사용자에게 네이티브 화면을 보여주는 일은 여전히 어렵습니다.
에이전트는 앱이 어떤 컴포넌트를 가지고 있는지 모르기 때문에, 날짜 선택기나 확인 버튼 같은 실제 UI를 건네줄 수 없습니다.
A2UI는 이 간극을 메우기 위한 프로토콜입니다.

A2UI 살펴보기​

A2UI의 핵심 아이디어는 단순합니다.
에이전트가 임의의 UI 코드를 만들어내는 대신, 클라이언트가 미리 정해둔 카탈로그 안에서만 UI를 조합합니다.

카탈로그가 계약이 됩니다​

모든 A2UI 인터페이스는 컴포넌트 카탈로그를 중심으로 동작합니다.
카탈로그는 에이전트가 사용할 수 있는 UI 요소와 속성, 함수를 선언합니다.
에이전트는 카탈로그에 등록되지 않은 컴포넌트를 만들어낼 수 없으므로, 렌더링 결과가 예측 가능한 범위를 벗어나지 않습니다.

임의 코드 실행이 없습니다​

A2UI 렌더러의 가장 중요한 성질은 임의 코드를 실행하지 않는다는 점입니다.
에이전트는 구조화된 데이터를 보내고, 클라이언트는 그 데이터를 네이티브 Compose 컴포넌트로 렌더링합니다.
서버에서 온 설명이 앱 안에서 코드로 실행되는 일이 없으므로, 신뢰 경계를 넘는 UI도 안전하게 다룰 수 있습니다.

Jetpack A2UI 렌더러의 구조​

Jetpack의 A2UI 렌더러는 디자인 시스템과 무관한 렌더링 엔진과 구체적인 카탈로그 구현을 분리합니다.
데이터 계층인 a2ui-model과 a2ui-engine이 프로토콜 메시지를 파싱하고 처리합니다.
UI 계층인 compose-runtime과 compose-ui가 앱과 카탈로그를 위한 API를 제공합니다.
Material 3 컴포넌트로 구성된 기본 카탈로그도 함께 제공되어, 별도 카탈로그 없이 바로 시작할 수 있습니다.

    implementation("androidx.a2ui:a2ui-model:1.0.0-alpha02")
    implementation("androidx.a2ui.compose:compose-runtime:1.0.0-alpha02")
    implementation("androidx.a2ui.compose:compose-ui:1.0.0-alpha02")
}

이번 alpha02에서는 기본 카탈로그의 함수 목록이 인터페이스로 바뀌었습니다.
구현체는 openUrl만 구현하면 되고, 나머지 함수는 기본 구현을 쓰거나 개별적으로 재정의할 수 있습니다.

val catalog = materialA2uiBasicCatalogV1(

아직 알파 단계이므로, 프로덕션 화면에 바로 적용할 라이브러리는 아닙니다.

베타 미리 보기 — Compose 1.13.0-beta01과 Material3 1.5.0-beta01의 소스 브레이킹 변경

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.
2026년 10월 7일에 공개된 Compose 1.13.0-beta01과 Material3 1.5.0-beta01의 변경 사항에 대해 설명해드리겠습니다.

배경​

2026년 10월 7일, Compose BOM의 두 축이 베타로 나왔습니다.
androidx.compose.runtime:runtime:1.13.0-beta01와 androidx.compose.material3:material3:1.5.0-beta01입니다.
같은 날 stable도 runtime 1.12.1과 material3 1.4.0으로 함께 릴리스되었습니다.
둘 다 아직 베타지만 소스 브레이킹 변경이 포함되어 있어, 지금 미리 파악해 두면 나중에 스테이블로 올릴 때 수월합니다.
공식 AndroidX 릴리스 노트(Material3, Runtime)를 기준으로 실무에 닿는 변경만 정리합니다.
참고로 이 글은 최근 30일 이내 릴리스를 다루는 심화 해설입니다.

무엇이 달라졌는지​

Slider와 RangeSlider의 상태 분리​

가장 큰 소스 브레이킹 변경입니다.
Material3 1.5.0-alpha29에서 Slider와 RangeSlider의 onValueChange가 필수 파라미터가 되었고, 파라미터 순서도 바뀌었습니다.
무상태(stateless) 오버로드는 deprecated(일부는 hidden) 처리되었고, 상태를 별도 객체로 분리하는 방식으로 이관이 권장됩니다.

// 기존 방식 (1.5.0에서 deprecated)
var value by remember { mutableFloatStateOf(0.5f) }
Slider(value = value, onValueChange = { value = it })

// 새 방식 — 상태를 별도 객체로 분리
val state = remember { SliderState(value = 0.5f) }
Slider(state = state)

var range by remember { mutableStateOf(0.2f..0.8f) }
RangeSlider(value = range, onValueChange = { range = it })
// → val state = remember { RangeSliderState(startValue = 0.2f, endValue = 0.8f) }
//   RangeSlider(state = state)

함께 바뀐 사항은 다음과 같습니다.

  • RangeSliderState의 activeRangeStart와 activeRangeEnd가 startValue와 endValue로 개명되었습니다.
  • SliderState는 더 이상 공개적으로 DraggableState를 구현하지 않습니다. 바이너리 호환 유지를 위해 DraggableState는 SliderState에 복원되었고, onValueChange가 nullable인 오버로드는 hidden deprecated로 유지됩니다.

소스 코드는 고쳐야 하지만 이미 빌드된 바이너리는 깨지지 않게 설계된 셈입니다.

computedStateOf의 읽기 전용 강제​

runtime 1.13.0-beta01부터 computedStateOf의 계산 블록 안에서 state에 쓰면 IllegalStateException이 던져집니다.
이전에도 쓰면 안 되는 패턴이었지만 실제로는 조용히 넘어가거나 이상한 무효화(invalidation)를 일으키곤 했습니다.
이는 외부 기여로 들어온 SnapshotStateObserver 읽기 시 예상 밖 무효화 수정과 같은 맥락입니다.
계산 블록은 순수하게 읽고 반환만 한다는 규칙이 강제됩니다.

Kotlin 2.2와 AGP 요구사항​

Compose 라이브러리들이 Kotlin 2.2를 타깃으로 빌드되고, kotlinc 2.2가 필요합니다.
또 androidx.lifecycle:lifecycle-runtime:2.10.0 의존성 업데이트 때문에, 번들된 lifecycle lint 체크가 동작하려면 AGP 9.5.0-alpha04 이상이 필요합니다.
툴체인 전체가 2.2와 37.1 라인으로 움직이고 있다는 신호입니다.

compileSdk 37.1 전이적 요구​

Compose 라이브러리의 compileSdk가 37.1로 올라갔습니다.
이는 Compose를 쓰는 모든 앱과 라이브러리도 compileSdk를 37.1로 올려야 한다는 뜻입니다.
Android 17(targetSdk 37) 대응을 아직 하지 않았다면, Compose 1.13과 1.5 스테이블로 올라가는 시점이 강제 마이그레이션 시점이 됩니다.

그 외 변경 사항​

  • 비밀번호 필드의 기본 난독화 방식이 RevealLastTyped에서 TextObfuscationMode.System으로 바뀝니다. SecureTextField와 OutlinedSecureTextField의 기본값 변경입니다.
  • Float.NaN 관련 리컴포지션 스킵 버그가 수정되었습니다. Dp.Unspecified(내부적으로 Float.NaN 기반)를 인자로 받은 컴포저블이 인자가 변하지 않았는데도 리컴포지션을 스킵하지 못하던 문제입니다.
  • BottomAppBar와 연관 API가 스테이블로 승격되었고, BasicAlertDialog가 Experimental을 졸업했습니다.
  • LocalMotionScheme이 제거되고 MaterialTheme.motionScheme으로 교체되었습니다.
  • ExposedDropdownMenu가 멤버 함수에서 ExposedDropdownMenuBoxScope의 확장 함수로 변경되어 import를 새로 잡아야 합니다.
  • 새로운 material3-ripple 라이브러리가 추가되었습니다. 기존 material-ripple의 대체이며 inset focus ring을 지원합니다.
  • DatePicker가 월 이동 가용성을 표시 월 인덱스에서 직접 계산해 1프레임에 해결되도록 개선되었습니다.
  • TopAppBarDefaults.enterAlwaysScrollBehavior의 reverseLayout 오버로드가 1.4 호환을 위해 deprecated(경고)로 복원되었습니다.
  • HorizontalCenteredHeroCarousel의 maxItemWidth가 preferredItemWidth로 개명되었고, 멀티애스펙트 캐러셀 API가 전역 carouselParallaxScrollEffect 모디파이어로 단순화되었습니다.
  • runtime에서는 movableContent 이동 시 wrapper 슬롯을 들고 있던 LinkComposer 메모리 누수가 수정되었고, CompositionObserver가 패스당 1회 해결되도록 변경되었으며, 오프-메인 스레드 ComposeTracer가 지원됩니다.

  • Slider 사용처를 전수 조사해야 합니다. 금융 앱에 수수료 슬라이더나 투자 금액 조절 같은 Slider와 RangeSlider가 있다면 1.5.0 스테이블 전에 상태 분리 방식으로 바꿔 두는 것이 좋습니다. onValueChange 필수화는 컴파일 에러로 드러나지만, 파라미터 순서가 바뀐 오버로드는 시그니처 자체가 바뀌어 에러가 나거나 deprecated로 걸리므로 리뷰는 한 번씩 필요합니다.

  • Kotlin 2.2와 AGP, compileSdk 37.1은 묶어서 계획해야 합니다. Compose 1.13은 Kotlin 2.2를, lint는 AGP 9.5.0-alpha04 이상을, Compose는 compileSdk 37.1을 각각 요구하므로 서로 의존합니다. 하나씩 따로 올리기보다 한 스프린트에 묶어 CI에서 함께 검증하는 편이 낫습니다.
  • 비밀번호 입력 UX 변경은 기획과 디자인 부서와 공유해야 합니다. 기본값이 System으로 바뀌면 타이핑 중 마지막 글자를 잠깐 보여주는 동작이 사라집니다. 보안 정책상 환영할 변화지만, 릴리스 노트 한 줄로 바뀌는 UX라 미리 공유하지 않으면 버그 문의가 들어올 수 있습니다.

init { load() }을 지우는 법 — stateIn으로 ViewModel UI 상태를 선언적으로

2026년 10월 17일 · 약 4분
Way
Android Developer

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.
최근 ProAndroidDev에 소개된 stateIn 기반 ViewModel 상태 선언 방식에 대해 설명해드리겠습니다.

배경​

ViewModel을 열면 거의 항상 비슷한 패턴이 나옵니다.
private val _uiState = MutableStateFlow(UiState())를 선언하고, init에서 load()를 호출하고, 데이터가 오면 .update로 복사하는 방식입니다.
틀린 코드는 아닙니다. 그런데 화면이 커질수록 이 수동 동기화 코드가 어딘가에서는 반드시 어긋나기 시작합니다.
The Power of stateIn in ViewModel에서는 이 문제를 명령(command)과 상태(state)의 구분으로 풀어냅니다.

stateIn으로 상태 선언하기​

핵심 요약​

  • init에서 로드하고 수동으로 _uiState를 갱신하는 패턴은, 상태가 어떻게 도출되는지가 아니라 언제 복사했는지를 코드에 남깁니다.
  • 입력이 하나만 있을 때는 괜찮지만, 검색어와 필터와 새로고침처럼 입력이 늘어나면 동기화 누락이 생깁니다.
  • 핵심 원칙은 하나입니다. MutableStateFlow는 수정 가능한 입력에만 두고, 파생 상태는 Flow 연산자로 표현해 stateIn으로 StateFlow로 노출합니다.
  • stateIn 자체는 데이터를 가져오지 않습니다. 상류 Flow가 뱉은 값을 공유하고 유지할 뿐이며, SharingStarted.WhileSubscribed(5_000) 같은 공유 전략은 화면 생명주기에 맞춰 선택해야 합니다.

명령과 상태의 구분​

  • 명령(commands)은 무슨 일이 일어나야 하는지를 뜻합니다. "제출해라", "삭제해라", "새로고침해라"처럼 사용자의 명시적 동작에 대한 반응입니다.
  • 상태(state)는 지금 무엇이 사실인지를 뜻합니다. "보이는 목록은 items와 query로부터 도출된다"처럼 관계가 코드에 선언됩니다.
  • 문제는 명령으로 상태를 동기화하려고 할 때 생깁니다.
  • 레포지토리가 이미 val items: Flow<List<Item>>을 들고 있는데도 ViewModel이 collect 해서 _uiState에 복사하고, 쿼리가 바뀌면 또 복사하는 구조에서는, 보이는 목록을 다시 계산해야 하는 모든 장소를 사람이 기억해야 합니다.

stateIn으로 바뀌는 코드​

  • 입력은 그대로 두되, 파생 UI 상태는 연산자로 표현합니다.
class PortfolioViewModel(repository: HoldingRepository) : ViewModel() {

    // 입력: 사용자가 바꾸는 검색어 — MutableStateFlow가 맞다
    private val query = MutableStateFlow("")

    // 파생 상태: 레포지토리 데이터 + 검색어로 도출 — map/combine이 관계다
    val uiState: StateFlow<PortfolioUiState> =
        combine(repository.holdings, query) { holdings, query ->
            PortfolioUiState(
                holdings = holdings.filter { it.matches(query) },
                query = query,
            )
        }.stateIn(
            scope = viewModelScope,
            started = SharingStarted.WhileSubscribed(5_000),
            initialValue = PortfolioUiState(),
        )

    fun onQueryChanged(query: String) {
        this.query.value = query // UI 액션은 입력만 바꾼다
    }
}
  • 사라지는 것들을 세어보면 명확해집니다. 수동 _uiState, init 블록, 복사용 load(), 레포지토리와 UI 모델 사이의 수동 동기화가 모두 없어집니다.
  • UI 액션인 onQueryChanged는 uiState를 직접 건드리지 않고 입력만 바꿉니다.
  • 양쪽 입력 중 하나라도 바뀌면 파생 상태가 자동으로 갱신됩니다.

공유 전략은 생명주기를 보고 고르기​

  • WhileSubscribed(5_000)는 첫 구독자가 생기면 상류를 수집하고, 마지막 구독자가 사라진 지 5초 후에 수집이 멈춥니다.
  • 타임아웃은 화면 회전 같은 짧은 구독 공백에서 상류 스트림이 끊겼다 다시 붙는 것을 막아줍니다.
  • 단, 글쓴이가 경고하는 함정이 있습니다. 수집이 멈췄다가 재개된다고 네트워크 요청이 반드시 다시 나가는 것은 아닙니다.
  • 그 동작은 상류 Flow가 어떻게 구현됐느냐에 달렸습니다. 레포지토리의 캐시와 공유 전략이 실제 동작을 결정합니다.
  • 공유 전략은 관성처럼 쓰는 관용구가 아니라, 원하는 생명주기 동작을 보고 선택해야 합니다.

실무에서 주의할 점​

  • **LaunchedEffect(Unit) { viewModel.load() }**로 화면에 들어갈 때마다 다시 로드하는 패턴은 "명령으로 상태를 동기화"하는 전형적인 예입니다. 그 데이터가 이미 레포지토리의 Flow로 존재한다면 stateIn 파생으로 바꾸는 것이 낫습니다.
  • 명시적 명령이 정당한 경우도 있습니다. 폼 제출, 삭제, 사용자가 누른 새로고침처럼 이벤트에 대한 반응은 명령으로 두어야 합니다. 모든 것을 Flow로 감싸지 않는 것이 중요합니다. 제거 대상은 "파생 상태를 동기화하기 위한 명령"뿐입니다.
  • 테스트가 쉬워집니다. 파생 로직은 순수 함수인 map과 combine 변환이라 ViewModel 전체를 띄우지 않고도 검증할 수 있습니다.
  • SharingStarted 선택은 코드 리뷰 포인트로 남겨두는 것이 좋습니다. WhileSubscribed와 Eagerly의 차이는 상류 비용(소켓, 폴링, 가격 스트리밍)을 누가 내는가와 직결됩니다.
  • 가격 스트리밍처럼 상류가 비싼 Flow라면, 파생 전에 레포지토리 단에서 공유를 정리하는 방식이 좋습니다.
// Repository: 비싼 상류를 여기서 공유 — ViewModel은 몰라도 된다
val holdings: Flow<List<Holding>> = priceSocket.stream()
    .map(::toHoldings)
    .shareIn(
        scope = externalScope,
        started = SharingStarted.WhileSubscribed(5_000),
        replay = 1,
    )
  • 이렇게 두면 ViewModel은 combine(holdings, query) 하나로 "검색어에 맞는 보유종목"이라는 관계를 선언합니다.
  • 소켓 구독 시점과 구독 종료 시점 같은 생명주기 판단은 공유 전략 선언 한 곳에서만 일어납니다.
  • 화면이 두 개로 늘어나도 동기화 코드를 복사해 붙여넣지 않아도 됩니다.

마치며​

상태를 명령으로 동기화하는 코드를 걷어내면, ViewModel에는 입력과 도출 관계만 남습니다.
입력은 MutableStateFlow로, 파생 상태는 연산자와 stateIn으로 선언하는 기준을 팀 규칙으로 정해두면 화면이 커져도 동기화 누락을 막을 수 있습니다.

Compose에서 Flow 수집의 진화 — collectAsState()에서 collectAsStateWithLifecycle()까지

2026년 10월 14일 · 약 2분
Way
Android Developer

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.
Compose에서 Flow를 수집하는 API가 어떻게 진화해 왔는지 설명해드리겠습니다.

배경​

Compose에서 UI 상태는 주로 Flow로 노출되고, 화면에서는 이를 State로 변환해 수집합니다.
문제는 수집 API가 라이프사이클을 모르면 액티비티가 백그라운드로 가도 수집이 계속된다는 점입니다.
실무에서는 여전히 collectAsState()를 관성으로 쓰는 코드가 많습니다.
10월 ProAndroidDev에 올라온 The Evolution of Flow Collection in Jetpack Compose 글(chanzmao)이 이 진화 과정을 정리했습니다.

Flow 수집 API의 진화​

1단계: collectAsState()​

  • Compose 1.0(2021년 7월)에 도입된 가장 단순한 수집 방법입니다.
  • Flow를 State로 바꾸고, 새 값이 emit될 때마다 관련 UI를 리컴포즈합니다.
  • 라이프사이클을 모르기 때문에 STARTED 아래로 내려가도 수집을 자동으로 멈추지 않습니다.
  • composition이 살아 있는 한 백그라운드에서도 계속 수집합니다.
val uiState by viewModel.uiState.collectAsState()

2단계: collectAsStateWithLifecycle()​

  • lifecycle-runtime-compose가 제공하는 라이프사이클 인식 API입니다.
  • 기본 minActiveState는 STARTED입니다.
  • 화면이 보이지 않으면 수집을 멈추고, 다시 보이면 재개합니다.
  • 지금의 정답에 해당하는 방법입니다.
val uiState by viewModel.uiState.collectAsStateWithLifecycle()

3단계: 일회성 이벤트는 다른 패턴으로​

  • 상태가 아니라 이벤트(네비게이션, 스낵바 등)를 소비할 때는 collectAsState 계열이 맞지 않습니다.
  • LaunchedEffect와 repeatOnLifecycle 조합을 사용합니다.
val lifecycle = LocalLifecycleOwner.current.lifecycle
LaunchedEffect(lifecycle) {
    lifecycle.repeatOnLifecycle(Lifecycle.State.STARTED) {
        viewModel.events.collect { event ->
            // 네비게이션, 스낵바 등 일회성 이벤트 처리
        }
    }
}

실무에서 주의할 점​

ViewModel의 uiState 같은 StateFlow는 collectAsStateWithLifecycle()를 기본값으로 두는 것이 안전합니다.
collectAsState()는 upstream이 가벼우면 문제가 없지만, 소켓·위치·센서처럼 비싼 작업을 하는 Flow면 백그라운드에서 리소스를 낭비합니다.
minActiveState 파라미터로 기준을 RESUMED까지 올릴 수도 있으니, 화면 요구사항에 맞게 조정해야 합니다.
SharedFlow 기반 일회성 이벤트에 collectAsState를 붙이는 실수는 여전히 흔하므로, 이벤트면 수집 패턴을 바꿔야 합니다.

마치며​

Flow 수집은 단순한 API 선택이 아니라 라이프사이클과 리소스 관리의 문제입니다.
상태는 collectAsStateWithLifecycle()로, 일회성 이벤트는 repeatOnLifecycle로 구분해 사용하는 것이 좋겠습니다.

}

같이 나온 것들​

  • Compose 1.13.0-beta01 (animation/foundation/material/runtime): 이번 배치부터 라이브러리들이 Kotlin 2.2를 타깃으로 하고 kotlinc 2.2를 요구합니다. 베타를 올릴 때는 Kotlin 버전을 2.2 이상으로 올려야 컴파일이 됩니다.
  • appfunctions 1.0.0-alpha13: @AppFunction → @AppFunctionDeclaration, ObserveAppFunctionsEvent → AppFunctionsChangeEvent로 리네임됐고, 접근 레벨 제한을 위한 @AppFunctionAccessLevel이 추가됐습니다. 에이전트·Gemini 시대의 앱 기능 노출 인터페이스라 실험 중이라면 이름 바뀐 것만 확인하면 됩니다.
  • collection 1.7.0 (스테이블): toOrderedScatterSet() 확장(빈 소스에선 할당 없는 싱글턴 반환), ScatterMap.getOrPut() 최적화, Float 키 해시 충돌 개선, 원시 타입 리스트(IntList/LongList 등)에 sortWith/sortBy/binarySearch 추가. 퍼포먼스에 민감한 데이터 구조를 쓰는 팀은 별도 변경 없이 이득을 볼 수 있습니다.
  • benchmark 1.6.0-alpha01: :lockClocks 태스크가 root 없이도 고정 성능 모드를 쓸 수 있게 돼서, 더 많은 실기기에서 안정적인 마이크로벤치마크가 가능합니다. 힙 프로파일링용 MemoryProfilingConfig도 추가됐습니다.

실무에서 주의할 점​

  • Remote Compose는 아직 알파입니다. API가 바뀔 수 있다는 전제로 실험·프로토타입 수준에서 접근하는 게 맞습니다. 다만 테마 인식, 텍스트 측정, 압축 문서 로딩처럼 운영에 쓰려면 꼭 있어야 할 기능들이 차례로 들어오고 있어서, 방향성 자체는 꽤 진지하게 보입니다.
  • 에이전트 시대의 SDUI: 최근 Android CLI와 에이전트 스킬 흐름과 맞물려, 에이전트가 생성한 UI를 어떻게 앱에 그릴 것인가가 실무 질문이 되고 있습니다. Remote Compose는 그 답 중 하나입니다. 당장 도입하지 않더라도 개념과 플레이어 구조는 한 번 훑어둘 만합니다.
  • Compose 1.13 베타 + Kotlin 2.2: 컴파일러 버전 요구사항이 같이 올라간 릴리스라서, 버전만 올렸다가 빌드가 깨지는 경우가 생길 수 있습니다. 베타를 쓸 거면 libs.versions.toml의 Kotlin 버전도 함께 올립니다.
  • appfunctions 리네임: 알파 실험 중이라면 컴파일 에러가 나는 게 정상이니, 이름만 바꿔 주면 됩니다.

당장은 프로덕션 도입이 아니라 관측 모드입니다.
스프린트 사이에 작은 실험 프로젝트 하나로 Remote Compose 플레이어에 문서 하나 띄워 보는 것 정도가 적당합니다.
관전 포인트는 두 가지입니다.

  1. 서버에서 보낸 문서가 다크 테마에서 깨지지 않는지 (createThemedRemoteColor 사용)
  2. 텍스트 길이 가변적인 배지 UI를 RemoteTextMeasurer로 제대로 그릴 수 있는지
// gradle/libs.versions.toml
[versions]
androidxRemoteCompose = "1.0.0-alpha21"
composeRemoteFoundation = "1.0.0-alpha04"

에이전트가 UI를 만드는 시대가 오고 있는데, 어떻게 그릴 것인가는 여전히 앱 개발자의 몫입니다.
Remote Compose가 그 몫을 나눠 가질 후보 중 하나라는 점에서, 이번 릴리스는 지켜볼 가치가 있습니다.

마치며​

10월 AndroidX 배치는 UI를 코드가 아니라 문서로 다루는 쪽으로 축이 이동하고 있음을 보여줍니다.
Remote Compose 알파21의 변경점 대부분이 렌더링 품질과 운영 편의(테마, 압축, 측정)에 집중돼 있다는 점이 그 신호이며, 다음에 SDUI를 고민할 때 선택지에 넣어두기 좋은 타이밍입니다.

Compose 1.13.0-beta01 정리 — Dp.Unspecified가 리컴포지션을 막던 버그 수정

2026년 10월 8일 · 약 3분
Way
Android Developer

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.
2026년 10월 7일 공개된 Compose 1.13.0-beta01에 대해 설명해드리겠습니다.

배경​

Compose의 stable 채널 최신 버전은 1.12.1이고, 1.13은 베타 단계에 있습니다.
이번 글에서는 Compose Runtime 릴리스 노트를 기준으로, runtime에서 실무에 닿는 변경만 추려서 정리하겠습니다.
특히 공용 컴포넌트를 많이 사용하는 코드베이스에서는 리컴포지션 관련 수정이 체감 성능에 영향을 줄 수 있습니다.

Compose 1.13.0-beta01 살펴보기​

Kotlin 2.2 타깃으로 상향​

1.13부터 Compose 라이브러리는 Kotlin 2.2를 타깃으로 빌드되며, kotlinc 2.2가 필요합니다.
버전 카탈로그에서 Compose BOM만 올리는 습관이 있다면, Kotlin 플러그인 버전이 뒤처진 모듈에서 먼저 걸릴 수 있으니 함께 확인하는 것이 좋습니다.

Dp.Unspecified를 받는 컴포저블이 스킵되지 않던 버그​

Float.NaN이나 Double.NaN을 인자로 받는 @Composable은 인자가 그대로여도 스킵되지 않고 매번 리컴포지션되는 버그가 있었습니다.
Dp.Unspecified가 내부적으로 Float.NaN 기반이기 때문에, 선택적 간격이나 크기를 Dp.Unspecified 기본값으로 받는 공용 컴포넌트가 조용히 리컴포지션 비용을 치르고 있었던 것입니다.

// 이런 공용 컴포넌트가 인자 변화가 없어도 스킵되지 않을 수 있었다
@Composable
fun PriceRow(
    label: String,
    topPadding: Dp = Dp.Unspecified
) { /* ... */ }

사내 디자인 시스템처럼 공용 컴포넌트에 Dp.Unspecified 기본값이 흔한 코드베이스라면, 1.13 stable이 나올 때 체감 성능이 좋아질 수 있습니다.

computedStateOf 계산 블록은 읽기 전용으로 강제​

computedStateOf의 계산 블록 안에서 상태에 쓰면 이제 IllegalStateException이 발생합니다.
기존에 계산 블록 안에서 쓰기까지 하던 코드가 있었다면 런타임에서 바로 드러나므로, 베타를 올리는 모듈부터 확인이 필요합니다.

그 외 버그 픽스​

  • CompositionObserver가 컴포지션 패스마다 한 번만 해석되고, 교체는 다음 패스부터 적용됩니다. movable content 삽입 시에도 begin/end 콜백이 보고됩니다.
  • movableContent 이동 시 래퍼 그룹 슬롯이 남아 있던 LinkComposer 메모리 누수를 고쳤습니다.
  • lifecycle-runtime 의존성이 2.10.0으로 올라갔습니다. 번들된 lifecycle lint 검사는 AGP 9.5.0-alpha04 이상과 맞물려 있으니, AGP 베타 채널을 쓰는 프로젝트는 같이 보는 것이 좋습니다.
  • ComposeTracer를 메인 스레드 밖에서도 쓸 수 있게 됐습니다.

실무에서 주의할 점​

1.12.1 stable은 1.12.0에서 변경이 없는 버전이라, 운영 앱은 stable 유지가 무난합니다.
베타는 성능 검증이 필요한 화면 위주로 먼저 올려 보고, 앱 전체 확대는 stable 이후가 안전합니다.
공용 컴포넌트를 많이 쓰는 MTS 특성상 리컴포지션 이슈가 체감되는 화면부터 적용해 보는 것이 좋습니다.

마치며​

이번 베타의 핵심은 Dp.Unspecified 기본값을 받는 공용 컴포넌트의 불필요한 리컴포지션을 막은 수정입니다.
stable이 공개되면 공용 컴포넌트 비중이 높은 프로젝트부터 우선 적용해 보시기 바랍니다.

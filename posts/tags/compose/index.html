Biometric 1.4.0-beta01 살펴보기 — Activity Result 패턴으로 바뀐 생체 인증

2026년 11월 6일 · 약 3분
Way
Android Developer

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.
2026년 11월 4일에 공개된 Biometric 1.4.0-beta01에 대해 설명해드리겠습니다.

배경​

Biometric의 현재 stable 버전은 1.1.0입니다.
1.4 라인은 2024년 5월 alpha01부터 이어져 왔고, 11월 4일 beta01에 들어섰습니다.
베타 단계는 API 표면이 기능적으로 완성된 상태입니다.
이번 1.4의 핵심은 기존 BiometricPrompt 콜백 방식을 Activity Result 패턴으로 바꾸는 것입니다.

Biometric 1.4.0-beta01 살펴보기​

registerForAuthenticationResult로 등록합니다​

1.4에서는 BiometricPrompt와 biometric-ktx 모듈을 대체하는 새로운 진입점이 도입되었습니다.
Activity Result API와 같은 방식으로 인증을 등록하고 실행합니다.
인증 입력은 AuthenticationRequest로, 결과는 AuthenticationResult로 받습니다.

private val auth = registerForAuthenticationResult { result ->
    when (result) {
        is AuthenticationResult.Success -> onAuthenticated()
        is AuthenticationResult.Error -> showError(result.errString)
        is AuthenticationResult.CustomFallbackSelected -> onFallbackSelected(result)
    }
}

AuthenticationRequest는 두 가지 종류가 있습니다.
생체 인증용 BiometricRequest는 강도(Strength)와 선택적인 Fallback을 지정합니다.
기기 자격 증명 전용 인증용 CredentialRequest도 함께 제공됩니다.
하나의 Activity나 Fragment에서 여러 인증 런처를 동시에 쓸 수도 있습니다.

biometric-compose에서 rememberAuthenticationLauncher를 사용합니다​

1.4.0-alpha05부터는 Compose 전용 biometric-compose 라이브러리도 함께 제공됩니다.
컴포저블 안에서 rememberAuthenticationLauncher로 인증 요청과 콜백을 처리합니다.

val auth = rememberAuthenticationLauncher { result ->
    when (result) {
        is AuthenticationResult.Success -> onAuthenticated()
        is AuthenticationResult.Error -> showError(result.errString)
        is AuthenticationResult.CustomFallbackSelected -> Unit
    }
}

의존성은 다음과 같이 추가합니다.

dependencies {
    implementation("androidx.biometric:biometric:1.4.0-beta01")
    implementation("androidx.biometric:biometric-compose:1.4.0-beta01")
}

Fallback 옵션을 여러 개 둘 수 있습니다​

Android 36.1(Baklava)부터는 생체 인증 프롬프트에서 최대 네 개의 커스텀 Fallback 옵션을 지원합니다.
기존의 단일 부정 버튼 대신, 아이콘을 함께 제공하는 여러 Fallback 옵션을 둘 수 있습니다.
Fallback 옵션은 AuthenticationRequest.Biometric.Fallback으로 제공합니다.
사용자가 Fallback을 선택하면 에러 코드가 아니라 AuthenticationResult.CustomFallbackSelected로 전달됩니다.

그 외 변경점​

BiometricPrompt.CryptoObject에 KeyAgreement 지원이 추가되었습니다.
기본 minSdk가 API 21에서 API 23으로 올라갔습니다.
라이브러리는 이제 JSpecify nullness 어노테이션을 사용합니다.
그 밖에 기기 회전 시 지문 아이콘이 사라지는 문제와 canAuthenticate()에서 잠금 오류를 잘못 반환하는 문제가 수정되었습니다.

실무 관점​

MTS의 로그인이나 이체 인증 화면에서 BiometricPrompt를 쓰고 있다면, 교체 설계는 지금 시작하는 것이 좋습니다.
다만 적용 시점은 stable 릴리스 이후로 잡는 편이 안전합니다.
베타 단계의 API는 기능적으로 완성되었지만, 변경 가능성이 남아 있기 때문입니다.
Fallback 옵션은 PIN이나 패턴 같은 기기 자격 증명 경로와 연결해 설계합니다.
minSdk 23 변경도 적용 대상 단말 목록과 함께 확인합니다.

마치며​

Biometric 1.4는 생체 인증을 Activity Result 패턴으로 바꾸고, Compose 전용 런처와 복수 Fallback 옵션을 함께 가져왔습니다.
인증 화면을 새로 만들거나 고칠 계획이 있다면, 1.4의 새 API를 기준으로 설계하는 것이 좋습니다.

Compose 1.13.0-rc01 살펴보기 — API가 확정된 1.13과 Slider 변경점

2026년 11월 6일 · 약 3분
Way
Android Developer

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.
2026년 11월 4일에 공개된 Compose 1.13.0-rc01과 Material3 1.5.0-rc01에 대해 설명해드리겠습니다.

배경​

현재 stable 버전은 Compose 1.12.1과 Material3 1.4.0입니다.
1.13 라인은 10월 7일 beta01, 10월 21일 beta02를 거쳐 11월 4일 RC 단계에 들어갔습니다.
RC는 API 표면이 확정된 예비 stable 릴리스입니다.
이 글은 10월 8일 beta01 글과 10월 26일 beta02 글의 후속으로, RC에서 확정된 변경점을 중심으로 정리했습니다.

Compose 1.13.0-rc01 살펴보기​

Kotlin 2.2가 필요합니다​

Compose 1.13 라이브러리는 Kotlin 2.2를 대상으로 빌드되며, 컴파일러도 2.2가 필요합니다.
업데이트 전에 libs.versions.toml의 Kotlin 버전을 먼저 확인합니다.

[versions]
kotlin = "2.2"

Slider에서 onValueChange이 필수가 되었습니다​

Slider, VerticalSlider, RangeSlider에서 onValueChange이 필수 파라미터가 되었습니다.
기존에 숨겨져 있던 deprecated API와 SliderState의 DraggableState 구현, 구형 Saver 오버로드가 제거되었습니다.
SliderState의 isVertical도 제거되었고, SliderDefaults.Thumb의 SliderState 오버로드는 isVertical 오버로드로 대체되었습니다.

var value by remember { mutableFloatStateOf(0.5f) }

Slider(
    value = value,
    onValueChange = { value = it },
)

기존 코드에서 onValueChange을 생략한 Slider가 있다면 컴파일 단계에서 바로 드러납니다.
값 변경을 받지 않는 표시 전용 슬라이더는 onValueChange에 빈 람다를 넘기는 대신, 읽기 전용 표시 방식을 검토하는 편이 낫습니다.

MediaQuery의 Posture가 WindowPosture로 바뀌었습니다​

MediaQuery의 Posture 클래스가 WindowPosture로 대체되었습니다.
WindowPosture는 물리적인 WindowFold를 FoldState와 FoldOrientation으로 노출합니다.
isTabletop과 isFlat 편의 프로퍼티가 추가되었고, 기존의 Book 자세 구분은 제거되었습니다.

if (posture.isTabletop) {
    // 접은 상태에서는 하단 화면에 컨트롤을 배치합니다.
} else if (posture.isFlat) {
    // 펼친 상태에서는 전체 화면 레이아웃을 사용합니다.
}

폴더블 대응 화면에서는 자세 판정 로직을 WindowPosture 기준으로 다시 확인합니다.

Progressive Blur API가 정리되었습니다​

1.13 alpha03에서 추가된 Modifier.blur { ... } API가 RC에서 정리되었습니다.
Modifier.blur의 radius 파라미터가 blurRadiusSpec으로 개명되었고, BlurScope.radius도 blurRadiusSpec으로 바뀌었습니다.
BlurStop.fraction에는 @FloatRange가 추가되었고, BlurRadiusSpec.radialGradient의 기본 fallOffRadius는 Dp.Unspecified로 변경되었습니다.

그 외 변경점​

VectorPainter가 같은 ImageVector를 여러 컴포저블에서 그릴 때 내부 그래픽 리소스를 공유합니다.
반복 아이콘을 쓰는 리스트에서 텍스처 업로드와 메모리 사용이 줄어듭니다.
이 최적화는 ComposeUiFlags.isVectorDrawCacheSharingEnabled 플래그로 끌 수 있습니다.
Modifier.border는 이제 아웃라인 크기를 기준으로 테두리를 그립니다.
문제가 생기면 ComposeFoundationFlags.isBorderMatchesOutlineBoundsFixEnabled 플래그로 이전 동작을 되돌릴 수 있습니다.
Material3 1.5.0-rc01에서는 ToggleButton의 눌림 상태 모양이 디자인 토큰을 따르도록 수정되었고, RangeSlider의 탭 시 값 미반영, 가로 스크롤 컨테이너 안에서의 스크롤 간섭, 이산 값 스냅 시 정밀도 손실이 수정되었습니다.
한편 1.13 alpha03부터 Compose 라이브러리의 compileSdk가 37.1로 올라갔습니다.
앱과 라이브러리의 compileSdk도 함께 올려야 합니다.

실무 관점​

RC 단계에서는 프로덕션 적용보다 검증이 먼저입니다.
Slider를 쓰는 화면이 있다면 onValueChange 누락 여부를 컴파일로 확인하고, Kotlin 2.2와 compileSdk 37.1 변경은 별도 브랜치에서 빌드를 검증합니다.
MTS에서는 주문 수량이나 조건 설정처럼 Slider를 쓰는 화면이 있어, 변경점이 적용되는 화면을 목록으로 정리해 두는 편이 좋습니다.

마치며​

Compose 1.13은 API가 확정된 RC 단계에 들어섰고, Slider 필수 파라미터화와 Kotlin 2.2 요구가 가장 큰 변경점입니다.
stable 릴리스가 나오면 적용 범위를 정해 단계적으로 올리는 것이 좋습니다.

Android Dev Summit 2026 정리: 에이전트와 적응형 UI의 시대

2026년 11월 5일 · 약 5분

Android Developer

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.
2026년 10월 28일부터 29일까지 열린 Android Dev Summit 2026의 핵심 발표를 정리해드리겠습니다.

배경​

이번 서밋은 도구와 에이전트, 에이전트 경험 API, 적응형 UI, XR이라는 네 가지 방향으로 발표가 나뉘었습니다.
구글은 개발자가 원하는 코딩 에이전트를 직접 고를 수 있게 하고, 앱이 에이전트와 연결되는 방식을 넓히는 데 초점을 맞췄습니다.
공개된 내용 중 상당수는 이미 stable 단계에 도달했거나, 베타와 알파로 구분되어 공개되었습니다.
실무에서는 어느 발표가 당장 적용 대상인지, 어느 발표가 준비 단계인지 구분하는 것이 중요합니다.

Android Studio Rabbit 2 살펴보기​

Android Studio Rabbit 2가 stable로 공개되었습니다.
이제 Claude Agent, Codex, Antigravity를 비롯해 40개 이상의 ACP 호환 에이전트를 IDE 안에서 직접 고를 수 있습니다.
에이전트는 에뮬레이터와 빌드 시스템, Logcat 같은 Android Studio의 개발 도구를 함께 쓸 수 있습니다.
Gemini만 쓰던 구조에서 벗어나 팀이 이미 쓰고 있는 에이전트를 그대로 가져올 수 있게 된 점이 가장 큰 변화입니다.

Android CLI 살펴보기​

Android CLI도 에이전트 중심으로 기능이 넓어졌습니다.
Firebase 기반의 Android Device Streaming으로 실제 기기를 원격으로 테스트할 수 있습니다.
에이전트는 Jetpack Compose 프리뷰를 렌더링해서 에뮬레이터나 APK 배포 없이 화면을 바로 확인할 수 있습니다.
프로파일링은 Perfetto 기반의 시스템 트레이스를 수집해 콜드 스타트와 UI 끊김, 백그라운드 깨움을 분석합니다.
Analyze 기능은 앱 번들과 라이브러리의 난독화와 최적화, 축소 점수를 검사해 Play 업로드 전에 품질 문제를 찾습니다.
20개 이상의 영역을 다루는 30개 이상의 Android 스킬도 함께 공개되었습니다.

android init
android skills list

위 명령으로 에이전트용 Android CLI 환경을 초기화하고, 설치된 스킬 목록을 확인할 수 있습니다.
공식 에이전트 플러그인도 Antigravity용에 이어 Claude Code와 Codex용이 새로 나왔습니다.

에이전트 경험을 만드는 API 살펴보기​

앱이 에이전트의 도구가 되는 흐름도 이번 서밋의 한 축입니다.
AppFunctions는 앱 기능을 에이전트가 호출할 수 있게 만드는 통합 도구 호출 계층입니다.
이번 서밋에서 AppFunctions가 베타 단계에 들어섰습니다.
에이전트는 함수 이름과 설명만 보고 호출을 결정하므로, 이름과 KDoc이 곧 스키마라는 점을 염두에 두어야 합니다.

/**
 * 코스피 지수 요약 정보를 반환합니다.
 *
 * @param market 조회할 시장 코드입니다.
 */
@AppFunctionDeclaration(isDescribedByKDoc = true)
suspend fun getIndexSummary(
    market: String
): IndexSummary = withContext(Dispatchers.IO) {
    marketRepository.getIndexSummary(market)
}

A2UI for Jetpack Compose는 알파로 공개되었습니다.
에이전트가 텍스트 답변이 아니라 앱 자체 컴포넌트로 만든 인터랙티브 UI를 반환할 수 있게 됩니다.
네이티브 Jetpack Compose 렌더러가 들어가 앱 안에서 자연스럽게 동작합니다.

ML Kit의 새로운 Agentic API도 알파로 공개되었습니다.
Gemini Nano 4를 기반으로 함수 실행과 대화 기록, 오케스트레이션 루프를 자동으로 처리하고 가드레일도 포함합니다.
온디바이스 에이전트를 만들 때 서버 왕복 없이 기기 안에서 루프를 돌릴 수 있다는 점이 특징입니다.

Connected Apps Platform도 함께 소개되었습니다.
앱 서비스를 Gemini가 시스템 AI 에이전트로 동작하는 사용자에게 공유하는 구조입니다.
지금은 프로토타입 단계이며, 프로덕션 게시를 위해서는 미리보기 프로그램 등록이 필요합니다.

Compose 1.13과 적응형 개발 살펴보기​

다가오는 Compose 1.13 stable에는 적응형 레이아웃 지원이 들어갑니다.
Grid와 Flexbox가 stable로 전환되고, Progressive Blur와 Formatted Text가 새로 추가됩니다.
Navigation 3 1.2는 딥 링크 지원과 함께 stable이 되었습니다.
AppState는 Compose의 반응형 모델을 상태 계층까지 확장하는 알파 단계의 building block입니다.
기기 설정이 바뀌어도 상태를 유지하는 구조를 앱과 AI 에이전트가 함께 쓸 수 있게 만드는 것이 목표입니다.

적응형 개발은 폰과 폴더블, 태블릿, 노트북, 차량, XR까지 한 코드베이스로 대응하는 방향으로 정리되었습니다.
Compose adaptive skill이 업데이트되어 기존 Compose UI를 감사하고 키보드 단축키와 커서, 호버 상태, 툴팁을 자동으로 구현합니다.
내비게이션 패턴 이전과 Grid, Flexbox, mediaQuery 기반의 레이아웃 이전도 skill이 다룹니다.
미디어와 카메라 화면을 폴더블의 테이블탑 레이아웃으로 바꾸는 최적화도 포함되었습니다.

Way
Android Developer

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.
Android Dev Summit 2026에서 다시 강조된 Navigation 3 1.2의 딥링크 API에 대해 설명해드리겠습니다.

배경​

기존 Navigation 2에서는 딥링크를 내비게이션 그래프에 선언하고, 컨트롤러가 백스택을 관리했습니다.
Navigation 3에서는 방향이 달라졌습니다.
백스택을 개발자가 직접 상태로 소유하고, 화면 전환은 그 상태를 렌더링하는 방식입니다.
이런 구조에서는 딥링크 처리도 그래프 선언이 아니라, 요청을 받아 키로 변환하는 과정이 됩니다.
1.2.0 안정 버전(2026년 9월 23일 공개)은 이 과정을 위한 딥링크 API를 정식으로 제공합니다.
Kotlin Multiplatform 환경에서도 같은 API로 딥링크를 다룰 수 있다는 점이 특징입니다.

Navigation 3 1.2 딥링크 살펴보기​

딥링크 처리는 크게 세 단계로 나뉩니다.
요청 만들기, 매처 정의하기, 요청과 매처를 대조해 키 얻기가 그 순서입니다.
각 단계를 코드와 함께 살펴보겠습니다.

DeepLinkRequest 만들기​

DeepLinkRequest는 들어온 딥링크를 표현하는 객체입니다.
문자열 URI, DeepLinkUri, Android Intent 중 하나로 만들 수 있습니다.
URI 외에 액션이나 MIME 타입 같은 부가 정보는 타입 안전한 RequestExtras로 함께 담습니다.

import androidx.navigation3.runtime.deeplink.DeepLinkRequest
import androidx.navigation3.runtime.deeplink.DeepLinkUri
import androidx.navigation3.runtime.deeplink.requestExtras

// 문자열 URI로 요청 만들기
val request = DeepLinkRequest(uri = "https://www.example.com/home")

// DeepLinkUri로 요청 만들기
val deepLinkUri = DeepLinkUri("https://www.example.com/home")
val requestFromUri = DeepLinkRequest(uri = deepLinkUri)

// 액션과 MIME 타입을 함께 담기
val requestWithExtras = DeepLinkRequest(
    uri = "https://www.example.com/image",
    extras = requestExtras {
        put(DeepLinkRequest.ActionExtrasKey, "android.intent.action.VIEW")
        put(DeepLinkRequest.MimeTypeExtrasKey, "image/*")
    }
)

// Activity로 들어온 Intent에서 바로 만들기
val requestFromIntent = DeepLinkRequest(intent = intent)

RequestExtras는 키와 값의 쌍을 타입에 맞게 보관하는 컨테이너입니다.
예전처럼 문자열 키로 값을 꺼내 형변환하던 방식보다 실수가 줄어듭니다.

DeepLinkMatcher 정의하기​

DeepLinkMatcher는 요청을 어떤 내비게이션 키에 연결할지 정의합니다.
하나의 키에 여러 매처를 연결할 수 있습니다.
기본 제공되는 매처는 세 가지입니다.

import androidx.navigation3.runtime.deeplink.DeepLinkMatcher
import androidx.navigation3.runtime.deeplink.DeepLinkUri
import androidx.navigation3.runtime.deeplink.StaticKeyDeepLinkMatcher
import androidx.navigation3.runtime.deeplink.UriDeepLinkMatcher
import androidx.navigation3.runtime.deeplink.withBackStack

// 고정 화면으로 연결되는 매처
val homeMatcher = StaticKeyDeepLinkMatcher(
    HomeKey,
    listOf(DeepLinkMatcher.actionFilter(Intent.ACTION_VIEW))
)

// 경로 인자를 추출하는 매처
val userProfileMatcher = UriDeepLinkMatcher(
    DeepLinkUri("www.example.com/users/{id}"),
    serializer<UserProfileKey>()
).withBackStack { matchResult ->
    listOf(HomeKey, matchResult.key)
}

UriDeepLinkMatcher는 URI 패턴의 {id} 같은 플레이스홀더를 인자로 추출합니다.
withBackStack은 매칭에 성공했을 때 합성 백스택을 함께 만듭니다.
사용자가 딥링크로 상세 화면에 들어왔을 때, 뒤로 가기를 누르면 홈 화면으로 돌아가는 흐름을 이렇게 보장합니다.

요청 매칭하고 백스택 구성하기​

매처 목록을 준비했으면, 들어온 요청과 대조해 키를 얻습니다.
매칭 결과는 비교가 가능하므로, 여러 매처 중 가장 적합한 결과를 고를 수 있습니다.

val deepLinkMatchers = listOf(homeMatcher, userProfileMatcher)

val request = DeepLinkRequest(intent = intent)
val matchResult = deepLinkMatchers.firstNotNullOfOrNull { matcher ->
    matcher.match(request)
}

val backStack = rememberNavBackStack(
    matchResult?.key ?: HomeKey
)

이렇게 얻은 키를 rememberNavBackStack의 시작점으로 넘기면, 이후는 평소와 같은 NavDisplay 흐름으로 이어집니다.
딥링크로 들어온 경우와 앱 안에서 이동한 경우의 화면 렌더링 방식이 달라지지 않습니다.
한편 Activity를 딥링크로 열려면 AndroidManifest.xml에 intent-filter를 등록하는 절차는 여전히 필요합니다.

예측 뒤로 가기와 결과 전달​

1.2에는 딥링크 외에도 두 가지 보강이 함께 들어 있습니다.
첫 번째는 예측 뒤로 가기 연결을 단순화하는 NavigationBackHandler와 rememberNavigationEventState입니다.
전환 도중에 뒤로 제스처가 들어와도 애니메이션이 어긋나지 않도록 처리합니다.
두 번째는 화면 간 결과 전달을 위한 Result API입니다.
ResultEventBus를 통해 항목 간 결과를 주고받고, ResultEffect로 흐름 형태로 수집합니다.

실무 관점​

MTS에서 딥링크는 푸시 알림, 공유 링크, 외부 연동 등 여러 진입점으로 연결됩니다.
딥링크로 바로 열리는 화면이 민감 정보를 다룬다면, 진입 전에 로그인 상태와 접근 권한을 먼저 확인해야 합니다.
합성 백스택은 뒤로 가기 경로를 자연스럽게 만들지만, 스택에 쌓이는 화면이 민감 화면을 거치지 않는지 함께 검토해야 합니다.

마치며​

Navigation 3 1.2는 딥링크를 그래프 선언이 아니라 요청과 매칭의 문제로 정리했습니다.
타입 안전한 요청과 합성 백스택 덕분에, 진입 경로가 달라도 화면 흐름을 일관되게 유지할 수 있습니다.

2026년 10월 30일 · 약 2분
Way
Android Developer

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.
2026년 10월 28일에 첫 알파로 공개된 AppState StateStore에 대해 설명해드리겠습니다.

배경​

Compose 상태는 보통 화면이나 ViewModel 안에 머무릅니다.
앱 전역에서 공유해야 하는 상태는 계층을 옮길 때마다 전달 코드가 늘어납니다.
상태를 앱 계층으로 끌어올리면 공유와 저장이 한곳에서 관리됩니다.
StateStore는 이 역할을 맡기 위해 새로 공개된 라이브러리입니다.

StateStore 살펴보기​

Compose 런타임 기반의 상태 저장소​

StateStore는 Compose 런타임을 기반으로 동작합니다.
스냅샷 상태를 앱 계층으로 끌어올려 커스텀 연동을 제공하는 래퍼입니다.
화면이 사라져도 상태의 수명을 앱 수준에서 유지할 수 있습니다.

DataStore 연동으로 상태 유지하기​

statestore-datastore 아티팩트는 상태 영속성을 제공합니다.
syncToDataStore로 스냅샷 상태를 DataStore 파일과 동기화할 수 있습니다.
앱을 다시 시작해도 이전 상태를 복원할 수 있습니다.

class MyApplication : Application() {
    val stateStore = StateStore()
    private val scope = CoroutineScope(SupervisorJob() + Dispatchers.Default)

    override fun onCreate() {
        super.onCreate()
        scope.launch {
            launch {
                try {
                    stateStore.syncToDataStore(
                        dataStoreFile("settings").absolutePath,
                        this
                    )
                } catch (e: Exception) {
                    e.printStackTrace()
                }
            }
        }
    }
}

의존성 추가하기​

Android 타깃 기준 의존성은 다음과 같습니다.

dependencies {
    implementation("androidx.appstate.statestore:statestore:1.0.0-alpha01")
    implementation("androidx.appstate.statestore:statestore-datastore:1.0.0-alpha01")
}

함께 공개된 Transform​

같은 날짜에 appstate-transform 아티팩트도 첫 알파로 공개되었습니다.
이 글에서는 StateStore의 개념과 저장 연동에 집중합니다.

배경​

Compose Runtime은 Compose의 상태 모델과 컴파일러 플러그인이 대상으로 하는 핵심 런타임입니다.

이제 프레임워크가 잘못된 코드를 바로 가리켜 줍니다.
derivedStateOf도 같은 계산 블록 규칙을 사용하므로 동일한 주의가 필요합니다.

// 변경 전 — 계산 블록 안에서 상태를 쓰면 IllegalStateException이 발생합니다.
val totalPrice = remember {
    derivedStateOf {
        // 아래와 같은 쓰기는 1.13 베타부터 허용되지 않습니다.
        // discountApplied.value = true
        cartItems.sumOf { it.price }
    }
}

// 권장 방식 — 상태 변경은 이벤트 핸들러에서 수행합니다.
fun onItemAdded(item: CartItem) {
    cartItems.add(item)
}

val totalPrice = remember {
    derivedStateOf { cartItems.sumOf { it.price } }
}

ComputedState 메모리 누수 수정​

beta02에서는 ComputedState와 관련된 수정이 들어갔습니다.
기록된 상태 값이 해제되지 않던 메모리 누수가 수정되었습니다.
계산 블록이 Snapshot.withoutReadObservation을 호출할 때 무효화가 제대로 되지 않던 문제도 함께 수정되었습니다.
파생 상태를 많이 사용하는 화면에서는 메모리와 무효화 동작을 함께 점검해 볼 만합니다.

  • CompositionObserver는 한 컴포지션 패스당 한 번만 해석됩니다.

  • Float.NaN이나 Double.NaN을 @Composable 함수에 전달하면 리컴포지션 스킵이 되지 않던 문제가 수정되었습니다.
  • Dp.Unspecified이 Float.NaN 기반이라 이 수정과 직접 연결됩니다.

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.
2026년 10월 21일 공개된 A2UI 1.0.0-alpha02에 대해 설명해드리겠습니다.

배경​

AI 에이전트는 이제 작업을 추론하고 도구를 호출하고 대화를 이어갈 수 있습니다.
그런데도 에이전트가 사용자에게 네이티브 화면을 보여주는 일은 여전히 어렵습니다.
에이전트는 앱이 어떤 컴포넌트를 가지고 있는지 모르기 때문에, 날짜 선택기나 확인 버튼 같은 실제 UI를 건네줄 수 없습니다.
A2UI는 이 간극을 메우기 위한 프로토콜입니다.

A2UI 살펴보기​

A2UI의 핵심 아이디어는 단순합니다.
에이전트가 임의의 UI 코드를 만들어내는 대신, 클라이언트가 미리 정해둔 카탈로그 안에서만 UI를 조합합니다.

카탈로그가 계약이 됩니다​

모든 A2UI 인터페이스는 컴포넌트 카탈로그를 중심으로 동작합니다.
카탈로그는 에이전트가 사용할 수 있는 UI 요소와 속성, 함수를 선언합니다.
에이전트는 카탈로그에 등록되지 않은 컴포넌트를 만들어낼 수 없으므로, 렌더링 결과가 예측 가능한 범위를 벗어나지 않습니다.

임의 코드 실행이 없습니다​

A2UI 렌더러의 가장 중요한 성질은 임의 코드를 실행하지 않는다는 점입니다.
에이전트는 구조화된 데이터를 보내고, 클라이언트는 그 데이터를 네이티브 Compose 컴포넌트로 렌더링합니다.
서버에서 온 설명이 앱 안에서 코드로 실행되는 일이 없으므로, 신뢰 경계를 넘는 UI도 안전하게 다룰 수 있습니다.

Jetpack A2UI 렌더러의 구조​

Jetpack의 A2UI 렌더러는 디자인 시스템과 무관한 렌더링 엔진과 구체적인 카탈로그 구현을 분리합니다.
데이터 계층인 a2ui-model과 a2ui-engine이 프로토콜 메시지를 파싱하고 처리합니다.
UI 계층인 compose-runtime과 compose-ui가 앱과 카탈로그를 위한 API를 제공합니다.
Material 3 컴포넌트로 구성된 기본 카탈로그도 함께 제공되어, 별도 카탈로그 없이 바로 시작할 수 있습니다.

dependencies {
    implementation("androidx.a2ui:a2ui-engine:1.0.0-alpha02")
    implementation("androidx.a2ui:a2ui-model:1.0.0-alpha02")
    implementation("androidx.a2ui.compose:compose-runtime:1.0.0-alpha02")
    implementation("androidx.a2ui.compose:compose-ui:1.0.0-alpha02")
}

alpha02에서 바뀐 점​

이번 alpha02에서는 기본 카탈로그의 함수 목록이 인터페이스로 바뀌었습니다.
구현체는 openUrl만 구현하면 되고, 나머지 함수는 기본 구현을 쓰거나 개별적으로 재정의할 수 있습니다.
클라이언트가 렌더링할 수 있는 카탈로그를 먼저 알리는 기능도 추가되어, 에이전트와 렌더러 사이의 capability 협상이 가능해졌습니다.

val catalog = materialA2uiBasicCatalogV1(
    functions = A2uiBasicCatalogV1.Functions(context)
)

실무 관점​

아직 알파 단계이므로, 프로덕션 화면에 바로 적용할 라이브러리는 아닙니다.
다만 MTS의 챗봇이나 상담 흐름처럼, 에이전트가 화면을 제시해야 하는 기능에는 참고할 만한 설계입니다.
카탈로그를 계약으로 삼는 방식은, 에이전트 출력이 화면을 망가뜨리는 위험을 구조적으로 줄여줍니다.
도입을 검토한다면, 렌더링할 컴포넌트 목록을 카탈로그로 먼저 정리하는 것부터 시작하는 편이 좋습니다.

2026년 10월 7일에 공개된 Compose 1.13.0-beta01과 Material3 1.5.0-beta01의 변경 사항에 대해 설명해드리겠습니다.

배경​

2026년 10월 7일, Compose BOM의 두 축이 베타로 나왔습니다.
androidx.compose.runtime:runtime:1.13.0-beta01와 androidx.compose.material3:material3:1.5.0-beta01입니다.
같은 날 stable도 runtime 1.12.1과 material3 1.4.0으로 함께 릴리스되었습니다.
둘 다 아직 베타지만 소스 브레이킹 변경이 포함되어 있어, 지금 미리 파악해 두면 나중에 스테이블로 올릴 때 수월합니다.
공식 AndroidX 릴리스 노트(Material3, Runtime)를 기준으로 실무에 닿는 변경만 정리합니다.
참고로 이 글은 최근 30일 이내 릴리스를 다루는 심화 해설입니다.

무엇이 달라졌는지​

Slider와 RangeSlider의 상태 분리​

가장 큰 소스 브레이킹 변경입니다.
Material3 1.5.0-alpha29에서 Slider와 RangeSlider의 onValueChange가 필수 파라미터가 되었고, 파라미터 순서도 바뀌었습니다.
무상태(stateless) 오버로드는 deprecated(일부는 hidden) 처리되었고, 상태를 별도 객체로 분리하는 방식으로 이관이 권장됩니다.

// 기존 방식 (1.5.0에서 deprecated)
var value by remember { mutableFloatStateOf(0.5f) }
Slider(value = value, onValueChange = { value = it })

// 새 방식 — 상태를 별도 객체로 분리
val state = remember { SliderState(value = 0.5f) }
Slider(state = state)

var range by remember { mutableStateOf(0.2f..0.8f) }
RangeSlider(value = range, onValueChange = { range = it })
// → val state = remember { RangeSliderState(startValue = 0.2f, endValue = 0.8f) }
//   RangeSlider(state = state)

함께 바뀐 사항은 다음과 같습니다.

  • RangeSliderState의 activeRangeStart와 activeRangeEnd가 startValue와 endValue로 개명되었습니다.
  • SliderState는 더 이상 공개적으로 DraggableState를 구현하지 않습니다. 바이너리 호환 유지를 위해 DraggableState는 SliderState에 복원되었고, onValueChange가 nullable인 오버로드는 hidden deprecated로 유지됩니다.

소스 코드는 고쳐야 하지만 이미 빌드된 바이너리는 깨지지 않게 설계된 셈입니다.

computedStateOf의 읽기 전용 강제​

runtime 1.13.0-beta01부터 computedStateOf의 계산 블록 안에서 state에 쓰면 IllegalStateException이 던져집니다.
이전에도 쓰면 안 되는 패턴이었지만 실제로는 조용히 넘어가거나 이상한 무효화(invalidation)를 일으키곤 했습니다.
이는 외부 기여로 들어온 SnapshotStateObserver 읽기 시 예상 밖 무효화 수정과 같은 맥락입니다.
계산 블록은 순수하게 읽고 반환만 한다는 규칙이 강제됩니다.

Kotlin 2.2와 AGP 요구사항​

Compose 라이브러리들이 Kotlin 2.2를 타깃으로 빌드되고, kotlinc 2.2가 필요합니다.
또 androidx.lifecycle:lifecycle-runtime:2.10.0 의존성 업데이트 때문에, 번들된 lifecycle lint 체크가 동작하려면 AGP 9.5.0-alpha04 이상이 필요합니다.
툴체인 전체가 2.2와 37.1 라인으로 움직이고 있다는 신호입니다.

compileSdk 37.1 전이적 요구​

Compose 라이브러리의 compileSdk가 37.1로 올라갔습니다.
이는 Compose를 쓰는 모든 앱과 라이브러리도 compileSdk를 37.1로 올려야 한다는 뜻입니다.
Android 17(targetSdk 37) 대응을 아직 하지 않았다면, Compose 1.13과 1.5 스테이블로 올라가는 시점이 강제 마이그레이션 시점이 됩니다.

그 외 변경 사항​

  • 비밀번호 필드의 기본 난독화 방식이 RevealLastTyped에서 TextObfuscationMode.System으로 바뀝니다. SecureTextField와 OutlinedSecureTextField의 기본값 변경입니다.
  • Float.NaN 관련 리컴포지션 스킵 버그가 수정되었습니다. Dp.Unspecified(내부적으로 Float.NaN 기반)를 인자로 받은 컴포저블이 인자가 변하지 않았는데도 리컴포지션을 스킵하지 못하던 문제입니다.
  • BottomAppBar와 연관 API가 스테이블로 승격되었고, BasicAlertDialog가 Experimental을 졸업했습니다.
  • LocalMotionScheme이 제거되고 MaterialTheme.motionScheme으로 교체되었습니다.
  • ExposedDropdownMenu가 멤버 함수에서 ExposedDropdownMenuBoxScope의 확장 함수로 변경되어 import를 새로 잡아야 합니다.
  • 새로운 material3-ripple 라이브러리가 추가되었습니다. 기존 material-ripple의 대체이며 inset focus ring을 지원합니다.
  • DatePicker가 월 이동 가용성을 표시 월 인덱스에서 직접 계산해 1프레임에 해결되도록 개선되었습니다.
  • TopAppBarDefaults.enterAlwaysScrollBehavior의 reverseLayout 오버로드가 1.4 호환을 위해 deprecated(경고)로 복원되었습니다.
  • HorizontalCenteredHeroCarousel의 maxItemWidth가 preferredItemWidth로 개명되었고, 멀티애스펙트 캐러셀 API가 전역 carouselParallaxScrollEffect 모디파이어로 단순화되었습니다.
  • runtime에서는 movableContent 이동 시 wrapper 슬롯을 들고 있던 LinkComposer 메모리 누수가 수정되었고, CompositionObserver가 패스당 1회 해결되도록 변경되었으며, 오프-메인 스레드 ComposeTracer가 지원됩니다.

실무에서 주의할 점​

  • Slider 사용처를 전수 조사해야 합니다. 금융 앱에 수수료 슬라이더나 투자 금액 조절 같은 Slider와 RangeSlider가 있다면 1.5.0 스테이블 전에 상태 분리 방식으로 바꿔 두는 것이 좋습니다. onValueChange 필수화는 컴파일 에러로 드러나지만, 파라미터 순서가 바뀐 오버로드는 시그니처 자체가 바뀌어 에러가 나거나 deprecated로 걸리므로 리뷰는 한 번씩 필요합니다.
  • computedStateOf와 derivedStateOf 블록 안에서 값을 쓰는 코드가 있는지 검사해야 합니다. IllegalStateException은 런타임에 발생하므로, 코드 검색으로 계산 블록 안에 대입이 있는지 미리 확인하는 것이 안전합니다.
  • Kotlin 2.2와 AGP, compileSdk 37.1은 묶어서 계획해야 합니다. Compose 1.13은 Kotlin 2.2를, lint는 AGP 9.5.0-alpha04 이상을, Compose는 compileSdk 37.1을 각각 요구하므로 서로 의존합니다. 하나씩 따로 올리기보다 한 스프린트에 묶어 CI에서 함께 검증하는 편이 낫습니다.
  • 비밀번호 입력 UX 변경은 기획과 디자인 부서와 공유해야 합니다. 기본값이 System으로 바뀌면 타이핑 중 마지막 글자를 잠깐 보여주는 동작이 사라집니다. 보안 정책상 환영할 변화지만, 릴리스 노트 한 줄로 바뀌는 UX라 미리 공유하지 않으면 버그 문의가 들어올 수 있습니다.
  • 베타 릴리스이므로 스테이블 전에 API가 또 바뀔 수 있습니다. 이 글에서 다룬 내용은 베타 시점에 확정된 변경 기준입니다.

마치며​

Compose 1.13과 Material3 1.5는 베타 단계에서 미리 확인해 두면 스테이블 상향이 훨씬 수월해집니다.
특히 Slider의 상태 분리와 툴체인 요구사항은 일정을 잡아 미리 준비하는 것이 좋습니다.

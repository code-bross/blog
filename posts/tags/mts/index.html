Kotlin 2.5.0-RC2에서 컴파일러 실행에 JDK 17이 필수가 됩니다

2026년 11월 27일 · 약 3분
Way
Android Developer

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.
2026년 11월 25일에 공개된 Kotlin 2.5.0-RC2의 JDK 17 최소 요구사항과 Java 28 바이트코드 지원에 대해 설명해드리겠습니다.
이번 변경은 컴파일러를 실행하는 JDK 버전과 직접 관련이 있어, 빌드 환경을 먼저 점검해야 합니다.

배경​

Kotlin 컴파일러는 그동안 JDK 8에서도 실행할 수 있었습니다.
2.5.0-Beta1부터 JDK 17보다 오래된 버전으로 컴파일러를 실행하면 경고가 나왔습니다.
2.5.0-RC2부터는 경고가 아니라 오류가 발생합니다.
컴파일러를 실행하는 JDK의 최소 버전이 17로 올라간 것입니다.
JetBrains는 새 Java 라이브러리를 활용하고 Gradle과 Maven과의 호환성을 유지하기 위해 최소 버전을 올렸다고 설명했습니다.

Kotlin 2.5.0-RC2의 JDK 요구사항 살펴보기​

컴파일러 실행에 JDK 17 이상이 필요합니다​

Kotlin 2.5.0-RC2부터 JDK 17보다 오래된 JDK로 Kotlin 컴파일러를 실행하면 빌드가 오류로 멈춥니다.
대상은 앱이 실행될 때 쓰는 런타임 JDK가 아니라, 컴파일러 자체를 실행하는 JDK입니다.
기존 프로젝트가 JDK 8이나 JDK 11로 빌드되고 있었다면, Kotlin 버전을 올리는 시점에 함께 확인해야 합니다.
이 변경은 2.5.0 정식 릴리스에서도 그대로 이어질 예정입니다.

일시적으로 오류를 피하는 방법​

아직 JDK를 올릴 수 없는 프로젝트에서는 -Xallow-pre-17-runtime-jdk 컴파일러 옵션을 추가하면 오류를 피할 수 있습니다.
이 옵션은 임시 방편이며, Kotlin 2.5.20이나 2.6.0에서는 제거될 예정입니다.
따라서 옵션을 넣는 것으로 끝내지 말고, JDK 17 이상으로 올리는 일정을 함께 잡는 것이 좋습니다.

kotlin {
    compilerOptions {
        freeCompilerArgs.add("-Xallow-pre-17-runtime-jdk")
    }
}

Java 28 바이트코드 생성 지원​

Kotlin 2.5.0-RC2부터 컴파일러는 Java 28 바이트코드를 포함하는 클래스를 생성할 수 있습니다.
JVM 타깃 버전을 높이는 프로젝트에서는 새로운 바이트코드 버전을 선택할 수 있게 되었습니다.
다만 Java 28 자체는 아직 정식 출시 전이므로, 당장 운영 코드의 타깃을 올리기보다는 지원 범위가 넓어졌다는 점으로 이해하는 것이 좋습니다.

프로젝트의 JDK 확인하기​

Gradle 프로젝트에서는 Kotlin DSL의 jvmToolchain으로 컴파일에 쓸 JDK 버전을 지정할 수 있습니다.
다음과 같이 지정하면 컴파일러가 JDK 17로 실행됩니다.

kotlin {
    jvmToolchain(17)
}

현재 빌드에 쓰이는 JDK는 ./gradlew -version 명령으로 확인할 수 있습니다.
출력되는 JVM 항목이 17보다 낮다면, gradle.properties의 org.gradle.java.home 설정이나 CI 에이전트에 설치된 JDK를 확인해야 합니다.
Android Studio는 내장 JDK를 함께 제공하므로, 로컬 빌드와 CI 빌드의 JDK가 다를 수 있다는 점도 함께 점검해야 합니다.

실무 관점​

MTS처럼 규모가 큰 프로젝트에서는 로컬 환경보다 CI 에이전트의 JDK 버전을 먼저 확인하는 것이 좋습니다.
에이전트 이미지에 JDK 8이나 JDK 11만 설치되어 있다면, Kotlin 2.5.0으로 올리는 순간 빌드가 멈춥니다.
옵트아웃 옵션은 마이그레이션 기간에만 쓰고, 정식 릴리스 전에 JDK 17 이상으로 전환하는 일정을 잡는 것이 안전합니다.
RC 버전이므로 릴리스 브랜치에는 적용하지 않고, 별도 브랜치에서 동작을 확인하는 것이 좋습니다.

마치며​

Kotlin 2.5.0-RC2부터 컴파일러 실행에는 JDK 17 이상이 필요합니다.
빌드 환경을 먼저 점검하고, Java 28 바이트코드 지원과 함께 정식 릴리스를 준비하는 것이 좋습니다.

Kotlin 2.5.0-RC2의 KMP 새 컴파일 방식과 게시 포맷 살펴보기

2026년 11월 27일 · 약 3분
Way
Android Developer

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.
2026년 11월 25일에 공개된 Kotlin 2.5.0-RC2의 Kotlin Multiplatform 새 컴파일 방식과 새 게시 포맷에 대해 설명해드리겠습니다.
두 변경 모두 실험적 기능이지만, 멀티플랫폼 프로젝트의 빌드와 게시 방식을 바꿀 수 있는 내용입니다.

배경​

Kotlin Multiplatform 프로젝트에서는 공통 소스셋의 코드를 컴파일러와 IDE가 다르게 해석하는 경우가 있었습니다.
오버로드 해석이나 타입 추론에서 IDE 분석과 컴파일러 판단이 달라지면, IDE에서는 되던 코드가 빌드에서 실패하기도 합니다.
게시 측면에서는 타깃을 추가할 때마다 게시 파일이 늘어나 Maven Central의 게시 크기 제한에 걸리는 문제도 있었습니다.
이번 릴리스에서는 이 두 가지 문제를 다루는 실험적 기능이 함께 공개되었습니다.

KMP 새 컴파일 방식과 게시 포맷 살펴보기​

공통 소스셋을 따로 컴파일하는 새 방식​

Kotlin 2.5.0-RC2에서는 Kotlin Multiplatform을 위한 새로운 실험적 컴파일 방식이 추가되었습니다.
이 방식에서는 컴파일러가 공통 소스셋을 IDE와 같은 기준으로 처리합니다.
공통 코드가 플랫폼 전용 선언으로 잘못 해석되는 일을 막고, 오버로드 해석과 타입 추론의 일관성을 높입니다.
공통 소스셋에 대한 증분 컴파일을 구현하는 기반도 됩니다.
자세한 내용은 Kotlin 2.5.0-RC2 변경 사항에서 확인할 수 있습니다.

.kar 아카이브 게시 포맷​

Kotlin 2.5.0-RC2에서는 멀티플랫폼 라이브러리를 위한 새로운 실험적 게시 포맷이 추가되었습니다.
새 포맷은 JVM과 Android을 제외한 플랫폼 아티팩트를 하나의 .kar 아카이브로 게시합니다.
.kar 파일은 ZIP 아카이브를 XZ로 한 번 더 압축한 형태입니다.
타깃을 추가해도 새 파일이 생기지 않으므로, 게시물 전체 크기가 크게 늘어나지 않습니다.
JetBrains가 예시로 든 cryptography-kotlin 라이브러리에서는 게시 파일이 7,539개에서 1,036개로, 전체 크기가 91MB에서 23MB로 줄었습니다.

모듈 단위로 새 포맷을 켜려면 빌드 스크립트에 다음과 같이 설정합니다.

kotlin {
    publishing {
        publicationFormat.set(KotlinPublicationFormat.KOTLIN_ARCHIVE)
    }
}

프로젝트의 모든 모듈에 적용하려면 gradle.properties에 다음 속성을 추가합니다.

kotlin.publicationFormat=KOTLIN_ARCHIVE

새 포맷으로 게시하는 기능은 아직 실험적이지만, 새 포맷으로 게시된 아티팩트를 가져다 쓰는 기능은 모든 프로젝트에서 이미 사용할 수 있습니다.
이 변경은 라이브러리를 게시하는 쪽에만 해당하며, 최종 앱을 만드는 개발자에게는 직접적인 영향이 없습니다.

실무 관점​

새 컴파일 방식은 공통 소스셋의 동작을 바꾸는 실험적 기능입니다.
적용하기 전에는 별도 브랜치에서 기존 테스트가 그대로 통과하는지 확인하는 것이 좋습니다.
.kar 게시 포맷은 MTS처럼 최종 앱을 만드는 프로젝트보다는, 내부 공용 라이브러리를 Maven에 게시하는 경우에 의미가 있습니다.
게시 크기가 제한에 걸려 타깃 추가를 미루고 있었다면, 새 포맷을 검토해 볼 만합니다.
두 기능 모두 실험적이므로, 정식 릴리스에서 동작이 바뀔 수 있다는 점을 고려해야 합니다.

마치며​

Kotlin 2.5.0-RC2의 새 컴파일 방식은 공통 소스셋의 해석을 IDE와 일치시키는 방향으로 나아가고 있습니다.
새 게시 포맷은 멀티플랫폼 라이브러리의 게시 크기를 크게 줄여, 타깃 확장의 부담을 덜어줍니다.

Kotlin 2.5.0-RC 살펴보기 — 이름으로 꺼내는 구조 분해

2026년 11월 24일 · 약 4분
Way
Android Developer

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.
11월 11일에 공개된 Kotlin 2.5.0-RC에서 안정화된 이름 기반 구조 분해에 대해 설명해드리겠습니다.

배경​

구조 분해는 객체를 여러 변수로 한 번에 나누는 문법입니다.
데이터 클래스의 값을 꺼낼 때 자주 사용합니다.
지금까지의 구조 분해는 위치 기반이었습니다.
변수는 프로퍼티 순서대로 componentN() 함수의 결과와 연결되었습니다.
이 방식에서는 변수 이름과 프로퍼티 이름이 달라도 컴파일러가 아무런 경고를 내지 않았습니다.
순서만 맞으면 이름이 뒤바뀐 채로 값이 들어가도 그대로 동작했습니다.
프로퍼티 순서가 바뀌면 받는 쪽 코드도 함께 바꿔야 했습니다.
이름 기반 구조 분해는 이 문제를 해결하기 위해 도입되었습니다.
변수를 위치가 아니라 프로퍼티 이름으로 연결하는 방식입니다.

이름 기반 구조 분해 살펴보기​

이름 기반 구조 분해는 Kotlin 2.5.0-RC에서 only-syntax 모드로 안정화되었습니다.
only-syntax 모드는 이제 기본값이므로, 별도의 컴파일러 옵션을 지정하지 않아도 새 문법을 사용할 수 있습니다.
기존 문법의 동작은 그대로 유지됩니다.
하나씩 살펴보겠습니다.

기존 방식의 문제​

위치 기반 구조 분해에서는 변수가 선언된 순서대로 값이 들어갑니다.
다음 예시에서 email 변수에는 username 값이 들어갑니다.

data class User(val username: String, val email: String)

fun main() {
    val user = User("alice", "alice@example.com")

    val (email, username) = user
    println(email) // alice
    println(username) // alice@example.com
}

email이라는 이름으로 username 값을 받는 코드가 컴파일됩니다.
실행 결과도 오류가 아니라 잘못된 값으로 나옵니다.
이런 실수는 코드 리뷰에서도 놓치기 쉽습니다.

새 문법​

이름 기반 구조 분해는 변수 앞에 val을 붙이는 명시적 형식을 사용합니다.
변수는 프로퍼티 이름과 연결됩니다.
이름을 바꿔서 받고 싶으면 =으로 새 이름을 지정할 수 있습니다.

data class User(val username: String, val email: String)

fun main() {
    val user = User("alice", "alice@example.com")

    (val mail = email, val name = username) = user
    println(name) // alice
    println(mail) // alice@example.com
}

mail 변수에는 email 프로퍼티 값이 들어갑니다.
name 변수에는 username 프로퍼티 값이 들어갑니다.
선언 순서와 프로퍼티 순서는 달라도 됩니다.
이름이 기준이 되므로, 프로퍼티 순서가 바뀌어도 받는 쪽 코드는 그대로 동작합니다.

세 가지 모드​

이름 기반 구조 분해의 동작은 컴파일러 옵션 -Xname-based-destructuring으로 조절할 수 있습니다.
모드는 세 가지입니다.
only-syntax 모드는 명시적 형식만 허용하고, 기존 구조 분해의 동작은 바꾸지 않습니다.
2.5.0-RC에서는 이 모드가 기본값입니다.
name-mismatch 모드는 위치 기반 구조 분해에서 변수 이름이 프로퍼티 이름과 다르면 경고를 냅니다.
complete 모드는 괄호 짧은 형식을 이름 기반으로 바꾸고, 위치 기반은 대괄호 문법으로 옮깁니다.

val point = Pair(10, 20)

// complete 모드에서 위치 기반 구조 분해는 대괄호를 사용합니다.
val [x, y] = point

대괄호 문법은 순서가 중요한 타입에 사용합니다.
Pair나 Triple, 리스트 같은 타입이 그 예입니다.
complete 모드는 아직 실험 단계이므로, 당장은 기본값인 only-syntax 모드로 시작하는 것이 안전합니다.

Full Value Class와 함께 쓰기​

Kotlin 2.5.0-RC에는 실험 기능인 full value class도 함께 들어왔습니다.
full value class에는 componentN() 함수가 없습니다.
그래서 위치 기반 구조 분해는 사용할 수 없고, 이름 기반 구조 분해로 값을 꺼냅니다.

value class Complex(val real: Double, val imaginary: Double)

fun main() {
    val value = Complex(1.0, 2.0)

    (val real, val imaginary) = value
    println(real) // 1.0
    println(imaginary) // 2.0
}

이름 기반 구조 분해는 full value class의 값을 꺼내는 기본 수단이 됩니다.
데이터 클래스와 full value class를 같은 방식으로 다룰 수 있습니다.

적용하기​

Kotlin 2.5.0-RC는 Version Catalog에서 Kotlin 버전을 교체하면 적용할 수 있습니다.

[versions]
kotlin = "2.5.0-RC"

[plugins]
kotlin-android = { id = "org.jetbrains.kotlin.android", version.ref = "kotlin" }

RC는 정식 출시 직전 단계이므로, 새 기능이 동결되고 안정화 작업이 중심이 됩니다.
only-syntax 모드는 안정화된 기능이지만, RC 버전 자체는 정식 버전이 아닙니다.

배경​

불변 API를 쓸 때는 반환값을 받는 것이 연산 그 자체입니다.
원본을 바꾸는 대신 새 값을 돌려주는 함수가 많기 때문입니다.
반환값을 받지 않으면 연산은 실행되지 않은 것과 같습니다.
그런데 지금까지는 반환값을 버려도 컴파일러가 아무런 경고를 내지 않았습니다.
코드는 정상적으로 컴파일되고, 테스트도 조용히 지나갔습니다.
화면에는 아무 변화가 없어야 할 변화가 없어도, 원인을 찾기까지 시간이 걸렸습니다.
미사용 반환값 검사는 이런 실수를 컴파일 시점에 잡아주는 기능입니다.
반환값을 써야 하는 호출의 결과를 무시하면 경고를 냅니다.

미사용 반환값 검사 살펴보기​

미사용 반환값 검사는 Kotlin 2.5.0-RC에서 안정화되고 기본으로 활성화되었습니다.
검사 대상은 Unit이 아닌 값을 돌려주는 표현식입니다.
결과를 변수에 담지 않고 그냥 호출만 하면 경고가 나옵니다.
하나씩 살펴보겠습니다.

어떤 경우에 경고가 나오는지​

가장 흔한 예는 컬렉션 변환 함수를 호출만 하고 결과를 쓰지 않는 경우입니다.
다음 코드는 원본 리스트를 바꾸지 않고 새 리스트를 돌려줍니다.
결과를 받지 않으면 아무 일도 일어나지 않습니다.

fun process(postalCodes: List<String>) {
    postalCodes.map { it.uppercase() } // 경고: Unused return value of 'map'
}

이진 연산의 결과를 무시하는 경우에도 경고가 나옵니다.
계산만 하고 결과를 어디에도 쓰지 않으면, 연산 자체가 의미가 없습니다.
다만 ++나 -- 같은 증감 연산은 경고 대상이 아닙니다.
condition || return처럼 오른쪽 식이 함수를 빠져나가는 단축 평가도 경고가 나오지 않습니다.

Check 모드와 Full 모드​

검사의 동작은 컴파일러 옵션 -Xreturn-value-checker로 조절할 수 있습니다.
모드는 세 가지입니다.
disable 모드는 검사를 끕니다.
check 모드는 표시된 함수의 반환값을 검사합니다.
표준 라이브러리의 대부분 함수가 이미 표시되어 있습니다.
2.5.0-RC에서는 check 모드가 기본값입니다.
full 모드는 프로젝트 안의 모든 함수를 검사 대상으로 봅니다.

// build.gradle.kts
kotlin {
    compilerOptions {
        freeCompilerArgs.add("-Xreturn-value-checker=check")
    }
}

기본값이 check 모드이므로, 별도 설정 없이도 표준 라이브러리 호출에 대한 검사가 동작합니다.
full 모드는 검사 범위가 넓어지므로, 팀에서 기준을 정한 뒤에 적용하는 것이 좋습니다.

내 함수에 표시하기​

검사 대상은 애너테이션으로 직접 지정할 수도 있습니다.
반환값을 반드시 써야 하는 함수에는 @MustUseReturnValues를 붙입니다.
반대로 반환값을 무시해도 되는 함수에는 @IgnorableReturnValue를 붙여 경고를 막습니다.

@MustUseReturnValues
fun calculateFee(amount: Long): Long {
    return amount * 3 / 100
}

@IgnorableReturnValue
fun tryRefresh(): Boolean {
    return true
}

calculateFee의 결과를 받지 않으면 경고가 나옵니다.
tryRefresh는 결과를 무시해도 경고가 나오지 않습니다.
라이브러리를 만드는 쪽에서는 이 표시가 호출하는 쪽의 실수를 막아줍니다.

의도적인 무시는 명시하기​

반환값을 일부러 쓰지 않는 경우도 있습니다.
함수를 부작용 때문에 호출하는 경우가 그 예입니다.
이럴 때는 val _ =으로 결과를 받는다고 명시하면 경고가 나오지 않습니다.

expr.apply {
    // 부작용을 위해 호출한다는 점을 명시합니다.
    val _ = computeResult()
}

스코프 함수와 함께 쓸 때는 주의가 필요합니다.
apply는 람다 결과를 Unit으로 바꾸므로, 안에서 호출한 함수의 반환값은 경고 대상이 됩니다.
let은 반환값의 무시 가능성을 그대로 전파합니다.
그래서 let 안에서는 전체 let 식의 결과를 무시할 때만 경고가 나옵니다.

expr.let {
    it.computeResult() // 전체 let 식의 결과를 무시할 때만 경고가 나옵니다.
}

기존 프로젝트에 올릴 때는 브랜치에서 먼저 빌드해 경고가 얼마나 나오는지 확인하는 것이 안전합니다.

@Composable

새 함수 살펴보기​

세 함수는 모두 Kotlin 2.5.0-RC에서 실험 API로 제공됩니다.
사용하려면 @OptIn(ExperimentalStdlibApi::class) 애너테이션을 붙이거나, 컴파일러 옵션으로 -opt-in=kotlin.ExperimentalStdlibApi를 지정해야 합니다.
함수마다 동작이 다르므로, 하나씩 살펴보겠습니다.

onTrue​

onTrue는 Boolean 값이 true일 때만 지정한 블록을 실행합니다.
블록을 실행한 뒤에는 원래의 Boolean 값을 그대로 돌려줍니다.
반환값을 그대로 돌려주기 때문에, 호출 결과를 변수에 담거나 체이닝을 이어갈 수 있습니다.

@OptIn(ExperimentalStdlibApi::class)
fun main() {
    val tags = mutableSetOf("kotlin", "jvm")

    // add()가 true를 돌려줄 때만 메시지를 출력합니다.
    val added = tags.add("wasm").onTrue {
        println("Tag added")
    }
    println(added) // Tag added
    // true
}

Set.add처럼 성공 여부를 Boolean으로 돌려주는 API와 함께 쓰면, 결과 확인과 로그를 한 줄로 묶을 수 있습니다.

onFalse​

onFalse는 Boolean 값이 false일 때만 지정한 블록을 실행합니다.
onTrue와 마찬가지로 원래의 Boolean 값을 그대로 돌려줍니다.
실패했을 때만 처리하고 싶은 경우에 사용합니다.

@OptIn(ExperimentalStdlibApi::class)
fun main() {
    val tags = mutableSetOf("kotlin", "jvm")

    // remove()가 false를 돌려줄 때만 메시지를 출력합니다.
    val removed = tags.remove("native").onFalse {
        println("Tag not found")
    }
    println(removed)
    // Tag not found
    // false
}

onTrue와 onFalse를 함께 쓰면, 성공과 실패 분기를 각각 한 줄씩 표현할 수 있습니다.

ifOrNull​

ifOrNull은 Boolean 값이 true일 때만 블록을 실행하고 그 결과를 돌려줍니다.
Boolean 값이 false이면 블록을 실행하지 않고 null을 돌려줍니다.
onTrue와 onFalse가 Boolean에 붙는 확장 함수인 것과 달리, ifOrNull은 Boolean을 인자로 받는 함수입니다.

@OptIn(ExperimentalStdlibApi::class)
fun main() {
    val tags = mutableSetOf("kotlin", "jvm", "wasm")

    // "wasm"이 tags 안에 있을 때만 메시지를 돌려줍니다.
    val message = ifOrNull("wasm" in tags) {
        "Wasm tag is available"
    }
    println(message)
    // Wasm tag is available
}

조건이 거짓이면 null이 나오므로, 엘비스 연산자나 널 안전 호출과 자연스럽게 이어집니다.
조건에 따라 값이 있을 수도 없을 수도 있는 경우에 if 식과 else 분기를 직접 쓰지 않아도 됩니다.

적용하기​

세 함수는 Kotlin 2.5.0-RC부터 사용할 수 있습니다.
Version Catalog에서 Kotlin 버전을 교체하면 RC를 적용할 수 있습니다.

[versions]
kotlin = "2.5.0-RC"

[plugins]
kotlin-android = { id = "org.jetbrains.kotlin.android", version.ref = "kotlin" }

RC는 정식 출시 직전 단계이므로, 새 기능이 동결되고 안정화 작업이 중심이 됩니다.
실험 API라는 점도 함께 고려해야 합니다.
정식 출시 전에 API 형태가 바뀔 수 있으므로, 핵심 로직보다는 주변 코드부터 적용하는 것이 안전합니다.

실무 관점​

국내 MTS 프로젝트에 적용한다면, 반환값을 그대로 돌려준다는 점을 활용하는 것이 좋습니다.
onTrue와 onFalse는 검사 결과를 그대로 이어주기 때문에, 기존 체이닝 구조를 바꾸지 않고 끼워 넣을 수 있습니다.
다만 블록 안에 무거운 로직을 넣으면 안 됩니다.
이 함수들은 조건부 실행을 짧게 표현하는 용도이지, 분기 로직 자체를 대신하는 용도가 아닙니다.
ifOrNull은 조건에 따라 값이 없을 수 있는 경우에만 쓰고, 조건이 복잡해지면 기존 if 식이 더 읽기 쉽습니다.
실험 API이므로, 적용한 위치를 목록으로 남겨 두면 정식 출시 때 확인하기 편합니다.

마치며​

onTrue와 onFalse, ifOrNull은 짧은 분기 패턴을 한 줄로 줄여주는 함수입니다.
조건 검사와 결과 처리를 분리하지 않고 묶을 수 있어, 작은 코드가 모이는 곳에서 효과가 큽니다.

R8 Consumer Keep Rules 살펴보기 — DEX 코드 최적화와 라이브러리 규칙 정리

2026년 11월 22일 · 약 6분
Way
Android Developer

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.
2026년 11월 17일에 공개된 Ship smarter keep rules에 대해 설명해드리겠습니다.

배경​

R8은 Android 앱 최적화 도구입니다.
사용하지 않는 코드를 제거하고, 남은 코드를 최적화하고 난독화합니다.
Google Play는 2027년 2월부터 DEX 코드 최적화 기준을 적용합니다.
DEX 코드가 10MB를 초과하는 앱은 난독화와 최적화, 축소 지표가 각각 25% 이상이어야 합니다.
기준에 미치지 못하면 앱 노출과 게시 기능에 영향을 받을 수 있습니다.
이 기준은 앱만의 문제가 아닙니다.
R8은 주어진 규칙 안에서만 최적화할 수 있습니다.
규칙에는 앱이 의존하는 라이브러리에 포함된 규칙도 들어갑니다.
국내 MTS처럼 규모가 큰 앱은 서드파티 SDK를 많이 사용합니다.
라이브러리가 넓은 규칙을 함께 보내면 앱 전체의 최적화 여지가 줄어듭니다.

R8 Consumer Keep Rules 살펴보기​

Consumer Keep Rules란​

Consumer Keep Rules는 라이브러리 안에 포함된 규칙입니다.
앱 수준 컴파일 과정에서 R8이 최적화하지 말아야 할 부분을 지정합니다.
리플렉션 대상과 네이티브 인터페이스가 제거되지 않도록 보호하는 역할을 합니다.
앱 개발자가 직접 규칙을 찾지 않아도 라이브러리를 그대로 쓸 수 있습니다.
의도적으로 좁게 작성된 규칙은 라이브러리와 앱 모두에 도움이 됩니다.
반대로 넓은 규칙은 사용하지 않는 코드까지 남겨 앱 성능에 영향을 줍니다.
Play Console에 추가된 DEX 코드 최적화 지표는 앱과 라이브러리 규칙의 합산 영향을 보여줍니다.

넓은 규칙이 문제가 되는 이유​

라이브러리 제공자는 SDK가 리플렉션으로 인한 충돌을 일으키지 않기를 바랍니다.
그래서 패키지 전체를 보존하는 넓은 규칙을 넣는 경우가 많습니다.
그러나 넓은 규칙은 R8의 전체 프로그램 최적화를 크게 제한합니다.
시작 시간과 다운로드 크기, 메모리 사용량, ANR 발생률에 영향을 줍니다.
성능을 중시하는 앱은 라이브러리 규칙을 직접 대체하는 규칙을 작성하기도 합니다.
이 경우 라이브러리 업데이트를 받아들이기 어려워지는 부작용도 생깁니다.

진입점만 보호하는 좁은 규칙​

리플렉션을 피할 수 없다면, 규칙은 실제로 리플렉션으로 접근하는 진입점만 지정하면 됩니다.
R8은 진입점을 기준으로 참조 그래프를 만들고, 참조되지 않는 클래스와 메서드, 필드를 제거합니다.
라이브러리를 이미 최적화하거나 난독화한 경우에도 같은 원칙이 적용됩니다.
앱 컴파일 단계에서 R8이 실제 사용되는 부분을 기준으로 다시 최적화하기 때문입니다.
서드파티 의존성에 대한 규칙도 좁게 작성해야 합니다.
대표적인 넓은 규칙 예시는 다음과 같습니다.

-keep public class com.google.android.gms.** { *; }

이 규칙은 앱이 다른 GMS 라이브러리에 대해 좁은 규칙을 갖고 있어도 이를 덮어씁니다.
많은 라이브러리가 이미 자체 Consumer Keep Rules를 제공하므로, 패키지 단위 규칙은 그 규칙까지 무력화할 수 있습니다.

리플렉션 대신 코드 생성 사용하기​

리플렉션은 컴파일 시점에 R8이 코드 사용 여부를 알 수 없게 만듭니다.
그래서 충돌을 막으려면 Keep Rules가 필요합니다.
가능하면 코드 생성을 사용하는 것이 좋습니다.
직렬화와 역직렬화, 의존성 주입이 대표적인 적용 대상입니다.
Hilt는 코드 생성을 사용하는 라이브러리입니다.
다만 모든 경우에 코드 생성이 맞는 것은 아닙니다.
선택적 의존성처럼 리플렉션이 필요한 패턴도 있습니다.
이 경우에는 필요한 진입점만 보호하는 좁은 규칙과 함께 사용합니다.

Jetpack Keep 어노테이션으로 규칙 생성하기​

Jetpack Keep 어노테이션은 현재 알파 단계입니다.
리플렉션 사용 위치에 어노테이션을 붙이면 빌드 시점에 Keep Rules를 생성합니다.
생성되는 규칙은 조건부 규칙입니다.
리플렉션을 호출하는 코드가 R8에 의해 남아야만 대상도 함께 남습니다.
사용하지 않는 기능의 규칙이 앱을 비대하게 만들지 않습니다.
AGP 8.7 이상에서 사용할 수 있고, 라이브러리와 플러그인 버전은 1.0.0-alpha01입니다.
설정은 libs.versions.toml에 다음과 같이 추가합니다.

[versions]
annotationKeep = "1.0.0-alpha01"

[libraries]
androidx-annotation-keep = { group = "androidx.annotation.keep", name = "keep", version.ref = "annotationKeep" }

[plugins]
androidx-annotation-keep = { id = "androidx.annotation.keep", version.ref = "annotationKeep" }

리플렉션으로 생성자를 호출하는 경우에는 @UsesReflectionToConstruct 어노테이션을 사용합니다.
다음 예시는 이름으로만 아는 클래스를 생성하는 함수입니다.

@UsesReflectionToConstruct(
    className = "com.example.ResourceLocatorImpl",
    parameterTypes = [],
)
fun loadResourceLocator(): ResourceLocator {
    val implClass = Class.forName("com.example.ResourceLocatorImpl")
    return implClass.getDeclaredConstructor().newInstance() as ResourceLocator
}

Lint가 어노테이션이 없는 리플렉션 호출을 찾아주고, 상당수는 자동으로 추가할 수도 있습니다.

조건부 Keep Rules로 선택적 기능 보호하기​

광고 미디에이션 어댑터처럼 선택적으로 포함되는 모듈에는 조건부 Keep Rules를 사용합니다.
앱에 해당 어댑터가 포함된 경우에만 기능을 보존합니다.
포함되지 않은 형식과 기능은 축소 대상이 됩니다.
Jetpack Keep 어노테이션을 쓰면 이런 조건부 규칙도 자동으로 생성할 수 있습니다.

규칙은 문서가 아니라 라이브러리에 포함하기​

Consumer Keep Rules는 라이브러리와 함께 배포해야 합니다.
문서에 규칙을 적어두면 앱 개발자가 직접 추가해야 하고 유지보수 부담이 생깁니다.
라이브러리를 업데이트하면서 클래스 이름이나 리플렉션 사용 방식이 바뀌면 문서도 함께 바꿔야 합니다.
버전을 거듭하면 앱에 더 이상 필요 없는 규칙이 쌓여 코드가 비대해집니다.

R8 Configuration Analyzer로 규칙 점검하기​

샘플 앱에서 R8을 활성화하고 핵심 사용자 여정을 테스트합니다.
R8 Configuration Analyzer는 축소와 최적화, 난독화 점수를 보여줍니다.
앱뿐 아니라 라이브러리에서 온 비효율적인 규칙도 함께 확인할 수 있습니다.
AGP 9.3 이상에서는 다음 태스크로 보고서를 만들 수 있습니다.

./gradlew :app:analyzeReleaseR8Config

보고서는 app/build/reports/r8/r8-config-analyzer-release.html 경로에 생성됩니다.
Android CLI의 analyze 명령은 AAR이나 JAR의 최적화 상태를 평가합니다.
보존된 메서드와 클래스, 필드를 확인하고 릴리스마다 비교하면 회귀를 잡을 수 있습니다.

android analyze --analysis=optimization -f json library.aar

Play SDK Console에서는 라이브러리 버전 사용량과 충돌도 함께 확인합니다.

릴리스 스택 트레이스는 난독화를 풀지 않고 읽기​

난독화된 스택 트레이스를 읽기 어렵다고 해서 keepnames를 쓰는 것은 권장되지 않습니다.
keepnames는 축소는 허용하지만 이름 변경 같은 추가 최적화를 막습니다.
Firebase Crashlytics와 Play Console, Android Studio Logcat은 스택 트레이스를 자동으로 복원합니다.
매핑 파일을 SDK Console에 업로드하면 SDK Console에서도 복원된 스택 트레이스를 볼 수 있습니다.

실무 관점​

국내 MTS는 서드파티 SDK가 많은 대형 앱입니다.
DEX 코드가 10MB를 초과할 가능성이 높고, 2027년 2월 기준이 직접 적용될 수 있습니다.
먼저 Play Console의 DEX 코드 최적화 지표와 R8 Configuration Analyzer 보고서를 확인합니다.
넓은 규칙을 보내는 라이브러리가 있다면 유지보수 담당자에게 보고서 수치와 함께 전달합니다.
앱 내부 규칙도 패키지 단위가 아니라 리플렉션 진입점 단위로 좁혀 나갑니다.
AGP 9.3 이상으로 올린다면 optimization 블록과 .keep 파일 형식도 함께 검토합니다.

마치며​

DEX 코드 최적화 기준은 앱과 라이브러리가 함께 지켜야 하는 기준입니다.
Consumer Keep Rules를 좁게 유지하면 앱은 더 작고 빨라집니다.

Android CLI 1.1 살펴보기 — 델타 설치와 Compose 트레이싱

2026년 11월 21일 · 약 4분
Way
Android Developer

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.
2026년 11월에 공개된 Android CLI 1.1.16919734에 대해 설명해드리겠습니다.

배경​

Android CLI는 터미널에서 Android 개발을 수행하는 공식 CLI입니다.
Android Studio를 열지 않고 빌드와 설치, 프로파일링, 기기 제어를 처리할 수 있습니다.
에이전트와 함께 쓰는 개발 흐름을 염두에 두고 만들어졌고, 스크립트와 CI에서도 그대로 쓸 수 있습니다.
2026년 11월 릴리스는 설치 속도와 프로파일링, 스크립트 친화성이 중심입니다.
새 명령이 추가된 릴리스가 아니라, 매일 쓰는 명령이 더 빠르고 정확해진 릴리스입니다.

Android CLI 1.1 살펴보기​

델타 설치로 재배치된 파일 재전송 방지​

android install과 android run은 변경되지 않은 파일을 다시 보내지 않습니다.
이번 릴리스에서는 APK 안에서 위치만 바뀐 파일도 재전송 대상에서 제외됩니다.
파일 내용이 그대로인데 위치만 이동한 경우, 설치 과정에서 다시 전송할 필요가 없어졌습니다.
반복 설치가 많은 개발 과정에서 체감되는 개선입니다.
기존 동작이 필요하면 --use-delta-install-instructions=COPY,DATA 옵션을 전달합니다.

android run
android install app-debug.apk

Compose 트레이싱으로 리컴포지션 원인 찾기​

android profiler systemtrace에 Compose 트레이싱이 들어왔습니다.
--enable=compose.composition을 전달하면 실행된 컴포저블 함수마다 슬라이스를 기록합니다.
--enable=compose.recomposition을 전달하면 리컴포지션을 일으킨 상태 읽기와 쓰기까지 함께 기록합니다.
앱에는 androidx.compose.runtime:runtime-tracing 1.13 이상이 필요합니다.
트레이스는 ZIP 파일로 저장되며, Android Studio 프로파일러에서 열어 확인할 수 있습니다.

android profiler systemtrace --enable=compose.recomposition

Perfetto 힙 덤프로 메모리 살펴보기​

android profiler heapdump capture에 --type=perfetto 옵션이 추가되었습니다.
Perfetto 트레이스 형태로 힙 덤프를 기록하며, 객체와 객체 사이의 참조를 포함합니다.
값 자체는 포함하지 않기 때문에 .hprof 파일보다 크기가 작습니다.
Android 12(API 31) 이상에서 동작하며, 프로파일이 가능하거나 디버깅이 가능한 앱이 필요합니다.
메모리 누수나 힙 증가를 살펴볼 때 가벼운 대안이 됩니다.

android profiler heapdump capture --type=perfetto

스크립트 친화적인 출력 형식​

android analyze --format=json의 출력 형식이 바뀌었습니다.
라이브러리 아티팩트(AAR, JAR)의 dexSizeBytes 필드는 이제 64비트 정수를 문자열로 직렬화합니다.
d8CompileResult와 r8CompileResult에 모두 적용됩니다.
JSON을 파싱하는 스크립트에서는 숫자가 아니라 문자열로 받는 점을 반영해야 합니다.
android input 하위 명령도 결과를 통일된 JSON 객체로 출력합니다.
표준 출력에는 results 목록이 나오고, 일치하는 요소가 없거나 여러 개가 일치하는 실패는 각 결과의 status 필드에 기록됩니다.
표준 에러의 텍스트를 파싱하지 않아도 결과를 처리할 수 있습니다.

android analyze --format=json app-debug.aab
android input tap text=Submit

에뮬레이터 명령의 종료 코드​

android emulator create와 start, stop, remove가 실패 시 0이 아닌 종료 코드를 반환합니다.
오류는 표준 에러로 출력됩니다.
이전에는 실패해도 스크립트에서 알아채기 어려웠던 경우가 있었습니다.
CI에서 에뮬레이터를 만들고 지우는 단계가 있다면, 종료 코드만으로 실패를 감지할 수 있습니다.

android emulator create --name test
android emulator start --name test

실무 관점​

국내 MTS 프로젝트에 적용한다면, 델타 설치 개선은 별도 설정 없이 바로 체감할 수 있습니다.
Compose 트레이싱을 쓰려면 runtime-tracing 의존성을 추가하고 Compose 1.13 이상을 사용해야 합니다.
리컴포지션 원인을 찾는 디버깅 단계에서만 켜고, 평소에는 끄는 것이 좋습니다.
android analyze 결과를 파싱하는 스크립트가 있다면 dexSizeBytes가 문자열로 바뀐 점을 먼저 확인합니다.
에뮬레이터를 다루는 CI 스크립트는 종료 코드 기반으로 실패 처리를 정리할 수 있습니다.

마치며​

Android CLI 1.1은 눈에 띄는 새 기능보다 매일 쓰는 명령의 완성도를 높인 릴리스입니다.
설치가 빨라지고, Compose 성능 원인을 터미널에서 바로 찾을 수 있게 되었습니다.

Android 개발자 인증, 2027년 전 세계로 확대됩니다

Android Developer

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.
2026년 11월에 공개된 Android 개발자 인증의 2027년 전 세계 확대 계획에 대해 설명해드리겠습니다.

배경​

Android 개발자 인증은 2025년에 발표된 보안 장치입니다.
악성 행위자가 반복적으로 위해를 확산시키는 일을 막기 위해, 앱을 배포하는 개발자의 신원을 확인합니다.
2026년 9월 30일부터 브라질과 인도네시아, 싱가포르, 태국에서 참여 스토어를 대상으로 사용자 보호가 적용됐습니다.
2027년 1월부터는 전 세계로 확대됩니다.
Play에만 배포하는 개발자에게도, Play 밖에서 배포하는 개발자에게도 해당되는 일정입니다.

2027년 확대 계획 살펴보기​

일곱 개 앱 배포처와 함께 시작합니다​

전 세계 확대는 2027년 1월에 시작합니다.
Google Play와 Galaxy Store, Honor, Oppo, Xiaomi, Transsion, Vivo까지 일곱 개 앱 배포처가 함께합니다.
이후 몇 개월에 걸쳐 모든 국가와 모든 설치 경로로 사용자 보호가 확대됩니다.
인증된 Android 기기에 설치되는 모든 앱이 대상입니다.
아직 신원을 확인하지 않았거나 앱을 등록하지 않았다면, 지금 완료할 수 있습니다.
앱 하나를 등록하는 데 10분도 걸리지 않습니다.

등록 현황과 확대 일정​

2026년 3월에 모든 개발자에게 인증이 개방된 이후, 전 세계에서 수백만 개의 앱이 등록됐습니다.
등록된 앱은 전 세계 Android 앱 설치의 99% 이상을 차지합니다.
배포처를 위한 안내에 따르면, 2027년 3월 1일을 준비 목표로 삼는 것이 좋습니다.
그때까지 모든 개발자는 신원 확인과 앱 등록을 마쳐야 배포가 끊기지 않습니다.
일정은 개발자 인증 안내 페이지에서 확인할 수 있습니다.

제한 배포 계정으로 가볍게 공유하기​

2026년 8월에는 학생과 취미 개발자를 위한 제한 배포 계정이 나왔습니다.
등록비나 정부 발급 신분증 확인 없이 앱을 공유할 수 있는 계정입니다.
공유할 수 있는 기기 수는 처음에는 20대였고, 이후 50대로 늘어났습니다.
테스트 범위에 맞춰 유연하게 공유할 수 있게 된 것입니다.
정식 배포가 아니라 가벼운 공유와 테스트가 목적이라면 이 계정을 검토할 수 있습니다.

등록 자동화 API로 CI에서 처리하기​

여러 앱을 관리하는 팀을 위해 등록 자동화 API가 나왔습니다.
Android Developer ID Status API는 패키지명이 이미 등록됐는지 확인합니다.
Android Developer Console API는 CI 파이프라인에서 패키지명을 직접 등록하고 관리할 수 있게 합니다.
앱이 많아질수록 손으로 등록하는 작업은 부담이 커집니다.
배포 파이프라인에 등록 상태 확인을 넣으면 누락을 미리 잡을 수 있습니다.

숙련된 사용자를 위한 고급 흐름​

미등록 앱을 설치하려는 숙련된 사용자를 위한 고급 흐름도 마련됐습니다.
사용자가 위험을 감수하고 선택하면 미등록 앱을 설치할 수 있습니다.
일상적인 사용자를 사회공학적 사기에서 지키는 장치는 그대로 유지됩니다.
개발자 입장에서는 등록되지 않은 앱이 완전히 막히는 것은 아니라는 점을 알아두면 됩니다.
다만 정식 배포 경로에서는 등록이 전제 조건입니다.

실무 관점​

국내 MTS 프로젝트에 적용한다면, Play Console에서 패키지 등록 상태를 먼저 확인합니다.
Play에 배포하는 앱뿐 아니라, Play 밖에서 배포하는 앱도 등록 대상에 들어갑니다.
사내 배포나 별도 채널로 나가는 앱이 있다면 Android Developer Console 등록도 함께 챙겨야 합니다.
앱이 여러 개라면 ID Status API로 등록 여부를 한 번에 확인하는 것이 좋습니다.
2027년 3월 1일을 기준으로 등록 작업을 정리해 두면, 확대 일정에 차질이 없습니다.

마치며​

Android 개발자 인증은 2027년부터 전 세계 모든 설치 경로로 확대됩니다.
등록 자체는 10분이면 끝나지만, 배포 채널이 여러 개라면 지금 확인해 두는 것이 안전합니다.

Appstate Statestore와 Transform 살펴보기 — UI 밖에서 Compose 상태를 다루는 새 라이브러리

2026년 11월 8일 · 약 3분
Way
Android Developer

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.
2026년 11월 4일에 공개된 Appstate Statestore와 Appstate Transform 1.0.0-alpha02에 대해 설명해드리겠습니다.
두 라이브러리 모두 Compose 런타임을 기반으로 하며, UI 밖에서 상태를 다루기 위한 기능을 제공합니다.

배경​

Compose의 상태는 지금까지 화면과 강하게 묶여 있었습니다.
mutableStateOf로 만든 상태는 컴포저블 안에서 읽고 쓰는 것이 자연스러웠고, 화면을 벗어난 앱 레이어에서 같은 상태를 다루려면 별도의 장치가 필요했습니다.
앱 전역 설정이나 백그라운드에서 갱신되는 값을 Compose 상태로 유지하면서 영속화까지 하려면 ViewModel과 DataStore를 직접 엮어야 했습니다.
Appstate는 이 지점을 겨냥한 새 Jetpack 라이브러리입니다.
스냅샷 상태를 앱 레이어로 끌어올리는 StateStore와, UI 밖에서 컴포지션을 실행하는 Transform으로 구성됩니다.

Appstate 살펴보기​

StateStore로 상태를 앱 레이어에 두기​

StateStore는 Compose 스냅샷 상태를 감싸는 래퍼입니다.
상태를 Application 같은 앱 레이어로 호이스팅하면 화면 생명주기와 무관하게 값을 유지할 수 있습니다.
statestore-datastore 아티팩트를 함께 쓰면 syncToDataStore로 상태를 DataStore에 영속화할 수 있습니다.

class MyApplication : Application() {
    val stateStore = StateStore()

    private val scope = CoroutineScope(SupervisorJob() + Dispatchers.Default)

    override fun onCreate() {
        super.onCreate()
        scope.launch {
            launch {
                try {
                    stateStore.syncToDataStore(
                        dataStoreFile("settings").absolutePath,
                        this
                    )
                } catch (e: Exception) {
                    e.printStackTrace()
                }
            }
        }
    }
}

동기화는 자식 코루틴에서 실행해 바깥 스코프를 막지 않는 구조입니다.
예외가 발생해도 앱 시작이 중단되지 않도록 try catch로 감싸는 형태가 공식 예시에 포함되어 있습니다.

Transform으로 UI 밖에서 컴포지션 실행하기​

Transform은 컴포지션을 UI 밖에서 실행할 수 있게 합니다.
transform 헬퍼 함수에 초기값과 스코프를 넘기면, 소스 상태가 바뀔 때마다 람다가 다시 실행되어 결과를 갱신합니다.

val scope = CoroutineScope(SupervisorJob() + Dispatchers.Default)
var sourceState by mutableStateOf(0)

val state = transform(initialValue = 0, scope = scope) {
    sourceState
}

TransformScope를 직접 다루는 방식도 있습니다.
launchTransform으로 변환을 시작하고 run으로 실행하며, 사용이 끝나면 dispose로 정리합니다.

val transformScope = TransformScope()
var sourceState by mutableStateOf(0)

val state = transformScope.launchTransform(initialValue = 0) {
    sourceState
}

scope.launch {
    try {
        transformScope.run()
    } finally {
        state.dispose()
    }
}

테스트를 위한 transformTest API도 함께 제공됩니다.
transform-testing 아티팩트를 쓰면 테스트 디스패처와 백그라운드 스코프를 지정해 상태 변화를 단계별로 검증할 수 있습니다.

@Test
fun testStateUpdate() = transformTest {
    var sourceState by mutableStateOf(0)
    val state = transform(
        initialValue = 0, scope = backgroundScope, dispatcher = testDispatcher
    ) {
        sourceState
    }

    assertThat(state.value).isEqualTo(0)
    sourceState = 1
    advance()
    assertThat(state.value).isEqualTo(1)
}

의존성 추가하기​

두 라이브러리는 멀티플랫폼 아티팩트로 제공됩니다.
Android, 데스크톱, iOS, JS, Wasm 등 각 플랫폼용 아티팩트가 나뉘어 있습니다.

dependencies {
    implementation("androidx.appstate.statestore:statestore:1.0.0-alpha02")
    implementation("androidx.appstate.statestore:statestore-datastore:1.0.0-alpha02")
    implementation("androidx.appstate.transform:transform:1.0.0-alpha02")
}

실무 관점​

아직 알파 단계라 API가 바뀌거나 사라질 수 있습니다.
운영 중인 MTS 앱에 바로 도입하기보다는, 상태 영속화와 백그라운드 상태 갱신이 필요한 화면부터 작은 범위로 검증하는 것이 안전합니다.
syncToDataStore는 코루틴 스코프와 예외 처리를 함께 설계해야 하며, 앱 시작 경로에서 동기화 실패가 전체 시작을 막지 않는지 확인이 필요합니다.
Transform은 컴포지션을 UI 밖으로 꺼내는 만큼, 변환 람다가 무거운 작업을 하지 않는지, 정리 시점이 명확한지 살펴야 합니다.

마치며​

Appstate는 Compose 상태를 화면 밖으로 꺼내는 방향을 제시합니다.
상태를 앱 레이어에 두고 영속화까지 연결하는 구조가 정식 버전에서 어떻게 다듬어지는지 지켜볼 만합니다.

CameraX 1.7.0-rc02 살펴보기 — Kotlin DSL 빌더와 미러 모드

2026년 11월 8일 · 약 3분
Way
Android Developer

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.
2026년 11월 4일에 공개된 CameraX 1.7.0-rc02에 대해 설명해드리겠습니다.
1.7.0은 릴리스 후보 단계에 들어섰으며, Kotlin DSL 빌더와 Camera2Interop 정리가 포함되어 있습니다.

배경​

CameraX는 지금까지 빌더 패턴으로 유스케이스를 만들었습니다.
Preview.Builder와 ImageCapture.Builder에 설정을 하나씩 쌓는 방식은 익숙했지만, 코드가 길어지고 설정 위치를 찾기 어려웠습니다.
Camera2의 세부 설정을 직접 다뤄야 할 때는 레거시 Interop API를 거쳐야 했고, 미러 모드는 실험적 애너테이션이 붙은 상태였습니다.
1.7.0은 이 세 지점을 함께 정리합니다.

CameraX 1.7.0 살펴보기​

Kotlin DSL 빌더로 유스케이스 만들기​

1.7.0-alpha03부터 preview, imageCapture, imageAnalysis, videoCapture DSL 빌더가 추가되었습니다.
빌더 객체를 직접 다루지 않고, 람다 안에서 설정을 모아 유스케이스를 만들 수 있습니다.

val preview = preview {
    // Preview 설정을 여기에 작성합니다.
}

val imageCapture = imageCapture {
    // ImageCapture 설정을 여기에 작성합니다.
}

cameraProvider.bindToLifecycle(
    lifecycleOwner, cameraSelector, preview, imageCapture
)

기존 빌더 방식과 비교하면 설정 코드가 한곳에 모이고, 유스케이스 생성 의도가 더 분명해집니다.

Camera2Interop 정리하기​

레거시 Camera2Interop API가 정리되었습니다.
Camera2Interop.Extender와 Camera2CameraControl, Camera2CameraInfo, CaptureRequestOptions는 deprecated 되었고, 대신 설정자 팩토리 메서드와 Kotlin 확장 함수를 사용합니다.
camera2Interop 확장 블록을 DSL 빌더 안에서 직접 쓸 수 있습니다.

val preview = preview {
    camera2Interop {
        // Camera2 설정을 직접 지정합니다.
    }
}

Camera2Interop에는 forUseCase와 forImageCapture, forSessionConfig, forCameraControl 팩토리 메서드가 추가되었습니다.
CameraInfo.cameraId와 CameraInfo.cameraCharacteristics 확장 프로퍼티로 Camera2의 카메라 ID와 특성을 바로 조회할 수 있으며, String.toCameraSelector()로 문자열에서 셀렉터를 만들 수 있습니다.
CameraControl.applyCamera2InteropAsync 확장 함수도 함께 제공됩니다.

미러 모드와 물리 카메라​

Preview.setMirrorMode와 VideoCapture.setMirrorMode가 정식 API가 되었습니다.
기존에 붙어 있던 ExperimentalMirrorMode 애너테이션은 제거되었습니다.
물리 카메라 지원도 넓어졌습니다.
CameraInfo.getPhysicalCameraInfos()로 물리 카메라 정보를 얻고, 물리 카메라용 CameraSelector로 유스케이스를 바인딩할 수 있습니다.
물리 카메라의 CameraInfo로 조회하면 논리 카메라가 아니라 물리 카메라 정보가 반환됩니다.

rc02에서 수정된 내용​

1.7.0-rc02 자체는 기능 추가가 아니라 버그 수정 릴리스입니다.
API 30에서 SYSTEM_ALERT_WINDOW 권한을 가진 앱이 카메라 유스케이스를 반복 바인딩할 때 발생하던 UnsupportedOperationException이 수정되었습니다.
VideoCapture를 언바인드할 때 미디어 프레임워크 스레드 하나가 남던 네이티브 스레드 누수도 수정되었습니다.
저조도 부스트 동작도 개선되었습니다.
저조도 부스트와 토치는 마지막 설정이 이기는 방식으로 동작하며, 저조도 부스트가 켜진 상태에서도 이미지 캡처 시 플래시가 동작합니다.

실무 관점​

RC 단계라 API 표면은 사실상 확정된 상태입니다.
정식 릴리스 전에 레거시 Camera2Interop 사용처가 있는지 점검하고, DSL 빌더로의 전환 범위를 정해 두는 것이 좋습니다.
미러 모드를 이미 실험적 API로 쓰고 있다면 애너테이션 제거에 맞춰 정식 API로 교체해야 합니다.
저조도 부스트와 토치의 동작이 바뀐 만큼, 야간 촬영이나 QR 인식처럼 두 기능을 함께 쓰는 화면이 있다면 동작을 다시 확인해야 합니다.

마치며​

CameraX 1.7.0은 카메라 코드를 짧게 쓰는 방향으로 정리되고 있습니다.
정식 릴리스가 나오면 DSL 빌더와 Interop 정리를 실제 화면에 적용해 볼 만합니다.

AppFunctions 1.0.0-rc01 살펴보기 — 앱 기능을 AI 에이전트에 연결하기

2026년 11월 7일 · 약 2분
Way
Android Developer

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.
2026년 11월 4일에 공개된 AppFunctions 1.0.0-rc01에 대해 설명해드리겠습니다.

배경​

AppFunctions는 앱의 기능을 AI 에이전트가 호출할 수 있게 노출하는 Jetpack 라이브러리입니다.
Android Dev Summit 2026에서 베타로 발표됐고, 11월 4일 RC 단계에 들어갔습니다.
RC는 API 표면이 확정된 예비 stable 릴리스입니다.
에이전트는 기능을 직접 실행하는 대신, 앱이 선언한 설명을 보고 호출합니다.

AppFunctions 1.0.0-rc01 살펴보기​

의존성을 추가합니다​

dependencies {
    implementation("androidx.appfunctions:appfunctions:1.0.0-rc01")
    ksp("androidx.appfunctions:appfunctions-compiler:1.0.0-rc01")
}

테스트용 아티팩트도 같은 버전으로 제공됩니다.
Android 16(API 36) 이상에서 동작하며, compileSdk 36이 필요합니다.

기능을 선언합니다​

@AppFunctionServiceEntryPoint
class MarketFunctions {

    /**
     * 보유 종목의 현재가를 조회합니다.
     *
     * @param symbol 종목 코드입니다.
     * @return 현재가 정보입니다.
     */
    @AppFunctionDeclaration(isDescribedByKDoc = true)
    suspend fun getStockPrice(symbol: String): StockPrice {
        return withContext(Dispatchers.IO) {
            stockRepository.getPrice(symbol)
        }
    }
}

선언은 @AppFunctionServiceEntryPoint가 붙은 서비스 클래스 안에 둡니다.
@AppFunctionDeclaration이 붙은 함수는 외부 앱이 호출할 수 있습니다.
KSP 컴파일러가 함수 설명을 XML로 만들어 assets에 넣고, 시스템이 이를 색인합니다.
isDescribedByKDoc은 KDoc을 에이전트용 설명으로 쓸지 정합니다.
beta01부터 기본값이 없어 반드시 지정해야 합니다.

기본적으로 메인 스레드에서 실행됩니다​

선언한 함수는 기본적으로 메인 스레드에서 실행됩니다.
네트워크나 파일 작업이 있으면 suspend 함수로 만들고 디스패처를 바꿉니다.
호출자는 EXECUTE_APP_FUNCTIONS 권한이 필요합니다.
사용자 정의 타입을 주고받을 때는 직렬화 규칙을 따라야 합니다.

RC01 변경점​

버전이 RC로 올라갔고, 기존 집계 컴파일러 옵션이 제거됐습니다.
Java 라이브러리 desugaring을 켠 앱에서 java.time 파라미터 역직렬화가 실패하던 문제가 수정됐습니다.
테스트는 Android 17 기기나 에뮬레이터에서 adb shell cmd app_function 명령으로 할 수 있습니다.

실무 관점​

노출하는 기능은 읽기 전용 조회부터 시작하는 것이 안전합니다.
주문처럼 돈이 움직이는 기능은 에이전트에 노출하지 않습니다.
프로덕션 배포는 Connected Apps Platform 프리뷰 등록이 별도로 필요합니다.
설명 문구는 에이전트가 기능을 선택하는 기준이 되므로, KDoc을 정확히 씁니다.

마치며​

AppFunctions가 RC에 들어서면서 에이전트 연동 준비가 한결 가까워졌습니다.
조회 기능부터 작은 범위로 적용해보고, 안정 버전에서 범위를 넓히겠습니다.

Kotlin 2.5.0-Beta2 살펴보기 — 이름 기반 구조 분해와 JDK 17 요구 사항

2026년 11월 7일 · 약 3분
Way
Android Developer

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.
2026년 10월 21일에 공개된 Kotlin 2.5.0-Beta2에 대해 설명해드리겠습니다.
안정 버전은 12월 공개가 목표입니다.

배경​

구조 분해는 data class의 프로퍼티를 순서대로 꺼내는 문법입니다.
프로퍼티 순서가 바뀌면 같은 타입의 값이 서로 뒤바뀌는 실수가 생깁니다.
이름으로 꺼내는 방식이 2.3.20부터 실험 기능으로 제공됐고, Beta2에서 안정화됐습니다.
컴파일러 실행에 JDK 17 이상이 필요해진 점도 함께 정리했습니다.

Kotlin 2.5.0-Beta2 살펴보기​

이름 기반 구조 분해가 안정화됐습니다​

only-syntax 모드에서 새 문법이 기본값이 됐습니다.
기존 문법은 위치 기준으로 동작합니다.
새 문법은 괄호 안에 val을 넣어 이름을 기준으로 꺼냅니다.
변수 이름은 프로퍼티 이름과 일치해야 하며, 순서는 달라도 됩니다.

data class Account(val owner: String, val balance: Long)

fun printAccount(account: Account) {
    // 기존 문법: 위치 기준으로 꺼냅니다
    val (owner, balance) = account
    println("$owner: $balance")
}

fun printAccountByName(account: Account) {
    // 새 문법: 이름 기준으로 꺼냅니다
    // 순서를 바꿔도 같은 프로퍼티가 들어갑니다
    (val balance, val owner) = account
    println("$owner: $balance")
}

향후 버전에서는 기존 괄호 문법도 이름 기준으로 동작할 예정입니다.
자세한 전환 계획은 The Road to Name-Based Destructuring에서 확인할 수 있습니다.

사용하지 않은 반환값 검사가 추가됐습니다​

반환값을 무시하고 함수를 호출하면 컴파일러가 이를 알려주는 검사가 들어갔습니다.
결과를 확인하지 않고 넘어가는 실수를 줄이는 목적입니다.
Beta 단계에서는 검사가 동작하는 범위를 확인하면서 적용하는 것이 좋습니다.

컴파일러 실행에 JDK 17이 필요합니다​

Beta1에서는 JDK 17보다 오래된 JDK로 컴파일러를 실행하면 경고가 나왔습니다.
Beta2부터는 오류가 발생합니다.
이전 JDK를 임시로 계속 쓰는 플래그가 제공됩니다.
MTS 빌드 환경의 JDK 버전을 먼저 확인합니다.

}

자세한 목록은 Kodee's Kotlin Roundup에서 확인할 수 있습니다.

배경​

Biometric의 현재 stable 버전은 1.1.0입니다.
1.4 라인은 2024년 5월 alpha01부터 이어져 왔고, 11월 4일 beta01에 들어섰습니다.
베타 단계는 API 표면이 기능적으로 완성된 상태입니다.
이번 1.4의 핵심은 기존 BiometricPrompt 콜백 방식을 Activity Result 패턴으로 바꾸는 것입니다.

Biometric 1.4.0-beta01 살펴보기​

registerForAuthenticationResult로 등록합니다​

1.4에서는 BiometricPrompt와 biometric-ktx 모듈을 대체하는 새로운 진입점이 도입되었습니다.
Activity Result API와 같은 방식으로 인증을 등록하고 실행합니다.
인증 입력은 AuthenticationRequest로, 결과는 AuthenticationResult로 받습니다.

private val auth = registerForAuthenticationResult { result ->
    when (result) {
        is AuthenticationResult.Success -> onAuthenticated()
        is AuthenticationResult.Error -> showError(result.errString)
        is AuthenticationResult.CustomFallbackSelected -> onFallbackSelected(result)
    }
}

AuthenticationRequest는 두 가지 종류가 있습니다.
생체 인증용 BiometricRequest는 강도(Strength)와 선택적인 Fallback을 지정합니다.
기기 자격 증명 전용 인증용 CredentialRequest도 함께 제공됩니다.
하나의 Activity나 Fragment에서 여러 인증 런처를 동시에 쓸 수도 있습니다.

biometric-compose에서 rememberAuthenticationLauncher를 사용합니다​

1.4.0-alpha05부터는 Compose 전용 biometric-compose 라이브러리도 함께 제공됩니다.
컴포저블 안에서 rememberAuthenticationLauncher로 인증 요청과 콜백을 처리합니다.

val auth = rememberAuthenticationLauncher { result ->
    when (result) {
        is AuthenticationResult.Success -> onAuthenticated()
        is AuthenticationResult.Error -> showError(result.errString)
        is AuthenticationResult.CustomFallbackSelected -> Unit
    }
}

의존성은 다음과 같이 추가합니다.

dependencies {
    implementation("androidx.biometric:biometric:1.4.0-beta01")
    implementation("androidx.biometric:biometric-compose:1.4.0-beta01")
}

Fallback 옵션을 여러 개 둘 수 있습니다​

Android 36.1(Baklava)부터는 생체 인증 프롬프트에서 최대 네 개의 커스텀 Fallback 옵션을 지원합니다.
기존의 단일 부정 버튼 대신, 아이콘을 함께 제공하는 여러 Fallback 옵션을 둘 수 있습니다.
Fallback 옵션은 AuthenticationRequest.Biometric.Fallback으로 제공합니다.
사용자가 Fallback을 선택하면 에러 코드가 아니라 AuthenticationResult.CustomFallbackSelected로 전달됩니다.

그 외 변경점​

BiometricPrompt.CryptoObject에 KeyAgreement 지원이 추가되었습니다.
기본 minSdk가 API 21에서 API 23으로 올라갔습니다.
라이브러리는 이제 JSpecify nullness 어노테이션을 사용합니다.
그 밖에 기기 회전 시 지문 아이콘이 사라지는 문제와 canAuthenticate()에서 잠금 오류를 잘못 반환하는 문제가 수정되었습니다.

실무 관점​

MTS의 로그인이나 이체 인증 화면에서 BiometricPrompt를 쓰고 있다면, 교체 설계는 지금 시작하는 것이 좋습니다.
다만 적용 시점은 stable 릴리스 이후로 잡는 편이 안전합니다.
베타 단계의 API는 기능적으로 완성되었지만, 변경 가능성이 남아 있기 때문입니다.
Fallback 옵션은 PIN이나 패턴 같은 기기 자격 증명 경로와 연결해 설계합니다.
minSdk 23 변경도 적용 대상 단말 목록과 함께 확인합니다.

마치며​

Biometric 1.4는 생체 인증을 Activity Result 패턴으로 바꾸고, Compose 전용 런처와 복수 Fallback 옵션을 함께 가져왔습니다.
인증 화면을 새로 만들거나 고칠 계획이 있다면, 1.4의 새 API를 기준으로 설계하는 것이 좋습니다.

Compose 1.13.0-rc01 살펴보기​

Kotlin 2.2가 필요합니다​

Compose 1.13 라이브러리는 Kotlin 2.2를 대상으로 빌드되며, 컴파일러도 2.2가 필요합니다.
업데이트 전에 libs.versions.toml의 Kotlin 버전을 먼저 확인합니다.

[versions]
kotlin = "2.2"

Slider에서 onValueChange이 필수가 되었습니다​

Slider, VerticalSlider, RangeSlider에서 onValueChange이 필수 파라미터가 되었습니다.
기존에 숨겨져 있던 deprecated API와 SliderState의 DraggableState 구현, 구형 Saver 오버로드가 제거되었습니다.
SliderState의 isVertical도 제거되었고, SliderDefaults.Thumb의 SliderState 오버로드는 isVertical 오버로드로 대체되었습니다.

var value by remember { mutableFloatStateOf(0.5f) }

Slider(
    value = value,
    onValueChange = { value = it },
)

기존 코드에서 onValueChange을 생략한 Slider가 있다면 컴파일 단계에서 바로 드러납니다.
값 변경을 받지 않는 표시 전용 슬라이더는 onValueChange에 빈 람다를 넘기는 대신, 읽기 전용 표시 방식을 검토하는 편이 낫습니다.

MediaQuery의 Posture가 WindowPosture로 바뀌었습니다​

MediaQuery의 Posture 클래스가 WindowPosture로 대체되었습니다.
WindowPosture는 물리적인 WindowFold를 FoldState와 FoldOrientation으로 노출합니다.
isTabletop과 isFlat 편의 프로퍼티가 추가되었고, 기존의 Book 자세 구분은 제거되었습니다.

if (posture.isTabletop) {
    // 접은 상태에서는 하단 화면에 컨트롤을 배치합니다.
} else if (posture.isFlat) {
    // 펼친 상태에서는 전체 화면 레이아웃을 사용합니다.
}

폴더블 대응 화면에서는 자세 판정 로직을 WindowPosture 기준으로 다시 확인합니다.

Progressive Blur API가 정리되었습니다​

1.13 alpha03에서 추가된 Modifier.blur { ... } API가 RC에서 정리되었습니다.
Modifier.blur의 radius 파라미터가 blurRadiusSpec으로 개명되었고, BlurScope.radius도 blurRadiusSpec으로 바뀌었습니다.
BlurStop.fraction에는 @FloatRange가 추가되었고, BlurRadiusSpec.radialGradient의 기본 fallOffRadius는 Dp.Unspecified로 변경되었습니다.

그 외 변경점​

VectorPainter가 같은 ImageVector를 여러 컴포저블에서 그릴 때 내부 그래픽 리소스를 공유합니다.
반복 아이콘을 쓰는 리스트에서 텍스처 업로드와 메모리 사용이 줄어듭니다.
이 최적화는 ComposeUiFlags.isVectorDrawCacheSharingEnabled 플래그로 끌 수 있습니다.
Modifier.border는 이제 아웃라인 크기를 기준으로 테두리를 그립니다.
문제가 생기면 ComposeFoundationFlags.isBorderMatchesOutlineBoundsFixEnabled 플래그로 이전 동작을 되돌릴 수 있습니다.
Material3 1.5.0-rc01에서는 ToggleButton의 눌림 상태 모양이 디자인 토큰을 따르도록 수정되었고, RangeSlider의 탭 시 값 미반영, 가로 스크롤 컨테이너 안에서의 스크롤 간섭, 이산 값 스냅 시 정밀도 손실이 수정되었습니다.
한편 1.13 alpha03부터 Compose 라이브러리의 compileSdk가 37.1로 올라갔습니다.
앱과 라이브러리의 compileSdk도 함께 올려야 합니다.

앱이 AI 에이전트의 도구가 된다 — AppFunctions 1.0.0-beta01 살펴보기

2026년 10월 24일 · 약 4분
Way
Android Developer

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.
2026년 10월 21일에 공개된 AppFunctions 1.0.0-beta01의 릴리스 노트를 정리해드리겠습니다.

현재 상황​

AppFunctions는 앱의 기능을 AI 에이전트가 발견하고 실행할 수 있게 만드는 Jetpack 라이브러리입니다.
앱이 온디바이스 MCP 서버처럼 동작한다는 비유로 설명되곤 합니다.
사용자가 앱을 직접 열지 않아도, 에이전트가 앱의 함수를 찾아 호출하고 결과를 돌려주는 흐름이 목표입니다.
그동안 알파 단계를 거치며 애너테이션 이름과 서비스 구조가 여러 차례 바뀌었습니다.
이번 beta01은 알파를 벗어난 첫 베타라는 점에서 의미가 있습니다.
아직 stable은 아니지만, API가 안정화 단계에 들어섰다는 신호로 읽을 수 있습니다.

AppFunctions 1.0.0-beta01 살펴보기​

앱 메타데이터 이름 변경​

AppFunctionAppMetadata의 description이 instructions로 바뀌었습니다.
XML 속성 이름도 함께 바뀌었습니다.
MCP의 명명 관례에 맞추기 위한 변경입니다.
앱 수준의 동작 방식과 제약을 에이전트에게 전달하는 필드이므로, 이름을 보고 역할을 짐작하기가 더 쉬워졌습니다.
기존 메타데이터를 쓰고 있었다면 이번 베타에서 이름을 함께 바꿔야 합니다.

isDescribedByKDoc 기본값 제거​

AppFunctionDeclaration, AppFunctionSerializable, AppFunctionSignature에서 isDescribedByKDoc의 기본값이 제거되었습니다.
이제 값을 반드시 명시적으로 지정해야 합니다.
이 값은 KDoc 주석을 에이전트가 읽는 설명으로 쓸지를 결정합니다.
기본값이 사라졌다는 것은, 설명 방식을 개발자가 의식적으로 선택하라는 뜻으로 읽힙니다.
KDoc을 대충 쓰면 에이전트가 함수를 잘못 이해할 수 있으니, 주석이 곧 스키마라는 점을 염두에 두어야 합니다.

@RequiresApi(36)
@AppFunctionServiceEntryPoint(
    serviceName = "PortfolioAppFunctionService",
    appFunctionXmlFileName = "portfolio_app_function_service"
)
abstract class BasePortfolioAppFunctionService : AppFunctionService() {

    /**
     * 보유 종목의 요약 정보를 반환합니다.
     *
     * @param accountId 조회할 계좌의 식별자입니다.
     */
    @AppFunctionDeclaration(isDescribedByKDoc = true)
    suspend fun getPortfolioSummary(
        accountId: String
    ): PortfolioSummary = withContext(Dispatchers.IO) {
        portfolioRepository.getSummary(accountId)
    }
}

위 예시에서 함수는 기본적으로 메인 스레드에서 실행됩니다.
그래서 블로킹 작업이 있다면 suspend 함수로 만들고 백그라운드 디스패처로 전환해야 합니다.
공식 API 레퍼런스에서도 같은 주의사항을 강조하고 있습니다.

그 밖의 API 변경​

AppFunctionName이 androidx.appfunctions.metadata 패키지에서 androidx.appfunctions 패키지로 이동했습니다.
임포트 경로를 정리하지 않으면 컴파일이 깨지니, 베타로 올릴 때 임포트부터 확인하는 편이 좋습니다.
AppFunctionResourceContainer와 AppFunctionTextResource는 실험적 API로 표시되었습니다.
@AppFunctionStringValueConstraint의 정규식 패턴은 android.os.PatternMatcher 기반의 패턴 매처로 대체되었습니다.
테스트 쪽에서는 AppFunctionTestRule이 AppFunctionServiceEntryPoint를 지원하게 되었습니다.
테스트에서 엔트리 포인트를 직접 다룰 수 있게 된 만큼, 함수 단위 검증이 조금 수월해졌습니다.

버그 수정​

자바 라이브러리 디슈가링을 켠 앱에서 java.time 파라미터 타입의 역직렬화가 실패하던 문제가 수정되었습니다.

SDK 37 이상에서 URI 권한이 두 번 부여되던 문제도 함께 수정되었습니다.
어느 하나 거창한 기능은 아니지만, 실무에서 마주치면 원인을 찾기 어려운 유형의 수정입니다.

WebView에 stable API로 온 allowlist — WebKit 1.18.0 살펴보기

2026년 10월 24일 · 약 3분
Way
Android Developer

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.
2026년 10월 21일에 공개된 WebKit 1.18.0의 릴리스 노트를 정리해드리겠습니다.

현재 상황​

지난 글에서는 WebView v156의 cross-origin isolation allowlist 개념을 정리한 바 있습니다.
당시에는 개념과 정책 방향이 중심이었습니다.
이번에는 그 기능이 Jetpack WebKit의 stable API로 확정된 내용을 정리합니다.
MTS 앱처럼 WebView를 많이 쓰는 앱에서는 웹 콘텐츠의 성능 기능과 보안 정책을 함께 다뤄야 합니다.
SharedArrayBuffer처럼 cross-origin isolation을 요구하는 API는 그동안 전부 아니면 전무에 가까웠습니다.
1.18.0은 신뢰하는 origin만 골라 허용하는 길을 stable API로 열어줍니다.

WebKit 1.18.0 살펴보기​

cross-origin isolated allowlist API​

핵심은 Profile 수준의 API입니다.
Profile#setCrossOriginIsolatedAllowlist와 Profile#getCrossOriginIsolatedAllowlist가 stable로 제공됩니다.
allowlist에 오른 origin에서는 완전히 cross-origin isolated 상태가 아니어도 SharedArrayBuffer 같은 API를 쓸 수 있습니다.
다만 웹 페이지 쪽에서도 Document-Isolation-Policy 헤더로 적절히 옵트인해야 합니다.
앱 API만 켠다고 끝나는 기능이 아니라, 웹 측 헤더와 함께 동작하는 기능입니다.

// 이미 확보한 Profile이라고 가정합니다
if (WebViewFeature.isFeatureSupported(WebViewFeature.CROSS_ORIGIN_ISOLATED_ALLOWLIST)) {
    profile.setCrossOriginIsolatedAllowlist(
        setOf("https://trusted.example.com")
    )
}

사용 전에 반드시 기능 지원 여부를 확인해야 합니다.
지원되지 않는 단말에서 호출하면 예외가 발생합니다.
공식 API 레퍼런스에서도 사용 전 확인을 강조하고 있습니다.
또한 기본값은 비활성화 상태입니다.
WebView는 렌더러 프로세스 격리를 지원하지 않기 때문에, 이 API를 호출한다는 것은 보안 보장을 완화하겠다는 뜻이 됩니다.
그래서 신뢰하는 origin만 등록해야 하고, 와일드카드 패턴은 피해야 합니다.
이미 로드된 페이지에도 이 설정이 적용된다는 점도 염두에 두어야 합니다.

prefetch 큐 비우기 여부 확인​

WebViewFeature에 WEBVIEW_NAVIGATE_DRAIN_PREFETCH 상수가 추가되었습니다.
이 상수로 Navigation#navigate가 이동 전에 prefetch 큐를 비우는지 확인할 수 있습니다.
prefetch를 쓰는 앱에서는 이동 시점에 어떤 요청이 남는지 예측하기가 한결 쉬워집니다.
단순한 상수 추가처럼 보이지만, 동작 예측 가능성을 높이는 변경입니다.

if (WebViewFeature.isFeatureSupported(WebViewFeature.WEBVIEW_NAVIGATE_DRAIN_PREFETCH)) {
    // Navigation#navigate가 prefetch 큐를 비우는지 확인할 수 있습니다
}

API 정리와 이름 변경​

PrefetchParameters#isJavaScriptEnabled는 includeClientHints로 이름이 바뀌었습니다.
기존 메서드는 deprecated 처리되었습니다.
Profile#addQuicHints는 preferQuicFor로 이름이 바뀌었습니다.
이름만 바뀐 변경이지만, 기존 이름을 그대로 쓰던 코드가 있다면 마이그레이션 목록에 올려두어야 합니다.
deprecated 경고를 방치하면 나중에 버전 올릴 때 한꺼번에 정리해야 합니다.

의존성 선언​

[versions]
webkit = "1.18.0"

[libraries]
webkit = { module = "androidx.webkit:webkit", version.ref = "webkit" }
dependencies {
    implementation(libs.webkit)
}

실무 관점​

MTS 앱에서 WebView allowlist를 쓴다면, 등록 대상은 자사 도메인처럼 확실히 신뢰하는 origin으로 한정해야 합니다.
외부 제휴 페이지나 광고성 페이지를 넓게 허용하면, 보안 보장을 완화한 대가를 치르게 됩니다.
적용 전에는 기능 지원 여부 확인, 헤더 설정, 기존 페이지 동작을 함께 테스트하는 편이 좋습니다.
이미 로드된 페이지에도 적용되므로, 설정 시점에 따라 동작이 달라질 수 있다는 점도 테스트 항목에 넣어야 합니다.
stable 릴리스인 만큼, 기존에 쓰던 이름 변경부터 정리하고 단계적으로 적용하는 것이 안전합니다.

마치며​

이번 stable은 allowlist라는 보안 기능을 실제 API로 쓸 수 있게 만든 릴리스입니다.
신뢰하는 origin만 좁게 허용한다는 원칙만 지키면, WebView의 성능 기능을 보다 안전하게 활용할 수 있습니다.

CameraX는 카메라 기능을 단말 파편화 없이 구현할 수 있게 돕는 Jetpack 라이브러리입니다.

CameraX 1.7.0-rc01 살펴보기​

네이티브 SIGSEGV 크래시 수정​

SurfaceProcessor가 입력 SurfaceTexture를 해제하는 시점에, 연결된 SurfaceRequest가 먼저 가비지 컬렉션되면 네이티브 SIGSEGV가 발생하던 버그가 수정되었습니다.
타이밍에 의존하는 문제라 특정 단말과 특정 시나리오에서만 나타나고, 주로 크래시 리포트에서만 보이는 유형입니다.
이펙트나 필터로 SurfaceProcessor를 직접 다루는 앱이라면 이번 수정이 반가울 것입니다.

Surface 누수와 OpenGL 크래시 수정​

CameraEffect의 executor나 HandlerThread가 SurfaceOutput이 닫히기 전에 종료되면, Surface 누수와 네이티브 OpenGL 크래시가 발생하던 문제가 수정되었습니다.
카메라 파이프라인의 종료 순서가 리소스 정리와 직결된다는 점을 보여주는 사례입니다.

Camera2Interop — 인터페이스에서 추상 클래스로 전환​

UseCaseCamera2Interop, ImageCaptureCamera2Interop, SessionConfigCamera2Interop, CameraControlCamera2Interop이 인터페이스에서 추상 클래스로 바뀌었습니다.
소스 호환성에 영향을 줄 수 있는 변경이니, interop 클래스를 직접 참조하는 코드가 있다면 1.7.0 적용 전에 컴파일을 확인해야 합니다.

val preview = preview {

        // Camera2 설정을 이 블록 안에 지정합니다
    }

Low Light Boost와 Torch — last setting wins​

저조도 부스트와 토치를 동시에 켜려고 하면 요청이 거부되던 동작이 바뀌었습니다.
이제는 마지막에 설정한 쪽이 이기는 방식으로 동작합니다. 하나를 켜면 다른 하나가 자동으로 꺼집니다.
저조도 부스트가 켜진 상태에서도 촬영 시 플래시가 터지도록 함께 개선되었습니다.

물리 카메라에 UseCase 바인딩​

CameraInfo.getPhysicalCameraInfos()에서 얻은 물리 카메라의 CameraSelector로 UseCase를 바인딩할 수 있게 되었습니다.
물리 CameraSelector로 CameraInfo를 조회하면 논리 카메라가 아닌 물리 카메라의 정보가 반환됩니다.
멀티 카메라 단말에서 특정 렌즈를 직접 다루는 기능에 활용할 수 있습니다.

연락처 직접 쓰기가 막힌다 — 차기 Android 릴리스의 WRITE_CONTACTS 동작 변경

2026년 10월 22일 · 약 2분
Way
Android Developer

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.
Android Developers' Blog에 2026년 10월 21일 올라온 연락처 관련 동작 변경 소식을 정리해드리겠습니다.

현재 상황​

지금까지는 WRITE_CONTACTS 권한을 받아 ContentResolver로 연락처에 직접 쓰는 방식이 가능했습니다.
송금 수취인 저장, 지인 초대 같은 기능에서 쓰이던 패턴입니다.
그런데 차기 Android 릴리스를 타깃하는 앱부터는 이 직접 쓰기가 막힌다고 공지되었습니다.
읽기 쪽이 이미 Contact Picker로 정리된 데 이어, 쓰기 쪽도 시스템 UI 경유로 수렴하는 흐름입니다.

바뀐 내용 살펴보기​

WRITE_CONTACTS 직접 쓰기 제한​

차기 릴리스를 target으로 하는 앱은 WRITE_CONTACTS 권한으로 연락처에 직접 쓸 수 없게 됩니다.
권한이 선언되어 있어도 쓰기 동작이 차단되는 행위 변경입니다.

시스템 제공 UI로 추가·편집하기​

추가와 편집은 시스템이 제공하는 UI, 즉 인텐트 기반 흐름을 쓰도록 바뀌었습니다.
연락처 앱의 편집 화면을 띄워 사용자가 직접 확인하고 저장하는 방식입니다.

// 연락처 추가 — 시스템 UI를 통해 저장
val intent = Intent(ContactsContract.Intents.Insert.ACTION).apply {
    type = ContactsContract.RawContacts.CONTENT_TYPE
    putExtra(ContactsContract.Intents.Insert.NAME, "홍길동")
    putExtra(ContactsContract.Intents.Insert.PHONE, "010-1234-5678")
}
startActivity(intent)

이 방식은 저장 전에 사용자가 내용을 확인할 수 있어, 잘못된 연락처가 등록되는 일을 줄여줍니다.

읽기 흐름과의 정합성​

읽기 쪽은 Android 17부터 Contact Picker가 표준입니다.
READ_CONTACTS 권한 없이 필요한 데이터 필드만 지정해, 사용자가 고른 연락처에만 접근합니다.
쓰기 제한까지 더해지면 연락처 접근 전반이 시스템 UI 경유라는 하나의 원칙으로 정리됩니다.

실무 관점​

ContentResolver.insert로 연락처를 직접 쓰던 코드가 있다면 targetSdk 상향 계획과 함께 감사 대상에 올려야 합니다.
WRITE_CONTACTS 권한 요청 흐름도 함께 정리할 수 있습니다.
시스템 UI 경유 방식은 사용자 확인이 개입되므로, 무음 저장을 기대하던 UX라면 흐름을 다시 설계해야 합니다.

마치며​

연락처 쓰기 제한은 권한 최소화 흐름의 연장선에 있는 변경입니다.
차기 릴리스 대응 체크리스트에 연락처 쓰기 경로를 미리 넣어두는 것이 안전합니다.

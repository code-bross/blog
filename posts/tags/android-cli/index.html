Android CLI 1.1 살펴보기 — 델타 설치와 Compose 트레이싱

2026년 11월 21일 · 약 4분
Way
Android Developer

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.
2026년 11월에 공개된 Android CLI 1.1.16919734에 대해 설명해드리겠습니다.

배경​

Android CLI는 터미널에서 Android 개발을 수행하는 공식 CLI입니다.
Android Studio를 열지 않고 빌드와 설치, 프로파일링, 기기 제어를 처리할 수 있습니다.
에이전트와 함께 쓰는 개발 흐름을 염두에 두고 만들어졌고, 스크립트와 CI에서도 그대로 쓸 수 있습니다.
2026년 11월 릴리스는 설치 속도와 프로파일링, 스크립트 친화성이 중심입니다.
새 명령이 추가된 릴리스가 아니라, 매일 쓰는 명령이 더 빠르고 정확해진 릴리스입니다.

Android CLI 1.1 살펴보기​

델타 설치로 재배치된 파일 재전송 방지​

android install과 android run은 변경되지 않은 파일을 다시 보내지 않습니다.
이번 릴리스에서는 APK 안에서 위치만 바뀐 파일도 재전송 대상에서 제외됩니다.
파일 내용이 그대로인데 위치만 이동한 경우, 설치 과정에서 다시 전송할 필요가 없어졌습니다.
반복 설치가 많은 개발 과정에서 체감되는 개선입니다.
기존 동작이 필요하면 --use-delta-install-instructions=COPY,DATA 옵션을 전달합니다.

android run
android install app-debug.apk

Compose 트레이싱으로 리컴포지션 원인 찾기​

android profiler systemtrace에 Compose 트레이싱이 들어왔습니다.
--enable=compose.composition을 전달하면 실행된 컴포저블 함수마다 슬라이스를 기록합니다.
--enable=compose.recomposition을 전달하면 리컴포지션을 일으킨 상태 읽기와 쓰기까지 함께 기록합니다.
앱에는 androidx.compose.runtime:runtime-tracing 1.13 이상이 필요합니다.
트레이스는 ZIP 파일로 저장되며, Android Studio 프로파일러에서 열어 확인할 수 있습니다.

android profiler systemtrace --enable=compose.recomposition

Perfetto 힙 덤프로 메모리 살펴보기​

android profiler heapdump capture에 --type=perfetto 옵션이 추가되었습니다.
Perfetto 트레이스 형태로 힙 덤프를 기록하며, 객체와 객체 사이의 참조를 포함합니다.
값 자체는 포함하지 않기 때문에 .hprof 파일보다 크기가 작습니다.
Android 12(API 31) 이상에서 동작하며, 프로파일이 가능하거나 디버깅이 가능한 앱이 필요합니다.
메모리 누수나 힙 증가를 살펴볼 때 가벼운 대안이 됩니다.

android profiler heapdump capture --type=perfetto

스크립트 친화적인 출력 형식​

android analyze --format=json의 출력 형식이 바뀌었습니다.
라이브러리 아티팩트(AAR, JAR)의 dexSizeBytes 필드는 이제 64비트 정수를 문자열로 직렬화합니다.
d8CompileResult와 r8CompileResult에 모두 적용됩니다.
JSON을 파싱하는 스크립트에서는 숫자가 아니라 문자열로 받는 점을 반영해야 합니다.
android input 하위 명령도 결과를 통일된 JSON 객체로 출력합니다.
표준 출력에는 results 목록이 나오고, 일치하는 요소가 없거나 여러 개가 일치하는 실패는 각 결과의 status 필드에 기록됩니다.
표준 에러의 텍스트를 파싱하지 않아도 결과를 처리할 수 있습니다.

android analyze --format=json app-debug.aab
android input tap text=Submit

에뮬레이터 명령의 종료 코드​

android emulator create와 start, stop, remove가 실패 시 0이 아닌 종료 코드를 반환합니다.
오류는 표준 에러로 출력됩니다.
이전에는 실패해도 스크립트에서 알아채기 어려웠던 경우가 있었습니다.
CI에서 에뮬레이터를 만들고 지우는 단계가 있다면, 종료 코드만으로 실패를 감지할 수 있습니다.

android emulator create --name test
android emulator start --name test

실무 관점​

국내 MTS 프로젝트에 적용한다면, 델타 설치 개선은 별도 설정 없이 바로 체감할 수 있습니다.
Compose 트레이싱을 쓰려면 runtime-tracing 의존성을 추가하고 Compose 1.13 이상을 사용해야 합니다.
리컴포지션 원인을 찾는 디버깅 단계에서만 켜고, 평소에는 끄는 것이 좋습니다.
android analyze 결과를 파싱하는 스크립트가 있다면 dexSizeBytes가 문자열로 바뀐 점을 먼저 확인합니다.
에뮬레이터를 다루는 CI 스크립트는 종료 코드 기반으로 실패 처리를 정리할 수 있습니다.

마치며​

Android CLI 1.1은 눈에 띄는 새 기능보다 매일 쓰는 명령의 완성도를 높인 릴리스입니다.
설치가 빨라지고, Compose 성능 원인을 터미널에서 바로 찾을 수 있게 되었습니다.

안드로이드 개발자에게 열린 Gemini 4 Argon — 자가 복구 빌드와 AGSL 셰이더

2026년 10월 15일 · 약 4분
Way
Android Developer

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.
안드로이드 개발자에게 개방된 Gemini 4 Argon에 대해 설명해드리겠습니다.

배경​

구글은 10월 13일 Android Developers Blog에서 최신 플래그십 모델 Gemini 4 Argon을 안드로이드 개발 표면에 개방한다고 발표했습니다.
자세한 내용은 원문 글(Jason Buchel)에서 확인할 수 있습니다.
지난주에 다뤘던 Android CLI와 디바이스 스트리밍, BYOA(원하는 에이전트 쓰기) 흐름의 연장선에 있는 발표입니다.
모델 자체보다 에이전트가 빌드를 스스로 고치고 셰이더까지 작성한다는 부분에 주목할 필요가 있습니다.

Gemini 4 Argon 살펴보기​

접근 경로​

  • Google Antigravity에서 사용할 수 있습니다. AI Ultra 구독이 전제이고, 데스크톱 앱·CLI·Android Studio Canary 안에 포함됩니다.
  • Android Studio에서는 Gemini API 유료 티어로 사용할 수 있습니다.
  • Google AI Studio의 Playground와 Build에서도 사용할 수 있습니다. AI Ultra 또는 Gemini API 유료 티어가 필요합니다.
  • 클라이언트 인앱 AI는 Firebase AI Logic 경유로 제공됩니다. Gemini API 유료 티어 개발자가 앱 안에서 Gemini 4 Argon을 직접 쓸 수 있습니다.

Self-Healing Build Loops​

  • 빌드 실패 시 Antigravity 하네스가 Gradle 데몬과 Kotlin 컴파일러 로그를 모델에 그대로 피드백합니다.
  • 모델은 근본 원인을 반복 진단해 수정안을 냅니다.
  • 편집 라운드마다 가설을 일관되게 유지하고 AST 인지를 활용해 표면 증상이 아닌 진짜 원인에 도달하도록 훈련되었다는 설명입니다.
  • 지금까지의 에이전트 코딩이 코드 자동완성의 연장에 가까웠다면, 이번 방향은 빌드 → 실패 로그 수집 → 원인 진단 → 수정 → 재빌드를 하네스와 모델이 돌리는 클로즈드 루프 실행입니다.

Compose 셰이더 생성​

  • AGSL(Android Graphics Shading Language)을 Compose Modifier.graphicsLayer나 셰이더 브러시에 직접 작성합니다.
  • 120fps Compose 애니메이션과 함께 도는 경량 GPU 셰이더를 생성합니다. 프로스트드 글래스, 동적 조명, 파문 같은 효과가 예시입니다.
  • 벡터·렌더링 수학까지 처리해 뽑아낸다고 합니다.
  • Compose 셰이더는 AGSL 문법과 렌더링 수학, 성능 예산 때문에 실무에서 진입 장벽이 높은 영역입니다.

터미널 에이전트 연결​

  • 터미널 에이전트 연결은 공식 Android CLI 플러그인이 맡습니다.
  • android init 한 줄이면 어떤 터미널 에이전트든 로컬 Android 도구와 연결됩니다.
  • Antigravity라면 플러그인 설치로 끝납니다.

실무에서 주의할 점​

빌드 로그가 곧 에이전트의 입력입니다.
Self-Healing이 동작하려면 빌드 실패 로그가 잘 읽혀야 합니다.
난독화된 멀티모듈 빌드에서 에이전트가 원인에 닿으려면, 지금부터라도 Gradle 빌드 스크립트와 에러 메시지를 사람이 읽을 수 있게 정리해 두는 것이 이득입니다.
비용 구조도 확인해야 합니다.
Antigravity는 AI Ultra 구독 전제이고, API 경로는 Gemini API 유료 티어 전제입니다.
인트로 가격은 2026년 11월 30일까지 적용되므로, 이후 정가를 모르면 팀 도입 판단이 어렵습니다. 도입 전에 Console에서 실제 과금을 먼저 확인해야 합니다.
셰이더 코드는 리뷰가 필수입니다.
"프로덕션급"이라는 표현은 모델 벤더의 주장일 뿐이고, AGSL 셰이더는 GPU와 디바이스별로 동작이 달라 실기 검증 없이는 쓸 수 없습니다. 에이전트가 짠 셰이더는 초안으로 보고 프레임 타임과 배터리부터 측정해야 합니다.
Firebase AI Logic 경로는 인앱 기능용입니다.
개발 워크플로(빌드 복구·코드 생성)와 앱 내 AI 기능(사용자 대면)은 접근 경로가 다르므로, 팀에서 둘을 혼동하면 과금·권한 설계가 꼬입니다.
터미널 에이전트에 Android CLI를 붙이는 방법은 다음과 같습니다.

# 어떤 터미널 에이전트에서든: 로컬 Android 도구와 연결
android init

# Antigravity를 쓴다면: 공식 Android CLI 플러그인 설치
agy plugin install android-cli-plugin

Firebase AI Logic으로 인앱에 붙일 때는 모델 선택만 새 모델로 바꾸는 구조라, 기존 Vertex AI와 Gemini Developer API 연동 코드의 모델명 교체 수준에서 검토가 가능합니다.
정확한 모델 식별자는 Firebase AI Logic 문서를 확인해야 하고, 릴리스 직후에는 SDK 업데이트가 필요할 수 있습니다.
샘플 프로젝트 gemini-4-antigravity-quickstart도 함께 공개되었으니, 에이전트 워크플로를 팀에 도입하기 전에 퀵스타트로 확인하는 것이 좋습니다.

마치며​

Gemini 4 Argon의 핵심은 모델 성능보다 빌드와 셰이더까지 에이전트 워크플로에 들어왔다는 점입니다.
도입 전에 비용 구조와 실기 검증 절차부터 정리해 두는 것이 좋겠습니다.

터미널에서 에이전트와 함께 개발하기 Android CLI 공식 플러그인

2026년 11월 2일 · 약 4분
Way
Android Developer

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.
최근 Android Dev Summit 2026에서 공개된 Android CLI 공식 에이전트 플러그인에 대해 설명해드리겠습니다.

배경​

최근 Android 개발 환경에서는 AI 코딩 에이전트의 역할이 빠르게 커지고 있습니다.
Android Studio Rabbit 2에서는 IDE 안에서 원하는 에이전트를 고르는 Bring Your Own Agent가 안정화되었습니다.
그런데 모든 개발자가 IDE 안에서만 에이전트를 쓰는 것은 아닙니다.
터미널에서 작업하는 에이전트, CI 파이프라인에서 동작하는 자동화 흐름도 함께 고려해야 합니다.
이번에 공개된 Android CLI 공식 에이전트 플러그인은 바로 이 지점을 겨냥합니다.
터미널에 상주하는 에이전트에게 Android 개발 도구를 직접 쥐여주는 방식입니다.

Android CLI 공식 플러그인 살펴보기​

플러그인은 Claude Code, OpenAI Codex, Google Antigravity에 공식으로 제공됩니다.
플러그인을 설치하면 에이전트에게 android-cli 스킬이 추가됩니다.
이 스킬을 통해 에이전트는 프로젝트 생성, 가상 기기 관리, 실시간 UI 레이아웃 검사, Journeys 실행, 공식 Android Knowledge Base 검색을 수행합니다.

설치하기​

각 에이전트마다 설치 명령이 조금씩 다릅니다.
Claude Code에서는 마켓플레이스를 추가한 뒤 플러그인을 설치합니다.

claude plugin marketplace add android/android-cli-plugin
claude plugin install android-cli@android-cli-plugin

Codex에서는 두 번째 명령의 동사가 add라는 점이 다릅니다.

codex plugin marketplace add android/android-cli-plugin
codex plugin add android-cli@android-cli-plugin

Antigravity에서는 전용 마켓플레이스 경로로 설치합니다.

agy plugin install android-cli-plugin@antigravity-plugins-official

설치가 끝나면 에이전트 세션 안에서 Android CLI를 바로 사용할 수 있습니다.
먼저 android init으로 에이전트 설정을 마치고, android skills list로 제공되는 스킬 목록을 확인하는 흐름이 안내됩니다.

Compose 프리뷰와 기기 스트리밍​

터미널 기반 에이전트의 약점은 화면을 직접 보지 못한다는 점이었습니다.
Android CLI는 이 약점을 두 가지 기능으로 보완합니다.
첫 번째는 Compose 프리뷰 렌더링입니다.
에뮬레이터를 띄우거나 APK를 설치하지 않고도 프리뷰를 렌더링해 UI 변경을 즉시 시각적으로 검증합니다.
두 번째는 Android Device Streaming입니다.
Firebase 기반으로 원격 실기기를 연결해 기기별 이슈를 직접 확인합니다.
구글은 내부 테스트 기준으로 android preview를 활용한 에이전트가 UI 작업을 더 빠르게 마쳤다고 밝혔습니다.
이 수치는 구글 자체 테스트 결과이므로, 참고용 지표로 받아들이는 편이 좋습니다.

프로파일링과 분석​

Android CLI에는 성능 분석 도구도 함께 들어 있습니다.
Perfetto 기반 시스템 트레이스를 수집해 콜드 스타트 지연, UI 끊김, 백그라운드 깨어남을 살펴봅니다.
메모리 누수 탐지에는 오픈소스 LeakCanary가 내장되어 있습니다.
analyze 기능은 앱 번들과 라이브러리를 검사해 난독화, 최적화, 축소 점수를 확인합니다.
Google Play에 업로드하기 전에 스토어와 같은 기준으로 품질 신호를 미리 점검하는 용도입니다.

30개 이상의 Android 스킬​

플러그인과 함께 제공되는 Android 스킬은 30개 이상이며, 20개 이상의 영역을 다룹니다.
권한 보안, Glance 위젯 레이아웃, Compose 성능 최적화 같은 주제가 포함됩니다.
에이전트가 범용 지식만으로 추측하지 않고, Android 공식 가이드에 근거해 작업하도록 돕는 장치입니다.
필요한 스킬만 골라 추가하는 방식이라, 프로젝트 성격에 맞게 범위를 조절할 수 있습니다.

실무 관점​

MTS처럼 보안과 정확성이 중요한 프로젝트에서 에이전트 도구를 쓸 때는 범위를 좁게 잡는 편이 좋습니다.
에이전트에게는 프리뷰 렌더링, 레이아웃 검사, 트레이스 수집 같은 확인 작업부터 맡기고, 실제 반영은 사람이 검토하는 구조가 안전합니다.
실기기 검증은 원격 스트리밍으로 1차 확인하고, 최종 검증은 내부 테스트 트랙과 실기기에서 마치는 편이 좋습니다.
에이전트가 생성한 코드는 빌드와 테스트를 통과했는지, 기존 아키텍처와 어긋나지 않는지 별도로 확인해야 합니다.

마치며​

Android CLI 공식 플러그인은 에이전트의 작업 공간을 IDE 밖으로 넓혔습니다.
터미널과 CI에서도 프리뷰, 기기, 프로파일링 도구를 같은 방식으로 쓸 수 있게 되었습니다.

Android CLI에 실기기 스트리밍이 붙었다 — 에이전트가 원격 단말에서 직접 확인하는 흐름

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.
2026년 10월 2일 공개된 Android CLI 업데이트에 대해 설명해드리겠습니다.

배경​

Android CLI는 특정 AI 모델에 묶이지 않고, 다양한 코딩 에이전트와 함께 프로젝트 생성, 빌드, 테스트, 에뮬레이터 실행을 돕는 커맨드라인 도구입니다.
실기기에서만 재현되는 하드웨어/OS 이슈는 에뮬레이터로 놓치기 쉽지만, 필요한 단말이 항상 책상 위에 있는 것도 아닙니다.
이번 업데이트의 핵심은 두 가지입니다.
원격 실기기에 붙는 Device Streaming을 CLI에서 쓸 수 있게 됐고, 에이전트용 Android skills가 20개를 넘어섰습니다.
자세한 내용은 Android Developers Blog 원문에서 확인할 수 있습니다.

무엇이 달라졌는지​

Device Streaming을 에이전트가 직접 쓴다​

CLI를 통해 Android Device Streaming에 접속하면, 손에 없는 실기기라도 원격으로 앱을 올리고 로그와 트레이스를 수집하고 스크린샷까지 찍을 수 있습니다.
에이전트가 보안이 적용된 ADB over SSL 연결을 통해 원격 단말을 마치 USB로 연결한 것처럼 다룰 수 있게 됐습니다.
가능한 작업은 대략 다음과 같습니다.

  • 원격 단말 깨우기, 빌드 배포
  • 로그/트레이스 수집
  • 헤드리스 스크린샷 캡처
  • 터미널 안에서 기기 목록을 보고 어떤 단말을 쓸지 선택

코드를 고쳤으니 실제 단말에서 눌러보고 결과를 가져오는 흐름을, 사람이 중간에 끼지 않고도 시도할 수 있는 기반이 생긴 것입니다.

Android skills가 실무형으로 늘어났다​

Android skills는 SKILL.md 형태의 구조화된 지침 모음입니다.
모델의 학습 시점에 기대지 않고, 공식 가이드 기준으로 에이전트에게 맥락을 주입하는 방식입니다.
공식 skills 저장소에는 이제 20개가 넘는 스킬이 있고, 성격도 꽤 실무적입니다.

  • 제출 전 Play 정책 준수 점검(매니페스트, 권한, 타깃 SDK, 개인정보 고지)
  • Credential Manager 기반 복원 로그인(Restore Credentials) 구현
  • 암시적 인텐트 탈취 같은 인텐트 보안 점검
  • 프로파일러로 프레임 드롭 원인을 찾고 PerfettoSQL로 트레이스 질의
  • 구형 Camera1/Camera2 코드를 CameraX로 이전
  • Leanback 기반 TV 화면을 Compose for TV로 전환
  • Media3 재생 상태와 Cast 수신기 동기화
  • 테스트 전략(단위 테스트, Compose UI 테스트, 스크린샷 테스트) 세팅
  • R8 설정 감사

이번 글에서는 Wear OS용 Compose Material 3 스킬이 스포트라이트로 소개됐습니다.
둥근 화면, 회전 입력, 저전력, TransformingLazyColumn, AppScaffold/ScreenScaffold 같은 Wear 특유의 패턴을 에이전트가 놓치지 않게 잡아주는 스킬입니다.
FotMob 팀이 기존 Wear 앱의 리스트 여러 개를 이 패턴으로 옮기면서 레거시 래퍼와 회전/포커스 보일러플레이트를 걷어냈다는 사례도 함께 실렸습니다.

스킬 관리가 CLI에 붙었다​

스킬은 프로젝트마다, 또 에이전트마다 디렉터리가 달라서 관리가 번거로울 수 있는데, 흐름은 비교적 단순하게 정리돼 있습니다.

# Android CLI 설치 후 android-cli 스킬 세팅
android init

# 공식 스킬 목록 확인
android skills list

# 필요한 스킬만 프로젝트에 추가 (예: Wear Compose M3)
android skills add wear-compose-m3 --project=.

# 나중에 일괄 업데이트
android skills update --all

이 스킬들은 특정 환경 전용이 아니라는 점이 중요합니다.
Android Studio, 다른 코드 에디터, 서드파티 에이전트 환경에서도 같은 스킬을 재사용하는 방향으로 설계됐다고 합니다.

실무에서 주의할 점​

금융 앱처럼 단말 파편화와 보안 정책이 중요한 환경에서는, 에이전트가 실기기 결과를 직접 확인하는 흐름이 매력적입니다.
다만 바로 운영 파이프라인에 넣기 전에 확인할 것도 있습니다.

  • 권한과 보안 연결: 원격 단말 접속은 ADB over SSL 기반이라지만, 사내 네트워크 정책과 단말 접근 통제 범위 안에서 써야 합니다. 어떤 프로젝트를 링크하고, 어떤 로그가 외부로 나가는지 먼저 정리가 필요합니다.
  • 스킬은 정답지가 아니라 맥락입니다: 스킬이 있어도 최종 판단은 코드 리뷰와 테스트가 해야 합니다. 특히 Play 정책, 권한, 인텐트 보안처럼 심사/보안과 닿은 영역은 스킬 결과를 그대로 믿지 말고 체크리스트로 한 번 더 확인하는 것이 좋습니다.
  • 비용이 드는 반복 실행 주의: 단말 확인을 에이전트 루프에 넣으면, 사람이 할 때보다 훨씬 자주 실행하게 됩니다. 테스트 단말 시간, 네트워크, CI 분(minute)을 먹는 구조인지 먼저 작은 작업으로 측정해 보시기 바랍니다.

장점도 분명합니다.
지금까지는 에이전트가 코드만 보고 추측했다면, 이제는 실행 결과(로그, 스크린샷, 트레이스)를 근거로 다음 패치를 제안하는 루프를 만들 수 있습니다.
UI 회귀나 단말별 렌더링 차이를 잡는 데 특히 도움이 될 만합니다.
거창하게 시작하기보다 스킬 한 개와 단말 한 대로 작은 실험부터 해 보는 것이 좋습니다.

# 1) 지금 프로젝트에 테스트 전략 스킬을 붙여 현재 테스트 구성을 점검
android skills add testing-strategy --project=.

# 2) 에이전트에게 요청하는 프롬프트 예시
# "이 모듈의 Compose UI 테스트가 비어 있는 화면을 찾아서,
#  Device Streaming 단말에서 스크린샷까지 확인한 뒤 결과를 보고해줘"

스크린샷 테스트가 약한 화면부터 에이전트에게 맡겨보면, 사람이 놓친 레이아웃 깨짐을 얼마나 잡아내는지, 반대로 오탐이 얼마나 나오는지 금방 감이 옵니다.
그 다음에 R8 감사나 CameraX 이전처럼 범위가 넓은 스킬로 확장해도 늦지 않습니다.

마치며​

이번 업데이트의 방향은 에이전트가 코드를 더 잘 쓰는 것에서, 에이전트가 실행 결과까지 확인하며 일하는 것으로 한 발 나간 것입니다.
CLI와 skills를 한 번쯤 직접 만져보면서, 내 프로젝트에서 자동으로 확인할 수 있는 일이 무엇인지 목록을 만들어보는 것만으로도 가치가 있을 것입니다.

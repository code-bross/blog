Remote Compose 1.0.0-alpha21 — 10월 AndroidX 릴리스에서 본 서버 구동 UI의 현재 위치

2026년 10월 12일 · 약 5분
Way
Android Developer

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.
2026년 10월 7일, AndroidX 정기 릴리스 배치가 나왔습니다. 그중에서도 눈에 띄는 건 remote-compose 1.0.0-alpha21과 compose.remote.foundation 1.0.0-alpha04입니다. Remote Compose는 서버 구동 UI(Server-Driven UI)를 위한 Jetpack 라이브러리인데, 릴리스 노트를 읽다 보면 "에이전트가 만든 UI를 앱 업데이트 없이 내려받아 그리는" 흐름이 점점 현실화되고 있다는 느낌을 받습니다. 이번 글에서는 Remote Compose 알파21의 변경점을 중심으로, 같이 묶여 나온 10월 배치의 실무 포인트를 정리합니다.

핵심 요약​

  • Remote Compose 1.0.0-alpha21: 라이트/다크 테마 인식 색상, 텍스트 크기 측정 API, RemoteDocumentPreview 설정 확장, 원형 텍스트 렌더링 지원, DEFLATE 압축 문서 로딩 등.
  • 새로 등장한 compose.remote.foundation 1.0.0-alpha04까지 합치면, "서버에서 UI 문서를 내려받아 그대로 그린다"는 그림이 Jetpack 레벨에서 정비되는 중입니다.
  • 같은 배치의 Compose 1.13.0-beta01은 이제 Kotlin 2.2를 타깃으로 하며 kotlinc 2.2를 요구합니다. 베타를 올릴 계획이라면 컴파일러 버전도 같이 봐야 합니다.
  • appfunctions 1.0.0-alpha13은 API 리네임이 있습니다. AppFunction 어노테이션이 AppFunctionDeclaration으로 바뀌었으니, 알파를 실험 중인 프로젝트는 릴리스 노트를 확인하고 올리세요.
  • collection 1.7.0 스테이블에는 ScatterMap 성능 개선과 원시 타입 리스트 정렬/이진 탐색 추가가 있습니다.

무엇이 달라졌는지​

Remote Compose 1.0.0-alpha21​

테마 인식 원격 색상

RemoteColor.Companion에 createThemedRemoteColor가 추가됐습니다. 서버에서 내려받은 문서가 클라이언트의 라이트/다크 테마를 따라 색상을 바꿀 수 있게 되는 겁니다. 서버 구동 UI에서 가장 자주 요구되는 "다크 모드 대응"을 플레이어 쪽이 해결해 주니, 문서 생성 로직에서 분기할 필요가 줄어듭니다.

텍스트 측정 API

RemoteTextMeasurer와 rememberRemoteTextMeasurer가 새로 들어왔습니다. Remote Compose 문서 안에서 텍스트의 실제 렌더링 크기를 잴 수 있게 된 것으로, 문서 생성 시점에 텍스트 길이에 따라 레이아웃을 조정해야 하는 경우(예: 배지, 동적 라벨) 유용합니다. Float.rsp/RemoteFloat.rsp 확장 프로퍼티도 추가돼서 Sp 단위의 RemoteTextUnit을 리터럴이나 동적 표현식에서 바로 만들 수 있습니다.

문서 생성·미리보기 개선

  • RemoteDocumentPreview에 profile 파라미터가 생겼습니다. 문서 버퍼를 팽창시키기 전에 설정을 조정할 수 있어, 테스트·디버깅 환경에서 문서 생성을 세밀하게 제어할 수 있습니다.
  • 플레이어와 테스트 프로파일이 DrawTextOnCircle을 지원합니다. 원형 경로에 텍스트를 그리는 연출이 이제 원격 문서에서도 깨지지 않습니다.
  • DEFLATE로 압축된 문서를 플레이어가 로드할 수 있게 됐습니다. 문서 크기가 크다면 전송량을 줄이는 방향으로 설계할 여지가 생깁니다.
  • captureSingleRemoteDocument/captureRemoteDocument의 라이프사이클과 스냅샷 처리가 다져졌고, 수집 속도가 리컴포지션을 따라가지 못할 때 업데이트가 조용히 누락되던 버그도 수정됐습니다. 서버 구동 UI에서 "가끔 화면이 안 바뀌는" 식의 간헐적 이슈가 줄어들 것으로 보입니다.
  • 커스텀 진입/종료 가시성 애니메이션 지원, 스프링 애니메이션의 스냅·범위 이탈 버그 수정 등 렌더링 품질 쪽도 여러 건 잡혔습니다.

compose.remote.foundation 1.0.0-alpha04

같은 배치에 androidx.compose.remote.foundation의 새 알파가 같이 나왔습니다. 의존성은 다음과 같이 선언합니다.

dependencies {
    implementation("androidx.compose.remote.foundation:foundation:1.0.0-alpha04")
}

같이 나온 것들​

  • Compose 1.13.0-beta01 (animation/foundation/material/runtime): 이번 배치부터 라이브러리들이 Kotlin 2.2를 타깃으로 하고 kotlinc 2.2를 요구합니다. 베타를 올릴 때는 Kotlin 버전을 2.2 이상으로 올려야 컴파일이 됩니다.
  • appfunctions 1.0.0-alpha13: @AppFunction → @AppFunctionDeclaration, ObserveAppFunctionsEvent → AppFunctionsChangeEvent로 리네임됐고, 접근 레벨 제한을 위한 @AppFunctionAccessLevel이 추가됐습니다. 에이전트·Gemini 시대의 앱 기능 노출 인터페이스라 실험 중이라면 이름 바뀐 것만 확인하면 됩니다.
  • collection 1.7.0 (스테이블): toOrderedScatterSet() 확장(빈 소스에선 할당 없는 싱글턴 반환), ScatterMap.getOrPut() 최적화, Float 키 해시 충돌 개선, 원시 타입 리스트(IntList/LongList 등)에 sortWith/sortBy/binarySearch 추가. 퍼포먼스에 민감한 데이터 구조를 쓰는 팀은 별도 변경 없이 이득을 볼 수 있습니다.
  • benchmark 1.6.0-alpha01: :lockClocks 태스크가 root 없이도 고정 성능 모드를 쓸 수 있게 돼서, 더 많은 실기기에서 안정적인 마이크로벤치마크가 가능합니다. 히프 프로파일링용 MemoryProfilingConfig도 추가됐습니다.

실무 영향 / 주의점​

  • Remote Compose는 아직 알파입니다. API가 바뀔 수 있다는 전제로 실험·프로토타입 수준에서 접근하는 게 맞습니다. 다만 테마 인식, 텍스트 측정, 압축 문서 로딩처럼 "운영에 쓰려면 꼭 있어야 할" 기능들이 차례로 들어오고 있어서, 방향성 자체는 꽤 진지하게 보입니다.
  • 에이전트 시대의 SDUI: 최근 Android CLI와 에이전트 스킬 흐름과 맞물려, "에이전트가 생성한 UI를 어떻게 앱에 그릴 것인가"가 실무 질문이 되고 있습니다. Remote Compose는 그 답 중 하나입니다. 당장 도입하지 않더라도 개념과 플레이어 구조는 한 번 훑어둘 만합니다.
  • Compose 1.13 베타 + Kotlin 2.2: 컴파일러 버전 요구사항이 같이 올라간 릴리스라서, 버전만 올렸다가 빌드가 깨지는 경우가 생길 수 있습니다. 베타를 쓸 거면 libs.versions.toml의 Kotlin 버전도 함께 올립니다.
  • appfunctions 리네임: 알파 실험 중이라면 컴파일 에러가 나는 게 정상이니, 이름만 바꿔 주면 됩니다.

내 코드에서 이렇게 써볼 생각입니다​

당장은 프로덕션 도입이 아니라 관측 모드입니다. SDK 36 대응 같은 급한 일에 밀려 손이 안 가겠지만, 스프린트 사이에 작은 실험 프로젝트 하나로 Remote Compose 플레이어에 문서 하나 띄워 보는 건 해볼 생각입니다. 관전 포인트는 두 가지입니다.

  1. 서버에서 보낸 문서가 다크 테마에서 깨지지 않는지 (createThemedRemoteColor 사용)
  2. 텍스트 길이 가변적인 배지 UI를 RemoteTextMeasurer로 제대로 그릴 수 있는지
// gradle/libs.versions.toml
[versions]
androidxRemoteCompose = "1.0.0-alpha21"
composeRemoteFoundation = "1.0.0-alpha04"

에이전트가 UI를 만드는 시대가 오고 있는데, "어떻게 그릴 것인가"는 여전히 앱 개발자의 몫입니다. Remote Compose가 그 몫을 나눠 가질 후보 중 하나라는 점에서, 이번 릴리스는 지켜볼 가치가 있습니다.

마치며​

10월 AndroidX 배치는 "UI를 코드가 아니라 문서로 다루는" 쪽으로 축이 이동하고 있음을 보여줍니다. Remote Compose 알파21의 변경점 대부분이 렌더링 품질과 운영 편의(테마, 압축, 측정)에 집중돼 있다는 점이 그 신호입니다. 바로 쓸 필요는 없지만, 다음에 SDUI를 고민할 때 선택지에 넣어두기 좋은 타이밍입니다.

Play 타깃 API 36 제출 차단이 현실화됐다 — 11월 1일 연장 신청과 대응 체크리스트

2026년 10월 12일 · 약 5분
Way
Android Developer

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.
2026년 8월 31일을 기점으로, Google Play에 제출되는 신규 앱과 앱 업데이트는 Android 16(API 36) 타깃이 필수 조건이 됐습니다. 경고로 끝나는 줄 알았던 마감일이 이제는 실제로 업로드를 막는 단계에 들어왔습니다. 한 줄짜리 크래시 핫픽스도 targetSdk를 36으로 올리기 전까지는 콘솔에 올라가지 않습니다. 아직 대응 전이라면 11월 1일까지 한 번의 연장을 신청할 수 있는데, 이것도 자동으로 주어지는 건 아닙니다. 이번 글에서는 규칙의 정확한 내용과 바로 실행할 수 있는 체크리스트를 정리합니다.

핵심 요약​

  • 2026년 8월 31일 이후, 신규 앱·앱 업데이트는 Android 16(API 레벨 36) 이상을 타깃해야 Google Play에 제출할 수 있습니다. (Wear OS·Android Automotive는 API 35, Android TV·Android XR은 API 34)
  • 이미 스토어에 있는 앱은 API 35 이상을 타깃해야 타깃보다 높은 OS를 쓰는 신규 사용자에게 계속 노출됩니다. API 34 이하에 머물면 신규 사용자 설치가 조용히 막힙니다.
  • 시간이 부족하면 Play Console에서 2026년 11월 1일까지의 연장을 한 번 신청할 수 있습니다. 한 번뿐이고, 11월 1일은 확정 기한입니다.
  • targetSdk만 바꾸는 게 끝이 아니라, Android 16의 동작 변경(엣지 투 엣지 의무화 등)에 대한 회귀 테스트가 진짜 작업량입니다.

무엇이 달라졌는지​

규칙은 제출 시점에 막는다​

이 요구사항의 포인트는 "심사"가 아니라 "제출" 단계에서 걸린다는 점입니다. Play Console에 AAB를 올리는 순간 타깃 API 검사가 먼저 돌아가고, 조건을 못 맞추면 업로드 자체가 거부됩니다. 즉, 심사 지연이 아니라 아예 리뷰 대기열에 들어가지도 못합니다. 한참 전에 만들어 둔 빌드를 "그냥 올려야지" 하던 팀은 여기서 바로 발목이 잡힙니다.

세 가지 상태, 세 가지 기준​

Google의 타깃 API 정책은 앱의 상태를 이렇게 구분합니다.

앱 상태적용 기준
신규 앱(아직 게시 안 됨)첫 제출부터 API 36 이상 (휴대폰·태블릿·폴더블 기준)
기존 앱의 업데이트 제출대체 버전 제출 시 API 36 이상
기존 앱(업데이트 안 함)API 35 이상이어야 신규 사용자에게 노출 유지

"기존 앱은 API 35면 되니까 업데이트도 35면 되지 않나?"라고 착각하기 쉬운데, 그렇지 않습니다. 업데이트를 한 번이라도 제출하면 그 순간부터 신규 앱과 같은 API 36 기준이 적용됩니다. API 35는 "아무것도 안 하고 놔둬도 스토어에서 사라지지는 않게 해주는" 완충선일 뿐, 업데이트 면제권이 아닙니다.

연장 신청: 11월 1일까지, 한 번​

Play Console에서 해당 앱의 타깃 API 경고 화면으로 들어가면 연장 신청 양식을 찾을 수 있습니다. 신청이 받아들여지면 기한이 2026년 11월 1일로 미뤄집니다. 중요한 건 이 연장이 "자동"도 아니고 "반복"도 안 된다는 점입니다. 11월 1일 이후에는 다시 기준이 원상복귀됩니다. 신청 안 하고 버티면 하루라도 늦은 날부터 제출이 막히니, 대응 일정이 빠듯하다면 일단 신청부터 해두고 개발을 진행하는 게 합리적입니다.

실무 영향 / 주의점​

  • 숫자 바꾸는 건 1분, 동작 변경 대응이 본게임: 2026년 10월 초에 세 개 앱을 API 36으로 올린 개발자의 회고에 따르면, build.gradle.kts의 숫자 변경은 1분이면 되지만 이후 작업에 이틀이 걸렸다고 합니다. Android 16에서는 엣지 투 엣지(Edge-to-Edge)가 의무화되고, 태블릿·폴더블에서는 방향 고정(orientation lock)이 무시되는 등 실제 동작이 바뀌는 지점이 있습니다. UI가 화면 끝까지 그려지는지, 인셋 처리가 깨지지 않는지 확인이 필요합니다.
  • API 34 이하에 머무르면 "조용히" 죽는다: 앱이 스토어에서 갑자기 삭제되는 게 아니라, 타깃보다 높은 OS 버전을 쓰는 신규 사용자에게만 노출이 중단됩니다. 설치율이 이유 없이 떨어지는 것처럼 보이기 때문에, 모니터링만 보고 있으면 원인 파악이 늦어집니다. 우리 앱의 현재 targetSdk를 Play Console 앱 대시보드에서 먼저 확인해 보세요.
  • 연장은 계획이 아니다: 연장을 신청하면 6주 남짓의 시간을 버는 것뿐이고, 작업량은 그대로입니다. 연장 승인이 났다는 이유로 회귀 테스트를 줄이면 나중에 더 아픕니다.
  • 연관 게이트도 같이 확인: 같은 시기, Play Billing을 쓰는 앱은 Billing Library 8.0.0 이상이 동반 요구되고, 네이티브 코드를 포함하는 앱은 2027년 2월 1일부터 16 KB 페이지 사이즈 지원 없이는 업로드가 거부됩니다. targetSdk 올릴 때 같이 점검하면 일정을 한 번으로 합칠 수 있습니다.

내 코드에서 이렇게 확인할 생각입니다​

급한 순서대로 체크리스트입니다.

// app/build.gradle.kts (Kotlin DSL)
android {
    compileSdk = 36
    defaultConfig {
        minSdk = 24
        targetSdk = 36   // ← 이 숫자. 8월 31일 이후 제출 조건
    }
}
  1. Play Console → 해당 앱 → 정책/타깃 API 경고 화면에서 현재 상태 확인
  2. 아직 36이 아니면 연장 신청 폼부터 제출 (11월 1일까지, 한 번)
  3. compileSdk/targetSdk 36으로 올리고 엣지 투 엣지·인셋·방향 처리 회귀 테스트
  4. Billing Library 버전(8.0.0+)과 16 KB 페이지 사이즈 대응 여부도 같은 패스에 확인

템플릿이나 프레임워크가 아직 35를 기본값으로 쓰고 있는 경우가 많으니, 신규 프로젝트라면 프로젝트 생성 직후 이 숫자부터 확인하는 습관을 들이는 게 좋습니다.

마치며​

타깃 API 마감일은 매년 오는 행사지만, 올해는 "제출 차단"이라는 점에서 체감 강도가 다릅니다. 특히 API 34 이하에 머무는 앱은 신규 사용자 노출이 조용히 막히기 때문에, 별다른 이상 없이 설치 지표가 떨어지는 상황이면 targetSdk를 먼저 의심해 보길 권합니다. 연장은 마지막 수단이 아니라, 일정 확보를 위한 첫 번째 행동입니다.

Kotlin 2.4.21 버그픽스 릴리스 — 2.4.x 라인 유지팀은 안전하게 올릴 시점

2026년 10월 11일 · 약 3분
Way
Android Developer

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.
2026년 10월 8일, JetBrains가 Kotlin 2.4.21을 릴리스했습니다. 기능 추가 없는 버그픽스 릴리스라서 2.4.x 라인을 쓰고 있는 팀이라면 특별한 고민 없이 올릴 수 있는 버전입니다.

핵심 요약​

  • K/Wasm에서 잘못된 타입의 인자로 람다를 호출하면 트랩이 나던 문제가 고쳐졌습니다. 이제 정상적으로 ClassCastException이 던져집니다.
  • Kotlin/JS 프로덕션 빌드에서 멤버 이름이 minify되지 않도록 되돌려졌습니다.
  • JVM 리플렉션의 KCallable 표현 방식이 K1 컴파일러 의존성을 제거하는 방향으로 바뀌었습니다.
  • Kotlin Script와 JSR-223(스크립트 2회 실행 시 NoClassDefFoundError, 바인딩 깨짐 등) 관련 수정이 여러 건 포함됐습니다.

무엇이 달라졌는지​

K/Wasm: 조용한 트랩 대신 예외가 던져진다​

(T) -> R 형태의 람다에 T가 아닌 인자를 넣었을 때, 이전에는 Wasm 트랩이 발생해 "뭘 잘못한 건지" 알기 어려웠습니다. 이번 수정으로 ClassCastException이 정상적으로 던져집니다. K/Wasm 타깃을 만지는 KMP 프로젝트라면, 기존에 트랩으로 죽던 경로가 이제 catch 가능한 예외로 바뀌는 것이니 예외 처리 로직을 한 번 확인해 볼 만합니다.

Kotlin/JS: 프로덕션 빌드에서 멤버 이름 유지​

K/JS 프로덕션 빌드에서 멤버 이름이 minify되던 변경이 되돌려졌습니다. 디버깅이나 런타임 이름 기반 처리에 영향을 받을 수 있는 프로젝트는 안심하고 올릴 수 있는 방향입니다.

리플렉션에서 K1 의존성 제거​

KCallable의 내부 표현이 K1 컴파일러에 의존하지 않도록 정리됐습니다. 겉으로는 드러나지 않지만, K2 컴파일러로 완전히 넘어가는 과정에서 남은 구형 의존성을 하나씩 걷어내는 작업입니다. 리플렉션을 쓰는 라이브러리의 내부 구현을 보는 편이라면 "왜 이런 식으로 바뀌었는지"의 맥락 정도로 이해하면 됩니다.

스크립트 관련 수정들​

Kotlin Script에서 전달 의존성이 있는 스크립트를 두 번째 실행하면 NoClassDefFoundError가 나던 문제, JSR-223에서 제네릭 Java 바인딩이 이후의 모든 eval() 호출을 깨뜨리던 문제가 수정됐습니다. 스크립트 엔진을 내장한 앱이라면 의미 있는 수정입니다.

그 밖의 수정​

  • @Serializable 제네릭 클래스에 클래스 상한(class upper bound)이 있을 때 잘못된 Wasm이 나오던 문제
  • K/N Gradle에서 SwiftPM import 시 로그가 넘쳐나던 문제

실무 영향 / 주의점​

  • 2.4.x 라인 유지 중이라면 이번엔 올리면 됩니다. 새 기능이 아니라 버그픽스 묶음이라 동작 변경 리스크가 낮습니다.
  • K/Wasm을 쓰는 KMP 프로젝트는 예외 경로를 점검하세요. 트랩이 예외로 바뀌는 건 에러 처리 전략에 직접 영향을 줍니다.
  • Kotlin/JS는 minify 복원이라 큰 주의점은 없습니다. 오히려 이전 버전에서 이상 징후가 있었다면 해소 방향입니다.
  • 스크립트 엔진 내장 앱(서버 측 혹은 내부 도구)은 이번 릴리스가 제법 알찹니다. 스크립트 실행 관련 수정이 4건이나 들어 있습니다.

내 코드에서는 이렇게 올릴 생각입니다​

버전 카탈로그 기준으로 버전만 바꾸는 게 전부입니다. 다만 올리고 나면 컴파일러가 바뀌는 만큼, 전체 빌드 한 번과 주요 화면 스모크 테스트 정도는 돌립니다.

// gradle/libs.versions.toml
[versions]
kotlin = "2.4.21" // 2.4.20 -> 2.4.21 (버그픽스, 동작 변경 없음 예상)

KMP 프로젝트에서 Wasm 타깃을 쓰는 경우, 릴리스 노트의 해당 항목이 내 코드 경로에 닿는지 빠르게 확인하는 스크립트를 CI에 걸어 두면 이후 릴리스에서도 부담이 없습니다.

마치며​

메이저 릴리스가 아니라서 화려하진 않지만, 이런 버그픽스 릴리스야말로 "그냥 올리면 좋은" 릴리스입니다. 2.4.x 라인에서 운영 중인 프로젝트가 있다면, 이번 주에 버전만 올리고 스모크 테스트 한 번 돌려 보길 권합니다.

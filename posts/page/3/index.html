FCM AndroidConfigV2로 푸시 알림 지연 줄이기

2026년 11월 4일 · 약 4분
Way
Android Developer

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.
2026년 11월 3일 Firebase 블로그에 공개된 FCM AndroidConfigV2에 대해 설명해드리겠습니다.

배경​

푸시 알림은 MTS에서 시세 알림과 체결 알림처럼 시간에 민감한 정보를 전달하는 통로입니다.
그런데 기존 FCM 구조에서는 알림이 제때 도착하지 않는 경우가 있었습니다.
원인은 기기 쪽의 배터리 절약 정책과 백그라운드 실행 제한이었습니다.
딥 도즈와 앱 대기 버킷 같은 단계가 메시지 전달을 늦추는 문턱으로 작용했습니다.
기존 방식은 메시지를 시스템 브로드캐스트로 전달했습니다.
앱은 onMessageReceived 콜백 하나에서 모든 메시지를 받았습니다.
이 콜백의 반환 타입이 void라서, 시스템은 알림이 제대로 표시됐는지 알 수 없었습니다.
서버 쪽에서도 우선순위 설정이 추측에 의존하는 경우가 많았습니다.
high와 normal 중 무엇을 골라야 하는지 기준이 명확하지 않았습니다.

AndroidConfigV2 살펴보기​

마이그레이션 문서에 따르면, 핵심 변화는 메시지를 의도 기준으로 나누는 것입니다.
우선순위를 숫자로 지정하는 대신, 메시지 타입 자체가 긴급도를 결정합니다.

두 가지 메시지 타입​

RemoteNotification은 긴급하고 사용자에게 보여야 하는 알림에 사용합니다.
이 타입은 도즈 제한과 배터리 배치 지연을 우회해 즉시 전달됩니다.
BackgroundSync는 긴급하지 않은 데이터 동기화에 사용합니다.
시세 캐시 갱신이나 앱 상태 동기화 같은 작업이 여기에 해당합니다.
이 타입은 배터리 최적화를 위해 배치가 되거나 지연될 수 있습니다.
사용자에게 보이는 알림을 이 타입으로 보내면 안 됩니다.

서버 전송 방식​

서버에서는 기존 android 블록 대신 android_v2 블록을 사용합니다.
그 안에 remote_notification 또는 background_sync 중 하나를 넣습니다.
ttl과 collapse_key 같은 공통 옵션은 그대로 함께 지정할 수 있습니다.
다음은 mutable_content를 켠 remote_notification 전송 예시입니다.

{
  "message": {
    "token": "<DEVICE_REGISTRATION_TOKEN>",
    "android_v2": {
      "ttl": "3600s",
      "collapse_key": "price_alerts",
      "remote_notification": {
        "mutable_content": true,
        "notification": {
          "title": "체결 알림",
          "body": "주문이 체결되었습니다.",
          "channel_id": "trade_alerts"
        }
      }
    }
  }
}

mutable_content가 false이면 기본값 동작으로 GMS Core가 서버 페이로드를 바로 표시합니다.
이 경우 앱의 백그라운드 코드를 깨우지 않습니다.
mutable_content가 true이면 GMS Core가 앱에 바인딩해 콜백을 호출합니다.
앱은 표시 전에 복호화나 이미지 첨부, 현지화 같은 가공을 할 수 있습니다.
이때도 notification 객체를 함께 보내는 것이 중요합니다.
콜백이 타임아웃되거나 충돌하면 이 페이로드가 폴백 알림으로 표시됩니다.

클라이언트 콜백​

클라이언트에서는 FirebaseMessagingService를 확장하는 서비스에 전용 콜백을 구현합니다.
onMessageReceived 하나로 받던 구조에서 역할별 콜백으로 나뉩니다.
onNotificationReceived는 NotificationResponse를 반환해야 합니다.
다음은 서버 알림을 가공해 반환하는 예시입니다.

class MyFirebaseMessagingService : FirebaseMessagingService() {

    override fun onNotificationReceived(message: RemoteMessage): NotificationResponse {
        val serverNotif = message.notification
        val channelId = serverNotif?.channelId ?: "default_channel"
        val builder = NotificationCompat.Builder(this, channelId)
            .setSmallIcon(R.drawable.ic_stat_notification)
            .setContentTitle(serverNotif?.title ?: "알림")
            .setContentText(decryptPayload(message.data["encrypted_content"]))
            .setPriority(NotificationCompat.PRIORITY_HIGH)
            .setAutoCancel(true)
        return NotificationResponse.create("trade_alert", 100, builder.build())
    }

    override fun onBackgroundSyncReceived(message: RemoteMessage) {
        // 사용자 알림을 표시하지 않고 데이터만 동기화합니다.
        syncMarketData(message.data)
    }
}

onNotificationReceived는 20초 안에 NotificationResponse를 반환해야 합니다.
시간을 초과하면 GMS Core가 서버 폴백 알림을 자동으로 표시합니다.
백그라운드 알림의 억제 비율에도 25% 상한이 있습니다.
이 상한을 넘기면 원래 알림이 자동으로 표시됩니다.
onDeletedMessages는 큐가 넘치거나 장기간 오프라인으로 메시지가 삭제된 경우에 호출됩니다.
이 콜백에서는 서버와 전체 상태를 다시 동기화하는 것이 안전합니다.

EAP 단계라는 점​

한 가지 실무적으로 중요한 사실이 있습니다.
클라이언트 SDK는 아직 EAP 단계입니다.
firebase-messaging 26.1.0-eap01은 공개 Maven 저장소가 아니라 로컬 m2repository 아카이브로 배포됩니다.
따라서 운영 앱에 바로 적용하기보다는 별도 브랜치에서 검증하는 것이 안전합니다.
서버 페이로드와 클라이언트 콜백은 독립적으로 업그레이드할 수 있게 설계됐습니다.
서버는 구버전 클라이언트에도 FCM이 자동 변환해 전달한다고 설명하고 있습니다.

실무 관점​

MTS에 적용한다면 메시지 분류부터 정리하는 것이 좋습니다.
체결 알림과 시세 급변 알림은 RemoteNotification으로 보냅니다.
관심종목 시세 동기화나 배지 갱신은 BackgroundSync로 보냅니다.
mutable_content는 복호화나 현지화가 필요할 때만 켜는 것이 좋습니다.
콜백을 거치면 20초 제한과 폴백 동작까지 함께 관리해야 하기 때문입니다.
폴백 페이로드는 항상 함께 보내서, 콜백 실패 시에도 빈 알림이 나가지 않게 합니다.
collapse_key는 오프라인 뒤 복귀 시 최신 페이로드 하나만 전달되게 정리합니다.

마치며​

AndroidConfigV2는 우선순위 추측을 메시지 의도 선언으로 바꾸는 변경입니다.
알림이 늦는 이유를 서버와 클라이언트가 함께 줄일 수 있는 구조가 됩니다.

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.
Canary 채널에 올라온 Android Studio Rabbit 3 Canary 2에 대해 설명해드리겠습니다.

배경​

Rabbit 2는 현재 Stable 채널에 있습니다.
다음 버전인 Rabbit 3은 Canary 채널에서 제공되고 있습니다.
Canary 빌드는 최신 기능을 먼저 써볼 수 있지만 가볍게 테스트된 단계입니다.
기능이 추가되거나 변경될 수 있다는 전제가 붙습니다.
Canary 2는 Android Gradle Plugin 9.6.0-alpha02와 함께 릴리스됐습니다.
프리뷰 버전의 Studio는 대응하는 프리뷰 AGP와 함께 쓰는 것이 원칙입니다.
이번 글에서는 Rabbit 3에 새로 들어온 기능 네 가지를 살펴보겠습니다.

Rabbit 3 살펴보기​

Compose Preview Screenshot Testing 도구​

Compose UI의 회귀를 막는 스크린샷 테스트 도구가 들어왔습니다.
이 도구는 Compose 프리뷰를 기준으로 스크린샷 테스트를 수행합니다.
결과는 HTML 리포트로 생성돼 UI 변화를 눈으로 확인할 수 있습니다.
디자인 시스템 컴포넌트처럼 화면이 자주 바뀌는 영역에 유용합니다.
스냅샷 비교를 수동 눈대중이 아니라 테스트로 고정할 수 있습니다.

Model Assignment​

AI 모델을 작업 종류별로 다르게 지정하는 기능입니다.
복잡한 추론이 필요한 Agent Mode에는 큰 규모의 모델을 지정할 수 있습니다.
커밋 메시지 생성이나 다음 편집 예측처럼 지연에 민감한 작업에는 가벼운 모델을 지정합니다.
이렇게 하면 품질과 속도, 쿼터 사용량을 작업별로 균형 있게 조절할 수 있습니다.
설정은 다음 경로에서 변경합니다.

File > Settings > Tools > AI > Model Providers > Model Assignment 탭

Agent Mode 패널의 모델 선택 드롭다운에서 직접 바꾸는 방법도 있습니다.
이 경우 Thinking 기능에 대한 Model Assignment 설정이 함께 업데이트됩니다.

iOS, Flutter, React Native 앱 마이그레이션​

기존 크로스 플랫폼 앱을 네이티브 Android 앱으로 바꾸는 도구가 들어왔습니다.
새 프로젝트 마법사에서 마이그레이션 어시스턴트를 호출합니다.
변환 대상은 iOS와 Flutter, React Native 프로젝트입니다.
결과물은 Kotlin과 Jetpack Compose 기반의 Android 앱입니다.
작업 계획과 코드 변환, 컴파일 검사가 통합 진행 UI로 보입니다.
결과물은 바로 테스트와 검증이 가능한 기능하는 프로젝트 형태입니다.

Publish to Google Play for testing​

Play Console 테스트 트랙에 IDE에서 바로 업로드하는 기능이 들어왔습니다.
서명된 앱 번들 생성 흐름이 끝나는 지점에서 이어서 선택합니다.
새 앱의 첫 릴리스는 내부 테스트 트랙에 업로드할 수 있습니다.
기존 앱은 다른 종류의 테스트 트랙에도 업로드할 수 있습니다.
이 기능을 쓰려면 Google Play Console에 등록돼 있어야 합니다.

실무 관점​

Canary는 Stable과 별도로 설치해 운영하는 것이 안전합니다.
운영 프로젝트의 빌드 환경을 Canary로 통째로 옮기는 것은 피하는 것이 좋습니다.
스크린샷 테스트는 전체 화면보다 디자인 시스템 컴포넌트부터 적용하는 것이 좋습니다.
Model Assignment는 쿼터가 소진되는 지점을 확인하면서 조정하는 것이 좋습니다.
Play 테스트 업로드는 내부 트랙부터 검증하고, 이후 트랙을 넓히는 순서가 안전합니다.
마이그레이션 도구는 자동 변환 결과를 그대로 운영에 쓰기보다 컴파일과 동작 검증 뒤에 적용합니다.

마치며​

Rabbit 3는 AI 모델 선택과 UI 회귀 방지, 마이그레이션, 테스트 배포를 한 번에 다룹니다.
Canary라는 전제를 지키면서, 팀에 맞는 기능부터 별도 환경에서 검증하는 것이 좋습니다.

테스트도 minSdk 24 시대로 — AndroidX Test 1.8.0-alpha03과 Espresso 3.8.0-alpha03 살펴보기

2026년 11월 3일 · 약 4분
Way
Android Developer

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.
2026년 10월 29일에 공개된 AndroidX Test 1.8.0-alpha03과 Espresso 3.8.0-alpha03 그룹 릴리스에 대해 설명해드리겠습니다.

배경​

Android 테스트 코드는 앱 코드만큼 오래 유지됩니다.
그런데 테스트 라이브러리가 지원하는 최소 SDK가 앱의 최소 SDK보다 낮으면, 테스트 코드 안에 오래된 SDK를 위한 분기 로직이 계속 남습니다.
이번 AndroidX Test 알파 그룹은 바로 이 지점을 정리합니다.
그룹 전체가 최소 SDK 24로 올라가며, SDK 24 미만을 위한 로직을 제거했습니다.
알파 버전이므로 운영 앱에 바로 적용하기보다는, 변경 내용을 미리 파악하고 테스트 모듈의 방향을 정하는 데 의미가 있습니다.

AndroidX Test 1.8.0-alpha03 살펴보기​

그룹 릴리스 구성​

2026년 10월 29일에는 테스트 그룹 전체가 함께 올라갔습니다.
Core는 1.8.0-alpha03, Espresso는 3.8.0-alpha03입니다.
Espresso Device는 1.2.0-alpha03, JUnit 확장은 1.4.0-alpha03, Truth 확장은 1.8.0-alpha03입니다.
Runner와 Rules도 1.8.0-alpha03, Orchestrator와 Services는 1.7.0-alpha03, Monitor는 1.9.0-alpha04입니다.
참고로 alpha03 항목 자체에는 별도의 변경 목록이 적혀 있지 않습니다.
실질적인 변경 내용은 직전 버전인 10월 15일의 alpha01에 담겨 있습니다.
따라서 이번 글에서는 alpha01의 변경을 중심으로 살펴보겠습니다.

dependencies {
    androidTestImplementation("androidx.test:core:1.8.0-alpha03")
    androidTestImplementation("androidx.test:core-ktx:1.8.0-alpha03")
    androidTestImplementation("androidx.test.espresso:espresso-core:3.8.0-alpha03")
    androidTestImplementation("androidx.test.ext:junit-ktx:1.4.0-alpha03")
}

최소 SDK 24로의 상향​

alpha01에서 그룹 전체의 최소 SDK가 24로 올라갔습니다.
Core와 Espresso, Espresso Device, JUnit 확장이 모두 같은 기준을 적용했습니다.
SDK 24는 Android 7.0에 해당합니다.
SDK 24 미만을 위한 로직이 제거되면서, 테스트 라이브러리 내부가 단순해졌습니다.
앱의 최소 SDK가 이미 24 이상이라면, 테스트 의존성만으로 인한 제약은 줄어듭니다.
반대로 앱의 최소 SDK가 24보다 낮다면, 이 알파 라인을 적용할 수 없습니다.
안정 버전은 여전히 Core 1.7.0과 Espresso 3.7.0이므로, 운영 모듈에서는 안정 버전을 유지하는 것이 안전합니다.

Espresso의 새로운 Intent 매처​

Espresso alpha01에는 IntentMatchers에 부정 매처가 추가되었습니다.
doesNotHaveFlag와 doesNotHaveFlags가 그 대상입니다.
Intent에 특정 플래그가 없어야 하는 경우를 검증할 때 사용합니다.
기존에는 플래그가 있는 경우를 확인하는 매처가 중심이었습니다.
부정 조건을 직접 표현할 수 있게 되면서, Intent 검증 코드가 읽기 쉬워집니다.
예를 들어 화면 전환 시 특정 플래그가 붙지 않아야 하는 정책을 테스트 코드로 남길 수 있습니다.

버그 수정 내용​

alpha01의 버그 수정도 함께 살펴볼 필요가 있습니다.
SDK 36 API를 사용할 때 TestLooperManagerCompat에서 불필요했던 리플렉션이 제거되었습니다.

BaseViewModel을 상속하지 않고 조합하기 — Kotlin 위임과 Lifecycle 2.11 스코프 ViewModel

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.
최근 Medium에서 다뤄진 BaseViewModel의 위임 전환과 Lifecycle 2.11의 스코프 ViewModel을 함께 살펴보겠습니다.

배경​

대부분의 성숙한 Android 코드베이스에는 BaseViewModel 파일이 있습니다.
처음에는 일회성 메시지나 로딩 표시 같은 보일러플레이트를 줄이는 것이 목적입니다.
그런데 시간이 지나면 네트워크 검사, 분석 추적, 오류 다이얼로그, 페이지네이션, 세션 로그아웃까지 쌓입니다.
결국 정적인 화면까지 수백 줄짜리 베이스 클래스를 상속하게 됩니다.
두 가지 부분 동작이 함께 필요한 화면에서는 단일 상속이 한계에 부딪힙니다.
페이지네이션과 검색을 동시에 쓰는 화면이 대표적인 경우입니다.
이 문제를 상속으로 해결하려 하면 베이스 클래스는 더 커지고, 단위 테스트는 모킹 중심으로 어려워집니다.

위임으로 BaseViewModel 대체하기​

기능별 홀더 인터페이스 나누기​

대안은 상속이 아니라 조합입니다.
Kotlin의 인터페이스 위임 by를 사용하면, 필요한 기능만 골라서 붙일 수 있습니다.
먼저 메시지 표시와 로딩 표시를 각각의 인터페이스로 나눕니다.
각 인터페이스는 상태와 상태 변경 함수만 정의합니다.
구현 클래스는 순수한 상태 보관 역할만 맡습니다.
코루틴 스코프는 ViewModel이 소유하므로, 홀더 안에 스코프를 두지 않습니다.

interface MessageHolder {
    val message: StateFlow<String?>
    fun showMessage(text: String)
    fun clearMessage()
}

class DefaultMessageHolder : MessageHolder {
    private val _message = MutableStateFlow<String?>(null)
    override val message: StateFlow<String?> = _message

    override fun showMessage(text: String) {
        _message.value = text
    }

    override fun clearMessage() {
        _message.value = null
    }
}

interface LoadingHolder {
    val isLoading: StateFlow<Boolean>
    fun setLoading(loading: Boolean)
}

class DefaultLoadingHolder : LoadingHolder {
    private val _isLoading = MutableStateFlow(false)
    override val isLoading: StateFlow<Boolean> = _isLoading

    override fun setLoading(loading: Boolean) {
        _isLoading.value = loading
    }
}

ViewModel에서 필요한 것만 조합하기​

ViewModel은 필요한 홀더만 위임으로 가져옵니다.
메시지만 필요한 화면의 ViewModel은 메시지 홀더만 위임합니다.
로딩까지 필요한 화면은 두 홀더를 함께 위임합니다.
두 가지 부분 동작이 필요한 경우에도, 두 인터페이스를 함께 위임하면 해결됩니다.
단위 테스트에서는 실제 홀더를 그대로 쓰거나, 작은 가짜 구현으로 교체할 수 있습니다.
베이스 클래스 전체를 모킹할 필요가 없어집니다.

class HomeViewModel(
    private val repository: HomeRepository
) : ViewModel(),
    MessageHolder by DefaultMessageHolder(),
    LoadingHolder by DefaultLoadingHolder() {

    fun load() {
        viewModelScope.launch {
            setLoading(true)
            try {
                repository.refresh()
            } catch (e: Exception) {
                showMessage("데이터를 불러오지 못했습니다.")
            } finally {
                setLoading(false)
            }
        }
    }
}

Lifecycle 2.11의 스코프 ViewModel​

위임과 함께 살펴볼 기능이 Lifecycle 2.11의 스코프 ViewModel입니다.
2.11.0은 2026년 6월 17일에 공개되었습니다.
ViewModelStoreProvider와 rememberViewModelStoreProvider, rememberViewModelStoreOwner가 새로 들어갔습니다.
이 API들은 ViewModel을 특정 UI 스코프에 묶는 용도입니다.
예를 들어 Pager의 각 페이지마다 별도의 ViewModel을 유지할 수 있습니다.
스코프에 묶인 ViewModel은 구성 변경에도 살아남습니다.
해당 Composable이 계층에서 제거되면 자동으로 정리됩니다.
Navigation3 연동도 함께 강화되었습니다.
ViewModelStoreNavEntryDecorator가 ViewModelStoreOwner를 받아, 중첩된 ViewModel에 생성 정보와 팩토리를 전달합니다.
removeViewModelStoreOnPop은 deprecated 되었습니다.
위임으로 기능을 나누고 스코프로 수명을 나누면, 베이스 클래스에 의존하지 않는 구조가 됩니다.

실무에서 적용할 때​

기존 BaseViewModel을 한 번에 지우지 않는 것이 좋습니다.
신규 화면부터 홀더 위임 방식으로 만들고, 기존 화면은 리팩터링 대상으로 따로 관리합니다.
홀더가 Android 프레임워크 타입에 의존하지 않도록 유지합니다.
그래야 단위 테스트에서 홀더를 그대로 재사용할 수 있습니다.
스코프 ViewModel은 Pager처럼 화면 단위 수명이 필요한 곳부터 적용합니다.
MTS처럼 화면이 많은 앱에서는, 수명 범위를 먼저 정하고 나서 도입하는 것이 안전합니다.

마치며​

상속은 기능을 한 번에 물려주지만, 필요 없는 기능까지 함께 물려줍니다.
위임은 필요한 기능만 골라서 조합하게 하고, 스코프 ViewModel은 수명까지 화면에 맞게 나눠줍니다.

Navigation 3 1.2 딥링크 API 살펴보기

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.
Android Dev Summit 2026에서 다시 강조된 Navigation 3 1.2의 딥링크 API에 대해 설명해드리겠습니다.

배경​

기존 Navigation 2에서는 딥링크를 내비게이션 그래프에 선언하고, 컨트롤러가 백스택을 관리했습니다.
Navigation 3에서는 방향이 달라졌습니다.
백스택을 개발자가 직접 상태로 소유하고, 화면 전환은 그 상태를 렌더링하는 방식입니다.
이런 구조에서는 딥링크 처리도 그래프 선언이 아니라, 요청을 받아 키로 변환하는 과정이 됩니다.
1.2.0 안정 버전(2026년 9월 23일 공개)은 이 과정을 위한 딥링크 API를 정식으로 제공합니다.
Kotlin Multiplatform 환경에서도 같은 API로 딥링크를 다룰 수 있다는 점이 특징입니다.

Navigation 3 1.2 딥링크 살펴보기​

딥링크 처리는 크게 세 단계로 나뉩니다.
요청 만들기, 매처 정의하기, 요청과 매처를 대조해 키 얻기가 그 순서입니다.
각 단계를 코드와 함께 살펴보겠습니다.

DeepLinkRequest 만들기​

DeepLinkRequest는 들어온 딥링크를 표현하는 객체입니다.
문자열 URI, DeepLinkUri, Android Intent 중 하나로 만들 수 있습니다.
URI 외에 액션이나 MIME 타입 같은 부가 정보는 타입 안전한 RequestExtras로 함께 담습니다.

import androidx.navigation3.runtime.deeplink.DeepLinkRequest
import androidx.navigation3.runtime.deeplink.DeepLinkUri
import androidx.navigation3.runtime.deeplink.requestExtras

// 문자열 URI로 요청 만들기
val request = DeepLinkRequest(uri = "https://www.example.com/home")

// DeepLinkUri로 요청 만들기
val deepLinkUri = DeepLinkUri("https://www.example.com/home")
val requestFromUri = DeepLinkRequest(uri = deepLinkUri)

// 액션과 MIME 타입을 함께 담기
val requestWithExtras = DeepLinkRequest(
    uri = "https://www.example.com/image",
    extras = requestExtras {
        put(DeepLinkRequest.ActionExtrasKey, "android.intent.action.VIEW")
        put(DeepLinkRequest.MimeTypeExtrasKey, "image/*")
    }
)

// Activity로 들어온 Intent에서 바로 만들기
val requestFromIntent = DeepLinkRequest(intent = intent)

RequestExtras는 키와 값의 쌍을 타입에 맞게 보관하는 컨테이너입니다.
예전처럼 문자열 키로 값을 꺼내 형변환하던 방식보다 실수가 줄어듭니다.

DeepLinkMatcher 정의하기​

DeepLinkMatcher는 요청을 어떤 내비게이션 키에 연결할지 정의합니다.
하나의 키에 여러 매처를 연결할 수 있습니다.
기본 제공되는 매처는 세 가지입니다.

import androidx.navigation3.runtime.deeplink.DeepLinkMatcher
import androidx.navigation3.runtime.deeplink.DeepLinkUri
import androidx.navigation3.runtime.deeplink.StaticKeyDeepLinkMatcher
import androidx.navigation3.runtime.deeplink.UriDeepLinkMatcher
import androidx.navigation3.runtime.deeplink.withBackStack

// 고정 화면으로 연결되는 매처
val homeMatcher = StaticKeyDeepLinkMatcher(
    HomeKey,
    listOf(DeepLinkMatcher.actionFilter(Intent.ACTION_VIEW))
)

// 경로 인자를 추출하는 매처
val userProfileMatcher = UriDeepLinkMatcher(
    DeepLinkUri("www.example.com/users/{id}"),
    serializer<UserProfileKey>()
).withBackStack { matchResult ->
    listOf(HomeKey, matchResult.key)
}

UriDeepLinkMatcher는 URI 패턴의 {id} 같은 플레이스홀더를 인자로 추출합니다.
withBackStack은 매칭에 성공했을 때 합성 백스택을 함께 만듭니다.
사용자가 딥링크로 상세 화면에 들어왔을 때, 뒤로 가기를 누르면 홈 화면으로 돌아가는 흐름을 이렇게 보장합니다.

요청 매칭하고 백스택 구성하기​

매처 목록을 준비했으면, 들어온 요청과 대조해 키를 얻습니다.
매칭 결과는 비교가 가능하므로, 여러 매처 중 가장 적합한 결과를 고를 수 있습니다.

val deepLinkMatchers = listOf(homeMatcher, userProfileMatcher)

val request = DeepLinkRequest(intent = intent)
val matchResult = deepLinkMatchers.firstNotNullOfOrNull { matcher ->
    matcher.match(request)
}

val backStack = rememberNavBackStack(
    matchResult?.key ?: HomeKey
)

이렇게 얻은 키를 rememberNavBackStack의 시작점으로 넘기면, 이후는 평소와 같은 NavDisplay 흐름으로 이어집니다.
딥링크로 들어온 경우와 앱 안에서 이동한 경우의 화면 렌더링 방식이 달라지지 않습니다.
한편 Activity를 딥링크로 열려면 AndroidManifest.xml에 intent-filter를 등록하는 절차는 여전히 필요합니다.

예측 뒤로 가기와 결과 전달​

1.2에는 딥링크 외에도 두 가지 보강이 함께 들어 있습니다.
첫 번째는 예측 뒤로 가기 연결을 단순화하는 NavigationBackHandler와 rememberNavigationEventState입니다.
전환 도중에 뒤로 제스처가 들어와도 애니메이션이 어긋나지 않도록 처리합니다.
두 번째는 화면 간 결과 전달을 위한 Result API입니다.
ResultEventBus를 통해 항목 간 결과를 주고받고, ResultEffect로 흐름 형태로 수집합니다.

실무 관점​

MTS에서 딥링크는 푸시 알림, 공유 링크, 외부 연동 등 여러 진입점으로 연결됩니다.
딥링크로 바로 열리는 화면이 민감 정보를 다룬다면, 진입 전에 로그인 상태와 접근 권한을 먼저 확인해야 합니다.
합성 백스택은 뒤로 가기 경로를 자연스럽게 만들지만, 스택에 쌓이는 화면이 민감 화면을 거치지 않는지 함께 검토해야 합니다.
URI 패턴은 서버나 마케팅 채널과 공유되므로, 패턴 변경 시에는 기존 링크의 호환 여부를 먼저 확인하는 편이 좋습니다.

마치며​

Navigation 3 1.2는 딥링크를 그래프 선언이 아니라 요청과 매칭의 문제로 정리했습니다.

프로젝트 루트에 아래 파일을 두면 VS Code가 확장 설치를 권합니다.

{
  "recommendations": [
    "JetBrains.intellij-server"
  ]
}

충돌 주의 사항​

Red Hat이나 Oracle의 Java 확장과는 코드 분석과 빠른 수정 기능이 겹칩니다.
동작이 중복되거나 충돌할 수 있으므로 함께 쓸 때는 해당 확장을 비활성화하는 것이 권장됩니다.
Spring 팀의 Spring Tools와는 함께 잘 동작하도록 맞춰져 있습니다.

라이선스 변경 사항​

1.0부터는 프리뷰 단계의 무료 제공이 끝났습니다.
30일 평가판 이후에는 IntelliJ IDEA Ultimate 구독이 필요합니다.
하나의 라이선스로 데스크톱 IDE와 VS Code 계열 에디터를 함께 쓸 수 있습니다.
라이선스는 인간 사용을 기준으로 설계되었습니다.
순수 에이전트 사용을 위한 라이선스 모델은 추후 안내될 예정입니다.

실무 관점​

Android Studio가 주 IDE인 팀이라면 이 확장이 주 IDE를 대체하지는 않습니다.
Cursor나 VS Code에서 코드 리뷰나 에이전트 작업을 할 때 IntelliJ 수준의 분석을 빌려오는 용도가 맞습니다.
Gradle 프로젝트는 빌드 파일 기준으로 가져오기가 진행되므로 모듈 구조가 복잡하면 초기 인덱싱 시간을 봐야 합니다.
팀 단위로 도입하기 전에는 Ultimate 구독 비용과 평가판 종료 시점을 먼저 확인하는 것이 좋습니다.
기존 Java 확장을 끄는 설정까지 권장 파일에 함께 정리해 두면 온보딩 마찰이 줄어듭습니다.

Kotlin Toolchain 0.13 — 새 KMP 프로젝트는 kotlin new로 시작하기

2026년 10월 8일 · 약 3분
Way
Android Developer

안녕하세요, 한국투자증권에서 한투-한국투자증권 개발을 담당하고 있는 way입니다.
JetBrains가 공개한 Kotlin Toolchain 0.13에 대해 설명해드리겠습니다.

배경​

신규 Kotlin Multiplatform(KMP) 프로젝트를 시작할 때는 Gradle 설정 파일을 손으로 짜는 것부터 시작하는 경우가 많았습니다.
JDK나 Android SDK 같은 필수 도구가 갖춰져 있지 않으면, 새 노트북에서 프로젝트를 처음 열었을 때 동기화부터 실패하곤 했습니다.
이번 0.13부터 JetBrains는 신규 KMP 프로젝트에 이 툴체인을 쓰는 것을 공식 권장 경로로 제시했습니다.
자세한 내용은 Kotlin 블로그 원문에서 확인할 수 있습니다.

Kotlin Toolchain 살펴보기​

Kotlin Toolchain은 JVM·Android·iOS·멀티플랫폼·서버 앱을 하나의 CLI 진입점으로 만들고, 빌드하고, 테스트하고, 배포하는 도구입니다.
필수 도구들을 선언적 설정에 맞춰 자동으로 내려받아 주기 때문에 온보딩 과정의 마찰이 크게 줄어듭니다.

kotlin new: 대화형 프로젝트 생성​

0.13의 핵심은 kotlin new 명령입니다.
웹의 KMP Wizard처럼 앱 유형을 고르고 타깃 플랫폼을 선택하면 프로젝트가 생성됩니다.
기존 kotlin init도 같은 흐름으로 맞췄는데, 차이는 kotlin init이 현재 디렉터리에 바로 파일을 만든다는 점입니다.

# 새 프로젝트 생성 (대화형)
kotlin new

# 이미 설치돼 있다면 업데이트
kotlin update

Android 개발자 관점에서 달라진 부분​

  • Android SDK 자동 프로비저닝이 IDE까지 확장: 이전에는 kotlin build/kotlin run 때만 SDK가 자동 설치돼서, 빌드 전에 IDE로 먼저 열면 SDK 누락 오류가 났습니다. 이제 프로젝트 import 시점에도 누락된 SDK 컴포넌트를 자동으로 받아 줍니다.
  • namespace/applicationId 검증 강화: com.example.app 같은 샘플 ID로 실수로 배포 빌드를 만드는 실수를 막아 줍니다.
  • 다운로드 진행 표시: JDK, Android SDK, iOS 런타임, 컴파일러 다운로드가 CLI에 진행 바로 표시됩니다.

Swift Package Manager 의존성 지원​

Apple 타깃에서 SPM 패키지를 선언적으로 가져올 수 있게 됐습니다.
설정 파일에 저장소와 버전을 적으면 됩니다.

dependencies:
  - swiftPackage:
      repository: "https://github.com/firebase/firebase-ios-sdk.git"
      version: "12.17.0"
      products: ["FirebaseCore", "FirebaseFirestore", "FirebaseAnalytics"]

가져온 Objective-C API는 swiftPMImport 접두사로 네임스페이스가 붙어, Kotlin 코드에서 명시적으로 구분됩니다.
로컬 SPM 패키지는 localSwiftPackage 키로 연결할 수 있습니다.

빌드 속도: Kotlin/Native 컴파일러 캐시​

Kotlin/Native 재빌드가 빨라집니다.
컴파일된 네이티브 의존성을 빌드 간, 심지어 프로젝트 간에 캐시로 재사용하고, 프로젝트 코드는 파일 단위 캐시로 링크 시 바뀐 부분만 다시 컴파일합니다.
기존 settings.kotlin.compileIncrementally 설정을 그대로 쓰고, .klib 컴파일 자체는 전체로 수행됩니다.

그 외 변경 사항​

  • IDE 동기화 상태를 에디터에서 확인할 수 있게 됐습니다.
  • 멀티플랫폼 라이브러리 배포 시 Compose Resources와 SwiftPM 의존성 메타데이터가 아티팩트와 함께 게시되고, 서드파티 멀티플랫폼 라이브러리의 Compose Resources도 해석됩니다.
  • AI 에이전트 연동도 강화됐습니다. Compose Hot Reload MCP 서버와 Kotlin용 에이전트 스킬(npx skills add kotlin/kotlin-agent-skills)이 제공됩니다.
  • IDE 기능은 IntelliJ IDEA 2026.2.3 또는 Android Studio Rabbit 1(2026.2.1) 이상에서 최신 Kotlin Toolchain 플러그인과 함께 쓸 수 있습니다.

실무에서 주의할 점​

기존 Gradle 기반 프로젝트를 당장 마이그레이션해야 하는 것은 아닙니다.
JetBrains도 로드맵에서 Gradle 프로젝트의 공백을 먼저 메우는 데 집중하겠다고 밝혔습니다.
따라서 운영 중인 프로젝트는 기존 흐름을 유지하고, 신규 프로젝트나 사이드 프로젝트부터 적용해 보는 것이 안전합니다.

마치며​

새로 KMP를 시작한다면 kotlin new 한 번으로 Android·iOS 환경을 한 번에 맞추는 경험은 꽤 매력적입니다.
다음에 KMP 프로젝트를 시작할 일이 있으면 이 경로로 시작해 보시기 바랍니다.
